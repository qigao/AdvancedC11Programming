# Chapter 4: From Callable to Graph — Make Computation Itself Data

> **Graph adds one capability: it preserves computation relationships.**
>
> Plain C already computes.
>
> Graph lets the system see operator, input/output type, callable, edge relation, and ownership before execution, so construction can validate, normalize, rewrite, and compile.

**Terminology:** An IR, or intermediate representation, records knowledge as data for later checking or transformation. This chapter’s Graph is an IR for computation relationships. The control plane constructs, validates, and selects an execution strategy; the hot path processes the actual values.

---

## 1. Plain C Baseline

~~~c
long sum_even_squares(const int *xs, size_t n)
{
    long total = 0;

    for (size_t i = 0; i < n; ++i) {
        int x = xs[i];

        if ((x & 1) != 0)
            continue;

        total += (long)x * x;
    }

    return total;
}
~~~

The loop is good C.

Its only limitation is that after execution the structure `Filter → Map → Reduce` no longer exists as a program object.

If inspection, rewriting, or alternate backends are unnecessary, keep the loop.

---

## 2. C Representation of Node and Edge

Conceptual Node:

~~~c
typedef struct cflow_node {
    cflow_op op;

    cmeta_type_id input_type;
    cmeta_type_id output_type;

    const cmeta_callable *callable;
} cflow_node;
~~~

Edge:

~~~c
typedef struct cflow_edge {
    uint32_t from;
    uint32_t to;
} cflow_edge;
~~~

Graph:

~~~c
typedef struct cflow_graph {
    cflow_node *nodes;
    size_t node_count;

    cflow_edge *edges;
    size_t edge_count;
} cflow_graph;
~~~

Graph stores **program structure**, not live execution state.

---

## 3. Build Algorithm: Reject Type Errors Before Execution

~~~text
add_edge(graph, from, to):

    a = graph.nodes[from]
    b = graph.nodes[to]

    require a.output_type == b.input_type

    require no forbidden cycle
    require capacity available

    graph.edges.append(from, to)

    return OK
~~~

Connecting `Map<int,long>` to `Filter<User>` fails during construction with `TYPE_MISMATCH`, because `long != User`.

## 4. Graph Validity Judgment

**Notation:** Read `Γ ⊢ e : T` as “under the types and assumptions in environment Γ, e has T.” Statements above the rule’s horizontal line are premises; the statement below is the conclusion. These judgments specify conditions the Graph must satisfy.

~~~text
Γ ⊢ node_i : A -> B
Γ ⊢ node_j : B -> C
──────────────────────
Γ ⊢ edge(i,j) : valid
~~~

Whole graph:

~~~text
all nodes typed
∧ all edges type-compatible
∧ all required inputs connected
∧ terminal/output constraints satisfied
───────────────────────────────────────
Γ ⊢ Graph : Valid
~~~

Graph.Valid is a premise for later normalization, optimization, and proof.

---

## 5. Graph Does Not Own Runtime State

Do not put current values, threads, sockets, pending wakes, or mutable subscription state inside the immutable Graph.

| Object | Meaning |
|---|---|
| Graph | program |
| Execution state | runtime instance |

Live state belongs to frame, subscription, executor, source, or machine instance.

---

## 6. Build -> Normalize -> Compile

The following is a **compiler/artifact transformation pipeline**: each arrow means “produce the next artifact,” not runtime dataflow.

~~~text
Surface Graph
    ↓ validate
Primitive Graph
    ↓ normalize
Normalized Snapshot
    ↓ optimize
Optimized Graph
    ↓ compile
Plan / Direct
~~~

Pseudocode:

~~~text
compile(graph):

    require validate(graph)

    g1 = normalize(graph)
    g2 = optimize(g1)

    if direct_eligible(g2):
        return compile_direct(g2)

    return compile_plan(g2)
~~~

Graph is a control-plane IR, not necessarily a per-value lookup structure.

---

## 7. Failure Cases

### Type mismatch

If source output and destination input types are incompatible, return `TYPE_MISMATCH`.

### Capacity

If `node_count == max_nodes`, return `FULL`.

### Unsupported backend shape

If an operator cannot lower to the selected backend, return `UNSUPPORTED`.

Do not silently fall back to another runtime.

The remainder of the chapter uses the same canonical pipeline to examine Graph semantics, proof obligations, C implementation, and performance evidence.

## 8. Canonical Example: Connect the Three Callables from Chapter 3

Chapter 3 prepared:

~~~text
is_even : int -> bool
square  : int -> int
sum     : int × int -> int
~~~

The most direct Plain C version is still good:

~~~c
long total = 0;
bool has_value = false;

for (size_t i = 0; i < n; ++i) {
    int x = input[i];

    if (!is_even(x))
        continue;

    int y = square(x);

    if (!has_value) {
        total = y;
        has_value = true;
    } else {
        total = sum(total, y);
    }
}
~~~

There is nothing wrong with it.

If the program has only this one fixed pipeline, ordinary C may still be the best implementation.

Graph becomes useful not because “for-loops are not modern,” but because the system wants to know before execution:

~~~text
Which stages exist?
What are their input/output types?
Which stages can drop values?
Which stages change cardinality?
Which Callables have effects/properties?
Which connections are invalid?
May the graph be normalized / optimized / compiled?
~~~

So the same computation can first be saved as:

~~~text
Input<int>
    ↓
Filter<int>(is_even)
    ↓
Map<int,int>(square)
    ↓
Reduce<int>(sum)
~~~

The essence is:

> **promote relationships that existed only in control flow into data that can be inspected and transformed.**

### 8.1 Graph Is Knowledge Before It Is an Execution Result

Once the relationships are saved, we simultaneously have:

~~~text
topology
types
operators
callables
effects
properties
parameters
nested subgraphs
~~~

Later stages can use this knowledge before any input value arrives.

Construction does not “flow into” execution here; the two phases pay different costs:

| Phase | Responsibility |
|---|---|
| Graph construction | pay semantic/structural cost early |
| Graph execution | use already-admitted structure |

This is the **Pay Before Execution** pattern repeated throughout the book.

## 9. Semantic Contract: What Counts as a Valid Typed Graph?

Graph is not merely “an array of nodes.”

It needs at least four classes of contract.

### 9.1 Topology Well-Formedness

Every Edge must reference existing nodes/ports.

There must be no dangling endpoints, invalid ports, invalid nested-subgraph references, or impossible entry/tail combinations. This is structural validity.

### 9.2 Type Preservation Across Edges

If node A outputs `T` and node B expects `U`, then the edge `A -> B` must satisfy the semantic type-compatibility relation.

The connection is not valid merely because both payloads fit into `void *`.

For the canonical example:

~~~text
Input<int>
  -> Filter<int>
  -> Map<int,int>
  -> Reduce<int>
~~~

every type transition is part of admission, not a runtime cast guess.

### 9.3 Operator Contract

A Node does not only store a Callable.

The Operator itself has semantics:

~~~text
FILTER
    cardinality: 0..1
    output type: same as input

MAP
    cardinality: 1
    output type: callable return

FLAT_MAP
    cardinality: 0..N

REDUCE
    cardinality: N..1
~~~

So type derivation depends on **operator schema, callable signature, and input type**, rather than only on a function pointer.

### 9.4 Mutation / Snapshot Boundary

The owning IR may be mutated during Graph construction.

But once a Graph is handed to normalize, optimize, compile, verify, or execute, those stages must bind to a specific structural version.

If Graph structure changes behind their backs while Plan/Certificate continues using old assumptions, the trust boundary breaks.

Graph version is therefore not merely a debug counter.

It means:

> **which concrete IR snapshot does this downstream knowledge belong to?**

## 10. Lean / Proof Obligation: What Should the Graph Layer Prove First?

Chapter 4 does not need to prove all optimizer correctness at once.

The important work here is to establish Graph semantics.

### 10.1 Well-Formed Graph

Define a predicate:

~~~text
WellFormed(g)
~~~

covering at least:

- all node references valid;
- all edges reference valid ports;
- all edge types compatible;
- operator signatures admitted;
- nested graphs well formed;
- root/entry/exit valid.

Later theorems can share the premise:

~~~text
WellFormed(g) → ...
~~~

instead of reproving structural validity for every rewrite.

### 10.2 Graph Observable Semantics

We must answer:

> What does it mean for two Graphs to have the same semantics?

A minimal model can treat a pure synchronous Graph as:

~~~text
input sequence
    ↓
zero or more output values / terminal result
~~~

and define:

~~~text
observe(g, input)
~~~

Later normalize/optimize theorems can state:

~~~text
observe(surface, input)
=
observe(normalized, input)
~~~

or a more general ObsEq.

Without observable semantics, “the structure is simpler” does not imply “the program is equivalent.”

### 10.3 Normalize Preservation

The first theorem Normalize should own is not “it is faster.” It is:

~~~text
WellFormed(surface)
→
ObsEq(surface, normalize(surface))
~~~

This law matters because **Surface Graph** and **Primitive / Normalized Graph** may be different physical representations while still denoting the same semantic program.

### 10.4 Lean Does Not Prove Graph Storage Layout

The proof boundary remains explicit.

Lean does not pretend to prove that malloc always succeeds, that C struct ABI is identical on every compiler, that a cache layout is always faster, or that pointer lifetimes are always correct. Those are C implementation/toolchain/runtime evidence questions.

Formalization here proves IR meaning, type relations, structural invariants, and semantic preservation.

## 11. Current C Implementation: Graph Is a Real Owning IR

Using the current Salts snapshot `qigao/salts@ad389928b437c0612c1c60844fe53677f3ed27a6`:

the current CFlow Graph is not pseudocode.

It has explicit structure:

~~~text
cflow_graph
  owns subgraphs

cflow_subgraph
  owns nodes + edges

cflow_node
  stores op/callable/types/params/nested refs

cflow_edge
  stores typed topology coordinates
~~~

### 11.1 Edge Is an Explicit IR Row

In the snapshot, the public `cflow_edge` definition explicitly includes ports:

~~~c
typedef struct cflow_edge {
    cflow_node_id from;
    uint16_t from_port;
    cflow_node_id to;
    uint16_t to_port;
} cflow_edge;
~~~

Graph is therefore not limited to “the next operator in a linear array.”

Branch, Relation, and Subgraph can all use explicit topology in the same IR.

### 11.2 Node Stores Operator Semantics + Callable + Type Knowledge

A node's responsibility in the same snapshot includes operator, optional callable, optional fused callable chain, input/output type, nested-subgraph references, typed semantic parameters, and relation policy.

This creates the real connection to the previous three chapters. It is a **node-construction equation**, not an execution order:

**Typed Graph Node = CMeta Type + CMeta Callable + CFlow Operator Schema**

Graph is the integration point of earlier Meta capabilities, not a second type system.

### 11.3 Graph Is an Owning Handle, but Rows Are Read-Only Introspection

The API draws a strong boundary:

~~~text
Graph builder functions
    → supported mutation API

node/edge/subgraph rows
    → read-only introspection
~~~

Direct mutation of storage/capacity is not a public contract.

This resolves a common C-library ambiguity:

> a public struct does not mean every field is freely writable by callers.

### 11.4 Version Binds Downstream Artifacts to a Specific Graph State

The owning Graph contains a process-local nonzero mutation token.

Successful mutation / clone / initialization updates the version; destroy returns it to zero.

So optimizer trace, certificate, compiled plan, and runtime admission can explicitly answer:

> Am I still bound to the same unchanged Graph?

### 11.5 Normalize / Optimize Produce New Graphs

The current optimizer contract treats **src as an immutable normalized Graph** and **dst as a newly owned optimized Graph**.

rather than modifying the source while executing.

This is a strong engineering boundary: source meaning remains inspectable, the transformation result owns new IR, and verification can compare both sides.

It also fits naturally with formal preservation proofs.

## 12. Evidence: A Complete C-Side Verification Chain

Chapter 4 needs more than “Graph validate returned true.”

The current code already supports a fuller verification pipeline:

~~~text
validate surface
    ↓
normalize + validate
    ↓
normalize(normalized)
    ↓
check structural idempotence
    ↓
optimize + validate
    ↓
optimize(optimized)
    ↓
check structural idempotence
    ↓
execute surface / normalized / optimized
    ↓
compare observable output
    ↓
when eligible:
compile direct plan
    ↓
compare output again
~~~

This separates several kinds of evidence.

### 12.1 Structural Evidence

Check whether topology, node descriptors, relation schema, and fused chains match expectations.

### 12.2 Differential Semantic Evidence

Run the same input through surface, normalized, optimized, and compiled-plan forms.

If observable results differ, the transformation chain has a real regression.

### 12.3 Formal Evidence

Lean proves that **a class of transformation preserves observable semantics under explicit premises**.

### 12.4 Runtime Evidence

C differential tests then check whether the real implementation conforms to the formalized transformation contract. Together they are stronger than either one alone.

## 13. Performance Evidence: Graph Must Account for Its Own Cost

Graph is control-plane IR, but that does not mean Graph traversal cost can be ignored.

The current CFlow implementation has dedicated graph-path benchmarks across operator counts 1, 16, 256, and 4096.

and compares different successor representations / traversal strategies.

This gives the book a useful rule:

> **If an abstraction may enter the hot path, measure it; if it should not enter the hot path, show how to compile/lower it away.**

So Chapter 4 does not need to claim “Graph is zero-cost.”

A more accurate statement is: **Graph is analyzable control-plane IR, and later execution paths should avoid repeated Graph interpretation when possible.**

This naturally leads to Chapter 7's Plan / Direct / AOT.

## 14. What We Learned

Chapter 4 completes a **design progression**, not a runtime pipeline:

**Typed Data → Typed Behavior → Typed Program Structure**.

The value of Graph is not replacing the for-loop.

It gives us:

1. **Topology becomes data.**
2. **Types survive across computation boundaries.**
3. **Operator semantics become explicit.**
4. **Construction/admission can fail before execution.**
5. **Normalize / Optimize / Compile can work on immutable snapshots.**
6. **Lean finally has a program structure on which to state preservation theorems.**
7. **C verification can compare surface/normalized/optimized/compiled observations.**
8. **Execution can later remove Graph knowledge instead of repeatedly interpreting it.**

The canonical example has now moved from three independent Callables

to:

~~~text
Source<int>
    ↓
Filter(is_even)
    ↓
Map(square)
    ↓
Reduce(sum)
~~~

Chapter 5 does not invent another data-processing runtime.

It asks only:

> **If Graph already expresses this pipeline, can ordinary C users get a lighter, more natural façade for constructing it?**

The answer is Stream.

**Summary: Graph Turns Behavior into Program Structure**

The previous chapter **described/projected a Function into a composable Callable**. This chapter then **materializes relationships among Callables as Graph**.

That is a semantic-design progression, not a runtime call chain. Graph stores relationships among behaviors; it is not “call Callable, then call Graph.”

For the first time we can **see the whole computation before execution** and apply Validation, Type Propagation, Inference, Lowering, Optimization, and Compilation.

This is where CFlow truly appears.

Once Graph exists, it becomes clear that it is especially good at expressing Filter, Map, FlatMap, Reduce, and Collect data transformations.

That naturally raises the next question:

> **If Graph already expresses data transformation well, can we place a Java-Stream-like surface on top so complex data processing can be written in C declaratively and with types?**

The next chapter continues from there: **from Graph to Stream — why an advanced data-transformation API can remain a thin Graph façade instead of becoming another heavyweight runtime.**
