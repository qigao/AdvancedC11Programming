# Chapter 4: From Callables to Graphs: Representation and Type Checking

CMeta describes individual function types and calls. Composing functions also requires a representation of which output feeds which input. A CFlow graph records those connections and checks types, capacity, and topology before execution. Starting with a sum-of-even-squares loop, this chapter builds nodes and edges, states rules for valid connections, and separates graph construction and normalization from execution state.

**Terminology:** An IR, or intermediate representation, records knowledge as data for later checking or transformation. This chapter’s Graph is an IR for computation relationships. The control plane constructs, validates, and selects an execution strategy; the hot path processes the actual values.

## 1. Plain C Baseline: Fix One Type Chain First

Before introducing Graph, define the three ordinary C functions used throughout Chapters 4–7:

~~~c
#include <stdbool.h>
#include <stddef.h>

static bool is_even(int x)
{
    return x % 2 == 0;
}

static long square(int x)
{
    return (long)x * (long)x;
}

static long sum(long a, long b)
{
    return a + b;
}

long sum_even_squares(const int *xs, size_t n)
{
    long total = 0;

    for (size_t i = 0; i < n; ++i) {
        int x = xs[i];

        if (!is_even(x))
            continue;

        total = sum(total, square(x));
    }

    return total;
}
~~~

The same signatures remain canonical in the following chapters:

~~~text
is_even : int -> bool
square  : int -> long
sum     : (long, long) -> long
~~~

The example assumes each square and accumulated sum is representable as `long`; Graph does not remove that arithmetic precondition.

The loop is already good C. If the system needs only this fixed computation and no inspection, rewriting, or alternate execution backend, keep it. Graph becomes useful when the relationship `Filter → Map → Reduce`, previously implicit in control flow, must become inspectable data before execution.

## 2. C Representation of Node and Edge

Conceptual Node:

~~~c
typedef struct cflow_node {
    cflow_op op;

    cmeta_type_id input_type;
    cmeta_type_id output_type;

    const cmeta_callable *callable;
} cflow_node;
~~~

Edge:

~~~c
typedef struct cflow_edge {
    uint32_t from;
    uint32_t to;
} cflow_edge;
~~~

Graph:

~~~c
typedef struct cflow_graph {
    cflow_node *nodes;
    size_t node_count;

    cflow_edge *edges;
    size_t edge_count;
} cflow_graph;
~~~

Graph stores **program structure**, not live execution state.

## 3. Build Algorithm: Reject Type Errors Before Execution

~~~text
add_edge(graph, from, to):

    a = graph.nodes[from]
    b = graph.nodes[to]

    require a.output_type == b.input_type

    require no forbidden cycle
    require capacity available

    graph.edges.append(from, to)

    return OK
~~~

Connecting `Map<int,long>` to `Filter<User>` fails during construction with `TYPE_MISMATCH`, because `long != User`.

## 4. Graph Validity Judgment

**Notation:** Read `Γ ⊢ e : T` as “under the types and assumptions in environment Γ, e has T.” Statements above the rule’s horizontal line are premises; the statement below is the conclusion. These judgments specify conditions the Graph must satisfy.

~~~text
Γ ⊢ node_i : A -> B
Γ ⊢ node_j : B -> C
──────────────────────
Γ ⊢ edge(i,j) : valid
~~~

Whole graph:

~~~text
all nodes typed
∧ all edges type-compatible
∧ all required inputs connected
∧ terminal/output constraints satisfied
───────────────────────────────────────
Γ ⊢ Graph : Valid
~~~

Graph.Valid is a premise for later normalization, optimization, and proof.

## 5. Graph Does Not Own Runtime State

Do not put current values, threads, sockets, pending wakes, or mutable subscription state inside the immutable Graph.

| Object | Meaning |
|---|---|
| Graph | program |
| Execution state | runtime instance |

Live state belongs to frame, subscription, executor, source, or machine instance.

## 6. Build -> Normalize -> Compile

The following is a **compiler/artifact transformation pipeline**: each arrow means “produce the next artifact,” not runtime dataflow.

~~~text
Surface Graph
    ↓ validate
Primitive Graph
    ↓ normalize
Normalized Snapshot
    ↓ optimize
Optimized Graph
    ↓ compile
Plan / Direct
~~~

Pseudocode:

~~~text
compile(graph):

    require validate(graph)

    g1 = normalize(graph)
    g2 = optimize(g1)

    if direct_eligible(g2):
        return compile_direct(g2)

    return compile_plan(g2)
~~~

Graph is a control-plane IR, not necessarily a per-value lookup structure.

## 7. Failure Cases

### Type mismatch

If source output and destination input types are incompatible, return `TYPE_MISMATCH`.

### Capacity

If `node_count == max_nodes`, return `FULL`.

### Unsupported backend shape

If an operator cannot lower to the selected backend, return `UNSUPPORTED`. Do not silently fall back to another runtime. The remainder of the chapter uses the same canonical pipeline to examine Graph semantics, proof obligations, C implementation, and performance evidence.

## 8. Save the Plain C Baseline as One Typed Graph

Section 1 fixed the actual types of the three callables, so Graph does not reinvent them:

~~~text
is_even : int -> bool
square  : int -> long
sum     : (long, long) -> long
~~~

Construction records the relationships between those calls:

~~~text
Input<int>
    ↓
Filter<int>(is_even)
    ↓
Map<int,long>(square)
    ↓
Reduce<long>(sum)
~~~

The type transition is now explicit: Filter preserves `int`, Map converts `int` to `long`, and Reduce accumulates in the `long` domain. A connection from `Map<int,long>` to `Filter<User>`, or a Reduce supplied with an `(int,int)->int` reducer, can be rejected during construction.

Graph does not add a second computation semantics. It adds **knowledge available before execution**:

| Fact stored by Graph | What later stages can do |
|---|---|
| topology | validate connections and normalize structure |
| input/output types | reject incompatible edges during construction |
| operators | select legal lowering / execution shapes |
| callables | bind concrete functions and ABI |
| effects/properties | select optimization candidates or block unsafe rewrites |

Graph construction pays semantic and structural costs early; execution consumes an already-admitted structure. Normalize, optimize, Plan, and Direct all build on this same typed program object.

## 9. Semantic Contract: What Counts as a Valid Typed Graph?

Graph is not merely “an array of nodes.” It needs at least four classes of contract.

### 9.1 Topology Well-Formedness

Every Edge must reference existing nodes/ports. There must be no dangling endpoints, invalid ports, invalid nested-subgraph references, or impossible entry/tail combinations. This is structural validity.

### 9.2 Type Preservation Across Edges

If node A outputs `T` and node B expects `U`, then the edge `A -> B` must satisfy the semantic type-compatibility relation. The connection is not valid merely because both payloads fit into `void *`. For the canonical example:

~~~text
Input<int>
  -> Filter<int>
  -> Map<int,long>
  -> Reduce<long>
~~~

every type transition is part of admission, not a runtime cast guess.

### 9.3 Operator Contract

A Node does not only store a Callable. The Operator itself has semantics:

~~~text
FILTER
    cardinality: 0..1
    output type: same as input

MAP
    cardinality: 1
    output type: callable return

FLAT_MAP
    cardinality: 0..N

REDUCE
    cardinality: N..1
~~~

So type derivation depends on **operator schema, callable signature, and input type**, rather than only on a function pointer.

### 9.4 Mutation / Snapshot Boundary

The owning IR may be mutated during Graph construction. But once a Graph is handed to normalize, optimize, compile, verify, or execute, those stages must bind to a specific structural version. If Graph structure changes behind their backs while Plan/Certificate continues using old assumptions, the trust boundary breaks. Graph version is therefore not merely a debug counter. It means:

which concrete IR snapshot does this downstream knowledge belong to?

## 10. Lean / Proof Obligation: What Should the Graph Layer Prove First?

Chapter 4 does not need to prove all optimizer correctness at once. The important work here is to establish Graph semantics.

### 10.1 Well-Formed Graph

Define a predicate:

~~~text
WellFormed(g)
~~~

covering at least:

- all node references valid;
- all edges reference valid ports;
- all edge types compatible;
- operator signatures admitted;
- nested graphs well formed;
- root/entry/exit valid.

Later theorems can share the premise:

~~~text
WellFormed(g) → ...
~~~

instead of reproving structural validity for every rewrite.

### 10.2 Graph Observable Semantics

We must answer:

> What does it mean for two Graphs to have the same semantics?

A minimal model can treat a pure synchronous Graph as:

~~~text
input sequence
    ↓
zero or more output values / terminal result
~~~

and define:

~~~text
observe(g, input)
~~~

Later normalize/optimize theorems can state:

~~~text
observe(surface, input)
=
observe(normalized, input)
~~~

or a more general ObsEq. Without observable semantics, “the structure is simpler” does not imply “the program is equivalent.”

### 10.3 Normalize Preservation

The first theorem Normalize should own is not “it is faster.” It is:

~~~text
WellFormed(surface)
→
ObsEq(surface, normalize(surface))
~~~

This law matters because **Surface Graph** and **Primitive / Normalized Graph** may be different physical representations while still denoting the same semantic program.

### 10.4 Lean Does Not Prove Graph Storage Layout

The proof boundary remains explicit. Lean does not pretend to prove that malloc always succeeds, that C struct ABI is identical on every compiler, that a cache layout is always faster, or that pointer lifetimes are always correct. Those are C implementation/toolchain/runtime evidence questions. Formalization here proves IR meaning, type relations, structural invariants, and semantic preservation.

## 11. Current C Implementation: Graph Is a Real Owning IR

Using the current Salts snapshot `qigao/salts@ad389928b437c0612c1c60844fe53677f3ed27a6`:

the current CFlow Graph is not pseudocode. It has explicit structure:

~~~text
cflow_graph
  owns subgraphs

cflow_subgraph
  owns nodes + edges

cflow_node
  stores op/callable/types/params/nested refs

cflow_edge
  stores typed topology coordinates
~~~

### 11.1 Edge Is an Explicit IR Row

In the snapshot, the public `cflow_edge` definition explicitly includes ports:

~~~c
typedef struct cflow_edge {
    cflow_node_id from;
    uint16_t from_port;
    cflow_node_id to;
    uint16_t to_port;
} cflow_edge;
~~~

Graph is therefore not limited to “the next operator in a linear array.” Branch, Relation, and Subgraph can all use explicit topology in the same IR.

### 11.2 Node Stores Operator Semantics + Callable + Type Knowledge

A node's responsibility in the same snapshot includes operator, optional callable, optional fused callable chain, input/output type, nested-subgraph references, typed semantic parameters, and relation policy. This creates the real connection to the previous three chapters. It is a **node-construction equation**, not an execution order:

**Typed Graph Node = CMeta Type + CMeta Callable + CFlow Operator Schema**

Graph is the integration point of earlier Meta capabilities, not a second type system.

### 11.3 Graph Is an Owning Handle, but Rows Are Read-Only Introspection

The API draws a strong boundary:

~~~text
Graph builder functions
    → supported mutation API

node/edge/subgraph rows
    → read-only introspection
~~~

Direct mutation of storage/capacity is not a public contract. This resolves a common C-library ambiguity:

> a public struct does not mean every field is freely writable by callers.

### 11.4 Version Binds Downstream Artifacts to a Specific Graph State

The owning Graph contains a process-local nonzero mutation token. Successful mutation / clone / initialization updates the version; destroy returns it to zero. So optimizer trace, certificate, compiled plan, and runtime admission can explicitly answer:

> Am I still bound to the same unchanged Graph?

### 11.5 Normalize / Optimize Produce New Graphs

The current optimizer contract treats **src as an immutable normalized Graph** and **dst as a newly owned optimized Graph**, rather than modifying the source while executing. This is a strong engineering boundary: source meaning remains inspectable, the transformation result owns new IR, and verification can compare both sides. It also fits naturally with formal preservation proofs.

## 12. Evidence: A Complete C-Side Verification Chain

Chapter 4 needs more than “Graph validate returned true.” The current code already supports a fuller verification pipeline:

~~~text
validate surface
    ↓
normalize + validate
    ↓
normalize(normalized)
    ↓
check structural idempotence
    ↓
optimize + validate
    ↓
optimize(optimized)
    ↓
check structural idempotence
    ↓
execute surface / normalized / optimized
    ↓
compare observable output
    ↓
when eligible:
compile direct plan
    ↓
compare output again
~~~

This separates several kinds of evidence.

### 12.1 Structural Evidence

Check whether topology, node descriptors, relation schema, and fused chains match expectations.

### 12.2 Differential Semantic Evidence

Run the same input through surface, normalized, optimized, and compiled-plan forms. If observable results differ, the transformation chain has a real regression.

### 12.3 Formal Evidence

Lean proves that **a class of transformation preserves observable semantics under explicit premises**.

### 12.4 Runtime Evidence

C differential tests then check whether the real implementation conforms to the formalized transformation contract. Together they are stronger than either one alone.

## 13. Performance Evidence: Graph Must Account for Its Own Cost

Graph is control-plane IR, but that does not mean Graph traversal cost can be ignored. The current CFlow implementation has dedicated graph-path benchmarks across operator counts 1, 16, 256, and 4096, comparing different successor representations and traversal strategies. This gives the book a useful rule:

If an abstraction may enter the hot path, measure it; if it should not enter the hot path, show how to compile/lower it away. So Chapter 4 does not need to claim “Graph is zero-cost.” A more accurate statement is: **Graph is analyzable control-plane IR, and later execution paths should avoid repeated Graph interpretation when possible.** This naturally leads to Chapter 7's Plan / Direct / AOT.

## 14. Summary

A graph records operations, types, and connections so incompatible types, missing inputs, and invalid topology can be rejected during construction. CMeta callables supply the parameter and result contracts used to check connections; live values, waiting state, and resources belong to separate execution instances. Immutable snapshots provide stable input for normalization, optimization, and plan compilation. Transformations must preserve specified observations, while execution cost is measured against an ordinary loop. Stream interfaces simplify construction on top of these rules.
