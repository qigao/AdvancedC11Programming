# Chapter 4: From Callables to Graphs: Representation and Type Checking

Calling three functions in sequence does not require a graph. A graph becomes useful when the program must inspect connections, select a supported execution form, or rewrite a composition before it runs. CFlow uses CMeta type descriptions and callables to represent these facts. The even-square sum provides a concrete example of what a graph stores and what its validation can establish.

## 1. Extracting a Computation from a Loop

This ordinary C function fragment requires `<stddef.h>`. Assume `n <= 1000`, inputs in `[-100, 100]`, and valid array storage whenever the input is nonempty. Each square is at most `10000` and the total at most ten million, within the range C11 guarantees for `long`.

~~~c
long sum_even_squares(const int *xs, size_t n)
{
    long total = 0;
    for (size_t i = 0; i < n; ++i) {
        int x = xs[i];
        if (x % 2 != 0)
            continue;
        total += (long)x * x;
    }
    return total;
}
~~~

Input `{1, 2, 3, 4, 5, 6}` produces `56`; empty input produces zero. Filtering retains even inputs, mapping converts each retained `int` to a `long` square, and reduction combines the squares.

| Operation | Call signature | Flow type and count |
|---|---|---|
| Filter | `int -> bool` | Preserves `int`; may reduce the count |
| Map | `int -> long` | Produces one `long` per retained input |
| Seeded Reduce | `(long, long) -> long` | Starts with zero and produces one `long` |

A seeded reduction explains this loop. Chapter 5's unseeded Reduce has no result for empty input, which requires an explicit decision by the consumer. A reducer taking `int` cannot follow a `long` output merely because the example values happen to be small.

## 2. Nodes, Ports, and Edges

An **intermediate representation**, or IR, stores program facts needed by later analysis or transformation. Graph is an IR of computation relationships. Nodes record operators, types, and calls; edges connect their ports. A **port** is a numbered input or output position, needed to distinguish connections on multi-input operators.

The pinned implementation represents an edge as:

~~~c
typedef struct cflow_edge {
    cflow_node_id from;
    uint16_t from_port;
    cflow_node_id to;
    uint16_t to_port;
} cflow_edge;
~~~

The following teaching representation is not an SDK layout. It retains only port types; real nodes also carry operator schemas, callables, and subgraph information.

~~~c
typedef struct book_port {
    const cmeta_type_desc *type;
} book_port;

typedef struct book_node_view {
    const book_port *inputs;
    size_t input_count;
    const book_port *outputs;
    size_t output_count;
} book_node_view;
~~~

Node IDs locate objects within the graph. CMeta type identities establish semantic compatibility. Descriptor-address equality is insufficient across translation units; the structural identity described in Chapter 2 supplies the relevant comparison.

## 3. Checking Bounds Before Reading Types

This connection-checking pseudocode uses `type_equal` for semantic type comparison. Its rejection categories are explanatory rather than promised API status names.

~~~text
connect(graph, from, out_port, to, in_port):
    reject if either node id is outside graph
    a = graph.nodes[from]
    b = graph.nodes[to]
    reject if out_port or in_port is outside its node
    reject if the destination port is already occupied
    reject if not type_equal(a.outputs[out_port], b.inputs[in_port])
    reject if this edge violates the operator's topology rules
    reserve storage; on failure leave the logical graph unchanged
    append the edge and update the graph version
~~~

The order matters. Reading `graph.nodes[from]` before checking `from` can already access outside the array. Type comparison similarly requires existing ports and valid descriptors.

Valid individual edges do not establish validity of the whole graph. During construction, required inputs may remain unconnected. Before normalization or compilation, validation must also establish complete required inputs, legal roots and terminals, valid nested-subgraph references, and topology allowed by each operator. Ordinary data edges cannot replace the waiting and resumption protocol described in Chapter 9.

## 4. Deriving Type Preservation

The judgment `Γ ⊢ e : T` means that `e` has type `T` under the declarations and assumptions in environment `Γ`. Composition has the following rule:

~~~text
Γ ⊢ f : A -> B       Γ ⊢ g : B -> C
-----------------------------------
Γ ⊢ g ∘ f : A -> C
~~~

Here `g ∘ f` applies `f` first. If `f` accepts a valid `A` and successfully produces a valid `B`, it supplies the type required by `g`. If `g` also succeeds, the result has type `C`. Induction over a finite linear pipeline shows that each successfully transferred value has the next node's input type.

This argument assumes descriptors accurately describe the C calls, storage is valid, and implementations obey their declarations. Type compatibility does not prove that `square` avoids overflow or that a borrowed pointer remains live. Numeric domains and lifetime contracts remain necessary.

Filter additionally changes the count: a true predicate passes the original value and a false predicate passes nothing. Thus retained values keep their type and relative order. Reduction needs closure of the accumulator type: each `long × long -> long` result can serve as the next accumulator. Permission to reorder reductions requires further laws, examined in Chapter 7.

## 5. Graphs and Running Instances

Graphs are mutable during construction. Validation, transformation, and compilation require the immutability specified by each borrowing API. The pinned implementation uses nonzero version tokens for initialized, cloned, and successfully mutated graph states; destruction clears the version. A version token helps reject stale evidence but does not synchronize concurrent access.

| Object | Stored state | Lifetime obligation |
|---|---|---|
| Graph | Nodes, edges, subgraphs, and construction parameters | Use graph construction/destruction APIs; keep borrowed descriptions valid |
| Plan | Resolved execution steps and call information | Use plan compilation/destruction APIs |
| Frame or Subscription | Current values, demand, waits, and cleanup state | Maintain separately for each execution |
| Executor | Queuing, running, and shutdown state | Fulfill cleanup obligations for accepted tasks |

A computation description can support multiple executions without sharing unsynchronized mutable counters. For example, a Take bound belongs to the graph; the count already consumed belongs to one execution.

## 6. Compiling a Valid Graph

**Normalization** converts different legal surface forms into the primitive representation expected by later stages. It changes program representation without consuming input values. Backend selection is explicit in this pseudocode:

~~~text
compile_surface(surface, requested_backend):
    require valid(surface)
    normalized = normalize_into_separate_destination(surface)
    require valid(normalized)
    optimized = apply_authorized_rewrites(normalized)
    require supported(optimized, requested_backend)
    return compile_for(optimized, requested_backend)
~~~

A valid graph can exceed a backend's capabilities. A Direct request containing Reduce is unsupported; a caller may separately choose Plan. Allocation failure is a different condition from unsupported execution. Real Graph storage follows its documented management rules; a fixed teaching array's `FULL` rule is not a universal Graph contract.

The pinned `cflow_graph_create_seeded_reduce_node` creates a homogeneous seeded reduction and owns a typed copy of the seed. It can express the first section's initial-value semantics, with a valid subgraph, matching reducer, and correct connections. Creating a low-level node does not establish validity of a complete graph.

## 7. Verifying Graph Validation

Test failures at their actual layer: invalid node and port IDs before dereferencing, a `Map<int,long>` connected to `Filter<User>`, and whole-graph errors such as missing inputs or invalid subgraphs. Compare a valid graph with the ordinary loop on Chapter 5's inputs, and test empty input separately.

Transformation checks must retain the source and compare observations before and after transformation. Mutating the source invalidates evidence tied to its old version; destroying and reinitializing it must not revive old evidence. Chapter 7 develops execution certificates.

The actual structures and APIs come from pinned [graph.h](https://github.com/qigao/salts/blob/a650262031e9b3e5f11a227a7911a75db9ae1fb8/cflow/include/cflow/graph.h). The type argument is a hand derivation for the stated linear composition, not an automatic proof of arbitrary graphs or C functions.

## 8. Summary

A graph records operators, types, and connections that were implicit in a loop. Valid connections require existing endpoints, legal ports, semantic type compatibility, and permitted topology. Execution additionally relies on value domains, storage validity, and lifetimes. Separating the description from execution state allows normalization and compilation to resolve structure in advance while each run maintains its own values, counters, and resources.
