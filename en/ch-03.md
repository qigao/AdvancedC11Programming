# Chapter 3: Function Reflection: Descriptors, Call Adapters, and Parameter Binding

A C function type determines how to call the function. Parameter direction, borrowed lifetimes, and result-cleanup obligations often remain in separate documentation. CMeta records these facts in function descriptors so that binders, generators, and dynamic modules can check them. This chapter starts with a direct call, expands a call adapter into ordinary C, and derives the conditions under which parameter binding preserves that call.

## 1. Ordinary Functions and Function Pointers

This fragment defines `square` and calls it through a pointer of the same type. The square of `7` is representable by `long`, so `y` is `49`. A version accepting arbitrary `int` inputs would also have to establish that the multiplication fits in `long`.

~~~c
long square(int x)
{
    return (long)x * x;
}

long (*fn)(int) = square;
long y = fn(7);
~~~

A function pointer is sufficient when the caller only needs to store and invoke this address. A descriptor becomes useful when several consumers need the same parameter directions, nullability, ownership, or effect information. It records these facts without requiring every caller to use an indirect invocation mechanism.

## 2. Generating a Declaration and Its Descriptors

`FunctionDecl` generates an ordinary prototype, an immutable translation-unit-local FunctionDesc, a FunctionAbi sidecar, and inline metadata accessors from one parameter list. An ordinary C function still provides the implementation. Calls to this `add` require a sum representable by `int`.

~~~c
FunctionDecl(value, int, add,
    (int, left, CMETA_PARAM_IN),
    (int, right, CMETA_PARAM_IN));

int add(int left, int right)
{
    return left + right;
}
~~~

The accessors retrieve the semantic and ABI descriptions:

~~~c
const cmeta_function_desc *f = FunctionMeta(add);
const cmeta_function_abi_desc *abi = FunctionAbi(add);
~~~

The declaration does not generate a universal dynamic invoker. Direct execution remains an ordinary call:

~~~c
int result = add(2, 3);
~~~

## 3. FunctionDesc and FunctionAbi

FunctionDesc records the semantic contract: names and types, parameter flags, effects, properties, and result ownership and nullability. FunctionAbi records native carrier categories at the call boundary.

A **sidecar** is associated metadata with a responsibility separate from the main descriptor. An ABI **carrier** is the native category used to pass a value, such as a scalar, object pointer, or aggregate. It describes representation at a local call boundary rather than the domain meaning of the parameter.

| Description | Recorded facts | Consumer checks |
|---|---|---|
| FunctionDesc | Parameter, result, and behavior contracts | Types, directions, ownership, and semantic conditions |
| FunctionAbi | Native return and parameter carriers | Compatibility with the selected invocation mechanism |

These descriptions support validation and code generation. Execution additionally requires a concrete target and an entry point that matches it.

## 4. Parameter Rows as Shared Facts

A parameter row has three, four, or five entries. The longer forms add an explicit type descriptor and then a native carrier. Omitted entries follow the declaration rules; consumers cannot invent different interpretations.

| Form | Explicit information |
|---|---|
| `(type, name, flags)` | C type, parameter name, and semantic flags |
| `(type, name, flags, descriptor)` | Also the type descriptor |
| `(type, name, flags, descriptor, abi_carrier)` | Also the native carrier |

For example:

~~~c
(int, value,
 CMETA_PARAM_IN,
 &cmeta_type_int,
 CMETA_ABI_SCALAR)
~~~

The same row can contribute to a prototype, ParamDesc, FunctionAbi, TinyMock declaration, Plugin export, or binding adapter. The tuple projections from Chapter 2 select entries consistently; each generator then checks the conditions required by its output.

## 5. Result Ownership and Cleanup

This declaration records a borrowed character pointer returned by `find_name`. Consumers can use that contract when deciding who must clean up the result.

~~~c
FunctionDeclAsAbiResult(
    value,
    char *,
    &cmeta_type_char_ptr,
    CMETA_ABI_OBJECT_POINTER,
    CMETA_RESULT_BORROWED,
    find_name,
    (int, id, CMETA_PARAM_IN,
     &cmeta_type_int, CMETA_ABI_SCALAR));
~~~

| Flag | Result contract |
|---|---|
| VALUE | A native value result |
| BORROWED | No transfer of ownership of the pointed-to resource |
| SHARED | A release obligation under the admitted sharing protocol |
| OWNED | Ownership transfer with the corresponding destruction obligation |

The descriptor does not perform cleanup or track whether a particular local object has moved or been destroyed. The generator or runtime owner must place cleanup on the appropriate success and failure paths.

## 6. Exact Call Adapters and Their Correctness

A **thunk**, as used here, is a small wrapper for a known function. It accepts argument-storage addresses through a uniform interface, reads values using their declared C types, calls the function, and stores the result. **Exact** means the generated call follows the concrete native signature.

**Type erasure** hides concrete types behind a uniform interface. The entry point below uses `void *`, but its generated body still knows the real types. Casting an arbitrary pointer does not establish that it addresses a suitable object. In other contexts, thunk may mean a wrapper for deferred computation; here it means a call adapter.

A consumer explicitly requests an erased exact adapter:

~~~c
#include <cmeta/invoke_decl.h>

FunctionInvokeDecl(value, int, increment,
    (int, input, CMETA_PARAM_IN));

int increment(int input)
{
    return input + 1;
}
~~~

The following fragment supplies live `int` objects:

~~~c
int input = 4;
int output = 0;
void *params[] = { &input };

bool ok =
    FunctionInvoke(increment)(
        &output,
        params,
        1);
~~~

The adapter checks the argument count and required pointers, reads `4`, invokes `increment`, and writes `5`. The caller must establish storage type, alignment, and lifetime. See the pinned [invoke_decl.h](https://github.com/qigao/salts/blob/a650262031e9b3e5f11a227a7911a75db9ae1fb8/cmeta/include/cmeta/invoke_decl.h). `FunctionDecl` generates descriptions; `FunctionInvokeDecl` additionally generates the adapter.

The following teaching expansion uses the preceding `increment` and requires `<stdbool.h>` and `<stddef.h>`. The actual macro emits different names and additional static checks.

~~~c
static bool increment_adapter(
    void *result, void *const *args, size_t count)
{
    if (count != 1 || args == NULL)
        return false;
    if (args[0] == NULL || result == NULL)
        return false;

    *(int *)result = increment(*(int *)args[0]);
    return true;
}
~~~

Its algorithm separates runtime checks from caller obligations:

~~~text
adapt_increment(result, args, count):
    reject wrong count or missing argument array
    reject missing argument or result storage
    read x from the int object at args[0]
    compute y = increment(x)
    write y to the int object at result
    return true
~~~

Assume `args` addresses at least one valid pointer element, `args[0]` addresses a live `int` containing `x`, and `result` addresses a writable live `int`. Storage is aligned, accesses have no data race, and `x < INT_MAX`. With count one and the required addresses present, neither rejection branch returns. The assignment reads `x`, calls `increment` once, stores the representable result `x + 1`, and returns true. Input and result may be the same object: the read and call finish before the assignment stores the result.

If a count or required-pointer check fails, execution returns before calling the target or writing the result. A dangling, misaligned, or incorrectly typed non-null pointer falls outside this guarantee. This hand derivation establishes the shown control flow, not a general runtime type proof for `void *`.

## 7. The Receiver Remains an Ordinary Parameter

A **receiver** is the object on which an operation acts. Here it is parameter zero of an ordinary C function:

~~~c
int list_add(IntList *self, int value);
~~~

`CMETA_PARAM_RECEIVER` records that role alongside direction and borrowing flags. It does not change the calling convention, allocate an object, or create a virtual function table. An optional syntax front end may translate `obj.add(x)` into `List_add(&obj, x)` using the declared receiver type and function; ordinary C callers can invoke the latter directly.

## 8. Parameter Projection After Receiver Binding

Binding `self` changes the exposed signature from `(self, value) -> result` to `(value) -> result`. The projected description must preserve the result type, ownership and nullability, effects, properties, and the remaining parameters' names, types, and flags.

The function module provides the receiver-projection check:

~~~c
cmeta_function_receiver_projection_valid(
    source,
    projected);
~~~

The general projection check relates the source ABI, projected ABI, and bound positions:

~~~c
cmeta_function_projection_valid(
    source_abi,
    projected_abi,
    bound,
    count);
~~~

These rules belong to the function description. Receiver lookup finds the original description rather than maintaining a second definition of its semantics.

## 9. Operation Sets Index Functions by Name

An operation row contains a name and a FunctionAbi pointer:

~~~c
typedef struct cmeta_receiver_operation {
    const char *name;
    const cmeta_function_abi_desc *abi;
} cmeta_receiver_operation;
~~~

An operation set performs lookup in the context of a receiver type and, where needed, a generic owner. The FunctionAbi leads to the existing FunctionDesc. Finding a name supplies descriptive information; an executable capability must still match the original function and the proposed binding.

## 10. Binding Fixes Some Arguments in Advance

**Binding** saves some arguments in a callable while leaving the others for a later call. Binding `a` to `10` in `add(a, b)` exposes a callable taking only `b`. The following declarations illustrate separate layers; they are not intended to be compiled together with the earlier `add` declaration as one standalone source file.

~~~c
int add(int a, int b);
~~~

First record the types, carriers, and ownership:

~~~c
FunctionDeclAsAbiResult(
    value,
    int,
    &cmeta_type_int,
    CMETA_ABI_SCALAR,
    CMETA_RESULT_VALUE,
    add,
    (int, a, CMETA_PARAM_IN,
     &cmeta_type_int, CMETA_ABI_SCALAR),
    (int, b, CMETA_PARAM_IN,
     &cmeta_type_int, CMETA_ABI_SCALAR));
~~~

Then declare the projection shape. `a` is captured and `b` remains a call argument; a subsequently constructed callable supplies the captured value.

~~~c
FunctionBindDeclAsAbiResult(
    value,
    int,
    &cmeta_type_int,
    CMETA_ABI_SCALAR,
    CMETA_RESULT_VALUE,
    plus10,
    add,
    CMETA_SIG_U_I_I,
    (value,
        (int, a, CMETA_PARAM_IN,
         &cmeta_type_int, CMETA_ABI_SCALAR)),
    (arg,
        (int, b, CMETA_PARAM_IN,
         &cmeta_type_int, CMETA_ABI_SCALAR)));
~~~

| Mode | Meaning |
|---|---|
| `arg` | Remains an argument to the projected call |
| `value` | Saves a registered trivial scalar snapshot |
| `borrow` | Saves an explicitly borrowed object pointer |

Receiver binding follows the same rules and retains the RECEIVER flag on the borrowed parameter. Projection checks establish agreement between parameter positions, types, and the remaining signature.

**Reconstructing arguments.** Let the original function have n parameters, with a binding table identifying saved positions. Unbound parameters retain their order. This teaching pseudocode follows successful type, ABI, and capture validation; it does not interpret an arbitrary signature at runtime.

~~~text
invoke_projected(capture, supplied):
    j = 0
    for i in original parameter order:
        if position i is bound:
            original[i] = the admitted capture for i
        else:
            original[i] = supplied[j]
            j = j + 1
    invoke the concrete original function once with original
~~~

The invariant is that the first i positions equal the corresponding original-call arguments, and j counts their unbound positions. The bound branch uses that position's admitted capture; the other branch consumes the next ordered input. Both preserve the invariant. At termination, every position is filled once and the concrete call equals a direct call with those values. For `plus10(b)`, reconstruction yields `(10, b)`; with `b <= INT_MAX - 10`, the sum is representable and equals `10 + b`. This compares saved values and later arguments, not early capture with later reevaluation of arbitrary side-effecting expressions.

## 11. Capture Capacity and Lifetime

A **capture** stores values or addresses needed by a later call. `cmeta_callable` provides `CMETA_CAPTURE_INLINE` bytes of inline storage. Copying the callable copies those bytes; copying a pointer does not extend the lifetime of its pointee, provider, or Plugin.

SBO, or **small-buffer optimization**, commonly stores small objects inline and allocates larger ones separately. This capture mechanism instead enforces a fixed bound: excess size is rejected without switching to heap allocation.

| Input | Admission condition |
|---|---|
| `value` | Registered trivial scalar |
| `borrow` | Object pointer explicitly marked BORROWED |
| Managed or consuming capture | Rejected |
| Capture exceeding inline capacity | Compilation failure |

The authoritative owner and any outer Plugin lease must cover every use, including cleanup that still accesses the captured object. Copying a Callable cannot discharge these obligations.

## 12. Invokable Connects Description and Execution

`cmeta_invokable_bind` checks agreement between a function description and a callable, producing a reusable execution capability on success. This fragment assumes the callable and output object have already been constructed under the preceding contracts.

~~~c
cmeta_status status =
    cmeta_invokable_bind(
        FunctionMeta(plus10),
        callable,
        &invokable);
~~~

The resulting Invokable still borrows descriptors, providers, modules, and captured objects. Successful validation establishes compatibility at admission time; their owners must preserve validity during later calls.

## 13. Reusing an Admitted Binding

The ordinary invocation entry point performs the required checks:

~~~c
cmeta_invokable_invoke(
    &invokable,
    &output,
    args);
~~~

An unmodified successfully admitted object with valid borrows may use the admitted entry point:

~~~c
cmeta_invokable_invoke_admitted(
    &invokable,
    &output,
    args);
~~~

This path still checks call storage but does not traverse the descriptor graph again. The saved work is repeated semantic validation. A modified description or expired borrow invalidates the basis for reuse.

## 14. An Object Provider Supplies the Matching Entry Point

Name lookup supplies descriptive information such as FunctionAbi. To execute an object operation, its provider also supplies an exact receiver-bound Callable and function data with the receiver removed. These are the check-entry names; ellipses denote omitted parameters:

~~~c
cmeta_receiver_operation_invokable_bind(...)
~~~

~~~c
cmeta_object_operation_invokable_bind(...)
~~~

The checker verifies that the description and executable object form a legal projection. It cannot infer an arbitrary function ABI from an object address or turn a method name alone into permission to call unknown code.

## 15. Functions and Interface Providers

FunctionDesc, FunctionAbi, and an optional adapter describe an independent operation. InterfaceDesc and `{self, vtable}` describe a provider offering multiple operations over a shared lifetime. Both may use Plugin admission and leases, but their descriptions and execution representations require their own checks. Shared infrastructure does not make their lifetime contracts interchangeable.

## 16. Effects and Properties

Effects describe interactions with external state or execution restrictions. Properties state behavioral laws that consumers may use when selecting operations or considering optimizations.

| Category | Examples | Interpretation |
|---|---|---|
| Effects and restrictions | `IO`, `STATEFUL`, `MAY_FAIL` | The function may perform I/O, depend on state, or fail |
| Behavioral properties | `DETERMINISTIC`, `IDEMPOTENT`, `ASSOCIATIVE` | Claims of determinism, idempotence, or associativity |

Setting a property flag states a claim. Removing the second call to an idempotent function requires `f(f(x)) = f(x)` over the admitted domain and observation model. If logs or error order are observable, their preservation also needs justification. Chapter 6 connects these conditions to graph rewrites.

## 17. Checking Generation and Call Contracts

Declaration generation, projection checks, call results, and borrowed lifetimes have different failure modes. One successful invocation cannot validate all four.

| Check | Expected result |
|---|---|
| `FunctionDecl` | Prototype and descriptions, without an implicit erased adapter |
| `FunctionInvokeDecl` | An explicitly generated adapter matching the native signature |
| Invalid projection | Reject mismatched signatures, carriers, flags, receivers, or bound positions |
| Invalid capture | Reject excess size, managed values, and unregistered projected signatures |
| Successful admission | Checked and admitted invocation agree semantically |
| Lifetime | Outer owners cover borrows; copying adds no implicit retention |

Measure direct calls, generated thunks, checked and admitted Invokables, and capturing bindings separately. Report inputs, compiler options, and measurement scope; a description of the abstraction is not performance evidence.

## 18. Summary

FunctionDesc records the semantic contract and FunctionAbi describes native carriers. Adapters, bound Callables, and Invokables provide execution capabilities with explicit conditions. Expanding a thunk shows that the uniform interface still calls a concretely typed C function; storage type, alignment, and lifetime remain caller obligations. Binding partitions parameters into saved values or borrows and later arguments. The projected call remains valid only while its original contract and all borrowed lifetimes hold.
