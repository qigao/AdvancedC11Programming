# Chapter 3: Function Semantics and Executable Projections — FunctionDesc, Receiver, Bind, and Invokable

> **This chapter makes one distinction:**
>
> describing what a C function is and deciding how to execute, bind, or project it are different operations.

---

## 1. Ordinary Functions and Function Pointers Remain the Baseline

The simplest case is still ordinary C:

~~~c
long square(int x)
{
    return (long)x * x;
}

long (*fn)(int) = square;
long y = fn(7);
~~~

If a caller only needs one function address, stop there.

Function Reflection becomes useful when several consumers need stable facts such as:

~~~text
parameter direction
ownership / nullability
result ownership
effects / properties
ABI carrier
receiver identity
~~~

---

## 2. FunctionDecl Emits Ordinary C First

A canonical declaration can be:

~~~c
FunctionDecl(value, int, add,
    (int, left, CMETA_PARAM_IN),
    (int, right, CMETA_PARAM_IN));

int add(int left, int right)
{
    return left + right;
}
~~~

It emits:

~~~text
normal C prototype
        +
immutable TU-local FunctionDesc
        +
immutable FunctionAbi sidecar
        +
static-inline metadata getters
~~~

Consumers use:

~~~c
const cmeta_function_desc *f = FunctionMeta(add);
const cmeta_function_abi_desc *abi = FunctionAbi(add);
~~~

The key rule is:

> **Function reflection is descriptive only.**

FunctionDecl does not automatically generate a universal erased invocation ABI.

Direct execution remains ordinary C:

~~~c
int result = add(2, 3);
~~~

---

## 3. FunctionDesc and FunctionAbi Answer Different Questions

FunctionDesc carries semantic contract facts:

~~~text
name
return type
parameter names / types / flags
effects
properties
result ownership / nullability
~~~

FunctionAbi is a sidecar for executable carrier facts:

~~~text
return carrier
parameter carriers
~~~

So:

~~~text
FunctionDesc
    = what the function means

FunctionAbi
    = how the declared native boundary is carried
~~~

Both remain metadata.

Neither gains execution authority merely by existing.

---

## 4. Parameter Rows Are Canonical Facts

Parameters admit several levels of explicitness:

~~~text
(type, name, flags)

(type, name, flags, descriptor)

(type, name, flags, descriptor, abi_carrier)
~~~

A complete ABI row can be:

~~~c
(int, value,
 CMETA_PARAM_IN,
 &cmeta_type_int,
 CMETA_ABI_SCALAR)
~~~

The same row can generate:

~~~text
native prototype
      +
ParamDesc
      +
FunctionAbi carrier
      +
TinyMock projection
      +
Plugin declaration
      +
bind / exact adapter
~~~

This is a concrete consumer of the finite tuple kernel from Chapter 2.

---

## 5. Result Ownership Is Descriptive Semantics, Not a Cleanup Runtime

An explicit result contract can be:

~~~c
FunctionDeclAsAbiResult(
    value,
    char *,
    &cmeta_type_char_ptr,
    CMETA_ABI_OBJECT_POINTER,
    CMETA_RESULT_BORROWED,
    find_name,
    (int, id, CMETA_PARAM_IN,
     &cmeta_type_int, CMETA_ABI_SCALAR));
~~~

VALUE, BORROWED, SHARED, and OWNED describe the result contract.

They tell compilers and generators how to reason:

~~~text
VALUE
    -> native value result

BORROWED
    -> no ownership transfer

SHARED
    -> release obligation when admitted

OWNED
    -> ownership transfer / destroy obligation
~~~

The descriptor itself does not execute cleanup and does not contain lexical LIVE/MOVED state.

Cleanup placement belongs to a compiler/generator or to the real runtime domain.

---

## 6. Exact Invocation Is an Explicit Opt-In

When a consumer really needs an erased exact thunk, request it explicitly:

~~~c
#include <cmeta/invoke_decl.h>

FunctionInvokeDecl(value, int, increment,
    (int, input, CMETA_PARAM_IN));

int increment(int input)
{
    return input + 1;
}
~~~

The generated exact invoke can then be used:

~~~c
int input = 4;
int output = 0;
void *params[] = { &input };

bool ok =
    FunctionInvoke(increment)(
        &output,
        params,
        1);
~~~

The causal relationship is:

~~~text
FunctionDecl
    -> description only

FunctionInvokeDecl
    -> FunctionDecl
       + explicitly requested exact thunk
~~~

not:

~~~text
Reflection
    -> automatic dynamic invocation
~~~

Description and execution capability stay separate.

---

## 7. Receiver Is a Semantic Role of Parameter Zero, Not a Hidden Object Runtime

A receiver function remains ordinary C:

~~~c
int list_add(IntList *self, int value);
~~~

Reflection marks parameter zero as a receiver, for example:

~~~text
IN / INOUT
+
BORROWED
+
CMETA_PARAM_RECEIVER
~~~

The rule is:

~~~text
receiver metadata
    -> descriptive role

C ABI
    -> unchanged ordinary first parameter
~~~

CMETA_PARAM_RECEIVER does not:

- change the native calling convention;
- create a vtable;
- create a hidden self object;
- imply runtime dispatch.

It lets a compiler or generator understand an optional projection such as:

~~~text
obj.add(x)
    may lower to
List_add(&obj, x)
~~~

Dot-call lowering is not a prerequisite for using CMeta.

---

## 8. Receiver Projection Semantics Belong to Function

After binding the receiver:

~~~text
original:
(self, value) -> result

projected:
(value) -> result
~~~

the rule is not simply to drop parameter zero.

The projection must preserve:

~~~text
same return type
same result ownership / nullability
same effects
same properties
same remaining parameter names / types / flags
~~~

Canonical validation is Function-owned:

~~~c
cmeta_function_receiver_projection_valid(
    source,
    projected);
~~~

General parameter projection uses:

~~~c
cmeta_function_projection_valid(
    source_abi,
    projected_abi,
    bound,
    count);
~~~

The receiver subsystem does not own a parallel copy of function semantics.

---

## 9. Receiver Operation Sets Are Thin Indexes

A current operation row is intentionally small:

~~~c
typedef struct cmeta_receiver_operation {
    const char *name;
    const cmeta_function_abi_desc *abi;
} cmeta_receiver_operation;
~~~

Conceptually:

~~~text
FunctionDesc
    ^
    |
FunctionAbi
    ^
    |
receiver operation
  { name, abi }
    ^
    |
operation set
  receiver type
  operations
  optional generic owner
~~~

The operation set provides:

~~~text
name -> canonical FunctionAbi
~~~

It does not store a second FunctionDesc.

> **receiver lookup may own an index, while Function remains the semantic authority for callable semantics.**

---

## 10. Bind Is Parameter Projection, Not a Separate Lambda Object Model

Start with:

~~~c
int add(int a, int b);
~~~

Declare canonical semantics:

~~~c
FunctionDeclAsAbiResult(
    value,
    int,
    &cmeta_type_int,
    CMETA_ABI_SCALAR,
    CMETA_RESULT_VALUE,
    add,
    (int, a, CMETA_PARAM_IN,
     &cmeta_type_int, CMETA_ABI_SCALAR),
    (int, b, CMETA_PARAM_IN,
     &cmeta_type_int, CMETA_ABI_SCALAR));
~~~

Then bind a = 10:

~~~c
FunctionBindDeclAsAbiResult(
    value,
    int,
    &cmeta_type_int,
    CMETA_ABI_SCALAR,
    CMETA_RESULT_VALUE,
    plus10,
    add,
    CMETA_SIG_U_I_I,
    (value,
        (int, a, CMETA_PARAM_IN,
         &cmeta_type_int, CMETA_ABI_SCALAR)),
    (arg,
        (int, b, CMETA_PARAM_IN,
         &cmeta_type_int, CMETA_ABI_SCALAR)));
~~~

The row modes are explicit:

~~~text
arg
    -> remains a call argument

value
    -> captures a trivial scalar snapshot

borrow
    -> captures an explicit borrowed object pointer
~~~

Receiver binding uses the same model: the borrow row also carries the RECEIVER flag.

There is no need for a parallel ReceiverClosure / MethodLambda / BoundMethodObject hierarchy.

---

## 11. Capture Is a Bounded Byte Snapshot, Not a Hidden Ownership System

cmeta_callable has a fixed inline capture capacity:

~~~text
CMETA_CAPTURE_INLINE
~~~

Binding rules include:

~~~text
value
    -> registered trivial scalar only

borrow
    -> explicit BORROWED object pointer only

managed / consuming capture
    -> rejected

capture bytes > inline capacity
    -> compile failure
~~~

There is no:

~~~text
hidden malloc
automatic retain
automatic release
silent SBO fallback
~~~

Copying a callable copies its inline bytes.

If those bytes contain a borrowed pointer:

~~~text
copy callable
    !=
retain pointee / provider / Plugin
~~~

The authoritative owner and outer Plugin lease must remain live.

---

## 12. cmeta_invokable Is the Admitted Join Between Semantics and Execution

Function metadata and cmeta_callable become executable together after binding:

~~~c
cmeta_status status =
    cmeta_invokable_bind(
        FunctionMeta(plus10),
        callable,
        &invokable);
~~~

A successful bind means:

~~~text
FunctionDesc
      +
cmeta_callable
      |
      v
validate semantic / executable agreement once
      |
      v
cmeta_invokable
~~~

The binding remains borrowed:

- it does not retain descriptors;
- it does not retain providers;
- it does not retain a Plugin module;
- it does not extend captured-borrow lifetime.

The authoritative owner must cover every use.

---

## 13. Validate Once, Then Use the Admitted Path

The checked call is:

~~~c
cmeta_invokable_invoke(
    &invokable,
    &output,
    args);
~~~

For an unmodified result of successful admission:

~~~c
cmeta_invokable_invoke_admitted(
    &invokable,
    &output,
    args);
~~~

The admitted path still checks call storage but does not re-walk descriptor graphs.

~~~text
foreign / raw metadata
        |
        v
full validation / bind
        |
        v
admitted capability
        |
        v
repeated execution
without re-proving descriptor graph
~~~

This is the recurring rule:

> **validate once; inspect/use many.**

---

## 14. An Object Provider Still Produces an Exact Receiver-Bound Callable

Operation lookup describes only:

~~~text
name
+
FunctionAbi
~~~

To execute an object receiver operation, the provider must produce:

~~~text
receiver-bound exact callable
        +
receiver-elided FunctionData
~~~

Then:

~~~c
cmeta_receiver_operation_invokable_bind(...)
~~~

or:

~~~c
cmeta_object_operation_invokable_bind(...)
~~~

validates that the pair is a legal projection of the canonical Function.

CMeta does not:

~~~text
take arbitrary receiver pointer
    -> cast it
    -> guess the original ABI
    -> invoke by method name
~~~

The ABI boundary stays explicit and fail-fast.

---

## 15. Function and Interface Remain Different Abstractions

An independent operation fits:

~~~text
FunctionDesc
+
FunctionAbi
+
optional exact adapter
~~~

A long-lived provider fits:

~~~text
InterfaceDesc
+
{ self, vtable }
~~~

They may share Plugin loader, lease, and admission infrastructure without pretending to be the same semantic representation.

---

## 16. Effects and Properties Are Claims, Not Rewrite Theorems

FunctionDesc can carry:

~~~text
effects:
    IO
    STATEFUL
    MAY_FAIL

properties:
    DETERMINISTIC
    IDEMPOTENT
    ASSOCIATIVE
~~~

These may guide admission and optimization candidate selection.

But:

~~~text
property bit
    !=
semantic proof
~~~

The laws that authorize CFlow rewrites belong in the Execution IR chapters.

---

## 17. Engineering Evidence

### Description-Only Contract

Plain FunctionDecl should prove:

~~~text
prototype exists
metadata exists
FunctionAbi exists
no implicit erased thunk
~~~

### Exact Invocation

Only explicit FunctionInvokeDecl generates the exact invocation surface.

### Projection Compile-Fail

Reject:

~~~text
wrong native signature
wrong result carrier
wrong parameter flags
wrong projected parameter
receiver mismatch
capture too large
managed value capture
unregistered projected signature
~~~

### Admission

Checked and admitted invocation must agree semantically after successful binding.

### Lifetime

Borrowed receiver, descriptor, provider, and module lifetime must be covered by an outer owner; copying a callable must not secretly retain them.

### Performance

Measure separately:

~~~text
direct C call
exact generated thunk
checked invokable
admitted invokable
capturing bind
~~~

Do not replace measurement with the phrase zero-cost.

## 18. What We Learned

The structure is:

~~~text
ordinary C function
       |
       +--> FunctionDesc
       |       semantic truth
       |
       +--> FunctionAbi
       |       carrier facts
       |
       +--> optional exact thunk
       |
       +--> receiver projection
       |
       '--> parameter bind
                |
                v
          cmeta_callable
                |
          validate / admit
                |
                v
          cmeta_invokable
~~~

Five boundaries matter:

1. Function Reflection is descriptive and does not automatically own invocation.
2. Receiver is canonical Function parameter semantics, not an object runtime.
3. Operation sets are thin indexes and do not duplicate FunctionDesc.
4. Bind is explicit parameter projection; capture is bounded and does not hide ownership.
5. Once admission succeeds, the capability can be reused instead of reinterpreting Reflection on every call.
