# Chapter 3: Function Reflection: Descriptors, Call Adapters, and Parameter Binding

A C function’s type determines how to call it, while parameter direction, borrowing, and result-cleanup obligations often remain in documentation. CMeta records these facts in function descriptors for binders, generators, and dynamic modules. Starting with a direct call, this chapter expands a call adapter, derives the preconditions for binding and type erasure, and examines the lifetime of descriptors and executable code.

## 1. Ordinary Functions and Function Pointers Remain the Baseline

The simplest case is still ordinary C:

~~~c
long square(int x)
{
    return (long)x * x;
}

long (*fn)(int) = square;
long y = fn(7);
~~~

If a caller only needs one function address, stop there. Function Reflection becomes useful when several consumers need stable facts such as:

- parameter direction
- ownership / nullability
- result ownership
- effects / properties
- ABI carrier
- receiver identity

## 2. FunctionDecl Emits Ordinary C First

A canonical declaration can be:

~~~c
FunctionDecl(value, int, add,
    (int, left, CMETA_PARAM_IN),
    (int, right, CMETA_PARAM_IN));

int add(int left, int right)
{
    return left + right;
}
~~~

It emits:

~~~text
normal C prototype
        +
immutable TU-local FunctionDesc
        +
immutable FunctionAbi sidecar
        +
static-inline metadata getters
~~~

Consumers use:

~~~c
const cmeta_function_desc *f = FunctionMeta(add);
const cmeta_function_abi_desc *abi = FunctionAbi(add);
~~~

The key rule is:

Function reflection is descriptive only. FunctionDecl does not automatically generate a universal erased invocation ABI. Direct execution remains ordinary C:

~~~c
int result = add(2, 3);
~~~

## 3. FunctionDesc and FunctionAbi Answer Different Questions

**Terminology:** A sidecar is associated metadata with a responsibility separate from the main descriptor. An ABI carrier identifies the native category crossing a call boundary, such as a scalar, object pointer, or aggregate; it is distinct from the parameter’s domain meaning.

FunctionDesc carries semantic contract facts:

~~~text
name
return type
parameter names / types / flags
effects
properties
result ownership / nullability
~~~

FunctionAbi is a sidecar for executable carrier facts:

~~~text
return carrier
parameter carriers
~~~

So:

~~~text
FunctionDesc
    = what the function means

FunctionAbi
    = how the declared native boundary is carried
~~~

Both remain metadata. Neither gains execution authority merely by existing.

## 4. Parameter Rows Are Canonical Facts

Parameters admit several levels of explicitness:

~~~text
(type, name, flags)

(type, name, flags, descriptor)

(type, name, flags, descriptor, abi_carrier)
~~~

A complete ABI row can be:

~~~c
(int, value,
 CMETA_PARAM_IN,
 &cmeta_type_int,
 CMETA_ABI_SCALAR)
~~~

The same row can generate:

~~~text
native prototype
      +
ParamDesc
      +
FunctionAbi carrier
      +
TinyMock projection
      +
Plugin declaration
      +
bind / exact adapter
~~~

This is a concrete consumer of the finite tuple kernel from Chapter 2.

## 5. Result Ownership Is Descriptive Semantics, Not a Cleanup Runtime

An explicit result contract can be:

~~~c
FunctionDeclAsAbiResult(
    value,
    char *,
    &cmeta_type_char_ptr,
    CMETA_ABI_OBJECT_POINTER,
    CMETA_RESULT_BORROWED,
    find_name,
    (int, id, CMETA_PARAM_IN,
     &cmeta_type_int, CMETA_ABI_SCALAR));
~~~

VALUE, BORROWED, SHARED, and OWNED describe the result contract. They tell compilers and generators how to reason:

~~~text
VALUE
    -> native value result

BORROWED
    -> no ownership transfer

SHARED
    -> release obligation when admitted

OWNED
    -> ownership transfer / destroy obligation
~~~

The descriptor itself does not execute cleanup and does not contain lexical LIVE/MOVED state. Cleanup placement belongs to a compiler/generator or to the real runtime domain.

## 6. Exact Invocation Is an Explicit Opt-In

**A thunk** here is a small wrapper generated for a known function: it accepts argument-storage addresses through a uniform interface, reads values using their declared C types, calls the original function, and stores the result. **Exact** means that the call still follows that function’s concrete native signature.

**Type erasure** hides concrete types behind a uniform interface. This entry point uses `void *`, but the generated thunk still knows the actual types; it cannot safely interpret arbitrary objects merely because they were cast. In other contexts, thunk can mean a wrapper for deferred computation. Here it means a call adapter.

When a consumer really needs an erased exact thunk, request it explicitly:

~~~c
#include <cmeta/invoke_decl.h>

FunctionInvokeDecl(value, int, increment,
    (int, input, CMETA_PARAM_IN));

int increment(int input)
{
    return input + 1;
}
~~~

The generated exact invoke can then be used:

~~~c
int input = 4;
int output = 0;
void *params[] = { &input };

bool ok =
    FunctionInvoke(increment)(
        &output,
        params,
        1);
~~~

In this example, the adapter checks the argument count and required storage pointers for null, reads the `int` object addressed by `params[0]`, calls `increment(4)`, and writes `5` to `output`. The caller must still supply correctly typed, aligned, live storage; null checks on `void *` cannot establish those properties. See [invoke_decl.h](https://github.com/qigao/salts/blob/a650262031e9b3e5f11a227a7911a75db9ae1fb8/cmeta/include/cmeta/invoke_decl.h) in the pinned snapshot. `FunctionDecl` generates descriptions; `FunctionInvokeDecl` additionally requests an adapter. The following expansion examines that additional code.

**Expanding the thunk into C.** This teaching expansion uses the preceding `increment` and requires `<stdbool.h>` and `<stddef.h>`. The actual macro generates different names and additional static checks; this fragment retains the runtime checks and concrete call so they can be examined directly.

~~~c
static bool increment_adapter(
    void *result, void *const *args, size_t count)
{
    if (count != 1 || args == NULL)
        return false;
    if (args[0] == NULL || result == NULL)
        return false;

    *(int *)result = increment(*(int *)args[0]);
    return true;
}
~~~

The pseudocode separates caller storage obligations from the steps performed by the adapter. It does not check actual object type, alignment, or lifetime at runtime; those are preconditions for valid reads and writes.

~~~text
adapt_increment(result, args, count):
    reject wrong count or missing argument array
    reject missing argument or result storage
    read x from the int object at args[0]
    compute y = increment(x)
    write y to the int object at result
    return true
~~~

**Correctness argument.** Assume `args` addresses at least one valid pointer element, `args[0]` addresses a live `int` containing `x`, and `result` addresses a writable live `int`. Storage is correctly aligned, accesses are free of data races, and `x < INT_MAX`. With `count == 1` and non-null required addresses, neither rejection branch returns. The assignment reads `x`, calls `increment` once to obtain the representable value `x + 1`, writes the result, and returns `true`. Input and result may be the same `int` object: the read and call finish before the assignment stores the value.

If the count or required-pointer checks fail, control returns `false` before invoking the target or writing the result. Non-null dangling, misaligned, or incorrectly typed addresses are outside that rejection guarantee and must be excluded by the caller before dereferencing. This hand derivation shows how the exact thunk retains a concrete signature without making `void *` a runtime proof of type.

### 6.1 Qualify Success and Rejection in One Executable Gate

The preceding fragments can be combined into one complete installed-consumer C11 program. It uses the pinned `<cmeta/invoke_decl.h>` and `Salts::CMeta`, and a call counter distinguishes “returned false” from “the native function really did not run”:

~~~c
#include <cmeta/invoke_decl.h>

static int calls;

FunctionInvokeDecl(
    value,
    int,
    increment,
    (int, input, CMETA_PARAM_IN));

int increment(int input)
{
    ++calls;
    return input + 1;
}

int main(void)
{
    int input = 4;
    int output = -1;
    void *params[] = { &input };

    if (!FunctionInvoke(increment)(&output, params, 1))
        return 1;
    if (output != 5 || calls != 1)
        return 2;

    int alias = 4;
    void *alias_params[] = { &alias };

    if (!FunctionInvoke(increment)(
            &alias, alias_params, 1))
        return 3;
    if (alias != 5 || calls != 2)
        return 4;

    output = 77;

    if (FunctionInvoke(increment)(
            &output, params, 0))
        return 5;
    if (output != 77 || calls != 2)
        return 6;

    if (FunctionInvoke(increment)(
            &output, NULL, 1))
        return 7;
    if (output != 77 || calls != 2)
        return 8;

    void *null_arg[] = { NULL };

    if (FunctionInvoke(increment)(
            &output, null_arg, 1))
        return 9;
    if (output != 77 || calls != 2)
        return 10;

    if (FunctionInvoke(increment)(
            NULL, params, 1))
        return 11;
    if (calls != 2)
        return 12;

    return 0;
}
~~~

The gate covers six behaviors:

| Case | Return | Native call count | Result storage |
|---|---:|---:|---|
| valid input `4` | `true` | +1 | writes `5` |
| input/result are the same `int` | `true` | +1 | becomes `5` in place |
| wrong count | `false` | unchanged | unchanged |
| `params == NULL` | `false` | unchanged | unchanged |
| `params[0] == NULL` | `false` | unchanged | unchanged |
| non-void `result == NULL` | `false` | unchanged | no write |

The rejection guarantee still covers only the **count/null contract** that the thunk can check. A non-null but mistyped, misaligned, dangling, or racing address is not a negative case that should return `false`; it violates the call preconditions. A test must not manufacture undefined behavior and then treat the result as evidence of runtime type checking.

An installed consumer needs only the public package boundary:

~~~cmake
find_package(Salts CONFIG REQUIRED)

add_executable(
    exact_invoke_gate
    exact_invoke_gate.c)

target_link_libraries(
    exact_invoke_gate
    PRIVATE
        Salts::CMeta)
~~~

This one gate therefore checks declaration generation, exact-thunk rejection order, native invocation count, and the installed public target without any Salts source-tree include path.

## 7. Receiver: From an Ordinary First Parameter to a Verified Projection

A receiver function remains ordinary C:

~~~c
int list_add(IntList *self, int value);
~~~

Reflection marks parameter zero as a receiver, for example:

~~~text
IN / INOUT
+
BORROWED
+
CMETA_PARAM_RECEIVER
~~~

The rule is:

~~~text
receiver metadata
    -> descriptive role

C ABI
    -> unchanged ordinary first parameter
~~~

CMETA_PARAM_RECEIVER does not:

- change the native calling convention;
- create a vtable;
- create a hidden self object;
- imply runtime dispatch.

It lets a compiler or generator understand an optional projection such as:

~~~text
obj.add(x)
    may lower to
List_add(&obj, x)
~~~

Dot-call lowering is not a prerequisite for using CMeta.

### 7.1 Receiver Projection Semantics Belong to Function

After binding the receiver:

~~~text
original:
(self, value) -> result

projected:
(value) -> result
~~~

the rule is not simply to drop parameter zero. The projection must preserve:

- same return type
- same result ownership / nullability
- same effects
- same properties
- same remaining parameter names / types / flags

Canonical validation is Function-owned:

~~~c
cmeta_function_receiver_projection_valid(
    source,
    projected);
~~~

General parameter projection uses:

~~~c
cmeta_function_projection_valid(
    source_abi,
    projected_abi,
    bound,
    count);
~~~

The receiver subsystem does not own a parallel copy of function semantics.

### 7.2 Operation Sets Index Functions Without Copying Their Semantics

A current operation row is intentionally small:

~~~c
typedef struct cmeta_receiver_operation {
    const char *name;
    const cmeta_function_abi_desc *abi;
} cmeta_receiver_operation;
~~~

Conceptually:

~~~text
FunctionDesc
    ^
    |
FunctionAbi
    ^
    |
receiver operation
  { name, abi }
    ^
    |
operation set
  receiver type
  operations
  optional generic owner
~~~

The operation set provides:

~~~text
name -> canonical FunctionAbi
~~~

It does not store a second FunctionDesc. Receiver lookup may own an index, while Function remains the semantic authority for callable semantics.

## 8. Binding and Capture: Turn Some Parameters into a Reusable Call Capability

Start with:

~~~c
int add(int a, int b);
~~~

Declare canonical semantics:

~~~c
FunctionDeclAsAbiResult(
    value,
    int,
    &cmeta_type_int,
    CMETA_ABI_SCALAR,
    CMETA_RESULT_VALUE,
    add,
    (int, a, CMETA_PARAM_IN,
     &cmeta_type_int, CMETA_ABI_SCALAR),
    (int, b, CMETA_PARAM_IN,
     &cmeta_type_int, CMETA_ABI_SCALAR));
~~~

Declare a projection that captures `a` and leaves `b` as a call argument. The declaration specifies the binding shape; a subsequently constructed callable supplies the value. With `a = 10`, its effect is `add(10, b)`:

~~~c
FunctionBindDeclAsAbiResult(
    value,
    int,
    &cmeta_type_int,
    CMETA_ABI_SCALAR,
    CMETA_RESULT_VALUE,
    plus10,
    add,
    CMETA_SIG_U_I_I,
    (value,
        (int, a, CMETA_PARAM_IN,
         &cmeta_type_int, CMETA_ABI_SCALAR)),
    (arg,
        (int, b, CMETA_PARAM_IN,
         &cmeta_type_int, CMETA_ABI_SCALAR)));
~~~

The row modes are explicit:

~~~text
arg
    -> remains a call argument

value
    -> captures a trivial scalar snapshot

borrow
    -> captures an explicit borrowed object pointer
~~~

Receiver binding uses the same model: the borrow row also carries the RECEIVER flag. There is no need for a parallel ReceiverClosure / MethodLambda / BoundMethodObject hierarchy.

### 8.1 Capture Is a Bounded Byte Snapshot, Not a Hidden Ownership System

Capture stores values or addresses that a later call will need in the callable. SBO, or small-buffer optimization, commonly stores small objects inline and allocates larger ones elsewhere. This fixed-capacity capture admits only the specified inline size and does not switch to heap allocation when it is exceeded. cmeta_callable has a fixed inline capture capacity:

~~~text
CMETA_CAPTURE_INLINE
~~~

Binding rules include:

~~~text
value
    -> registered trivial scalar only

borrow
    -> explicit BORROWED object pointer only

managed / consuming capture
    -> rejected

capture bytes > inline capacity
    -> compile failure
~~~

There is no:

- hidden malloc
- automatic retain
- automatic release
- silent SBO fallback

Copying a callable copies its inline bytes. If those bytes contain a borrowed pointer:

~~~text
copy callable
    !=
retain pointee / provider / Plugin
~~~

The authoritative owner and outer Plugin lease must remain live.

### 8.2 cmeta_invokable Joins Semantics and Execution After Admission

Function metadata and cmeta_callable become executable together after binding:

~~~c
cmeta_status status =
    cmeta_invokable_bind(
        FunctionMeta(plus10),
        callable,
        &invokable);
~~~

A successful bind means:

~~~text
FunctionDesc
      +
cmeta_callable
      |
      v
validate semantic / executable agreement once
      |
      v
cmeta_invokable
~~~

The binding remains borrowed:

- it does not retain descriptors;
- it does not retain providers;
- it does not retain a Plugin module;
- it does not extend captured-borrow lifetime.

The authoritative owner must cover every use.

### 8.3 Validate Once, Then Reuse the Admitted Path

The checked call is:

~~~c
cmeta_invokable_invoke(
    &invokable,
    &output,
    args);
~~~

For an unmodified result of successful admission:

~~~c
cmeta_invokable_invoke_admitted(
    &invokable,
    &output,
    args);
~~~

The admitted path still checks call storage but does not re-walk descriptor graphs.

~~~text
foreign / raw metadata
        |
        v
full validation / bind
        |
        v
admitted capability
        |
        v
repeated execution
without re-proving descriptor graph
~~~

This is the recurring rule:

validate once; inspect/use many.

## 9. Object Providers Must Supply Both Description and an Executable Entry Point

Operation lookup describes only:

~~~text
name
+
FunctionAbi
~~~

To execute an object receiver operation, the provider must produce:

~~~text
receiver-bound exact callable
        +
receiver-elided FunctionData
~~~

Then:

~~~c
cmeta_receiver_operation_invokable_bind(...)
~~~

or:

~~~c
cmeta_object_operation_invokable_bind(...)
~~~

validates that the pair is a legal projection of the canonical Function. CMeta does not:

~~~text
take arbitrary receiver pointer
    -> cast it
    -> guess the original ABI
    -> invoke by method name
~~~

The ABI boundary stays explicit and fail-fast.

### 9.1 Function and Interface Remain Different Abstractions

An independent operation fits:

~~~text
FunctionDesc
+
FunctionAbi
+
optional exact adapter
~~~

A long-lived provider fits:

~~~text
InterfaceDesc
+
{ self, vtable }
~~~

They may share Plugin loader, lease, and admission infrastructure without pretending to be the same semantic representation.

## 10. Effects and Properties Are Checkable Claims, Not Rewrite Theorems

FunctionDesc can carry:

~~~text
effects:
    IO
    STATEFUL
    MAY_FAIL

properties:
    DETERMINISTIC
    IDEMPOTENT
    ASSOCIATIVE
~~~

These may guide admission and optimization candidate selection. But:

~~~text
property bit
    !=
semantic proof
~~~

The laws that authorize CFlow rewrites belong in the Execution IR chapters.

## 11. Verify Generation, Call Results, and Borrowed Lifetimes Separately

Verification covers declaration generation, projection checks, call results, and borrowed lifetimes separately. One successful call cannot establish the entire binding model.

| Check | Expected result |
|---|---|
| `FunctionDecl` | Prototypes and descriptions, without an implicit erased invocation entry point |
| `FunctionInvokeDecl` | An explicitly generated adapter matching the native signature |
| Invalid projection | Reject mismatched signatures, carriers, flags, receivers, or bound positions |
| Invalid capture | Reject excess size, managed values, and unregistered projected signatures |
| Successful admission | Checked and admitted calls agree semantically |
| Lifetime | Outer owners cover borrows; copying a Callable adds no implicit retention |

Measure direct C calls, generated thunks, checked Invokables, admitted Invokables, and capturing bindings separately. Report inputs, compiler options, and measurement scope rather than describing the result as zero-cost without evidence.

## 12. Summary

FunctionDesc records the semantic contract and FunctionAbi describes native carriers; a thunk, bound Callable, and Invokable provide distinct execution capabilities. Expanding the thunk shows that a uniform entry point still calls a concretely typed C function, while the caller remains responsible for storage type, alignment, and lifetime. Binding leaves some parameters as future inputs and saves others as bounded value snapshots or explicit borrows. Copying a callable does not extend the lifetime of pointees or shared libraries. An admitted capability remains reusable only while its contract holds; graphs next record typed connections between these calls.
