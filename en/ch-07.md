# Chapter 7: From Graphs to Execution Plans: Optimization and Direct Execution

A graph interpreter may query nodes and edges for every value; a compiler can instead resolve those relationships into a plan before execution. This separates preparation from per-value cost without automatically removing every indirect call, allocation, or lifecycle check. This chapter describes normalization and plan compilation, the actual Direct support boundary, ordered parallel reduction, and cost amortization.

## 1. Normalization and Optimization Produce Separate Artifacts

Surface operators make graphs convenient to construct. Normalization translates them into the primitive forms consumed by later stages; optimization applies authorized rewrites to eligible structures. Each transformation borrows an unchanged source and builds a separate destination, with cleanup governed by its API.

~~~text
prepare(surface):
    validate surface
    normalized = normalize(surface)
    validate normalized
    optimized = clone or rewrite normalized
    for each candidate in a finite worklist:
        if shape and metadata and authorized law all match:
            replace the candidate and record the rewrite
        otherwise:
            keep the candidate unchanged
    validate optimized
    return optimized with its trace
~~~

A **worklist** holds candidates still to process. Finiteness matters: if a rule creates another occurrence of its own pattern, termination needs a decreasing measure or explicit bound. “Repeat until unchanged” is not itself a termination proof. Normalization must not consume source values, request subscription demand, or advance an executor.

The pinned `cflow_graph_normalize(dst, src)` uses a separate destination. Surface, normalized, and optimized graphs have distinct identities; a version belonging to one cannot identify another. Chapter 6's traces connect particular source and destination artifacts.

## 2. Queries Moved to Compilation

**Lowering** translates an abstract representation into one closer to execution. Plan compilation resolves topology, handlers, types, and call information in advance. The following teaching structures are not the public `cflow_plan` layout.

~~~c
typedef struct book_instruction book_instruction;
typedef int (*book_handler)(const book_instruction *, void *);

struct book_instruction {
    book_handler execute;
    size_t input_slot;
    size_t output_slot;
    const void *static_data;
};

typedef struct book_plan_view {
    const book_instruction *code;
    size_t count;
} book_plan_view;
~~~

Given a validated plan and valid frame, the teaching execution loop is:

~~~c
int book_execute(const book_plan_view *plan, void *frame)
{
    for (size_t i = 0; i < plan->count; ++i) {
        const book_instruction *insn = &plan->code[i];
        int status = insn->execute(insn, frame);
        if (status != 0)
            return status;
    }
    return 0;
}
~~~

This shows resolved dispatch: handlers and slots are known, so the loop need not find graph edges. A real plan must also handle terminals, ownership, and failure cleanup. A **hot path** is the repeatedly executed value-processing part. Moving structure queries out of it does not remove every runtime obligation.

The pinned `cflow_plan_compile` accepts an already normalized primitive graph. `cflow_plan_compile_surface` supplies a surface-graph convenience entry. Execution no longer queries Graph, Node, Edge, or Subgraph topology. Sequential materialized execution supports both trivial values and values with admitted copy, move, and destroy traits; it is not universally allocation-free.

## 3. Storage and Failure Cleanup

`cflow_plan_eval_array` borrows input. Its successful result independently owns returned values and is released with `cflow_result_destroy`. A reusable workspace follows a different contract:

| Object or operation | Pinned restriction |
|---|---|
| `cflow_plan_batch_workspace` | Fused plans with canonical raw-batch calls and trivial value storage |
| Initialization | Reserves scratch for a specified maximum input count |
| Workspace evaluation | No heap allocation or release; count must fit capacity |
| Workspace result | Borrowed until next evaluation or destruction; never pass to `cflow_result_destroy` |
| Concurrent use | Single-owner workspace; no simultaneous evaluations |

Allocation ahead of execution is a property of this admitted path. Saving a workspace result for an asynchronous task requires an appropriate owned copy or exclusive retention of the workspace for the whole use interval. Copying the result's pointer does not acquire its values.

## 4. Computations Supported by Direct

**AOT**, or ahead-of-time compilation, describes when execution code is generated and compiled. Direct describes its execution form. This version supports at most sixteen Filter/Map stages in Direct. A complete Filter/Map/Reduce pipeline requires a supported Plan path.

This declaration fragment uses Chapter 5's admitted `sample_even` and `sample_square` callables and requires `<cflow/direct.h>`:

~~~c
#define EvenSquareSteps(M) \
    CFlowDirectSteps(M, \
        (filter, int, int, sample_even), \
        (map, int, long, sample_square))

cflow_direct_pipeline(even_squares,
    int, &cmeta_type_int, long, 2, EvenSquareSteps);
~~~

It generates a builder, stage description, eligibility check, and array evaluator. The six example inputs produce `{4, 16, 36}`, not yet the reduced `56`. The evaluator requires output capacity at least equal to input count; it does not first run predicates to guess the final size.

Eligibility requires trivial copy and destruction, a bindable capture-free callable, PURE effects, DETERMINISTIC, TOTAL, and NO_ALIAS properties, and matching signatures throughout the type chain. Filter returns `bool` while preserving the flow type; Map returns another Direct-eligible type. Chapter 5's bounded input domain remains necessary for the square function. Metadata cannot extend the range of `long`.

Stage IR distinguishes static targets, canonical raw-batch calls, and adapters. Only an appropriate all-static-target path can generate directly named C calls. This does not promise that the C compiler will inline every body into machine code.

## 5. Direct Rejection Conditions

The generated array path checks input, complete output-capacity, and count-storage ranges, including size overflow and forbidden overlap. It performs no allocation, scheduling, or indirect stage calls. Failure returns a Direct status without selecting Plan.

~~~text
evaluate_direct(inputs, count, outputs, capacity, written):
    validate byte ranges and required disjointness
    set written to zero
    reject an ineligible schema
    reject capacity < count
    for each input in encounter order:
        apply the statically named Filter/Map stages
        append each surviving output
    commit written count
~~~

This summarizes control flow. Range checks cannot prove that arbitrary non-null addresses denote real C objects; the caller supplies valid live storage. If range validation fails, the actual entry returns before writing `written`. It cannot promise to zero an invalid count pointer.

## 6. Deriving Ordered Parallel Reduction

Parallel reduction retains the semantic operator while changing grouping, making it an execution refinement. Suppose `⊕` is associative over admitted values: `(a ⊕ b) ⊕ c = a ⊕ (b ⊕ c)`, with no observed effects or failures. Divide input into contiguous nonempty chunks, reduce each in order, then combine chunk results in original chunk order. Only parentheses change; elements do not exchange positions.

~~~text
ordered_reduce(values, chunks):
    require valid nonempty contiguous chunks
    require a homogeneous, pure, total associative reducer
    submit one admitted reduction task for each chunk
    collect chunk results into their original positions
    combine those results in chunk order
~~~

Repeated associativity transforms the chunked expression into the sequential one. Commutativity is unnecessary, but combining results in completion order is not justified. Seeded reduction must also preserve the original number of seed occurrences; a non-identity seed cannot simply be inserted into every chunk.

Associativity of mathematical integer addition does not establish safe arbitrary signed C addition. In the even-square sum, all terms are nonnegative and the total is bounded, so any contiguous regrouping has intermediate sums no larger than the total. Regrouping is safe in that domain. Floating-point addition generally lacks exact associativity; an ASSOCIATIVE flag cannot guarantee identical bits.

The actual parallel Plan also requires supported trivial storage, an executor with the needed concurrency capability, valid task and chunk bounds, and the complete admission contract. Unsupported plans, insufficient nonempty chunks, invalid options, and rejected tasks fail explicitly without sequential retry.

## 7. Certificates Bind Plans to Graphs

A **certificate** here is a checkable record of execution correspondence, not a cryptographic signature. It includes execution path, order, required capabilities, graph version and fingerprint, and rows describing operations, types, callables, and parameters.

~~~text
check_certificate(certificate, graph, plan):
    require a supported certificate version and execution path
    require matching graph identity and structure
    require every recorded row to match graph and plan semantics
    require the requested order and capabilities
    accept only after all rows match
~~~

The version rejects records predating a mutation. The fingerprint helps bind structure but is not a cryptographic collision-resistant signature. Pointer-bearing rows are process-local execution evidence, not a persistent interchange format. Lean certificate theorems establish row correspondence and observation preservation in the model; C checkers, lifetimes, and toolchains still need engineering validation.

The implementation contracts are in [plan.h](https://github.com/qigao/salts/blob/a650262031e9b3e5f11a227a7911a75db9ae1fb8/cflow/include/cflow/plan.h), [direct.h](https://github.com/qigao/salts/blob/a650262031e9b3e5f11a227a7911a75db9ae1fb8/cflow/include/cflow/direct.h), and [certificate.h](https://github.com/qigao/salts/blob/a650262031e9b3e5f11a227a7911a75db9ae1fb8/cflow/include/cflow/certificate.h). Resource and rejection behavior matter as much as successful results.

## 8. When Preparation Cost Is Amortized

Let additional plan preparation cost be `B`, interpretation of one fixed input batch cost `I`, and plan execution of that batch cost `P`. For `k` repetitions, the plan wins when `B + kP < kI`. Only if `I > P` can this be rearranged to `k > B / (I - P)`. Otherwise repetition cannot recover the preparation cost.

This is a cost model, not a measurement. Report construction, normalization, optimization, compilation, evaluation, workspace bytes, and code size separately. Distinguish rebuilding per request from reuse across requests. Measure trivial integers, managed values, short inputs, and long inputs separately; one workspace-path result does not characterize all plans.

## 9. Summary

Plans resolve structure in advance; Direct generates direct calls under stricter conditions; workspaces move allocation out of specific execution paths. Parallel reduction depends on value domains, associativity, order, and resources. Certificates relate executable artifacts to specific graphs. Support boundaries, failure contracts, and measurements determine which path is appropriate.
