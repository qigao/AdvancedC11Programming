# Chapter 7: From Graphs to Execution Plans: Optimization and Direct Execution

Graph types, connections, and operations can be resolved before execution instead of being looked up for every value. This chapter gives algorithms for normalization, rule matching, and plan compilation, identifies what remains in the plan, and examines supported computations that can become direct C calls or loops. Transformation proofs constrain results; baseline measurements establish actual cost.

## 1. Compiler Pipeline: From Snapshot to Executable Artifact

Do not mutate the user's Surface Graph in place.

~~~text
Surface Graph
    ↓ validate
Primitive Graph
    ↓ normalize
Normalized Snapshot
    ↓ optimize
Optimized Snapshot
    ↓ compile
Plan or Direct
~~~

Each immutable snapshot can have its own fingerprint so the input artifact, rewrite trace, certificate, and compiled plan remain related.

### 1.1 Normalize Algorithm

**Normalization** converts different valid representations into the common form expected by later stages, for example by expanding compound operators or standardizing edge order. It must preserve semantics; choosing a faster execution strategy belongs to later optimization.

Normalization performs semantic-preserving canonicalization without speculative policy.

~~~text
normalize(graph):

    require Graph.Valid

    out = empty primitive graph

    for node in topological_order(graph):
        lower surface aliases
        expand compound operators
        canonicalize type ids
        canonicalize edge ordering
        append primitive node

    freeze(out)

    return out
~~~

Required relation:

~~~text
observe(eval(surface))
=
observe(eval(normalized))
~~~

### 1.2 Optimize Algorithm

~~~text
optimize(graph):

    current = graph

    for rule in approved_rules:

        while match =
            rule.find_candidate(current):

            if !rule.metadata_admits(match):
                break

            if !rule.proof_authorized(match):
                break

            next =
                rule.rewrite(current, match)

            record_trace(rule,current,next)

            current = next

    freeze(current)

    return current
~~~

A rewrite requires **shape match, metadata admission, and proof authorization**.

### 1.3 Plan Representation: Pre-Resolve the Hot Path

Conceptual Plan:

~~~c
typedef struct cflow_step {
    cflow_step_fn handler;
    uint32_t input_slot;
    uint32_t output_slot;
    const void *static_data;
} cflow_step;

typedef struct cflow_plan {
    const cflow_step *steps;
    size_t step_count;
    size_t frame_size;
} cflow_plan;
~~~

Execution:

~~~c
for (size_t i = 0; i < plan->step_count; ++i) {
    const cflow_step *step = &plan->steps[i];

    step->handler(step, frame);
}
~~~

No node-id lookup, operator switch, edge resolution, or signature resolution remains in the per-step path; those decisions were resolved while compiling the Plan.

### 1.4 Direct Eligibility

**AOT (ahead-of-time compilation)** generates and compiles execution code before the program runs. This book’s Direct path turns eligible Graphs into direct C calls or loops. Direct describes an execution form; AOT describes compilation timing. Neither guarantees that an arbitrary Graph can become a loop.

Some Graphs can remove even Plan dispatch.

~~~text
direct_eligible(graph):

    require linear pipeline
    require supported operators
    require no dynamic topology
    require no WAIT/reactive boundary
    require fixed admitted callable ABI
    require ownership fully resolved

    return true
~~~

Then generate:

~~~c
long total = 0;

for (size_t i = 0; i < n; ++i) {
    int x = xs[i];

    if (!is_even(x))
        continue;

    total += square(x);
}
~~~

Graph disappears from the hot path.

### 1.5 No Silent Fallback

Do not promise a PARALLEL plan and silently execute sequentially when qualification fails; that is an explicit anti-pattern, not a fallback hidden inside the backend. Return UNSUPPORTED. The caller explicitly chooses another backend or fails build/admission. Performance and resource contracts remain observable.

### 1.6 Cost Model

Measure separately:

- build cost;
- normalize cost;
- optimize cost;
- compile-plan cost;
- per-value cost;
- memory/frame cost;
- binary/code-size cost.

Do not compare “Graph versus loop” without separating control-plane and execution-plane costs.

### 1.7 Failure Cases

Invalid Graph: if `Graph.Valid = false`, do not normalize or compile. Rewrite lacks proof: if shape and metadata match but proof is unavailable, keep the original Graph. Direct unsupported: if Graph is valid and Plan is supported but Direct is not, explicitly compile a Plan. Plan here is an explicit backend selection, not a silent fallback from a promised Direct contract. The remainder of the chapter walks the canonical pipeline end-to-end through rewrite, Plan, Direct/AOT, certificate, and measurement evidence.

## 2. End-to-End Case: Canonical Pipeline from Surface API to Plan

Return to the Part II pipeline:

~~~text
Source<int>
    ↓
Filter(is_even)
    ↓
Map(square)
    ↓
Reduce(sum)
~~~

The user-facing surface may be:

~~~c
stream.filter(&stream, is_even)
      ->map(&stream, square)
      ->reduce(&stream, sum);
~~~

This API is not an execution strategy. It first creates a **Surface Graph** recording operator identity, callable, input/output type, effects/properties, topology, cardinality, and parameters. The real execution chain starts here.

### 2.1 Step 1 — Surface Graph

Surface Graph must **faithfully record user meaning**. It may retain higher-level operators or structure. Its key properties are easy to construct, easy to inspect, and easy to diagnose—not fastest per-value execution representation.

### 2.2 Step 2 — Normalize

Current CFlow `cflow_graph_normalize(dst, src)` requires `src` to be a borrowed immutable Surface Graph and `dst` a separate empty destination. Normalize validates input, performs only static IR rewriting, validates output, and publishes an independent primitive snapshot. It does not own Subscription scheduling, live demand, runtime buffers, or Executor state. So:

Normalization is a pure control-plane IR transformation, not partial execution. This boundary is crucial.

### 2.3 Step 3 — Optimize

Optimizer continues with an **artifact transformation**:

~~~text
normalized immutable source
      ↓ apply admitted rewrites
new optimized Graph
~~~

The arrow means “construct a new optimized artifact,” not per-value execution dataflow. Current passes include canonicalize, dead subgraphs, map fusion, relation simplify, and property rewrites, and record nodes before/after, map fusion count, blocked transformations, and idempotent map eliminations. Especially useful are counters such as `effect_blocked_*` and `property_blocked_*`. because they express the correct optimizer attitude:

If a rewrite cannot be proved/admitted, explicitly do not perform it instead of using silent best effort.

### 2.4 Step 4 — Compile Plan

The full canonical pipeline ends with Reduce. A compiled Plan is therefore its natural execution artifact. Plan compile precomputes topology decoding, execution-handler resolution, type/callable binding, terminal Reduce state, and instruction sequence. Execution explicitly promises:

no Graph / Node / Edge / Subgraph topology lookup. So:

| Object | Role |
|---|---|
| Graph | source program description |
| Plan | pre-decoded execution representation |

Plan is not another Graph. Its purpose is to **remove repeated topology decisions from execution**.

### 2.5 Step 5 — Execute

Sequential Plan evaluation receives borrowed input, compiled instructions, pre-resolved callables/types, and an owned output result, then runs. Ideally, the per-value path no longer walks arbitrary Graph topology, looks up operator schema, infers types, chooses a backend, validates signatures, or decides rewrites. Those costs have already been paid. This is:

These checks are performed during construction, so execution can use the validated transition definition.

## 3. A Real Rewrite: Why a Metadata Bit Is Not Enough

The canonical pipeline has only one Map, so it is not a good rewrite example by itself. Use a local variant, but write both the Graph nodes and the per-element value flow explicitly:

~~~text
input x
  ↓
Map(clamp)          # first Graph node
  ↓
y = clamp(x)
  ↓
Map(clamp)          # second Graph node
  ↓
z = clamp(y) = clamp(clamp(x))
~~~

This is **sequential composition of two Map nodes**. Expanding one element yields the nested function application `clamp(clamp(x))`. It is not recursion because the implementation of `clamp` does not call itself. Assume `clamp : int -> int` and the actual idempotence law:

~~~text
∀x, clamp(clamp(x)) = clamp(x)
~~~

Then write the transformation explicitly:

~~~text
before:
x -> Map(clamp) -> clamp(x) -> Map(clamp) -> clamp(clamp(x))

after:
x -> Map(clamp) -> clamp(x)
~~~

The current CFlow optimizer has the stable semantic rewrite id `IDEMPOTENT_MAP_ELIMINATION`, and traced optimization can record the input subgraph, retained node/callable index, and removed node/callable index.

| Evidence | Answers |
|---|---|
| Proof of Rule | whether the rewrite is valid in general |
| Trace of Instance | where this concrete rewrite occurred |

### 3.1 Property Claim Only Handles Admission

A C callable may claim `IDEMPOTENT`, but that is only claim/admission metadata. Rewrite correctness comes from the semantic law. If a C function falsely claims:

~~~text
IDEMPOTENT
~~~

Lean does not magically prove that arbitrary machine code satisfies the law. The trust chain must therefore include:

~~~text
implementation identity
+
metadata claim
+
trusted/verified semantic meaning
+
rewrite theorem
+
rewrite trace
~~~

Chapter 6 established this trusted chain.

### 3.2 Lean Already Has the Corresponding Theorem

The current formal Rewrite proof includes `map_idempotent_elimination` and `certified_rewrite_preserves_observations`. The book no longer has to say “in theory, one day we could prove the optimizer.” Instead it can discuss:

how an existing rewrite theorem authorizes an existing optimizer rule. That is the professional loop between Modern C and Lean.

## 4. Direct / AOT: The Simplest Path Should Not Need Plan at All

Plan is already much simpler than Graph interpretation. But for a very simple, closed, synchronous Filter/Map pipeline, even Plan may be unnecessary. The current CFlow Direct/AOT path supports Filter and Map in a bounded Stage IR. with an explicit stage-count limit. Each stage must satisfy strict eligibility.

### 4.1 Direct Eligibility Is Permission to Delete Runtime Abstraction

Current direct-stage eligibility checks:

- type is direct-eligible;
- callable can bind;
- `capture_size = 0`;
- `effects = PURE`;
- required properties include `DETERMINISTIC`, `TOTAL`, and `NO_ALIAS`;
- signature protocol/type chain matches.

Filter also requires a bool return and output type = input type. Map requires the return type itself to be direct-eligible. These checks answer:

When are we entitled to skip the generic invoke/runtime layer completely?

### 4.2 AOT Dispatch Has Several Authorities

The current Stage IR can represent `STATIC_TARGET`, `CANONICAL_RAW_BATCH`, and `ADAPTER`. A surface callable therefore does not imply every path can become a direct static C call. Eligibility must match the real dispatch authority.

### 4.3 The Important Promise of the Direct Macro Path

The generated Direct array path explicitly promises no indirect stage callback, no allocation, and no scheduler operation, while validating input/output storage, capacity, overflow, aliasing/range overlap, and the type chain. Failure returns explicit `INVALID_ARGUMENT`, `INELIGIBLE`, or `CAPACITY_EXCEEDED`; it does not silently fall back to Plan or Kernel. This anticipates Chapter 14's No Silent Fallback discipline.

### 4.4 Current Direct Does Not Mean Full Reduce Lowering

The current closed Direct pipeline focuses on Filter/Map. For canonical `Filter → Map → Reduce`, Reduce should currently use a compiled Plan. We do not overstate Direct/AOT as “arbitrary Graph always becomes one ordinary loop.” A professional book should describe support boundaries more clearly than marketing material.

## 5. Parallel Reduce: Parallelism Is an Execution Refinement, Not a Graph Rewrite

Reduce is a useful example. The semantic Graph can remain `Reduce(sum)` while execution chooses sequential reduce or, under strict premises, ordered parallel reduce. These are different classes of transformation.

### 5.1 Separate Semantic Rewrite from Physical Execution Refinement

A semantic rewrite can be written as **Map(identity) → remove**: it changes semantic IR shape while a theorem proves observations remain equal. By contrast, **Reduce sequential ⇒ Parallel Reduce** denotes an admitted physical execution refinement: the semantic operator stays the same while the execution form changes. The notation is deliberately different: `→` denotes semantic rewrite; `⇒` denotes execution refinement. The formal calculus explicitly distinguishes **rewrite rule** from **execution refinement rule**.

### 5.2 Parallel Reduce Needs a Full Admission Contract

At minimum it requires:

- homogeneous reducer;
- PURE;
- TOTAL;
- an ASSOCIATIVE semantic law;
- the required order model;
- CONCURRENT Executor capability;
- supported value storage;
- valid task/chunk bounds.

A worker pool existing is not sufficient reason to parallelize Reduce.

### 5.3 Unsupported Parallel Mode Must Not Quietly Retry Sequentially

The current Plan contract explicitly makes:

~~~text
unsupported plan
insufficient nonempty chunks
invalid options
rejected tasks
    ↓
false / explicit failure
~~~

rather than:

~~~text
parallel failed
    ↓
quietly rerun sequentially
~~~

Why? Because silent fallback can change latency/resource behavior, hide admission bugs, violate caller policy, and distort benchmarks. Fallback should itself be an explicit policy in a higher layer.

## 6. Certificate / Proof Trace: Bind Execution Artifacts to Graph

After Plan has decoded execution, Graph topology leaves the hot path. How do we know Plan still corresponds to the approved normalized Graph? The current certificate records version, certified path, order, required capabilities, graph version, graph fingerprint, and semantic rows. Each row contains opcode, instruction index, callable index, effects, properties, input/output type, callable, and typed parameter. A certificate is therefore not “trust me, this plan was compiled”; it is a checkable execution witness.

### 6.1 Certificate Is Not a Wire Format

The current implementation contains pointer-bearing rows, process-local Graph identity, and an execution-only witness. Therefore it must not be serialized to disk, shipped to another process, or treated as stable identity through raw pointer/address. This follows the earlier semantic-identity principle.

### 6.2 Version + Fingerprint Prevent Stale Artifacts

After Graph mutation, version changes and certificate binding fails. When stronger structural binding is needed, fingerprint helps ensure rows/topology/callables still correspond. The purpose is not cryptographic signing. It is:

prevent an execution artifact from remaining “trusted” after the source program has changed.

### 6.3 Lean Already Proves Certificate / Refinement Observation Preservation

The formal proof includes `certificate_preserves_observation`, `parallel_certificate_preserves_observation`, and `execution_refinement_preserves_semantics`. Importantly, `parallel_certificate_preserves_observation` is not unconditional. It requires premises such as:

~~~text
CertificateValid(...)
certificate.path = orderedParallelReduce
ParallelReducePremises Γ K ty
~~~

Under those premises it combines two proof obligations:

~~~text
Graph-to-Plan observation equality
+
Reduce ⇒ ParallelReduce physical execution refinement
    ↓ proof composition
same semantic result
~~~

The downward arrow means “derive the conclusion from both proofs,” not execution order. Certificate is therefore more than a runtime validation feature. It is a bridge between the **formal theorem** and the **C runtime witness**.

### 6.4 Proof Trace: Why Record Which Rewrite Happened?

Certificate primarily answers: “Is this Plan / execution path bound to this Graph?” Proof Trace answers: “Why is this optimized Graph allowed to come from that source Graph?” The traced optimizer transactionally produces optimized Graph + owned rewrite trace, and binds exact source Graph object/version plus exact optimized Graph object/version. The trusted chain becomes:

~~~text
Lean:
    proves rewrite rule

Optimizer:
    emits rewrite instance trace

Checker/AOT matcher:
    verifies this trace matches concrete Graphs

Plan Certificate:
    binds execution artifact to approved optimized Graph
~~~

This is far stronger than merely recording “optimizer says success.”

## 7. Cost Model: Lean Should Not “Prove Benchmark Numbers” Either

Formalization can describe representation/refinement cost dimensions such as graph queries, scheduler hops, buffering, and dispatch layers. The current formal Cost proof includes:

- `direct_excludes_kernel_trigger`;
- `plan_excludes_kernel_trigger`;
- `direct_cost_dominates_plan`;
- `plan_cost_dominates_kernel`;
- `costed_refinement_preserves_semantics`.

But these theorems must be read precisely. For example, `direct_cost_dominates_plan` also requires `0 < workload.items * workload.operators`. meaning the workload actually contains callback work. It is not a universal “better even for empty workloads” claim. The theorem says:

> under a given abstract cost model and premises, one representation removes certain cost dimensions while preserving semantics.

It does not prove “17.3% faster on this CPU,” “Clang 19 will always inline,” an exact L1 cache-miss reduction, or “Windows is faster than Linux.” Real wall-clock/perf claims require benchmarks. Again: **formal evidence ≠ empirical evidence**.

## 8. Performance Evidence: This Chapter Needs Measurement Discipline

The current CFlow implementation has dedicated benchmarks: cflow_direct_benchmark, cflow_parallel_reduce_benchmark, cflow_graph_path_benchmark, cflow_branching_csr_benchmark, cflow_reactive_benchmark, and cflow_machine_hierarchy_benchmark. Any concrete performance claim in the book should record commit, compiler, compiler version, optimization flags, platform/CPU, input size, operator count, warmup, repetition count, statistic, and baseline.

### 8.1 The Canonical Data-Flow Benchmark Should Compare at Least

- hand-written C loop;
- Graph/kernel execution;
- compiled Plan;
- eligible Direct Filter/Map prefix.

For the full pipeline containing Reduce, also compare hand-written sequential loop, sequential compiled Plan, and ordered parallel reduce Plan. Paths not supported by Direct must be marked **not eligible**. rather than assigned a fallback number.

### 8.2 Measure Control-Plane Cost Too

Build Once, Execute Many does not mean build cost is zero. Measure Graph build, normalize, optimize, plan compile, certificate build/check, and execution separately. Then answer the real engineering question:

> How many executions are needed before the up-front control-plane cost is amortized?

That is more useful than only reporting one hot-loop ns/op number.

### 8.3 Do Not Write “X Times Faster” Without Fresh Measurement

The book can explain which dynamic steps Direct removes in theory, why Plan no longer performs topology queries, and what additional work Graph interpretation performs. Concrete numbers belong only after a canonical benchmark runs at a fixed commit. This editorial discipline prevents an engineering book from becoming performance marketing.

## 9. Summary

Normalization standardizes representation, optimization applies approved rules, and plan compilation resolves operations and connections ahead of time. Execution can then use predetermined handlers and storage slots. Each stage needs a defined input snapshot, rejection conditions, and an argument for semantic preservation. The pinned Direct path covers eligible Filter/Map computations within its supported scope; the full Filter/Map/Reduce example should use a compiled plan where required. Unsupported execution modes must be reported explicitly rather than silently changing policy. Construction, compilation, and execution costs should be measured separately.
