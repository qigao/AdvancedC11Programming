# Chapter 9: Reactive Execution: Waiting, Waking, Demand, and Backpressure

The same filtering and mapping computation can process an array or network data that has not arrived. An array usually supplies the next element immediately; an external source may temporarily have none. Reactive execution preserves unfinished work, resumes after conditions change, and limits downstream delivery. This chapter applies CMeta type and lifetime contracts to subscription state, examining delivery, waiting, waking, cancellation, and completion.

A **continuation** is the information needed to resume unfinished computation, such as execution position, retained values, and node state. A C implementation can keep it in structures without retaining an entire thread stack. **Demand** is the number of values downstream still permits. **Backpressure** constrains delivery and related resource use by downstream capacity.

## 1. Outcomes of One Resume Call

The pinned interface represents a resume result with `cflow_step`. The table distinguishes outcomes that construct a live value in the caller's empty storage from outcomes that leave it empty. A **live value** is an initialized object whose lifetime has not ended; empty storage does not yet contain such an object.

| Outcome | Output storage | Next action |
|---|---|---|
| `CFLOW_STEP_VALUE` | One live value | Process it through the graph; the source may resume again |
| `CFLOW_STEP_VALUE_AND_DONE` | One live value | Process the final value, then record source completion |
| `CFLOW_STEP_WAIT` | Remains empty | Preserve the continuation and obtain a waitable |
| `CFLOW_STEP_DONE` | Remains empty | Record source completion and handle unfinished graph output |
| `CFLOW_STEP_ERROR` | Remains empty | Enter failure handling and settle live state |

`WAIT` only reports that no value is currently available. It consumes no demand, does not finish the run, and does not establish a notification registration. A **waitable** provides registration and cancellation operations. A **waker** is the notification callback used when conditions may have changed. To **arm** is to register that callback; arming and receiving `WAIT` are separate steps.

Resumption still obeys CMeta object contracts. Saving a borrowed pointer does not keep its object alive across suspension, and the next resume cannot simply overwrite a live output. The pinned `cflow_resumable_ops` requires output construction only for the two value-producing outcomes; all others leave storage empty.

## 2. Account for Demand at Delivery

Consider `Filter(is_even)` followed by `Map(square)`. With one requested downstream value, the source may first return 1 and then 2. Filtering discards 1; mapping turns 2 into output 4. One delivery therefore required two source values. Operators that change output counts require accounting at the graph's outlet, rather than at every source `VALUE`.

The following C11 teaching fragment is for serialized use. Argument `d` must address a valid writable counter. It demonstrates saturating addition and one-credit consumption, not the concurrent runtime or subscription termination checks. The actual request API separately rejects a zero request.

~~~c
#include <stdbool.h>
#include <stddef.h>
#include <stdint.h>

typedef struct demand_counter {
    size_t remaining;
} demand_counter;

/* Serialized teaching model; not safe for concurrent callers. */
static size_t demand_add(demand_counter *d, size_t n)
{
    size_t room = SIZE_MAX - d->remaining;
    size_t added = n < room ? n : room;
    d->remaining += added;
    return added;
}

static bool demand_take(demand_counter *d)
{
    if (d->remaining == 0)
        return false;
    --d->remaining;
    return true;
}
~~~

**Saturating addition** retains the maximum value instead of wrapping to zero. Computing `SIZE_MAX - remaining` first determines the available room; adding only what fits cannot overflow. Concurrent requests require synchronization around reading, checking, and updating. Calling this ordinary C code from multiple threads would introduce a data race.

Let `A` count credits actually added, `E` count deliveries reserved and begun, and `D` be remaining demand. Without a reset, the teaching model maintains `D = A - E`. These cumulative quantities are mathematical integers. When addition saturates, `A` increases only by credits that fit, rather than by every requested argument. Delivery takes its credit before invoking downstream. Subsequent rejection by the callback fails the run; it does not make the invocation disappear from accounting.

| Event | Source values obtained | Downstream deliveries | Remaining demand |
|---|---:|---:|---:|
| Request one value | 0 | 0 | 1 |
| Source returns 1; Filter discards it | 1 | 0 | 1 |
| Source returns `WAIT`; a wake follows | 1 | 0 | 1 |
| Source returns 2; deliver square 4 | 2 | 1 | 0 |

Induct on events to establish the accounting invariant. A request increases only `A` and `D`; successful credit consumption increases `E` and decreases `D`; source reads, waiting, and waking leave all three unchanged. Since `demand_take` refuses to decrement zero, `E <= A`. This bounds delivery counts, not automatically source attempts, buffering, or scheduler queues.

## 3. Drive Through the Graph's Outlet

The following teaching pseudocode includes a step budget and is not a transcription of `subscription.c`. The budget limits consecutive work during one scheduler turn; it illustrates an additional fairness requirement, not an existing parameter of the pinned runtime. Every live value still needs an owner: release it after filtering, retain it when accumulating, and end the borrow after delivery.

~~~text
drive(run, step_budget):
    while run is RUNNING and run.wait is READY and step_budget > 0:
        step_budget -= 1
        if a downstream value is pending:
            if demand is zero: return
            reserve one credit
            invoke the subscriber with the borrowed value
            release the value; terminate on subscriber rejection
        else if source is done:
            advance draining or finish, if permitted by its contract
            return if draining needs credit that is unavailable
        else:
            if demand is zero: return
            result = resume source into empty storage
            VALUE / VALUE_AND_DONE:
                pass the value through the graph
                save any pending output or per-node state
                for VALUE_AND_DONE, mark source done
            WAIT:
                register waiting; return
            DONE:
                mark source done
            ERROR:
                terminate with error; return
    if runnable work remains: request a later turn
~~~

A source value first passes through graph processing. Only a pending downstream output reserves delivery credit. Reduce may consume several source values before producing a result, while Filter may discard several before producing one output. If an infinite source never satisfies the predicate, an unbudgeted loop may occupy a thread indefinitely even with demand one. Credit limits, per-turn execution budgets, and storage capacities are separate constraints.

Completion notification is also distinct from value delivery. Completion with no pending value need not consume credit; an accumulated result still needs its output credit. The pinned source interface additionally provides terminal polling so execution can observe completion when needed. “At zero demand, ignore every terminal event” is not a complete protocol.

## 4. Derive Registration from the Lost-Wakeup Race

A lost wakeup can occur when the consumer sees `WAIT`, the source becomes ready and signals before registration, and the consumer subsequently suspends with no notification left to receive. Checking readiness after registration covers that interval. However, a callback between the final check and the write of the suspended state can still lose the signal.

Use an explicit teaching model. The provider's `arm_and_observe` connects registration with readiness observation: prior readiness is observable, and later changes notify the registered waker. A transient event that cannot remain observable needs a retained event or sequence number. This pseudocode operation is not an SDK name. Actual `cflow_waitable.arm` returns a Boolean; a provider can indicate an already-observed signal by invoking the waker synchronously.

Waiting state and the callback share one lock. The execution owner serializes resumption and re-registration; callbacks only modify waiting flags and request scheduling. Provider calls, callback-quiescence waits, and scheduler calls occur outside the lock because they can invoke callbacks immediately or wait for another thread. The run and registration context must remain alive throughout these operations.

~~~text
arm_wait(run):
    lock(run)
    if run is terminal: unlock(run); return
    g = allocate a fresh, non-reused registration token
    run.token = g
    run.pending = false
    run.wait = ARMING
    unlock(run)

    outcome = provider.arm_and_observe(g, wake)   # may call wake now
    lock(run)
    if run is terminal:
        action = release_registration
    else if outcome is FAILED:
        mark terminal error
        action = release_registration
    else if outcome is SIGNAL or run.pending:
        run.wait = READY
        action = release_registration_then_schedule
    else:
        run.wait = SUSPENDED
        action = none
    unlock(run)
    perform action outside the lock
~~~

The matching wake pseudocode uses the same lock. `ARMING` means registration is in progress, `SUSPENDED` means registration completed without an observed signal, and `READY` permits a retry. Run termination is recorded separately.

~~~text
wake(run, g):
    lock(run)
    if run is terminal or g != run.token:
        unlock(run); return STALE
    if run.wait == ARMING:
        run.pending = true
        unlock(run); return
    if run.wait == SUSPENDED:
        run.wait = READY
        need_schedule = true
    else:
        need_schedule = false
    unlock(run)
    if need_schedule: request a coalesced execution turn
~~~

**Race argument.** A signal before registration must be observed as `SIGNAL` by the provider. During registration, the callback sets `pending` under the lock, causing the final check to choose `READY`. After the final check, the callback cannot acquire the lock until `SUSPENDED` has been written; it then changes that state to `READY`. Thus there is no gap in which the callback decides the run is not waiting and the owner then suspends. Repeated signals in `READY` coalesce and grant no credit.

The argument depends on the provider protocol and shared lock. An isolated `is_ready()` call is insufficient. It establishes that these transitions do not lose a signal, not that work eventually executes. If scheduler admission fails, the owner must retain the runnable fact and report the outcome rather than claiming eventual progress.

## 5. Registration Identity, Cancellation, and Callback Lifetime

A registration **token** identifies one wait; a **generation** distinguishes successive registrations on the same object. An old callback must not resume a newer wait. Model tokens are not reused while old callbacks can remain. A finite counter approaching wraparound needs an explicit rejection or quiescent reconstruction policy.

Token checking addresses identity, not memory lifetime. A callback must safely access the run before comparing its token. If the run has been freed, “detect stale and ignore” already performs an invalid access. **Quiescence** here means old callbacks have exited and cannot access the objects again through the old registration. Cancellation must invalidate that registration and establish quiescence before releasing its context.

An auditable close sequence establishes termination and prohibits new progress under synchronization, cancels registration and waits for in-flight callbacks outside the lock, then settles continuations, live values, and the source. Already-entered progress must finish or stop at a defined boundary before concurrent cleanup can access its state. A registration left active after the preceding wake is handled by the execution owner before reusing the waitable; a callback must not wait for itself to exit.

A terminal state is **absorbing** when no new normal computation step starts from it. This does not freeze every wait field: cleanup may continue, but an old notification cannot restart computation. The pinned close contract also distinguishes external calls from calls inside the subscription's own callback. External close completes synchronously; callback-initiated close defers destruction until the active pump returns.

## 6. Source Completion Can Precede the Last Result

For the even-square sum of `1, 2, 3, 4`, the source may return 4 with `VALUE_AND_DONE`. Execution first maps 4 to 16, combines it with accumulator 4 to obtain 20, and delivers that result. Treating source completion as immediate whole-run completion would lose 20.

**Draining** performs remaining accumulator output, buffer draining, or node finalization after the source stops producing new input. Graph structure stays unchanged, but the subscription records source termination, drain progress, and run termination separately. An empty unseeded reduction has no accumulator and must not manufacture a zero result.

| State fact | Meaning in this example |
|---|---|
| Source done | Do not request a fifth source element |
| Drain unfinished | Accumulator 20 still awaits delivery |
| Run completed | Pending output has obeyed demand and node finalization is complete |
| Run cancelled | The caller terminated execution; cancellation settles undelivered state |

Cancellation is a caller's control decision; an error is a source or computation failure. They need distinct terminal outcomes. In either case, the reusable graph must not contain this run's accumulator, demand, or cancellation flag.

## 7. Ownership in the Pinned C Interface

The following declarations are excerpted from [reactive.h](https://github.com/qigao/salts/blob/a650262031e9b3e5f11a227a7911a75db9ae1fb8/cflow/include/cflow/reactive.h), with other entry points omitted. An **opaque** handle lets callers use an object without depending on its internal layout. A `void *impl` field is not permission to cast it to a guessed internal structure.

~~~c
typedef struct cflow_subscription {
    void *impl;
} cflow_subscription;

bool cflow_subscribe(cflow_subscription *subscription,
                     const cflow_graph *graph,
                     cflow_publisher *publisher,
                     cflow_scheduler *scheduler,
                     const cflow_subscriber *subscriber);

cflow_status_result cflow_subscription_request_result(
    cflow_subscription *subscription, size_t n);
void cflow_subscription_close(cflow_subscription *subscription);
~~~

A subscription must initially be zeroed. Successful `cflow_subscribe` takes the Publisher and clears the caller's Publisher handle; failed admission leaves ownership with the caller. Graph, Scheduler, and Subscriber are borrowed. CMeta interface tables provide concrete invocation capabilities and type contracts, while the subscription separately owns demand, waiting, and live-object state. Descriptors do not extend borrowed lifetimes.

The pinned `cflow_subscription_request_result` rejects `n == 0`, adds demand with saturation, and then attempts to schedule the pump. Immediate scheduling failure retains the demand already recorded; a later explicit trigger may retry scheduling. A caller must not blindly add the same request again after a non-success result, which could double-count it. `CLOSED` can mean either an already-completed subscription or a scheduler that rejected work after accounting; interpret it with subscription state and outstanding demand.

The downstream value callback borrows its value only for the callback's duration. Retaining it requires a permitted copy, move, or reference-holding protocol. Saving the parameter address for later provides no lifetime guarantee. Type checking, execution admission, and object lifetime address related but separate obligations.

## 8. Relate the Hand Arguments to Lean Theorems

**Small-step semantics** represents execution as local state transitions, each handling an event such as source acquisition, registration, waking, or delivery. The pinned [execution model](https://github.com/qigao/salts/blob/a650262031e9b3e5f11a227a7911a75db9ae1fb8/formal/cmeta_cflow_calculus/CMetaCFlowCalculus/CFlow/Execution.lean) and [proof file](https://github.com/qigao/salts/blob/a650262031e9b3e5f11a227a7911a75db9ae1fb8/formal/cmeta_cflow_calculus/CMetaCFlowCalculus/Proofs/Execution.lean) provide such a model. This chapter's new teaching pseudocode is not generated from those files and adds no machine-checked proof.

Consider “zero demand cannot deliver.” The following existing proof is read within its original module and definitions. `before` and `after` are configurations, `Step` is a permitted transition, `event.EmitsValue` means delivery, and `¬` denotes negation.

~~~lean
theorem zero_demand_no_value {sourceTy outputTy : CMeta.Ty}
    {before after : Config sourceTy outputTy}
    {event : Event sourceTy outputTy}
    (zero : before.runtime.demand = .finite 0)
    (step : Step before event after) :
    ¬event.EmitsValue := by
  intro emits
  obtain ⟨n, positive, _⟩ := step_value_decrements_demand step emits
  rw [zero] at positive
  simp at positive
~~~

Assuming a delivery, `step_value_decrements_demand` establishes that demand before the transition was `n + 1`. Substituting the known zero demand contradicts the positivity of that natural number. A **witness** is evidence establishing a premise, such as the positive-credit evidence provided by successful consumption. It is neither another delivery nor an arbitrary Boolean flag in runtime code.

| Existing theorem | Property established in the model | Implementation obligation or limit |
|---|---|---|
| `source_value_preserves_demand` | Source acquisition preserves credit | Consume at the graph outlet rather than source inlet |
| `wait_arm_wake_preserves_source` | Quiet arm and matching wake preserve the continuation, credit, and other payload state | Notification must not reconstruct or discard live values |
| `signal_before_arm_is_ready`, `signal_concurrent_with_arm_is_ready` | An observed signal leaves waiting state ready | The platform protocol must implement those observation conditions |
| `arm_issues_fresh_token` | Each arm obtains its token and advances generation | C still needs finite-counter and callback-lifetime handling |
| `terminal_no_step`, `cancel_unarms_and_terminates` | Termination prevents new steps; cancellation establishes termination | Locks, callback exit, and destruction still require validation |

**Safety** excludes forbidden events, such as delivery without demand. **Liveness** establishes eventual desired progress. These state-machine results do not ensure eventual device readiness, fair scheduling, or freedom from permanent thread starvation. Relating C execution to the model is a **refinement** obligation: actual synchronization, failures, and resource handling must implement the modeled transitions. Similar-looking structure fields do not prove that relationship.

## 9. Scheduling Strategies and Repeatable Validation

A scheduler selects when and in which execution context a subscription progresses. It does not change Filter, Map, or Reduce meaning. **Admission** checks capabilities and capacity before accepting work; rejection must not become implicit capacity growth or silent substitution of an execution strategy.

| Strategy | Progress mechanism | Useful property to check |
|---|---|---|
| Inline | Accepted zero-delay work executes before admission returns | Immediate callbacks require initialization to be complete first |
| Manual | Caller-driven bounded ready queue, without a timer clock | Execution order controlled without thread races |
| Test / Manual Clock | Explicit logical-time advancement | Deterministic wait, timer wake, and cancellation order |
| Worker | Worker threads with bounded ready and timer capacity | Concurrent callbacks, full queues, and shutdown ownership |

Implementation references are [scheduler.h](https://github.com/qigao/salts/blob/a650262031e9b3e5f11a227a7911a75db9ae1fb8/cflow/include/cflow/scheduler.h), [subscription.c](https://github.com/qigao/salts/blob/a650262031e9b3e5f11a227a7911a75db9ae1fb8/cflow/src/subscription.c), and [readiness.c](https://github.com/qigao/salts/blob/a650262031e9b3e5f11a227a7911a75db9ae1fb8/cflow/src/readiness.c). The teaching token model does not claim a field-for-field copy in the runtime subscription. Actual synchronization and identity responsibilities are distributed across the subscription, wait adapter, and underlying registration.

The [reactive tests](https://github.com/qigao/salts/blob/a650262031e9b3e5f11a227a7911a75db9ae1fb8/cflow/tests/cflow_reactive_test.c) check retained and consumed demand and scheduler rejection. The [readiness tests](https://github.com/qigao/salts/blob/a650262031e9b3e5f11a227a7911a75db9ae1fb8/cflow/tests/cflow_readiness_test.c) include failed admission retaining ownership, cancellation waiting for an old callback to become quiescent, and user close/free waiting for an in-flight callback. These are cases in the pinned source, not measurements newly rerun for this chapter.

Validation of the teaching model should distinguish zero-credit rejection, filtering without consumption, and saturation without wraparound; signals before, during, and after registration; duplicate and stale notifications; source completion with pending output; retained credit after queue rejection; and cancellation preventing old callbacks from accessing freed storage. Finite event enumeration can check the modeled race branches. Real concurrent tests must additionally validate platform synchronization and object lifetimes.

## 10. Summary

Reactive execution applies CMeta type and lifetime contracts to computation across time. The source obtains values, the graph processes them, and the outlet delivers under demand; waiting and waking only change when a retry is possible. Correct registration depends on an observable provider protocol and atomic waiting-state transitions, while cancellation must also wait for old callbacks to exit. Keeping these facts separate makes empty output, draining, backpressure, and cleanup explainable without treating notification as data or additional permission to deliver.
