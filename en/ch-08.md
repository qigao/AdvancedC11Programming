# Chapter 9: Reactive Execution: Waiting, Waking, Demand, and Backpressure

An array traversal can usually obtain its next element immediately; network or timer input may temporarily have no data. Reactive execution preserves unfinished computation and resumes when input is ready and downstream permits delivery. This chapter keeps the existing graph, puts live state in the subscription, and derives polling, wait registration, waking, and cancellation rules from demand and state invariants.

**Terminology:** Demand is the remaining number of values the downstream consumer permits. Backpressure constrains production or delivery by downstream capacity. This chapter uses explicit demand to limit deliveries; a wake notification only indicates that conditions may have changed and grants no additional demand.

## 1. Source Poll Protocol: VALUE / WAIT / DONE / ERROR

**A continuation** holds the information needed to resume unfinished computation, such as its execution position, retained values, and node state. In this chapter’s C implementation, explicit state structures can hold it; language-level coroutines or preservation of an entire thread stack are not required.

Start with C instead of the word “asynchronous”:

~~~c
typedef enum cflow_poll_kind {
    CFLOW_POLL_VALUE,
    CFLOW_POLL_WAIT,
    CFLOW_POLL_DONE,
    CFLOW_POLL_ERROR
} cflow_poll_kind;

typedef struct cflow_poll_result {
    cflow_poll_kind kind;
    int error;
} cflow_poll_result;

cflow_poll_result
source_poll(source *src, value *out);
~~~

A synchronous source usually needs VALUE, DONE, and ERROR. An asynchronous source adds WAIT. `WAIT` means only: **no value now; the continuation is still valid; poll again after an external condition changes.** It does not mean block, sleep, spin, consume demand, or complete.

## 2. Subscription State Machine

**Terminology:** A waitable represents a condition or object on which a wait can be registered. A waker is the notification entry point used when that condition may have changed; arm registers the notification. A wake generation distinguishes successive registrations so an old callback cannot incorrectly resume a new wait.

Graph remains immutable program structure. Live execution state belongs to Subscription:

~~~c
typedef enum subscription_state {
    SUB_READY,
    SUB_ARMING,
    SUB_SUSPENDED,
    SUB_TERMINAL
} subscription_state;

typedef struct subscription {
    subscription_state state;
    uint64_t demand;
    uint64_t wake_generation;
    bool wake_pending;
} subscription;
~~~

Execution:

~~~text
READY
  poll -> VALUE  : emit; demand--; stay READY
  poll -> WAIT   : ARMING
  poll -> DONE   : TERMINAL
  poll -> ERROR  : TERMINAL

ARMING
  install waker
  recheck source
  ready          : cancel arm -> READY
  still waiting  : SUSPENDED

SUSPENDED
  matching wake  : READY
  cancel         : TERMINAL

TERMINAL
  no further step
~~~

## 3. Poll Loop Pseudocode

~~~text
drive(subscription):

    while subscription.state == READY:

        if subscription.demand == 0:
            return

        r = source.poll()

        match r:
            VALUE:
                downstream.emit(value)
                subscription.demand -= 1

            WAIT:
                subscription.state = ARMING
                arm_wait(subscription)
                return

            DONE:
                subscription.state = TERMINAL
                downstream.complete()
                return

            ERROR:
                subscription.state = TERMINAL
                downstream.error(r.error)
                return
~~~

Demand is now precise:

- Demand limits emitted VALUEs.
- Demand does not count poll attempts.
- `WAIT` does not consume demand.
- Wake does not consume demand.

Ledger:

~~~text
emitted <= requested

requested - emitted = remaining demand
~~~

## 4. Lost Wakeup: Why ARMING Requires Recheck

Broken interleaving:

~~~text
T0  poll() -> WAIT
T1  source becomes ready
T2  source emits wake
T3  consumer installs waker
T4  consumer sleeps forever
~~~

Therefore do not implement:

~~~text
WAIT
 -> install waker
 -> sleep
~~~

Use:

~~~text
WAIT
 -> ARMING
 -> install waker
 -> recheck readiness
 -> only then SUSPENDED
~~~

Pseudocode:

~~~text
arm_wait(sub):

    g = sub.wake_generation + 1
    sub.wake_generation = g

    source.install_waker(g, wake_callback)

    if source.is_ready():
        source.cancel_waker(g)
        sub.state = READY
        schedule(sub)
        return

    if sub.wake_pending_for(g):
        sub.state = READY
        schedule(sub)
        return

    sub.state = SUSPENDED
~~~

The real proof obligation is: **ready-after-first-WAIT cannot be lost between arm and suspend**.

## 5. Wake Rule and Generation

Wake does not execute Graph directly. It changes state and schedules:

~~~text
wake(sub, generation):

    if sub.state == TERMINAL:
        return STALE

    if generation != sub.wake_generation:
        return STALE

    if sub.state == ARMING:
        sub.wake_pending = true
        return OK

    if sub.state == SUSPENDED:
        sub.state = READY
        scheduler.schedule(sub)
        return OK

    return ALREADY_READY
~~~

Generation prevents completion from an old wait cycle from waking a newer one.

## 6. Scheduler Decides Only When to Continue

Scheduler does not own Graph or demand semantics. A minimal interface might look like:

~~~c
typedef struct scheduler_vtable {
    int (*schedule)(void *self, subscription *sub);
    int (*schedule_at)(void *self, uint64_t deadline, subscription *sub);
} scheduler_vtable;
~~~

| Object | Owns |
|---|---|
| Graph | operator topology |
| Subscription | live demand/wait/terminal state |
| Source | readiness + value production |
| Waker | one resume signal |
| Scheduler | when a READY subscription runs |
| Executor | where/how scheduled work runs |

Do not merge these into one giant Reactive runtime object.

## 7. Failure Paths

At least these failures are explicit:

- `request(0)`: no-op or invalid by contract;
- request while TERMINAL: return `CLOSED`;
- wake with stale generation: return `STALE`;
- exhausted arm-resource capacity: return a bounded error, not a hidden allocation.

The core invariant is **TERMINAL is absorbing**. That is:

~~~text
state = TERMINAL
─────────────────
no VALUE / WAIT transition
~~~

The formal model later in the chapter proves rules that are already concrete here.

## 8. Canonical Example: Graph Is Unchanged, Source Acquires Time

The synchronous Stream from Part II is the following **value dataflow**:

~~~text
input array / Range
      ↓ value
Source<int>
      ↓ value
Filter(is_even)
      ↓ value
Map(square)
      ↓ value
Reduce(sum)
~~~

A synchronous source hides the assumption:

> every query immediately produces a value or immediately completes.

Reactive changes only that assumption. Graph still contains the Filter(is_even), Map(square), and Reduce(sum) operators. The source protocol changes. This is not a sequence; these are **five mutually exclusive outcomes of one resume() call**:

~~~text
resume()
  ├─ VALUE
  ├─ VALUE_AND_DONE
  ├─ WAIT
  ├─ DONE
  └─ ERROR
~~~

WAIT means:

There is no value now, but this continuation is still valid; when external conditions change, the system may wake and retry. It is not sleep current thread, treat as DONE, or spin until something appears. That one distinction lets the same Graph extend from already-materialized input to timer, channel, readiness, socket/pipe/file completion, or a custom asynchronous publisher without redesigning operator semantics.

## 9. Semantic Contract: Reactive Adds Execution State, Not Graph State

The most important separation is:

| Object | Meaning |
|---|---|
| Graph | immutable/reusable program description |
| Subscription | one live execution |

### 9.1 WAIT Is a Source Outcome, Not “Arm Already Succeeded”

When a source returns `WAIT`, it says only that the continuation is saved and a waitable is available. A separate `arm(waitable, waker)` step still exists. Therefore **WAIT ≠ SUSPENDED**. A more accurate transition is:

~~~text
READY
  ↓ resume returns WAIT
PENDING_ARM
  ↓ arm succeeds quietly
SUSPENDED
  ↓ matching wake
READY
~~~

Separating WAIT from armed suspension is the key to lost-wakeup correctness.

### 9.2 Wake Does Not Produce Demand

Wake means:

> external conditions may have changed, so rescheduling the continuation is appropriate.

It does not mean “one more downstream value is allowed.” Wake must preserve demand.

| Concept | Meaning |
|---|---|
| readiness | can retry |
| demand | downstream permits output |

They come from different sources of truth.

### 9.3 Demand Means Downstream Values, Not Publisher Pull Count

This remains one of the easiest Reactive mistakes. For:

~~~text
Source<int>
    ↓
Filter(is_even)
    ↓
Map(square)
~~~

if downstream requests `demand = 1`, that does not mean `source.resume() exactly once`. The first input may be filtered away. Producing one downstream value may require several source resumes. So:

Demand is consumed only when one value is actually emitted downstream. Source VALUE does not automatically consume downstream demand. This lets Filter, FlatMap, Relation, and other cardinality-changing operators share one consistent demand meaning.

### 9.4 Terminal Must Have One Source of Truth

Reactive termination should not be assembled from many booleans such as `done`, `cancelled`, `failed`, and `maybe_source_done`. A clearer model is:

~~~text
RUNNING
DONE
ERROR(message)
CANCELLED
~~~

Once terminal state exists, no new kernel small-step may begin. We must distinguish **source done** from **whole run done**, because after source completion the Graph may still need reduce finalization, buffer drain, or pending terminal emission. The run lifecycle therefore keeps an explicit draining phase:

~~~text
source completion
    ↓ enter draining
draining
    ↓ downstream finalized
whole-run DONE
~~~

The arrows are lifecycle transitions; source done and whole-run done are different states.

### 9.5 Cancel Is an Explicit Semantic, Not an Alias for Error

Cancel should:

- stop new execution progress;
- unarm/cancel the active wait registration;
- establish CANCELLED terminal state;
- release or settle live state according to ownership contracts.

It is not:

~~~text
ERROR("cancelled")
~~~

because cancellation is a control-plane decision, while error is a computation/source failure.

### 9.6 Subscription Is the Single Owner of Live State

Graph should not store demand, wait registration, cancelled flag, reduce accumulator, slice counter, live temporary values, or opened backend state. Those belong to one execution. A Subscription ownership contract is therefore approximately:

~~~text
owns:
    moved Publisher
    demand
    wait state
    continuation/live slots
    per-node mutable state
    cancellation/terminal/error state

borrows:
    immutable Graph
    Scheduler
    Subscriber
    backend/interface tables
~~~

This boundary is what later allows Executor, Machine, and Actor to compose safely.

## 10. Lean: A Real Reactive Small-Step Calculus Already Exists

We do not need to invent a hypothetical model. The edition Salts snapshot contains:

~~~text
formal/cmeta_cflow_calculus/
  CMetaCFlowCalculus/CFlow/Execution.lean
  CMetaCFlowCalculus/Proofs/Execution.lean
~~~

It explicitly models:

~~~text
SourceState
Demand
WaitState
Terminal
SourceTerminal
DrainState
RuntimeState
Config
SourceResult
SourceStep
ArmStep
WakeStep
EmitStep
DrainStep
FinishStep
CancelStep
~~~

This is a good example of Lean clarifying C design.

### 10.1 `Demand.consume`: Zero Demand Cannot Emit

The formal model defines demand as a finite remaining quantity:

~~~text
consume(0)
    = none

consume(n + 1)
    = some(n)
~~~

A witness is evidence that a required proposition holds. In the demand model, successful `consume` provides evidence that positive demand was available and decremented. It is not another delivery and cannot be replaced by a wake notification. A downstream emission therefore requires a successful consume witness. Existing theorem `step_value_decrements_demand` states:

> each actual downstream value emission consumes exactly one demand.

And `zero_demand_no_value` states:

> when demand is zero, no value-emitting kernel step can occur.

This directly models the core C runtime backpressure safety property.

### 10.2 Source VALUE Does Not Directly Consume Downstream Demand

The theorem `source_value_preserves_demand` proves:

~~~text
SourceStep VALUE
    ↓
demand unchanged
~~~

because the source value may still pass through Filter, FlatMap, or another cardinality-changing computation. Demand is consumed at downstream EmitStep. That is the formal version of “Demand is not Publisher pull count.”

### 10.3 WAIT → Arm → Wake Preserves Continuation and Demand

The theorem `wait_arm_wake_preserves_source` states that after quiet arm + matching wake:

~~~text
saved continuation preserved
wait returns READY
ownership preserved
demand preserved
source terminal preserved
drain state preserved
run terminal preserved
wake generation advances exactly once
~~~

This is valuable because:

> Wake is neither data consumption nor state reconstruction; it safely resumes the same continuation.

### 10.4 Lost Wakeup Is More Than “Add a Lock”

The formal model distinguishes `noSignal`, `signalBeforeArm`, and `signalConcurrentWithArm`, and proves `signal_before_arm_is_ready` and `signal_concurrent_with_arm_is_ready`. so that readiness observed before or concurrently with registration cannot become a false suspended state. Also, `arm_issues_fresh_token` ensures each arm uses the current generation and advances generation exactly once. Stale wake can therefore be distinguished from the current registration. This is much stronger than simply saying “avoid lost wakeup.” It turns the race into an explicit state-machine contract.

### 10.5 Terminal Is Absorbing

The theorem `terminal_no_step` says:

~~~text
terminal != RUNNING
    ↓
no kernel Step can start
~~~

and `cancel_unarms_and_terminates` says Cancel performs:

~~~text
wait -> READY
terminal -> CANCELLED
~~~

This gives the C implementation a direct refinement target.

### 10.6 Safety and Liveness Must Remain Separate

Most theorems above are safety properties: no emission under zero demand, no step after terminal, no permanent lost suspension for already-observed arm races, and wake does not mutate demand. They do not automatically prove that an external device eventually becomes ready, Scheduler eventually runs a task, OS eventually returns I/O completion, or threads are never starved. Those require environment fairness or platform liveness assumptions. So:

Lean can prove how the state machine changes safely if an event occurs; it cannot manufacture the event in the real world.

## 11. Current C Implementation: Formal State Has Clear C Counterparts

Against the edition Salts snapshot `qigao/salts@ad389928b437c0612c1c60844fe53677f3ed27a6`:

### 11.1 Source Outcome Is a Five-State Protocol

The C API defines `CFLOW_STEP_VALUE`, `CFLOW_STEP_VALUE_AND_DONE`, `CFLOW_STEP_WAIT`, `CFLOW_STEP_DONE`, and `CFLOW_STEP_ERROR`, matching the formal SourceResult. WAIT also carries a waitable:

~~~text
arm(waker)
cancel()
~~~

Waiting is therefore a protocol object, not a boolean.

### 11.2 Publish Context Carries an Exact Downstream-Demand Snapshot

The current publish context stores scheduler and downstream_demand. and documents downstream_demand as:

> the exact outstanding downstream-value demand before Subscription calls resume.

A source may use it for bounded read/window admission, but cannot redefine its meaning. For example an I/O publisher can set:

~~~text
target window
=
min(downstream demand, configured capacity)
~~~

This connects backpressure to bounded resources.

### 11.3 Subscription Is an Opaque Execution Owner

Graph deliberately keeps concrete IR rows for introspection and verification. Subscription does the opposite:

~~~c
typedef struct cflow_subscription {
    void *impl;
} cflow_subscription;
~~~

because it owns live mutable execution state, locks/scheduling state, demand, wait registration, continuations, mutable node state, and terminal state. These details need freedom to evolve and must not be directly mutated by callers.

| Object | API shape |
|---|---|
| Graph | concrete read-only IR rows |
| Subscription | opaque mutable execution owner |

This is not inconsistent style; it follows different ownership roles.

### 11.4 Subscribe Uses Move-Style Publisher Ownership

Current contract:

~~~text
before success:
    caller owns Publisher

subscribe succeeds:
    Subscription takes Publisher
    caller Publisher is cleared

admission fails:
    ownership remains with caller
~~~

while Graph, Scheduler, and Subscriber remain borrowed. This makes recovery and destruction order easier to reason about.

### 11.5 Request Retains Demand Even If Scheduling Admission Temporarily Fails

The request API uses this **demand-accounting sequence**:

~~~text
demand accepted
    ↓ scheduling attempt
pump scheduling may fail immediately
    ↓ accounting unchanged
outstanding demand remains retained
    ↓ later trigger
later wake/request may retry
~~~

The arrows describe demand/accounting-state progression, not value dataflow. So scheduler queue full must not be interpreted as downstream no longer wants the value. Demand is a semantic fact. Scheduler admission is a resource fact. They are separate.

### 11.6 Wake May Be Called from Any Driver/Event-Loop Callback

`cflow_subscription_wake()` is an advanced integration hook that external event loops / driver callbacks may invoke. Wake re-enters Subscription pump admission rather than letting the driver mutate Graph execution state directly. This is a **control-notification path**:

~~~text
external readiness
    ↓ notify
wake notification
    ↓ enqueue/resume ownership
Subscription / Scheduler
    ↓ drive admitted work
Graph execution
~~~

It is not the flow of a data value itself.

## 12. Scheduler: Time and Execution Context Are Capabilities, Not an Inheritance Tree

Scheduler is also a small Interface rather than a class hierarchy. It declares capabilities such as DELAYED, MANUAL_CLOCK, CONCURRENT, and CALLER_DRIVEN_ZERO_DELAY, with several execution strategies.

### 12.1 Inline Scheduler

The Inline Scheduler timing guarantee is: **an accepted zero-delay task executes before admission returns**. It has no queue, clock, or timer storage, which makes it useful for explicit zero-hop boundaries.

### 12.2 Manual Scheduler

Manual Scheduler uses a bounded ready queue driven by caller operations `run_one` / `run_ready` / `run_until_idle`, with no timer clock. It is useful for external event loops, deterministic batch processing, and tests.

### 12.3 Test Scheduler / Manual Clock

It supports `post_after`, `advance(ticks)`, and `run_until_idle`, so time does not depend on `sleep(...)` or wall-clock races. and temporal tests can be deterministic.

### 12.4 Worker Scheduler

Moves dispatch to worker threads and exposes bounded ready/timer capacity plus statistics. Therefore:

> Scheduler answers when/where execution runs; it does not own Graph semantics.

## 13. Evidence: Reactive Must Validate Demand, Wait, Races, and Bounded Resources Together

One async demo is not enough. We need several forms of evidence.

### 13.1 Demand Conformance

Current Reactive tests check request result, outstanding demand retained/decremented, and that scheduler admission failure does not silently discard demand. Calculus-conformance tests directly observe:

~~~text
demand = 1
...
emit
...
demand = 0
~~~

matching `step_value_decrements_demand`.

### 13.2 WAIT / Waitable Evidence

Reactive, Temporal, I/O, and Machine-adapter tests all exercise:

~~~text
resume
    ↓
CFLOW_STEP_WAIT
    ↓
waitable valid
    ↓
arm(waker)
~~~

WAIT is therefore a shared subsystem protocol rather than a special socket state.

### 13.3 Wake Race / Quiescence Evidence

Readiness tests include concrete concurrency cases such as **cancel waits until old callback waker is quiescent**. These are C implementation race tests. Lean ArmTiming theorems give the state-machine safety model; real readiness tests verify:

> whether callback/lock/lifetime implementation follows that model.

Neither replaces the other.

### 13.4 Bounded Scheduler Evidence

Scheduler tests check bounded admission, for example:

~~~text
capacity = 1
second admission rejected_full
drain/advance
capacity reused
~~~

Backpressure is therefore more than a demand counter. It also includes bounded scheduling, bounded buffers, bounded publisher windows, and bounded operator state.

### 13.5 Temporal Determinism

Timer/temporal tests use controllable Scheduler/Clock paths to check **WAIT → advance time → wake → resume → terminal → cancel**. This is a stronger semantic regression gate than wall-clock sleep-based testing.

## 14. Summary

A reactive subscription retains execution position, live values, demand, and wait registration. WAIT means no value is currently available; suspension follows successful registration and rechecking. A matching wake permits another attempt, and only a delivered downstream value consumes demand. Cancellation and termination must settle live state and prevent stale callbacks from reviving completed execution. A model can establish invariant preservation under specified events; real I/O readiness and scheduler fairness require external assumptions and implementation evidence.
