# Chapter 2: Finite Metaprogramming: Generics, Structs, Traits, and Type Relations

Field and parameter lists are reused for declarations, type checks, and reflection. Independent consumers can disagree about element counts, positions, or separators. This chapter develops CMeta’s finite preprocessor kernel, shows how one declaration generates several outputs, and constrains generics and type relations through unique matching and structural identity.

**Terminology:** A tuple is an ordered group of elements, such as `(int, value, flags)`. Here it is a row of preprocessor tokens, not a runtime container. A projection selects or maps information from that row, for example its type and name to generate a declaration.

## 1. Start with One Field Set Consumed in Two Places

Suppose a program needs both the native declaration of `User` and a table of field names. The direct implementation writes `id` and `score` twice: once in the `struct` and once in metadata. A rename or added field can make the two copies drift.

Before introducing CMeta, plain C11 macros are enough to demonstrate the useful idea: record the field set once and replay it mechanically.

~~~c
#include <stddef.h>
#include <stdio.h>

#define USER_FIELDS(X) \
    X(int, id)         \
    X(double, score)

#define DECL_FIELD(type, name) type name;
#define FIELD_NAME(type, name) #name,

typedef struct User {
    USER_FIELDS(DECL_FIELD)
} User;

static const char *const User_field_names[] = {
    USER_FIELDS(FIELD_NAME)
};

int main(void)
{
    User u = { .id = 7, .score = 9.5 };

    printf("%s=%d %s=%.1f\n",
           User_field_names[0], u.id,
           User_field_names[1], u.score);
    return 0;
}
~~~

The important part is not the macro spelling. It is the dependency:

~~~text
USER_FIELDS
    |
    +--> native field declarations
    '--> field-name metadata
~~~

`USER_FIELDS` is the only handwritten field set. Adding `X(long, generation)` gives both consumers a third row.

The example also exposes the next problem. In a larger project, every subsystem can end up reimplementing `FOR_EACH`, argument counting, tuple extraction, separator placement, and empty-argument rules. The duplication has not disappeared; it has moved into macro infrastructure. CMeta therefore centralizes these mechanics in one **finite, explicit, bounded** PP/compiler kernel. Generic, Struct, Traits, and later Function declarations describe their own semantic facts instead of rebuilding preprocessing machinery.

## 2. A Production PP Kernel Should Be Finite First

Current canonical CMeta mapping entries include:

~~~c
CMETA_PP_MAP(M, C, a, b, c)
CMETA_PP_MAP_N(3, M, C, a, b, c)

CMETA_PP_MAP_COMMA_N(...)
CMETA_PP_MAP_SEMI_N(...)
CMETA_PP_MAP_PREFIX_COMMA_N(...)
~~~

Flat type/name pairs use the same finite kernel:

~~~c
CMETA_PP_PAIR_MAP_N(
    2,
    EMIT_PARAM,
    context,
    int, fd,
    size_t *, written
)
~~~

The mapper describes one item:

~~~c
#define EMIT_PARAM(type, name, context) type name
~~~

The same source facts can then feed several projections:

~~~text
int, fd, size_t *, written
            |
            v
      finite pair map
       |      |      |
       v      v      v
 prototype metadata arguments
~~~

The current families are explicitly bounded to 0–16 items. That boundary gives useful engineering properties:

~~~text
finite expansion
    -> bounded compile behavior

explicit arity
    -> testable failure boundary

shared map
    -> no per-DSL R0..R16 family
~~~

The production core does not need a recursive DEFER / OBSTRUCT / EVAL macro machine as its foundation.

## 3. Separator Policy and Tuple Projection Belong in the Kernel

If every mapper owns comma and semicolon placement, APIs quickly grow:

~~~text
EMIT_PARAM
EMIT_PARAM_COMMA
EMIT_PARAM_FIRST
EMIT_PARAM_LAST
EMIT_PARAM_SEMI
~~~

Separator policy therefore belongs to shared maps:

~~~c
CMETA_PP_MAP_COMMA(...)
CMETA_PP_MAP_SEMI(...)
CMETA_PP_MAP_PREFIX_COMMA(...)
~~~

Likewise, consumers should not each invent positional extractors for canonical rows. A function-parameter row may have the internal shape:

~~~text
(type, name, flags, descriptor, carrier)
~~~

Shared tuple primitives include:

~~~c
CMETA_PP_TUPLE_GET_0(row)
CMETA_PP_TUPLE_GET_1(row)
CMETA_PP_TUPLE_GET_2(row)
CMETA_PP_TUPLE_HEAD(row)
CMETA_PP_TUPLE_TAIL(row)
CMETA_PP_TUPLE_APPLY(M, row)
~~~

One row can feed:

~~~text
parameter row
      |
      +--> native declaration
      +--> FunctionDesc
      +--> ABI validation
      '--> exact adapter
~~~

arity and row position are shared data contracts; they should not be encoded in every DSL's macro names.

## 4. A Token Predicate Is Not the C Type System

The PP layer can provide finite boolean mechanics:

~~~c
CMETA_PP_BOOL(x)
CMETA_PP_NOT(x)
CMETA_PP_AND(a, b)
CMETA_PP_OR(a, b)
CMETA_PP_IF(x)
CMETA_PP_WHEN(x)

CMETA_PP_IS_VOID(x)
~~~

But these answer token questions only.

~~~text
CMETA_PP_IS_VOID(void)
    -> token predicate

typedef void nothing;
CMETA_PP_IS_VOID(nothing)
    -> not general C type introspection
~~~

Keep three layers separate:

~~~text
PP token relation
        !=
native compiler type relation
        !=
CMeta semantic identity
~~~

Compiler-native type reasoning belongs to facilities such as CMETA_NATIVE_TYPEOF and CMETA_SAME_TYPE. CMeta descriptor selection uses CMETA_TYPEOF(T). These are two different notions of typeof:

~~~text
CMETA_NATIVE_TYPEOF(expr)
    -> C compiler native type

CMETA_TYPEOF(T)
    -> CMeta semantic descriptor
~~~

## 5. Zero Arguments and Unique Names Need Explicit Boundaries

Empty variadic arguments are a portability risk. Only when the capability:

~~~c
CMETA_HAS_VA_OPT
~~~

is admitted are standard zero-safe forms exposed, including:

~~~c
CMETA_PP_NARG_ZERO(...)
CMETA_PP_MAP_ZERO(...)
CMETA_PP_MAP_COMMA_ZERO(...)
CMETA_PP_PREFIX_COMMA(...)
~~~

Strict C11 can keep an explicit count:

~~~c
CMETA_PP_MAP_N(0, M, C, )
~~~

The rule is:

~~~text
compiler happens to accept an extension
        !=
library promises that capability
~~~

Generated local names follow the same discipline:

~~~c
CMETA_PP_UNIQUE(cmeta_scope_)
~~~

This solves same-TU lexical naming. It does not define:

- cross-TU type identity
- Plugin contract identity
- schema order
- resource order

So:

~~~text
unique token != semantic stable ID
~~~

## 6. Generic Is One Consumer of the Kernel

A historical entry point can grow into a universal router:

~~~text
typed(...)
    -> container?
    -> callable?
    -> operator?
    -> another DSL?
~~~

The current canonical Generic entry point is narrower:

~~~c
cmeta_type(List, IntList, int);
cmeta_type(Vec, IntVec, int);
~~~

It accepts only registered finite generic kinds.

~~~text
registered(kind)
        |
        v
cmeta_type(kind, Name, T)
        |
        v
concrete ordinary-C type

unregistered(kind)
        |
        v
compile failure
~~~

Generic is therefore not a universal token router. It is:

an explicit mapping from one finite Generic kind to one concrete C declaration. Call sites still use concrete APIs:

~~~c
IntList list = {0};
IntList_push_back(&list, 10);
~~~

There is no runtime template engine.

## 7. Generate Small Typed Facades, Not Copies of Entire Algorithms

**A façade (also spelled facade)** is a thin interface over an existing implementation. A typed façade uses concrete C types for checking and forwarding while leaving the algorithm in the shared implementation.

A Generic declaration commonly produces:

~~~text
cmeta_type(List, IntList, int)
        |
        +--> concrete C type
        +--> canonical metadata
        '--> small typed wrappers
~~~

A typed wrapper can conceptually look like:

~~~c
static inline cmeta_status
IntList_push(IntList *self, int value)
{
    return list_push_raw(
        &self->raw,
        &value,
        sizeof(value),
        CMETA_TYPEOF(int));
}
~~~

The allocation, growth, and move algorithms should remain shared where practical. So:

~~~text
macro generation
    -> declaration / small wrapper

runtime algorithm
    -> shared ordinary C
~~~

This keeps Generic from becoming a code-bloat generator.

## 8. Struct: Promote Field Facts Only When Structural Metadata Is Needed

Ordinary C remains valid:

~~~c
typedef struct User {
    int id;
    double score;
} User;
~~~

If only C code needs the type, stop there. When several consumers need field facts:

~~~c
cmeta_struct(User,
    cmeta_field(int, id)
    cmeta_field(double, score)
);
~~~

The same facts produce:

~~~text
native struct declaration
        +
field metadata
        +
layout proof
        +
inline metadata accessor
~~~

Compile-time proof checks the real native layout:

To make “layout proof” concrete, first imagine the macro as the following **teaching expansion**. This is not a verbatim copy of the pinned descriptor implementation; it keeps only the native declaration and compile-time obligations:

~~~c
#include <stddef.h>

typedef struct User {
    int id;
    double score;
} User;

_Static_assert(
    _Generic(&((User *)0)->id,
             int *: 1,
             default: 0),
    "User.id type mismatch");

_Static_assert(
    _Generic(&((User *)0)->score,
             double *: 1,
             default: 0),
    "User.score type mismatch");

_Static_assert(
    offsetof(User, id) + sizeof(((User *)0)->id)
        <= sizeof(User),
    "User.id outside owner layout");

_Static_assert(
    offsetof(User, score) + sizeof(((User *)0)->score)
        <= sizeof(User),
    "User.score outside owner layout");
~~~

There is no runtime reflection lookup here. The compiler's native type system checks the field types, and `_Static_assert` rejects invalid offset/size obligations during translation. The real CMeta generator also projects the same field facts into field descriptors and accessors, so the declaration and metadata are not two independent handwritten schemas.


~~~text
declared field type
        ==
actual member type

offset + size
        within owner
~~~

Metadata is therefore not a second handwritten schema.

### Existing Native Types Do Not Need to Be Rewritten

A project may already have:

~~~c
typedef struct Account {
    int id;
    double balance;
} Account;
~~~

It can publish an external projection:

~~~c
cmeta_reflect_data(Account, "app.Account",
    cmeta_field(int, id)
    cmeta_field(double, balance)
);
~~~

The relation is:

~~~text
existing native type
        +
selected field facts
        |
        v
semantic projection
~~~

Reflection does not need to own or replace the native declaration.

## 9. Traits: The Flag and Callback Must Come from the Same Fact

A fragile design writes capability twice:

~~~c
traits.flags =
    CMETA_TRAIT_EQUAL |
    CMETA_TRAIT_HASH;

traits.equal = user_equal;
traits.hash = user_hash;
~~~

A canonical declaration can use:

~~~c
cmeta_traits(User,
    (equal, user_equal),
    (hash, user_hash)
);
~~~

The same row produces both outputs:

~~~text
(equal, user_equal)
        |
        +--> CMETA_TRAIT_EQUAL
        '--> .equal = user_equal
~~~

Compile-time generation can reject:

- duplicate trait
- unknown trait
- callback signature mismatch

instead of leaving a runtime state such as:

~~~text
flag says HASH
but hash callback == NULL
~~~

Traits are finite capability metadata, not a dynamic object hierarchy.

## 10. TypeFunction: A Finite Type Relation Is a Semantic Fact Too

Some knowledge has the form:

~~~text
f(T1, T2) = T3
~~~

For example:

~~~c
TypeFunction(CommonArithmetic,
    (int, int, int),
    (int, double, double),
    (double, int, double),
    (double, double, double)
);
~~~

Use it with:

~~~c
typedef TypeEval(CommonArithmetic, int, double) result_type;
~~~

The rule is explicit:

~~~text
lookup(CommonArithmetic, int, double)
    = exactly one row
    -> double
~~~

Failure is explicit too:

~~~text
no row
    -> unsupported

duplicate / ambiguous row
    -> invalid definition
~~~

This is not best-effort implicit conversion and not a hidden template-specialization system. If the same rows are also needed for runtime inference, project that requirement explicitly:

~~~c
InferenceRules(common_type_relation, CommonRows);
~~~

The causal direction remains:

~~~text
canonical finite rows
      |
      +--> compile-time TypeFunction / TypeEval
      '--> explicit runtime inference projection
~~~

TypeFunction does not secretly own a runtime registry.

## 11. Semantic Identity Is Not Descriptor Address Equality

Separate translation units may hold separate descriptor objects. Therefore:

~~~text
descriptor address equality
        !=
semantic type identity
~~~

A Generic application conceptually derives identity from:

~~~text
generic constructor stable identity
        +
argument semantic identities
~~~

For example:

~~~text
List<int>
    =
List stable generic owner
    +
int semantic identity
~~~

This becomes important later at Multi-TU, DSO, Plugin, and installed-consumer boundaries. A unique token from CMETA_PP_UNIQUE cannot substitute for semantic stable identity either.

**Deriving structural identity.** Let `Atom(id)` name a base type by a stable identifier and `Apply(k, args)` apply constructor `k` to type arguments. The following finite, acyclic model explains identity comparison; it is teaching pseudocode, not the source of the current CMeta comparison function.

~~~text
same_type(a, b):
    if a.kind != b.kind: return false
    if a.kind == ATOM: return a.stable_id == b.stable_id
    if a.constructor_id != b.constructor_id: return false
    if a.argument_count != b.argument_count: return false
    for each corresponding argument pair (x, y):
        if not same_type(x, y): return false
    return true
~~~

Assume stable identifiers have no collisions within the agreed namespace and type applications form finite acyclic trees. Induct on tree height: at height zero, equal base types share their identifier; at greater heights, equal constructors, argument counts, and corresponding child identities make the comparison succeed. No step uses a descriptor address, so relocating or copying a descriptor in another translation unit does not change the modeled identity. This argument establishes an identity relation, not equality of layout or cleanup protocols. Consumers relying on those properties must check the corresponding descriptor facts. The implementation also needs cross-translation-unit and shared-library tests.

## 12. Why Not Collapse Everything into One Universal DSL?

At this point we have:

~~~text
PP map / tuple kernel
compiler capabilities
cmeta_type
cmeta_struct
cmeta_reflect_data
cmeta_traits
TypeFunction
~~~

They can share implementation mechanics without sharing one universal semantic authority.

| Entry | Fact declared |
|---|---|
| cmeta_type | finite generic application |
| cmeta_struct | native declaration + structure |
| cmeta_reflect_data | projection of existing native data |
| cmeta_traits | finite capability set |
| TypeFunction | finite type relation |
| PP/compiler kernel | mechanical generation capability |

The correct shape is:

~~~text
shared mechanics
      |
      v
separate semantic entry points
~~~

not:

~~~text
OneMetaThing(...)
    -> guess everything
~~~

## 13. Engineering Evidence

The claims here are primarily toolchain claims.

### Compile-Pass

~~~text
registered generic kind
valid Struct rows
valid Traits rows
valid TypeFunction rows
    -> compile
~~~

### Compile-Fail

~~~text
unregistered generic kind
wrong field type
duplicate trait
wrong callback type
unsupported relation
arity beyond finite bound
    -> fail early
~~~

### Preprocess

~~~bash
cc -E sample.c
~~~

The output should expose:

~~~text
finite rows
    -> ordinary C declarations
    -> static metadata
    -> small typed facade
~~~

### Multi-TU

Semantic identity must not depend on descriptor pointer equality.

### Code Size

Generated wrappers should stay small; large algorithms should not be duplicated for every concrete type.

## 14. Summary

Finite mapping centralizes counts, separators, and tuple positions for Generic, Struct, Traits, and type relations. Each entry point still validates its own declarations: unknown generic kinds, duplicate relation rows, invalid callback signatures, and excess capacity must be rejected at the specified boundary. Type identity follows the semantic identities of the constructor and arguments; a descriptor address identifies storage. This supports recognition across translation units and provides the basis for sharing function-parameter facts in the next chapter.
