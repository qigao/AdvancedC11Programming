# Chapter 8: Contract Binding and Code Generation with CMeta and DataBind

A `get_user` operation may appear as a C function, HTTP route, RPC method, and Plugin export. Maintaining input types, error mappings, and cleanup rules independently invites drift. DataBind relates service contracts to CMeta native facts and compiles a checkable binding plan. Each invocation separately owns staging, output state, and cleanup progress.

## 1. Native Functions and External Contracts

This application declaration requires `<stdint.h>`. For the example, zero means success and `name` borrows character data from the repository, which must keep it valid during use.

~~~c
typedef struct UserRepository UserRepository;

typedef struct User {
    uint64_t id;
    const char *name;
} User;

int get_user(
    UserRepository *repo,
    uint64_t id,
    User *out_user);
~~~

A direct C caller prepares a `User` and checks status. An external caller should neither receive `UserRepository *` nor treat raw `User` bytes as a wire response. Pointer width, padding, and character-storage lifetime belong to native representation.

**IDL**, an interface definition language, declares logical requests, responses, events, and errors. This simplified IDL illustrates the relationships; it is not a complete file with all imports and data definitions.

~~~text
message GetUserRequest {
    uint64 id;
}
message GetUserResponse {
    User user;
}
service UserService {
    GetUser: GetUserRequest -> GetUserResponse;
}
~~~

A Service describes request/response operations, a Channel messages or events, and a Component their composition. These do not select DLL names, routes, or process deployment. FunctionDesc describes a native signature; the DataBind contract describes an external promise.

## 2. Every Parameter Needs an Explicit Source

**Binding** relates the contract to concrete C storage and calls. **Projection** maps it into a transport or artifact representation. The example requires these correspondences:

| Native object | Source or destination | Condition |
|---|---|---|
| `repo` | Host-injected context | Repository borrow covers invocation and result use |
| `id` | `GetUserRequest.id` | Lossless conversion to `uint64_t` |
| `out_user` | `GetUserResponse.user` | Valid output storage and defined field lifetimes |
| Returned `int` | Native status and business-error mapping | Contract defines zero and nonzero meanings |

This is a binding design, not a promise that any legacy C function can be adapted automatically. An existing `get_user` can be wrapped in the generated service ABI and described with CMeta. That wrapper must handle repository dependencies and borrowed strings explicitly.

A logical `uint64` cannot bind to `const char *` without an admitted conversion. Equal sizes do not help. Pointer reinterpretation, implicit string conversion, and truncation are not type compatibility.

## 3. Numeric Bounds in Input Conversion

The HTTP path text `"42"` is a character sequence rather than an existing `uint64_t` object. This complete ordinary C function illustrates the required decimal-conversion check. It needs `<stdbool.h>`, `<stddef.h>`, and `<stdint.h>`, accepts only a nonempty sequence of decimal digits, and requires writable output storage.

~~~c
bool book_parse_u64(const char *text, uint64_t *out)
{
    if (text == NULL || out == NULL || *text == '\0')
        return false;
    uint64_t value = 0;
    for (const char *p = text; *p != '\0'; ++p) {
        if (*p < '0' || *p > '9')
            return false;
        unsigned digit = (unsigned)(*p - '0');
        if (value > (UINT64_MAX - digit) / 10u)
            return false;
        value = value * 10u + digit;
    }
    *out = value;
    return true;
}
~~~

The loop invariant is that `value` equals the consumed prefix and does not exceed `UINT64_MAX`. The precondition on multiplication rearranges `10 × value + digit <= UINT64_MAX` into a comparison that cannot first overflow. Only full success stores through `out`, so rejection preserves the previous output.

This is not a replacement DataBind decoder. It demonstrates why conversion admission needs range checks. Generated bindings also distinguish absence, explicit null, defaults, and format rules; absence is not numeric zero.

## 4. Generation and Plan Compilation

At build time, `salts-idlc` generates native request, response, and typed-error representations and immutable inputs such as `DataBindServiceNativeBinding`. At startup or mounting, DataBind combines them with a projection and current CMeta descriptions to compile the final plan.

~~~c
DataBindStatus data_bind_binding_plan_compile_service(
    DataBind *codec,
    const char *service_name,
    const char *operation_name,
    const DataBindBindingProjection *projection,
    const DataBindServiceNativeBinding *native,
    DataBindBindingPlan **out_plan,
    DataBindBindingPlanDiagnostic *diagnostic);
~~~

This is a public signature. A call requires valid codec, names, projection, and native binding. Plan compilation avoids interpreting IDL per request; the resulting plan is also not a directly serializable static compiler artifact.

~~~text
compile_binding(contract, projection, native):
    resolve the logical operation
    validate native descriptors and declared request/response/error shapes
    for each required field:
        resolve its native location and direction
        require an admitted type conversion and ownership rule
        compile a transport-neutral address
    copy the plan-owned names and entries
    publish the immutable plan only after every check succeeds
~~~

**Ingress** brings external values into native objects; **egress** projects native results to an external provider. Core DataBind interprets generic binding classes. Projection-defined spaces, names, and ordinals belong to the selected adapter, without core branching on HTTP, RPC, or messaging protocols.

The plan is an **opaque type**, accessed through public operation, function, and entry accessors and freed with `data_bind_binding_plan_free`. It retains no frontend AST node or codec-owned temporary string. Borrowed descriptors and code still require an outer owner.

## 5. Exact Execution Remains a Concrete C Call

The pinned execution description joins CMeta semantics, ABI, and an explicit adapter:

~~~c
typedef struct DataBindNativeExecution {
    size_t size;
    uint32_t abi_version;
    const cmeta_function_desc *function;
    const cmeta_function_abi_desc *abi;
    void *context;
    DataBindNativeInvokeFn invoke;
} DataBindNativeExecution;
~~~

`invoke` is the known-signature adapter developed in Chapter 3. Each `params[i]` addresses its exact C parameter object, and return storage matches the real return type. The bridge's boolean reports admission/invocation success; the business function's `int` status remains in its reflected return contract.

| Outcome layer | Meaning | Business result |
|---|---|---|
| Bridge or admission failure | Exact invocation could not validly complete | Cannot be treated as a business error |
| Nonzero native status | Function reports its defined status | No success or typed-error payload is published |
| Typed error | Declared error variant and payload | Publish its error projection |
| Success | Normal response | Publish the success projection |

Ambiguous native-status-plus-typed-error combinations are rejected. Descriptor equality establishes compatibility, not executable ABI reconstruction from unknown addresses. The provider must explicitly supply execution authority.

## 6. A Call-Lifetime Transaction

`DataBindBindingCallLifetime` represents a single-owner cleanup obligation after successful binding. The complete binding entry is:

~~~c
DataBindStatus data_bind_binding_plan_bind_call(
    const DataBindBindingPlan *plan,
    const DataBindBindingProvider *provider,
    const DataBindNativeOptions *native_options,
    DataBindBindingCallFrame *frame,
    DataBindBindingCallLifetime *lifetime,
    DataBindBindingPlanDiagnostic *diagnostic);
~~~

Staging must be fresh and unowned. Lifecycle locations must be distinct except for the explicitly supported root-request alias. A live lifetime must not be copied or reinitialized, nor may frame metadata or parameter arrays change. Deferred execution can transfer exclusive access through a synchronized handoff.

~~~text
call_service(plan, frame, provider):
    initialize an empty call lifetime
    bind the complete frame
    if binding fails:
        return with initialized staging rolled back and lifetime empty
    invoke the admitted exact capability
    if bridge succeeds:
        classify and transactionally publish one outcome
    restore native values through their canonical lifecycle
    consume the call lifetime
~~~

Use an initialized-object set `L` to reason about rollback. Initially empty, it gains an object only after successful initialization. Failure destroys only members of `L`, avoiding both uninitialized destruction and leaked earlier acquisitions. Full success transfers the set into the live lifetime; invocation failure, output failure, and abandonment all require discharge.

`data_bind_binding_call_restore_zero` uses cached canonical descriptions and clears presence/null overlays. **Semantic zero** is the lifecycle-defined empty state; arbitrary `memset` is not resource destruction. Invalid frame or error-kind preflight leaves the lifetime live and values unchanged. Once teardown starts, the lifetime is consumed; a canonical cleanup failure is reported while remaining values are restored. Retrying must not repeat destruction.

## 7. Transactional Output

A provider exposes begin, write, commit, and abort operations. To preserve failure atomicity, it stages writes until commit and discards them on abort. Implementing write as irreversible network output would violate that premise.

~~~text
publish(outcome):
    validate the selected success or typed-error shape
    begin output transaction
    for each compiled output entry:
        convert and write into transaction-local storage
        on failure: abort and return failure
    commit the complete output
    on commit failure: abort and report failure
~~~

Any write failure exits before successful publication; only all-successful writes reach the single commit attempt. Commit failure must follow its provider contract. Uncertain network delivery cannot be reinterpreted as proof that the business function never ran, and publication failure generally does not authorize repeating a side-effecting invocation.

## 8. HTTP Mounting and Deferred Execution

An HTTP projection selects method, route, parameter placement, encoding, and status mapping. For example, `GET /users/:id` maps a path field into request `id`. That route does not belong to the pure Service contract. Pinned `CHttp::Service` checks MethodPlan, native layout, and execution capability at mount before publishing the route.

| Mode | Work after admission |
|---|---|
| INLINE_DIRECT | Invoke the exact entry on the HTTP owner callback |
| DEFERRED_DIRECT | Materialize a native frame, then submit to a bounded executor |
| DEFERRED_CFLOW | Compile at mount, execute the immutable plan on a worker |
| DEFERRED_PLUGIN | Resolve an export and retain a lease at mount; invoke the cached entry |

**Materialization** converts transient views into objects with specified storage and lifetimes. Deferred modes cannot pass HTTP request views or CNet callback views to workers. An already materialized native frame crosses that boundary. Accepted work retains its mounted method domain until finalization cleans request, response, and error values.

The pinned Service supports only its documented ingress/egress subset; structured body/egress and requested HTTP context still have rejection boundaries. The complete string-bearing `User` is therefore a binding-design example, not evidence that this snapshot supports the whole HTTP path. Selecting deferred mode also does not admit a `CMETA_EFFECT_ASYNC` function: deferred execution here offloads an admitted synchronous operation.

Each invocation encodes output once into transaction-local bounded `mem_buffer_t` storage, finishes the writer, and publishes through `chttp_server_reply_buffer`. Calls do not share mutable request or response staging. After stopping the server, wait for accepted executor tasks to settle, then destroy server and Service in the documented order. Live deferred invocations make Service destruction return BUSY while preserving required resources.

## 9. RPC and Documentation Reuse the Contract

`CHttp::RpcService` mounts RPC MethodPlans, native bindings, and exact execution capabilities. The RPC projection owns method names, parameter names or ordinals, results, and typed-error mappings. CRPC owns the **envelope**, the outer protocol message carrying request identity, method, parameters, or result, plus batching, notifications, deadlines, and transport.

Typed clients use compiled ingress entries to encode and classified outcomes to decode into caller storage. SUCCESS, TYPED_ERROR, and REMOTE_ERROR remain distinct from transport, HTTP, deadline, and envelope failures.

The pinned RPC path has scalar-parameter and limited result-shape boundaries; unsupported structured or mixed projections fail closed. OpenAPI derives from Service plus HTTP projection: the contract provides `id` type and requiredness, while the projection places it in the path. Documentation generation is not a request-time execution hop.

## 10. Plugin, WASM, and Build Artifacts

`salts_idl_target` is the build frontend. `ARTIFACTS` selects generated artifact forms and `TRANSPORTS` selects transport projections. This pinned call shape requires application-supplied `image.schema` and `business.c`.

~~~cmake
salts_idl_target(
  TARGET installed_image
  IDL image.schema
  COMPONENT "Image.ImageProcessor"
  VERSION "1.0.0"
  ARTIFACT_NAME "image"
  ARTIFACTS PLUGIN
  SOURCES business.c)
~~~

Plugin artifacts require explicit Component, version, and implementation inputs. Generated publication includes contract, FunctionDesc, FunctionAbi, and exact entry. `data_bind_plugin_operation_execution_admit` checks the operation catalog against the function export. Long-lived providers instead publish InterfaceDesc and `{self, vtable}` without splitting their object contract into unrelated functions.

A **lease** retains the lifetime of module code and data. It must cover resolution, binding, invocation, output, and canonical cleanup, whose code may itself reside in the module. Destroy dependent plans and native values before releasing the last lease; covering only the business call is insufficient.

WASM artifacts additionally need Component and `WASM_CORE_MODULE`. Native repository pointers, object pointers, and vtables are not guest-usable addresses. A bridge must translate representation and ownership under a portable ABI, rejecting contracts it cannot represent safely.

HTTP contracts are in the [CHttp Service header](https://github.com/qigao/chttp/blob/2e950615a7f47190258c4cb1d2cdab32e80a05b8/service/include/chttp_service/service.h).

That CHttp snapshot still uses pre-migration Plugin type names. Independent repository evidence and consistent prose naming do not establish a qualified combined SDK with this edition's CMeta/SaltsUtils. `SOURCE_SNAPSHOTS.md` records the outstanding integration boundary.

Verification begins with generated-C compilation, rejected mappings, rollback, and output abort, then separately exercises real HTTP/RPC round trips and installed Plugin loading, leases, and cleanup. Generated runtime targets should depend on DataBind and required runtimes without retaining the IDL/Schema frontend. The conversion and lifetime arguments here are hand derivations, not a claim that all bridges have machine-checked implementation proofs.

## 12. Summary

DataBind contracts, CMeta native descriptions, and transport projections compile into binding plans before requests execute. Exact invocation still calls concrete C functions. Each call separately owns staging and cleanup, output commits transactionally, and Plugin leases cover final teardown. Reusing a contract reduces duplicate knowledge while leaving each transport's support, ABI, and resource boundaries explicit.
