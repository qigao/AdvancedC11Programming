# Chapter 8: From Repeated API Contracts to a Contract Compiler — DataBind IDL, FunctionDesc, and Multi-Backend Generation

> **Chapter path**
>
> This chapter no longer surveys Serialization, RPC, Plugin, Workflow, and other systems as a list of “advanced applications.” It follows one concrete problem: **why is the same business operation described again in C prototypes, HTTP, RPC, Plugin, OpenAPI, Mock, and WASM?**
>
> Then it removes that duplication:
>
> ~~~text
> DataBind Contract IR
>         +
> generated native binding
>         +
> CMeta Native Semantic IR
>         ↓ compile/admit
> immutable DataBindBindingPlan
>         +
> exact DataBindNativeExecution
>         ↓
> HTTP / RPC / Plugin / WASM / OpenAPI / Mock
> ~~~
>
> The goal is not to invent more runtime machinery.
>
> The goal is the opposite:
>
> **move more decisions into the compiler/control plane so runtime executes already-compiled plans.**

---

## 1. From One C Function to a Logical Contract

Suppose the system has one user lookup:

~~~c
typedef struct UserRepository UserRepository;

typedef struct User {
    uint64_t id;
    const char *name;
} User;

int get_user(
    UserRepository *repo,
    uint64_t id,
    User *out_user);
~~~

This is good C.

A direct call is simple:

~~~c
User user = {0};

int rc = get_user(repo, 42u, &user);

if (rc != 0) {
    ...
}
~~~

If the program has one call site, it does not need an IDL.

The problem appears when the operation is exposed through several systems.

---

### 1.1 HTTP Describes the Same Operation Again

A normal HTTP handler may look like:

~~~c
static int get_user_http(
    void *ctx,
    const chttp_server_request_view *request,
    chttp_server_response *response)
{
    UserRepository *repo = ctx;

    const char *id_text =
        chttp_server_request_param(request, "id");

    uint64_t id = 0;

    if (parse_u64(id_text, &id) != 0)
        return chttp_server_reply(response, 400, "text/plain",
                                  "invalid id", 10);

    User user = {0};

    if (get_user(repo, id, &user) != 0)
        return chttp_server_reply(response, 404, "text/plain",
                                  "not found", 9);

    char json[1024];
    size_t json_size = encode_user_json(json, sizeof(json), &user);

    return chttp_server_reply(
        response,
        200,
        "application/json",
        json,
        json_size);
}
~~~

and registration:

~~~c
chttp_server_get(
    server,
    "/users/:id",
    get_user_http,
    repo);
~~~

The following facts now appear again: operation identity, input field `id`, input type `uint64`, result `User`, and error mapping. HTTP is not wrong.

Stable knowledge has simply started to duplicate.

---

### 1.2 RPC, OpenAPI, Plugin, Mock, and WASM Repeat It Again

RPC may add:

~~~c
crpc_server_register(
    rpc,
    "UserService.GetUser",
    get_user_rpc,
    repo);
~~~

OpenAPI repeats:

~~~text
GET /users/{id}

parameter:
    id : uint64

response 200:
    User

response 404:
    NotFound
~~~

Plugin adds export identity, version, function metadata, and adapter information. Mocking repeats the function shape, and WASM defines a host/guest ABI.

The project eventually maintains a C prototype, HTTP route/decoder, RPC method/decoder, OpenAPI schema, Plugin export, Mock declaration, and WASM ABI.

The lines differ, but they maintain one fact:

> **UserService.GetUser is one typed logical operation.**

That is the duplicated knowledge we want to remove.

---

### 1.3 FunctionDesc Is Native Truth, Not the Logical Contract

Chapter 3 introduced `cmeta_function_desc`.

Conceptually:

~~~c
static const cmeta_param_desc get_user_params[] = {
    { "repo",     CMETA_TYPE(UserRepository_ptr), CMETA_IN },
    { "id",       CMETA_TYPE(uint64_t),           CMETA_IN },
    { "out_user", CMETA_TYPE(User_ptr),           CMETA_OUT }
};

static const cmeta_function_desc get_user_desc = {
    .name = "get_user",
    .return_type = CMETA_TYPE(int),
    .params = get_user_params,
    .param_count = 3
};
~~~

This tells tooling what the native C function is.

It does not tell us:

- What is the business operation called?
- What is the logical request?
- What is the logical response?
- Is `repo` business input or a host dependency?
- Should HTTP/RPC/Plugin ever see `repo`?

Therefore **FunctionDesc != Service Contract**.

Function reflection does not replace an IDL.

---

### 1.4 DataBind IDL Describes the Logical Contract

Write the logical contract once:

~~~text
message GetUserRequest {
    uint64 id;
}

message GetUserResponse {
    User user;
}

service UserService {
    GetUser: GetUserRequest -> GetUserResponse;
}
~~~

There is no GET, POST, route, RPC alias, DLL name, WASM export, or C symbol here.

The IDL answers **what is promised?**; CMeta answers **what is implemented in C?**.

---

### 1.5 Service, Channel, and Component Have Different Jobs

The vocabulary should remain small.

### Service

Service means **Request → Response**.

### Channel

Channel means **Message / Event**.

### Component

A component groups capabilities:

~~~text
component UserModule {
    service UserService;
    channel UserEvents;
}
~~~

It says which capabilities form one logical module.

It does not mean DLL, process, HTTP server, or WASM module.

Those are projections.

## 2. Native Binding: Join Contract IR with CMeta

The compiler may generate a standard Service ABI:

~~~c
int user_service_get_user(
    const GetUserRequest *request,
    GetUserResponse *response);
~~~

The user implements:

~~~c
#include "user.generated.h"

int user_service_get_user(
    const GetUserRequest *request,
    GetUserResponse *response)
{
    User user = {0};

    if (repository_get(
            global_repository(),
            request->id,
            &user) != 0) {
        return USER_SERVICE_NOT_FOUND;
    }

    response->user = user;
    return 0;
}
~~~

Existing code may not use that shape.

We still want to bind:

~~~c
int get_user(
    UserRepository *repo,
    uint64_t id,
    User *out_user);
~~~

That is a compiler join.

---

### 2.1 Binding Judgment

Logical operation:

~~~text
UserService.GetUser :
    GetUserRequest -> GetUserResponse
~~~

Native function:

~~~text
get_user :
    (UserRepository*, uint64_t, User*) -> int
~~~

A simplified judgment is:

~~~text
Γ ⊢ UserService.GetUser :
      GetUserRequest -> GetUserResponse

Γ ⊢ get_user :
      (UserRepository*, uint64_t, User*) -> int

Γ ⊢ repo : injected-context
Γ ⊢ GetUserRequest.id ↦ id : exact
Γ ⊢ out_user ↦ GetUserResponse.user : exact
────────────────────────────────────────────
Γ ⊢ bind(UserService.GetUser, get_user) : valid
~~~

This makes four facts explicit:

1. repo is not wire input;
2. request.id binds to native id;
3. native OUT User constructs response.user;
4. binding is not positional guessing.

---


### 2.2 Binding Compilation Is Now Explicitly Two-Stage

Current SaltsUtils makes the time boundary more precise.

The build-time compiler emits **immutable native-binding inputs**:

~~~text
IDL Service operation
      ↓ salts-idlc
generated Request / Response native data
      +
DataBindServiceNativeBinding
      +
FunctionDesc / FunctionAbi references
~~~

It deliberately does **not** serialize a final `DataBindBindingPlan` as a fake static compiler artifact.

The final plan is compiled by DataBind in the control plane:

~~~c
DataBindStatus data_bind_binding_plan_compile_service(
    DataBind *codec,
    const char *service_name,
    const char *operation_name,
    const DataBindBindingProjection *projection,
    const DataBindServiceNativeBinding *native,
    DataBindBindingPlan **out_plan,
    DataBindBindingPlanDiagnostic *diagnostic);
~~~

That step joins facts that are actually available and valid in the current runtime domain:

~~~text
logical DataBind contract
        +
compile-time projection
        +
generated native binding
        +
current CMeta Function/Data descriptors
        ↓
immutable DataBindBindingPlan
~~~

So the timeline is:

~~~text
build time:
    salts-idlc
        -> generated native binding inputs

startup / admission / plan construction:
    data_bind_binding_plan_compile_service(...)
        -> immutable plan

request hot path:
    execute immutable entries
        -> exact native execution
~~~

Moving work earlier does not require pretending that every control-plane object must be frozen at build time.


### 2.3 BindingPlan Is a Real Opaque, Immutable, Transport-Neutral Object

The public API keeps `DataBindBindingPlan` opaque:

~~~c
typedef struct DataBindBindingPlan DataBindBindingPlan;
~~~

After compilation, callers read pre-resolved operation/projection/function identity and ingress/egress entries:

~~~c
const char *data_bind_binding_plan_operation_id(
    const DataBindBindingPlan *plan);

const cmeta_function_desc *data_bind_binding_plan_function(
    const DataBindBindingPlan *plan);

size_t data_bind_binding_plan_ingress_count(
    const DataBindBindingPlan *plan);

size_t data_bind_binding_plan_egress_count(
    const DataBindBindingPlan *plan);
~~~

That gives the actual ownership boundary:

- no frontend AST node is retained;
- no codec-owned temporary string is retained;
- HTTP request, RPC envelope, and Plugin session state do not enter the plan;
- ingress/egress have already become generic immutable addresses;
- descriptor/callback lifetime still belongs to the authoritative owner.

So the control-plane shape is:

~~~text
IDL/frontend objects
      ↓ compile
generated native binding
      +
CMeta descriptors
      ↓ plan compile
DataBindBindingPlan
      ↓
immutable runtime execution input
~~~


### 2.4 Exact Execution Still Is Not Universal Dynamic Invocation

Native execution uses an explicit exact descriptor.

Conceptually it carries:

~~~text
FunctionDesc
FunctionAbi
context
exact invoke function
~~~

This is `DataBindNativeExecution`.

The path is therefore:

~~~text
FunctionDesc / FunctionAbi
        ↓ validate/admit
DataBindNativeExecution
        ↓ exact invoke
ordinary C implementation
~~~

There is still no universal Reflection VM interpreting arbitrary C ABI shapes at runtime.

The responsibilities are distinct:

| Object | Role |
|---|---|
| FunctionDesc | native semantic truth |
| FunctionAbi | exact carrier facts |
| DataBindServiceNativeBinding | generated Service/native join input |
| DataBindBindingPlan | compiled logical/native binding |
| DataBindNativeExecution | admitted exact execution |

Unsupported execution shapes fail closed rather than falling back to `values[]` plus ABI guessing.

## 3. HTTP / RPC / OpenAPI Projections

The Service operation `GetUser: GetUserRequest -> GetUserResponse` does not say that it is `GET /users/{id}`.

The HTTP backend compiles convention/configuration into an immutable MethodPlan:

~~~text
HTTP MethodPlan

method = GET
route  = /users/:id

ingress:
    path "id"
        -> GetUserRequest.id

egress:
    GetUserResponse
        -> JSON body

errors:
    NOT_FOUND -> 404
~~~

GET, path, query, header, cookie, and body placement belong to the HTTP projection, not canonical Service IDL.

---

### 3.1 CHttp::Service Executes Generated MethodPlans

CHttp::Server remains responsible for HTTP runtime primitives: H1/H2, router, middleware, admission, sessions, body sinks, deferred replies, streaming, WebSocket, and file serving.

Generated routes can use the existing handler-plus-user interface:

~~~c
chttp_server_route(
    server,
    plan->method,
    plan->route,
    chttp_service_dispatch,
    plan);
~~~

This is the **HTTP runtime hot path**; arrows denote request/control flow, not compiler lowering:

~~~text
request
    ↓ route lookup
router
    ↓ select immutable plan
HTTP MethodPlan
    ↓ decode/bind
precompiled ingress
    ↓ invoke
exact adapter
    ↓ encode/map result
precompiled egress
    ↓ emit
response
~~~

It does not parse IDL, walk schema ASTs, look up FunctionDesc, or guess a native ABI.

---

### 3.2 RPC Uses the Same Service Through a Different MethodPlan

The RPC backend may generate:

~~~text
RPC MethodPlan

wire_name:
    UserService.GetUser

params:
    id -> GetUserRequest.id

result:
    GetUserResponse -> result

errors:
    NOT_FOUND -> application error
~~~

CRPC still owns the JSON-RPC envelope, batch, notification, deadlines, cancellation, and transport.

The logical Service contract is shared.

---

### 3.3 OpenAPI Comes from Service + HTTP Projection

Service alone cannot tell OpenAPI that an operation is GET /users/{id}.

OpenAPI is a **compile-time derived artifact**, not a runtime hop:

~~~text
Service Contract
        +
HTTP projection IR
        ↓ derive documentation
OpenAPI
~~~

Runtime routes and documentation therefore come from the same compiled HTTP facts.

## 4. Plugin / Interface / WASM / Build Projections

For:

~~~text
component UserModule {
    service UserService;
}
~~~

select:

~~~cmake
PROJECTIONS
    PLUGIN
~~~

and generate:

~~~text
Plugin
└── UserService
    └── GetUser
        ├── FunctionDesc
        └── exact adapter
~~~

Users do not maintain export tables, manifests, or `salts_plugin_query()` for the normal generated path.

---

### 4.1 Provider/vtable Capabilities Remain Interfaces

Executor is a different semantic shape.

It naturally has a long-lived self and related operations:

~~~c
typedef struct cflow_executor {
    void *self;
    const cflow_executor_vtable *vtable;
} cflow_executor;
~~~

A Plugin can publish:

~~~text
InterfaceDesc
+
{ self, vtable }
~~~

without flattening Executor into unrelated FunctionDesc exports.

One Plugin runtime can therefore carry two representations:

| Capability shape | Representation |
|---|---|
| Service / Function | FunctionDesc + exact adapter |
| Provider / Interface | InterfaceDesc + `{self,vtable}` |

They share loader, registry, lease, and quiescent unload, but not semantic shape.

---

### 4.2 WASM: Contract Is Above Native ABI

Select:

~~~cmake
PROJECTIONS
    WASM
~~~

The backend cannot expose UserRepository*, User*, or native vtable addresses as portable guest values.

It must go through a **WASM ABI-lowering pipeline**:

~~~text
DataBind logical data
    ↓ lower portable representation
portable ABI representation
    ↓ generate bridge
host/guest adapter
    ↓ materialize boundary
WASM import/export
~~~

Unsupported ownership or lifetime shapes fail generation.

---


### 4.3 The Real Compiler / CMake Entry: `salts-idlc` and `salts_idl_target`

The current compiler identity is:

~~~text
salts-idlc
~~~

The old `databindc` identity is removed without an alias.

The installed CMake frontend is one real entry point:

~~~cmake
salts_idl_target(
  TARGET installed_image
  IDL image.schema
  COMPONENT "Image.ImageProcessor"
  VERSION "1.0.0"
  ARTIFACT_NAME "image"
  ARTIFACTS PLUGIN
  SOURCES business.c)
~~~

Transport and artifact remain orthogonal axes.

The current public CMake surface accepts:

~~~text
ARTIFACTS:
    NATIVE
    MESSAGE
    PLUGIN
    WASM
    OPENAPI

TRANSPORTS:
    HTTP
    RPC
    SOCKET
    FLOWMQ
~~~

For example:

~~~cmake
salts_idl_target(
  TARGET installed_socket
  IDL socket.schema
  ARTIFACT_NAME "installed_device"
  TRANSPORTS SOCKET
  PROJECTION_CONFIG socket_config.json)
~~~

The pipeline is now grounded in the actual tool:

~~~text
.schema
   ↓ salts-idlc
typed IdlContract
   ├── binding compiler inputs
   ├── format plans
   ├── transport plans
   └── artifact projections
            ↓
generated ordinary C / build targets
~~~

DataBind runtime then joins those generated binding inputs with current CMeta descriptors to compile the immutable `DataBindBindingPlan`.

### 4.4 IDL Completeness Requires Both Reflection and the Plugin Boundary

Generating a C header is not enough to establish a complete logical Service contract.

For this book, the criterion is:

~~~text
Reflection can represent/admit it
        AND
Plugin can publish/use it safely across a DSO
        AND
no second handwritten semantic contract is required
~~~

The Plugin path now has a concrete admission helper:

~~~c
data_bind_plugin_operation_execution_admit(
    operation,
    function_export,
    &execution);
~~~

It proves that a generated DataBind catalog row and a Plugin FUNCTION export describe the same FunctionDesc / FunctionAbi / request / response shape, then produces the canonical `DataBindNativeExecution`.

The lease interval is equally important:

~~~text
acquire Plugin lease
    ↓
admit operation/export
    ↓
compile/use BindingPlan
    ↓
bind native staging
    ↓
invoke exact execution
    ↓
publish response / typed error
    ↓
restore native values to semantic zero
    ↓
release Plugin lease
~~~

The lease cannot cover only the machine-code call because descriptors, exact invoke code, lifecycle callbacks, and provider-owned cleanup may all belong to the DSO.

That is the concrete meaning of:

~~~text
IDL completeness
    <=>
Reflection completeness
AND
Plugin-boundary completeness
~~~

under the existing memory/lifecycle model.

## 5. Failure Semantics and Proof Obligations

IDL:

~~~text
message GetUserRequest {
    uint64 id;
}
~~~

Native function:

~~~c
int get_user(
    UserRepository *repo,
    const char *id,
    User *out);
~~~

Without an admitted conversion:

~~~text
uint64 -> const char *
~~~

generation fails.

There is no runtime atoi fallback and no reinterpret cast.

The error should name both sides.

---


### 5.1 Failure Atomicity Has a Real Lifetime Transaction

A complete Service call can establish a single-owner lifetime explicitly:

~~~c
DataBindStatus data_bind_binding_plan_bind_call(
    const DataBindBindingPlan *plan,
    const DataBindBindingProvider *provider,
    const DataBindNativeOptions *native_options,
    DataBindBindingCallFrame *frame,
    DataBindBindingCallLifetime *lifetime,
    DataBindBindingPlanDiagnostic *diagnostic);
~~~

A successful path is:

~~~text
fresh native staging
    ↓ bind_call
live DataBindBindingCallLifetime
    ↓ exact invocation
DataBindBindingOutcome
    ↓ transactional egress
write_outcome
    ↓ cleanup
data_bind_binding_call_restore_zero
~~~

The failure semantics are concrete:

- failed `bind_call` rolls initialized native values back to canonical semantic zero;
- the lifetime becomes live only after complete binding succeeds;
- typed error, native status, and bridge/admission failure remain different layers;
- output publication uses begin/write/commit/abort transaction semantics;
- teardown consumes the lifetime once, so destruction is not retried;
- Plugin-backed cleanup must finish before final lease release.

The core invariant is:

~~~text
bind_call = error
    -> lifetime is empty
    -> no partially-owned native staging escapes

live lifetime
    -> exactly one restore_zero discharge
~~~

Cleanup authority comes from canonical CMeta/DataBind lifecycle semantics, not pointer spelling.

### 5.2 What Deserves Formal Proof

Parsing a normal field does not justify Lean.

More interesting obligations include projection preservation, binding refinement, and transactional laws.

For example:

~~~text
exec_HTTP(P_HTTP(op), req)
=
exec_Logical(op, decode_HTTP(req))
~~~

or a refinement relation between generated exact adapters and the logical Service result.

State the rule first. Machine-check it when risk and reuse justify the cost.

## 6. Three IRs and the Runtime Hot Path

~~~text
DataBind Contract IR
    UserService.GetUser
    Request -> Response

CMeta Native Semantic IR
    get_user
    params / direction / ownership

CFlow Execution IR
    optional admitted execution graph
~~~

This is a **compiler join / optional execution projection**, not a runtime pipeline:

~~~text
Contract IR
    +
Native Semantic IR
    ↓ compile binding
BindingPlan / exact adapter
    ↓ optional execution admission
Execution IR
~~~

Do not collapse these into one giant descriptor.

They answer different questions.

---

### 6.1 What Remains in the Runtime

The first path is an explicit **runtime anti-pattern**:

~~~text
request
    ↓ runtime reflection
reflection
    ↓ schema lookup
schema lookup
    ↓ dynamic ABI work
dynamic invocation
~~~

The desired hot path is:

~~~text
request
    ↓ pre-resolved plan
precompiled MethodPlan
    ↓ exact call
exact C adapter
    ↓ encode/emit
response
~~~

This is the same rule used throughout the book:

> **Know more before execution; do less during execution.**

A real implementation needs different evidence for different claims.

### IDL/codegen

~~~text
valid IDL -> generated C compiles
invalid IDL -> deterministic diagnostic
~~~

### Native binding

~~~text
compatible Service + FunctionDesc -> plan
incompatible -> generation fails
~~~

### HTTP

~~~text
generated MethodPlan
-> real CHttp::Server
-> request/response integration test
~~~

### RPC

~~~text
typed client
-> CRPC
-> typed server
-> round trip
~~~

### Plugin / installed SDK

The installed-consumer qualification uses `salts_idl_target(... ARTIFACTS PLUGIN ...)` to generate Plugin and client targets.

The test also requires generated Plugin/client runtime targets to avoid linking the `Salts::IDL` / `Salts::Schema` frontend, while retaining the canonical `Salts::DataBind` runtime closure; the client additionally links `Salts::Plugin`.

That is evidence that frontend/compiler knowledge disappears in the build plane.

The runtime lifecycle still has to qualify:

~~~text
installed shared library
-> acquire lease
-> admit generated operation/export
-> bind/call/publish/cleanup
-> quiescent unload
~~~

### WASM

~~~text
host
-> generated adapter
-> .wasm
-> response
~~~

### Cross-TU / DSO identity

Here descriptor addresses may differ while semantic identity still matches.

## 8. This Is Not a Larger Framework

The result is not HTTP owning Service, RPC owning another Service, Plugin owning function metadata, and WASM owning another IDL.

The ownership is:

| Layer | Responsibility |
|---|---|
| DataBind | logical contract |
| CMeta | native semantics |
| `salts-idlc` / `salts_idl_target` | IDL frontend + build-time projections |
| DataBind runtime plan compiler | generated binding + CMeta -> immutable BindingPlan |
| CHttp / CRPC / Plugin / WASM | runtime consumers |
| CFlow | optional execution IR |

The thing we remove is duplicated stable knowledge, not ordinary C implementation.

## 9. What We Learned

We started with:

~~~c
int get_user(UserRepository *, uint64_t, User *);
~~~

and noticed that HTTP, RPC, Plugin, OpenAPI, Mock, and WASM were repeatedly describing the same logical operation.

The smallest shared object was not another runtime. It was a Contract IR.

CMeta retains FunctionDesc/FunctionAbi as native truth.

`salts-idlc` owns the typed contract and build-time projections. Generated `DataBindServiceNativeBinding` is then joined with current CMeta descriptors by the DataBind runtime to compile an immutable `DataBindBindingPlan`.

The Plugin path proves publication and native semantics match through exact execution admission, and the lease spans bind/invoke/egress/cleanup.

The hot path finally executes a precompiled plan plus an exact ordinary-C call.
