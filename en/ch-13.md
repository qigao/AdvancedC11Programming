# Chapter 8: Contract Binding and Code Generation with CMeta and DataBind

The same `get_user` operation can appear as a C function, an HTTP route, an RPC method, and a Plugin export. Separate descriptions can drift in parameter types, errors, and cleanup obligations. This chapter joins DataBind service contracts to CMeta function descriptions, generates binding plans and exact calls, and uses rollback and lease lifetimes to explain safe reuse.

**Terminology:** An IDL, or interface definition language, declares contracts such as operations, requests, responses, and errors. A binding connects that contract to concrete C types and functions. A projection derives the representation needed by a target such as HTTP or RPC from the same contract.

## 1. From One C Function to a Logical Contract

Suppose the system has one user lookup:

~~~c
typedef struct UserRepository UserRepository;

typedef struct User {
    uint64_t id;
    const char *name;
} User;

int get_user(
    UserRepository *repo,
    uint64_t id,
    User *out_user);
~~~

This is good C. A direct call is simple:

~~~c
User user = {0};

int rc = get_user(repo, 42u, &user);

if (rc != 0) {
    ...
}
~~~

If the program has one call site, it does not need an IDL. The problem appears when the operation is exposed through several systems.

### 1.1 HTTP Describes the Same Operation Again

A normal HTTP handler may look like:

~~~c
static int get_user_http(
    void *ctx,
    const chttp_server_request_view *request,
    chttp_server_response *response)
{
    UserRepository *repo = ctx;

    const char *id_text =
        chttp_server_request_param(request, "id");

    uint64_t id = 0;

    if (parse_u64(id_text, &id) != 0)
        return chttp_server_reply(response, 400, "text/plain",
                                  "invalid id", 10);

    User user = {0};

    if (get_user(repo, id, &user) != 0)
        return chttp_server_reply(response, 404, "text/plain",
                                  "not found", 9);

    char json[1024];
    size_t json_size = encode_user_json(json, sizeof(json), &user);

    return chttp_server_reply(
        response,
        200,
        "application/json",
        json,
        json_size);
}
~~~

and registration:

~~~c
chttp_server_get(
    server,
    "/users/:id",
    get_user_http,
    repo);
~~~

The following facts now appear again: operation identity, input field `id`, input type `uint64`, result `User`, and error mapping. HTTP is not wrong. Stable knowledge has simply started to duplicate.

### 1.2 RPC, OpenAPI, Plugin, Mock, and WASM Repeat It Again

RPC may add:

~~~c
crpc_server_register(
    rpc,
    "UserService.GetUser",
    get_user_rpc,
    repo);
~~~

OpenAPI repeats:

~~~text
GET /users/{id}

parameter:
    id : uint64

response 200:
    User

response 404:
    NotFound
~~~

Plugin adds export identity, version, function metadata, and adapter information. Mocking repeats the function shape, and WASM defines a host/guest ABI. The project eventually maintains a C prototype, HTTP route/decoder, RPC method/decoder, OpenAPI schema, Plugin export, Mock declaration, and WASM ABI. The lines differ, but they maintain one fact:

UserService.GetUser is one typed logical operation. That is the duplicated knowledge we want to remove.

### 1.3 FunctionDesc Is Native Truth, Not the Logical Contract

Chapter 3 introduced `cmeta_function_desc`. Conceptually:

~~~c
static const cmeta_param_desc get_user_params[] = {
    { "repo",     CMETA_TYPE(UserRepository_ptr), CMETA_IN },
    { "id",       CMETA_TYPE(uint64_t),           CMETA_IN },
    { "out_user", CMETA_TYPE(User_ptr),           CMETA_OUT }
};

static const cmeta_function_desc get_user_desc = {
    .name = "get_user",
    .return_type = CMETA_TYPE(int),
    .params = get_user_params,
    .param_count = 3
};
~~~

This tells tooling what the native C function is. It does not tell us:

- What is the business operation called?
- What is the logical request?
- What is the logical response?
- Is `repo` business input or a host dependency?
- Should HTTP/RPC/Plugin ever see `repo`?

Therefore **FunctionDesc != Service Contract**. Function reflection does not replace an IDL.

### 1.4 DataBind IDL Describes the Logical Contract

Write the logical contract once:

~~~text
message GetUserRequest {
    uint64 id;
}

message GetUserResponse {
    User user;
}

service UserService {
    GetUser: GetUserRequest -> GetUserResponse;
}
~~~

There is no GET, POST, route, RPC alias, DLL name, WASM export, or C symbol here. The IDL answers **what is promised?**; CMeta answers **what is implemented in C?**.

### 1.5 Service, Channel, and Component Have Different Jobs

The vocabulary should remain small.

### Service

Service means **Request → Response**.

### Channel

Channel means **Message / Event**.

### Component

A component groups capabilities:

~~~text
component UserModule {
    service UserService;
    channel UserEvents;
}
~~~

It says which capabilities form one logical module. It does not mean DLL, process, HTTP server, or WASM module. Those are projections.

## 2. Native Binding: Join Contract IR with CMeta

The compiler may generate a standard Service ABI:

~~~c
int user_service_get_user(
    const GetUserRequest *request,
    GetUserResponse *response);
~~~

The user implements:

~~~c
#include "user.generated.h"

int user_service_get_user(
    const GetUserRequest *request,
    GetUserResponse *response)
{
    User user = {0};

    if (repository_get(
            global_repository(),
            request->id,
            &user) != 0) {
        return USER_SERVICE_NOT_FOUND;
    }

    response->user = user;
    return 0;
}
~~~

Existing code may not use that shape. We still want to bind:

~~~c
int get_user(
    UserRepository *repo,
    uint64_t id,
    User *out_user);
~~~

That is a compiler join.

### 2.1 Binding Judgment

Logical operation:

~~~text
UserService.GetUser :
    GetUserRequest -> GetUserResponse
~~~

Native function:

~~~text
get_user :
    (UserRepository*, uint64_t, User*) -> int
~~~

A simplified judgment is:

~~~text
Γ ⊢ UserService.GetUser :
      GetUserRequest -> GetUserResponse

Γ ⊢ get_user :
      (UserRepository*, uint64_t, User*) -> int

Γ ⊢ repo : injected-context
Γ ⊢ GetUserRequest.id ↦ id : exact
Γ ⊢ out_user ↦ GetUserResponse.user : exact
────────────────────────────────────────────
Γ ⊢ bind(UserService.GetUser, get_user) : valid
~~~

This makes four facts explicit:

1. repo is not wire input;
2. request.id binds to native id;
3. native OUT User constructs response.user;
4. binding is not positional guessing.

### 2.2 Binding Compilation Is Now Explicitly Two-Stage

Current SaltsUtils makes the time boundary more precise. The build-time compiler emits **immutable native-binding inputs**:

~~~text
IDL Service operation
      ↓ salts-idlc
generated Request / Response native data
      +
DataBindServiceNativeBinding
      +
FunctionDesc / FunctionAbi references
~~~

It deliberately does **not** serialize a final `DataBindBindingPlan` as a fake static compiler artifact. The final plan is compiled by DataBind in the control plane:

~~~c
DataBindStatus data_bind_binding_plan_compile_service(
    DataBind *codec,
    const char *service_name,
    const char *operation_name,
    const DataBindBindingProjection *projection,
    const DataBindServiceNativeBinding *native,
    DataBindBindingPlan **out_plan,
    DataBindBindingPlanDiagnostic *diagnostic);
~~~

That step joins facts that are actually available and valid in the current runtime domain:

~~~text
logical DataBind contract
        +
compile-time projection
        +
generated native binding
        +
current CMeta Function/Data descriptors
        ↓
immutable DataBindBindingPlan
~~~

So the timeline is:

~~~text
build time:
    salts-idlc
        -> generated native binding inputs

startup / admission / plan construction:
    data_bind_binding_plan_compile_service(...)
        -> immutable plan

request hot path:
    execute immutable entries
        -> exact native execution
~~~

Moving work earlier does not require pretending that every control-plane object must be frozen at build time.

### 2.3 BindingPlan Is a Real Opaque, Immutable, Transport-Neutral Object

An opaque type exposes its name in the public header while callers use pointers and public functions instead of accessing fields. Here the binding plan’s layout is hidden; ownership, available operations, and destruction obligations remain part of the public contract. The public API keeps `DataBindBindingPlan` opaque:

~~~c
typedef struct DataBindBindingPlan DataBindBindingPlan;
~~~

After compilation, callers read pre-resolved operation/projection/function identity and ingress/egress entries:

~~~c
const char *data_bind_binding_plan_operation_id(
    const DataBindBindingPlan *plan);

const cmeta_function_desc *data_bind_binding_plan_function(
    const DataBindBindingPlan *plan);

size_t data_bind_binding_plan_ingress_count(
    const DataBindBindingPlan *plan);

size_t data_bind_binding_plan_egress_count(
    const DataBindBindingPlan *plan);
~~~

That gives the actual ownership boundary:

- no frontend AST node is retained;
- no codec-owned temporary string is retained;
- HTTP request, RPC envelope, and Plugin session state do not enter the plan;
- ingress/egress have already become generic immutable addresses;
- descriptor/callback lifetime still belongs to the authoritative owner.

So the control-plane shape is:

~~~text
IDL/frontend objects
      ↓ compile
generated native binding
      +
CMeta descriptors
      ↓ plan compile
DataBindBindingPlan
      ↓
immutable runtime execution input
~~~

### 2.4 Exact Execution Still Is Not Universal Dynamic Invocation

Native execution uses an explicit exact descriptor. Conceptually it carries:

- FunctionDesc
- FunctionAbi
- context
- exact invoke function

This is `DataBindNativeExecution`. The path is therefore:

~~~text
FunctionDesc / FunctionAbi
        ↓ validate/admit
DataBindNativeExecution
        ↓ exact invoke
ordinary C implementation
~~~

There is still no universal Reflection VM interpreting arbitrary C ABI shapes at runtime. The responsibilities are distinct:

| Object | Role |
|---|---|
| FunctionDesc | native semantic truth |
| FunctionAbi | exact carrier facts |
| DataBindServiceNativeBinding | generated Service/native join input |
| DataBindBindingPlan | compiled logical/native binding |
| DataBindNativeExecution | admitted exact execution |

Unsupported execution shapes fail closed rather than falling back to `values[]` plus ABI guessing.

## 3. HTTP / RPC / OpenAPI Projections

The Service operation `GetUser: GetUserRequest -> GetUserResponse` does not say that it is `GET /users/{id}`. The HTTP backend compiles convention/configuration into an immutable MethodPlan:

~~~text
HTTP MethodPlan

method = GET
route  = /users/:id

ingress:
    path "id"
        -> GetUserRequest.id

egress:
    GetUserResponse
        -> JSON body

errors:
    NOT_FOUND -> 404
~~~

GET, path, query, header, cookie, and body placement belong to the HTTP projection, not canonical Service IDL.

### 3.1 CHttp::Service Is a Real Runtime Consumer, Not a Conceptual Generic Handler

Current CHttp exports an installed `CHttp::Service` target. It keeps `CHttp::Server` independent of IDL and places one explicit adapter runtime between the server and generated DataBind artifacts. The following is an **illustrative mount shape using this edition's CMeta Plugin names, not a verbatim snapshot excerpt**. The pinned CHttp public header still uses the pre-migration Plugin type names; `cmeta_plugin_registry` / `cmeta_plugin_ref` below show the intended alignment with the current CMeta Plugin API, not a claim that this CHttp snapshot has passed a combined build with the edition's Salts / SaltsUtils SDKs. See the accompanying release file `SOURCE_SNAPSHOTS.md`.

~~~c
typedef struct chttp_service_http_mount {
    size_t size;
    const DataBindHttpMethodPlan *method_plan;
    const DataBindServiceNativeBinding *native_binding;
    const DataBindNativeExecution *execution;
    chttp_service_execution_mode execution_mode;
    cflow_executor *executor;
    const cflow_function_typed_adapter_projection *cflow_projection;

    cmeta_plugin_registry *plugin_registry;
    cmeta_plugin_ref plugin_ref;
    const char *plugin_export_id;
} chttp_service_http_mount;
~~~

and the mount call is:

~~~c
int chttp_service_mount_http(
    chttp_service *service,
    chttp_server *server,
    const chttp_service_http_mount *mount);
~~~

This joins four authorities without merging them:

~~~text
DataBindHttpMethodPlan
    = HTTP projection truth

DataBindServiceNativeBinding
    = request/response/error native layout

DataBindNativeExecution
    = admitted exact FunctionDesc/FunctionAbi execution

CHttp::Server
    = HTTP transport/runtime
~~~

Admission happens once at mount time. The current implementation has four explicit execution modes:

| mode | control-plane meaning |
|---|---|
| INLINE_DIRECT | run the exact native capability on the HTTP owner callback |
| DEFERRED_DIRECT | materialize the native frame, then hand it to a bounded executor |
| DEFERRED_CFLOW | compile one immutable CFlow Plan at mount and execute only that Plan on workers |
| DEFERRED_PLUGIN | resolve the Plugin export at mount, retain an independent lease, and cache exact execution |

The hot-path boundary is qualified directly. Request execution must not redo FunctionDesc equality, ABI validation, Plugin registry lookup, FunctionMeta/FunctionAbi lookup, CFlow graph construction, or Plan compilation. The admitted path is:

~~~text
HTTP request
    ↓ route
mounted MethodPlan / BindingPlan
    ↓ bind native frame
precompiled ingress
    ↓ exact capability
DataBindNativeExecution or immutable CFlow Plan
    ↓ transactional egress
DataBindBindingOutcome
    ↓ materialize once
pooled mem_buffer_t
    ↓ retained publish
chttp_server_reply_buffer()
~~~

So the earlier conceptual handwritten `chttp_service_dispatch(plan,...)` example is no longer needed. The stronger rule is:

CHttp::Service performs semantic/ABI admission in the mount/control plane; request execution does not look up Reflection or reconstruct native ABI.

#### Deferred lifetime has a real boundary too

Deferred execution may not retain callback-scoped:

- chttp_server_request_view *
- CNet callback views

Only an already-materialized native request frame crosses to the worker. Accepted deferred work retains mounted method/domain lifetime until the task finalizer has torn down request/response/error native values. Therefore:

~~~text
deferred_in_flight > 0
        ↓
chttp_service_destroy()
        -> SALTS_EBUSY
~~~

Plugin mode keeps a mount-owned Plugin lease through Service destruction. Any dependent CFlow Plan, descriptor, and exact execution state must end before that lease is released. This lines up three independent authorities:

~~~text
HTTP domain lifetime
    owns when work may still run

DataBind/CMeta lifecycle
    owns how native values are destroyed

Plugin lease
    owns DSO code/data reachability
~~~

They must not collapse into one cleanup flag.

#### Egress is now single-materialization

The generated Service success path is:

~~~text
native result
    ↓
DataBind / CSerde encode once
    ↓
pooled mem_buffer_t
    ↓
cserde_writer_finish()
    ↓
chttp_server_reply_buffer()
~~~

Per-call mutable state belongs to the invocation; the mounted operation retains only immutable/control metadata.

### 3.2 CHttp::RpcService Uses the Same Service Contract Through Another Plan-Driven Runtime

Current CHttp also exports:

~~~text
CHttp::RpcService
~~~

The real server mount input is:

~~~c
typedef struct chttp_rpc_service_mount_options {
    size_t size;
    const char *target;
    const DataBindRpcMethodPlan *method_plan;
    const DataBindServiceNativeBinding *native_binding;
    const DataBindNativeExecution *execution;
} chttp_rpc_service_mount_options;
~~~

and registration is:

~~~c
int chttp_rpc_service_mount(
    chttp_rpc_service *service,
    crpc_server *server,
    const chttp_rpc_service_mount_options *mount);
~~~

As with HTTP:

~~~text
mount
    -> validate FunctionDesc / FunctionAbi / native layout once

call hot path
    -> no Reflection lookup
    -> no dynamic ABI reconstruction
~~~

CRPC runtime still owns JSON-RPC envelope semantics, request ids, batches, notifications, deadlines/cancellation, H1/H2/TLS transport, and remote protocol errors. The generated RpcMethodPlan owns wire method, parameter name/ordinal projection, result projection, and typed-error mapping. Therefore:

~~~text
logical Service Contract
        |
        +--> HTTP MethodPlan -> CHttp::Service
        |
        '--> RPC MethodPlan  -> CHttp::RpcService
~~~

There is no second Service model.

#### The typed client no longer needs handwritten encoders

The current blocking typed entry is:

~~~c
int chttp_rpc_service_client_call(
    crpc_client *client,
    const chttp_rpc_service_client_call_options *options,
    chttp_rpc_service_client_outcome *outcome,
    crpc_error *out_error);
~~~

It consumes:

~~~text
DataBindRpcMethodPlan
+
DataBindServiceNativeBinding
+
caller-owned native request/response/error storage
~~~

The caller therefore does not provide a handwritten `encode_params` callback and does not manually walk `cserde_token`. The path is:

~~~text
native request
    ↓ plan-driven params
CRPC JSON-RPC envelope
    ↓ HTTP/CNet
remote response
    ↓ plan-driven result/error binding
native response / generated typed-error envelope
~~~

Valid protocol outcomes stay distinct:

~~~text
SUCCESS
TYPED_ERROR
REMOTE_ERROR
~~~

while transport, HTTP, deadline, envelope, and native encode/decode failures remain a different error layer. This again demonstrates:

Transport failure and logical application outcome should not collapse into one integer status. The current RpcService slice is deliberately finite: scalar parameters and bounded result/error shapes are admitted; unsupported structured or mixed projections fail closed.

### 3.3 OpenAPI Comes from Service + HTTP Projection

Service alone cannot tell OpenAPI that an operation is GET /users/{id}. The current CHttp tree includes a DataBind HTTP OpenAPI provider, so OpenAPI is a **compile-time derived artifact**, not a runtime hop:

~~~text
Service Contract
        +
HTTP projection IR
        ↓ derive documentation
OpenAPI
~~~

Runtime routes and documentation therefore come from the same compiled HTTP facts.

## 4. Plugin / Interface / WASM / Build Projections

For:

~~~text
component UserModule {
    service UserService;
}
~~~

In the current public frontend, this is:

~~~cmake
ARTIFACTS
    PLUGIN
~~~

The complete `salts_idl_target()` call must also provide the Plugin-specific `COMPONENT`, `VERSION`, and `SOURCES`/`LIBRARIES` inputs, and generate:

~~~text
Plugin
└── UserService
    └── GetUser
        ├── FunctionDesc
        └── exact adapter
~~~

Users do not maintain export tables, manifests, or `cmeta_plugin_query()` for the normal generated path.

### 4.1 Provider/vtable Capabilities Remain Interfaces

Executor is a different semantic shape. It naturally has a long-lived self and related operations:

~~~c
typedef struct cflow_executor {
    void *self;
    const cflow_executor_vtable *vtable;
} cflow_executor;
~~~

A Plugin can publish:

~~~text
InterfaceDesc
+
{ self, vtable }
~~~

without flattening Executor into unrelated FunctionDesc exports. One Plugin runtime can therefore carry two representations:

| Capability shape | Representation |
|---|---|
| Service / Function | FunctionDesc + exact adapter |
| Provider / Interface | InterfaceDesc + `{self,vtable}` |

They share loader, registry, lease, and quiescent unload, but not semantic shape.

**Quiescent** means that relevant execution and callbacks have ended and will no longer access resources pending unload. Quiescent unload therefore closes new access, waits for users and associated leases to finish, and only then unloads the shared library.

### 4.2 WASM: Contract Is Above Native ABI

In the current public frontend, this is:

~~~cmake
ARTIFACTS
    WASM
~~~

The complete target must also provide COMPONENT and WASM_CORE_MODULE explicitly. The backend cannot expose UserRepository*, User*, or native vtable addresses as portable guest values. It must go through a **WASM ABI-lowering pipeline**:

~~~text
DataBind logical data
    ↓ lower portable representation
portable ABI representation
    ↓ generate bridge
host/guest adapter
    ↓ materialize boundary
WASM import/export
~~~

Unsupported ownership or lifetime shapes fail generation.

### 4.3 The Real Compiler / CMake Entry: `salts-idlc` and `salts_idl_target`

The current compiler identity is:

~~~text
salts-idlc
~~~

The old `databindc` identity is removed without an alias. The installed CMake frontend is one real entry point:

The pipeline is now grounded in the actual tool:

~~~text

            ↓
~~~

DataBind runtime then joins those generated binding inputs with current CMeta descriptors to compile the immutable `DataBindBindingPlan`.

### 4.4 IDL Completeness Requires Both Reflection and the Plugin Boundary

Generating a C header is not enough to establish a complete logical Service contract. For this book, the criterion is:

~~~text
Reflection can represent/admit it
        AND
Plugin can publish/use it safely across a DSO
        AND
no second handwritten semantic contract is required
~~~

The Plugin path now has a concrete admission helper:

~~~c
data_bind_plugin_operation_execution_admit(
    operation,
    function_export,
    &execution);
~~~

It proves that a generated DataBind catalog row and a Plugin FUNCTION export describe the same FunctionDesc / FunctionAbi / request / response shape, then produces the canonical `DataBindNativeExecution`. The lease interval is equally important:

~~~text
acquire Plugin lease
    ↓
admit operation/export
    ↓
compile/use BindingPlan
    ↓
bind native staging
    ↓
invoke exact execution
    ↓
publish response / typed error
    ↓
restore native values to semantic zero
    ↓
release Plugin lease
~~~

The lease cannot cover only the machine-code call because descriptors, exact invoke code, lifecycle callbacks, and provider-owned cleanup may all belong to the DSO. That is the concrete meaning of:

~~~text
IDL completeness
    <=>
Reflection completeness
AND
Plugin-boundary completeness
~~~

under the existing memory/lifecycle model.

## 5. Failure Semantics and Proof Obligations

IDL:

~~~text
message GetUserRequest {
    uint64 id;
}
~~~

Native function:

~~~c
int get_user(
    UserRepository *repo,
    const char *id,
    User *out);
~~~

Without an admitted conversion:

~~~text
uint64 -> const char *
~~~

generation fails. There is no runtime atoi fallback and no reinterpret cast. The error should name both sides.

### 5.1 Failure Atomicity Has a Real Lifetime Transaction

A complete Service call can establish a single-owner lifetime explicitly:

~~~c
DataBindStatus data_bind_binding_plan_bind_call(
    const DataBindBindingPlan *plan,
    const DataBindBindingProvider *provider,
    const DataBindNativeOptions *native_options,
    DataBindBindingCallFrame *frame,
    DataBindBindingCallLifetime *lifetime,
    DataBindBindingPlanDiagnostic *diagnostic);
~~~

A successful path is:

~~~text
fresh native staging
    ↓ bind_call
live DataBindBindingCallLifetime
    ↓ exact invocation
DataBindBindingOutcome
    ↓ transactional egress
write_outcome
    ↓ cleanup
data_bind_binding_call_restore_zero
~~~

The failure semantics are concrete:

- failed `bind_call` rolls initialized native values back to canonical semantic zero;
- the lifetime becomes live only after complete binding succeeds;
- typed error, native status, and bridge/admission failure remain different layers;
- output publication uses begin/write/commit/abort transaction semantics;
- teardown consumes the lifetime once, so destruction is not retried;
- Plugin-backed cleanup must finish before final lease release.

The core invariant is:

~~~text
bind_call = error
    -> lifetime is empty
    -> no partially-owned native staging escapes

live lifetime
    -> exactly one restore_zero discharge
~~~

Cleanup authority comes from canonical CMeta/DataBind lifecycle semantics, not pointer spelling.

### 5.2 What Deserves Formal Proof

Parsing a normal field does not justify Lean. More interesting obligations include projection preservation, binding refinement, and transactional laws. For example:

~~~text
exec_HTTP(P_HTTP(op), req)
=
exec_Logical(op, decode_HTTP(req))
~~~

or a refinement relation between generated exact adapters and the logical Service result. State the rule first. Machine-check it when risk and reuse justify the cost.

## 6. Three IRs and the Runtime Hot Path

~~~text
DataBind Contract IR
    UserService.GetUser
    Request -> Response

CMeta Native Semantic IR
    get_user
    params / direction / ownership

CFlow Execution IR
    optional admitted execution graph
~~~

This is a **compiler join / optional execution projection**, not a runtime pipeline:

~~~text
Contract IR
    +
Native Semantic IR
    ↓ compile binding
BindingPlan / exact adapter
    ↓ optional execution admission
Execution IR
~~~

Do not collapse these into one giant descriptor. They answer different questions.

### 6.1 What Remains in the Runtime

The first path is an explicit **runtime anti-pattern**:

~~~text
request
    ↓ runtime reflection
reflection
    ↓ schema lookup
schema lookup
    ↓ dynamic ABI work
dynamic invocation
~~~

The desired hot path is:

~~~text
request
    ↓ pre-resolved plan
precompiled MethodPlan
    ↓ exact call
exact C adapter
    ↓ encode/emit
response
~~~

This is the same rule used throughout the book:

Know more before execution; do less during execution.

## 8. This Is Not a Larger Framework

The result is not HTTP owning Service, RPC owning another Service, Plugin owning function metadata, and WASM owning another IDL. The ownership is:

| Layer | Responsibility |
|---|---|
| DataBind | logical contract |
| CMeta | native semantics |
| `salts-idlc` / `salts_idl_target` | IDL frontend + build-time projections |
| DataBind runtime plan compiler | generated binding + CMeta -> immutable BindingPlan |
| CHttp / CRPC / Plugin / WASM | runtime consumers |
| CFlow | optional execution IR |

The thing we remove is duplicated stable knowledge, not ordinary C implementation.

## 9. Summary

Binding compilation joins DataBind logical contracts to CMeta native function facts. Plans retain checked field mappings, conversions, and execution entry points; each invocation owns its temporary values, errors, and cleanup progress. Transports use distinct projections while sharing the operation contract. A failed binding rolls back only successfully initialized objects. On the Plugin path, the outer lease spans input conversion, invocation, output conversion, and cleanup. API migrations between pinned snapshots still require independent combined-build qualification; illustrative naming is not that evidence.
