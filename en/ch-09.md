# Chapter 10: Executors and Schedulers: Tasks, Capacity, and Completion Obligations

Asynchronous calls separate the requester from the execution context and divide resource obligations into phases before and after admission. An Executor must specify who cleans up a rejected task, what happens to queued work during shutdown, and when callback context may be released. A bounded queue and task ledger make these obligations precise.

## 1. Task Descriptors and Context Lifetime

The pinned descriptor, declared in `<cflow/executor.h>`, is:

~~~c
typedef struct cflow_executor_task {
    cflow_task_fn run;
    cflow_task_fn cancel;
    cflow_task_fn finalize;
    void *user;
} cflow_executor_task;
~~~

Successful admission copies the descriptor, selects exactly one of the run or cancel paths, and then invokes a non-null finalize callback. Rejection invokes no task callback. `user` is borrowed: copying the descriptor neither copies the context nor retains it. When finalize exists, run and cancel must leave the context valid; final release belongs in finalize.

These ordinary C callbacks require `<stdlib.h>`. They demonstrate releasing one application-owned reference at finalization. They assume the executor's ordered termination protocol and no unsynchronized access by other threads.

~~~c
struct book_job {
    int input;
    int output;
    int cancelled;
};

static void book_run(void *user)
{
    struct book_job *job = user;
    job->output = job->input; /* A stand-in for the admitted computation. */
}

static void book_cancel(void *user)
{
    struct book_job *job = user;
    job->cancelled = 1;
}

static void book_finalize(void *user)
{
    free(user);
}
~~~

The job must come from a matching allocation. Finalization may release it after admission, so the submitter cannot use its original pointer to read a result after success. Result delivery needs a separately specified lifetime. Execution may start before submission returns; callback access cannot depend on the return having occurred.

## 2. Admission Is a Commit

This pseudocode describes nonblocking admission. The lock covers lifecycle, capacity checks, and enqueueing; user callbacks run outside it.

~~~text
try_post(task):
    validate the descriptor
    lock executor
    if lifecycle is not OPEN: unlock; return CLOSED
    if queued == capacity: unlock; return FULL
    copy task into one queue slot
    increment queued and accepted
    unlock executor
    notify a worker if required
    return ACCEPTED
~~~

**Admission** decides whether work and its resulting obligations are accepted. The executor then owes an execution or cancellation outcome; it does not acquire every resource reachable from `user`. Rejection leaves context cleanup with the submitter.

~~~text
job = allocate and fully initialize context
status = try_post({run, cancel, finalize, job})
if status is not ACCEPTED:
    release the caller-owned context
else:
    do not access context through the submitted ownership reference
~~~

The release paths are exclusive. Rejection creates no callback obligation, so the caller releases once. Acceptance makes finalize responsible for one release. This argument assumes that the same uniquely owned pointer was not submitted twice and no access follows release.

## 3. Conservation of Accepted Tasks

Let `A` count accepted tasks, `Q` queued tasks, `R` running tasks, `C` completed tasks, and `X` cancelled tasks. Their phases are exclusive:

~~~text
A = Q + R + C + X
0 <= Q <= capacity
for a Serial executor: R <= 1
~~~

Each transition preserves the equation. Admission increments `A` and `Q`. Starting moves one task from `Q` to `R`. Completion moves it from `R` to `C`. Pending cancellation moves it from `Q` to `X`. FULL and CLOSED leave this ledger unchanged, although rejection statistics may increase.

For a capacity-two Manual executor, two accepted tasks give `(A,Q,R,C,X)=(2,2,0,0,0)`. A third submission is rejected. Running one produces `(2,1,0,1,0)`; cancelling the other produces `(2,0,0,1,1)`. Once idle, `A=C+X`: every accepted task has one terminal outcome.

For example, Manual keeps detached tasks undergoing cancel/finalize in the protocol's queued count until cleanup completes and they become cancelled. Physical queue length and protocol phase counts are therefore not interchangeable; mixing them would make shutdown appear to lose tasks.

This invariant uses mathematical integers. C statistics have finite width, so indefinitely exact counters require an implementation-defined overflow policy beyond the natural-number model. A statistics snapshot also does not replace synchronization that waits for settlement.

## 4. Shutdown Closes Admission Before Settling Work

The lifecycle is OPEN, CLOSING, then CLOSED. The first shutdown selects its policy: DRAIN runs queued accepted tasks; CANCEL_PENDING cancels those not yet started. Running callbacks still complete their required termination sequence.

~~~text
begin_shutdown(policy):
    lock executor
    close admission and select the policy once
    if cancel-pending:
        detach queued tasks into a settlement set
    unlock executor
    for each detached task:
        call cancel if present
        call finalize if present
        account for terminal settlement
    wait or explicitly drive remaining work as the backend requires
    publish CLOSED only after accepted work is settled
~~~

**Settlement** includes running or cancelling, final callbacks, and accounting. An empty queue is not settlement: a worker may still be accessing context. Destroy the executor and its borrowed resources only after the specified synchronization point.

## 5. Manual, Serial, and Worker Executors

| Form | Progress mechanism | Property available to callers |
|---|---|---|
| Manual | Explicit caller drive | Controlled execution order; waiting does not secretly pump work |
| Serial | Serialized execution context | At most one task mutates this execution domain |
| Worker | Worker pool | Concurrent execution, without proving tasks interchangeable |

Manual control waiting may return PENDING and require explicit drive. Pool callers may wait for bounded capacity under the control protocol; a same-executor callback returns WOULD_BLOCK when that would require waiting for itself. `cflow_executor_try_post_task` is nonblocking admission, whereas `cflow_executor_control_post_task` belongs to the optional control interface.

Chapter 3's InterfaceDesc and `{self, vtable}` support provider dispatch. `cflow_executor_as_control` asks the creating provider for a control view. The view borrows the backend and expires on owner destruction. Another dynamic module must not infer backend identity by inspecting private layouts.

## 6. Why a Callback Cannot Wait for Itself

Suppose serial task T submits U and synchronously waits for the executor to become idle. Idle requires T to finish, while T waits for idle: a dependency cycle. Spare queue capacity cannot resolve it. A callback must not destroy or synchronously wait on the same executor; schedule a continuation task or have an external control thread wait.

A Scheduler adds clocks, delays, cancellation identities, and resumption policy to task execution. Chapter 9's subscription uses it to decide when to advance again. An Executor handles accepted-task execution. A Worker capability does not establish associativity for an arbitrary reduction.

## 7. Formal and Implementation Evidence

The pinned [Proofs/ExecutorProtocol.lean](https://github.com/qigao/salts/blob/a650262031e9b3e5f11a227a7911a75db9ae1fb8/formal/cmeta_cflow_calculus/CMetaCFlowCalculus/Proofs/ExecutorProtocol.lean) proves `task_partition` by list induction: the empty list has zero counts; adding a task increases exactly its own phase count. `tryPost_preserves_safe`, `start_preserves_safe`, and `finish_preserves_safe` cover admission, starting, and completion.

These theorems constrain an abstract protocol. They do not prove operating-system fairness or replace C lock, lifetime, and memory-model validation. The actual interface is in [executor.h](https://github.com/qigao/salts/blob/a650262031e9b3e5f11a227a7911a75db9ae1fb8/cflow/include/cflow/executor.h).

Implementation tests should cover capacity-one or capacity-two queues, run/cancel/finalize exclusivity and order, repeated shutdown, recursive submission, same-executor waiting, and finalization releasing the last context reference. After settlement, check `accepted == completed + cancelled`, and instrument Serial execution to detect overlapping running tasks. One successful callback does not validate the protocol.

## 8. Summary

An Executor links task admission to terminal cleanup. Conservation explains why shutdown and rejection cannot lose accepted tasks; exclusive callback paths establish who releases context. Copying a descriptor creates a borrow, so providers, context, and callback code must survive their last use. Backends determine how tasks advance; computation contracts determine whether concurrent execution is valid.
