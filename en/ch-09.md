# Chapter 10: Executors and Schedulers: Tasks, Capacity, and Completion Obligations

A computation describes the work; an executor is responsible for accepted tasks, their execution, and cleanup after cancellation. This chapter develops bounded admission and shutdown algorithms, uses task-count conservation to check for lost work, and compares manual, serial, and worker execution. A scheduler adds timing and resumption context without establishing that a computation is safe to parallelize.

## 1. Minimal Task Contract

The smallest task is:

~~~c
typedef void (*task_run_fn)(void *user);

typedef struct task {
    task_run_fn run;
    void *user;
} task;
~~~

A real executor often also needs cancellation and final cleanup:

~~~c
typedef struct executor_task {
    void (*run)(void *user);
    void (*cancel)(void *user);
    void (*finalize)(void *user);
    void *user;
} executor_task;
~~~

Ownership of an accepted task belongs to the Executor until either **run + finalize** or **cancel + finalize** has completed.

## 2. Admission Algorithm: FULL and CLOSED Are Normal Results

~~~text
try_post(exec, task):

    lock(exec)

    if exec.state != OPEN:
        unlock(exec)
        return CLOSED

    if exec.queue.size == exec.capacity:
        exec.stats.full += 1
        unlock(exec)
        return FULL

    exec.queue.push(task)
    exec.accepted += 1

    unlock(exec)

    wake_one_worker(exec)

    return OK
~~~

There is no hidden queue growth, silent drop, automatic retry, or synchronous fallback. The caller sees `FULL` and owns the policy decision.

## 3. Settlement Ledger

The core invariant is not “the task probably runs eventually.” Accepted work must not disappear. Track `accepted`, `queued`, `running`, and `settled`. The core invariant is **`accepted = queued + running + settled`**. Transitions:

~~~text
POST:
    accepted++, queued++

START:
    queued--, running++

COMPLETE:
    running--, settled++

CANCEL_PENDING:
    queued--, settled++
~~~

FULL and CLOSED leave the ledger unchanged:

~~~text
post(task) = FULL or CLOSED
───────────────────────────
accepted' = accepted
~~~

## 4. Lifecycle State Machine

~~~text
OPEN
  post accepted
  shutdown -> CLOSING

CLOSING
  no new post
  queued/running tasks settle
  queued=0 && running=0 -> CLOSED

CLOSED
  terminal
~~~

Pseudocode:

~~~text
shutdown(exec, policy):

    atomic OPEN -> CLOSING

    if policy == CANCEL_PENDING:
        while queue not empty:
            task = pop()
            task.cancel()
            task.finalize()
            settled++

    wake_all_workers()

    when queue empty and running == 0:
        state = CLOSED
~~~

Shutdown policy is chosen once.

## 5. Manual / Serial / Worker Share a Protocol, Not an Implementation

| Capability | Manual | Serial | Worker |
|---|---:|---:|---:|
| caller-driven drain | yes | no | no |
| concurrent producers | possible | possible | yes |
| max running | 1 | 1 | N |
| single mutable owner guarantee | caller discipline | yes | no |
| hidden thread required | no | maybe | yes |
| same Task contract | yes | yes | yes |

Serial's key invariant is **`running <= 1`**. It does not imply “one dedicated thread.”

## 6. Executor Interface and Scheduler Boundary

Executor is a natural Interface/vtable capability because it is a long-lived provider:

~~~c
typedef struct cflow_executor {
    void *self;
    const cflow_executor_vtable *vtable;
} cflow_executor;
~~~

Callers depend on capabilities such as `try_post`, `shutdown`, and `stats`.

| Object | Decides |
|---|---|
| Scheduler | when |
| Executor | how / where |

Therefore **Scheduler != Executor**. A valid composition is:

~~~text
timer scheduler
    ↓ due task
serial executor
    ↓
task.run()
~~~

not an inheritance hierarchy.

## 7. Fail-Fast Cases

### Same-executor synchronous wait

~~~text
Serial executor callback
    ↓
posts task to same executor
    ↓
waits synchronously for that task
~~~

This self-deadlocks. Detect the execution context and return WOULD_BLOCK / INVALID.

### Capacity exhausted

When `queue.size == capacity`, return `FULL`; do not allocate secretly.

### Shutdown

When `state != OPEN`, return `CLOSED`; do not accept first and silently cancel later. The formal model later in the chapter proves these already-explicit ledger, boundedness, and lifecycle rules.

## 8. Semantic Contract: Executor Is Small, Not Vague

Executor API may be small, but its contract must be precise.

### 8.1 Task Admission Is an Explicit Ownership Boundary

The smallest task can still be:

~~~c
void task(void *user);
~~~

but real tasks often also need `run`, `cancel`, `finalize`, and `user`. If shutdown chooses cancel pending, “the task did not run” does not mean “nothing needs cleanup”; it may still need to release retained user state, return a buffer to a pool, settle a promise/future, or decrement outstanding ownership. A task descriptor is therefore closer to:

~~~text
accepted
    ↓
exactly one of:
    run
    cancel
    ↓
optional finalize
~~~

Rejected admission must:

> invoke no task callback and not steal caller ownership.

This turns FULL/CLOSED from vague error codes into an ownership protocol.

### 8.2 Capacity Is a Semantic Boundary, Not a Performance Hint

If Executor declares `capacity = N`, then it must maintain `queued <= N`. It cannot secretly allocate an overflow queue when full. Otherwise the visible backpressure contract is false. FULL means:

the current resource boundary is reached; higher layers choose the next policy. Executor itself does not automatically drop, retry forever, block any caller, spill to heap, or create a new worker.

### 8.3 Serial Means Single Mutable Owner, Not “One Dedicated Thread”

The real Serial guarantee is:

~~~text
running <= 1
~~~

not “must have a dedicated thread.” Serial may be implemented through a manual caller-driven queue, a single worker, or an external event-loop adapter. This lets State Machine / Actor depend on serial semantics without depending on a concrete thread topology.

### 8.4 Worker Provides Concurrent Capability, Not Permission for Semantic Parallelism

Worker Executor can run multiple tasks concurrently. That does not mean any Graph node, State transition, or Actor message is allowed to run in parallel. The real admission relation remains:

~~~text
semantic layer says parallelism is legal
        +
Executor provides CONCURRENT capability
        ↓
parallel execution admitted
~~~

Mechanism does not choose policy.

### 8.5 Lifecycle Must Move Explicitly from OPEN to CLOSED

Executor lifecycle needs at least:

~~~text
OPEN
    ↓ shutdown
CLOSING
    ↓ all accepted work settles
CLOSED
~~~

Once no longer OPEN:

~~~text
new post
    → CLOSED / rejected
~~~

How already accepted tasks settle depends on explicit policy: `DRAIN` or `CANCEL_PENDING`. This is much safer than “destroy() then hope callbacks stop.”

### 8.6 A Same-Executor Callback Must Not Synchronously Wait on Itself

This is an easy deadlock boundary to overlook. If currently inside a callback on the same Executor and the queue is full, then a blocking post that waits for capacity—or `wait_idle()` waiting for itself—causes self-deadlock. The contract must therefore allow explicit `WOULD_BLOCK`. This is part of the execution model, not an implementation detail.

### 9.1 Bounded: Queue Never Exceeds Capacity

Formal state defines:

~~~text
Bounded(state)
:=
queued <= capacity
~~~

and theorem:

~~~text
accepted_post_is_bounded_and_conserved
~~~

proves that when room exists, accepted post gives:

~~~text
queued' = queued + 1
accepted' = accepted + 1
Safe(state')
~~~

More generally, `tryPost_preserves_safe` proves ACCEPTED/FULL/CLOSED do not violate the Safe invariant. This constrains C directly:

> if a C backend secretly stores a task after returning FULL, it is not merely “implemented differently”; it violates the model.

### 9.2 Task Ledger Conservation: Accepted Tasks Do Not Disappear

The formal model defines:

~~~text
accepted
=
queued
+
running
+
completed
+
cancelled
~~~

and `state_conserved` proves conservation; after settlement:

~~~text
accepted
=
completed + cancelled
~~~

through `settled_tasks_have_exactly_one_terminal_outcome`. This gives shutdown a strong engineering target:

> every accepted task must eventually have exactly one terminal outcome.

Not “maybe ran / maybe disappeared during destroy.”

### 9.3 SerialSafe: Manual / Serial Have at Most One Running Task

The formal definition is:

| Mode | Running constraint |
|---|---|
| manual / serial | `running <= 1` |
| worker | no such restriction |

`start_preserves_safe` ensures a start transition preserves that property. This is the mathematical form of single mutable owner.

### 9.4 FULL and CLOSED Preserve the Task Ledger

Theorems `full_post_preserves_task_ledger` and `post_shutdown_rejected` show rejected posts do not append a task, only update rejection observations. This matches the ownership rule:

~~~text
rejected admission
    ↓
caller still owns task/user
~~~

### 9.5 Same-Callback Blocking Operations Fail Fast

The theorem `self_blocking_operations_fail_fast` states that when the caller is a callback of the same Executor and the queue is full:

~~~text
blockingPost
    → WOULD_BLOCK

waitIdle
    → WOULD_BLOCK
~~~

This is a practical example of Lean improving API design. Without a model, a “convenient” blocking API can survive until production reveals self-deadlock.

### 9.6 Shutdown Settlement

The formal model distinguishes drain from cancelPending and proves `beginShutdown_preserves_safe`, `settleShutdown_settled`, `settleShutdown_quiescent`, and `close_produces_closed_quiescent`. So CLOSED does not merely mean “a bool was set true.” It means `lifecycle = CLOSED`, `queued = 0`, and `running = 0` simultaneously. That is ClosedQuiescent.

### 9.7 This Still Does Not Prove OS Fairness

Formal `settleShutdown` is a summary transition and explicitly relies on the external premise that running tasks eventually finish and drain-mode queued tasks are eventually driven. Lean proves:

~~~text
if accepted work is driven/settled
then protocol accounting is correct
~~~

It does not prove that a worker thread can never hang, the OS always schedules, or a user task always returns. This is the same safety/liveness boundary as Chapter 9.

## 10. Current C Implementation: Task Protocol Is Richer Than `fn/user`

Against the edition Salts snapshot qigao/salts@a650262031e9b3e5f11a227a7911a75db9ae1fb8:

the built-in task descriptor is:

~~~c
typedef struct cflow_executor_task {
    cflow_task_fn run;
    cflow_task_fn cancel;
    cflow_task_fn finalize;
    void *user;
} cflow_executor_task;
~~~

Its contract is a **settlement rule**, not dataflow:

| Admission result | Required callback outcome |
|---|---|
| successful admission | exactly one of run/cancel, then finalize if present |
| rejected admission | no task callback |

This aligns closely with the Lean task ledger's “exactly one terminal outcome.”

### 10.1 Manual Executor Is an Explicit Caller-Driven Queue

Current Manual implementation owns a bounded task array, count, settling state, capacity, accepted/completed/cancelled counters, rejection counters, lifecycle, shutdown policy, and running flag. It is not a “test fake.” It represents a real execution policy:

> task admission and task driving are separate; the owner decides when to call run_one/run_ready.

That makes it useful for deterministic tests, external batch/event loops, and single-thread ownership boundaries.

### 10.2 FULL Is Counted, Not Hidden by Automatic Growth

Manual `try_post` behaves conceptually as:

~~~text
if count >= capacity
    rejected_full++
    return FULL
~~~

There is no hidden fallback allocation. This directly refines formal Bounded.

### 10.3 Shutdown Policy Is Selected Once

The implementation records shutdown_policy_selected. The first shutdown selects DRAIN or CANCEL_PENDING; later attempts to redefine shutdown meaning with another policy fail. This prevents the application from changing semantics halfway through closing.

### 10.4 CANCEL_PENDING Executes Cancel/Finalize

When pending tasks are cancelled:

~~~text
cancel(user)
finalize(user)
cancelled++
~~~

The queue row is not merely discarded. This is ownership protocol in actual code.

### 10.5 Callback Context Is Tracked Across a Thread-Local Boundary

Manual implementation records which Executor state is currently running. Therefore a post that would need waiting and wait_idle can return WOULD_BLOCK from a same-executor callback instead of self-deadlocking. This is the C counterpart of `self_blocking_operations_fail_fast`.

## 11. Manual / Serial / Worker Share a Protocol, Not a Structure

We should not describe these as three frameworks. They share Task admission, capacity, lifecycle, settlement, statistics, and capabilities.

### 11.1 Manual

CAP_MANUAL means caller-driven work with running <= 1. It is best for deterministic control.

### 11.2 Serial

CAP_SERIAL may be automatically driven, while its semantic guarantee remains a single running task. It is useful for Machine mutation, Actor state, and single-owner callbacks.

### 11.3 Worker

CAP_CONCURRENT allows multiple accepted tasks to run concurrently. It is useful for parallel Plan, independent work, and I/O/computation dispatch, but only after upper-level semantic admission allows parallelism.

## 12. Why Executor and Scheduler Still Need Separate Objects

Scheduler and Executor have different responsibilities:

| Object | Main responsibilities |
|---|---|
| Scheduler | delay, clock, cancel by task id, advance virtual time, timer queue |
| Executor | accept Task, run Task, bound work, settle lifecycle |

Executor is an execution resource / ordering primitive; Scheduler is a temporal dispatch policy. Scheduler may internally use Executor without becoming the same interface. A typical relation is **temporal-dispatch composition**, not dataflow:

~~~text
timer/readiness
    ↓ decides when
Scheduler
    ↓ posts admitted work
Executor / posting context
    ↓ runs
Task
~~~

Manual Scheduler may also compose with Manual Executor. This is capability composition, not inheritance.

### 13.2 Ledger Evidence

After normal completion, cancel-pending shutdown, and drain shutdown, check:

~~~text

~~~

### 13.3 Serial Evidence

Submit multiple tasks and prove **running never exceeds 1** using instrumentation / atomic counters, not only final output order.

### 13.4 Self-Callback Evidence

Inside a task callback test:

~~~text
wait_idle(same executor)
    → WOULD_BLOCK

    → WOULD_BLOCK
~~~

Happy-path tests would not reveal this deadlock boundary.

### 13.5 Shutdown Evidence

Test separately:

~~~text

~~~

and repeated/invalid shutdown-policy behavior.

The most dangerous task-user ownership paths include accepted-then-cancelled, recursive post from run callback, finalize releasing the last ref, and destroy racing with pending work. These need ASan/UBSan plus stress/race-focused tests. Lean does not find use-after-free.

## 14. ACE Synchronization: CMeta Specifies Policies, Platform Executes Them

This is a **later Salts 2.3 released-SDK application**, not an extension of this chapter's pinned Executor/Lean proof. The complete installed C11 gate is [ch03_cmeta_ace_patterns.c](../qualification/ch03_cmeta_ace_patterns.c).

### 14.1 Scoped/Strategized Locking and Thread-Safe Interface

A locking Strategy does not attach a fictitious mutex to metadata. It passes an **explicit, typed lock capability** across a synchronous call boundary. `<cmeta/ace_synchronization.h>` exposes `cmeta_ace_lockable`; real Platform mutex/RWLock operations provide `acquire/release`. CMeta validates only the typed interface and borrow lifetime:

~~~c
typedef struct book_counter { int value; } book_counter;
CMETA_ACE_SYNCHRONIZED(book_counter_gate, book_counter);

static cmeta_status book_counter_add(book_counter *state)
{
    ++state->value;
    return CMETA_OK;
}

/* policy is a cmeta_ace_lockable bound to a real mutex */
cmeta_status status = book_counter_gate_run(
    &policy, &counter, book_counter_add);
~~~

`book_counter_gate_run` enters the guard, invokes an **already-locked private** body and releases on exit; that body must never re-enter the public method backed by the same nonrecursive lock. The guard must not span an asynchronous suspension, `longjmp`, or lifetime destruction. The installed test uses four workers performing 100 increments each, verifies 400, and requires duplicate guard entry to return `CMETA_BUSY`. A name such as “thread-safe” is not sufficient evidence.

### 14.2 Monitor Object, Thread-Specific Storage, and Leader/Followers

These patterns distribute **ownership of facts** across different layers:

| Pattern | What CMeta describes | Actual runtime and requirement |
|---|---|---|
| Monitor Object | Typed `put/take/close` interface | Platform mutex + condition; recheck predicates under the lock, broadcast close, join waiters before destroy |
| Thread-Specific Storage | Exact callback/owner types | Platform TLS; each thread has its own live storage, never a cross-thread borrowed pointer |
| Leader/Followers | FunctionDesc/FunctionAbi for CPU event callbacks, role and borrow contracts | Platform worker/condition handoff; the actual backend Owner retains I/O observe authority |
| Active Object | Typed request Port and Strategy | Optional application CFlow Actor with bounded mailbox, Worker and shutdown responsibilities |

`owner-affine` does not automatically mean thread-safe. Rejecting access from other threads through one fixed Owner is a different choice from adding a shared lock. A network server already using CNet SG should not manufacture a blocking mailbox, poll thread, or second Reactor just to match a pattern name.

### 14.3 A Proactor Completion Token Is Not the I/O Engine

`NATIVE_IO_ACE_TOKEN_TYPE` binds a NativeIO request, endpoint, user-data and caller context into a checked token. Its first matching completion settles exactly once; a second settlement returns `SALTS_EALREADY`. This proves a **specific completion obligation**, not submission or observation of actual I/O. NativeIO and CNet still own those operations. It neither replaces the Executor task ledger nor supports unmeasured performance claims.

## 15. Executable ACE Monitor Object and Thread-Specific Storage

Monitor Object and Thread-Specific Storage now have an independent latest-installed strict C11 [`ch10_cmeta_ace_monitor.c`](../qualification/ch10_cmeta_ace_monitor.c) consumer. This is **later Salts 2.3 SDK evidence**, not a retroactive extension of this chapter's fixed-edition Executor proof.

### 15.1 Monitor Object: One Lock Owns Predicates, Value, and Close

A capacity-one Monitor stores `full`, `closed`, `stored_value`, and `waiters`. One `CMETA_INTERFACE` declaration generates exact reflected `put(int)`, `take(int *out)`, and `close()` methods. Their ordinary C implementations use real Platform `cmeta_mutex_t` and `cmeta_cond_t`:

~~~c
#define BOOK_MONITOR_METHODS(X, I) /* FR1 put/take + FV0 close */
CMETA_INTERFACE(book_ace_monitor_port, BOOK_MONITOR_METHODS);

/* Conceptual shape; the real implementation also checks timeouts/close */
lock(mutex);
while (full && !closed)
    cond_wait(changed, mutex); /* atomically releases/reacquires mutex */
if (closed)
    reject_without_write();
else
    publish_value_and_signal();
unlock(mutex);
~~~

Always **recheck the predicate after a wakeup**; one condition signal does not prove capacity. `put` blocks on full; `take` blocks on empty; close broadcasts to waiting borrowers. New posts after close reject. Already stored data may still be drained once; an empty closed `take` returns `CMETA_BUSY` without modifying the caller's `out`. Join every worker before destroying the mutex/condition or unloading any code/context borrowed by the callbacks.

### 15.2 Real Two-Way Wakeup and Rejection

~~~text
consumer.take(empty) -> blocks on condition
owner.put(7) -> signals -> consumer receives 7

owner.put(13) -> full
producer.put(29) -> blocks
owner.take() -> 13 -> signals -> producer commits 29
owner.take() -> 29

consumer.take(empty) -> blocks
owner.close() -> broadcast -> consumer returns BUSY
rejected OUT unchanged; put-after-close -> BUSY

put(41) -> close() -> take() returns 41 exactly once
next take() -> BUSY without modifying OUT
~~~

All operations use real Platform worker threads and condition variables, not an invented test mailbox. A timed-out waiter is a **hard test failure**, not silently skipped execution; destruction follows close and joining borrowers. This establishes the illustrated Monitor path, not scheduler fairness, sustained stress, or throughput.

### 15.3 Thread-Specific Storage Is Not a Borrowed Global with an Owner Tag

~~~c
static SALTS_THREAD_LOCAL int book_tls_value;

static int nested_add(int delta) {
    book_tls_value += delta;
    return book_tls_value;
}
~~~

Two independently created native worker threads initialize `11` and `29`, observe `13` and `31` through nested calls, and clear their own TLS before exiting. The main thread retains its separate value `101` during those calls. `cmeta_thread_current_token()` can identify an Owner, but **it is not a lock and does not make borrowed pointers cross-thread safe**. Do not compare thread tokens after workers exit and OS identities may be reused; the gate compares workers only against a living main thread. CMeta defines exact typed behavior; Platform and the application own TLS storage and cleanup.

## 16. ACE Leader/Followers: Elect the Successor Before Executing a CPU Callback

The Monitor Object above establishes synchronization around one predicate and its data. Leader/Followers adds a separate invariant: **at most one elected Leader may claim the next event**. A Worker that claimed an event must explicitly elect a successor while holding the election lock, then release that lock before executing its CPU handler. This is **not** CNet SG's exclusive NativeIO observe authority. This example uses an application-owned CPU-event source and never asks multiple Workers to race for a CNet Backend.

The new [standalone installed C11 gate](../qualification/ch10_cmeta_ace_leader_followers.c) uses a real Platform mutex, condition, and two native workers with exactly two admission credits. CMeta reflects an exact typed `handle(int event)` callback; Platform owns real worker lifetimes.

~~~text
Application CPU source -- capacity=2 -- submit(0), submit(1)
                                         |
                         Leader A dequeues event 0
                                         |
                         under lock, elect Follower B as next Leader
                                         |
                         unlock, A.handle(0) [blocked]
                                         |
                         Leader B dequeues event 1
                         elect successor if available
                         unlock, B.handle(1) [settled]
                                         |
                         observe event 1 settled while A still blocked
                                         |
                         release A.handle(0) -> settled
                         close -> broadcast -> join workers -> destroy
~~~

Rather than only checking `handoffs >= 1`, the first callback **really waits**; the test observes event 1 settle **before releasing** event 0, proving successor execution overlaps it. A third submission receives `FULL` and remains producer-owned. On every role transition, acceptance obeys:

\[
accepted = queued + processing + settled
\]

Closing stops new admission but drains accepted events. Workers are joined before the borrowed CMeta callback context, mutex, or condition is released. Separate cases check closing an empty pool and draining an initially paused full queue when closed.

**Leader/Followers** decides who claims the next CPU event; **Monitor Object** owns a guarded shared predicate; **CFlow Active Object** owns an application mailbox and state machine. Select the semantics actually needed. None authorizes adding a second I/O poller or moving a CNet SG Owner; no unmeasured fairness, throughput or general scheduler ABI is claimed.

## 17. Summary

After accepting a task, an executor owes execution or cancellation and final cleanup. The equation `accepted = queued + running + settled` makes that obligation checkable. FULL and CLOSED reject a post without increasing the accepted count or transferring task ownership. Manual, serial, and worker executors can share admission and shutdown contracts while providing different execution contexts. Schedulers add timing and resumption policy; permission to parallelize a computation still depends on its types, ownership, and semantic conditions.
