# Chapter 5: Stream Interfaces: Building Typed Graphs

Nodes and edges can express the computation directly, while filtering, mapping, and reduction benefit from a more compact interface. This chapter uses Stream to build the preceding chapter’s graph, tracking the generated nodes, borrowed input range, and creation of execution state. It then explains why changes to the interface must preserve the graph’s outputs, order, and errors.

**Terminology reminder:** A façade is a thin interface; this chapter’s Stream converts user operations into a Graph. Observable semantics means behavior a caller can observe under the contract, such as output values, order, and errors. A more convenient interface must preserve those observations.

## 1. Surface API: Change Construction Syntax, Not the Type Chain

Chapter 4 fixed one computation:

~~~text
is_even : int -> bool
square  : int -> long
sum     : (long, long) -> long
~~~

The Stream façade only provides a more compact way to construct that Graph. To avoid making illustrative syntax look like the real SDK, use explicitly **typed pseudocode** rather than pseudo-compilable C:

~~~text
s0 : Stream<int> =
    source(xs)

s1 : Stream<int> =
    filter(s0, is_even)

s2 : Stream<long> =
    map(s1, square)

result : Terminal<long> =
    reduce(s2, 0L, sum)
~~~

The type changes are visible: Filter preserves `int`, Map produces `long`, and Reduce uses a `long` accumulator/result. The actual CFlow surface uses ISO C11 explicit-self method/function-pointer façade functions; Section 11.3 shows that real interface shape.

No input element has been traversed yet. Each operation only appends or connects Graph nodes in the control plane; a later evaluation creates separate execution state.

## 2. Builder Pseudocode

~~~text
stream.filter(predicate):

    require predicate : T -> bool

    node =
        graph.add(
            FILTER,
            input=T,
            output=T,
            callable=predicate)

    graph.connect(stream.tail, node)

    return Stream<T>(
        graph = stream.graph,
        tail  = node)
~~~

Map:

~~~text
stream.map(f):

    require f : T -> U

    node = graph.add(
        MAP,
        input=T,
        output=U,
        callable=f)

    graph.connect(stream.tail, node)

    return Stream<U>(graph,node)
~~~

Reduce:

~~~text
stream.reduce(init, reducer):

    require reducer : (A,T) -> A

    node = graph.add(
        REDUCE,
        input=T,
        output=A,
        callable=reducer,
        init=init)

    graph.connect(stream.tail, node)

    return Terminal<A>(graph,node)
~~~

## 3. Type Rules

Filter:

~~~text
p : T -> bool
────────────────
Filter<T>(p) : T -> T
~~~

Map:

~~~text
f : T -> U
──────────────
Map<T,U>(f) : T -> U
~~~

Reduce:

~~~text
r : (A,T) -> A
────────────────
Reduce<A,T>(r) : Stream<T> -> A
~~~

Many errors therefore fail while building the surface program.

## 4. Range / Stream / Collector Ownership

Do not let Stream secretly own user data.

| Object | Ownership |
|---|---|
| Range | borrows source data |
| Stream | owns/borrows Graph-builder state |
| Collector | owns destination policy |
| Execution | owns transient frame |

Ownership remains ordinary C ownership.

## 5. Façade Preservation Rule

Interface construction and direct construction must describe the same computation. Equality here concerns graph semantics, not descriptor addresses:

~~~text
build_stream(program)
=
build_graph(program)
~~~

and:

~~~text
eval(lower(StreamSurface))
=
eval(CanonicalGraph)
~~~

Stream must not silently change encounter order, buffering, errors, ownership, or backend policy.

## 6. Lower Back to an Ordinary Loop

For:

~~~text
Source
 -> Filter(is_even)
 -> Map(square)
 -> Reduce(sum)
~~~

the following ordinary loop is a semantic baseline. The pinned Direct path primarily supports Filter/Map; the full computation containing Reduce should use a compiled plan as described in Chapter 7. This loop is not a claim that current Direct emits the complete reduction:

~~~c
long total = 0;

for (size_t i = 0; i < n; ++i) {
    int x = xs[i];

    if (!is_even(x))
        continue;

    total = sum(total, square(x));
}
~~~

This baseline supports comparison of results and execution cost. Generating equivalent direct code depends on the selected backend’s supported scope and eligibility checks.

## 7. Failure Cases

Wrong predicate: if `Stream<int>` receives a `User -> bool` predicate, return `TYPE_MISMATCH`. Invalid reducer: if the reducer is `(double,int) -> long` but the required type is `(long,int) -> long`, return `TYPE_MISMATCH`. Unsupported lowering: if the surface is accepted and the canonical Graph is valid but the selected backend cannot lower it, return `UNSUPPORTED`. The remainder of the chapter checks the canonical pipeline, semantic preservation, real C implementation, and benchmark discipline.

## 8. The Same Graph: Surface Operations Map One-to-One to Graph Rows

Stream does not introduce a second semantics. The four surface operations above map directly to the Graph structure defined in Chapter 4:

| Surface operation | Graph content added | Type transition |
|---|---|---|
| `source(xs)` | Input/Source | `— -> int` |
| `filter(..., is_even)` | Filter node | `int -> int` |
| `map(..., square)` | Map node | `int -> long` |
| `reduce(..., 0L, sum)` | Reduce terminal | `Stream<long> -> long` |

Façade correctness therefore means more than “the method chain runs.” The Graph produced through the surface must contain the same operators, callables, type connections, and parameters as the program built directly through the Graph builder.

That is also why the surface API may evolve without forcing normalize, optimize, Plan, or Certificate to change: those later stages consume the canonical Graph, not chaining syntax.

## 9. Semantic Contract: What the Stream Façade Must Not Change

### 9.1 Operator Semantics Must Match Graph

If Graph defines:

~~~text
FILTER
    output type = input type
    cardinality = 0..1

MAP
    output type = callable return
    cardinality = 1

REDUCE
    homogeneous fold
    cardinality = N..1
~~~

Stream cannot redefine those rules because it has a different surface. A Stream method should therefore be a **typed Graph builder wrapper**, not a second semantic authority.

### 9.2 Stream Owns the Description, Not Source Data

Stream may own Graph description, copied Range view, evaluation options, and builder/admission state, but the real input object/container remains owned by its original owner. Therefore **Stream lifetime ≠ container lifetime**. For a borrowed Range, the owner must remain alive and satisfy the Range contract throughout evaluation.

### 9.3 Evaluation State Must Be Separate from Reusable Graph

One critical contract is:

> the same Stream/Graph description may execute repeatedly when allowed, but each execution gets fresh cursor/operator state.

Do not write live facts such as reduce accumulator, skip counter, take counter, or publisher cursor back into Graph; otherwise **Build Once, Execute Many** fails immediately.

### 9.4 Chainable Does Not Mean Unbounded Deferred Runtime Objects

Stream handles construction. At execution time the program can choose direct synchronous evaluation, normalized Graph, compiled Plan, or Reactive Subscription. Chained syntax is not itself a cost model. Cost depends on:

the execution backend actually selected.

## 10. Lean / Proof Obligation: What Should Stream Prove?

Stream does not need a second complex formal semantics. A better proof target is:

### 10.1 Surface-to-Graph Construction Correctness

If Stream methods filter f, map g, and reduce h construct FILTER(f), MAP(g), and REDUCE(h), then Stream's observable meaning should inherit Graph's meaning directly. Conceptually:

~~~text
BuildStream(ops) = g
→
StreamSemantics(ops, input)
=
GraphSemantics(g, input)
~~~

If Stream is a deterministic builder, this theorem should be thin. That is a strength:

the thinner the façade, the less independent semantics must be proved.

### 10.2 Type-Chain Preservation

For:

~~~text
T
  --filter--> T
  --map f--> U
  --reduce--> U
~~~

surface methods must not bypass Graph admission. If:

~~~text
map : T -> U
next filter expects V
U != V
~~~

construction/admission should fail.

### 10.3 Reusable Description / Fresh Execution Separation

The formal model should distinguish **Program Description** from **Execution State**. This becomes even more important in the next Reactive chapter. If cursor/demand/cancel state is placed inside Graph itself, control plane and execution plane become entangled.

## 11. Current C Implementation: Stream Really Is a Graph Façade

Against the edition Salts snapshot `qigao/salts@a650262031e9b3e5f11a227a7911a75db9ae1fb8`:

the central `cflow_stream` shape is straightforward:

~~~c
struct cflow_stream {
    cflow_graph graph;

    cmeta_range input_range;
    bool has_input_range;

    cflow_eval_options eval_options;
    bool failed;

    /* generated explicit-self operator methods */
    ...
};
~~~

The representation answers several questions directly.

### 11.1 Graph Is Stream's Core Owned Description

Stream is not a pointer to a hidden Stream runtime. It directly owns `cflow_graph graph`; operator methods mainly extend that Graph. So **Stream → Graph** is not only an architectural diagram; it is reflected in the data layout.

### 11.2 Range Is an Input Protocol, Not Part of Graph

`input_range` and `has_input_range` say which input view this Stream is currently bound to, but they do not change operator semantics. That lets arrays, container Ranges, channel-like publishers, and other sources reuse the same computation description.

### 11.3 Method Fields Are ISO C11 Explicit-Self Façade Functions

Current Stream methods are not C++ member functions. They are C function-pointer fields:

~~~text
stream.filter(&stream, ...)
stream.map(&stream, ...)
~~~

This preserves:

1. ISO C11;
2. a fluent-looking surface without an object runtime.

### 11.4 Public Graph View Is Read-Only Introspection

The current `cflow_stream_graph()` API returns a borrowed read-only Graph view. Users should not mutate `stream.graph.nodes[...] = ...` to bypass the builder contract. This continues Chapter 4's rule:

public visibility does not imply arbitrary mutability.

### 11.5 Qualify Surface-to-Graph Construction with the Public API

The façade claim can be checked without executing a value. The following complete C11 consumer defines the canonical Filter/Map callables, builds them through `cflow_stream`, and then inspects only documented read-only Graph rows:

~~~c
#include <cflow/meta.h>
#include <cflow/stream.h>

cmeta_function(filter, value, bool, even, (int x))
{
    return (x % 2) == 0;
}

cmeta_function(map, value, long, square, (int x))
{
    return (long)x * (long)x;
}

int main(void)
{
    cflow_stream stream = {0};
    const cflow_graph *graph = NULL;
    const cflow_subgraph *root = NULL;
    const cflow_node *input = NULL;
    const cflow_node *filter = NULL;
    const cflow_node *map = NULL;
    const cflow_edge *first = NULL;
    const cflow_edge *second = NULL;
    const char *error = NULL;
    int rc = 0;

    if (!cflow_stream_init(&stream, &cmeta_type_int))
        return 1;

    stream.filter(&stream, even);
    stream.map(&stream, square);

    if (!cflow_stream_ok(&stream)) {
        rc = 2;
        goto done;
    }

    graph = cflow_stream_graph(&stream);

    if (!graph || !cflow_graph_validate(graph, &error)) {
        rc = 3;
        goto done;
    }

    root = cflow_graph_subgraph(graph, graph->root);

    if (!root ||
        root->node_count != 3u ||
        root->edge_count != 2u) {
        rc = 4;
        goto done;
    }

    input = cflow_subgraph_node(root, 0u);
    filter = cflow_subgraph_node(root, 1u);
    map = cflow_subgraph_node(root, 2u);
    first = cflow_subgraph_edge(root, 0u);
    second = cflow_subgraph_edge(root, 1u);

    if (!input || !filter || !map || !first || !second) {
        rc = 5;
        goto done;
    }

    if (input->op != CFLOW_OP_INPUT ||
        filter->op != CFLOW_OP_FILTER ||
        map->op != CFLOW_OP_MAP) {
        rc = 6;
        goto done;
    }

    if (!cmeta_type_equal(input->input_type, &cmeta_type_int) ||
        !cmeta_type_equal(input->output_type, &cmeta_type_int) ||
        !cmeta_type_equal(filter->input_type, &cmeta_type_int) ||
        !cmeta_type_equal(filter->output_type, &cmeta_type_int) ||
        !cmeta_type_equal(map->input_type, &cmeta_type_int) ||
        !cmeta_type_equal(map->output_type, &cmeta_type_long) ||
        !cmeta_type_equal(
            cflow_stream_output_type(&stream),
            &cmeta_type_long)) {
        rc = 7;
        goto done;
    }

    if (first->from != 0u || first->from_port != 0u ||
        first->to != 1u || first->to_port != 0u ||
        second->from != 1u || second->from_port != 0u ||
        second->to != 2u || second->to_port != 0u) {
        rc = 8;
        goto done;
    }

done:
    cflow_stream_destroy(&stream);
    return rc;
}
~~~

The gate reads `graph->root` only as documented read-only introspection; it does not modify Graph storage. The expected IR is therefore not “two opaque chained methods.” Initialization creates the source node first, and the two façade calls append two operator rows:

~~~text
node 0  INPUT   int  -> int
  |
node 1  FILTER  int  -> int
  |
node 2  MAP     int  -> long
~~~

with two explicit `0 -> 1` and `1 -> 2` edges. The gate checks semantic type equality through CMeta rather than pointer identity, and it asks `cflow_graph_validate` to admit the completed IR.

No element has been evaluated. That limitation is intentional: this gate proves the **surface-to-Graph construction claim** from Section 10.1. Execution equivalence belongs to the differential Plan/Direct evidence in later chapters. Keeping the obligations separate makes a failure attributable to construction, transformation, or execution instead of collapsing all three into one demo.

A fresh-prefix consumer needs only the exported runtime target:

~~~cmake
find_package(Salts CONFIG REQUIRED)

add_executable(
    stream_graph_gate
    stream_graph_gate.c)

target_link_libraries(
    stream_graph_gate
    PRIVATE
        Salts::CFlow)
~~~

`Salts::CFlow` publicly carries its required CMeta dependency, so this also checks that the installed target exports the transitive public contract expected by the headers.

## 12. Evidence: The Canonical Pipeline Already Exists in Real Tests

Current CFlow certificate tests use almost exactly the canonical pipeline from this book:

~~~text
filter even
    ↓
map square
    ↓
reduce add
~~~

The test continues through:

~~~text
Stream
    ↓
Surface Graph
    ↓
Normalize
    ↓
Optimize
    ↓
Compile Plan
    ↓
Build Certificate
    ↓
Check Certificate
~~~

So the canonical example is not a toy invented only for the book. It is already part of a real trusted execution path.

### 12.1 Surface/API Evidence

Section 11.5 turns this claim into an executable gate:

~~~text
filter/map façade calls
    ↓
INPUT -> FILTER -> MAP Graph rows
    ↓
int -> int -> long type chain
    ↓
Graph validation succeeds
~~~

### 12.2 Reuse Evidence

Repeated evaluation of one Stream description under a valid Range contract should use independent execution state. In particular, reduce accumulators, take/skip counters, and temporary value storage must not leak back into Graph description.

### 12.3 Ownership Evidence

Tests must make clear that Stream destroys its Graph but does not destroy a borrowed container/Range owner.

### 12.4 Certificate / Verification Evidence

Once Stream has built the Graph, trusted transformations should target **Graph / Plan / Certificate**, not surface syntax. Again:

Stream is not the semantic center; Graph is.

## 13. Performance: Benchmark the Execution Path, Not the Chaining Syntax

Stream API work is mostly construction/control-plane work. So the useful performance question is not “How much slower is stream.map() than plain C?” It is: **How does the same pipeline finally execute?** Compare the hand-written C loop, surface Graph interpreter, normalized/optimized Graph, compiled Plan, and direct/AOT path. If lowering produces an execution form equivalent to the hand-written loop, then high-level Stream expression and hot-path cost can be separated. That is one of the book's central ideas:

the cost of a high-level API should not automatically become a per-value execution cost.

## 14. Summary

Stream translates filtering, mapping, and reduction requests into a graph. Graph rules continue to govern types and operations, and input ranges retain their borrowing conditions. A reusable description must keep one execution’s cursor, accumulator, and waiting state separate. Correctness requires the interface-built graph to preserve the specified observations of the directly built graph. Performance comparisons should hold inputs, operations, and backend fixed while measuring construction and execution separately. The next chapter defines the observations and proof conditions for rewriting graphs.
