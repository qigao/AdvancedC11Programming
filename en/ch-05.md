# Chapter 5: From Graph to Stream — Build the Same Typed Graph Through a Higher-Level Surface

> **Stream does not own a second execution semantics.**
>
> It is a Graph-builder façade.
>
> The key property is: **the Stream surface lowers to the same canonical Graph.** If the façade changes observable semantics, it is not merely a façade.

**Terminology reminder:** A façade is a thin interface; this chapter’s Stream converts user operations into a Graph. Observable semantics means behavior a caller can observe under the contract, such as output values, order, and errors. A more convenient interface must preserve those observations.

---

## 1. Surface API

A user may prefer:

~~~c
stream_int s =
    stream_from_int(xs, n);

stream_long out =
    stream_int_filter(
        &s,
        &is_even)
    .map(&square);

long total =
    stream_long_reduce(
        &out,
        0,
        &sum);
~~~

Exact API spelling is secondary.

Each call constructs Graph.

---

## 2. Builder Pseudocode

~~~text
stream.filter(predicate):

    require predicate : T -> bool

    node =
        graph.add(
            FILTER,
            input=T,
            output=T,
            callable=predicate)

    graph.connect(stream.tail, node)

    return Stream<T>(
        graph = stream.graph,
        tail  = node)
~~~

Map:

~~~text
stream.map(f):

    require f : T -> U

    node = graph.add(
        MAP,
        input=T,
        output=U,
        callable=f)

    graph.connect(stream.tail, node)

    return Stream<U>(graph,node)
~~~

Reduce:

~~~text
stream.reduce(init, reducer):

    require reducer : (A,T) -> A

    node = graph.add(
        REDUCE,
        input=T,
        output=A,
        callable=reducer,
        init=init)

    graph.connect(stream.tail, node)

    return Terminal<A>(graph,node)
~~~

---

## 3. Type Rules

Filter:

~~~text
p : T -> bool
────────────────
Filter<T>(p) : T -> T
~~~

Map:

~~~text
f : T -> U
──────────────
Map<T,U>(f) : T -> U
~~~

Reduce:

~~~text
r : (A,T) -> A
────────────────
Reduce<A,T>(r) : Stream<T> -> A
~~~

Many errors therefore fail while building the surface program.

---

## 4. Range / Stream / Collector Ownership

Do not let Stream secretly own user data.

| Object | Ownership |
|---|---|
| Range | borrows source data |
| Stream | owns/borrows Graph-builder state |
| Collector | owns destination policy |
| Execution | owns transient frame |

Ownership remains ordinary C ownership.

---

## 5. Façade Preservation Rule

Correctness is not “chain syntax looks nice.”

It is:

~~~text
build_stream(program)
=
build_graph(program)
~~~

and:

~~~text
eval(lower(StreamSurface))
=
eval(CanonicalGraph)
~~~

Stream must not silently change encounter order, buffering, errors, ownership, or backend policy.

---

## 6. Lower Back to an Ordinary Loop

For:

~~~text
Source
 -> Filter(is_even)
 -> Map(square)
 -> Reduce(sum)
~~~

eligible Direct lowering can generate:

~~~c
long total = 0;

for (size_t i = 0; i < n; ++i) {
    int x = xs[i];

    if (!is_even(x))
        continue;

    total += square(x);
}
~~~

The Stream façade should disappear from the hot path.

---

## 7. Failure Cases

Wrong predicate: if `Stream<int>` receives a `User -> bool` predicate, return `TYPE_MISMATCH`.

Invalid reducer: if the reducer is `(double,int) -> long` but the required type is `(long,int) -> long`, return `TYPE_MISMATCH`.

Unsupported lowering: if the surface is accepted and the canonical Graph is valid but the selected backend cannot lower it, return `UNSUPPORTED`.

The remainder of the chapter checks the canonical pipeline, semantic preservation, real C implementation, and benchmark discipline.

## 8. Canonical Example: The Same Graph Through a User-Friendly Entry Point

Chapter 4 already had:

~~~text
Input<int>
    ↓
Filter(is_even)
    ↓
Map(square)
    ↓
Reduce(sum)
~~~

If users must call low-level Graph builders every time, the API is unnecessarily mechanical.

Stream lets construction resemble the data transformation:

~~~c
cflow_stream s = {0};

cflow_stream_init(&s, &cmeta_type_int);

s.filter(&s, is_even)
 ->map(&s, square)
 ->reduce(&s, sum);
~~~

The important part is not fluent syntax.

The important part is:

> **these calls still construct the same Graph IR.**

Stream does not own a separate StreamNode, StreamExecutor, StreamOptimizer, or StreamTypeSystem. It is only a **user-friendly construction surface over the same typed Graph**. A high-level interface is not the same thing as a new runtime.

## 9. Semantic Contract: What the Stream Façade Must Not Change

### 9.1 Operator Semantics Must Match Graph

If Graph defines:

~~~text
FILTER
    output type = input type
    cardinality = 0..1

MAP
    output type = callable return
    cardinality = 1

REDUCE
    homogeneous fold
    cardinality = N..1
~~~

Stream cannot redefine those rules because it has a different surface.

A Stream method should therefore be a **typed Graph builder wrapper**, not a second semantic authority.

### 9.2 Stream Owns the Description, Not Source Data

Stream may own Graph description, copied Range view, evaluation options, and builder/admission state, but the real input object/container remains owned by its original owner. Therefore **Stream lifetime ≠ container lifetime**.

For a borrowed Range, the owner must remain alive and satisfy the Range contract throughout evaluation.

### 9.3 Evaluation State Must Be Separate from Reusable Graph

One critical contract is:

> the same Stream/Graph description may execute repeatedly when allowed, but each execution gets fresh cursor/operator state.

Do not write live facts such as reduce accumulator, skip counter, take counter, or publisher cursor back into Graph; otherwise **Build Once, Execute Many** fails immediately.

### 9.4 Chainable Does Not Mean Unbounded Deferred Runtime Objects

Stream handles construction.

At execution time the program can choose direct synchronous evaluation, normalized Graph, compiled Plan, or Reactive Subscription. Chained syntax is not itself a cost model.

Cost depends on:

> **the execution backend actually selected.**

## 10. Lean / Proof Obligation: What Should Stream Prove?

Stream does not need a second complex formal semantics.

A better proof target is:

### 10.1 Surface-to-Graph Construction Correctness

If Stream methods filter f, map g, and reduce h construct FILTER(f), MAP(g), and REDUCE(h), then Stream's observable meaning should inherit Graph's meaning directly.

Conceptually:

~~~text
BuildStream(ops) = g
→
StreamSemantics(ops, input)
=
GraphSemantics(g, input)
~~~

If Stream is a deterministic builder, this theorem should be thin.

That is a strength:

> **the thinner the façade, the less independent semantics must be proved.**

### 10.2 Type-Chain Preservation

For:

~~~text
T
  --filter--> T
  --map f--> U
  --reduce--> U
~~~

surface methods must not bypass Graph admission.

If:

~~~text
map : T -> U
next filter expects V
U != V
~~~

construction/admission should fail.

### 10.3 Reusable Description / Fresh Execution Separation

The formal model should distinguish **Program Description** from **Execution State**.

This becomes even more important in the next Reactive chapter.

If cursor/demand/cancel state is placed inside Graph itself, control plane and execution plane become entangled.

## 11. Current C Implementation: Stream Really Is a Graph Façade

Against the current Salts snapshot `qigao/salts@ad389928b437c0612c1c60844fe53677f3ed27a6`:

the central `cflow_stream` shape is straightforward:

~~~c
struct cflow_stream {
    cflow_graph graph;

    cmeta_range input_range;
    bool has_input_range;

    cflow_eval_options eval_options;
    bool failed;

    /* generated explicit-self operator methods */
    ...
};
~~~

The representation answers several questions directly.

### 11.1 Graph Is Stream's Core Owned Description

Stream is not a pointer to a hidden Stream runtime.

It directly owns `cflow_graph graph`; operator methods mainly extend that Graph.

So **Stream → Graph** is not only an architectural diagram; it is reflected in the data layout.

### 11.2 Range Is an Input Protocol, Not Part of Graph

`input_range` and `has_input_range` say which input view this Stream is currently bound to, but they do not change operator semantics.

That lets arrays, container Ranges, channel-like publishers, and other sources reuse the same computation description.

### 11.3 Method Fields Are ISO C11 Explicit-Self Façade Functions

Current Stream methods are not C++ member functions.

They are C function-pointer fields:

~~~text
stream.filter(&stream, ...)
stream.map(&stream, ...)
~~~

This preserves:

1. ISO C11;
2. a fluent-looking surface without an object runtime.

### 11.4 Public Graph View Is Read-Only Introspection

The current `cflow_stream_graph()` API returns a borrowed read-only Graph view. Users should not mutate `stream.graph.nodes[...] = ...` to bypass the builder contract.

This continues Chapter 4's rule:

> **public visibility does not imply arbitrary mutability.**

## 13. Performance: Benchmark the Execution Path, Not the Chaining Syntax

Stream API work is mostly construction/control-plane work.

So the useful performance question is not “How much slower is stream.map() than plain C?” It is: **How does the same pipeline finally execute?**

Compare the hand-written C loop, surface Graph interpreter, normalized/optimized Graph, compiled Plan, and direct/AOT path.

If lowering produces an execution form equivalent to the hand-written loop, then high-level Stream expression and hot-path cost can be separated.

That is one of the book's central ideas:

> **the cost of a high-level API should not automatically become a per-value execution cost.**

## 14. What We Learned

Chapter 5 does not merely “add chaining to C.”

It establishes a more important **lowering relation**:

~~~text
Friendly Surface Syntax
        ↓ builds
Typed Graph IR
        ↓ compiled/lowered by
Independent Execution Backends
~~~

Therefore:

1. **Stream is a façade, not a second runtime.**
2. **Operator semantics belong to Graph/operator schema.**
3. **Input Range ownership remains explicit.**
4. **Program description and execution state are separate.**
5. **A reusable Stream can create fresh execution state each time.**
6. **Formal reasoning should target Graph meaning, not surface syntax.**
7. **Performance evidence must compare execution backends, not API aesthetics.**

The canonical pipeline now has two views:

| View | Representation |
|---|---|
| user view | filter → map → reduce |
| compiler/control-plane view | typed Graph |

The next chapter does not add a new runtime capability yet. It asks a more basic question:

> **When an optimizer rewrites one Graph into another, why should we believe observable meaning is preserved?**

That leads to Observable Semantics, rewrite judgments, Lean theorems, and proof/certificate boundaries.

**Summary: Stream Is Graph's First High-Level Application, Not Its Foundation**

The key responsibilities are:

| Object | Responsibility |
|---|---|
| Graph | describes computation |
| Stream | provides a convenient data-transformation interface |
| Range | provides input |
| Collector | provides output |
| Executor | later decides how to execute |

The only directional relation we need here is the lowering relation: **Stream façade builds Typed Graph; selected execution backend later consumes that Graph/Plan.**

The main advantage is:

> **high-level interfaces and low-level execution are no longer bound together.**

Users can get declarative data transformation similar to Java Stream while the system remains free to lower it to an ordinary C loop, precompiled Plan, or other execution forms.

The value of Stream is not making C look like Java.

It is proving that once C has Type, Callable, and Graph, it can express data transformation at a high level **without giving up the simple, efficient execution model that made C valuable in the first place.**

The next chapter continues the Graph thread through correctness:

> **Which transformations are admissible, and what is the difference between a metadata property and a semantic law that actually authorizes a rewrite?**

That is the transition from Graph/Stream surface to Verified Rewrite.
