# Chapter 5: Stream Interfaces: Building Typed Graphs

Filtering, mapping, and reduction often occur together. An ordinary C loop can perform them; Stream makes their composition available as a checked, reusable computation description. This chapter develops the even-square-sum example from a loop into typed graph construction, then examines what the interface must preserve. CMeta supplies callable types, signatures, and declared properties, which CFlow uses to build the graph.

A **façade** offers a convenient interface to an existing mechanism. Stream is a graph façade: filter and map calls append nodes; traversal occurs during execution. **Observable semantics** means the results a contract allows callers to observe, including values, order, and errors. An equivalence claim must specify which observations it compares.

## 1. Start with a Runnable C Program

The following complete C11 program can be saved as `stream_baseline.c`. The even inputs are 2, 4, and 6, whose squares sum to 56. For other uses of its helper, assume `n <= 1000`, every element lies in `[-100, 100]`, and `xs` addresses at least `n` readable `int` objects. These bounds limit the sum to 10,000,000, within the minimum range C11 requires for `long`. Casting to `long` alone does not prove multiplication safe for arbitrary input.

~~~c
#include <stdbool.h>
#include <stddef.h>
#include <stdio.h>

static bool is_even(int x) { return x % 2 == 0; }
static long square(int x) { return (long)x * (long)x; }

static long even_square_sum(const int *xs, size_t n)
{
    long total = 0;
    for (size_t i = 0; i < n; ++i) {
        if (is_even(xs[i]))
            total += square(xs[i]);
    }
    return total;
}

int main(void)
{
    const int xs[] = {1, 2, 3, 4, 5, 6};
    printf("%ld\n", even_square_sum(xs, sizeof xs / sizeof xs[0]));
    return 0;
}
~~~

~~~bash
cc -std=c11 -Wall -Wextra -Werror -pedantic stream_baseline.c -o stream_baseline
./stream_baseline
~~~

**Loop invariant.** On entry to iteration `i`, `total` is the sum of the squares of the even elements in the first `i` positions. Initially, the empty prefix has sum zero. A rejected element extends the prefix without contributing; an accepted element contributes exactly its square. Both cases preserve the invariant for the next iteration. At termination, `i = n`, giving the result for the whole input. This hand derivation depends on valid storage and the stated integer bounds.

## 2. Describe Three Callables with CMeta

The following fragment uses the pinned macros and Stream entry points. It requires an installed CMeta/CFlow SDK and is not a standalone replacement for the preceding program. In addition to the concrete function, `cmeta_function` supplies an operator-specific callable object. Passing those objects to the builder makes signature facts available for checking.

~~~c
#include <cflow/cflow.h>

cmeta_function(filter, value, bool, sample_even, (int x)) {
    return x % 2 == 0;
}
cmeta_function(map, value, long, sample_square, (int x)) {
    return (long)x * (long)x;
}
cmeta_function(reduce, associative, long, sample_add,
               (long left, long right)) {
    return left + right;
}

static bool build_pipeline(cflow_stream *s)
{
    if (!cflow_stream_init(s, &cmeta_type_int))
        return false;

    s->filter(s, sample_even);
    s->map(s, sample_square);
    s->reduce(s, sample_add);
    return cflow_stream_ok(s);
}
~~~

The caller supplies an uninitialized Stream, such as `cflow_stream s = {0};`. After successful construction, `cflow_stream_graph(&s)` yields a borrowed read-only view. Call `cflow_stream_destroy(&s)` when finished; if initialization succeeded but a later operation failed, the acquired graph resources still need destruction. Do not reinitialize a Stream that still holds resources.

The `associative` declaration claims that `(a + b) + c = a + (b + c)` within the applicable domain. The macro does not prove this property from the function body. Signed overflow invalidates the reasoning for arbitrary integers. For the bounded nonnegative square terms in this example, every partial sum is no greater than the total, so regrouping remains representable. Reusing `sample_add` on another domain requires checking that domain separately.

Check `cflow_stream_ok` after the three method calls. The pinned implementation records failures and may still return the same non-null Stream pointer. A non-null method result therefore does not establish successful construction. Chaining changes the notation, not this error contract.

## 3. Type Connections and the Builder Algorithm

A **predicate** returns a Boolean result. **Reduction** combines values into at most one result. **Cardinality** describes how many outputs an input produces. The following table concerns sequential execution and reduction without an initial seed.

| Operation | Required callable | Graph type transition | Cardinality |
|---|---|---|---|
| Filter | `T -> bool` | `T -> T` | Zero or one output per input |
| Map | `T -> U` | `T -> U` | One output per successfully processed input |
| Reduce | `(T, T) -> T` | `T -> T` | One result for nonempty input; no accumulator for empty input |

Here `T` and `U` are type variables, and an arrow relates parameter and result types; it does not describe ownership transfer. The pinned ordinary Reduce requires the input, accumulator, and result to have the same type. This example therefore maps `int` to `long` before applying `(long, long) -> long` addition. A more general `(A, T) -> A` fold needs its own interface and rules; it must not be presented as this entry point.

The following pseudocode summarizes the order in `stream.c`. Binding validates and obtains a usable callable description; it does not execute the user function. Graph continues to handle node connections, type checks, and capacity constraints.

~~~text
append(stream, operator, callable):
    if stream has a recorded failure: return stream
    bind and validate the callable's signature and contract
    if binding fails: record failure; return stream
    ask Graph to check and append this operator
    if Graph rejects it: record failure
    return stream
~~~

A successful Filter keeps tail type `T`. A successful Map changes it to result type `U`, and a following Reduce requires `(U, U) -> U`. For example, connecting `int -> long` mapping to a `(double, double) -> double` reduction must fail. Similar-looking type names do not suffice; the checks use CMeta type and callable contracts.

A failed Stream must not execute. The pseudocode promises failure recording, not byte-for-byte rollback for every underlying failure. Transactional construction would require an explicit staging, commit, and rollback contract.

## 4. Why Construction Preserves Meaning

Let `ops` be an ordered operator list and `Build(ops)` its successfully constructed graph. Let `Obs(P, xs)` denote the output sequence, completion or error result, and their ordering permitted by the contract for program `P` and input `xs`. On valid inputs, the interface should satisfy:

~~~text
Obs(Stream(ops), xs) = Obs(Graph(Build(ops)), xs)
~~~

This is a proof obligation with a hand derivation, not a newly machine-checked theorem. Induct on the number of successfully appended operations. With no operations, both descriptions use the same input protocol. For the induction step, the interface passes the same operator and callable to Graph without executing an extra user call or reordering inputs. Equal observations for the prefix give the new node equal inputs; the same node rule gives equal subsequent observations. The argument assumes the interface adds no hidden buffering, error suppression, or backend substitution.

This construction argument does not authorize arbitrary optimization. Removing a Map changes the number of user-function calls. If the function logs a message, equal numeric results can still have different observable behavior. Rewriting requires Chapter 6's additional semantic assumptions and Chapter 7's backend eligibility checks.

Comparison with Section 1 also requires an empty-input decision. That loop returns zero when there are no inputs or all are filtered out. The unseeded Reduce here has no accumulator when it receives no values. The shared result 56 therefore compares the supplied nonempty filtered input; it does not establish equivalence for every input. To require an empty sum of zero, use an entry point with an explicit initial-value contract and include that contract in the proof.

## 5. Borrowed Input and Fresh Execution State

A **Range** describes traversal, for example through an object address, element type, and next-element operation. Copying that view copies the description without extending the underlying array or container's lifetime. A **Collector** specifies how outputs reach a destination; destination storage, commit, and failure behavior retain their own contracts.

| Object | Facts it holds | Lifetime requirement |
|---|---|---|
| Stream / Graph | Operators, types, connections, immutable parameters | A borrowed graph view requires the original description to remain valid |
| Range | Input object and traversal protocol | Storage survives traversal; repetition requires a reusable Range contract |
| One execution | Cursor, accumulator, counters, temporary values | Completion or cancellation settles these resources |
| Collector | Output-write and commit policy | Borrowed output and context cover execution and cleanup |

Executing the same description twice requires a fresh accumulator each time. If the first run produces 56 and the second starts from that value, it produces 112: shared live state has contaminated the reusable description. Skip counts, take counts, and wait registrations have the same problem. Reusable graph structure does not make a single-pass Range restartable or authorize concurrent traversal of the same input.

Asynchronous collection extends these borrowing periods. The pinned `cflow_stream_execution_start` owns its normalized graph, subscription, and collector state, but borrows the scheduler, Range backing object, and relevant collector contexts until destruction completes. This entry point requires concurrent scheduler capability. Returning from the stack frame that stores the input after a successful start would still leave a dangling borrow.

## 6. Generate Ordinary C Interfaces from One Operator Table

`CFlowOperators` declares operator kinds, callable parameter roles, and output rules in one place. `Replay(CFlowOperators, consumer)` feeds normalized rows to different consumers that generate method types, fields, initialization assignments, and builder wrappers. This applies Chapter 2's finite table expansion: a Filter declaration need not be maintained independently in four locations.

The following teaching expansion shows the relevant Filter declarations. Its pieces belong in a type declaration, the Stream structure, and the initialization function respectively; they are not a standalone translation unit.

~~~c
typedef cflow_stream *(*cflow_stream_filter_method)(
    cflow_stream *self, cflow_filter_callable fn);

/* Field generated inside struct cflow_stream: */
cflow_stream_filter_method filter;

/* Assignment performed during initialization: */
s->filter = cflow_stream_filter;
~~~

`s->filter(s, sample_even)` remains an ordinary C function-pointer call. The explicit `s` is the receiver, and the initialized field selects the builder function. That function obtains signature and type facts from the callable and passes them to Graph. Macros remove repeated declarations, descriptors support construction checks, and function pointers retain ordinary C calls.

Visible structure fields are not all writable public state. The pinned header designates generated methods as stable invocation fields, the graph as advanced read-only introspection, and fields such as `input_range`, `eval_options`, and failure state as internal. Prefer `cflow_stream_graph` for inspection rather than editing nodes around the builder.

Asynchronous borrowing is documented in [stream_execution.h](https://github.com/qigao/salts/blob/a650262031e9b3e5f11a227a7911a75db9ae1fb8/cflow/include/cflow/stream_execution.h). All links use the edition commit in `SOURCE_SNAPSHOTS.md`.

The [certificate tests](https://github.com/qigao/salts/blob/a650262031e9b3e5f11a227a7911a75db9ae1fb8/cflow/tests/cflow_certificate_test.c) use the same even-filter, square-map, and addition-reduce pipeline, then normalize, optimize, compile a plan, and build and check its certificate. A **certificate** records checkable facts relating a graph to a plan. Passing its checker does not prove arbitrary C function bodies obey their declared associativity. The tests also alter recorded fields to check rejection; read these counterexamples alongside successful execution.

| Check | Required observation | What it does not establish |
|---|---|---|
| Incorrect predicate or reducer type | Failed construction with a queryable error | Validity of every runtime object address |
| Repeated execution of one description | Independent live execution state | Concurrent or repeated traversal of every Range |
| Unsupported graph on the selected backend | Explicit rejection without silent backend replacement | Support for every valid graph on every backend |
| Altered certificate fields | Rejection by the corresponding checks | Mathematical laws of user function bodies |

Section 1 also provides a performance baseline. Measure construction and execution separately, fixing input, operations, result checking, and backend before comparing repeated runs. Direct means an execution path that reduces per-value interpretation; AOT, or ahead-of-time generation, produces and compiles code before execution. The pinned Direct scope primarily covers Filter/Map. Do not present the complete reduction loop as code already emitted by Direct. Chapter 7 covers plans containing Reduce and their eligibility conditions; interface notation supplies no performance measurements.

## 8. Summary

Stream uses CMeta function and type facts to construct graphs. Methods append nodes and Graph checks their connections; input remains with its original owner, while each execution keeps fresh cursors and accumulated state. Establishing meaning requires matching operations, callable objects, and observations, including initial values, empty inputs, failure behavior, and backend scope. These checks connect the convenient interface to its graph description and eventual ordinary C execution.
