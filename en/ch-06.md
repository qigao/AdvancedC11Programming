# Chapter 6: Graph Semantics and Rewrite Proofs

Removing or combining graph nodes changes the function calls that execute. Correctness therefore requires a definition of observable behavior and a proof that the transformation preserves it. This chapter derives an idempotent Map rewrite from a function equation, then explains the separate roles of CMeta property declarations, Lean theorems, and checks in the C optimizer.

## 1. Property Claim Is Not Rewrite Authority

**Idempotent** here means that `f(f(x)) = f(x)` for admitted inputs. This is a property of behavior. Setting an `IDEMPOTENT` flag claims that the property holds; it does not supply a proof.

Suppose metadata says:

~~~c
clamp.properties |= IDEMPOTENT;
~~~

and the optimizer wants to eliminate two **sequential** Map nodes. Write the data flow explicitly:

~~~text
input x
  |
  v
Map(clamp)
  |
  | y = clamp(x)
  v
Map(clamp)
  |
  | z = clamp(y)
  v
output z
~~~

The classification is:

~~~text
Graph level:
    two Map nodes execute in sequence
    = sequential composition

Per-element expansion:
    y = clamp(x)
    z = clamp(y)
      = clamp(clamp(x))
    = nested function application

Recursion:
    no.
    The implementation of clamp() does not call clamp() itself.
~~~

For two different functions:

~~~text
Map(f) -> Map(g)

on one element x means:

g(f(x))

therefore:

Map(g) after Map(f)
    = Map(g ∘ f)
~~~

Here f = g = clamp:

~~~text
Map(clamp) -> Map(clamp)
    = Map(clamp ∘ clamp)
~~~

The optimizer wants to replace it with one Map(clamp). The metadata bit is not enough. The actual law is:

~~~text
∀x, clamp(clamp(x)) = clamp(x)

equivalently:

clamp ∘ clamp = clamp
~~~

The roles are different:

| Object | Role |
|---|---|
| property bit | admission claim |
| semantic theorem | rewrite authority |

## 2. Define Observable Semantics First

For a pure data-flow pipeline, a simplified evaluator may be:

~~~text
eval(Source(xs)) = xs

eval(Filter(p, s)) =
    [x in eval(s) | p(x)]

eval(Map(f, s)) =
    [f(x) | x in eval(s)]

eval(Reduce(r, z, s)) =
    foldl(r, z, eval(s))
~~~

This is **specification semantics**, not runtime implementation. Without an observation model, rewrite preservation is undefined.

## 3. Rewrite Judgment

Write optimizer authorization as:

~~~text
Γ ⊢ P ~> Q
~~~

with:

~~~text
Γ ⊢ admitted(P)
Γ ⊢ rewrite_preconditions(P,Q)
Γ ⊢ ∀input, observe(eval(P,input))
             = observe(eval(Q,input))
────────────────────────────────────────
Γ ⊢ P ~> Q : sound
~~~

For an idempotent map, fix the notation first:

~~~text
Map(f); Map(f)
~~~

The semicolon means **execute the left Map and then the right Map in the pipeline**. It does not mean recursion. For one input x:

~~~text
x
 -> first Map(f)
 -> f(x)
 -> second Map(f)
 -> f(f(x))
~~~

The rewrite rule is therefore:

~~~text
IDEMPOTENT(f)
∧ theorem ∀x, f(f(x)) = f(x)
────────────────────────────────
Map(f); Map(f)  ~>  Map(f)
~~~

Metadata selects candidates. The theorem authorizes the transformation.

## 4. Lean Theorem Must Bind to a Concrete Transformation

Conceptually:

~~~text
theorem map_idempotent_preserves_eval
    (hf : ∀ x, f (f x) = f x) :
    eval (Map f (Map f s))
    =
    eval (Map f s)
~~~

C optimizer does not run Lean at runtime. This is a **proof-to-optimizer registration pipeline**: the arrows carry artifacts/authority, not runtime values.

~~~text
Lean source
    ↓ prove theorem
approved rule manifest
    ↓ register authorized rule
C optimizer matcher
    ↓ apply matching rule
rewrite
~~~

Normal C builds need no theorem prover.

## 5. Proof Trace and Certificate

**Terminology:** Refinement relates a concrete implementation to the behavior specified by an abstract model; this chapter focuses on preserving defined observations. A certificate is an evidence record that a checker uses to relate a concrete artifact to approved rules, not a security certification. A fingerprint is a content summary for identifying or linking artifacts, not a proof of semantic equivalence.

A rewrite records rule id, input Graph fingerprint, output Graph fingerprint, required property ids, and proof/certificate version. For example:

~~~c
typedef struct rewrite_trace {
    uint32_t rule_id;
    uint64_t before_hash;
    uint64_t after_hash;
    uint32_t certificate_version;
} rewrite_trace;
~~~

Trace answers which rewrite happened; Certificate answers whether a concrete artifact satisfies an approved refinement relation. They are different objects.

## 6. Trusted Boundary

| Claim | Evidence |
|---|---|
| property declared | C metadata / generator |
| rewrite law valid | Lean theorem |
| optimizer used approved rule | trace / matcher test |
| generated C matches plan | differential/refinement test |
| ABI works | compile/link/install |
| faster | benchmark |

Do not use a theorem to prove ABI, a finite unit-test suite to prove universal semantic equivalence, or a benchmark to prove correctness.

## 7. Failure Cases

### Claim but no theorem

If the `IDEMPOTENT` bit is present but no proof rule is available, return `NO_REWRITE`.

### Stale certificate

If the Graph fingerprint changed while the certificate still names the old fingerprint, return `REJECT_CERTIFICATE`.

### Undefined observation model

If a transformation may change encounter order, error timing, side effects, or allocation observations and semantics do not say whether they are observable, then **rewrite not admitted**. Do not let a PURE bit substitute for missing semantics. The remainder of the chapter walks the complete trusted chain through the concrete Idempotent Map case.

## 8. How the Current Implementation Maps to the Derivation

Sections 1–7 already derived the semantic obligation, so there is no need to expand `clamp(clamp(x)) = clamp(x)` again. The remaining question is whether the pinned formal objects, optimizer rule, and trace correspond to that derivation.

The current formal Rewrite proof contains `map_idempotent_elimination`. Its premise is not a bare `IDEMPOTENT` bit but `IdempotentEndomapPremises Γ ty`, which includes modeled callable meaning and the actual idempotence law. More generally, `certified_rewrite_preserves_observations` establishes observation preservation for finite compositions of certified rewrites under their premises.

On the C side, the stable rule id `IDEMPOTENT_MAP_ELIMINATION` names this rewrite class, while the Proof Trace records the concrete source subgraph, retained node/callable, and removed node/callable. The same rewrite therefore has four distinct objects at four layers:

| Layer | Concrete object | Responsibility |
|---|---|---|
| CMeta metadata | `IDEMPOTENT` | select a callable as a candidate; no proof |
| Lean | `map_idempotent_elimination` | prove the rule sound under its premises |
| C optimizer | `IDEMPOTENT_MAP_ELIMINATION` | apply an authorized rule to a concrete Graph |
| Proof Trace / checker | source/target coordinates + rule id | establish that this rewrite instance matches the approved rule |

A checker therefore validates more than the presence of a bit: the trace must bind the exact source Graph/version and optimized Graph/version, the rule id must be supported, source and target coordinates must match, and the final structure must match the expected Stage IR.

The negative case is just as important. If metadata claims `IDEMPOTENT` but no theorem-backed rule is available, the optimizer keeps the original Graph. If the trace is stale or cannot bind the current Graph, the checker rejects it rather than treating the property bit as rewrite authority.

## 9. Manifest: How Lean Enters Ordinary C Without Entering the Ordinary C Build

If formalization requires every application consumer to install Lean, the engineering boundary has failed. The current Salts snapshot uses checked-in generated artifacts.

### 9.1 Builtin Signature Manifest

Lean validates the finite built-in type/signature relation and generates `cmeta/include/cmeta/generated/builtin_signature_manifest.h`. An ordinary C/C++ build includes the checked-in header and **does not run Lean**. Only CI / semantic development workflows run **cmeta-signature-gen --check** to ensure:

~~~text
formal source
    ↔
checked-in C artifact
~~~

has not drifted.

### 9.2 Builtin Operator Policy

Similarly, the finite CFlow operator-policy relation is checked by the formal package and generates `cflow/include/cflow/generated/builtin_operator_policy.h`. The C optimizer/runtime consumes an ordinary C table/header instead of invoking a theorem prover in the hot path.

### 9.3 Generator Is Part of the Trusted Bridge

We must be honest here. A correct theorem plus an incorrect generator may still create a wrong C header. So the trusted bridge includes formal definitions/theorems, generator mapping, generated-artifact checks, and C consumer interpretation. Generated headers should therefore be:

- simple;
- readable;
- diff-friendly;
- reproducible/checkable in CI;
- never hand-edited into a second source of truth.

## 10. Certificate and Proof Trace: Two Different Runtime Bridges

### 10.1 Proof Trace

Answers:

> Why did the optimized Graph change from the source Graph to this structure?

It records rewrite rule id, source coordinate, retained/removed node, callable coordinate, and source/output Graph binding. Trace is a **Transformation Witness**.

### 10.2 Certificate

Answers:

> Does this Plan / execution path still correspond to the approved normalized/optimized semantic program?

It records Graph version/fingerprint, certified opcode rows, types, callables, effects/properties, execution path, ordering, and required capabilities. A witness is evidence used by a checker to establish that a concrete execution artifact satisfies the required relation. A certificate relates the artifact to its graph, rules, and execution conditions; it is more than a flag claiming successful compilation. So the chain is:

~~~text
Source Graph
    ↓
Optimizer
    ↓
Proof Trace
    ↓
Optimized Graph
    ↓
Plan Compile
    ↓
Certificate
    ↓
Execution
~~~

Future stronger assurance can independently improve trace checker, certificate checker, artifact identity, and generator provenance without converting the whole runtime into a theorem prover.

## 11. Formal Trusted Base and Execution Trusted Base Must Be Separate

“Trusted computing base” means different things at different layers.

### 11.1 Formal Proof Trusted Base

At minimum it includes formal definitions, theorem statements/premises, Lean checker/kernel/toolchain assumptions, and the semantic model itself. A theorem is correct only relative to its model and premises. If observable semantics is specified incorrectly, the proof may be perfectly valid while proving the wrong thing. Specification review matters as much as theorem proof.

### 11.2 Bridge Trusted Base

The bridge trusted base includes generators, rule-id mapping, trace construction/checking, certificate construction/checking, and type/callable identity mapping. These connect the formal world to C artifacts.

### 11.3 Execution Trusted Base

The execution trusted base includes the C compiler/linker, C implementation, allocator/thread primitives, OS/runtime, hardware, and borrowed callback/user code. Only parts that are actually formalized/refined inherit theorem guarantees; other parts need tests, sanitizers, ABI qualification, stress, platform CI, and benchmarks.

### 11.4 External Liveness Assumptions

Statements such as “OS eventually schedules worker,” “socket eventually becomes ready,” “device eventually completes,” and “user callback eventually returns” are usually environment assumptions, not CMeta/CFlow theorems. The book must label them explicitly so a safety proof is not overstated as “the system can never get stuck.”

## 12. How Proof, Test, and Runtime Checks Work Together

A mature feature should not ask “proof or test?” It should ask:

At which layers does this claim require evidence? For idempotent rewrite:

~~~text
Semantic law
    → Lean theorem

Concrete optimizer event
    → proof trace

Graph/optimized binding
    → trace checker

Plan binding
    → certificate

C implementation regression
    → differential tests

memory/lifetime
    → sanitizer

performance benefit
    → benchmark
~~~

For Reactive demand:

~~~text
demand mathematical invariant
    → Lean

runtime state mapping
    → conformance tests

wake/cancel race
    → stress/readiness tests

scheduler capacity behavior
    → bounded protocol tests

latency/throughput
    → benchmark
~~~

A professional verification stack is therefore:

~~~text
Formal proof
+
Generated facts
+
Runtime admission
+
Differential testing
+
Memory/concurrency testing
+
ABI/platform qualification
+
Measurement
~~~

not one of these pretending to replace all others.

## 13. Summary

A rewrite needs a semantic model defining observations, a transformation law under stated assumptions, and an implementation that applies the law only when those assumptions hold. CMeta property flags can select candidate rules but cannot prove that arbitrary C code satisfies a law. Idempotent Map proceeds from `f(f(x)) = f(x)` to equal elementwise results. Order, errors, side effects, and resource behavior must also be modeled when observable. Traces and certificates relate concrete artifacts to approved rules, while differential tests check whether the C implementation follows them.
