# Chapter 6: Graph Semantics and Rewrite Proofs

An optimizer may reduce the number of calls, but removing a call is correct only if its observable behavior is preserved. CMeta property flags provide declarations for rule selection; CFlow's semantic model and proofs specify when those declarations can authorize a transformation. This chapter connects a concrete C function, list semantics, a Lean theorem, and a recorded rewrite instance.

## 1. A Checkable Idempotent Function

This complete function clamps an integer to `[0, 100]`. It performs no arithmetic and cannot overflow on extreme `int` inputs.

~~~c
int clamp100(int x)
{
    if (x < 0)
        return 0;
    if (x > 100)
        return 100;
    return x;
}
~~~

**Idempotence** means applying the function again leaves the first result unchanged: `f(f(x)) = f(x)`. There are three cases. A negative input becomes zero, which remains zero. An input above one hundred becomes one hundred, which remains one hundred. An input within the interval is returned unchanged by both calls. These cases cover the entire `int` domain.

This is not recursion: the body never calls itself. Two consecutive Map nodes apply `clamp100(clamp100(x))` to an input. Idempotence allows us to consider removing one node.

## 2. Defining the Observations

Comparing only final values misses logging, errors, and cleanup. **Observational semantics** specifies what an external observer can distinguish. The model used here includes value sequences, effect records, terminal outcomes, and ownership-safety information. Implementation checks must cover the corresponding callback ordering and resource behavior.

| Behavior | Are two Maps naturally equivalent to one? |
|---|---|
| Output of `clamp100` | Yes, by the preceding argument |
| Logging on every call | No: the number of log entries changes |
| Failure on every second call | No: call count affects failure |
| Resource acquisition and release on each call | Requires additional effect and ownership reasoning |

A **pure** function has no external effects observed by the model. A **total** function has a normally defined result for every admitted input. A `return` statement does not establish totality of C code: undefined behavior must also be excluded. These conditions are straightforward for the branch-only function above but require separate justification for an arbitrary callback.

## 3. Lifting the Law to a Stream

For a finite list `xs`, `map(f, xs)` applies `f` to every element in encounter order. The desired equality is:

~~~text
map(f, map(f, xs)) = map(f, xs)
assuming: for every admitted x, f(f(x)) = f(x)
~~~

Both sides are empty for an empty list. For `xs = h :: t`, the left head is `f(f(h))`, equal to `f(h)` by idempotence. The tails are equal by the induction hypothesis. Equal heads and tails establish equal lists. The notation `h :: t` means a head element followed by its tail list.

This argument concerns values. Full StreamResult equality also requires the model's purity, totality, and other premises so that effects, termination, and ownership observations remain unchanged. The pinned theorem collects these conditions in `IdempotentEndomapPremises`. An **endomap** maps a type to itself; otherwise `f(f(x))` might not even be well-typed.

## 4. What the Lean Theorem Establishes

The following is an existing theorem from the pinned source. Its `premises` supply an admitted semantic interpretation and `stream` is a model result. It does not automatically assign a proved mathematical meaning to an arbitrary C function pointer.

~~~lean
theorem map_idempotent_elimination {Γ : Env} {ty : Ty}
    (premises : IdempotentEndomapPremises Γ ty)
    (stream : StreamResult (Value ty)) :
    (stream.map premises.meaning.apply).map premises.meaning.apply =
      stream.map premises.meaning.apply := by
  cases stream
  simp [StreamResult.map,
    list_map_idempotent premises.meaning.apply premises.idempotentLaw]
~~~

`cases stream` exposes the result structure. `simp` uses the stream-map definition and the proved list lemma to simplify the equality. The preceding induction explains the lemma. The theorem comes from [Proofs/Rewrite.lean](https://github.com/qigao/salts/blob/a650262031e9b3e5f11a227a7911a75db9ae1fb8/formal/cmeta_cflow_calculus/CMetaCFlowCalculus/Proofs/Rewrite.lean); the C branch argument in this chapter is a hand proof, not a new machine-checked verification of the C implementation.

An `IDEMPOTENT` flag states a claim. If the function increments a global counter on every call, incorrect metadata is not repaired by the theorem. Relating the implementation to its semantic interpretation remains a responsibility of providers, generators, and verification.

## 5. From a General Rule to One Rewrite

A **rewrite trace** records where a specific transformation occurred and what justified it. The theorem establishes the general rule under its premises; the trace identifies its application to a concrete input graph. This is explanatory pseudocode rather than a verbatim SDK implementation.

~~~text
remove_duplicate_map(graph, candidate):
    require candidate contains two consecutive Map nodes
    require the same admitted callable meaning at both nodes
    require the callable is a pure, total endomap
    require an authorized idempotence law for that meaning
    build a new graph with one Map removed
    validate the new graph
    record rule, source identity, target identity, and affected nodes
    publish graph and record together
~~~

Equal function pointers alone do not establish equal complete calls: captures, signatures, and semantic conditions also matter. Equal function names likewise do not establish implementation identity. The trace must bind the actual source and destination snapshots so that evidence for an old graph cannot justify a modified one.

The pinned `IDEMPOTENT_MAP_ELIMINATION` rule records affected subgraphs, retained and removed nodes, and callable indices. A checker can validate only rules it understands. Unknown events must be rejected rather than ignored.

## 6. Composing Correct Rewrites

If one transformation proves `observe(G0) = observe(G1)` and another proves `observe(G1) = observe(G2)`, transitivity gives `observe(G0) = observe(G2)`. Induction extends this argument to any finite sequence. The pinned `certified_rewrite_preserves_observations` establishes such preservation for the model's certified rewrite composition.

The two occurrences of `G1` must denote the same checked artifact. A trace for an old version cannot be joined with a trace for a later mutation merely because both rule names are valid. Versions, structural matching, and borrowed lifetimes constrain this connection.

Map fusion is a separate rule: `map(g, map(f, xs))` and `map(g ∘ f, xs)` preserve value order. Composition `g ∘ f` applies `f` before `g`. Errors and external effects require the full observation conditions; a numeric equality does not authorize arbitrary execution reordering.

## 7. Generated Tables, Checkers, and Trust

**Refinement** implements an abstract meaning with a more concrete representation or sequence of steps while preserving specified observations. Compiling a graph into a plan establishes this kind of correspondence; it does not reprove the machine code of every C callback.

The pinned project exports some built-in signatures and operator policies into generated headers, including `builtin_signature_manifest.h` and `builtin_operator_policy.h`. Ordinary C builds consume these artifacts without necessarily running Lean. Release verification must establish agreement among the formal project, generation tools, and committed output.

| Layer | Evidence | Remaining assumptions |
|---|---|---|
| Mathematical model and Lean theorems | Semantic equalities under stated premises | The definitions express the intended property |
| Rule and artifact checkers | The instance matches supported forms and snapshots | Correct checker implementation and valid input storage |
| C execution and callbacks | Compilation, differential runs, failure-path tests | Callback behavior, ABI, toolchain, and lifetime contracts |

The scope of a proof follows its claim. Safety says that a bad event cannot occur, such as executing a rejected call. Progress says that work eventually completes. Neither type preservation nor rewrite equivalence guarantees that an external source will eventually supply data.

## 8. Verification and Exercise

Test `clamp100` at `INT_MIN`, `-1`, `0`, `50`, `100`, `101`, and `INT_MAX`, comparing one and two calls. Such tests can reveal disagreement with the branch argument but cannot replace its whole-domain proof. Graph checks should compare values, order, termination, and resource behavior, including rejection of false metadata and stale traces where the checker can detect them.

For an exercise, add a log counter to the clamp function. Prove that its returned values remain idempotent, then explain why its full observations differ. The example makes the authorization conditions explicit: a property name alone does not justify deleting a node.

## 9. Summary

A correct optimization connects C behavior, an explicit observation model, an applicable rule, and a trace bound to concrete artifacts. Induction lifts a value law to lists, and transitivity composes rewrites. Both arguments depend on valid premises and matching intermediate artifacts. Property flags help select candidates; they do not independently prove arbitrary implementations correct.
