# Chapter 1: CMeta Foundations: Macros, Inline Functions, and Compile-Time Constraints

CMeta uses macros to generate declarations, ordinary and inline functions to perform typed operations, and static metadata to describe facts shared by multiple modules. This chapter starts with repeated evaluation in macros, compares the guarantees of functions, finite expansion, and compiler extensions, and applies them to member-pointer recovery, type selection, and scope cleanup.

This book calls the metaprogramming, RAII, and reflection component **CMeta**. Literal `cmeta_*` / `CMETA_*` identifiers remain unchanged, while Salts names the source repository, SDK distribution, and real build targets such as `Salts::CMeta`. Reflection here primarily means generated, inspectable static descriptors for types and functions. RAII conventionally binds resource lifetime to object lifetime; in C, this book uses explicit cleanup protocols and separately identified scope-cleanup extensions rather than a hidden runtime.

## 1. Establish the Need from an Ordinary Function

This comparison function maps the ordering of two `int` objects to minus one, zero, or one. It uses ordinary C type and comparison rules; the caller must keep both pointers valid for the duration of the call.

~~~c
static int int_compare(const int *a, const int *b)
{
    return (*a > *b) - (*a < *b);
}
~~~

If the system needs only this implementation, a direct call is sufficient. If comparison, hashing, and serialization need the same type set or field list, record those shared facts and generate each required declaration or descriptor from them. That duplication establishes where CMeta is useful: identify the knowledge to reuse before choosing macros or metadata to represent it.

## 2. static inline: Solve Typed Behavior Before Reaching for a Macro

One classic macro problem is repeated evaluation. For example:

~~~c
#define MAX(a, b) ((a) > (b) ? (a) : (b))
~~~

A call such as:

~~~c
int x = MAX(next_a(), next_b());
~~~

does not give the caller the evaluation behavior suggested by a normal function call. If the problem is simply typed behavior, prefer a function:

~~~c
static inline int
int_max(int a, int b)
{
    return a > b ? a : b;
}
~~~

The call remains ordinary C:

~~~c
int x = int_max(next_a(), next_b());
~~~

The compiler checks argument types, and the body accesses parameter objects containing already-evaluated values. The `inline` specifier allows consideration for inlining but does not guarantee removal of the call. Function evaluation rules apply either way. Macros instead generate identifiers, types, and declaration structure that function parameters cannot express.

**Deriving the evaluation count.** In expanded `MAX(a, b)`, the comparison evaluates both arguments and the selected branch evaluates one of them again. For defined, normally completing execution, the selected expression is evaluated twice and the other once. In `int_max(a, b)`, each argument is evaluated once to initialize parameter objects; the body reads those objects. The pseudocode describes counts without choosing an argument order.

~~~text
macro_max(a, b):
    compare evaluate(a) with evaluate(b)
    evaluate the selected expression again

function_max(a, b):
    evaluate each argument once and initialize parameter objects
    compare the parameter values
    return the selected parameter value
~~~

The control flow therefore gives three argument-expression evaluations for the macro and two for the function on normal completion. This is independent of compiler inlining and does not impose an order on the function arguments. If both arguments modify the same scalar without sequencing between those modifications, replacing the macro with a function does not remove the undefined behavior.

The following complete C11 program turns the difference into an observable result. The two helper functions modify different counters, so the example does not depend on argument evaluation order and does not create unsequenced modifications of the same scalar.

~~~c
#include <stdio.h>

#define MAX(a, b) ((a) > (b) ? (a) : (b))

static int a_calls;
static int b_calls;

static int next_a(void)
{
    ++a_calls;
    return 10;
}

static int next_b(void)
{
    ++b_calls;
    return 5;
}

static inline int int_max(int a, int b)
{
    return a > b ? a : b;
}

int main(void)
{
    int m = MAX(next_a(), next_b());

    printf("macro: value=%d a=%d b=%d\n",
           m, a_calls, b_calls);

    a_calls = 0;
    b_calls = 0;

    int f = int_max(next_a(), next_b());

    printf("func : value=%d a=%d b=%d\n",
           f, a_calls, b_calls);
    return 0;
}
~~~

A conforming implementation may choose a different order for the two function arguments, but the counts remain:

~~~text
macro: value=10 a=2 b=1
func : value=10 a=1 b=1
~~~

That gives the first testable rule for the rest of the chapter: **when a macro accepts an expression that may have side effects, its evaluation count must be explicit; the default design target is one evaluation.**

## 3. Macros Are Best at Things C Functions Cannot Express

A normal function cannot generate:

- a type name;
- a field declaration;
- a function prototype;
- an identifier;
- an initializer row;
- a metadata declaration.

Those live in the token/declaration plane. Suppose the same builtin type set is consumed by compare, hash, and serialization code:

~~~c
#define BUILTIN_TYPES(X) \
    X(int)               \
    X(long)              \
    X(float)
~~~

Different consumers replay the same facts:

~~~c
#define GEN_COMPARE(T) DEFINE_COMPARE(T)
BUILTIN_TYPES(GEN_COMPARE)

#define GEN_HASH(T) DEFINE_HASH(T)
BUILTIN_TYPES(GEN_HASH)
~~~

The reusable object is not mainly the generated code. It is the fact:

~~~text
supported type set
    =
{ int, long, float }
~~~

So:

the most valuable use of a macro is not to hide runtime logic, but to generate structure that C cannot express as a function argument.

## 4. Linux-Style Finite Mapping: Make Arity Data, Not Part of Every Macro Name

**Terminology:** Arity is the number of arguments or elements; here it counts `(type, name)` declaration pairs. PP abbreviates preprocessor. A DSL, or domain-specific language, is a notation tailored to a particular task, such as these declaration macros.

An interface may represent parameters as flat pairs:

~~~text
int, fd,
size_t *, written
~~~

The direct but poor scaling path is:

~~~text
PARAMS_0
PARAMS_1
PARAMS_2
PARAMS_3
...
~~~

followed by another arity family in every higher-level DSL:

~~~text
DECLARE_0..N
CALL_0..N
META_0..N
VALIDATE_0..N
~~~

CMeta now centralizes these mechanics in a finite PP kernel. Examples include:

~~~c
CMETA_PP_PAIR_MAP_N(N, M, C, ...)
CMETA_PP_MAP_COMMA_N(N, M, C, ...)
CMETA_PP_MAP_PREFIX_COMMA_N(N, M, C, ...)
~~~

Conceptually:

~~~text
(type,name,type,name,...)
          ↓
   finite pair map
      /        \
 declaration   arguments
      |           |
 metadata      wrapper
~~~

The important part is not macro cleverness. It is the design constraint:

~~~text
finite
explicit
bounded
~~~

The production core does not need an unbounded recursive macro machine built from:

~~~text
DEFER -> OBSTRUCT -> EVAL -> recursive expansion
~~~

A more clever preprocessor is not automatically a better engineering boundary.

## 5. pp.h and compiler.h Are Different Layers

Preprocessor mechanics and compiler capabilities are not the same thing. The boundary can be drawn as:

~~~text
cmeta/pp.h
    token
    tuple
    finite map
    boolean
    unique-name composition
          |
          v
cmeta/compiler.h
    typeof capability
    auto-type capability
    type compatibility
    cleanup attribute
    section/used attribute
    compile-time expression requirement
          |
          v
higher-level CMeta declarations
~~~

Higher-level code should not repeatedly grow:

~~~c
#ifdef __GNUC__
...
#elif defined(__clang__)
...
#elif defined(_MSC_VER)
...
#endif
~~~

It should ask for a documented capability instead. Representative CMeta entry points now include:

~~~c
CMETA_NATIVE_TYPEOF(expr)
CMETA_SAME_TYPE(a, b)
CMETA_AUTO(name, expr)
CMETA_CONST_REQUIRE(condition)
~~~

The rule is:

when a capability is unavailable, do not silently pretend that a weaker mechanism provides the same guarantee. Either the capability exists, an explicitly weaker contract is selected, or compilation fails.

## 6. Single Evaluation: Macros and Compiler Facilities Must Protect the Caller Together

Some generic helpers really do require a macro because they need the native type of an expression. Even then, the intended shape should be:

~~~text
user expression
      ↓
evaluate once
      ↓
typed local
      ↓
operate on local
~~~

When the capability exists:

~~~c
CMETA_AUTO(tmp, expression);
~~~

The goal is not to create a dynamic `Any`. It is to create an ordinary native local:

~~~text
expression
    ↓ once
native typed local
    ↓
ordinary C operation
~~~

This rule will recur throughout the book:

if a macro accepts an expression that may have side effects, single evaluation is the default requirement; if that cannot be guaranteed, the limitation belongs in the contract.

## 7. container_of: How Macros, typeof, and Layout Checks Cooperate

`container_of` is a good Modern C example. The goal is to recover an enclosing object from the address of its actual member:

~~~c
struct Node {
    int value;
    struct Link link;
};

struct Link *p = ...;
struct Node *node =
    cmeta_container_of(p, struct Node, link);
~~~

The useful contract is more than:

~~~c
(char *)p - offsetof(struct Node, link)
~~~

Where the compiler permits it, we also want a compile-time relationship equivalent to:

~~~text
type(p)
    ==
type(&((struct Node *)0)->link)
~~~

CMeta therefore separates:

~~~text
compiler capability
    CMETA_NATIVE_TYPEOF
    CMETA_SAME_TYPE
            |
            v
container/member recovery
    cmeta_container_of(...)
~~~

If a compiler cannot provide inferred native typeof, the explicit-member-type entry point is used instead of pretending the guarantees are identical. This gives a recurring pattern:

~~~text
macro
  + compiler type fact
  + compile-time requirement
        ↓
ordinary pointer arithmetic
~~~

There is no runtime reflection lookup.

## 8. _Generic Is Compile-Time Dispatch, Not Semantic Authority

**Terminology:** Ownership identifies who is responsible for releasing or transferring a resource. A borrow permits access within an agreed lifetime without acquiring ownership. A TU, or translation unit, is the unit produced by preprocessing a source file, including its included headers.

C11 `_Generic` can make a finite selection:

~~~c
#define print_value(x) _Generic((x), \
    int: print_int,                  \
    long: print_long,                \
    double: print_double             \
)(x)
~~~

It answers:

> given the static C type of this expression, which existing expression should be selected?

It does not automatically answer:

- what the semantic identity of the type is;
- which lifecycle provider owns it;
- which fields a struct exposes;
- the IN/OUT/ownership contract of a function;
- whether descriptors from different translation units mean the same thing.

Therefore:

~~~text
_Generic
    =
compile-time selection

Reflection descriptor
    =
semantic authority
~~~

They can cooperate, but they do not replace one another.

## 9. Macro + static inline + Reflection Are Not Three Runtimes

Consider a common declaration-generation shape:

~~~text
schema / declaration row
        ↓ macro replay
ordinary C declaration
        +
static metadata
        +
static inline typed accessor
~~~

A caller may simply write:

~~~c
const cmeta_function_desc *desc =
    get_user_cmeta_function();
~~~

while execution remains:

~~~c
int rc = get_user(repo, id, &user);
~~~

The existence of Function Reflection should not automatically turn execution into:

~~~text
box arguments
   ↓
dynamic lookup
   ↓
erased dispatcher
   ↓
unbox result
~~~

Reflection does not imply dynamic dispatch. Reflection preserves stable meaning. The consumer decides how, or whether, that meaning becomes executable.

## 10. Keep the Static Path and the Dynamic Boundary Separate

**Terminology:** Canonical means the authoritative representation used by subsequent stages; it does not require descriptors to share a memory address. DSO commonly means a dynamic shared object: a shared library supplying code and data. An ABI, or application binary interface, specifies calling conventions and data layout between compiled modules.

**Admission** checks a descriptor or operation against its contract before accepting it. The resulting capability is usable only within its specified authority and lifetime. A **hot path** is frequently executed, cost-sensitive code; the aim here is to move checks into one-time admission.

For a canonical declaration known at compile time:

~~~text
known type/function
      ↓
direct generated binding
      ↓
static inline / direct call
~~~

we should not walk a descriptor graph on every call. A Plugin, DSO, or foreign descriptor is a different problem:

~~~text
foreign/raw descriptor
        ↓
validate ABI / layout / semantics
        ↓
admit once
        ↓
small admitted capability
        ↓
reuse many times
~~~

Validation and execution have the following responsibilities:

~~~text
static world
    -> prove/generate early

dynamic boundary
    -> validate once

hot path
    -> use admitted/direct representation
~~~

The validated representation can be reused while its contract remains valid, avoiding repeated descriptor traversal in the hot path.

## 11. Optional Syntax Lowering Is Not a Requirement for CMeta

**Lowering** converts higher-level syntax or representation into a form closer to the implementation while preserving its specified semantics. The example below turns member-style syntax into an ordinary C call with an explicit receiver argument. Lowering alone does not guarantee a speedup.

Later we will encounter receiver-like syntax, conceptually:

~~~c
list.add(10);
~~~

A frontend may lower it to:

~~~c
IntList_add(&list, 10);
~~~

But canonical CMeta must not require every ordinary C consumer to pass through a source translator. The correct relationship is:

~~~text
optional syntax frontend
        ↓
canonical semantic resolution
        ↓
ordinary C API
~~~

not:

~~~text
CMeta
  =
mandatory new C source language
~~~

Receiver metadata, Reflection, Generic, and the rest of the semantic layer must remain directly consumable from ordinary C.

## 12. A Practical Decision Tree

Chapter 1 can now be reduced to one practical test:

~~~text
Can a normal C function express it?
        |
       yes
        v
normal function / static inline

Need to create tokens, declarations, identifiers,
or replay a finite schema?
        |
       yes
        v
finite macro / PP kernel

Need native compiler knowledge such as typeof,
same-type, cleanup or section placement?
        |
       yes
        v
capability-gated compiler abstraction

Need stable meaning shared by several consumers?
        |
       yes
        v
canonical Reflection / semantic descriptor

Crossing a foreign or dynamic boundary?
        |
       yes
        v
validate once -> admitted capability
~~~

Do not collapse these layers into one universal mechanism.

## 13. Four Real Linux Kernel Patterns: Learn the Engineering Rule, Not the Extension Syntax

“Linux-style C” is not useful if it remains only an adjective. This edition pins four concrete Linux kernel patterns as reference points, but extracts their engineering rules instead of treating kernel-specific compiler extensions as portable C contracts.

### 13.1 syscall `__MAP`: finite pair replay

Linux syscall declarations organize parameters as:

~~~text
type, name, type, name, ...
~~~

A finite `__MAP(n,...)` family then projects the same pairs into declaration, argument, and metadata shapes. The CMeta counterpart is:

~~~c
CMETA_PP_PAIR_MAP_N(N, M, C, ...)
CMETA_PP_PAIR_MAP_COMMA_N(N, M, C, ...)
~~~

The shared rule is:

~~~text
one finite row source
        ↓
several mechanical projections
        ↓
no duplicated arity family per DSL
~~~

The contracts are still different:

~~~text
Linux syscall map:
    kernel/toolchain-local contract

CMeta pair map:
    shared library kernel
    + explicit finite bound
    + separator/context variants
~~~

### 13.2 min/max: capture once, then type-check

Linux `min/max` does not repeatedly substitute side-effecting operands into the final comparison. Its essential shape is:

~~~text
x expression ─┐
              ├─> unique typed temporary
y expression ─┘
                    ↓
              compile-time compatibility check
                    ↓
                compare locals
~~~

CMeta does not need to copy the kernel statement-expression implementation. It separates the required capabilities:

~~~c
CMETA_AUTO(tmp, expr)
CMETA_SAME_TYPE(a, b)
CMETA_CONST_REQUIRE(condition)
CMETA_PP_UNIQUE(prefix)
~~~

The transferable rule is:

a macro may compose expression shape, but user expressions should be evaluated once by default and type constraints should fail at compile time when possible.

### 13.3 container_of: prove the member relation before pointer recovery

Current Linux `container_of` is more than `offsetof` arithmetic. It checks the member-pointer type, and the const-preserving surface additionally uses `_Generic` to preserve constness. CMeta exposes:

~~~c
cmeta_container_of(ptr, Owner, member)
cmeta_container_of_as(ptr, Owner, MemberType, member)
~~~

The relation is:

~~~text
member address
    +
native member-type proof
    +
owner layout relation
        ↓
enclosing object pointer
~~~

If a compiler cannot provide a sufficiently strong native `typeof`, CMeta uses the explicit-`MemberType` entry instead of pretending that both backends provide identical guarantees. That yields a broader rule:

a weaker backend must expose a weaker documented contract, not silently claim equivalence with a stronger backend.

### 13.4 DEFINE_FREE / guard: cleanup attributes perform lexical lowering only

Linux cleanup helpers include `DEFINE_FREE`, `guard`, and `scoped_guard`. They use compiler cleanup support to let lexical scope assist with LIFO unwind. The easy mistake is to conclude:

~~~text
compiler cleanup attribute
        =
universal ownership model
~~~

The correct layering is:

~~~text
resource semantic authority
        ↓
small cleanup adapter
        ↓
compiler lexical cleanup
        ↓
reverse-order discharge
~~~

CMeta keeps these concerns separate:

~~~text
CMETA_ATTR_CLEANUP
    = compiler capability

cmeta_scope
    = structured lexical lowering

DataDesc / ObjectRef / Plugin lease
    = resource-specific semantic authority
~~~

**A lease** here is an explicitly acquired and released lifetime claim that keeps borrowed shared-library code and data available during use. It is not a network lease that expires after a timeout; later chapters explain why cleanup callbacks can still need it after a call returns.

A Plugin lease, a managed Data value, and a shard-owned asynchronous operation therefore should not collapse into one universal `destroy(void *)` contract merely because all of them eventually require cleanup.

### 13.5 Mapping table

| Linux kernel pattern | CMeta counterpart | Shared engineering rule |
|---|---|---|
| syscall finite `__MAP` | `CMETA_PP_PAIR_MAP_N` | finite row replay |
| careful `min/max` | `CMETA_AUTO` + `CMETA_SAME_TYPE` + `CMETA_PP_UNIQUE` | single evaluation + compile-time check |
| `container_of(_const)` | `cmeta_container_of(_as)` | type/layout proof before pointer recovery |
| `DEFINE_FREE/guard/scoped_guard` | cleanup capability + `cmeta_scope` | lexical lowering is not resource semantics |

Together these examples establish:

~~~text
Linux kernel
    teaches the shape of the engineering problem

CMeta
    extracts a bounded/capability-gated contract

ordinary C
    remains the generated/executed form
~~~

## 14. Engineering Evidence

### Preprocess

~~~bash
cc -E sample.c
~~~

Check that macro expansion still produces ordinary C that humans are willing to read and debug.

### Compile-Pass / Compile-Fail

Qualification should include cases such as:

~~~text
supported arity        -> compile
unsupported relation   -> fail
wrong member type      -> fail
invalid flags/layout   -> fail
~~~

### Cross-Compiler

Distinguish the real capabilities of GCC, Clang, and MSVC. The goal is not “make every compiler pretend to be identical.” It is:

~~~text
same semantic contract
    +
explicit capability differences
~~~

### Runtime

For the static path, the ideal evidence remains:

no new runtime cost center. If the final machine path is equivalent to handwritten direct C, most abstraction cost belongs in the build/control plane.

## 15. Summary

Functions provide type checking and parameter passing; macros generate identifiers, declarations, and initializers; compiler facilities add native type and scope information; reflection descriptors record facts shared by consumers. Select a mechanism by identifying whether the problem concerns runtime behavior or compile-time structure, then check its required capabilities and rejection conditions. Single evaluation constrains evaluation count, not the order of function arguments. Scope cleanup determines when a cleanup action runs; borrowing, sharing, and Plugin leases retain their resource-specific obligations. The next chapter collects repeated list traversal and declaration projection into a finite shared kernel.
