# Chapter 1: CMeta Foundations: Macros, Inline Functions, and Compile-Time Constraints

CMeta uses macros to generate declarations, ordinary functions to manipulate typed values, and static descriptors to share facts among consumers. This chapter develops that division through argument evaluation, finite expansion, and resource cleanup. Reflection means inspectable descriptions of types or functions. RAII abbreviates Resource Acquisition Is Initialization; in C, ownership and cleanup paths must still be explicit, with compiler attributes handling only part of the mechanism.

| `cmeta_*` / `CMETA_*` | Actual types, functions, macros, and constants |

## 1. Express Typed Behavior with a Function

This C fragment compares two live `int` objects. The pointers must remain valid during the call. Its results are minus one, zero, and one; it avoids the potentially overflowing subtraction `*a - *b`.

~~~c
static int int_compare(const int *a, const int *b)
{
    return (*a > *b) - (*a < *b);
}
~~~

Direct calls suffice when only this type is needed. Extract a shared declaration when several modules require the same type set, fields, or parameters. Repeated facts justify descriptors; a function does not need replacement merely because it is concrete.

## 2. Single Evaluation Does Not Specify Evaluation Order

The selected argument expression appears again in the macro's selected branch. Here `next_a` and `next_b` stand for functions returning `int`; the following fragments are alternative comparisons.

~~~c
#define MAX(a, b) ((a) > (b) ? (a) : (b))
~~~

~~~c
int x = MAX(next_a(), next_b());
~~~

A typed function evaluates each argument once and then accesses parameter objects:

~~~c
static inline int
int_max(int a, int b)
{
    return a > b ? a : b;
}
~~~

~~~c
int x = int_max(next_a(), next_b());
~~~

This pseudocode counts evaluations without ordering the two arguments.

~~~text
macro_max(a, b):
    compare evaluate(a) with evaluate(b)
    evaluate the selected expression again

function_max(a, b):
    evaluate each argument once and initialize parameter objects
    compare the parameter values
    return the selected parameter value
~~~

**Derivation.** Assuming defined evaluation and normal completion, the macro evaluates both arguments for comparison and the selected expression again, for three evaluations. The function evaluates each argument once, for two. Neither rule depends on actual inlining, which `inline` does not guarantee. C11 still does not specify function argument order; unsequenced conflicting accesses to one scalar remain undefined even after replacing the macro with a function.

Repeated names and repeated evaluation are different questions. Inspect expression positions and control flow after preprocessing, rather than just the parentheses at the call site.

## 3. Generate Declarations from a Finite List

A function cannot generate identifiers, fields, or prototypes. The preprocessor can transform **tokens**, the lexical units it manipulates. **Finite expansion** generates declarations within a specified element bound, without a runtime loop.

This complete declaration fragment does not depend on CMeta:

~~~c
#define BOOK_FIELDS(X) \
    X(int, id)         \
    X(double, score)
#define BOOK_DECLARE(T, name) T name;
typedef struct BookUser { BOOK_FIELDS(BOOK_DECLARE) } BookUser;
#undef BOOK_DECLARE
~~~

It expands to `typedef struct BookUser { int id; double score; } BookUser;`. A metadata generator consuming the same rows obtains the same field order. Induct on the row count: an empty list emits no fields, and appending one row appends that row's field. Consumers that process rows in the same order therefore agree on field order. Compiler checks must still establish offsets and types; the ordering argument does not establish layout.

CMeta's `CMETA_PP_PAIR_MAP_N` maps type/name pairs to a consumer, with comma and semicolon variants controlling separators. **Arity** is the number of items, and a **projection** selects information from a row. Chapter 2 develops both mechanisms.

## 4. Separate Preprocessing from Compiler Capabilities

`pp.h` handles token composition, tuple extraction, and finite mapping. `compiler.h` abstracts native type deduction, compatibility checking, cleanup attributes, and related compiler facilities. A **capability check** states whether a toolchain can supply a guarantee instead of guessing from a vendor name.

~~~c
CMETA_NATIVE_TYPEOF(expr)
CMETA_SAME_TYPE(a, b)
CMETA_AUTO(name, expr)
CMETA_CONST_REQUIRE(condition)
~~~

These are entry-point shapes with placeholder arguments. `CMETA_NATIVE_TYPEOF` denotes a native compiler type; `CMETA_AUTO` saves one evaluation in a deduced local; `CMETA_CONST_REQUIRE` expresses a compile-time requirement. They do not create a dynamic any-type container. Missing facilities require a documented explicit-type operation or rejection, rather than silently weakening type or cleanup guarantees under the same interface.

## 5. Preconditions for Recovering an Enclosing Object

`container_of` recovers an enclosing object from a member address. This fragment omits the definition of `Link` and the origin of `p`. The pointer must actually address the `link` member of a live `Node`.

~~~c
struct Node {
    int value;
    struct Link link;
};

struct Link *p = ...;
struct Node *node =
    cmeta_container_of(p, struct Node, link);
~~~

If the enclosing base is `b` and member offset is `k`, the real member address is `b + k`, so subtracting `k` recovers `b`. The argument assumes the member relationship, lifetime, alignment, and supported compiler pointer semantics. An arbitrary pointer with the right pointed-to type does not establish those conditions.

CMeta checks member-pointer types with native compiler facilities and provides `cmeta_container_of_as` with an explicit `MemberType`. Matching types still do not prove object provenance. Use this idiom under the supported toolchain and library contract; a character-pointer subtraction is not a universal proof for arbitrary strict C11 implementations.

## 6. Compile-Time Selection and Static Description

The following fragment assumes the three printing functions are declared. `_Generic` selects a function from the controlling expression's type without evaluating that expression; the final `(x)` supplies the actual call argument.

~~~c
#define print_value(x) _Generic((x), \
    int: print_int,                  \
    long: print_long,                \
    double: print_double             \
)(x)
~~~

This removes a finite handwritten type dispatch, but discovers neither fields nor result-cleanup obligations. Descriptors record those facts; direct calls or function pointers execute behavior. **Ownership** assigns resource release or transfer responsibility. A **borrow** permits access for a specified lifetime without transferring that responsibility.

Known functions can remain direct calls. Foreign descriptions or dynamic modules undergo **admission**: checking types, layout, ABI, and execution capability, then retaining a lifetime-bounded result for reuse. The application binary interface, or ABI, governs calls and layout between compiled modules. Successful checking establishes compatible contracts at that boundary, not perpetual validity of borrowed objects.

## 7. Scope Cleanup and Resource Responsibility

A scope-cleanup attribute can invoke a cleanup function on lexical exit. It does not determine whether a pointer is borrowed, owned, or already moved. This pseudocode acquires two resources whose release operations must match their acquisition protocols.

~~~text
acquire A
if A failed: return failure
acquire B
if B failed: release A; return failure
use A and B
release B
release A
~~~

**Cleanup invariant.** At each program point, track resources successfully acquired and not yet released. Successful acquisition adds one; completed release removes one. The normal path releases B then A, while failed acquisition of B releases only A. Each successful acquisition is thus released once. Transfer removes a resource from the current cleanup set and assigns responsibility to its new owner. This argument excludes process termination, undefined behavior, and nonlocal control transfers outside the protocol.

A Plugin **lease** explicitly holds code and data alive; it is not a timed network lease. Destruction callbacks may still require module code after an invocation returns, so the lease extends through the final associated cleanup. Objects spanning asynchronous suspension cannot rely solely on cleanup of the original stack frame.

## 8. Extract Checkable Rules from Linux Idioms

The fixed Linux reference supplies finite mapping, single-evaluation, member-recovery, and scope-cleanup examples. See `SOURCE_SNAPSHOTS.md` for provenance; kernel extensions are not a portability promise for the entire library.

| Kernel reference | Extracted rule | CMeta boundary |
|---|---|---|
| `include/linux/syscalls.h` | Generate multiple declarations from parameter rows | Finite pair mapping and separators |
| `include/linux/minmax.h` | Capture operands before comparison and check types | Native type facilities and single evaluation |
| `include/linux/container_of.h` | Types and the real containing-object relation both matter | Member checks and caller object preconditions |
| `include/linux/cleanup.h` | Automatic cleanup still depends on resource protocols | Compiler attributes, scope, and resource owners |

Inspect generated code with `cc -E`, then prepare both accepted and rejected compile cases. Runtime checks cover side-effect counts and normal/failure cleanup; cross-compiler checks validate capability claims. Assembly and benchmarks can assess actual call overhead, but compilation alone establishes no zero-cost claim.

## 9. Summary

Functions manipulate values, finite macros generate declarations, compiler facilities supply native type and scope support, and descriptors share stable facts. Each mechanism has a specific proof obligation: evaluation counts, row projection, member relationships, or resource accounting. Stating these preconditions makes a combined interface traceable to the ordinary C operations it performs.
