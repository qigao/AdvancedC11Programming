# Chapter 1: From Linux-Style C to CMeta — Macros, static inline, and Zero-Runtime Abstraction

> **This chapter answers one question only:**
>
> Without turning C into another language or adding a new runtime, how can repeated structure, type constraints, and stable semantics be moved earlier into the build?

---

## 1. First Rule: If Ordinary C Is Enough, Stop There

Start with an ordinary function:

~~~c
static int int_compare(const int *a, const int *b)
{
    return (*a > *b) - (*a < *b);
}
~~~

If the system needs only this implementation, does not generate declarations, does not share a schema, and has no duplicated stable fact across consumers, stop here.

Modern C is not:

~~~text
plain C
   ↓
replace everything with macros
~~~

It is:

~~~text
plain C
   ↓ only when repeated knowledge appears
small compile-time abstraction
   ↓
ordinary C again
~~~

So the book keeps one constraint from the beginning:

> **do not abstract merely to look modern; promote only knowledge that is both repeated and stable.**

---

## 2. static inline: Solve Typed Behavior Before Reaching for a Macro

One classic macro problem is repeated evaluation.

For example:

~~~c
#define MAX(a, b) ((a) > (b) ? (a) : (b))
~~~

A call such as:

~~~c
int x = MAX(next_a(), next_b());
~~~

does not give the caller the evaluation behavior suggested by a normal function call.

If the problem is simply typed behavior, prefer a function:

~~~c
static inline int
int_max(int a, int b)
{
    return a > b ? a : b;
}
~~~

The call remains ordinary C:

~~~c
int x = int_max(next_a(), next_b());
~~~

This gives us:

- normal C argument evaluation;
- normal type checking;
- a debugger-visible function boundary;
- a direct call the compiler may inline;
- no new runtime object.

This is an important Linux-style separation:

~~~text
behavior over C values
        ↓
static inline / normal function

token or declaration generation
        ↓
macro
~~~

A macro is not a more advanced inline function.

They solve different problems.

## 3. Macros Are Best at Things C Functions Cannot Express

A normal function cannot generate:

- a type name;
- a field declaration;
- a function prototype;
- an identifier;
- an initializer row;
- a metadata declaration.

Those live in the token/declaration plane.

Suppose the same builtin type set is consumed by compare, hash, and serialization code:

~~~c
#define BUILTIN_TYPES(X) \
    X(int)               \
    X(long)              \
    X(float)
~~~

Different consumers replay the same facts:

~~~c
#define GEN_COMPARE(T) DEFINE_COMPARE(T)
BUILTIN_TYPES(GEN_COMPARE)

#define GEN_HASH(T) DEFINE_HASH(T)
BUILTIN_TYPES(GEN_HASH)
~~~

The reusable object is not mainly the generated code. It is the fact:

~~~text
supported type set
    =
{ int, long, float }
~~~

So:

> **the most valuable use of a macro is not to hide runtime logic, but to generate structure that C cannot express as a function argument.**

---

## 4. Linux-Style Finite Mapping: Make Arity Data, Not Part of Every Macro Name

An interface may represent parameters as flat pairs:

~~~text
int, fd,
size_t *, written
~~~

The direct but poor scaling path is:

~~~text
PARAMS_0
PARAMS_1
PARAMS_2
PARAMS_3
...
~~~

followed by another arity family in every higher-level DSL:

~~~text
DECLARE_0..N
CALL_0..N
META_0..N
VALIDATE_0..N
~~~

Salts now centralizes this mechanics in a finite PP kernel.

Examples include:

~~~c
CMETA_PP_PAIR_MAP_N(N, M, C, ...)
CMETA_PP_MAP_COMMA_N(N, M, C, ...)
CMETA_PP_MAP_PREFIX_COMMA_N(N, M, C, ...)
~~~

Conceptually:

~~~text
(type,name,type,name,...)
          ↓
   finite pair map
      /        \
 declaration   arguments
      |           |
 metadata      wrapper
~~~

The important part is not macro cleverness. It is the design constraint:

~~~text
finite
explicit
bounded
~~~

The production core does not need an unbounded recursive macro machine built from:

~~~text
DEFER -> OBSTRUCT -> EVAL -> recursive expansion
~~~

A more clever preprocessor is not automatically a better engineering boundary.

---

## 5. pp.h and compiler.h Are Different Layers

Preprocessor mechanics and compiler capabilities are not the same thing.

The boundary can be drawn as:

~~~text
cmeta/pp.h
    token
    tuple
    finite map
    boolean
    unique-name composition
          |
          v
cmeta/compiler.h
    typeof capability
    auto-type capability
    type compatibility
    cleanup attribute
    section/used attribute
    compile-time expression requirement
          |
          v
higher-level CMeta declarations
~~~

Higher-level code should not repeatedly grow:

~~~c
#ifdef __GNUC__
...
#elif defined(__clang__)
...
#elif defined(_MSC_VER)
...
#endif
~~~

It should ask for a documented capability instead.

Representative Salts entry points now include:

~~~c
CMETA_NATIVE_TYPEOF(expr)
CMETA_SAME_TYPE(a, b)
CMETA_AUTO(name, expr)
CMETA_CONST_REQUIRE(condition)
~~~

The rule is:

> **when a capability is unavailable, do not silently pretend that a weaker mechanism provides the same guarantee.**

Either the capability exists, an explicitly weaker contract is selected, or compilation fails.

---

## 6. Single Evaluation: Macros and Compiler Facilities Must Protect the Caller Together

Some generic helpers really do require a macro because they need the native type of an expression.

Even then, the intended shape should be:

~~~text
user expression
      ↓
evaluate once
      ↓
typed local
      ↓
operate on local
~~~

When the capability exists:

~~~c
CMETA_AUTO(tmp, expression);
~~~

The goal is not to create a dynamic `Any`. It is to create an ordinary native local:

~~~text
expression
    ↓ once
native typed local
    ↓
ordinary C operation
~~~

This rule will recur throughout the book:

> **if a macro accepts an expression that may have side effects, single evaluation is the default requirement; if that cannot be guaranteed, the limitation belongs in the contract.**

---

## 7. container_of: How Macros, typeof, and Layout Checks Cooperate

`container_of` is a good Modern C example.

The goal is to recover an enclosing object from the address of its actual member:

~~~c
struct Node {
    int value;
    struct Link link;
};

struct Link *p = ...;
struct Node *node =
    cmeta_container_of(p, struct Node, link);
~~~

The useful contract is more than:

~~~c
(char *)p - offsetof(struct Node, link)
~~~

Where the compiler permits it, we also want a compile-time relationship equivalent to:

~~~text
type(p)
    ==
type(&((struct Node *)0)->link)
~~~

Salts therefore separates:

~~~text
compiler capability
    CMETA_NATIVE_TYPEOF
    CMETA_SAME_TYPE
            |
            v
container/member recovery
    cmeta_container_of(...)
~~~

If a compiler cannot provide inferred native typeof, the explicit-member-type entry point is used instead of pretending the guarantees are identical.

This gives a recurring pattern:

~~~text
macro
  + compiler type fact
  + compile-time requirement
        ↓
ordinary pointer arithmetic
~~~

There is no runtime reflection lookup.

## 8. _Generic Is Compile-Time Dispatch, Not Semantic Authority

C11 `_Generic` can make a finite selection:

~~~c
#define print_value(x) _Generic((x), \
    int: print_int,                  \
    long: print_long,                \
    double: print_double             \
)(x)
~~~

It answers:

> given the static C type of this expression, which existing expression should be selected?

It does not automatically answer:

- what the semantic identity of the type is;
- which lifecycle provider owns it;
- which fields a struct exposes;
- the IN/OUT/ownership contract of a function;
- whether descriptors from different translation units mean the same thing.

Therefore:

~~~text
_Generic
    =
compile-time selection

Reflection descriptor
    =
semantic authority
~~~

They can cooperate, but they do not replace one another.

## 9. Macro + static inline + Reflection Are Not Three Runtimes

Consider a common declaration-generation shape:

~~~text
schema / declaration row
        ↓ macro replay
ordinary C declaration
        +
static metadata
        +
static inline typed accessor
~~~

A caller may simply write:

~~~c
const cmeta_function_desc *desc =
    get_user_cmeta_function();
~~~

while execution remains:

~~~c
int rc = get_user(repo, id, &user);
~~~

The existence of Function Reflection should not automatically turn execution into:

~~~text
box arguments
   ↓
dynamic lookup
   ↓
erased dispatcher
   ↓
unbox result
~~~

This rule is fundamental:

> **Reflection does not imply dynamic dispatch.**

Reflection preserves stable meaning.

The consumer decides how, or whether, that meaning becomes executable.

---

## 10. Keep the Static Path and the Dynamic Boundary Separate

For a canonical declaration known at compile time:

~~~text
known type/function
      ↓
direct generated binding
      ↓
static inline / direct call
~~~

we should not walk a descriptor graph on every call.

A Plugin, DSO, or foreign descriptor is a different problem:

~~~text
foreign/raw descriptor
        ↓
validate ABI / layout / semantics
        ↓
admit once
        ↓
small admitted capability
        ↓
reuse many times
~~~

The model is not:

~~~text
Reflection everywhere at runtime
~~~

It is:

~~~text
static world
    -> prove/generate early

dynamic boundary
    -> validate once

hot path
    -> use admitted/direct representation
~~~

This is one concrete meaning of “know more before execution; do less at runtime.”

---

## 11. Optional Syntax Lowering Is Not a Requirement for CMeta

Later we will encounter receiver-like syntax, conceptually:

~~~c
list.add(10);
~~~

A frontend may lower it to:

~~~c
IntList_add(&list, 10);
~~~

But canonical CMeta must not require every ordinary C consumer to pass through a source translator.

The correct relationship is:

~~~text
optional syntax frontend
        ↓
canonical semantic resolution
        ↓
ordinary C API
~~~

not:

~~~text
CMeta
  =
mandatory new C source language
~~~

Receiver metadata, Reflection, Generic, and the rest of the semantic layer must remain directly consumable from ordinary C.

## 12. A Practical Decision Tree

Chapter 1 can now be reduced to one practical test:

~~~text
Can a normal C function express it?
        |
       yes
        v
normal function / static inline

Need to create tokens, declarations, identifiers,
or replay a finite schema?
        |
       yes
        v
finite macro / PP kernel

Need native compiler knowledge such as typeof,
same-type, cleanup or section placement?
        |
       yes
        v
capability-gated compiler abstraction

Need stable meaning shared by several consumers?
        |
       yes
        v
canonical Reflection / semantic descriptor

Crossing a foreign or dynamic boundary?
        |
       yes
        v
validate once -> admitted capability
~~~

Do not collapse these layers into one universal mechanism.

## 13. Four Real Linux Kernel Patterns: Learn the Engineering Rule, Not the Extension Syntax

“Linux-style C” is not useful if it remains only an adjective.

This edition pins four concrete Linux kernel patterns as reference points, but extracts their engineering rules instead of treating kernel-specific compiler extensions as portable C contracts.

### 13.1 syscall `__MAP`: finite pair replay

Linux syscall declarations organize parameters as:

~~~text
type, name, type, name, ...
~~~

A finite `__MAP(n,...)` family then projects the same pairs into declaration, argument, and metadata shapes.

The CMeta counterpart is:

~~~c
CMETA_PP_PAIR_MAP_N(N, M, C, ...)
CMETA_PP_PAIR_MAP_COMMA_N(N, M, C, ...)
~~~

The shared rule is:

~~~text
one finite row source
        ↓
several mechanical projections
        ↓
no duplicated arity family per DSL
~~~

The contracts are still different:

~~~text
Linux syscall map:
    kernel/toolchain-local contract

CMeta pair map:
    shared library kernel
    + explicit finite bound
    + separator/context variants
~~~

### 13.2 min/max: capture once, then type-check

Linux `min/max` does not repeatedly substitute side-effecting operands into the final comparison.

Its essential shape is:

~~~text
x expression ─┐
              ├─> unique typed temporary
y expression ─┘
                    ↓
              compile-time compatibility check
                    ↓
                compare locals
~~~

CMeta does not need to copy the kernel statement-expression implementation. It separates the required capabilities:

~~~c
CMETA_AUTO(tmp, expr)
CMETA_SAME_TYPE(a, b)
CMETA_CONST_REQUIRE(condition)
CMETA_PP_UNIQUE(prefix)
~~~

The transferable rule is:

> **a macro may compose expression shape, but user expressions should be evaluated once by default and type constraints should fail at compile time when possible.**

### 13.3 container_of: prove the member relation before pointer recovery

Current Linux `container_of` is more than `offsetof` arithmetic.

It checks the member-pointer type, and the const-preserving surface additionally uses `_Generic` to preserve constness.

CMeta exposes:

~~~c
cmeta_container_of(ptr, Owner, member)
cmeta_container_of_as(ptr, Owner, MemberType, member)
~~~

The relation is:

~~~text
member address
    +
native member-type proof
    +
owner layout relation
        ↓
enclosing object pointer
~~~

If a compiler cannot provide a sufficiently strong native `typeof`, CMeta uses the explicit-`MemberType` entry instead of pretending that both backends provide identical guarantees.

That yields a broader rule:

> **a weaker backend must expose a weaker documented contract, not silently claim equivalence with a stronger backend.**

### 13.4 DEFINE_FREE / guard: cleanup attributes perform lexical lowering only

Linux cleanup helpers include `DEFINE_FREE`, `guard`, and `scoped_guard`.

They use compiler cleanup support to let lexical scope assist with LIFO unwind.

The easy mistake is to conclude:

~~~text
compiler cleanup attribute
        =
universal ownership model
~~~

The correct layering is:

~~~text
resource semantic authority
        ↓
small cleanup adapter
        ↓
compiler lexical cleanup
        ↓
reverse-order discharge
~~~

CMeta keeps these concerns separate:

~~~text
CMETA_ATTR_CLEANUP
    = compiler capability

cmeta_scope
    = structured lexical lowering

DataDesc / ObjectRef / Plugin lease
    = resource-specific semantic authority
~~~

A Plugin lease, a managed Data value, and a shard-owned asynchronous operation therefore should not collapse into one universal `destroy(void *)` contract merely because all of them eventually require cleanup.

### 13.5 Mapping table

| Linux kernel pattern | CMeta counterpart | Shared engineering rule |
|---|---|---|
| syscall finite `__MAP` | `CMETA_PP_PAIR_MAP_N` | finite row replay |
| careful `min/max` | `CMETA_AUTO` + `CMETA_SAME_TYPE` + `CMETA_PP_UNIQUE` | single evaluation + compile-time check |
| `container_of(_const)` | `cmeta_container_of(_as)` | type/layout proof before pointer recovery |
| `DEFINE_FREE/guard/scoped_guard` | cleanup capability + `cmeta_scope` | lexical lowering is not resource semantics |

Together these examples establish:

~~~text
Linux kernel
    teaches the shape of the engineering problem

CMeta
    extracts a bounded/capability-gated contract

ordinary C
    remains the generated/executed form
~~~

## 14. Engineering Evidence

### Preprocess

~~~bash
cc -E sample.c
~~~

Check that macro expansion still produces ordinary C that humans are willing to read and debug.

### Compile-Pass / Compile-Fail

Qualification should include cases such as:

~~~text
supported arity        -> compile
unsupported relation   -> fail
wrong member type      -> fail
invalid flags/layout   -> fail
~~~

### Cross-Compiler

Distinguish the real capabilities of GCC, Clang, and MSVC.

The goal is not “make every compiler pretend to be identical.” It is:

~~~text
same semantic contract
    +
explicit capability differences
~~~

### Runtime

For the static path, the ideal evidence remains:

> **no new runtime cost center.**

If the final machine path is equivalent to handwritten direct C, most abstraction cost belongs in the build/control plane.

## 15. What We Learned

This chapter did not conclude that macros should disappear.

It established four responsibilities:

| Tool | Responsibility |
|---|---|
| function / `static inline` | typed behavior |
| finite macro / PP | tokens, declarations, schema replay |
| compiler capability | native compile-time facts |
| Reflection | stable semantic truth |

The final path is:

~~~text
facts once
   ↓
macros generate structure
   ↓
static inline preserves typed C semantics
   ↓
Reflection preserves meaning
   ↓
compiler removes abstraction
   ↓
ordinary C executes
~~~
