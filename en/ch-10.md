# Chapter 11: Events and State Machines: Types, Transitions, and Commit

Connection handling selects actions from the current state and an incoming event. Representing transitions as data lets CMeta type descriptions and callables check event payloads, guards, and actions. This chapter derives construction, selection, staging, and commit from those C representations, identifying where concurrent input, action failure, and cancellation affect visible state.

## 1. Typed Event and Immutable Transition

~~~c
typedef struct cflow_event {
    uint32_t type_id;
    const cmeta_type_desc *payload_type;
    const void *payload;
} cflow_event;
~~~

Event identity and payload type are separate. Build/admission validates both instead of asking actions to guess payload layout.

### 1.1 Transition Is an Immutable Definition

~~~c
typedef struct machine_transition {
    uint32_t from_state;
    uint32_t event_type;
    cmeta_callable guard;
    cmeta_callable action;
    uint32_t to_state;
} machine_transition;
~~~

Machine definition becomes immutable after build. Instance owns only mutable execution state:

~~~c
typedef struct machine_instance {
    const machine_def *def;
    uint32_t state;
} machine_instance;
~~~

Therefore:

| Object | Meaning |
|---|---|
| MachineDef | program |
| MachineInstance | mutable execution state |

## 2. Build / Step / Admission

~~~text
build_machine(definition):

    require unique state ids
    require unique event ids

    for transition in definition.transitions:

        require known_state(transition.from)
        require known_state(transition.to)
        require known_event(transition.event)

        require guard signature admitted
        require action signature admitted

        bucket =
            index[transition.from,
                  transition.event]

        if transition is unguarded
           and bucket already has unguarded transition:
            reject AMBIGUOUS

        bucket.append(transition)

    for terminal state:
        require no outgoing admitted transition

    freeze definition
~~~

Build-time failures include unknown state/event, payload mismatch, duplicate unguarded transition, invalid guard/action signature, and terminal states with outgoing transitions.

### 2.1 Step Algorithm: Separate Selection, Action, and Commit

~~~text
step(instance, event):

    require instance.state not terminal
    require event payload type valid

    candidates =
        index[instance.state, event.type]

    enabled = []

    for t in candidates:
        if no guard(t) or guard(t, event):
            enabled.append(t)

    require exactly_one(enabled)

    t = enabled[0]

    staged =
        run_action(t.action,
                   instance.state,
                   event)

    require staged.success

    old = instance.state
    instance.state = t.to_state

    observe_commit(old, event, t.to_state)

    return staged.effects
~~~

A linearization point is the instant within a concurrent operation at which it is treated as having taken effect. Here commit determines whether a transition result or cancellation takes effect first, giving concurrent calls a defined order. Lock placement is an implementation mechanism that must agree with this ordering contract. The linearization point is `instance.state = t.to_state`. Everything before it is selection/staging. Only after it is the transition observable as committed.

## 3. Small-Step Judgment, Admission, and Failure

Core semantics:

~~~text
M ⊢ (s, e) ⇓ (s', effects)
~~~

with premises:

~~~text
event_typed(e)
∧ transition_selected_uniquely(M, s, e)
∧ guard_enabled
∧ action_success
────────────────────────────────────────
M ⊢ (s, e) ⇓ (s', effects)
~~~

Determinism:

~~~text
M.Valid
∧ M ⊢ (s,e) ⇓ r1
∧ M ⊢ (s,e) ⇓ r2
────────────────
r1 = r2
~~~

Terminal law:

~~~text
terminal(M, s)
──────────────
no step from s
~~~

These are appropriate proof obligations for Lean.

### 3.1 Admission Is Not Execution

With mailbox/Actor composition, this is the **message-admission + serialized-execution path**:

~~~text
send(event)
    ↓ admission check
mailbox
    ↓ dequeue accepted event
serial executor
    ↓ owns mutation context
step(instance,event)
~~~

`send()` returning `OK` means the event was accepted; it does not mean the transition has committed.

### 3.2 Failure Paths

#### Ambiguous transition

~~~text
same state + same event
two enabled transitions
        ↓
AMBIGUOUS
~~~

Never pick one arbitrarily.

#### Action failure

~~~text
action fails before commit
        ↓
state unchanged
~~~

Law:

~~~text
action(t,e) = error
───────────────────
state_after = state_before
~~~

#### Terminal state

~~~text
state is terminal
    ↓
CLOSED / NO_STEP
~~~

Do not silently revive a terminal state. The formal SmallStep model, current C implementation, and evidence later in the chapter now refer to these explicit algorithms.

## 4. From Machine Structure to the Canonical Machine

The design now separates the critical boundaries: Event is a typed value; Machine is immutable/validated definition; Instance owns mutable state; Guard only determines enablement; Action reuses Callable; Serial Executor isolates mutation; Machine and Statechart remain distinct abstractions. The rest of the chapter fixes one canonical connection-machine transition contract: Event is admitted, typed, selected, guarded, staged, and committed. Lean small-step semantics and C implementation both target the same contract, and build tests, typed-event tests, serial-mutation tests, close/cancel race tests, and sanitizers constrain the implementation.

### 4.1 Canonical Machine: Turn the Connection FSM into a Typed Control Program

The chapter already uses five states—Disconnected, Connecting, Connected, Closing, Closed—and five events—Connect, ConnectedEvent, Disconnect, Timeout, ClosedEvent. The Plain C baseline remains excellent:

~~~c
switch (state) {
case DISCONNECTED:
    if (event.id == CONNECT) {
        state = CONNECTING;
    }
    break;

case CONNECTING:
    if (event.id == CONNECTED_EVENT) {
        state = CONNECTED;
    } else if (event.id == TIMEOUT) {
        state = DISCONNECTED;
    }
    break;

case CONNECTED:
    if (event.id == DISCONNECT) {
        state = CLOSING;
    }
    break;

case CLOSING:
    if (event.id == CLOSED_EVENT) {
        state = CLOSED;
    }
    break;

case CLOSED:
    break;
}
~~~

Machine IR becomes worthwhile only when we need typed event-payload validation, transition-ambiguity detection, guard/action contracts, state-value type changes, terminal-state validation, reachability analysis, bounded mailbox admission, serialized mutation, formal small-step semantics, or reusable observation/runtime adapters. So the chapter continues the book's first rule:

Plain C first. Machine IR does not replace a simple switch; it preserves program knowledge once that switch begins scattering it.

## 5. Semantic Contract: How Exactly Does One Event Change State?

Once Machine becomes IR, the important issue is the **Machine small-step phase pipeline**:

~~~text
Event Admission
      ↓ validate identity/type
Transition Selection
      ↓ evaluate enablement
Guard Evaluation
      ↓ choose admitted transition
Action Evaluation
      ↓ stage result
State Commit
      ↓ publish committed effect
Observation Publication
~~~

The arrows denote phase progression inside one SmallStep; each stage has a different ownership and failure boundary.

### 5.1 Event Admission Is Not Event Execution

When a Producer calls send, the first steps are to validate event id/payload type, copy the event into a bounded mailbox, and return an admission result—not to run guard/action directly on the producer thread and mutate state inline. This is not a time sequence; it is a **concurrency-funnel topology**:

| External concurrency | Admission boundary | Mutable owner |
|---|---|---|
| many producers | one bounded mailbox | one serialized Machine owner |

This accepts concurrent sends while keeping the caller stack separate from the transition-execution stack.

### 5.2 Event Identity and Payload Type Must Both Match

A valid Event requires an existing event id and a submitted payload type matching the declared payload type. Even if both carry Buffer, `DataReceived(Buffer)` and `ConfigLoaded(Buffer)` remain different Events. Payload type alone does not replace event identity.

### 5.3 Transition Selection Must Be Deterministic

For `state = Connecting, event = Timeout`, there must not be two equal-priority enabled transitions with runtime choosing one by array order. Machine build should move ambiguity to the control plane. If multiple candidates are allowed, selection policy must be explicit—for example, **lowest explicit priority wins**—and priority keys must be unique enough to avoid unresolved ties.

### 5.4 Guard Determines Enablement; It Does Not Own Commit

Guard may read current state value and event payload and return enabled/disabled, but should not secretly mutate Machine-owned state. Otherwise transition selection itself has side effects and determinism, retry, and verification become much harder. Guard contract therefore tends toward `PURE`, `DETERMINISTIC`, `TOTAL`, and `NO_ALIAS`. These remain admission metadata; stronger mathematical claims still require trusted implementation/proof.

### 5.5 Action Builds a Staged Target Before Commit

Action should not overwrite current state while executing. A safer transactional boundary is:

~~~text
current state
+
event
    ↓
action
    ↓
staged target state
+
optional observation
    ↓
validate result
    ↓
atomic commit
~~~

Then Action failure can preserve **current Machine state unchanged**, at least for Machine-owned state. Whether external I/O effects can be rolled back is another contract and must not be pretended away by Machine.

### 5.6 Commit Is the Linearization Point of the Transition

When close/cancel races with an executing transition, we need one precise question:

> Which operation wins first?

If commit wins first:

~~~text
new state/observation
    → visible exactly once
~~~

If cancel wins before commit:

~~~text
staged state/observation
    → discarded
~~~

This linearization boundary defines observable semantics more importantly than “the whole function is protected by a mutex.”

### 5.7 Terminal State Blocks Further SmallStep

Closed/Done/Error terminal states are not merely names. Once Machine terminal is established, no later Event may start a state-changing SmallStep. Producer may receive `CLOSED`, `CANCELLED`, or another terminal status, but may not reactivate the same Instance; a new active run requires a new Instance.

## 6. Lean: Machine Has Real SmallStep Semantics

The edition Salts snapshot contains:

~~~text
CMetaCFlowCalculus/CFlow/Machine.lean
CMetaCFlowCalculus/Proofs/Machine.lean
~~~

which model Machine as a formal transition system. Core formal objects include StateDecl, GuardDecl, ActionDecl, Transition, Machine, TypedEvent, Config, ActionResult, MachineObservation, and SmallStep. The mapping to this chapter's C design is direct.

### 6.1 `Machine.Valid`: Build-Time Validation Becomes a Proof Premise

Formal `Machine.Valid` requires:

- states nonempty;
- state / guard / action IDs unique and nonzero;
- event schema valid;
- initial state known;
- transition source/target/event known;
- guard types aligned;
- action source/event/target types aligned;
- active-source requirement;
- priority keys unique;
- all states reachable;
- all declared guards/actions used.

These are exactly the facts a professional Machine builder should establish before publishing immutable IR. Runtime theorems then do not repeatedly ask “does this target state even exist?” because `Machine.Valid` paid that cost before execution. This is another:

These checks are performed during construction, so execution can use the validated transition definition.

### 6.2 `smallStep_deterministic`

The theorem `smallStep_deterministic` states that for the same Machine, Guard valuation, Action evaluation, Before Config, and Typed Event, if we obtain two results first and second, then:

~~~text
first = second
~~~

This is the core State Machine determinism property. It does not say arbitrary C callbacks are deterministic. It says:

> given the formal guard/action evaluations, the Machine transition relation itself is deterministic.

That forces the C design to make selection rule, priority, ambiguity, and guard/action contract explicit.

### 6.3 `smallStep_requires_event_typing`

The theorem `smallStep_requires_event_typing` states that any successful SmallStep implies a known event id and a payload type matching the declared event schema. Typed mailbox is therefore not merely API ergonomics. It is a precondition of transition semantics.

### 6.4 `step_consumes_once`

The theorem `step_consumes_once` proves every successful SmallStep satisfies:

~~~text
after.consumedEvents
=
before.consumedEvents + 1
~~~

This gives a valuable execution invariant:

~~~text
one admitted/selected event
    → at most one committed Machine step
~~~

When Machine later sits behind an Actor mailbox, this becomes part of message accounting.

### 6.5 `step_preserves_state_typing`

Under:

~~~text
Machine.Valid
before.WellTyped
EventTyped
SmallStep
~~~

the theorem `step_preserves_state_typing` proves:

~~~text
after.WellTyped
~~~

A legal transition cannot leave state bytes with a type that disagrees with the target-state declaration. This is a real advantage over a plain “enum state + void*”.

### 6.6 `terminal_no_step` / `terminal_state_no_step`

These prove:

~~~text
terminal Config
or
terminal state kind
    ↓
no next Machine step
~~~

Terminal behavior is a structural constraint of the transition relation, not a documentation convention.

### 6.7 Action Failure Preserves Machine-Owned State

The theorem `applyTransition_action_failure` states that when a MAY_FAIL Action actually returns an error, the after-state preserves:

~~~text
state = before.state
stateValue = before.stateValue
terminal = error(message)
~~~

That precisely captures:

> action may fail, but it must not leave a partial Machine-state commit.

This is the formal justification for staged action + atomic commit.

## 7. Current C Implementation: Machine Definition and Instance Are Strictly Layered

Against the edition Salts snapshot qigao/salts@ad389928b437c0612c1c60844fe53677f3ed27a6:

the implementation clearly separates:

| Object | Responsibility |
|---|---|
| cflow_machine | immutable definition |
| cflow_machine_instance | live mutable execution owner |

This is much clearer than one giant mutable Machine struct.

### 7.1 Immutable Machine Is a Transactional Build Artifact

Machine definition input includes states, events, guards, actions, transitions, and initial state. Build performs copy, normalize, validate, and atomically publish. and leaves the destination empty on failure. This follows the same “publish a new artifact” discipline as Graph normalize/optimize. Build can explicitly reject duplicate id, unknown state/event/guard/action, type mismatch, invalid contract, invalid observation, terminal transition, ambiguous transition, unreachable state, unused declaration, and limit exceeded. Many errors have genuinely moved from runtime transition into build/admission.

### 7.2 Transition Row Is Ordinary Inspectable Data

A transition stores source, event, guard, action, target, and priority. The transition relation no longer hides inside callback control flow. Build, diagnostics, formal model, and testing tools can all talk about the same structure.

### 7.3 State / Guard / Action All Carry Type Information

The typed facts can be summarized as:

| Row | Typed facts |
|---|---|
| State | state id, state value type, state kind |
| Guard | state type, event id/type, effects, properties |
| Action | source type, event id/type, target type, effects, properties, observation kind/type |

Machine therefore reuses the CMeta/Callable vocabulary rather than inventing a weakly typed callback system.

### 7.4 Instance Owns Mutable State

Machine Instance configuration includes immutable Machine, initial state bytes, guard/action bindings, bounded mailbox capacity, Serial Executor, and optional output type. Instance owns current state, mailbox, in-flight transition, first error, cancel/close, observations, and stats. matching the formal Config / runtime layer.

### 7.5 Instance Explicitly Requires a Non-Manual SerialExecutor

Current init contract requires **executor must be a non-manual SerialExecutor**. This is the first direct payoff of the previous Executor chapter. Machine does not need to know which worker thread, thread-pool layout, or OS scheduling; it depends only on **serialized execution capability**. so transition mutation has a single owner.

### 7.6 Mailbox Is a Bounded Typed Admission Boundary

Current Event/Mailbox API uses a finite event-id + payload-descriptor schema. Initialization fixes schema, capacity, and payload stride/storage. Send returns explicit statuses:

~~~text
unknown id
    → INVALID_ARGUMENT

known id + wrong payload type
    → TYPE_MISMATCH

full
    → FULL

closed/cancelled
    → explicit terminal status
~~~

No silent drop. This becomes the foundation of Actor message admission in the next chapter.

## 8. Close / Cancel Versus a Running Transition

The hardest parts of stateful runtime are usually shutdown races. Machine Instance distinguishes:

~~~text
close
cancel
~~~

### 8.1 Close

Close stops new admission, cancels queued Events, and preserves an already executing transition commit. If close overlaps a transition:

> once the running transition has won commit, its result remains visible exactly once before terminal settlement.

This is graceful shutdown behavior.

### 8.2 Cancel

Cancel also stops admission and cancels queued Events, but races against commit:

~~~text
cancel wins before commit
    → staged state/observation discarded

commit wins first
    → result remains observable exactly once
~~~

Commit/cancel linearization is the semantic contract. The lock is only the implementation mechanism.

### 8.3 External Action Effects Do Not Automatically Roll Back

The contract is explicit:

> effects produced by Action outside Machine-owned state are not automatically rolled back.

Machine transaction can protect its own staged state and observation publication. It cannot magically undo a network send, database write, file change, or external hardware effect. If compensation is required, that belongs to a higher-level Workflow/transaction policy, not Machine core.

## 9. Evidence: Machine Needs Build, Step, Race, and Refinement Tests Together

### 9.1 Build-Time Evidence

Every invalid-Machine class should have explicit tests for duplicate IDs, unknown references, type mismatch, ambiguous transitions, transitions from terminal sources, unreachable states, unused guard/action declarations, and invalid observation contracts. and verify:

~~~text
failed build
    → destination remains empty
~~~

### 9.2 Small-Step Conformance

C tests should construct the same state schema, event schema, transition rows, and guard/action outcomes as the Lean fixture, then compare Lean SmallStep expected trace/state with C Instance observed trace/state. This approaches refinement more directly than only checking a few business outputs.

### 9.3 Typed Event Evidence

Mailbox tests need:

~~~text
correct event id/type
    → accepted

known id + wrong descriptor
    → TYPE_MISMATCH

unknown id
    → INVALID_ARGUMENT

capacity exhausted
    → FULL
~~~

and failure must not partially write the mailbox.

### 9.4 Serial Mutation Evidence

With multiple producers sending concurrently, current-state mutation must still satisfy **one transition commit at a time**. Use in-flight instrumentation, transition trace, Serial Executor stats, and stress tests rather than assuming “there is a mutex” is equivalent.

### 9.5 Close / Cancel Race Evidence

Cover at least close before execution, close during action before commit, close after commit, cancel before commit, cancel after commit, and repeated close/cancel; check state visibility, observation count, queued event cancellation, first error, and terminal flags.

### 9.6 Sanitizer Evidence

Guard/action binding and typed-state copying involve borrowed callbacks, user contexts, state buffers, event payload copies, and mailbox storage. They belong in ASan/UBSan/stress gates. Lean proves WellTyped; it does not find C buffer lifetime bugs.

## 10. Summary

A machine definition records states, events, and transition rules; an instance owns mutable state. Construction uses CMeta type and call contracts to validate payloads, guards, and actions. Execution selects, stages, and commits a transition. Queue admission does not mean the transition has executed. Action failure, closing, and cancellation require an explicit commit order to determine visible results, with one state-mutating owner per instance. Actors add concurrent admission, identity, and lifetime management around this model.
