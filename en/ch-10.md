# Chapter 11: Events and State Machines: Types, Transitions, and Commit

A connection changes state when it receives requests, completion notifications, and close events. A state machine centralizes these branches so that event types and transition relationships can be checked before execution. CFlow Machine stores an immutable definition; Machine Instance stores current state, mailbox, and execution progress. Both rely on CMeta type and call contracts.

## 1. Defining Connection States and Events

Consider Disconnected, Connecting, and Connected states. ConnectRequested begins an attempt, ConnectedEvent carries a connection identifier, and CloseRequested ends use. Events have separate identities even when their payloads share a C type.

These ordinary C types belong to the teaching example, not the SDK:

~~~c
typedef struct book_connecting {
    unsigned attempt;
} book_connecting;

typedef struct book_connected_event {
    int socket_id;
} book_connected_event;

typedef struct book_connected {
    int socket_id;
} book_connected;
~~~

The successful-connect action copies an admitted identifier into the target state. Here `socket_id` is only a nonnegative integer identifier; the action does not validate or acquire ownership of an operating-system socket. A real application must separately specify responsibility for closing that resource.

| Source | Event | Action result | Target |
|---|---|---|---|
| Disconnected | ConnectRequested | State for a new attempt | Connecting |
| Connecting | ConnectedEvent | Save the admitted identifier | Connected |
| Connecting or Connected | CloseRequested | Construct terminal state value | Closed |

The table defines application meaning. Thread choice and arrival time are separate runtime concerns.

## 2. Definitions and Instances

The pinned transition row records source, event, guard, action, target, and priority:

~~~c
typedef struct cflow_machine_transition {
    cflow_machine_state_id source;
    cflow_event_id event;
    cflow_machine_guard_id guard;
    cflow_machine_action_id action;
    cflow_machine_state_id target;
    uint32_t priority;
} cflow_machine_transition;
~~~

A **guard** decides whether a candidate transition is enabled. An **action** constructs a target state and may prepare output from the source state and event. Definitions describe their types, effects, and identifiers; instances bind actual callbacks and contexts.

`cflow_machine_build` copies declaration arrays, normalizes, validates, and atomically publishes an immutable Machine. Failure leaves the output empty. CMeta descriptors remain borrowed until destruction. Construction rejects duplicate or unknown identities, type mismatches, illegal terminal transitions, and unresolved ambiguity instead of selecting whichever row happens to appear first.

## 3. Admission Does Not Execute a Transition

`cflow_machine_instance_try_send` copies a typed event into a bounded mailbox. Acceptance establishes responsibility for the event; it does not imply that the target state is already visible. Event identity and payload type must both match. Equal byte sizes cannot distinguish different events.

~~~text
admit_event(instance, event):
    reject closed or cancelled admission
    require declared event identity
    require matching payload type and valid storage
    require supported bounded payload and free mailbox capacity
    copy payload into one mailbox slot
    publish the accepted event
~~~

The actual instance requires a non-manual SerialExecutor and borrows the Machine, executor, callbacks, and contexts until destruction. Multiple producers may send, while the serial execution domain mutates state. Short callback duration does not substitute for serialization.

## 4. Preparing a Target Before Publication

This ordinary C teaching action uses the preceding types and requires `<stdbool.h>` and `<stddef.h>`. Callers provide live, correctly typed objects; `target` is separate staging storage.

~~~c
static bool book_prepare_connected(
    const book_connecting *source,
    const book_connected_event *event,
    book_connected *target)
{
    if (source == NULL || event == NULL || target == NULL)
        return false;
    if (event->socket_id < 0)
        return false;

    book_connected next = { .socket_id = event->socket_id };
    *target = next;
    return true;
}
~~~

Rejection occurs before writing `target`, and source state is read-only throughout. Success constructs a complete `next` before storing it. **Staging** prepares a candidate result before deciding whether to publish it, avoiding partially updated visible state.

The SDK's uniform action callback uses `void *` storage. Generated or bound code must preserve real type, alignment, and lifetime, as Chapter 3's thunk does. A `const void *` parameter cannot prevent mutation through another alias; borrowing and alias contracts remain implementation obligations.

## 5. Selection, Execution, and Commit

This algorithm summarizes the instance protocol. Internal synchronization and callback placement are simplified; it is not a replacement concurrent implementation.

~~~text
step(instance, event):
    require a running, well-typed instance and a typed accepted event
    select one transition by the validated priority/guard rules
    if selection fails: record terminal error and consume this event once
    prepare target state and optional observation in separate storage
    if action fails:
        discard prepared output
        retain the old state value and record terminal error
    else:
        enter commit synchronization
        if cancellation has already won:
            discard prepared state and observation
        else:
            publish target state and its observation once
        leave commit synchronization
    settle the event and its temporary storage
~~~

A **linearization point** is the defined instant at which a concurrent operation takes effect. Publishing under commit synchronization lets observers see a complete old or new state. It does not mean the entire action executes in one machine instruction.

Type preservation follows the steps: the valid definition relates the selected action's source and event types to its inputs; successful execution constructs the declared target type; commit publishes only that checked value. Failure retains the old value and records terminal error. A callback that lies about types or writes outside storage violates these premises; metadata cannot repair the resulting memory error.

## 6. Close and Cancel

The pinned operations treat in-flight work differently:

| Operation | New and queued events | Executing transition |
|---|---|---|
| close | Stops admission and cancels queued events | Preserves its commit before terminal settlement |
| cancel | Stops admission and cancels queued events | Competes with commit; cancellation winning first discards staged output |

Suppose an action has prepared its target but not committed. Close preserves that in-flight work, so a normally successful transition publishes once. If cancel wins commit synchronization, both staged state and observation are discarded. If commit wins, its result remains observable once and cancellation prevents later events. Action failure still follows the error path.

These rules cover Machine-owned state and prepared observations. Network requests, logs, and mutations of external objects are not automatically undone. Applications needing compensation, idempotent requests, or transactional resources must provide that protocol separately.

## 7. Small-Step Semantics and Proof Scope

**Small-step semantics** defines one event's state advancement. The pinned `smallStep_deterministic` says that identical Machine, guard valuation, action interpretation, prior configuration, and event yield the same resulting configuration for two valid steps. It does not prove that a real callback reading a clock returns the same value across runs.

`step_consumes_once` establishes that a valid small step increments consumption by one. An error step can also consume an event, so this is not a promise that every event causes one successful transition. `step_preserves_state_typing` preserves model typing, while `terminal_no_step` and `terminal_state_no_step` prohibit steps after termination.

The action-failure theorem preserves the old state and value while entering terminal error. This agrees with staging but promises no external-I/O rollback. See [Proofs/Machine.lean](https://github.com/qigao/salts/blob/a650262031e9b3e5f11a227a7911a75db9ae1fb8/formal/cmeta_cflow_calculus/CMetaCFlowCalculus/Proofs/Machine.lean).

## 8. Application and Verification

Definition tests cover unknown events, incorrect target types, ambiguous priorities, and outgoing transitions from terminals. Instance tests cover payload rejection before enqueueing, serial mutation after admission, action failure without partial publication, and different close/cancel outcomes around commit.

In the connection example, a controlled barrier inside the action lets a test issue close or cancel before preparation, after preparation but before commit, and after commit. These schedules correspond directly to the contract and are easier to diagnose than random sleeps. Before destruction, producers and attached Publisher/Resumable adapters must be quiescent. `cflow_machine_instance_destroy` requires a quiescent instance; it is not arbitrary concurrent cancellation.

The contracts are in [machine.h](https://github.com/qigao/salts/blob/a650262031e9b3e5f11a227a7911a75db9ae1fb8/cflow/include/cflow/machine.h) and [machine_instance.h](https://github.com/qigao/salts/blob/a650262031e9b3e5f11a227a7911a75db9ae1fb8/cflow/include/cflow/machine_instance.h). The next chapter adds Actor identity and lifecycle control for independently retained producer capabilities.

## 9. Summary

Machine definitions store types and transition rules; instances store mutable execution state. Admission, preparation, and commit have distinct checks and failure behavior. Staging preserves old state on action failure, while commit synchronization resolves cancellation races. These guarantees assume accurate types, serialized mutation, and live borrows; they do not roll back external effects.
