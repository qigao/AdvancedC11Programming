# Chapter 15: Integrating CMeta: From Declared Facts to Reliable Execution

This chapter reconnects the techniques in a complete application: field declarations generate type facts, function descriptions support binding and calls, graphs record composition, and runtime instances own state and cleanup. Comparing the inputs, outputs, and proof obligations of those steps helps place a new requirement in a macro, descriptor, generator, or runtime.

## 1. From the Division of Labor in Ordinary C to Native Semantic IR

The book no longer begins with “macros are painful, so escape macros.” It begins by assigning responsibilities to ordinary-C mechanisms:

| Mechanism | Responsibility |
|---|---|
| normal function / static inline | typed behavior |
| finite macro / PP | tokens, declarations, schema replay |
| compiler capability | native compile-time facts |
| CMeta | stable native semantic facts |
| DataBind | logical contract facts |
| CFlow | execution relations |
| Lean | selected semantic laws |

The first step is not to replace C with macros. It is:

~~~text
ordinary C
    |
    v
identify repeated stable knowledge
    |
    v
use the smallest compile-time / semantic object
    |
    v
return to ordinary C execution
~~~

The goal remains:

define one stable fact once, let several consumers use it, and consume as much of it as possible before execution.

### 1.1 Native Semantic IR Describes Meaning Without Automatically Adding Runtime

CMeta adds a finite, explicit native semantic model:

| C reality | Semantic object |
|---|---|
| C type | TypeDesc / semantic identity |
| field facts | Struct / reflected-data metadata |
| capability | Traits / InterfaceDesc |
| native function | FunctionDesc + FunctionAbi |
| executable value | cmeta_callable |
| admitted semantic/execution join | cmeta_invokable |

The important separation is now:

| Descriptive object | Execution / binding object |
|---|---|
| FunctionDesc + FunctionAbi | direct C call / optional exact thunk / cmeta_callable / cmeta_invokable |
| InterfaceDesc | live {self,vtable} |

Function Reflection is descriptive. The existence of metadata does not turn:

~~~c
add(2, 3);
~~~

into runtime Reflection dispatch. A dynamic or foreign boundary instead uses:

~~~text
raw descriptor
    -> validate / admit once
    -> admitted capability
    -> repeated use
~~~

### 1.2 Generic and Type Relations Share a Kernel, Not a Universal Router

The current Generic entry is finite and explicit:

~~~c
cmeta_type(Vec, IntVec, int);
cmeta_type(Option, MaybeUser, User);
~~~

It accepts registered Generic kinds only. That differs from the historical universal routing surface:

~~~text
historical:
typed(...)
    -> many unrelated DSL families

current:
cmeta_type(...)
    -> finite Generic declaration only
~~~

Finite type relations remain explicit rows:

~~~c
TypeFunction(CommonArithmetic,
    (int, int, int),
    (int, double, double),
    (double, int, double),
    (double, double, double)
);
~~~

A missing row fails explicitly. The book-wide discipline remains:

finite, explicit, bounded, unsupported is explicit.

### 1.3 Function Semantics and Executable Projection Are Explicit Choices

A direct call:

~~~c
long square(int x);
~~~

does not require a Callable object. When several consumers need native function meaning:

~~~text
FunctionDecl
    -> FunctionDesc
    -> FunctionAbi
~~~

When an exact erased boundary is required:

~~~text
FunctionInvokeDecl
    -> explicitly generated exact thunk
~~~

When receiver or parameter binding is required:

~~~text
canonical Function
    -> explicit projection
    -> bounded cmeta_callable capture
    -> cmeta_invokable admission
~~~

A receiver operation set is only a thin:

~~~text
name -> canonical FunctionAbi
~~~

index; it does not duplicate FunctionDesc. The smallest representation is therefore:

| Requirement | Smallest representation |
|---|---|
| direct call | ordinary function / function pointer |
| describe native function | FunctionDesc + FunctionAbi |
| exact erased boundary | explicit exact thunk |
| bind / capture / receiver projection | cmeta_callable + cmeta_invokable |
| long-lived provider | Interface + {self,vtable} |

Bind is explicit parameter projection. It does not require a separate Lambda object model and does not hide malloc, retain, or managed ownership.

## 2. Execution IR and Verified Transformations

Once admitted callables compose, the new knowledge is the relation between them. For example:

~~~text
Source<int>
    ↓
Filter(is_even)
    ↓
Map(square)
    ↓
Reduce(sum)
~~~

Graph preserves topology, type chain, operator semantics, and callable relations as a program object. That enables work before execution:

- type admission;
- normalization;
- semantic rewrite;
- Plan compilation;
- Direct/AOT eligibility.

If one fixed loop is sufficient, Graph is unnecessary.

### 2.1 Formal Semantics: Proof Serves Real Transformations

Formal proof becomes relevant when an optimizer wants to replace P with Q. For example:

~~~text
Map(f); Map(f)  ~>  Map(f)
~~~

requires more than an `IDEMPOTENT` metadata bit. It needs:

~~~text
∀x, f(f(x)) = f(x)
~~~

The evidence layers differ:

| Layer | Evidence |
|---|---|
| metadata claim | admission |
| semantic law | Lean theorem |
| one concrete rewrite | trace / certificate |
| real C implementation | differential test |
| performance | benchmark |

Lean is not decoration, and it does not replace ABI, link, sanitizer, or benchmark evidence.

## 3. Contract IR and Live Runtime

Native function semantics do not define the public logical contract. For example:

~~~c
int get_user(
    UserRepository *repo,
    uint64_t id,
    User *out_user);
~~~

CMeta can describe these parameters, but it cannot decide by itself that `repo` is a host dependency, `id` is a request field, and `out_user` constructs the response. DataBind therefore adds Contract IR:

~~~text
service UserService {
    GetUser: GetUserRequest -> GetUserResponse;
}
~~~

The compiler joins Contract IR and Native Semantic IR:

~~~text
Service Operation
      +
FunctionDesc
      ↓
BindingPlan
      +
exact adapter
~~~

HTTP, RPC, Plugin, WASM, OpenAPI, and Mock are projections of the same contract instead of independent service truths.

### 3.1 Live Runtime: Add State Without Duplicating Semantic Truth

Reactive, Executor, Machine, and Actor do not invent a second application semantics. They add bounded live state:

| Runtime object | Live concern added |
|---|---|
| Subscription | WAIT / Wake / Demand / terminal |
| Executor | bounded admission / settlement |
| Machine Instance | current state / transition commit |
| Actor | mailbox / ref / lifecycle / single owner |
| Plugin lease | DSO lifetime / quiescent unload |

The shared rule is: **separate immutable description from live execution state**. That lets one Graph, Service, or Machine definition be reused by many runtime instances while the hot path avoids rediscovering metadata.

## 4. The Three IRs Form One Compiler Chain

The book is no longer a collection of independent features.

| IR | Question answered |
|---|---|
| DataBind Contract IR | What does the program promise? |
| CMeta Native Semantic IR | What is the C implementation? |
| CFlow Execution IR | How is admitted work composed/executed? |

The layers join in the compiler/control plane rather than through runtime guesswork:

~~~text
DataBind Contract IR
        +
CMeta Native IR
        ↓
binding / validation / generation
        ↓
immutable plans / exact adapters
        ↓
optional CFlow Execution IR
        ↓
lowered ordinary C execution
~~~

The next section stops reviewing individual features and turns this chain into a reusable method.

## 5. The Final Method: Understand → Model → Formalize → Verify → Implement → Lower → Measure

All earlier chapters can be reduced to these seven steps. This is not a mechanical process. It is an order of questions.

### 5.1 Understand: See the Plain C Problem Clearly First

Do not begin by choosing a framework, inventing a macro, or asking whether Lean can prove the design. Ask first: **How would ordinary C solve this with no new abstraction?** Establish a runnable Plain C baseline, including its failure behavior, then identify what is actually being repeated: code, stable facts, a type relation, a runtime decision, or a semantic obligation. Similar-looking code is not enough. Modeling becomes worthwhile when the same stable knowledge is being maintained independently by multiple consumers.

### 5.2 Model: Make the Stable Knowledge Explicit

A model is not necessarily a DSL. It may be as small as a Type Descriptor, Trait, Callable Signature, Event Schema, Graph Node, Transition Row, or Executor State. A useful model makes data, identity, ownership, lifetime, failure, capacity, state transitions, and module ownership explicit. It must also answer a harder question: **which facts are semantic truth, and which are only representation or mechanism?** For example:

| Representation / mechanism | Semantic meaning |
|---|---|
| descriptor address | semantic type identity |
| Actor worker thread | Actor lifecycle + mailbox + single mutable owner |

The left column records representation or mechanism; the right column records the meaning other components may rely on. Modeling turns an implicit convention into an explicit, checkable program fact.

### 5.3 Formalize: Formalize Only Stable Relations Worth Sharing

Not every model belongs in Lean. Strong candidates are finite type relations, rewrite laws, demand invariants, wait/wake state transitions, executor ledgers, state-machine small steps, refinement relations, and certificate conditions. Before formalizing any of them, define the observable semantics. If the observations are unclear, a proof of rewrite correctness is premature. Formalization is valuable partly because it exposes assumptions that prose often leaves unstated:

- What numerical semantics make ASSOCIATIVE true?
- Are WAIT and SUSPENDED the same state?
- Who wins the cancel/commit linearization point?
- Does parallel reduce preserve encounter order?

Proof obligations often improve the API. That is more valuable than “adding a theorem at the end.”

### 5.4 Verify: Choose Evidence at the Correct Layer

Verification is not synonymous with Lean. Different claims need different evidence:

| Claim | Evidence |
|---|---|
| semantic law | Lean theorem |
| generated fact | generator check |
| C representation | compile/runtime tests |
| Multi-TU identity | peer translation-unit test |
| ABI/install | independent installed consumer |
| memory/lifetime | sanitizer |
| race | stress / deterministic concurrency test |
| performance | benchmark |

Professional engineering means matching evidence to the claim. Do not use one kind of evidence to prove something it cannot establish: a Lean theorem does not replace a shared-library link test, and a benchmark does not replace a semantic-preservation proof.

### 5.5 Implement: Bring the Design Back to Ordinary C Ownership

Implementation must return to concrete C questions:

- Who owns memory?
- Who borrows?
- Who destroys?
- Who may mutate?
- When does failure happen?
- What is the capacity?
- In which context does callback run?
- What is public ABI?

The final surface should contain real structs, enums, functions, statuses, descriptors, opaque handles, builders, and destroy paths—not only an architecture diagram. A useful standard is simple: a C engineer who never read the formal proof should still be able to understand ownership and failure contracts from the public headers.

### 5.6 Lower: Consume Rich Knowledge Before Execution Whenever Possible

The goal of a typed model is not to make runtime keep querying metadata. The goal is:

~~~text
know more before execution
    ↓
validate earlier
    ↓
bind earlier
    ↓
normalize earlier
    ↓
optimize earlier
    ↓
compile earlier
    ↓
do less per value/event/task
~~~

A typical path:

~~~text
Stream
    ↓
Surface Graph
    ↓
Normalize
    ↓
Optimize
    ↓
Plan / Direct
    ↓
simple execution
~~~

Machine follows the same idea:

~~~text
Definition
    ↓
Build validation
    ↓
Immutable Machine
    ↓
Instance
    ↓
selection / guard / action / commit
~~~

If metadata cannot be consumed before the hot path, ask whether it is actually runtime state or runtime policy rather than metadata.

### 5.7 Measure: Finally Check the Cost on Real Machines

Measurement decides whether the abstraction is worth keeping. Separate control-plane cost, execution cost, memory cost, compile-time cost, binary/ABI cost, and operational cost. A design may be more expensive to construct but cheaper after repeated execution; another may look elegant at the API while preserving an unnecessary dynamic dispatch in the hot path. Benchmarks, profiling, installed builds, and real workloads provide this evidence. The loop is therefore not “Design → Done” but:

~~~text
Understand
→ Model
→ Formalize
→ Verify
→ Implement
→ Lower
→ Measure
        ↓
        └──── feedback to Model/Design
~~~

## 6. Three Worked Syntheses: The Same Method Can Produce Different Answers

The method is useful precisely because it does not always conclude that a more advanced abstraction is needed.

### 6.1 One Fixed Filter + Map

Suppose the requirement is only to iterate an array, keep even numbers, square them, and write the output. There is one fixed pipeline, one call site, and no dynamic composition. The Plain C baseline already expresses the full requirement, and there is **no new stable knowledge to share**:

~~~c
for (...) {
    if (!is_even(x))
        continue;
    out[n++] = square(x);
}
~~~

Ordinary C is the best answer. If the project later grows into dozens of pipelines, unified operators, type propagation, verification, or multiple execution backends, then upgrade to Graph.

### 6.2 One Asynchronous Data Source

Now consider a source that originally only supports “read the next value.” Once it must distinguish value available, temporarily unavailable, end of stream, and error, the model gains `VALUE`, `WAIT`, `DONE`, and `ERROR`, together with downstream demand. Formalization then exposes four essential rules: `WAIT` is not the same as an armed wait; Wake does not consume demand; Emit consumes demand; and terminal states are absorbing. Those rules in turn require explicit pending-arm state, wake generations, and cancellation behavior in the C runtime. Here the abstraction is justified because it centralizes race, demand, and lifecycle knowledge that every asynchronous source would otherwise have to reimplement.

### 6.3 One Long-Lived Concurrent Connection Object

The initial implementation may be:

~~~c
mutex_lock();
switch (state) {
...
}
mutex_unlock();
~~~

If there are only a few states and events, no multiple producers, and no complex lifecycle, keep the ordinary implementation. When requirements grow to typed event payload, multiple producers, bounded admission, serialized transition, close/cancel races, stale producer refs, or formal transition correctness, the design gradually becomes:

~~~text
Typed Event
    ↓
Machine
    ↓
Mailbox
    ↓
Serial Executor
    ↓
Actor lifecycle shell
~~~

Actor was not the starting point. It is the result of requirements becoming stable enough to justify composition. This is one answer for **application-owned state**, not a mandatory runtime shell for every long-lived connection.

If the runtime already uses Salts 2.3 CNet Sharded Graph, a more direct answer is `CNet Owner + admission/placement policy + Manager/ClientPool`. Choosing a local Owner differs from choosing a remote Endpoint; neither decision reserves actual capacity. A connection is not reusable until its protocol is READY, and a transport reconnect does not grant permission to retry application DATA. A CMeta ACE-style typed Strategy callback can express behavior without allocating an Actor, another Reactor, or a hidden worker. The Chapter 12 [SG comparison](./ch-11.md) and installed [C11 gate](../qualification/ch12_cnet_strategy.c) exercise those boundaries; they are **not** a proof that the Actor Lean model implements CNet SG.

## 7. Final Equation: The Modern C of This Book

The design can now be compressed into:

~~~text
Ordinary C
+
Explicit Contract IR
+
Explicit Native Semantics
+
Explicit Execution IR
+
Verified High-Risk Transformations
+
Aggressive Lowering
=
Modern C
~~~

Each term has a concrete representation.

### 7.1 Ordinary C

Keep native layout, ordinary ABI, explicit lifetime, direct calls, and normal compiler/linker/debugger tooling.

### 7.2 Explicit Contract IR

DataBind describes Contract IR with message, service, channel, and component. It answers: **What does the program promise?**

### 7.3 Explicit Native Semantics

CMeta describes type identity, traits, FunctionDesc, InterfaceDesc, effects/properties, and ownership facts. It answers: **What is the C implementation?**

### 7.4 Explicit Execution IR

CFlow describes Graph, Plan, Publisher/Subscription, Machine, and execution relations. It answers: **How is admitted work composed and executed?**

### 7.5 Verified High-Risk Transformations

Use machine-checkable evidence for semantic risk such as rewrite, normalization, state invariants, refinement, and certificates.

### 7.6 Aggressive Lowering

Consume high-level knowledge in build, generation, admission, and control-plane stages so the hot path returns toward ordinary C.

## 8. DataBind / CMeta / CFlow / Lean: Promise / Know / Structure / Trust

This is not one giant framework. The layers answer different questions.

### 8.1 DataBind — Promise

DataBind builds Contract IR and answers:

- What data is exchanged?
- What operation is promised?
- What messages/events exist?
- Which capabilities form one component?

It does not own HTTP sockets, plugin loading, a WASM engine, or the CFlow scheduler.

### 8.2 CMeta — Know

CMeta builds Native Semantic IR and answers:

- What is this C type?
- What is this native function?
- Which parameter is IN / OUT?
- What ownership/capability is known?
- What semantic identity survives representation boundaries?

### 8.3 CFlow — Structure / Execute

CFlow builds Execution IR and answers:

- How are computations related?
- Which execution shapes are admitted?
- How can work be normalized, scheduled, optimized, or lowered?

### 8.4 Lean — Trust selected semantic claims

Lean owns no runtime. It asks selected semantic questions:

- Does this rewrite preserve observation?
- Does this transition preserve the invariant?
- Does this refinement preserve the promised result?

The complete relationship is:

~~~text
DataBind Contract IR
        +
CMeta Native IR
        ↓
compiler / binding
        ↓
generated plans/adapters
        ↓
optional CFlow Execution IR
        ↓
verified transformation where needed
        ↓
ordinary C execution
~~~

All of these serve ordinary C instead of replacing it.

## 9. Modern C and the Final Design Checklist

Language comparisons often ask whether C can have lambda, generic, stream, or actor. This book cares more about another question:

Can a C system maintain less duplicated knowledge while preserving explicit ownership, stable ABI, predictable cost, and an ordinary toolchain? So “modern” is not more syntax sugar; it is stronger semantic sharing, earlier error detection, clearer ownership, less trusted duplication, more verifiable transformation, and simpler execution. That is Modern C in a systems-engineering sense.

### 9.1 Final Design Checklist for the Reader

For a new C systems problem, ask in this order:

1. What is the Plain C baseline?
2. What is the real pain point?
3. Is the duplication code or knowledge?
4. Which facts are already stable?
5. Which module owns those facts?
6. Is semantic identity required?
7. Are ownership/lifetime/capacity/failure explicit?
8. Which errors can move earlier?
9. Which dynamic behavior is genuinely necessary?
10. What are the observable semantics?
11. Which laws/invariants deserve formalization?
12. Which real implementation behavior does the theorem authorize?
13. What is the C representation?
14. Does the Multi-TU/ABI/install boundary hold?
15. Can the abstraction disappear from the hot path?
16. How will performance/memory/concurrency cost be measured?
17. Is ordinary C still simpler?

If the answer to question 17 is **Yes**, then use ordinary C. That is a completely correct result.

## 10. What a Modern C Book Should Ultimately Teach

The goal is not to memorize a macro API. It is to develop the following capabilities.

### 10.1 Recognize Stable Knowledge in Code

Know what should remain ordinary code and what has become stable enough to be schema/type/relation.

### 10.2 See Ownership Beneath a High-Level API

When looking at lambda, stream, actor, or rpc, still ask: Who owns? Who borrows? What is capacity? How does failure happen? What is lifetime? What reaches the hot path?

### 10.3 Use Formal Proof as Design Feedback

Not “write code, then check a theorem box.” Instead:

~~~text
proof obligation
    ↓
discover design ambiguity
    ↓
change API/runtime contract
~~~

### 10.4 Look for Lowering in Every Abstraction

Whenever a layer is added, ask:

How does it become simple C again?

### 10.5 Stay Honest Through Measurement

Do not use zero-cost, faster, or scalable as design adjectives. Let measurements decide.

## 11. CMeta + ACE Pattern Map: Choose Responsibilities Before Patterns

`ACE` supplies composable design vocabulary, not a class/runtime hierarchy that C must copy in full. CMeta lowers contracts to static C11 types, X-lists, FunctionDesc, FunctionAbi and finite hooks; actual execution still belongs to the appropriate component. This map distinguishes **later Salts 2.3 released-SDK evidence** from the book's pinned edition snapshots.

| ACE pattern | CMeta contribution | Execution/lifetime authority | Installed evidence |
|---|---|---|---|
| Strategy / Adapter | Typed `{self,vtable}`, exact function ABI, borrowed callbacks | Ordinary C service or CNet client/server | `ch03_cmeta_ace_patterns.c`; `ch12_cnet_strategy.c` |
| Interceptor | Exact target/hook; at most 16 hooks; forward enter/reverse unwind | Caller retains hooks, contexts and Plugin Scope | `ch03_cmeta_ace_patterns.c` |
| Scoped/Strategized Locking, Thread-Safe Interface | `cmeta_ace_lockable` and typed synchronous body | Platform mutex/RWLock; no suspension under guard | `ch03_cmeta_ace_patterns.c` |
| Monitor Object, Thread-Specific Storage, Leader/Followers | Typed methods, CPU-event FunctionDesc, owner contracts | Platform mutex/condition/TLS and explicit CPU-event baton election | Book `ch10_cmeta_ace_monitor.c` qualifies Monitor/TLS; `ch10_cmeta_ace_leader_followers.c` independently verifies bounded CPU-event handoff, terminal conservation and close, not a CNet I/O Reactor |
| Active Object | Typed application Port/Strategy | CFlow Actor, Machine, bounded mailbox, Executor | `ch12_cmeta_ace_active_object.c` |
| Half-Sync/Half-Async, Pipes and Filters | Typed channel element and filter/map semantics | CFlow Channel/Graph/Scheduler, capacity and demand | Upstream installed CFlow ACE consumer; existing book Graph/Channel gates |
| Reactor-style application dispatch / Acceptor-Connector | CMeta fully reflected typed Handler; no backend ownership | Caller handles listener readiness and CNet client polling; CNet still observes NativeIO | `ch12_ace_reactor_dispatch.c` |
| Proactor / NativeIO SG | Completion-callback ABI and one-shot token identity | One SG host lease observes completions; final Owner owns terminal/recycle/credit | `ch12_cnet_sg_handoff.c`; `ch03_cmeta_ace_patterns.c` |
| Service Configurator (application example) | Independent typed Server Owner and Client Destination Strategies selected from config | Application owns strict parsing, borrow leases and quiescent publication, delegates to actual CNet public policy APIs; **not a generic deployment runtime** | `ch15_cmeta_ace_configurator.c`; `ch15_cmeta_ace_cnet_policy_config.c` |

The choice can be made with **decision pseudocode**, not an inheritance tree:

~~~text
fixed direct call?                     -> ordinary C function
multiple implementations, exact ABI?  -> CMeta Strategy
cross-cutting call checks?             -> CMeta Interceptor (borrowed hooks)
shared mutable state?                  -> Platform lock + typed scoped gate
network I/O and many connections?      -> CNet/NativeIO SG Owner + policies
application typed event/state machine? -> CFlow Active Object (optional)
I/O-to-CPU handoff?                    -> bounded CFlow Channel + explicit FULL policy
runtime reconfiguration?               -> validate config, quiesce old owner, replace explicitly
~~~

`Config/Configurator` is an **application control-plane design**: DataBind may parse/validate a config file that selects a CMeta Strategy or CNet client/server policy. That does not automatically confer hot replacement, Plugin leases, implicit reconnect, or connection movement. Replacement must stop new admission, settle old tasks and borrows, then publish a new immutable configuration. Without lifecycle qualification, “dynamically configurable” is not a delivered feature.

The installed programs and existing SG gate separately establish ordered `ABTba/AB21` interception, guarded counts under four workers, one-shot NativeIO completion, Actor accept/stop/STALE, and real TCP handoff. They **do not prove** that all ACE patterns are implemented, nor replace performance, sanitizers, or cross-platform ABI evidence. A separate native SDK matrix owns that last qualification.

### 11.1 Service Configurator: A File Chooses a Strategy, Not a Runtime Owner

The ACE Service Configurator problem starts with **when configuration becomes callable behavior**. An application may parse a file and publish a borrowed CMeta Interface at a clear control-plane boundary. This is not the same capability as arbitrary hot replacement of connections, plugins or workers.

The [installed C11 example](../qualification/ch15_cmeta_ace_configurator.c) consumes real config files rather than inventing a class system. Its deliberately small grammar is inspectable:

~~~text
version=1
strategy=add
operand=3
~~~

Every field must appear exactly once. `strategy` accepts `add` or `scale`; `operand` is bounded to `1..16`. Unknown, repeated or missing keys, out-of-range integers and invalid text fail before publication. Parsing produces a temporary typed `book_config` and updates the address-stable Owner's `active` record **only after complete validation**. DataBind may parse/validate richer JSON or YAML in a production application; this example intentionally keeps the admission and publication mechanics visible rather than pretending to implement a full DataBind Configurator.

~~~text
config file -> strict parser -> candidate typed spec
                                    |
                           validation fails?
                             yes: no publication
                                    |
                            owner + no live lease?
                             no: BUSY / reject
                                    |
                       commit config generation
                                    |
                   acquire fresh ONE-SHOT lease
                                    |
                    bind CMeta self to lease
                                    |
                              ordinary C call
~~~

`CMETA_INTERFACE(book_ace_config_strategy, ...)` declares an exact **`apply(int value, int *out)` status/out contract** (`FR2`: the function return is a Salts status; business data is written only to the caller-owned `out`). Two `CMETA_IMPLEMENTS` bind ordinary add/scale functions. Null output, signed overflow or a revoked lease must reject **before writing output**, so a negative business value cannot be confused with an error code. `book_host_acquire()` requires a **fresh zero-initialized, address-stable, one-shot lease slot** and binds CMeta Interface `self` to that slot, never directly to the shared host. Each `apply` verifies slot identity, `live`, Owner token, and configuration generation. A released Interface returns `SALTS_ESHUTDOWN` **even when another fresh lease is active**. A spent slot cannot be reacquired at the same address, preventing stale Interface ABA resurrection. The caller keeps slot storage alive until no stale borrowed Interface is inspected. `reload` and `close` remain blocked by live leases; copying a lease never duplicates release authority.

~~~text
add.cfg      acquire -> apply(7) = 10
scale.cfg    reload with live lease -> BUSY, generation unchanged
             release once -> OK; second release -> STALE
             old Interface.apply() -> ESHUTDOWN, even with new lease
             acquire using spent slot -> STALE (one-shot only)
invalid.cfg  reload -> INVALID, active config unchanged
scale.cfg    reload when quiescent -> generation++ -> apply(7) = 14
close        no live leases -> OK; later acquire -> STALE
~~~

This is the useful ACE technique in modern C: **behavior is a typed Interface; reconfiguration is committed at a quiescent point by its application Owner; execution remains ordinary C**. A complete hot-deployment system would separately qualify Plugin leases, CNet Owners, callback settlement and connection movement. This example implements none of those extra runtime guarantees and must not be presented as a shipped generic CMeta Configurator.

### 11.2 Reactor and Proactor: Verify Dispatch and Asynchronous Completion Separately

These two ACE event models belong on the same architectural map, but “both use asynchronous I/O” does not make their contracts interchangeable:

~~~text
Reactor-style: listener.wait(READY) -> accept -> owner.poll()
                  -> CMeta typed Observer -> application decision
Proactor:      async NativeIO/CNet submit -> SG host.observe(COMPLETION)
                  -> CNet route_batch -> final Owner terminal/recycle
~~~

Chapter 12's [`ch12_ace_reactor_dispatch.c`](../qualification/ch12_ace_reactor_dispatch.c) registers and dispatches a typed observer for real TCP and checks fail-before-callback admission, CONNECTED/terminal counts and callback lifetimes. The existing [`ch12_cnet_sg_handoff.c`](../qualification/ch12_cnet_sg_handoff.c) uses two real SG Owners to observe completions, transfer an accepted socket, exchange data and settle credit once. Chapter 10's `NATIVE_IO_ACE_TOKEN_TYPE` separately validates one completion identity; it is not an I/O executor.

Crucially, `cnet_client_poll` **also consumes NativeIO completions internally**. “Reactor-style” in the book describes the caller's readiness check and Handler dispatch structure, **not** another pure Reactor backend. Once CNet SG exists, an application should not create a second Reactor, Actor or thread pool merely to illustrate an ACE pattern.

### 11.3 A Practical Network Service Configurator: Server Owner versus Client Destination

The preceding `add/scale` example demonstrates a file-selected Strategy, but a real network application must configure both **server-side connection ownership** and **client-side remote destination choice**. These are not interchangeable and must not disguise implicit migration of an established SG Owner.

The new independently installed C11 program [`ch15_cmeta_ace_cnet_policy_config.c`](../qualification/ch15_cmeta_ace_cnet_policy_config.c) uses a deliberately closed file contract:

~~~text
version=1
server=strict_key
client=round_robin
~~~

Both `server` and `client` accept `strict_key` or `round_robin` independently. The parser requires each field once and rejects missing/duplicated/unknown values before publication. Distinct CMeta Interfaces generate exact native `book_ace_server_policy.select(ticket, out)` and `book_ace_client_policy.select(ticket, out)` methods (`FR2`, real `int *` OUT borrow and its ABI descriptor). Four `CMETA_IMPLEMENTS` delegates call the **actual released CNet APIs**, not reimplemented selection algorithms:

~~~c
/* Local final Owner: key % owner_count */
cnet_owner_placement_choose(&placement, &owner);

/* Stable remote endpoint_id: strict-key rendezvous hashing */
cnet_destination_choose(&selection, &destination);
~~~

The application owns one fixed Owner. Each acquisition supplies a **fresh, nonreusable one-shot lease slot** borrowed as `self` by both typed server/client Interfaces. Every call checks that precise slot identity and generation; an old copied Interface remains revoked even while another new lease is live. Every in-flight call holds a generation-safe lease. Both server and client policy changes publish together only when `leases == 0`, incrementing the generation once. Foreign threads cannot acquire leases or change configuration; **even directly invoking a copied Interface from a foreign thread returns `SALTS_EPERM`**. Calling a former borrow after the last lease is released returns `SALTS_ESHUTDOWN`. Copying a lease never duplicates release authority. Rejection leaves the caller's `out` untouched—an inspectable contract that prevents accidental fallback.

~~~text
Initial config: strict / strict
    local ticket 5 -> SG Owner 2 (5 % 3)
    remote ticket 5 -> stable endpoint_id (11 / 22 / 33)
    pinned local FULL    -> ENOBUFS, not rerouted
    pinned remote FULL   -> ENOBUFS, not rerouted

Live call: reload(strict / rr) -> BUSY
After all calls settle: reload(strict / rr) -> generation + 1
    local ticket 5 -> Owner 2
    remote ticket 5 -> endpoint_id 33

Later reload(rr / rr):
    owner 2 unavailable -> select Owner 0
    endpoint 33 unavailable -> select endpoint 11
~~~

A successful Server `choose` still requires `cnet_handoff_reserve`, `cnet_manager_reserve`, or actual final-Owner CNet admission. A successful Client `choose` still requires authority/security compatibility, a real dial, or a protocol-READY pool lease. This example **does not** open sockets, schedule retries, instantiate Actors or create another Reactor. Its evidence is application ACE Configurator + two public CNet strategy dimensions, not end-to-end load-balancing performance.

## 12. Summary

CMeta techniques share a process: declarations record reusable facts, type and contract checks generate or select calls, and applications manage execution state. Macro expansion, call adaptation, graph rewriting, and asynchronous progress each have distinct inputs, outputs, and correctness conditions; sharing descriptors does not merge those responsibilities. For a new application, first write the ordinary C baseline and its failure behavior, then identify facts worth sharing. Specify the generation algorithm or state transitions, derive preconditions and invariants, and check the implementation through compilation, execution, or proof. Retain the added mechanism when these steps establish a maintenance or execution benefit.
