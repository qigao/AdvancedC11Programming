# Chapter 15: Integrating CMeta: From Declared Facts to Reliable Execution

This chapter reconnects the techniques in a complete application: field declarations generate type facts, function descriptions support binding and calls, graphs record composition, and runtime instances own state and cleanup. Comparing the inputs, outputs, and proof obligations of those steps helps place a new requirement in a macro, descriptor, generator, or runtime.

## 1. From the Division of Labor in Ordinary C to Native Semantic IR

The book no longer begins with “macros are painful, so escape macros.” It begins by assigning responsibilities to ordinary-C mechanisms:

| Mechanism | Responsibility |
|---|---|
| normal function / static inline | typed behavior |
| finite macro / PP | tokens, declarations, schema replay |
| compiler capability | native compile-time facts |
| CMeta | stable native semantic facts |
| DataBind | logical contract facts |
| CFlow | execution relations |
| Lean | selected semantic laws |

The first step is not to replace C with macros. It is:

~~~text
ordinary C
    |
    v
identify repeated stable knowledge
    |
    v
use the smallest compile-time / semantic object
    |
    v
return to ordinary C execution
~~~

The goal remains:

define one stable fact once, let several consumers use it, and consume as much of it as possible before execution.

### 1.1 Native Semantic IR Describes Meaning Without Automatically Adding Runtime

CMeta adds a finite, explicit native semantic model:

| C reality | Semantic object |
|---|---|
| C type | TypeDesc / semantic identity |
| field facts | Struct / reflected-data metadata |
| capability | Traits / InterfaceDesc |
| native function | FunctionDesc + FunctionAbi |
| executable value | cmeta_callable |
| admitted semantic/execution join | cmeta_invokable |

The important separation is now:

| Descriptive object | Execution / binding object |
|---|---|
| FunctionDesc + FunctionAbi | direct C call / optional exact thunk / cmeta_callable / cmeta_invokable |
| InterfaceDesc | live {self,vtable} |

Function Reflection is descriptive. The existence of metadata does not turn:

~~~c
add(2, 3);
~~~

into runtime Reflection dispatch. A dynamic or foreign boundary instead uses:

~~~text
raw descriptor
    -> validate / admit once
    -> admitted capability
    -> repeated use
~~~

### 1.2 Generic and Type Relations Share a Kernel, Not a Universal Router

The current Generic entry is finite and explicit:

~~~c
cmeta_type(Vec, IntVec, int);
cmeta_type(Option, MaybeUser, User);
~~~

It accepts registered Generic kinds only. That differs from the historical universal routing surface:

~~~text
historical:
typed(...)
    -> many unrelated DSL families

current:
cmeta_type(...)
    -> finite Generic declaration only
~~~

Finite type relations remain explicit rows:

~~~c
TypeFunction(CommonArithmetic,
    (int, int, int),
    (int, double, double),
    (double, int, double),
    (double, double, double)
);
~~~

A missing row fails explicitly. The book-wide discipline remains:

finite, explicit, bounded, unsupported is explicit.

### 1.3 Function Semantics and Executable Projection Are Explicit Choices

A direct call:

~~~c
long square(int x);
~~~

does not require a Callable object. When several consumers need native function meaning:

~~~text
FunctionDecl
    -> FunctionDesc
    -> FunctionAbi
~~~

When an exact erased boundary is required:

~~~text
FunctionInvokeDecl
    -> explicitly generated exact thunk
~~~

When receiver or parameter binding is required:

~~~text
canonical Function
    -> explicit projection
    -> bounded cmeta_callable capture
    -> cmeta_invokable admission
~~~

A receiver operation set is only a thin:

~~~text
name -> canonical FunctionAbi
~~~

index; it does not duplicate FunctionDesc. The smallest representation is therefore:

| Requirement | Smallest representation |
|---|---|
| direct call | ordinary function / function pointer |
| describe native function | FunctionDesc + FunctionAbi |
| exact erased boundary | explicit exact thunk |
| bind / capture / receiver projection | cmeta_callable + cmeta_invokable |
| long-lived provider | Interface + {self,vtable} |

Bind is explicit parameter projection. It does not require a separate Lambda object model and does not hide malloc, retain, or managed ownership.

## 2. Execution IR and Verified Transformations

Once admitted callables compose, the new knowledge is the relation between them. For example:

~~~text
Source<int>
    ↓
Filter(is_even)
    ↓
Map(square)
    ↓
Reduce(sum)
~~~

Graph preserves topology, type chain, operator semantics, and callable relations as a program object. That enables work before execution:

- type admission;
- normalization;
- semantic rewrite;
- Plan compilation;
- Direct/AOT eligibility.

If one fixed loop is sufficient, Graph is unnecessary.

### 2.1 Formal Semantics: Proof Serves Real Transformations

Formal proof becomes relevant when an optimizer wants to replace P with Q. For example:

~~~text
Map(f); Map(f)  ~>  Map(f)
~~~

requires more than an `IDEMPOTENT` metadata bit. It needs:

~~~text
∀x, f(f(x)) = f(x)
~~~

The evidence layers differ:

| Layer | Evidence |
|---|---|
| metadata claim | admission |
| semantic law | Lean theorem |
| one concrete rewrite | trace / certificate |
| real C implementation | differential test |
| performance | benchmark |

Lean is not decoration, and it does not replace ABI, link, sanitizer, or benchmark evidence.

## 3. Contract IR and Live Runtime

Native function semantics do not define the public logical contract. For example:

~~~c
int get_user(
    UserRepository *repo,
    uint64_t id,
    User *out_user);
~~~

CMeta can describe these parameters, but it cannot decide by itself that `repo` is a host dependency, `id` is a request field, and `out_user` constructs the response. DataBind therefore adds Contract IR:

~~~text
service UserService {
    GetUser: GetUserRequest -> GetUserResponse;
}
~~~

The compiler joins Contract IR and Native Semantic IR:

~~~text
Service Operation
      +
FunctionDesc
      ↓
BindingPlan
      +
exact adapter
~~~

HTTP, RPC, Plugin, WASM, OpenAPI, and Mock are projections of the same contract instead of independent service truths.

### 3.1 Live Runtime: Add State Without Duplicating Semantic Truth

Reactive, Executor, Machine, and Actor do not invent a second application semantics. They add bounded live state:

| Runtime object | Live concern added |
|---|---|
| Subscription | WAIT / Wake / Demand / terminal |
| Executor | bounded admission / settlement |
| Machine Instance | current state / transition commit |
| Actor | mailbox / ref / lifecycle / single owner |
| Plugin lease | DSO lifetime / quiescent unload |

The shared rule is: **separate immutable description from live execution state**. That lets one Graph, Service, or Machine definition be reused by many runtime instances while the hot path avoids rediscovering metadata.

## 4. The Three IRs Form One Compiler Chain

The book is no longer a collection of independent features.

| IR | Question answered |
|---|---|
| DataBind Contract IR | What does the program promise? |
| CMeta Native Semantic IR | What is the C implementation? |
| CFlow Execution IR | How is admitted work composed/executed? |

The layers join in the compiler/control plane rather than through runtime guesswork:

~~~text
DataBind Contract IR
        +
CMeta Native IR
        ↓
binding / validation / generation
        ↓
immutable plans / exact adapters
        ↓
optional CFlow Execution IR
        ↓
lowered ordinary C execution
~~~

Section 10 stops reviewing features and turns this chain into a reusable method.

## 5. The Final Method: Understand → Model → Formalize → Verify → Implement → Lower → Measure

All earlier chapters can be reduced to these seven steps. This is not a mechanical process. It is an order of questions.

### 5.1 Understand: See the Plain C Problem Clearly First

Do not begin by asking “Which framework should I use?”, “Which macro should I invent?”, or “Can Lean prove this?”. Begin with:

How would ordinary C solve this if I added no new abstraction? Establish a **Plain C baseline**, then identify whether the repetition is code, facts, a type relation, a runtime decision, or semantic reasoning. If two code fragments only look similar, do not abstract yet. Move on only when the same stable knowledge is independently maintained by several modules.

### 5.2 Model: Make the Stable Knowledge Explicit

A Model is not necessarily a DSL. It may be as small as a Type Descriptor, Trait, Callable Signature, Event Schema, Graph Node, Transition Row, or Executor State. A good model makes data, identity, ownership, lifetime, failure, capacity, state transition, and module owner explicit. and answers:

Which information is semantic truth, and which is only representation? For example:

| Representation / mechanism | Semantic meaning |
|---|---|
| descriptor address | semantic type identity |
| Actor worker thread | Actor lifecycle + mailbox + single mutable owner |

The left side is representation/mechanism; the right side is semantic meaning. The goal is to turn implicit convention into explicit program facts.

### 5.3 Formalize: Formalize Only Stable Relations Worth Sharing

Not every model belongs in Lean. The strongest targets are finite type relations, rewrite laws, demand invariants, wait/wake state transitions, executor ledgers, state-machine small steps, refinement relations, and certificate conditions. Before formalizing, ask:

What are the observable semantics? If we cannot answer that, it is too early to prove rewrite correctness. One of the most useful effects of formalization is exposing assumptions that were never stated. For example:

- What numerical semantics make ASSOCIATIVE true?
- Are WAIT and SUSPENDED the same state?
- Who wins the cancel/commit linearization point?
- Does parallel reduce preserve encounter order?

Proof obligations often improve the API. That is more valuable than “adding a theorem at the end.”

### 5.4 Verify: Choose Evidence at the Correct Layer

Verification is not synonymous with Lean. Different claims need different evidence:

| Claim | Evidence |
|---|---|
| semantic law | Lean theorem |
| generated fact | generator check |
| C representation | compile/runtime tests |
| Multi-TU identity | peer translation-unit test |
| ABI/install | independent installed consumer |
| memory/lifetime | sanitizer |
| race | stress / deterministic concurrency test |
| performance | benchmark |

Professional engineering means:

do not use one kind of evidence to prove something it cannot prove. A Lean theorem does not replace a shared-library link test; a benchmark does not replace a semantic-preservation proof.

### 5.5 Implement: Bring the Design Back to Ordinary C Ownership

Implementation must return to concrete C questions:

- Who owns memory?
- Who borrows?
- Who destroys?
- Who may mutate?
- When does failure happen?
- What is the capacity?
- In which context does callback run?
- What is public ABI?

The final surface should contain real structs, enums, functions, statuses, descriptors, opaque handles, builders, and destroy paths—not only an architecture diagram. A good standard is:

a C engineer who never read the formal proof can still understand ownership and failure contracts from the public headers.

### 5.6 Lower: Consume Rich Knowledge Before Execution Whenever Possible

The goal of a typed model is not to make runtime keep querying metadata. The goal is:

~~~text
know more before execution
    ↓
validate earlier
    ↓
bind earlier
    ↓
normalize earlier
    ↓
optimize earlier
    ↓
compile earlier
    ↓
do less per value/event/task
~~~

A typical path:

~~~text
Stream
    ↓
Surface Graph
    ↓
Normalize
    ↓
Optimize
    ↓
Plan / Direct
    ↓
simple execution
~~~

Machine follows the same idea:

~~~text
Definition
    ↓
Build validation
    ↓
Immutable Machine
    ↓
Instance
    ↓
selection / guard / action / commit
~~~

If Meta cannot be consumed before the hot path, ask:

Is it actually a Runtime Feature instead?

### 5.7 Measure: Finally Check the Cost on Real Machines

Only Measure can answer completely whether an abstraction is worth it. Separate control-plane cost, execution cost, memory cost, compile-time cost, binary/ABI cost, and operational cost. An abstraction may cost more to build but become cheaper after many executions, or look elegant at the API while keeping an extra dynamic dispatch forever in the hot path. Only benchmark, profiling, installed builds, and real workloads can answer these questions. The loop is therefore not “Design → Done.” It is:

~~~text
Understand
→ Model
→ Formalize
→ Verify
→ Implement
→ Lower
→ Measure
        ↓
        └──── feedback to Model/Design
~~~

## 6. Three Worked Syntheses: The Same Method Can Produce Different Answers

The most important property of this method is:

it does not always conclude that we need a more advanced abstraction.

### 6.1 One Fixed Filter + Map

The requirement is simply: iterate an array, keep even numbers, square them, and write output. Understand: one fixed pipeline, one call site, no dynamic composition. Model: **there is no new stable knowledge to share**. Conclusion:

~~~c
for (...) {
    if (!is_even(x))
        continue;
    out[n++] = square(x);
}
~~~

Ordinary C is the best answer. If the project later grows into dozens of pipelines, unified operators, type propagation, verification, or multiple execution backends, then upgrade to Graph.

### 6.2 One Asynchronous Data Source

Initially the system only needs read source / process value. Later the source must express now has value, temporarily unavailable, done, or error, so the Model gains `VALUE`, `WAIT`, `DONE`, and `ERROR`. plus downstream demand. Formalization reveals four key semantics: **WAIT != armed wait**, Wake does not consume demand, Emit consumes demand, and Terminal is absorbing. Lean proofs then force pendingArm, suspended generation, and explicit cancellation. and the C runtime gains a clearer Subscription state machine. Here abstraction is justified because it removes race/demand/lifecycle knowledge that would otherwise be reimplemented by every async source.

### 6.3 One Long-Lived Concurrent Connection Object

The initial implementation may be:

~~~c
mutex_lock();
switch (state) {
...
}
mutex_unlock();
~~~

If there are only a few states and events, no multiple producers, and no complex lifecycle, keep the ordinary implementation. When requirements grow to typed event payload, multiple producers, bounded admission, serialized transition, close/cancel races, stale producer refs, or formal transition correctness, the design gradually becomes:

~~~text
Typed Event
    ↓
Machine
    ↓
Mailbox
    ↓
Serial Executor
    ↓
Actor lifecycle shell
~~~

Actor was not the starting point. It is the result of requirements becoming stable enough to justify composition.

## 7. Final Equation: The Modern C of This Book

The design can now be compressed into:

~~~text
Ordinary C
+
Explicit Contract IR
+
Explicit Native Semantics
+
Explicit Execution IR
+
Verified High-Risk Transformations
+
Aggressive Lowering
=
Modern C
~~~

Each term has a concrete representation.

### 7.1 Ordinary C

Keep native layout, ordinary ABI, explicit lifetime, direct calls, and normal compiler/linker/debugger tooling.

### 7.2 Explicit Contract IR

DataBind describes Contract IR with message, service, channel, and component. It answers: **What does the program promise?**

### 7.3 Explicit Native Semantics

CMeta describes type identity, traits, FunctionDesc, InterfaceDesc, effects/properties, and ownership facts. It answers: **What is the C implementation?**

### 7.4 Explicit Execution IR

CFlow describes Graph, Plan, Publisher/Subscription, Machine, and execution relations. It answers: **How is admitted work composed and executed?**

### 7.5 Verified High-Risk Transformations

Use machine-checkable evidence for semantic risk such as rewrite, normalization, state invariants, refinement, and certificates.

### 7.6 Aggressive Lowering

Consume high-level knowledge in build, generation, admission, and control-plane stages so the hot path returns toward ordinary C.

## 8. DataBind / CMeta / CFlow / Lean: Promise / Know / Structure / Trust

This is not one giant framework. The layers answer different questions.

### 8.1 DataBind — Promise

DataBind builds Contract IR and answers:

- What data is exchanged?
- What operation is promised?
- What messages/events exist?
- Which capabilities form one component?

It does not own HTTP sockets, plugin loading, a WASM engine, or the CFlow scheduler.

### 8.2 CMeta — Know

CMeta builds Native Semantic IR and answers:

- What is this C type?
- What is this native function?
- Which parameter is IN / OUT?
- What ownership/capability is known?
- What semantic identity survives representation boundaries?

### 8.3 CFlow — Structure / Execute

CFlow builds Execution IR and answers:

- How are computations related?
- Which execution shapes are admitted?
- How can work be normalized, scheduled, optimized, or lowered?

### 8.4 Lean — Trust selected semantic claims

Lean owns no runtime. It asks selected semantic questions:

- Does this rewrite preserve observation?
- Does this transition preserve the invariant?
- Does this refinement preserve the promised result?

The complete relationship is:

~~~text
DataBind Contract IR
        +
CMeta Native IR
        ↓
compiler / binding
        ↓
generated plans/adapters
        ↓
optional CFlow Execution IR
        ↓
verified transformation where needed
        ↓
ordinary C execution
~~~

All of these serve ordinary C instead of replacing it.

## 9. Modern C and the Final Design Checklist

Language comparisons often ask whether C can have lambda, generic, stream, or actor. This book cares more about another question:

Can a C system maintain less duplicated knowledge while preserving explicit ownership, stable ABI, predictable cost, and an ordinary toolchain? So “modern” is not more syntax sugar; it is stronger semantic sharing, earlier error detection, clearer ownership, less trusted duplication, more verifiable transformation, and simpler execution. That is Modern C in a systems-engineering sense.

### 9.1 Final Design Checklist for the Reader

For a new C systems problem, ask in this order:

1. What is the Plain C baseline?
2. What is the real pain point?
3. Is the duplication code or knowledge?
4. Which facts are already stable?
5. Which module owns those facts?
6. Is semantic identity required?
7. Are ownership/lifetime/capacity/failure explicit?
8. Which errors can move earlier?
9. Which dynamic behavior is genuinely necessary?
10. What are the observable semantics?
11. Which laws/invariants deserve formalization?
12. Which real implementation behavior does the theorem authorize?
13. What is the C representation?
14. Does the Multi-TU/ABI/install boundary hold?
15. Can the abstraction disappear from the hot path?
16. How will performance/memory/concurrency cost be measured?
17. Is ordinary C still simpler?

If the answer to question 17 is **Yes**, then use ordinary C. That is a completely correct result.

## 10. What a Modern C Book Should Ultimately Teach

The goal is not to memorize a macro API. It is to develop the following capabilities.

### 10.1 Recognize Stable Knowledge in Code

Know what should remain ordinary code and what has become stable enough to be schema/type/relation.

### 10.2 See Ownership Beneath a High-Level API

When looking at lambda, stream, actor, or rpc, still ask: Who owns? Who borrows? What is capacity? How does failure happen? What is lifetime? What reaches the hot path?

### 10.3 Use Formal Proof as Design Feedback

Not “write code, then check a theorem box.” Instead:

~~~text
proof obligation
    ↓
discover design ambiguity
    ↓
change API/runtime contract
~~~

### 10.4 Look for Lowering in Every Abstraction

Whenever a layer is added, ask:

How does it become simple C again?

### 10.5 Stay Honest Through Measurement

Do not use zero-cost, faster, or scalable as design adjectives. Let measurements decide.

## 11. Summary

CMeta techniques share a process: declarations record reusable facts, type and contract checks generate or select calls, and applications manage execution state. Macro expansion, call adaptation, graph rewriting, and asynchronous progress each have distinct inputs, outputs, and correctness conditions; sharing descriptors does not merge those responsibilities. For a new application, first write the ordinary C baseline and its failure behavior, then identify facts worth sharing. Specify the generation algorithm or state transitions, derive preconditions and invariants, and check the implementation through compilation, execution, or proof. Retain the added mechanism when these steps establish a maintenance or execution benefit.
