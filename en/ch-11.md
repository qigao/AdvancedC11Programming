# Chapter 12: Actors: Mailboxes, Serialized Mutation, and Object Lifetime

Several producers may send events to one connection machine without acquiring permission to mutate its state or dereference it after destruction. Actor adds lifecycle control, independently retained producer references, and shutdown around Machine Instance. It reuses the preceding transition semantics while adding concurrent admission and resource control.

## 1. Owner and Producer References

The pinned public handles are opaque:

~~~c
typedef struct cflow_actor {
    void *impl;
} cflow_actor;

typedef struct cflow_actor_ref {
    void *impl;
} cflow_actor_ref;
~~~

`cflow_actor` retains the root reference and controls the runtime. `cflow_actor_ref` is an independently retained producer capability. Both require zero initialization and their acquisition/release APIs. Assigning an owning handle into another variable and releasing both is not reference retention.

A **capability** here is a protocol-governed handle authorizing an operation. It is not an address from which liveness can be guessed. After owner destruction, retained references can safely report STALE because the control block survives until the final producer reference is released.

This fragment assumes successful initialization of `actor`. Publishing references to producers needs application synchronization. Do not release a handle while another thread is using that same handle.

~~~c
cflow_actor_ref producer = {0};
cflow_actor_ref second_producer = {0};

if (!cflow_actor_ref_acquire(&actor, &producer))
    return false;
if (!cflow_actor_ref_retain(&producer, &second_producer)) {
    cflow_actor_ref_release(&producer);
    return false;
}

/* Publish each reference to its producer with proper synchronization. */
/* After both producers have stopped using their respective handles: */
cflow_actor_ref_release(&second_producer);
cflow_actor_ref_release(&producer);
~~~

## 2. Sending Establishes Responsibility at Commit

`cflow_actor_ref_try_send` copies an event into a fixed-capacity mailbox under lifecycle admission control. This pseudocode describes the ordering; the gate implementation must satisfy the public nonblocking admission contract.

~~~text
try_send(ref, event):
    safely access the retained control block
    if ref is stale: return STALE
    if lifecycle is not RUNNING: return its specific rejection
    require valid event identity, payload type, and storage
    require mailbox capacity
    atomically admit one bounded payload copy
    return ACCEPTED
~~~

Stale classification precedes payload interpretation, preventing a revoked capability from being used to infer schema details. Lifecycle checks and mailbox commit must share synchronization rules. Observing RUNNING, releasing protection, then appending unconditionally after stopping is invalid.

Rejection leaves the queue unchanged. ACCEPTED appends exactly one event; it neither executes a Machine action nor takes ownership of the input view. The pinned API borrows the view during the call and saves a bounded trivial payload copy on success. Copying pointer bytes does not extend pointee lifetime.

## 3. Queue Invariants with Multiple Producers

For capacity `K` and queue `Q`, admission maintains `0 <= |Q| <= K`. Rejection leaves `Q` untouched. Acceptance checks `|Q| < K` and appends one element, preserving the bound. The check and append must appear as one commit to competing producers.

FIFO means mailbox commit order, not wall-clock call-start order. Producer P can enter first and pause before commit while R commits first. Consuming R's event first still respects FIFO. Verification must record commits rather than infer ordering from thread logging.

| Send result | Queue change | Producer response |
|---|---|---|
| ACCEPTED | Append once | End borrowing of the original input view |
| FULL | None | Apply an explicit wait, rejection, or retry policy |
| NOT_STARTED, STOPPING, STOPPED, FAILED | None | Handle the specific lifecycle condition |
| STALE | None | Release the stale reference; it cannot address the old runtime |
| TYPE_MISMATCH or INVALID_ARGUMENT | None | Correct the event contract or storage |

The library send path does not wait for space, resize, retry, overwrite, or silently drop. An application retry policy needs its own deadline and duplication rules; only a submission known to have been rejected can be retried as the same unsent event.

## 4. Serialized Mutation Reuses Machine Semantics

Actor owns the Machine Instance, mailbox, output identity graph and Subscription, and lifecycle control block. It borrows the immutable Machine, SerialExecutor, concurrent Scheduler, type descriptions, and callback contexts. The executor serializes transitions; the scheduler advances the subscription.

~~~text
drain_accepted_work:
    take the next admitted event from the instance mailbox
    perform the Machine selection, staging, and commit protocol
    expose each committed observation through the owned subscription
    settle the event before advancing the serialized state owner
~~~

This is a division of responsibilities, not another Actor-specific transition algorithm. A **single mutable owner** means at most one transition has permission to mutate a state at a time. It does not require a dedicated operating-system thread per Actor. Producer threads perform admission without running connection actions on their send stacks.

## 5. Lifecycle Closes Admission First

| Lifecycle | New events | Subsequent behavior |
|---|---|---|
| START | Rejected | Explicit start enters RUNNING |
| RUNNING | Accepted subject to type and capacity | Process work or begin stopping |
| STOPPING | Rejected | Close the instance and settle in-flight work |
| STOPPED | Rejected | Terminal; cannot restart |
| FAILED | Rejected | Retain failure and settle resources; no implicit restart |

`cflow_actor_request_stop` closes admission before closing the owned instance. Machine close cancels queued events while preserving its in-flight commit contract. Actor stopping does not guarantee execution of every queued message. An application needing “process everything before stopping” requires an explicit acknowledgement protocol.

FAILED is an **absorbing state**: ordinary later operations do not return it to running. A **supervisor** may explicitly create a new instance or retry requests, but this is application policy. Old references cannot disguise a new runtime identity as uninterrupted execution.

## 6. Stale References and Destruction

Adding a generation number to a raw pointer does not prevent use-after-free: reading the generation may itself dereference freed memory. Independently retained control blocks make safe STALE reporting possible.

~~~text
destroy_owner:
    serialize owner-side control operations
    mark retained producer references stale
    close the owned instance and subscription synchronously
    clear the owner handle
    release the root reference
    reclaim the control block only after the last producer releases
~~~

**Quiescence**, introduced in Chapter 9, means in-flight callbacks that can access a resource have ended, not merely that a stop flag was set. Borrowed Machine, executor, scheduler, and contexts must survive until destroy returns. Executor and scheduler must remain operational during that interval so Actor can settle.

Subscriber callbacks run without the Actor gate held, allowing self-send and stop requests. They must not wait for or destroy the Actor: those operations depend on the current callback finishing and would create self-waiting.

## 7. Composing the Formal Models

`send_accepted_only_running` restricts acceptance to RUNNING. `send_accepted_appends_once` proves one append, and `send_rejected_preserves_queue` proves queue preservation. The reasoning splits on liveness, lifecycle, and mailbox admission: failure branches return the original queue; the sole success branch uses the mailbox's valid append.

`accepted_handoff_refines_machine` relates accepted handoff to the original Machine semantics instead of inventing another commit meaning. `requestStop_cancels_pending` and terminal-state theorems constrain stopping and failure. See [Proofs/Actor.lean](https://github.com/qigao/salts/blob/a650262031e9b3e5f11a227a7911a75db9ae1fb8/formal/cmeta_cflow_calculus/CMetaCFlowCalculus/Proofs/Actor.lean).

These are model theorems. C control-block retention, concurrent admission, callback lifetimes, and scheduler progress require implementation evidence. [actor.h](https://github.com/qigao/salts/blob/a650262031e9b3e5f11a227a7911a75db9ae1fb8/cflow/include/cflow/actor.h) specifies the real ownership contracts.

## 8. Verifying the Connection Actor

Place Chapter 11's Machine in a capacity-two Actor and send well-typed events from multiple producers. Compare accepted and rejected counts with mailbox commit order, verify one transition at a time, and attempt sends after STOPPING to confirm closed admission.

Retain an independent producer reference, destroy the owner, then send both a valid event and one with a bad payload. Both should first report stale identity. Release the remaining reference and use memory instrumentation to verify final control-block reclamation. Tests must obey owner-side serialization rather than race destruction against forbidden owner-handle access.

As an exercise, explain why unlimited immediate retry on FULL can consume CPU without guaranteeing progress. Design a deadline-based application policy that retains the property that one successful admission represents exactly one event.

## 9. Summary

Actor adds revocable producer capabilities, lifecycle checks, and concurrent mailbox admission while Machine retains transition meaning. Safe sending requires a retained control block; orderly destruction closes admission before settling work. FIFO describes commit order, and single ownership describes mutation authority. Neither promises call-start ordering or a dedicated thread.
