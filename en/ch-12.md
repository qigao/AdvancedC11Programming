# Chapter 13: Engineering Boundaries — ABI, Multi-TU, Semantic Identity, and Installable C Libraries

> **Do not begin this chapter with “ABI matters.”**
>
> Start with two Translation Units and let pointer equality fail. Engineering boundaries require Multi-TU tests, installed consumers, real DSOs, versioned ABI, and sanitizer/stress—not merely “it links inside the source tree.”

---

## 1. Semantic Identity Across Translation Units

Current CMeta explicitly separates semantic identity from descriptor-object address.

A header-local type can be written as:

~~~c
/* user_meta.h */

typedef struct User {
    int id;
} User;

static const cmeta_type_identity User_identity =
    CMETA_TYPE_ID_ATOM_INIT("book.User");

static const cmeta_type_desc User_desc = {
    .name = "User",
    .size = sizeof(User),
    .align = _Alignof(User),
    .kind = CMETA_T_OBJECT,
    .pointee = NULL,
    .traits = NULL,
    .identity = &User_identity
};

static inline const cmeta_type_desc *
User_type(void)
{
    return &User_desc;
}
~~~

TU A:

~~~c
const cmeta_type_desc *type_from_a(void)
{
    return User_type();
}
~~~

TU B:

~~~c
const cmeta_type_desc *type_from_b(void)
{
    return User_type();
}
~~~

Each Translation Unit owns its own header-local representation.

The test should allow different descriptor addresses while requiring semantic equality:

~~~c
const cmeta_type_desc *a = type_from_a();
const cmeta_type_desc *b = type_from_b();

assert(a != b);

assert(cmeta_type_equal(a, b));

assert(cmeta_type_identity_equal(
    cmeta_type_identity_of(a),
    cmeta_type_identity_of(b)));
~~~

Do not compare:

~~~c
a->identity == b->identity
~~~

because identity objects themselves may also be TU-local representations.

Core rule:

| Object | Meaning |
|---|---|
| descriptor pointer | descriptor representation identity |
| `cmeta_type_identity` | structural semantic identity |
| `cmeta_type_equal()` | TypeDesc semantic equality authority |

---

### 1.1 Apply the Same Test Shape to FunctionDesc

Function metadata cannot use address identity either:

~~~c
const cmeta_function_desc *fa =
    function_from_a();

const cmeta_function_desc *fb =
    function_from_b();

assert(fa != fb);

assert(cmeta_function_desc_equal(
    fa, fb));
~~~

Current `cmeta_function_desc_equal()` compares name, return-type semantic equality, parameter count/name/type/flags, result flags, effects, and properties. If exact execution carriers are also part of the boundary contract, compare `cmeta_function_abi_desc_equal()` separately; FunctionDesc semantic equality must not silently stand in for FunctionAbi equality.

---

### 1.2 DataBind Contract Identity Is Also Not an Address

Two independent generated consumers may contain the same:

~~~text
service UserService {
    GetUser: GetUserRequest -> GetUserResponse;
}
~~~

Host and Plugin descriptors may live at different addresses.

Compare qualified contract id, contract version, operation identities, and logical request/response types.

Therefore **Contract IR identity != descriptor address**.

## 2. DSO Lifetime and Plugin ABI

Do not qualify Plugin only inside one executable.

Use:

~~~text
host executable
    |
    | dlopen / LoadLibrary
    v
plugin DSO
    |
    +-- manifest
    +-- FunctionDesc exports
    +-- Interface {self,vtable}
~~~

Host code uses the current Salts 2.1 Plugin runtime:

~~~c
cmeta_plugin_ref ref = {0};
cmeta_plugin_lease lease = {0};
const cmeta_plugin_manifest *manifest = NULL;

assert(
    cmeta_plugin_registry_load(
        &registry,
        plugin_path,
        &ref) == CMETA_PLUGIN_OK);

assert(
    cmeta_plugin_registry_start(
        &registry,
        ref) == CMETA_PLUGIN_OK);

assert(
    cmeta_plugin_registry_acquire(
        &registry,
        ref,
        &lease,
        &manifest) == CMETA_PLUGIN_OK);
~~~

`acquire` borrows DSO-owned manifest/export/FunctionDesc/FunctionAbi/interface/code from a **STARTED plugin**. A lease is not necessarily one lease per call; it must cover every operation that may still dereference those DSO-owned objects.

The test validates contract identity, exact ABI-epoch admission, borrow lifetime, DSO code lifetime, generation, and quiescent unload.

---

### 2.1 Interface/vtable Borrow Must Block Unload

If the host owns:

~~~c
cflow_executor exec;
~~~

and exec.vtable points into Plugin code, then:

~~~text
lease > 0
or callback in flight
──────────────────────
unload = BUSY
~~~

The real test is a **lifetime-qualification sequence**:

~~~text
acquire interface lease
attempt unload -> CMETA_PLUGIN_BUSY
release lease
request stop / reach quiescent
unload -> CMETA_PLUGIN_OK
old ref -> CMETA_PLUGIN_STALE
~~~

This is stronger than prose saying “vtable lifetime matters.”

---

## 3. Installed/Public Contract Gate

Source-tree linking may accidentally see private paths and targets.

Qualification must follow the full **installed-consumer qualification pipeline**:

~~~text
build library
  ↓ install artifact
install to fresh prefix
  ↓ configure consumer
independent project
  ↓ package discovery
find_package(...)
  ↓ public compile contract
include only public headers
  ↓ public link contract
link only public targets
  ↓ runtime smoke test
run
~~~

Any hidden source-tree dependency should fail here.

---

### 3.1 Current Plugin ABI Uses an Exact Epoch, Not Readable-Prefix Negotiation

`cmeta_plugin_manifest` does contain:

~~~c
uint32_t struct_size;
uint32_t abi_version;
~~~

but the current Salts Plugin contract is **not** “compatible whenever a prefix is readable.”

It requires:

~~~text
manifest.struct_size == current layout
manifest.abi_version == CMETA_PLUGIN_ABI_VERSION
        |
        v
admit

otherwise
        |
        v
reject / rebuild plugin
~~~

The reason is that Plugin exports directly expose current CMeta Reflection layouts:

~~~text
FunctionDesc
FunctionAbi
InterfaceDesc
Type/Data/trait pointers
exact invoke code
~~~

The Plugin ABI epoch therefore covers both publication layout and the Reflection ABI transitively exposed through exports.

The current design deliberately has no:

~~~text
old-layout retry
ABI negotiation
readable-prefix compatibility
tail compatibility
fallback adapter
~~~

> **Plugin uses exact epoch + fail-fast rebuild, not cross-epoch struct compatibility.**

Other provider ABIs later in this chapter may legitimately use a size-versioned readable prefix, but that extension strategy must not be projected onto the current Plugin manifest.

---

### 3.2 Evidence Matrix

| Claim | Real gate |
|---|---|
| semantic identity survives TU boundary | two-TU test |
| FunctionDesc survives duplicate representation | independent descriptor test |
| DataBind contract survives codegen boundary | cross-generated contract test |
| Plugin ABI survives DSO | installed host + real shared library |
| vtable borrow blocks unload | live lease + BUSY unload test |
| old ref cannot call recycled plugin | generation STALE test |
| public package is complete | fresh-prefix installed consumer |
| memory/lifetime is safe | ASan/UBSan + stress |
| Plugin ABI epoch mismatch fails closed | wrong epoch/layout -> load rejection |

The remaining case studies and ABI rules in this chapter should be read as explanations of these executable gates.

## 4. Semantic Identity Case Studies

In a single Translation Unit the tempting implementation is:

~~~c
if (a_type == b_type) {
    /* same type */
}
~~~

If every descriptor comes from one global object, this may appear correct for a long time.

But once we have header-local generated descriptors, static archives embedded into multiple DSOs, plugin/shared-library boundaries, or independent translation units, the same semantic type may have several descriptor objects with different addresses but identical meaning. Therefore **pointer equality ≠ semantic type equality**.

This is Multi-TU/DSO correctness, not abstract purity.

### 4.1 Current CMeta Explicitly Separates Identity from Descriptor

The current type descriptor contains name, size, align, kind, pointee, traits, and identity, while `cmeta_type_identity` can express:

~~~text
ATOM(stable id)
POINTER(base identity)
CONST(base identity)
APPLY(generic constructor, arguments...)
~~~

Generic constructor itself also has stable_id, display_name, min/max arity, and category.

So `Pair<int, long>` has the following structural semantic identity:

~~~text
APPLY(
    constructor = "cmeta.Pair",
    args = ["cmeta.int", "cmeta.long"]
)
~~~

rather than the address of one Pair descriptor.

### 4.2 Structural Identity Has a Real Multi-TU Test

The current test does not compare two pointers created in one source file. A peer Translation Unit returns an independently constructed identity for local `Pair<A,B>` and peer `Pair<A,B>`.

and validates:

~~~text
local identity address != peer identity address
local constructor address != peer constructor address

but

cmeta_type_identity_equal(local, peer) == true
~~~

This is the right kind of evidence for this chapter:

> **make two truly independent compilation units produce different representations, then verify semantic equality.**

### 4.3 Custom Trait Descriptor Must Also Stay Semantically Consistent Across TUs

Current CMeta tests also cover a custom `owned_int` descriptor in TU A and a peer descriptor in TU B.

Again, the goal is not descriptor pointer equality.

The required result is the same type semantics, the same trait contract, and valid cross-TU behavior.

Otherwise Traits would be only a header-demo mechanism.

---

### 4.4 Callable Identity: Function Address Is Not One Universal Answer Either

Callable is more complex than Type because it may include:

~~~text
canonical raw target
adapter
generator
capture
effects
properties
signature
~~~

So Callable identity must first ask:

> Which dispatch representation is authoritative?

The current implementation distinguishes `CANONICAL_RAW` and `ADAPTER`:

| Dispatch representation | Identity authority |
|---|---|
| canonical raw | authoritative raw target across translation units |
| adapter | adapter/generator pointers + capture bytes |

### 4.5 Why Canonical Raw Works Across TUs

Suppose two Translation Units produce different wrapper/adapter addresses but both resolve to the same authoritative raw C function. Semantic callable identity should not fail because wrappers differ.

Current tests cover canonical callable identity across translation units by raw target. This is consumed by Graph structural equality, Optimizer duplicate detection, AOT Graph/Stage matching, and Certificate checking.

Callable identity is therefore not a local helper.

It is part of compiler/control-plane correctness.

### 4.6 Capturing Callable Must Include Capture in Identity

For:

~~~text
bind(multiply, 10)
bind(multiply, 20)
~~~

raw/adapter code may be identical, while captures differ.

They are not the same callable.

So the rule is neither “always compare pointer” nor “never compare pointer.”

It is:

> **define equality according to the semantic authority of the representation.**

---

### 4.7 Static / Shared Library: Duplicate Globals Must Not Become Semantic Accidents

The current CMeta CMake setup contains an important engineering choice.

The static CMeta archive uses `C_VISIBILITY_PRESET hidden`.

The reason is not merely “export fewer symbols.”

The comment explicitly notes that a static CMeta archive may be embedded by Core and multiple bridge DSOs; each image may keep its immutable descriptors/helpers local; and type compatibility is semantic, not address-based.

This is a mature ABI principle.

If semantic correctness depends on one process-wide unique descriptor address, then embedding one static archive into two DSOs is inherently fragile.

The current direction is a **semantic identity rule**: duplicate representation objects may exist, while semantic identity must still agree. Symbol visibility becomes an encapsulation/optimization issue, not the source of type semantics.

## 5. Public / Versioned ABI Contracts

A common C-library mistake is the false implication:

> **struct is in public header ⇒ every field is caller contract**

That is false. C visibility and semantic ownership must remain separate.

Chapter 7 already kept Graph as concrete IR for introspection, while Subscription / Actor live owners use opaque handles.

Public fields should be understood in three categories.

### 5.1 Stable Contract Fields

Examples include configuration rows, status/result structs, documented method pointers, and semantic enum values. Callers may initialize/read them according to documentation.

### 5.2 Read-Only Introspection

Examples include Graph, Node, Edge, Subgraph, Plan input/output type, and stats. Visibility exists for diagnostics, verification, and advanced tooling.

not to let callers bypass builder mutation.

### 5.3 Internal Carrier

For example, `void *impl` has no additional semantic meaning even when visible in a public struct.

Callers must not dereference, serialize, compare as identity, copy a live owner, or use `sizeof/offsetof` as a persistence protocol.

The ABI philosophy should state:

> **C visibility is not semantic ownership.**

---

### 5.4 Versioned Provider ABI: Extensible Structs Need Admission Boundaries

A dangerous pattern for extensible provider/vtable APIs is assuming caller and library always share exactly the same struct layout.

Current CMeta data descriptor/provider uses fields such as `struct_size` and `abi_version`.

A checked façade can first validate provider ABI version, minimum struct prefix size, storage type identity, ownership/layout contract, and required operations before using optional appended fields.

This pattern works for descriptors, provider ops, plugin ABI, and extension interfaces.

but must obey:

1. old prefix meaning must not silently change;
2. appended fields need version/size admission;
3. optional capability and required capability remain distinct;
4. current field presence must not imply future ABI guarantees;
5. public enum/status numeric values are ABI too.

---

### 5.5 CFlow SOVERSION: ABI Version Is a Real Library Artifact

The current CFlow library snapshot has `version = 4.1.0` and `SOVERSION = 4`.

Windows shared builds also encode ABI major in the output name.

This matters.

A library exposing public structs, enum values, function signatures, calling conventions, symbol names, or ownership contracts should not hide ABI breaks only in Git history. It needs at least a library ABI major, package version, and release compatibility policy.

Of course:

> **SOVERSION does not automatically make an ABI stable.**

It merely gives incompatible boundaries a way to be expressed.

Real stability still comes from public API discipline and qualification.

---

### 5.6 Compile-Time Configuration Is Also Part of ABI

CMeta's finite signature universe and CFlow configured limits can enter the public compilation surface.

For example, CFlow exports `CFLOW_MACHINE_MAX_STATES`, `CFLOW_MACHINE_MAX_EVENTS`, `CFLOW_MACHINE_MAX_GUARDS`, `CFLOW_MACHINE_MAX_ACTIONS`, `CFLOW_MACHINE_MAX_TRANSITIONS`, and related limits as PUBLIC compile definitions.

Consumer compilation must therefore see configuration consistent with the library contract.

Likewise, CMeta user relation/type lists are shared compile-time configuration.

The documentation explicitly requires:

> affected translation units must see consistent callable ABI/configuration.

Multi-TU correctness includes more than the same struct declaration. It includes the same finite signature universe, compile-time configuration, and public feature/limit contract.

If different TUs use different relation universes while exchanging callables/descriptors, a semantic bug can become an ABI bug.

---

### 5.7 Header / Source Boundary: Which Meta Must Stay at the Call Site?

A Modern C meta library should become neither everything header-only nor everything hidden in `.c`.

The right boundary depends on where the necessary information exists.

### 5.8 What Must Remain in Headers / at the Call Site

Typical examples include `_Generic` selection, compile-time type assertions, finite macro specialization, typed-wrapper generation, and call-site C type inspection, because only the compiler at the call site knows the actual static C type.

### 5.9 What Belongs in the Compiled C Library

Examples include container algorithms, Graph mutation/validation, Subscription runtime, Executor, Machine/Actor runtime, type-identity comparison, optimizer, plan compiler, and certificate checker.

These do not need to be copied into every Translation Unit merely because the project uses Meta.

Therefore:

> **header-only typed façade does not imply header-only implementation.**

This matters for code size, ABI, compile time, and debugging.


### 5.10 Compiler Capability Is a Public Engineering Boundary

Chapters 1 through 3 use finite preprocessing, native typeof, same-type checks, zero-argument variadics, cleanup attributes, and related compiler facilities.

These cannot disappear from the engineering story as mere implementation details.

If a public header provides different guarantees depending on compiler or language mode, the consumer compilation environment is part of the contract.

The correct model is:

~~~text
semantic requirement
        |
        v
compiler capability query
        |
   +----+----+
   |         |
supported   unsupported
   |         |
   v         v
strong      explicit weaker contract
surface     or compile failure
~~~

Not:

~~~text
feature unavailable
        |
        v
unsafe cast / guessed fallback
        |
        v
pretend the guarantee is unchanged
~~~

Qualification should distinguish questions such as:

| Capability | Engineering question |
|---|---|
| native typeof / same-type | Does this C/C++ compiler mode really provide the required type guarantee? |
| zero-argument variadics | Is the build in an admitted standard VA_OPT mode? |
| cleanup attribute | Does this backend actually provide lexical cleanup support? |
| section / used attributes | Is the ELF / COFF / Mach-O backend contract explicit? |
| unique counter | Is it used only for TU-local naming rather than semantic identity? |

A cross-compiler gate should therefore ask more than “do GCC, Clang, and MSVC compile?”

It should ask:

~~~text
same semantic contract?
+
capability differences explicit?
+
unsupported paths fail honestly?
+
installed public headers preserve the documented guarantee?
~~~

This is fail-fast applied to compiler abstraction.

> **Portability does not mean pretending all compilers are identical. It means containing differences behind an explicit, testable capability boundary.**

## 6. Generated Artifact Ownership and Packaging

The book already uses generated C headers such as `builtin_signature_manifest.h` and `builtin_operator_policy.h`; artifacts of this kind should be generated one-way from formal sources/generators and checked by CI.

The engineering rule must be strict:

| Artifact | Role |
|---|---|
| formal model | authoritative source |
| generated header | checked-in build artifact |
| manual edit generated header | forbidden |

Ordinary consumer builds **do not require Lean**. CI / semantic development uses `generator --check` to verify no artifact drift.

This gives a reproducible package, ordinary C consumer, single source of truth, and reviewable generated diff.

---

### 6.1 Install / Export: Linking in the Source Tree Is Not Enough

The edition Salts snapshot uses a normal CMake package/export boundary with SaltsConfig.cmake, SaltsConfigVersion.cmake, SaltsTargets.cmake, and the Salts:: namespace.

CMeta / CFlow export as **Salts::CMeta** and **Salts::CFlow**, together with public headers, library/archive/runtime artifacts, package config, and target exports.

A consumer should use:

~~~cmake
find_package(Salts CONFIG REQUIRED)

target_link_libraries(app PRIVATE
    Salts::CMeta
    Salts::CFlow)
~~~

This matters far more than relying on source-tree add_subdirectory, source-tree include paths, or linking an arbitrary .a file.

because the install boundary exposes:

~~~text
missing public dependency
wrong include interface
private header leak
missing transitive target
wrong compile definition export
bad symbol visibility
source-tree-only path
~~~

### 6.2 CFlow Public Dependencies Must Be Exported Through Target Contract

Current CFlow link contract includes:

~~~text
PUBLIC
    Salts::CMeta
    Salts::NativeIO
    Salts::Platform

PRIVATE
    Salts::Concurrency
~~~

This is not CMake aesthetics.

It says:

> which dependencies are exported contract for external consumers of CFlow public headers/symbols, and which are implementation details.

If a PRIVATE dependency leaks into public ABI without export, source-tree builds may succeed while installed consumer linking fails.

### 6.3 Public Header Install Must Exclude Private Headers

Current CFlow installs public cflow headers while explicitly excluding plan_internal.h and relation_exec.h.

This boundary matters:

> **a header existing in the repository does not make it part of the SDK.**

If a public header includes a private one accidentally, installed builds expose the mistake quickly.

---

### 6.4 Installed Consumer Qualification: The Gate Closest to a Real User

This book recommends installed-consumer testing as a formal gate rather than a manual pre-release smoke test.

A strong flow is:

~~~text
clean source checkout
    ↓
configure/build/test Salts
    ↓
install into empty prefix
    ↓
new independent consumer source tree
    ↓
find_package(Salts CONFIG REQUIRED)
    ↓
link only exported Salts::* targets
    ↓
include only installed headers
    ↓
build
    ↓
run
~~~

The consumer should cover at least:

- CMeta type/traits/callable;
- CFlow Graph/Stream;
- Multi-TU use;
- static build;
- shared build where supported;
- C/C++ header compatibility.

Rules: no source-tree include path, no build-tree target, no undeclared private library, and no generated source file copied manually.

Only then can we claim:

> **the installable library is not just documentation; a user can consume a real SDK contract.**

## 7. Qualification Across Boundaries

A weak Multi-TU test only proves `foo.c calls bar.c`; that is not enough for Meta identity.

A strong test deliberately makes two TUs own independent representations.

### 7.1 Type Identity Test

~~~text
TU A:
    independently constructs Pair<A,B> identity

TU B:
    independently constructs Pair<A,B> identity

assert:
    addresses differ
    constructors may differ
    semantic equality true
~~~

The current CMeta implementation already has such a peer test.

### 7.2 Callable Identity Test

~~~text
TU A:
    canonical callable wrapper A

TU B:
    canonical callable wrapper B

assert:
    wrapper representation can differ
    authoritative raw target identity agrees
~~~

Current tests cover this too.

### 7.3 Generated Configuration Test

Also test that the shared configuration header is included consistently in TU A/TU B and that callable-signature ABI agrees across both, then add negative compile/link tests where possible:

~~~text
intentionally inconsistent configuration
    → fail fast
~~~

If the toolchain cannot diagnose reliably, document the configuration as explicitly unsupported instead of guessing at runtime.

---

### 7.4 Cross-Compiler: Core Semantics Must Not Depend on Accidental Extensions

CMeta can rely on C11 `_Generic`, the preprocessor, `_Static_assert`, and standard alignment/type rules, and configure MSVC's conforming preprocessor mode where required.

But the book keeps one principle:

> **compiler extensions may optimize an implementation, but must not be the only basis of the semantic model.**

Extensions such as GNU statement expressions, `typeof`, or compiler-specific section tricks may be optional fast paths.

Core type relations, callable semantics, and ABI contracts should still be expressible using the official mechanisms of supported target compilers.

Cross-compiler CI is not merely “the syntax compiles everywhere.” It should validate the same declared semantics, ownership/error contract, and installed API shape across target compiler families.

---

### 7.5 ABI Qualification: Do Not Only Compare `sizeof(struct)`

ABI tests have at least four layers.

### 7.6 Compile ABI

Check that public headers compile as C11 and from supported C++ mode, macros do not depend on include accidents, and generated headers are self-consistent.

The current CFlow implementation already has public/header C++ compile tests; this category of gate should keep expanding.

### 7.7 Link ABI

Check that public symbols exist, calling conventions match, transitive dependencies are exported, and static/shared consumers link.

This is where installed consumers matter.

### 7.8 Semantic ABI

Even if function signatures stay identical, changes such as FULL suddenly dropping, CLOSED becoming retryable, Actor stale refs becoming INVALID_ARGUMENT, or Graph mutation no longer changing version are breaking behavior.

Therefore:

> **status meaning, ownership, lifecycle, ordering, and fallback are part of semantic ABI.**

### 7.9 Data ABI

For structs explicitly promised across binary boundaries, prefix fields, version, `struct_size`, enum values, alignment, and ownership of pointed data must be versioned intentionally. Opaque owners such as `void *impl` exist precisely to keep internal layout out of ABI.

---

### 7.10 Fail Fast Across Boundaries: The Later the Error, the More Expensive It Is

This is not a runtime pipeline; it is **diagnostic-stage ordering**. Earlier detection is cheaper.

~~~text
compile-time
    ↓ earlier is cheaper
build-time
    ↓
install/package-time
    ↓
link-time
    ↓
admission-time
    ↓
execution-time
~~~

Rule:

> **if the same error can be found earlier, do not postpone it to a later boundary.**

| Error | Earliest proper boundary |
|---|---|
| unsupported TypeFunction row | compile-time |
| invalid Machine schema | build-time |
| generated manifest drift | CI/generator check |
| missing public link dependency | installed consumer link |
| wrong Event payload | admission |
| I/O failure | execution |

Turning every error into a runtime error string is not “a simpler API.”

It only transfers diagnostic cost to the user.

## 8. What We Learned

Chapter 13 brings all earlier “advanced” capability back into ordinary C engineering reality.

A mature Modern C abstraction requires all of these to hold:

~~~text
semantic identity
    does not depend on representation address

Multi-TU
    sees compatible finite configuration

public ABI
    separates stable/read-only/internal fields

generated artifacts
    have one authority

ordinary build
    does not require Lean

static/shared libraries
    do not rely on duplicate-global coincidence

install/export
    publishes real dependency contracts

external consumer
    builds only from installed SDK

cross-compiler
    preserves core semantics

status/ownership/lifecycle
    are treated as semantic ABI
~~~

The edition Salts snapshot already contains structural type identity, cross-TU identity tests, cross-TU callable tests, CMake install/export, `Salts::*` imported targets, CFlow SOVERSION, public/private install headers, generated-header CI checks, and public-header compile checks.

Mature qualification should continue to treat independent installed consumers, static/shared matrices, negative ABI/config tests, platform/toolchain matrices, and release compatibility as formal gates.

Lean's role is also clear here.

It can help define semantic identity, finite schema, generated manifests, and protocol invariants; linker, loader, symbol visibility, CMake package export, compiler ABI, and shared-library resolution must be validated with real toolchains.

This is not a weakness of formal methods.

It is:

> **the right question should be answered with the right evidence.**

The next chapter stops adding foundational mechanisms and asks the opposite question:

> **When are these abstractions not worth using at all? When is one loop, one function pointer, one switch, or one direct link the better design?**

That is the role of Restraint: continue abstracting only when the stable duplication removed is worth the long-term cost introduced.
