# Chapter 14: Choosing Techniques: When Ordinary C Is Sufficient

Descriptors, generators, and runtime objects add maintenance obligations. Choosing a CMeta technique requires comparing the duplicate facts it removes with the new type, capacity, lifetime, and build constraints it introduces. A bounded ordinary C function provides a baseline for deciding when macros, reflection, or execution objects are justified.

## 1. A Bounded Filter/Map Function

This ordinary C function requires `<stdbool.h>` and `<stddef.h>`. It accepts at most one thousand integers in `[-100, 100]` and writes even squares to a `long` array. Nonempty arrays must be valid, and input, complete output storage, and the object at `written` must be disjoint. These are caller preconditions; null checks cannot prove object validity.

~~~c
bool book_copy_even_squares(
    const int *xs, size_t n,
    long *out, size_t capacity, size_t *written)
{
    if (written == NULL || n > 1000 || capacity < n)
        return false;
    if (n != 0 && (xs == NULL || out == NULL))
        return false;
    for (size_t i = 0; i < n; ++i)
        if (xs[i] < -100 || xs[i] > 100)
            return false;

    size_t m = 0;
    for (size_t i = 0; i < n; ++i) {
        int x = xs[i];
        if (x % 2 == 0)
            out[m++] = (long)x * x;
    }
    *written = m;
    return true;
}
~~~

The first pass checks the whole domain before any output write, so invalid input leaves no partial squares. Requiring `capacity >= n` is stronger than the eventual retained count but establishes enough space before running the predicate. A precise smaller-capacity interface could count first, at the cost of another traversal and a requirement that input remain unchanged between passes.

## 2. Deriving Correctness from the Loop Invariant

Before processing index `i` in the second loop, `0 <= m <= i` and the first `m` outputs are exactly the even squares among the first `i` inputs, in order. Initially both counts are zero. An odd value writes nothing; an even value appends one square. Since `m <= i < n <= capacity`, every write is in bounds.

Validation bounds each square by `10000`, representable in `long`. At termination, all retained values have been written and `written` records their count. Input `{1,2,3,4,5,6}` produces `{4,16,36}` and count three; empty input succeeds with count zero. Subject to caller storage obligations, rejection precedes every output write.

One fixed call site may need no more. Graph becomes useful when compositions need inspection or transformation, many pipelines share operator facts, or execution forms must vary. Otherwise construction, diagnostics, and destruction enlarge the implementation without removing repeated knowledge.

## 3. Choose a Mechanism for the Information Needed

| Need | Starting mechanism | Additional conditions |
|---|---|---|
| Computation with known types | Function or `static inline` | Argument and value-domain preconditions |
| Fields, identifiers, or declarations | Finite macro and shared schema | Expansion bounds, separators, diagnostics |
| Native call-site type checks | Compiler capability interface | Supported compilation modes |
| Shared type or function facts | CMeta descriptors | Identity, configuration, lifetimes |
| Multiple compositions and execution forms | CFlow Graph/Plan | Support boundaries, proofs, resources |
| Repeated external service contracts | DataBind contracts and projections | Versions, binding, errors, transport limits |

Functions provide normal argument-evaluation rules; macros generate declarations and tokens functions cannot. Descriptors share facts without requiring known direct calls to become dynamic reflection calls.

Two similarly shaped getters do not automatically justify reflection. If a serializer, binder, and validator independently maintain the same field schema, Chapter 2's shared declaration has a concrete benefit: one change generates consistent consumers.

## 4. Minimal Callbacks, Contracts, and Modules

A simple asynchronous interface can retain this ordinary declaration:

~~~c
typedef void (*book_done_fn)(void *user);
void book_request_start(book_done_fn done, void *user);
~~~

It still needs callback-delivery, possible synchronous execution, cancellation, and `user` lifetime rules. Without binding, reflection, or composition requirements, it may not need a Callable object. A small interface does not eliminate lifetime design.

Similarly, an internal directly called `get_user` usually needs no IDL. Introduce contract compilation when independent external consumers maintain the same requests, responses, and errors. A link-time implementation can use `target_link_libraries(app PRIVATE image_codec)`; Plugin discovery, replacement, and unloading need actual requirements.

## 5. Hidden Allocation Changes the Contract

Fixed inline capture makes Callable copying a bounded byte copy. Automatically allocating larger captures introduces choices about deep copying or sharing, destruction, allocation failure, and cross-thread retention. The original value semantics have changed.

~~~text
choose_capture(values, required_bytes):
    if required_bytes fits the declared inline bound:
        construct the admitted inline capture
    else:
        reject this representation
        let the caller explicitly choose an external context or other API
~~~

Borrowed pointers likewise must not acquire hidden retention. An owned external context needs explicit construction, copy, and destruction rules. Hiding the distinction behind one surface invalidates existing cleanup arguments.

## 6. Capacity and Execution Choice Are Observable

If sustained production rate `λ` exceeds consumption rate `μ`, an unbounded queue accumulates approximately `(λ-μ)t` items over time `t`. Growth postpones memory and latency failure. A bounded queue returns FULL so the application can choose rejection, waiting, or deadline-limited retry.

This approximation is neither a throughput measurement nor a claim that every short burst overflows. It explains why sustained overload cannot be repaired by allocating indefinitely. Chapter 10's ledger also requires rejected work to retain its caller-side cleanup obligation.

Silently replacing requested parallel reduction with sequential execution changes latency, thread use, and deadlines even when values agree. Preserve selection failure explicitly:

~~~text
result = try_requested_backend(plan, policy)
if result is unsupported or rejected:
    report it to the policy owner
    only an explicit policy decision may start another execution
~~~

A retry also requires knowing whether the first attempt produced external effects. A fallback policy must define retry eligibility, ownership, and observations, not merely select another function.

## 7. Keep Component Responsibilities Explainable

CMeta records native type and call facts, DataBind records logical contracts, and transport adapters interpret HTTP or RPC addresses. Putting JSON field syntax into CMeta or business retries into Executor hides domain policy inside shared mechanisms.

A proposed public fact should have the same meaning for independent consumers and be necessary to that layer's contract. One application's compensation workflow can remain local. Reusing a mechanism does not require transferring semantic responsibility to it.

Dynamic boundaries such as replaceable Publishers and Plugin providers suit `{self, vtable}`. Known internal calls can remain direct. Plans may retain useful indirect dispatch; Chapter 7's measurements determine whether eliminating it is worthwhile.

## 8. Verification Cost and an Exercise

| Added claim | Required evidence |
|---|---|
| Correct generated declarations | Compile-pass and expected compile-fail cases |
| Cross-TU/DSO identity | Independent representations and shared-library tests |
| Bounded resources and single cleanup | Capacity, rejection, and lifetime checks |
| Semantics-preserving optimization | Explicit-premise proof and differential execution |
| Usable installation | Independent installed consumer |
| Faster execution | Matched-input and matched-configuration measurements |

Add an output callback to the first function. If notification has external effects, failure after the first notification no longer satisfies the original atomic-output contract. Design both “compute everything before notification” and “allow partial progress and return the committed count.” Identify extra storage and retry conditions for each.

The cost of an abstraction includes what callers may rely on in the future. Actual usage and verifiable conditions should determine which contract survives.

## 9. Summary

An ordinary C baseline makes the benefit of added mechanisms assessable. Macros generate declarations, descriptors share facts, and runtime objects manage specified state and lifetimes. Fixed bounds, explicit rejection, and visible execution policy keep those conditions checkable. Hidden allocation and silent retries alter both proofs and cleanup obligations.
