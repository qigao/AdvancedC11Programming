# 第七章：从计算图到执行计划：优化与直接执行

计算图中的类型、连接和操作信息可以在执行前解析，避免每处理一个值都重新查找。本章给出规范化、规则匹配和计划编译的伪代码，说明哪些信息进入执行计划，以及哪些受支持的计算可以进一步生成直接的 C 调用或循环。变换证明用于约束结果，基线测量用于判断实际成本。

## 1. 编译流水线：从快照到可执行产物

不要让 optimizer 原地修改用户的 Surface Graph。

~~~text
Surface Graph
    ↓ validate
Primitive Graph
    ↓ normalize
Normalized Snapshot
    ↓ optimize
Optimized Snapshot
    ↓ compile
Plan or Direct
~~~

每一层不可变快照都有自己的 fingerprint，使输入产物、改写 trace、certificate 与编译后的 Plan 能够稳定关联。

### 1.1 Normalize Algorithm

**Normalization（规范化）**把多种合法写法整理成后续阶段约定的统一形式。例如展开复合算子、统一边的排列；保持语义是要求，选择更快的执行策略则属于后续优化。

Normalization 只做语义保持、无策略猜测的 canonicalization。

~~~text
normalize(graph):

    require Graph.Valid

    out = empty primitive graph

    for node in topological_order(graph):
        lower surface aliases
        expand compound operators
        canonicalize type ids
        canonicalize edge ordering
        append primitive node

    freeze(out)

    return out
~~~

要求：

~~~text
observe(eval(surface))
=
observe(eval(normalized))
~~~

### 1.2 Optimize Algorithm

~~~text
optimize(graph):

    current = graph

    for rule in approved_rules:

        while match =
            rule.find_candidate(current):

            if !rule.metadata_admits(match):
                break

            if !rule.proof_authorized(match):
                break

            next =
                rule.rewrite(current, match)

            record_trace(rule,current,next)

            current = next

    freeze(current)

    return current
~~~

一次改写必须同时满足**结构匹配、元数据准入和证明授权**；任一条件缺失，都保持原图不变。

### 1.3 Plan 表示：把解析工作移出热路径

概念 Plan：

~~~c
typedef struct cflow_step {
    cflow_step_fn handler;
    uint32_t input_slot;
    uint32_t output_slot;
    const void *static_data;
} cflow_step;

typedef struct cflow_plan {
    const cflow_step *steps;
    size_t step_count;
    size_t frame_size;
} cflow_plan;
~~~

运行：

~~~c
for (size_t i = 0; i < plan->step_count; ++i) {
    const cflow_step *step = &plan->steps[i];

    step->handler(step, frame);
}
~~~

进入执行阶段后，不再查找 node id、不再执行 `switch(node->op)`、解析边或重新解析 callable 签名；这些工作都在编译 Plan 时完成。

### 1.4 Direct Eligibility

**AOT（ahead-of-time，提前编译）**指在程序执行前生成并编译执行代码。本书的 Direct 路径强调符合条件的 Graph 可以落实为直接的 C 调用或循环；Direct 描述执行形式，AOT 描述编译时机，二者不能作为任意 Graph 都可生成循环的保证。

某些 Graph 可以连 Plan dispatch 都删除。

~~~text
direct_eligible(graph):

    require linear pipeline
    require supported operators
    require no dynamic topology
    require no WAIT/reactive boundary
    require fixed admitted callable ABI
    require ownership fully resolved

    return true
~~~

然后生成：

~~~c
long total = 0;

for (size_t i = 0; i < n; ++i) {
    int x = xs[i];

    if (!is_even(x))
        continue;

    total += square(x);
}
~~~

Graph 完全退出热路径。

### 1.5 No Silent Fallback

明确的 anti-pattern 是：

~~~text
requested PARALLEL plan
parallel qualification fails
    ↓ silent fallback
run sequential anyway
~~~

否则性能契约、资源模型和延迟预期都会变成猜测。正确行为是显式返回不支持：

~~~text
compile_parallel(graph)
    -> UNSUPPORTED
~~~

调用方再显式决定是否改用串行后端，或者让构建/准入失败。

### 1.6 Cost Model

分别测量：

- build cost；
- normalize cost；
- optimize cost；
- compile-plan cost；
- per-value cost；
- memory/frame cost；
- binary/code-size cost。

不要只报告“Graph 比循环慢”，而不区分**控制面**与**执行面**。例如，“只构建一次，再执行 (10^8) 个值”和“每个请求都重新构建，却只执行 10 个值”对应完全不同的成本模型。

### 1.7 Failure Cases

#### Invalid graph

如果 `Graph.Valid = false`，就不进入 normalize/compile。

#### Rewrite lacks proof

如果 pattern 与元数据都匹配，但证明 unavailable，就保留原 Graph。

#### Direct unsupported

如果 Graph 合法、Plan 支持而 Direct 不支持，就显式编译 Plan。这里的 Plan 是调用方选择的执行后端，不是对 Direct 契约的静默降级。后半章沿同一条 canonical pipeline 展开，依次给出改写、Plan、Direct/AOT、certificate 和测量证据。

## 2. End-to-End Case：canonical pipeline 从 Surface API 走到 Plan

回到 Part II 一直使用的 pipeline：

~~~text
Source<int>
    ↓
Filter(is_even)
    ↓
Map(square)
    ↓
Reduce(sum)
~~~

用户看到的 surface 可能是：

~~~c
stream.filter(&stream, is_even)
      ->map(&stream, square)
      ->reduce(&stream, sum);
~~~

这段 API 本身不是执行策略。它首先产生 **Surface Graph**，其中保留 operator identity、callable、input/output type、effects/properties、topology、cardinality 和参数。真正的执行链从这里开始。

### 2.1 Step 1 — Surface Graph

Surface Graph 的职责是**忠实记录用户表达的计算含义**。它可以保留较高层的 operator 和结构；这一层最重要的是容易构造、容易检查、容易诊断，而不是追求最快的逐值执行表示。

### 2.2 Step 2 — Normalize

本版 CFlow 的 `cflow_graph_normalize(dst, src)` 要求 `src` 是借用的不可变 Surface Graph，`dst` 是独立的空目标。Normalize 负责校验输入、只执行静态 IR 重写、校验输出，并发布独立的 primitive snapshot。它不拥有 Subscription 调度、活动 demand、运行时 buffer 或 Executor 状态。因此：

Normalization 是纯控制面 IR transformation，而不是半执行。

### 2.3 Step 3 — Optimize

Optimizer 继续使用一条 **artifact transformation**：

~~~text
normalized immutable source
      ↓ apply admitted rewrites
new optimized Graph
~~~

这里的箭头表示“构造新的优化产物”，不是运行时值的数据流。当前 pass 包括 canonicalize、dead subgraphs、map fusion、relation simplify 和 property rewrites，并记录改写前后节点数、map fusion 次数、被阻止的变换以及幂等 Map 消除次数。`effect_blocked_*` 和 `property_blocked_*` 尤其重要，因为它们直接记录“为什么没有改写”：

无法证明或无法通过准入检查的改写，应明确保持原状，而不是做静默的“尽力优化”。

### 2.4 Step 4 — Compile Plan

完整的 canonical pipeline 包含终端 Reduce，因此当前编译后的 Plan 是最自然的执行产物。Plan 编译阶段会提前解析 topology、确定执行 handler、绑定类型与 callable 元数据、记录终端 Reduce，并生成指令序列。进入执行阶段后，它明确承诺：

不再查询 Graph / Node / Edge / Subgraph topology。也就是说：

| 对象 | 作用 |
|---|---|
| Graph | source program description |
| Plan | pre-decoded execution representation |

Plan 不是另一张 Graph；它存在的意义，就是把重复的拓扑判断从执行阶段移走。

### 2.5 Step 5 — Execute

顺序 Plan 执行接收借用输入、已编译指令、预解析的 callable/type 和自己拥有的输出结果。理想情况下，逐值路径不再遍历任意 Graph topology，不查 operator schema、不推断类型、不选择后端、不重新验证签名，也不决定是否改写；这些成本都已经在控制面支付。运行时只消费已经验证的执行定义。

## 3. 一个真实 Rewrite：为什么 Metadata Bit 还不够

canonical pipeline 本身只有一个 Map，不适合为了展示改写硬造第二个 stage。所以我们单独使用一个局部变体。先把 Graph node 与单元素值流同时写出来：

~~~text
输入 x
  ↓
Map(clamp)          # first Graph node
  ↓
y = clamp(x)
  ↓
Map(clamp)          # second Graph node
  ↓
z = clamp(y) = clamp(clamp(x))
~~~

这里是**两个 Map node 的串行组合**；对单个元素展开后才得到嵌套函数应用 `clamp(clamp(x))`。这不是递归，因为 `clamp` 的函数体并没有调用自身。假设 `clamp : int -> int`，并且真正满足幂等律：

~~~text
∀x, clamp(clamp(x)) = clamp(x)
~~~

那么改写前后可以明确写成：

~~~text
before:
x -> Map(clamp) -> clamp(x) -> Map(clamp) -> clamp(clamp(x))

after:
x -> Map(clamp) -> clamp(x)
~~~

本版 CFlow optimizer 已经有稳定 semantic 改写 id `IDEMPOTENT_MAP_ELIMINATION`，并可以在 traced optimization 中记录 input subgraph、retained node/callable index 和 removed node/callable index。

| Evidence | 回答什么 |
|---|---|
| Proof of Rule | 这条改写是否普遍成立 |
| Trace of Instance | 这一次具体改写发生在哪里 |

### 3.1 Property 主张只负责准入检查

C callable 可以声明 `IDEMPOTENT`，但这本身只是主张/准入检查元数据。真正的改写 correctness 来自 semantic law。如果某个 C function 谎报 `IDEMPOTENT`，Lean 并不会神奇地证明那个任意机器码真的满足 law。因此可信链必须明确：

~~~text
implementation identity
+
metadata claim
+
trusted/verified semantic meaning
+
rewrite theorem
+
rewrite trace
~~~

第六章已经把这条 trusted chain 完整展开。

### 3.2 Lean 已经有对应定理

本版 formal calculus 的 Rewrite 证明已经包含 `map_idempotent_elimination` 和 `certified_rewrite_preserves_observations`。因此书不必再停留在“理论上我们以后可以证明 optimizer”。而可以直接讨论：

现有改写定理怎样授权现有 optimizer rule。这正是 Modern C + Lean 的专业闭环。

## 4. Direct / AOT：最简单的路径应该连 Plan 都不需要

Plan 已经比 Graph Interpreter 简单很多。但对于非常简单、封闭、同步的 Filter/Map pipeline，Plan 仍然可能是多余层次。本版 CFlow Direct/AOT path 明确支持有界 Stage IR 中的 Filter 和 Map。stage 数量也有显式上限。它要求每个 stage 满足严格 eligibility。

### 4.1 Direct eligibility 是删除运行时 abstraction 的资格

当前 direct-stage eligibility 会检查：

- type is direct-eligible；
- callable can bind；
- `capture_size = 0`；
- `effects = PURE`；
- required properties 包含 `DETERMINISTIC`、`TOTAL`、`NO_ALIAS`；
- 签名 protocol/type chain matches。

Filter 还要求 return bool 且 output type = input type；Map 则要求 return type itself direct-eligible。这不是“为了检查而检查”。它是在回答：

我们什么时候有资格完全跳过通用 invoke/运行时 layer？

### 4.2 AOT dispatch 也分多种 authority

当前 Stage IR 可表示 `STATIC_TARGET`、`CANONICAL_RAW_BATCH` 和 `ADAPTER`。因此一个 surface callable 并不自动意味着所有路径都能生成 direct static C call。eligibility 必须与真实 dispatch authority 一致。

### 4.3 Direct macro 的重要 promise

当前生成的 Direct array 路径明确承诺：没有间接 stage 回调、没有动态分配、没有 scheduler 操作；同时检查输入/输出存储、容量、溢出、别名/区间重叠和类型链。失败时明确返回 `INVALID_ARGUMENT`、`INELIGIBLE` 或 `CAPACITY_EXCEEDED`，不会静默降级到 Plan/Kernel。这正是第十四章“No Silent Fallback”原则的具体实例。

### 4.4 但当前 Direct 不等于完整 Reduce pipeline

固定快照的 Direct 路径主要覆盖 Filter/Map。对 `Filter → Map → Reduce`，包含 Reduce 的执行应使用受支持的编译计划；不能据此推断任意计算图都能生成一个直接循环。

## 5. Parallel Reduce：并行是 Execution Refinement，不是 Graph Rewrite

Reduce 是一个特别好的例子。Graph semantic program可以保持：

~~~text
Reduce(sum)
~~~

execution 可以选择 sequential reduce，或者在严格前提下选择 ordered parallel reduce。这不是同一类 transformation。

### 5.1 Semantic 改写与 physical execution refinement 要分开

语义改写可以写成 **Map(identity) → remove**：它改变语义 IR 的结构，但定理证明可观察结果不变。**Reduce sequential ⇒ Parallel Reduce** 则表示执行精化：语义 operator 不变，只改变物理执行形式。因此本书刻意使用不同箭头：`→` 表示语义改写，`⇒` 表示已经准入的执行精化。formal calculus 也明确区分 rewrite rule 与 execution-refinement rule；两者的证明义务不能混用。

### 5.2 并行 Reduce 需要完整准入检查 contract

至少需要：

- homogeneous reducer；
- PURE；
- TOTAL；
- ASSOCIATIVE semantic law；
- required order model；
- CONCURRENT Executor capability；
- supported value storage；
- valid task/chunk bounds。

不能因为 “worker pool exists” 就自动 parallelize Reduce。

### 5.3 Unsupported parallel mode 不能 silent sequential retry

当前 Plan contract 明确：

~~~text
unsupported plan
insufficient nonempty chunks
invalid options
rejected tasks
    ↓
false / explicit failure
~~~

而不是：

~~~text
parallel failed
    ↓
quietly rerun sequentially
~~~

为什么？因为 silent fallback 会改变 latency/resource behavior、掩盖准入检查 bug、破坏调用方 policy，并让 benchmark 失真。所以 fallback 本身必须是上层显式 policy。

## 6. Certificate / Proof Trace：把 Execution Artifact 绑定到 Graph

Plan 完成预解码后，执行阶段不再遍历 Graph topology。问题随之变成：怎样确认这个 Plan 仍对应那张已经批准的 normalized Graph？当前 certificate 记录自身版本、certified path、顺序要求、所需 capability、Graph version、Graph fingerprint 以及语义条目；每条记录包含 opcode、instruction index、callable index、effects、properties、输入/输出类型、callable 和有类型参数。

所以 certificate 不是“trust me, this plan was compiled”，而是一个可检查 execution witness。

### 6.1 Certificate 不是 wire format

当前实现明确包含 含指针的条目、process-local Graph identity，并把 certificate 定义为 execution-only witness。因此不能 serialize certificate to disk、ship to another process，也不能把 raw pointer/address 当成稳定身份。这与前面语义身份的原则一致。

### 6.2 Version + fingerprint 防止 stale artifact

Graph 被 mutation 后 version changes，certificate 绑定失败。如果还需要更强结构绑定，fingerprint 进一步确保声明行/topology/callables 对应。目的不是密码学签名。目的是：

让一个 execution artifact 无法在 source program 已变化后继续被误当成可信。

### 6.3 Lean 已经证明 certificate/refinement observation preservation

当前 formal 证明中已有 `certificate_preserves_observation`、`parallel_certificate_preserves_observation` 和 `execution_refinement_preserves_semantics`。特别是 `parallel_certificate_preserves_observation` 不是无条件结论。它要求：

~~~text
CertificateValid(...)
certificate.path = orderedParallelReduce
ParallelReducePremises Γ K ty
~~~

在这些前提下，它才把两条证明 obligation 组合起来：

~~~text
Graph-to-Plan observation equality
+
Reduce ⇒ ParallelReduce physical execution refinement
    ↓ proof composition
same semantic result
~~~

这里的下降箭头表示“由两项证明前提推出结论”，不是执行顺序。这使 Certificate 不只是运行时 validation feature。它是 **formal 定理与 C 运行时 witness 之间的 bridge**。

### 6.4 Proof Trace：为什么还需要记录“发生了哪一次 Rewrite”

Certificate 主要回答：“这个 Plan/执行路径是否仍绑定到这张 Graph？” Proof Trace 回答另一个问题：“这张 optimized Graph 为什么可以由 source Graph 得到？” 当前 traced optimizer 以事务方式生成 optimized Graph 和自己拥有的改写 trace；trace 同时绑定精确的 source Graph 对象/version 与 optimized Graph 对象/version。因此可信链可以拆成：

~~~text
Lean:
    proves rewrite rule

Optimizer:
    emits rewrite instance trace

Checker/AOT matcher:
    verifies this trace matches concrete Graphs

Plan Certificate:
    binds execution artifact to approved optimized Graph
~~~

这比单纯记录“optimizer says success”强得多。

## 7. Cost Model：Lean 也不应该“证明 benchmark 数字”

形式化可以讨论 representation/refinement cost dimensions，例如 graph queries、scheduler hops、buffering 和 dispatch layers。当前 formal Cost 证明已经有：

- `direct_excludes_kernel_trigger`；
- `plan_excludes_kernel_trigger`；
- `direct_cost_dominates_plan`；
- `plan_cost_dominates_kernel`；
- `costed_refinement_preserves_semantics`。

但必须准确理解这种定理。例如 `direct_cost_dominates_plan` 还要求 `0 < workload.items * workload.operators`。也就是 workload 中确实存在回调 work；它不是对空 workload 的“无条件更优”宣传。它证明的是：

> 在给定抽象 cost model 和 premises 下，某 representation 消除了某些 cost dimensions / 保持 semantics。

它不证明“这个 CPU 上快 17.3%”、“Clang 19 一定 inline”、“L1 cache miss 一定减少多少”或“Windows 比 Linux 快”。真实 wall-clock/perf 数据必须来自 benchmark。也就是说：**formal 证据 ≠ empirical 证据**。

## 8. Performance Evidence：本章必须建立 measurement discipline

本版 CFlow 已经提供专门的 benchmark target：`cflow_direct_benchmark`、`cflow_parallel_reduce_benchmark`、`cflow_graph_path_benchmark`、`cflow_branching_csr_benchmark`、`cflow_reactive_benchmark` 和 `cflow_machine_hierarchy_benchmark`。书中若给出具体性能结论，必须同时记录 commit、编译器及版本、优化选项、platform/CPU、输入规模、operator 数量、warmup、重复次数、统计量和基线。

### 8.1 canonical data-flow benchmark 应至少比较

- hand-written C loop；
- Graph/kernel execution；
- compiled Plan；
- eligible Direct Filter/Map prefix。

对于含 Reduce 的完整 pipeline，还应比较 hand-written sequential loop、sequential compiled Plan 和 ordered parallel reduce Plan。Direct 不支持的路径必须标成 **not eligible**。而不是强行给出一个 fallback 数字。

### 8.2 Control-plane cost 也要测

Build Once, Execute Many 不是说 build cost 等于零。应该分别测 Graph build、normalize、optimize、plan compile、certificate build/check 和 execution。然后根据 workload amortization 回答：

> 重复执行多少次以后，提前付出的控制面 cost 才值得？

这比单独展示一个 hot-loop ns/op 更有工程意义。

### 8.3 不在没有 fresh measurement 时写“X 倍更快”

书可以解释为什么 Direct 理论上少了哪些动态步骤、为什么 Plan 不再做 topology query、为什么 Graph interpretation 多哪些工作，但具体数字必须等 canonical benchmark 在固定 commit 上执行以后再写入。这条编辑纪律会防止本书从 engineering book 退化成性能宣传材料。

## 9. 小结

规范化整理表示，优化应用获准规则，计划编译预先解析操作与连接。执行计划因此可以直接访问已确定的处理函数和存储槽。每一步都需要清楚的输入快照、失败条件和语义保持依据。固定快照中的 Direct 路径只覆盖满足资格检查的 Filter/Map 等范围；完整的 Filter/Map/Reduce 示例仍应按实际支持范围使用编译计划。请求不支持的执行方式时应显式返回结果，不能静默改变策略。构造、编译和执行成本需要分别测量。
