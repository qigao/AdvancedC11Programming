# 第一章：CMeta 基础：宏、内联函数与编译期约束

CMeta 利用宏生成声明，用普通函数和内联函数执行有类型的操作，再用静态元数据描述多个模块需要共享的事实。本章从宏参数重复求值开始，比较函数、有限宏展开与编译器扩展各自能保证什么，并通过成员指针恢复、类型选择和作用域清理说明这些技巧的使用条件。

本书把元编程、RAII 与反射能力统称为 **CMeta**；代码中的 `cmeta_*` / `CMETA_*` 保留真实标识符，Salts 只指源码仓库、SDK 发行包和 `Salts::CMeta` 等真实构建目标。Reflection（反射）在本书中主要指由声明生成、可被程序检查的静态类型/函数描述符。RAII 原指把资源生存期绑定到对象生存期；在 C 中，本书只使用明确的清理协议和有条件的作用域清理扩展，不把它包装成隐藏运行时。

## 1. 从普通函数确定抽象需求

这个比较函数把两个 `int` 对象的大小关系转换为负一、零或一。它直接使用 C 的类型和比较规则，调用方只需保证两个指针在调用期间指向有效对象。

~~~c
static int int_compare(const int *a, const int *b)
{
    return (*a > *b) - (*a < *b);
}
~~~

若系统只需要这一份实现，继续直接调用即可。若比较、哈希和序列化等多个模块都需要同一类型集合或字段列表，就应记录这组共享事实，再分别生成需要的声明或元数据。CMeta 的介入点由这项重复决定：先确定哪些知识要复用，再选择宏或描述符保存它。

## 2. static inline：先解决有类型的行为，再考虑 macro

C 宏常见的问题是参数表达式可能被重复求值。例如：

~~~c
#define MAX(a, b) ((a) > (b) ? (a) : (b))
~~~

调用：

~~~c
int x = MAX(next_a(), next_b());
~~~

不能只从表面语法判断每个参数会执行几次。如果问题只是一个有类型的行为，优先用函数：

~~~c
static inline int
int_max(int a, int b)
{
    return a > b ? a : b;
}
~~~

调用仍然是普通 C：

~~~c
int x = int_max(next_a(), next_b());
~~~

函数调用由编译器检查参数类型，并通过参数对象访问已经求得的值。`inline` 允许编译器考虑内联，但不保证一定消除调用；无论是否内联，C 的函数求值规则都适用。宏则适合生成函数参数无法表达的标识符、类型或声明结构。

**求值次数的推导。** 对 `MAX(a, b)` 展开后的条件表达式，比较阶段读取两个实参，随后只执行被选择的分支；若执行有定义并正常完成，被选择的实参表达式总共求值两次，另一个求值一次。函数调用 `int_max(a, b)` 则先把两个实参各求值一次，函数体只访问参数对象。下面的伪代码只描述次数；其中“求值两个实参”不指定先后顺序。

~~~text
macro_max(a, b):
    compare evaluate(a) with evaluate(b)
    evaluate the selected expression again

function_max(a, b):
    evaluate each argument once and initialize parameter objects
    compare the parameter values
    return the selected parameter value
~~~

由控制流可得：宏正常完成时实参表达式共求值三次，函数正常完成时共求值两次。这个结论不依赖编译器是否内联函数；C11 也没有因此规定两个函数实参的求值顺序。若两个实参修改同一个标量且这些修改未被排序，改用函数仍不能消除未定义行为。

下面的完整 C11 程序把这个差别变成可观察结果。两个函数分别修改不同计数器，因此示例不依赖实参求值顺序，也不会制造未排序地修改同一标量的问题。

~~~c
#include <stdio.h>

#define MAX(a, b) ((a) > (b) ? (a) : (b))

static int a_calls;
static int b_calls;

static int next_a(void)
{
    ++a_calls;
    return 10;
}

static int next_b(void)
{
    ++b_calls;
    return 5;
}

static inline int int_max(int a, int b)
{
    return a > b ? a : b;
}

int main(void)
{
    int m = MAX(next_a(), next_b());

    printf("macro: value=%d a=%d b=%d\n",
           m, a_calls, b_calls);

    a_calls = 0;
    b_calls = 0;

    int f = int_max(next_a(), next_b());

    printf("func : value=%d a=%d b=%d\n",
           f, a_calls, b_calls);
    return 0;
}
~~~

在符合 C11 的实现上，两行的调用先后次序可以不同，但计数结果固定为：

~~~text
macro: value=10 a=2 b=1
func : value=10 a=1 b=1
~~~

这个小实验给出本章后续宏设计的第一条可测试规则：**只要宏接收可能有副作用的表达式，就必须明确说明它会求值几次；默认目标应是一次。**

## 3. Macro 真正擅长的是 C 函数做不到的事

普通函数不能生成：

- 类型名、字段声明和函数原型；
- 按规则组合的标识符；
- 初始化项和元数据声明。

预处理器处理记号并生成声明，适合把一份类型集合提供给比较、哈希和序列化等多个使用方。例如：

~~~c
#define BUILTIN_TYPES(X) \
    X(int)               \
    X(long)              \
    X(float)
~~~

不同消费者 replay 同一份 facts：

~~~c
#define GEN_COMPARE(T) DEFINE_COMPARE(T)
BUILTIN_TYPES(GEN_COMPARE)

#define GEN_HASH(T) DEFINE_HASH(T)
BUILTIN_TYPES(GEN_HASH)
~~~

真正被复用的不是代码本身，而是：

~~~text
supported type set
    =
{ int, long, float }
~~~

所以：

macro 最有价值的用途不是隐藏运行时逻辑，而是生成 C 本身无法以函数参数表达的结构。

## 4. Linux-style finite map：让参数个数成为数据，而不是宏名

**术语说明：** arity（元数）是参数或元素的个数；这里按声明中的 `(type, name)` 对计数。PP 是 preprocessor（预处理器）的缩写；DSL 是 domain-specific language（领域专用语言），这里指针对声明任务设计的小套宏语法。

一个典型接口可能把参数写成平铺 pair：

~~~text
int, fd,
size_t *, written
~~~

最直接但最差的扩展方式是：

~~~text
PARAMS_0
PARAMS_1
PARAMS_2
PARAMS_3
...
~~~

然后每一个上层 DSL 再复制一套：

~~~text
DECLARE_0..N
CALL_0..N
META_0..N
VALIDATE_0..N
~~~

CMeta 现在把这类机械能力收敛到有限 PP kernel。例如：

~~~c
CMETA_PP_PAIR_MAP_N(N, M, C, ...)
CMETA_PP_MAP_COMMA_N(N, M, C, ...)
CMETA_PP_MAP_PREFIX_COMMA_N(N, M, C, ...)
~~~

概念上：

~~~text
(type,name,type,name,...)
          ↓
   finite pair map
      /        \
 declaration   arguments
      |           |
 metadata      wrapper
~~~

这里最重要的不是宏技巧本身，而是设计约束：

~~~text
finite
explicit
bounded
~~~

生产核心不依赖无限递归式：

~~~text
DEFER -> OBSTRUCT -> EVAL -> recursive macro machine
~~~

因为更聪明的 preprocessor 不等于更好的工程边界。

## 5. pp.h 与compiler.h 必须分开

预处理机制负责记号替换、列表展开和名字组合；编译器能力（compiler capability）则指具体编译器是否提供类型推导、清理属性等设施。`pp.h` 与 `compiler.h` 分别处理这两类问题，上层声明通过明确入口查询所需能力：

~~~text
cmeta/pp.h
    token
    tuple
    finite map
    boolean
    unique-name composition
          |
          v
cmeta/compiler.h
    typeof capability
    auto-type capability
    type compatibility
    cleanup attribute
    section/used attribute
    compile-time expression requirement
          |
          v
higher-level CMeta declarations
~~~

这样上层代码不需要到处出现：

~~~c
#ifdef __GNUC__
...
#elif defined(__clang__)
...
#elif defined(_MSC_VER)
...
#endif
~~~

而是查询明确能力。CMeta 当前提供的典型入口包括：

~~~c
CMETA_NATIVE_TYPEOF(expr)
CMETA_SAME_TYPE(a, b)
CMETA_AUTO(name, expr)
CMETA_CONST_REQUIRE(condition)
~~~

上层操作必须检查所依赖的能力。不支持时，应按文档提供明确定义的受限接口，或拒绝该声明；不能让相同接口在不同编译器上悄悄失去类型或清理保证。

## 6. Single evaluation：macro 与编译器 facility 应该共同保护调用者

有些 generic helper 确实需要宏，因为它必须取得表达式的本地类型。这时仍然应该保证：

~~~text
user expression
      ↓
evaluate once
      ↓
typed local
      ↓
operate on local
~~~

例如能力存在时：

~~~c
CMETA_AUTO(tmp, expression);
~~~

其目标不是增加一个动态 `Any`，而只是得到一个普通 C local：

~~~text
expression
    ↓ once
native typed local
    ↓
ordinary C operation
~~~

这条规则应该贯穿后续所有 helper：

如果宏接受一个可能有副作用的 expression，默认要求单次求值；做不到时必须把限制写进 contract。

## 7. container_of：Macro、typeof 与 layout check 怎样合作

`container_of` 是一个很好的 Modern C 例子。目标是从真实 member 地址恢复 enclosing object：

~~~c
struct Node {
    int value;
    struct Link link;
};

struct Link *p = ...;
struct Node *node =
    cmeta_container_of(p, struct Node, link);
~~~

它需要的并不只是：

~~~c
(char *)p - offsetof(struct Node, link)
~~~

还需要尽可能在编译期检查：

~~~text
type(p)
    ==
type(&((struct Node *)0)->link)
~~~

CMeta 因此把它拆成两层：

~~~text
compiler capability
    CMETA_NATIVE_TYPEOF
    CMETA_SAME_TYPE
            |
            v
container/member recovery
    cmeta_container_of(...)
~~~

如果当前编译器无法提供推导型 native typeof，则使用显式 member type 的入口，而不是假装两者保证相同。

~~~text
macro
  + compiler type fact
  + compile-time requirement
        ↓
ordinary pointer arithmetic
~~~

没有运行时 reflection lookup。

## 8. _Generic：是编译期 dispatch，不是 semantic authority

**术语说明：** ownership（所有权）说明谁负责资源的释放或转交；borrow（借用）允许在约定生存期内访问资源，而不取得其所有权。TU 是 translation unit（翻译单元）的缩写，即一个源文件经过头文件展开等预处理后交给编译器的单位。

C11 的 `_Generic` 可以做有限选择：

~~~c
#define print_value(x) _Generic((x), \
    int: print_int,                  \
    long: print_long,                \
    double: print_double             \
)(x)
~~~

它回答：

> 给定这个 C expression 的 static type，选择哪个已有 expression？

它不自动回答：

- 这个 type 的语义身份是什么；
- 它的 lifecycle 提供方是谁；
- 一个 struct 有哪些字段；
- 一个 function 的 IN/OUT/所有权是什么；
- 两个不同 TU 中的描述符是否表达同一个 meaning。

因此：

~~~text
_Generic
    =
compile-time selection

Reflection descriptor
    =
semantic authority
~~~

两者可以合作，但不能互相替代。

## 9. Macro + static inline + 反射：三层不是三个运行时

考虑一种常见生成模式：

~~~text
schema / declaration row
        ↓ macro replay
ordinary C declaration
        +
static metadata
        +
static inline typed accessor
~~~

调用侧可能只是：

~~~c
const cmeta_function_desc *desc =
    get_user_cmeta_function();
~~~

而真正执行仍然是：

~~~c
int rc = get_user(repo, id, &user);
~~~

函数反射的存在不应该自动把调用改成：

~~~text
box arguments
   ↓
dynamic lookup
   ↓
erased dispatcher
   ↓
unbox result
~~~

Reflection does not imply dynamic dispatch. 反射保存的是稳定 meaning。执行方式由真正的使用方决定。

## 10. Static path 与 dynamic boundary 必须分开

**术语说明：** canonical（规范的）表示后续步骤共同依据的权威表示；它不要求所有描述符具有同一个内存地址。DSO 是 dynamic shared object 的缩写，这里指提供代码和数据的动态共享库。ABI（application binary interface，应用二进制接口）约定已编译模块之间的调用方式与数据布局。

**Admission（准入检查）**是在接受外部描述符或操作前验证其契约；通过检查得到的 capability（能力凭据）只能在规定的权限与生存期内使用。hot path（热路径）指频繁执行、对开销敏感的代码；这里的目标是把检查移到一次性的准入阶段。

对编译期已知的 canonical 声明：

~~~text
known type/function
      ↓
direct generated binding
      ↓
static inline / direct call
~~~

不应该在每次调用时重新遍历描述符 graph。但 Plugin / DSO / foreign 元数据是不同的问题：

~~~text
foreign/raw descriptor
        ↓
validate ABI / layout / semantics
        ↓
admit once
        ↓
small admitted capability
        ↓
reuse many times
~~~

校验和执行分别承担以下工作：

~~~text
static world
    -> prove/generate early

dynamic boundary
    -> validate once

hot path
    -> use admitted/direct representation
~~~

描述符验证的结果在契约有效期间复用，使热路径不必逐次重复完整检查。

## 11. 可选 syntax lowering 不是 CMeta 的存在前提

**Lowering（降低抽象层次的转换）**把较高层的语法或表示转换为更接近实现的形式，同时保持约定语义。例如，把下面的成员式调用转换为带显式接收者参数的普通 C 调用；它本身不意味着性能一定提升。

以后我们还会看到 receiver-like syntax，例如概念上的：

~~~c
list.add(10);
~~~

它可以被 frontend/lowering 转成：

~~~c
IntList_add(&list, 10);
~~~

但是 canonical CMeta 不能要求所有普通 C 使用方先经过一套 source translator。正确关系是：

~~~text
optional syntax frontend
        ↓
canonical semantic resolution
        ↓
ordinary C API
~~~

而不是：

~~~text
CMeta
  =
mandatory new C source language
~~~

因此 receiver 元数据、反射、Generic 等能力必须能够被普通 C 直接消费。

## 12. 一个决策树

到这里可以把 Chapter 1 收成一个非常实用的判断：

~~~text
Can a normal C function express it?
        |
       yes
        v
normal function / static inline

Need to create tokens, declarations, identifiers,
or replay a finite schema?
        |
       yes
        v
finite macro / PP kernel

Need native compiler knowledge such as typeof,
same-type, cleanup or section placement?
        |
       yes
        v
capability-gated compiler abstraction

Need stable meaning shared by several consumers?
        |
       yes
        v
canonical Reflection / semantic descriptor

Crossing a foreign or dynamic boundary?
        |
       yes
        v
validate once -> admitted capability
~~~

不要把这些层合并成一个万能机制。

## 13. 四个真实 Linux Kernel Pattern：学工程规则，不复制扩展语法

“Linux-style C”如果只停留在形容词，就没有技术含量。本书固定参考 Linux kernel snapshot 中四类真实 pattern，但只提炼工程规则，不把 kernel-specific 编译器 extension 当成 portable C contract。

### 13.1 syscall `__MAP`：有限 pair replay

Linux 的 syscall 声明把参数组织成：

~~~text
type, name, type, name, ...
~~~

然后用一个有限 `__MAP(n,...)` family 把同一组 pair 投影成声明、argument、元数据等不同形状。CMeta 对应的是：

~~~c
CMETA_PP_PAIR_MAP_N(N, M, C, ...)
CMETA_PP_PAIR_MAP_COMMA_N(N, M, C, ...)
~~~

二者共享的不是宏名字，而是这个规则：

~~~text
one finite row source
        ↓
several mechanical projections
        ↓
no duplicated arity family per DSL
~~~

区别也必须明确：

~~~text
Linux syscall map:
    kernel/toolchain-local contract

CMeta pair map:
    shared portable library kernel
    + explicit 0..N bound
    + separator/context variants
~~~

### 13.2 min/max：先捕获一次，再做类型检查

Linux 的 `min/max` 实现不会把带副作用的 operand 直接重复塞回 comparison。它的核心 shape 是：

~~~text
x expression ─┐
              ├─> unique typed temporary
y expression ─┘
                    ↓
              compile-time compatibility check
                    ↓
                compare locals
~~~

CMeta 不需要复制 kernel 的 statement-expression 实现；它把能力拆成：

~~~c
CMETA_AUTO(tmp, expr)
CMETA_SAME_TYPE(a, b)
CMETA_CONST_REQUIRE(condition)
CMETA_PP_UNIQUE(prefix)
~~~

因此真正值得学习的是：

宏可以负责组合 expression shape，但 user expression 默认只求值一次，类型约束尽量在编译期失败。

### 13.3 container_of：pointer arithmetic 之前先证明 member relation

当前 Linux `container_of` 不只是 `offsetof` arithmetic。它还检查 member pointer type；新的 const-preserving surface 再通过 `_Generic` 保留 constness。CMeta 对应：

~~~c
cmeta_container_of(ptr, Owner, member)
cmeta_container_of_as(ptr, Owner, MemberType, member)
~~~

关系是：

~~~text
member address
    +
native member-type proof
    +
owner layout relation
        ↓
enclosing object pointer
~~~

如果编译器没有足够强的 native `typeof`，CMeta 使用显式 `MemberType` 入口，而不是伪装成同等静态保证。这比“提供一个 container_of 宏”更重要：

弱 backend 必须暴露较弱 contract，而不是静默声称和强 backend 等价。

### 13.4 DEFINE_FREE / guard：cleanup attribute 只负责 lexical lowering

Linux 的 cleanup helpers 包括 `DEFINE_FREE`、`guard`、`scoped_guard` 等。它们利用编译器 cleanup support 让 lexical scope 帮助执行 LIFO unwind。但这里最容易学错。错误结论是：

~~~text
compiler cleanup attribute
        =
universal ownership model
~~~

正确分层是：

~~~text
resource semantic authority
        ↓
small cleanup adapter
        ↓
compiler lexical cleanup
        ↓
reverse-order discharge
~~~

CMeta 对应地把：

~~~text
CMETA_ATTR_CLEANUP
    = compiler capability

cmeta_scope
    = structured lexical lowering

DataDesc / ObjectRef / Plugin lease
    = resource-specific semantic authority
~~~

保持分开。

**Lease（生存期租约）**在这里是显式取得并释放的凭据，保证借用的动态库代码和数据在使用期间保持有效。它不是超时到期的网络租约；后文会说明为什么调用结束后，清理回调仍可能需要它。

所以一个 Plugin lease、一个 managed Data value、一个 shard-owned async operation 不应该因为都“需要 cleanup”就被压成同一个 `destroy(void *)` contract。

### 13.5 对照表

| Linux kernel pattern | CMeta counterpart | 共同工程规则 |
|---|---|---|
| syscall finite `__MAP` | `CMETA_PP_PAIR_MAP_N` | finite 声明行 replay |
| careful `min/max` | `CMETA_AUTO` + `CMETA_SAME_TYPE` + `CMETA_PP_UNIQUE` | single evaluation + 编译期 check |
| `container_of(_const)` | `cmeta_container_of(_as)` | type/layout 证明 before pointer recovery |
| `DEFINE_FREE/guard/scoped_guard` | cleanup capability + `cmeta_scope` | lexical lowering is not resource semantics |

这四个例子共同说明：

~~~text
Linux kernel
    teaches the shape of the engineering problem

CMeta
    extracts a bounded/capability-gated contract

ordinary C
    remains the generated/executed form
~~~

## 14. Engineering Evidence

### Preprocess

~~~bash
cc -E sample.c
~~~

检查 macro 最终是否生成可读、可调试的普通 C。

### Compile-pass / compile-fail

必须覆盖：

~~~text
supported arity        -> compile
unsupported relation   -> fail
wrong member type      -> fail
invalid flags/layout   -> fail
~~~

### Cross-compiler

至少区分 GCC、Clang、MSVC 的真实 capability。测试目标不是“每个编译器都假装一样”，而是：

~~~text
same semantic contract
    +
explicit capability difference
~~~

### Runtime

对 static path，理想证据仍然是：

没有新的运行时 cost center。如果最终机器路径与手写 direct C 等价，抽象成本应该主要发生在 build/控制面。

## 15. 小结

函数提供类型检查与参数传值，宏生成标识符、声明和初始化项，编译器能力补充本地类型与作用域信息，反射描述符保存多个使用方需要共同检查的事实。选择机制时应先确定需要表达的是运行时行为还是编译期结构，再检查扩展能力和不支持条件。单次求值只约束表达式的求值次数，并不规定函数实参之间的求值顺序。作用域清理只决定何时调用清理动作；借用、共享和 Plugin 租约的义务仍来自资源协议。下一章将重复的列表遍历和声明投影收进共享的有限内核。
