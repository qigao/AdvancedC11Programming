# 第一章：CMeta 基础：宏、内联函数与编译期约束

CMeta 用宏生成声明，用普通函数处理有类型的值，再用静态描述符保存多个使用方需要的事实。本章从参数求值、有限展开和资源清理三个问题说明这些机制怎样配合。后文的 Reflection（反射）指可检查的类型或函数描述；RAII 是 Resource Acquisition Is Initialization，原指资源取得与对象初始化相联系的生存期管理。在 C 中，仍须给出明确的所有者和清理路径，编译器属性只负责其中一部分动作。

| 名称 | 本书用法 |
|---|---|
| CMeta、CMeta Plugin | 元编程、反射、生存期及 `cmeta_plugin_*` 接口 |
| `cmeta_*`、`CMETA_*` | 实际类型、函数、宏及常量 |
| Salts | 仓库、SDK 发行包以及 `find_package(Salts)` |
| `Salts::CMeta`、`Salts::Plugin` | 固定快照中的真实构建目标 |

## 1. 先用函数表示有类型的行为

下面的 C 片段比较两个 `int` 对象。要求指针指向调用期间有效的对象；比较结果分别为负一、零和一，不使用可能溢出的减法 `*a - *b`。

~~~c
static int int_compare(const int *a, const int *b)
{
    return (*a > *b) - (*a < *b);
}
~~~

如果比较只服务于一种类型，直接调用即可。多个模块需要相同的类型集合、字段或函数参数时，再把这些共享事实提取为声明。描述符的必要性来自重复维护的事实，而不是函数本身不够抽象。

## 2. 单次求值不等于固定求值顺序

下列宏中，获选的实参表达式会被再次求值。`next_a`、`next_b` 在这里代表返回 `int` 的函数；以下各段是分别比较的片段。

~~~c
#define MAX(a, b) ((a) > (b) ? (a) : (b))
~~~

~~~c
int x = MAX(next_a(), next_b());
~~~

把有类型的计算写成函数，实参各求值一次，函数体再访问参数对象：

~~~c
static inline int
int_max(int a, int b)
{
    return a > b ? a : b;
}
~~~

~~~c
int x = int_max(next_a(), next_b());
~~~

下面的伪代码只描述次数，不规定两个实参谁先执行。

~~~text
macro_max(a, b):
    compare evaluate(a) with evaluate(b)
    evaluate the selected expression again

function_max(a, b):
    evaluate each argument once and initialize parameter objects
    compare the parameter values
    return the selected parameter value
~~~

**推导。** 假设表达式求值有定义并正常完成，宏先求值两个实参以比较，再求值被选择的一个，共三次；函数的两个实参各求值一次，共两次。`inline` 不影响这条语言规则，也不保证编译器一定消除函数调用。C11 没有因此规定函数实参的求值顺序；两个实参对同一标量作未排序的冲突访问时，换成函数仍不能消除未定义行为。

这个例子还说明“重复出现一个名字”和“重复执行表达式”是不同问题。检查宏应看预处理后的表达式位置及控制流，不能只看调用处的括号。

## 3. 用有限列表生成声明

函数不能生成标识符、字段或函数原型，预处理器却可以对记号进行替换。**记号（token）**是预处理器操作的词法单位；**有限展开（finite expansion）**在预先规定的元素数量内重复生成声明，不依赖运行时循环。

下面是完整的声明生成片段，不依赖 CMeta：

~~~c
#define BOOK_FIELDS(X) \
    X(int, id)         \
    X(double, score)
#define BOOK_DECLARE(T, name) T name;
typedef struct BookUser { BOOK_FIELDS(BOOK_DECLARE) } BookUser;
#undef BOOK_DECLARE
~~~

它展开为 `typedef struct BookUser { int id; double score; } BookUser;`。再提供一个读取相同行的元数据生成器，就能得到相同字段次序。对行数作归纳：空列表不生成字段；追加一行只追加该行对应的字段。因此，只要每个生成器都按相同次序处理每行，声明和描述的字段次序一致。字段偏移和类型仍须由编译器检查，不能由这个次序证明代替。

CMeta 的 `CMETA_PP_PAIR_MAP_N` 把类型、名字成对映射给使用方，逗号版和分号版控制结果之间的分隔。**元数（arity）**是元素个数；**投影（projection）**是从一行选择需要的信息。第二章进一步展开这两项机制。

## 4. 区分预处理机制与编译器能力

`pp.h` 处理记号拼接、元组拆分和有限映射；`compiler.h` 封装本地类型推导、类型相容检查、清理属性等编译器能力。**能力检查（capability check）**说明当前工具链能否实现某项保证，而不是仅凭厂商名称推测其行为。

~~~c
CMETA_NATIVE_TYPEOF(expr)
CMETA_SAME_TYPE(a, b)
CMETA_AUTO(name, expr)
CMETA_CONST_REQUIRE(condition)
~~~

这些是入口形式，`expr` 等为占位参数。`CMETA_NATIVE_TYPEOF` 表示编译器的本地类型，`CMETA_AUTO` 用推导出的类型保存一次表达式求值的结果，`CMETA_CONST_REQUIRE` 表达编译期要求。它们不是动态的任意类型容器。缺少必要能力时，调用方应采用文档明确的显式类型入口或拒绝该操作；不能保留相同接口名称，却悄悄放弃类型或清理保证。

## 5. 成员地址恢复需要哪些前提

`container_of` 从成员地址恢复包含它的对象。下面只展示调用形状，`Link` 的定义和 `p` 的来源省略；`p` 必须确实指向仍存活的 `Node` 对象的 `link` 成员。

~~~c
struct Node {
    int value;
    struct Link link;
};

struct Link *p = ...;
struct Node *node =
    cmeta_container_of(p, struct Node, link);
~~~

偏移关系解释了目标地址，但仅有偏移不够。若外层对象起始地址为 `b`，成员偏移为 `k`，则真实成员地址为 `b + k`，减去 `k` 才回到 `b`。推导前提包括成员关系、对象生存期、对齐和所用编译器的指针语义；不能从任意同类型指针推断这些前提。

CMeta 用本地类型能力检查成员指针类型，并提供显式 `MemberType` 的 `cmeta_container_of_as` 入口。类型相同仍不证明指针来自正确对象。该习惯用法应按受支持工具链及库契约使用，不把一行字符指针减法说成对任意严格 C11 实现都成立的通用证明。

## 6. 编译期选择与静态描述各有用途

下面的片段假定三个打印函数已声明。`_Generic` 按控制表达式的类型选择一个函数，控制表达式本身不求值；末尾的 `(x)` 才是实际调用实参。

~~~c
#define print_value(x) _Generic((x), \
    int: print_int,                  \
    long: print_long,                \
    double: print_double             \
)(x)
~~~

这可消除调用方手写的有限类型分支，却不会发现结构体字段或返回值清理责任。反射描述符保存这些事实，函数指针或直接调用执行行为。**所有权（ownership）**说明谁负责资源释放或转交；**借用（borrow）**允许在约定生存期内访问对象，且不取得释放责任。

已知函数仍可直接调用。外来描述符或动态模块则先做**准入检查（admission）**：检查类型、布局、ABI 和执行能力，保存有生存期限制的结果，之后复用。ABI 是应用二进制接口，规定已编译模块间的调用和布局。通过检查只说明当前契约相容，不让借用对象永远有效。

## 7. 作用域清理与资源责任

作用域清理属性可以在离开词法作用域时调用清理函数；它不知道指针是借用、独占还是已经移出。下面的伪代码展示两个按顺序取得的资源，`release` 必须对应各自的取得协议。

~~~text
acquire A
if A failed: return failure
acquire B
if B failed: release A; return failure
use A and B
release B
release A
~~~

**清理不变量。** 每个程序点记录“已经取得且尚未释放”的资源集合。取得成功才加入，释放完成才移除；正常路径逆序清理 B、A，第二次取得失败的路径只清理 A。因此每个成功取得的资源恰好释放一次。若发生所有权转移，应从当前清理集合移除，并把责任交给新所有者。这个推导不覆盖进程被终止、未定义行为或未纳入协议的非局部控制转移。

**租约（lease）**在 Plugin 中是显式持有代码与数据生存期的凭据，不是计时到期的网络租约。即使一次函数调用已经返回，后续销毁回调仍可能依赖模块代码，因此租约要保持到最后一次相关清理之后。跨越异步等待的对象不能仅凭原栈帧的作用域清理保证安全。

## 8. 从 Linux 习惯用法取得可验证的规则

本书固定参考 Linux 提供的有限映射、单次求值、成员恢复和作用域清理模式。参考点见 `SOURCE_SNAPSHOTS.md`；内核扩展不是整个库的可移植性承诺。

| 内核参考 | 提炼的规则 | CMeta 中检查的位置 |
|---|---|---|
| `include/linux/syscalls.h` | 同一参数行生成多种声明 | 有限 pair map 与分隔策略 |
| `include/linux/minmax.h` | 捕获实参后比较，并检查类型 | 本地类型能力与一次求值 |
| `include/linux/container_of.h` | 成员类型和真实包含关系都重要 | 成员检查与调用方对象前提 |
| `include/linux/cleanup.h` | 自动触发清理仍依赖资源协议 | 编译器属性、作用域和资源所有者 |

验证时先用 `cc -E` 检查生成结果，再分别准备应编译通过和应拒绝的例子。运行检查验证副作用次数和正常、失败清理路径；跨编译器检查则确认能力声明真实。汇编与基准可以检验实际调用开销，但编译成功本身不能证明“零成本”。

## 9. 小结

普通函数处理值，有限宏生成声明，编译器能力提供本地类型与作用域支持，描述符共享稳定事实。每一种技巧都有自己的证明对象：求值次数、行投影、成员关系或资源集合。先写清这些前提，再组合机制，才能从高级接口追踪到普通 C 实际执行的步骤。
