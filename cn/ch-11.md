# 第十二章：Actor：邮箱、串行修改与对象生存期

多个生产者向同一个连接状态机发送事件时，需要共享发送能力，同时避免任何生产者直接修改状态或在销毁后访问失效对象。Actor 在 Machine Instance 外增加生命周期、独立生产者引用和关闭协议。它复用前章的转移语义，新增的是并发准入与资源控制。

## 1. 所有者与生产者引用

固定快照公开两个不透明句柄：

~~~c
typedef struct cflow_actor {
    void *impl;
} cflow_actor;

typedef struct cflow_actor_ref {
    void *impl;
} cflow_actor_ref;
~~~

`cflow_actor` 持有根引用并控制运行实例；`cflow_actor_ref` 是独立持有的生产者能力。两者都要求零初始化，通过对应 API 获取和释放，不能直接赋值复制一个拥有引用并把两份都释放。

**能力（capability）**在这里指按协议持有、可用于某项操作的句柄。它不是仅凭一个地址猜测对象是否仍存在。所有者销毁后，独立引用还能安全查询到 STALE，因为控制块在最后一个生产者引用释放前继续存在。

下面是基于已成功初始化 `actor` 的片段。生产者间如何传递引用还需应用自己的同步；不要在另一线程使用 `producer` 时同时释放同一个句柄。

~~~c
cflow_actor_ref producer = {0};
cflow_actor_ref second_producer = {0};

if (!cflow_actor_ref_acquire(&actor, &producer))
    return false;
if (!cflow_actor_ref_retain(&producer, &second_producer)) {
    cflow_actor_ref_release(&producer);
    return false;
}

/* Publish each reference to its producer with proper synchronization. */
/* After both producers have stopped using their respective handles: */
cflow_actor_ref_release(&second_producer);
cflow_actor_ref_release(&producer);
~~~

## 2. 发送在一个提交点建立责任

`cflow_actor_ref_try_send` 在 Actor 的生命周期门控下，把事件复制进固定容量邮箱。以下是控制关系伪代码，门控实现必须遵守公开接口的非阻塞准入契约。

~~~text
try_send(ref, event):
    safely access the retained control block
    if ref is stale: return STALE
    if lifecycle is not RUNNING: return its specific rejection
    require valid event identity, payload type, and storage
    require mailbox capacity
    atomically admit one bounded payload copy
    return ACCEPTED
~~~

检查失效引用应先于解析载荷，避免从已撤销能力继续推断事件模式。生命周期和邮箱提交需要被同一套同步规则约束：不能先看到 RUNNING，释放保护，再在停止之后无条件追加消息。

被拒绝的发送保持队列不变。ACCEPTED 则恰好增加一个事件，不表示已执行 Machine 动作，也不取得输入事件视图的所有权。固定快照仅在调用期间借用输入视图，成功时保存有界的平凡载荷副本；若载荷包含指针，复制指针字节不能延长所指对象的生存期。

## 3. 队列不变量与多个生产者

设邮箱容量为 `K`，当前排队序列为 `Q`。准入维持 `0 <= |Q| <= K`。拒绝路径返回前不修改 `Q`；接受路径在确认 `|Q| < K` 后追加一个事件，因此新长度不超过 `K`。这个推导要求检查与追加在其他生产者看来是一个提交操作。

两个生产者 P、R 同时调用时，FIFO 指邮箱提交顺序，不是调用开始的墙钟顺序。P 先进入函数但在提交前被暂停，R 可以先提交；消费者先取 R 的事件仍然符合 FIFO。验证应记录提交序列，不能用线程打印顺序代替。

| 发送结果 | 队列变化 | 生产者下一步 |
|---|---|---|
| ACCEPTED | 追加一次 | 原始输入视图可结束借用 |
| FULL | 不变 | 按应用策略等待、拒绝请求或稍后显式重试 |
| NOT_STARTED、STOPPING、STOPPED、FAILED | 不变 | 处理对应生命周期 |
| STALE | 不变 | 释放失效引用，不能继续使用原运行实例 |
| TYPE_MISMATCH 或 INVALID_ARGUMENT | 不变 | 修正事件契约或存储 |

库的发送路径不会自动阻塞等待空间、扩容、重试、覆盖旧消息或静默丢弃。上层若选择重试，应另行约束截止时间和重复发送；只能重试明确未被接受的那次投递。

## 4. 串行修改复用 Machine 语义

Actor 拥有 Machine Instance、邮箱、用于连接输出的图与 Subscription，以及生命周期控制块。它借用不可变 Machine、SerialExecutor、并发 Scheduler、类型描述和回调上下文。执行器串行推进转移，调度器推进订阅；两者承担不同职责。

~~~text
drain_accepted_work:
    take the next admitted event from the instance mailbox
    perform the Machine selection, staging, and commit protocol
    expose each committed observation through the owned subscription
    settle the event before advancing the serialized state owner
~~~

这是概念上的分工，不是另一个 Actor 专属转移算法。**单修改者（single mutable owner）**表示同一状态同时只有一个转移拥有修改权，不要求每个 Actor 都拥有一条专用线程。生产者线程只做准入，不能在 send 栈上直接执行连接动作。

## 5. 生命周期先关闭入口

| 生命周期 | 接受新事件 | 后续规则 |
|---|---|---|
| START | 否 | 显式启动后进入 RUNNING |
| RUNNING | 是，仍受类型和容量限制 | 处理事件或开始停止 |
| STOPPING | 否 | 关闭实例并终结在途工作 |
| STOPPED | 否 | 终态，不重新启动 |
| FAILED | 否 | 保留失败并终结资源，不隐式重启 |

`cflow_actor_request_stop` 先停止接受，再关闭拥有的实例。Machine close 取消排队事件并保留在途转移的提交规则；不能把 Actor 停止描述为保证排队消息全部执行。若需要应用级“全部处理完再停”，应另行设计确认协议。

FAILED 是 **吸收态（absorbing state）**：普通后续操作不会把它变回运行态。监督器（supervisor）若要创建新实例或重试请求，是应用的明确策略；新的运行身份不能复用旧引用来伪装连续运行。

## 6. 失效引用与销毁顺序

仅给裸指针附加一个 generation（代号）不能解决释放后访问：读取代号本身就可能解引用已释放内存。固定快照采用被独立引用持有的控制块，才能在所有者消失后安全报告 STALE。

~~~text
destroy_owner:
    serialize owner-side control operations
    mark retained producer references stale
    close the owned instance and subscription synchronously
    clear the owner handle
    release the root reference
    reclaim the control block only after the last producer releases
~~~

第九章的 **静止（quiescence）**指可能访问资源的在途回调已经结束，而不只是设置了一个停止标志。Actor 的借用 Machine、执行器、调度器和回调上下文必须活到 destroy 返回，执行器与调度器在此期间仍需能够工作。过早关闭它们可能使 Actor 无法完成自己的终结。

回调不在 Actor 门控锁内运行，因此允许自发送和请求停止；这不允许从回调中等待 Actor 或销毁它。等待与销毁会依赖当前回调结束，形成与前章相同的自等待问题。

## 7. 形式模型为何可以组合

`send_accepted_only_running` 把成功接受限制在 RUNNING；`send_accepted_appends_once` 证明一次追加；`send_rejected_preserves_queue` 证明拒绝保持队列。证明按引用有效性、生命周期和邮箱检查分支展开：所有失败分支返回原队列，唯一成功分支调用邮箱的合法追加。

`accepted_handoff_refines_machine` 将已接受事件的交接连接到原 Machine 语义。它避免为 Actor 发明第二套状态提交含义。`requestStop_cancels_pending` 与终态定理则约束关闭和失败后的行为。源文件见 [Proofs/Actor.lean](https://github.com/qigao/salts/blob/a650262031e9b3e5f11a227a7911a75db9ae1fb8/formal/cmeta_cflow_calculus/CMetaCFlowCalculus/Proofs/Actor.lean)。

这些定理在模型内成立。C 中控制块引用、并发门控、回调生存期和调度器进展仍需相应验证。实际 API 与所有权说明见 [actor.h](https://github.com/qigao/salts/blob/a650262031e9b3e5f11a227a7911a75db9ae1fb8/cflow/include/cflow/actor.h)。

## 8. 验证连接 Actor

把第十一章的连接 Machine 放入容量二的 Actor，使用多个生产者同时发送类型正确的事件。检查接受数、拒绝数与邮箱提交序列，验证同一时刻只有一个转移执行，并在 STOPPING 后继续尝试发送，确认没有新事件进入。

第二组测试保留独立生产者引用后销毁所有者，再发送一个有效事件及一个载荷错误的事件；两者都应先报告引用失效。最后释放引用，配合内存检查确认控制块只在最后一次释放后回收。销毁必须遵守所有者侧串行控制，不能用测试主动违反句柄并发访问契约。

作为练习，分析“FULL 后立即无限重试”的生产者为何可能占满 CPU 却不能保证进展，再设计有截止时间的应用策略。策略应保留一次成功准入只对应一个事件的性质。

## 9. 小结

Actor 增加可撤销的生产者能力、生命周期检查和并发邮箱准入，状态转移仍由 Machine 定义。安全发送依赖受保护的控制块，正确关闭依赖先关入口再终结在途工作。FIFO 对应提交顺序，单修改者对应状态修改权限；它们都不等同于调用开始顺序或专用线程。
