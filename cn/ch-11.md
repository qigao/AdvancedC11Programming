# 第十二章：Actor：邮箱、串行修改与对象生存期

多个生产者向同一状态机发送事件时，需要限制排队容量，并保证同一实例的状态不会被同时修改。本章用邮箱、身份与代次标识包装已有状态机，分别展开发送和取出执行的算法。证明围绕接受事件的条件、单一修改者、关闭顺序和过期引用展开。

## 1. Identity：Owner 与 Producer Ref 分开

Actor owner 可以近似：

~~~c
typedef struct actor {
    actor_id id;
    uint32_t generation;

    actor_lifecycle lifecycle;

    mailbox inbox;
    machine_instance machine;
    cflow_executor executor;
} actor;
~~~

Producer 不持有 actor 指针：

~~~c
typedef struct actor_ref {
    actor_id id;
    uint32_t generation;
} actor_ref;
~~~

所以 **pointer address != actor identity**。reload/recycle 后 generation 变化，旧 ref 自动变成 STALE。

## 2. Admission 与 Single-Owner Drain

~~~text
send(registry, ref, event):

    actor = registry.resolve(ref.id)

    if actor == null:
        return STALE

    if actor.generation != ref.generation:
        return STALE

    if actor.lifecycle != RUNNING:
        return CLOSED

    if actor.inbox.full:
        return FULL

    actor.inbox.push(event)

    schedule_drain_once(actor)

    return OK
~~~

这里不执行 Machine transition：**send 只负责准入检查，drain 才负责 execution**。

### 2.1 Rejected Send 不改变 Queue

这是最小但重要的 contract：

~~~text
send(ref,e) = STALE | CLOSED | FULL
───────────────────────────────────
mailbox_after = mailbox_before
~~~

所以不能先 push、再发现 lifecycle closed、最后尝试 rollback。Admission 必须在 commit queue mutation 前完成。

### 2.2 Drain Algorithm：Multiple Producers，Single State Owner

~~~text
drain(actor):

    require execution_context owns actor mutation

    while actor.lifecycle permits draining:

        event = actor.inbox.try_pop()

        if none:
            break

        result = machine_step(actor.machine, event)

        settle(event, result)

    clear_scheduled_flag(actor)

    if inbox not empty
       and lifecycle permits draining:
        schedule_drain_once(actor)
~~~

多个 producer 可以同时 send。但必须保持 **`machine_step` concurrent count <= 1**。这是 Actor 真正提供的可变-state isolation。

## 3. Lifecycle 与 Failure

~~~text
CREATED
  start -> RUNNING

RUNNING
  send accepted
  request_stop -> STOPPING
  failure      -> FAILED

STOPPING
  no new send
  drain/cancel existing accepted work
  settled -> STOPPED
  failure -> FAILED

STOPPED
  terminal

FAILED
  terminal
~~~

关键顺序：

~~~text
request_stop:
    close admission first
    then settle accepted work
~~~

不能先 wait queue empty 再 close 准入检查，否则新的 producer 可以不断填入。

### 3.1 Actor 不拥有线程

Manual Executor、Serial Executor 和单线程 event loop 都可以满足同一 Actor 契约。因此 **Actor 语义不等于专用线程**。Actor 只要求状态修改被串行化，具体怎样实现这一保证由 Executor 决定。

### 3.2 Failure / Identity Rules

#### Stale before event validation

对于 old ref + malformed event，首先返回 `STALE`，因为旧 ref 没有 authority 调用这个 actor。不要先解析/验证 payload 再发现 ref 已失效。

#### STOPPING

当 `lifecycle = STOPPING` 时，新的 `send` 返回 `CLOSED`；已经 accepted 的 work 继续 settle。

#### FAILED

`FAILED` 默认是 absorbing state。不要偷偷 restart。如果需要 supervisor/restart，那是更高层 policy。后面的 formal model只需要证明 lifecycle gate、queue preservation 和 Machine refinement，而不是重新证明 Machine transition。

## 4. 从 Actor 外壳到 Canonical Actor

前十八节已经得到 Actor 的最小定义：它不是“一条线程”，而是在既有 Machine 语义外增加有界 mailbox、non-blocking 准入检查、single 可变 owner、显式 lifecycle，以及 owner/reference/stale identity 边界。多 producer 只增加并发准入检查，不增加并行 state mutation。

后半章不再扩展 Supervisor、Effect 或“大一统模型”，而是用 canonical Actor 检查这层外壳究竟新增了什么：只有 `RUNNING` 接受 send；被拒绝的 send 不改变 queue；`STOPPING` 先关闭准入；`FAILED`/`STOPPED` 是终止状态；已接受的 handoff 继续 refine 原来的 Machine transition。随后再核对 Lean 模型、当前 C 所有权、identity 和并发/生命周期证据。

### 4.1 Canonical Actor：给同一个 Connection Machine 加并发外壳

前一章的 Machine 已经解决 Event typing、Transition selection、Guard/Action、Atomic commit、State typing 和 Terminal semantics，Actor 不应该重新实现这些逻辑。Actor 真正新增的问题是：

- 谁可以发送？
- 什么时候允许发送？
- 消息在哪里等待？
- 哪个 execution owner 修改状态？
- owner 销毁以后旧 producer ref 怎么办？
- 运行时 failure 如何进入 lifecycle？

因此应把 Connection Actor 拆成两条不同语义的路径。

**Admission path**：箭头表示 message 被 admission/copy 到 mailbox。

~~~text
many producer refs
      ↓ send/admission
Actor admission gate
      ↓ accepted event copy
bounded typed mailbox
~~~

**Serialized execution path**：箭头表示 accepted event 被单 owner 执行。

~~~text
bounded typed mailbox
      ↓ dequeue
Serial Executor
      ↓ owns mutation context
single Machine Instance
      ↓ execute
Connection Machine SmallStep
~~~

Actor owns 一个 Machine Instance；Serial Executor 只负责保证它的 mutation context 串行化。这里不是“一 Actor 一线程”的模型。真正不可妥协的是：

同一个 Actor 的 Machine-owned 可变 state 同时只有一个 transition owner。它是否拥有专用 OS thread，只是 execution policy。

## 5. Semantic Contract：Actor 只增加 lifecycle/准入检查，不增加 transition meaning

### 5.1 Lifecycle 是 Actor 自己的新语义

Machine 有自己的 terminal state。Actor 还需要独立 lifecycle：START、RUNNING、STOPPING、STOPPED、FAILED。为什么不能直接复用 Machine state？因为：

| 状态 | 含义 |
|---|---|
| Machine state | application/domain control state |
| Actor lifecycle | 运行时所有权/准入检查 state |

例如 Connection Machine 可能当前仍是 `Connected`，但 Actor lifecycle 已经进入 `STOPPING`。此时 domain state 与运行时准入检查必须能同时存在。

### 5.2 Send 第一阶段只做 Actor-gated 准入检查

Producer ref 的 send 不应该直接运行 Machine transition。它只做：

~~~text
is ref live?
is Actor RUNNING?
is event id/type valid?
is mailbox capacity available?
      ↓
copy into mailbox
      ↓
return exact status
~~~

因此 send status 可以精确区分 `ACCEPTED`、`INVALID_ARGUMENT`、`TYPE_MISMATCH`、`FULL`、`NOT_STARTED`、`STOPPING`、`STOPPED`、`FAILED`、`STALE`。这些状态不是“错误字符串”。它们是 producer policy 的输入。

### 5.3 Rejected send 必须保持 queue 不变

如果 send 返回：

~~~text
FULL
STOPPING
STOPPED
FAILED
STALE
TYPE_MISMATCH
~~~

底层不能部分写入、覆盖旧消息、偷偷 drop 另一条消息、自动 retry 或改变 Machine state。所以 rejected 准入检查的关键 contract 是：

~~~text
mailbox after
=
mailbox before
~~~

这与 Executor 的 rejected task 所有权是同一种设计。

### 5.4 Multiple Producers 不改变 FIFO / single-使用方 semantics

多个 producer 只意味着多个线程可以并发尝试准入，并不意味着多个线程可以并发执行 transition。Mailbox commit 可以采用 MPMC 准入，但 Machine execution 仍然只有**一个使用方和一条串行 transition stream**。这样，“给整个 domain object 加锁”的问题就被拆成了并发 enqueue 与串行状态修改。

### 5.5 Actor Owner 与 Producer Ref 必须分开

如果 producer 直接持有 Actor owner pointer，那么 destroy 以后最危险的问题是：

~~~text
旧 producer 仍然调用 send
    ↓
use-after-free
~~~

所以需要两个概念：

| 对象 | Ownership |
|---|---|
| Actor owner | owns root reference and lifecycle control |
| Actor ref | independently retained producer capability |

destroy owner 时，不需要立即让整个小 control block 消失。可以：

~~~text
mark refs stale
close runtime
release root
wait until last producer ref released
    ↓
reclaim control block
~~~

这样 STALE 就成为显式 semantic status，而不是野指针行为。

### 5.6 Stale classification 应先于 Event validation

一个已经 stale 的 producer ref 即使同时携带未知 event id 或错误 payload type，首要事实仍然是：**这个引用已经不再指向活动 Actor**。因此 stale 应优先分类，避免调用方继续从一个已经失效的运行时 capability 推断 schema 或生命周期状态。

### 5.7 STOPPING 必须先关闭准入检查

`request_stop` 的第一个效果应该是 **no new messages admitted**；然后才 cancel/close queued 运行时、settle in-flight work、transition to `STOPPED`. 否则在 shutdown 过程中 producer 仍然不断加入新消息，系统就没有有限的 settlement boundary。

### 5.8 FAILED 应成为 terminal lifecycle，而不是隐式 restart

如果底层 Machine/Subscription/运行时失败：

~~~text
Actor -> FAILED
~~~

后续 send 明确返回 `FAILED`，而不是静默创建新的 Machine Instance、重试消息，或用旧/新状态自动 restart。自动重启属于 Supervisor/Application policy，不应藏进 Actor primitive。

## 6. Lean：Actor formal model 只增加 lifecycle gate，并复用 Machine semantics

本版 formal calculus 已经包含 `CMetaCFlowCalculus/CFlow/Actor.lean` 与 `CMetaCFlowCalculus/Proofs/Actor.lean`。模型非常符合本章目标：

~~~text
Actor.State
    lifecycle
    mailbox
    live
~~~

注意：

> Actor formal state 甚至没有复制一份 Machine transition state。

这正好强调：**Machine/Mailbox remain authoritative；Actor 只增加 lifecycle 准入检查 boundary。**

### 6.1 State.Valid：Lifecycle 与 Mailbox terminal 必须一致

formal Actor.Valid 要求：

~~~text
mailbox.Valid
+
mailbox.terminal
=
lifecycle.expectedMailboxTerminal
~~~

其中：

~~~text
START/RUNNING
    → mailbox OPEN

STOPPING/STOPPED/FAILED
    → mailbox CANCELLED
~~~

这样 lifecycle 不是一个与 Mailbox 无关的 flag。它直接约束准入检查 substrate。

### 6.2 start / requestStop / settle / fail 全部 preserve Valid

已有定理 `start_preserves_valid`、`requestStop_preserves_valid`、`settle_preserves_valid` 和 `fail_preserves_valid`。这说明 Actor lifecycle 与 Mailbox terminal 不能进入互相矛盾的组合。例如：

~~~text
Actor STOPPED
+
Mailbox OPEN
~~~

在模型里就不属于 Valid state。

### 6.3 requestStop_cancels_pending

已有定理 `requestStop_cancels_pending`。对于 START/RUNNING：

~~~text
requestStop
    ↓
mailbox queue = []
mailbox terminal = CANCELLED
~~~

这精确表达 shutdown 准入检查 boundary。Actor 不只是把 `state = STOPPING`，还要把消息入口同时终止。

### 6.4 send_accepted_only_running

已有定理 `send_accepted_only_running`，证明如果 send 返回 ACCEPTED，那么 before 必须：

~~~text
live = true
lifecycle = RUNNING
~~~

这给 producer API 一个非常强的 semantic statement。

### 6.5 send_accepted_appends_once

已有定理 `send_accepted_appends_once`，证明一次 accepted send：

~~~text
queue_after
=
queue_before ++ [event]
~~~

这同时表达 no overwrite、no duplicate insertion，以及 abstract 准入检查 layer 不发生 hidden reordering。

### 6.6 send_rejected_preserves_queue

对应地，`send_rejected_preserves_queue` 证明所有非 ACCEPTED 结果：

~~~text
queue_after
=
queue_before
~~~

这给出了有界、非阻塞准入算法需要保持的性质。

### 6.7 STOPPED / FAILED 是 absorbing lifecycle

已有定理 `stopped_cannot_restart`、`failed_cannot_restart`、`stopped_is_terminal` 和 `failed_is_terminal`。所以 primitive Actor 不提供隐式 resurrection。如果系统想 restart：

> 创建新 Actor / 使用更高层 Supervisor protocol。

### 6.8 accepted_handoff_refines_machine：Actor 不发明新的 transition

最关键的定理是 `accepted_handoff_refines_machine`。它把一次 Actor handoff 定义成一个 **refinement mapping**，不是新增第二套 transition：

~~~text
Actor send accepted
      ↓ same Event admitted
Mailbox receives exact same Event
      ↓ hand off to existing semantics
existing Machine RuntimeStep
~~~

并证明：

~~~text
Actor was live/running
event appended once
same event received
Machine after.trace
=
before.trace ++ Machine traceSuffix
~~~

这条定理非常漂亮地说明：

Actor 只是准入检查/lifecycle shell；真正的 domain state transition 仍然由第十一章的 Machine semantics 决定。没有 Actor-specific “第二份 commit state”。这正是组合式架构最重要的验证之一。

## 7. Current C Implementation 与 Runtime Identity

本版 CFlow Actor API 明确区分：

| Handle | Ownership |
|---|---|
| cflow_actor | owner handle |
| cflow_actor_ref | independently retained producer handle |

两者都是 opaque handle，但所有权不同。

前面用 `actor_ref { id, generation }` 解释 stale identity，那是**语义教学模型**，不是公开 ABI 的字段布局。固定快照实际公开的是两个零初始化 opaque handle：

~~~c
typedef struct cflow_actor {
    void *impl;
} cflow_actor;

typedef struct cflow_actor_ref {
    void *impl;
} cflow_actor_ref;
~~~

generation/invalidation 事实由内部 retained control block 表达，使用方不能读取 `impl` 来猜 Actor 是否仍然有效。生产者必须通过 acquire/retain/release 协议持有 capability：

~~~c
cflow_actor_ref producer = {0};
cflow_actor_ref second_producer = {0};

if (!cflow_actor_ref_acquire(&actor, &producer))
    return false;

if (!cflow_actor_ref_retain(&producer, &second_producer)) {
    cflow_actor_ref_release(&producer);
    return false;
}

/* 用同步机制把各自的 ref 发布给对应 producer。 */

/* producer 生命周期结束后，每个独立 ref 各释放一次。 */
cflow_actor_ref_release(&second_producer);
cflow_actor_ref_release(&producer);
~~~

普通 C 赋值：

~~~c
second_producer = producer;
~~~

**不是 retain**。如果随后把两个变量都 release，就会把一个 ownership token 当成两个；正确复制 capability 必须调用 `cflow_actor_ref_retain`。

owner destroy 与 producer ref 也故意解耦。假定 `event` 是按本章契约构造的有效 `cflow_event_view`：

~~~c
cflow_actor_ref producer = {0};

if (!cflow_actor_ref_acquire(&actor, &producer))
    return false;

/* owner-side serialization: destroy 关闭 runtime 并让 refs stale。 */
cflow_actor_destroy(&actor);

cflow_actor_send_status status =
    cflow_actor_ref_try_send(&producer, &event);

if (status != CFLOW_ACTOR_SEND_STALE) {
    cflow_actor_ref_release(&producer);
    return false;
}

cflow_actor_ref_release(&producer);
~~~

这里没有 use-after-free：`cflow_actor_destroy` 先把 control block 标记为 stale、关闭 runtime、清除 owner handle 并释放 root reference；control block 要等最后一个 producer ref release 后才回收。固定快照的 `cflow_actor_ref_try_send` 也在同一 gate 下先检查 stale，再检查 event/lifecycle，因此旧 capability 得到确定的 `CFLOW_ACTOR_SEND_STALE`，不会因为底层地址复用重新获得 authority。

### 7.1 Actor owns runtime shell

Actor owner 的所有权可以概括为：

| Owns | Borrows |
|---|---|
| Machine or Statechart Instance | immutable definition |
| bounded Mailbox | SerialExecutor |
| identity Graph | concurrent Scheduler |
| Subscription | guard/action bindings |
| lifecycle control block | callback contexts |
| root reference | type descriptors |

这让 destroy 顺序可以被明确写出来。

### 7.2 Scheduler 必须提供 CONCURRENT capability

为什么 Actor 外层 Scheduler 要 concurrent，而内部 Machine transition 仍然 Serial？因为两个层次解决不同问题：

| Capability | Responsibility |
|---|---|
| Scheduler | many Actors / async wakeups share execution resources |
| Machine SerialExecutor | one Actor's state mutation remains serialized |

所以 **concurrency outside, serialization inside** 并不矛盾。这是 Actor scalability 的核心。

### 7.3 Actor send 明确禁止隐藏行为

当前 producer send 契约直接承诺：**不阻塞、不自动重试、不覆盖、不扩容、不静默丢弃、不分配内存**。这是一条很强的有界运行时承诺；`FULL` 就意味着确实已满。应用若要稍后重试、丢弃最新/最旧消息、让请求失败，或向上游施加 backpressure，必须显式选择策略。

### 7.4 Owner destroy 先让 refs stale，再回收 root

destroy contract 是一条 **所有权/lifecycle sequence**：

~~~text
mark producer refs stale
      ↓ close live runtime
synchronously close selected instance/Subscription
      ↓ detach owner
clear owner handle
      ↓ release root ownership
release root reference
      ↓ wait for retained producer refs
last producer ref releases
      ↓ reclaim
control block reclaimed
~~~

所以 producer 可以安全得到 STALE，而不是访问已经 free 的 owner object。

### 7.5 Identity：为什么 Actor 不能只靠 pointer address

Actor identity 至少有两层。

#### 7.5.1 Runtime object identity

一个 producer ref 必须知道自己是否仍绑定到 the same live Actor generation/control block。owner destroy 以后，pointer-shaped capability 不能继续表示有效身份。STALE 是 identity/生存期的联合结果。

#### 7.5.2 Domain identity

更高层系统还可能需要 user actor、device actor、connection actor、order actor 这类 domain key。它不应该等于运行时 address。Actor 运行时可以更换/重建，但 domain identity 是否延续是 Supervisor/Application policy。所以这本书继续坚持：

address is representation location, not semantic identity. 这和 Type 描述符、Callable、Graph certificate 的 identity 问题属于同一条主线。

## 8. Evidence：Actor 必须验证 concurrent 准入检查 + serialized mutation + lifecycle

### 8.1 Bounded multi-producer admission

并发 producer 同时 send，必须验证：

- accepted count <= capacity available；
- FULL does not alter queue；
- accepted events each appear exactly once；
- no silent drop。

队列顺序应按 documented mailbox commit/FIFO contract 验证，而不是假设 producer call-start 顺序。

### 8.2 Single mutable owner

Machine transition instrumentation 应验证 **in-flight transition count <= 1**，即使 many producers、concurrent scheduler 和 shared worker pool 同时存在。这比“没有 crash”更能证明 Actor semantic isolation。

### 8.3 Lifecycle admission matrix

分别测试：

~~~text
START
    send → NOT_STARTED

RUNNING
    send → ACCEPTED/FULL/type error

STOPPING
    send → STOPPING

STOPPED
    send → STOPPED

FAILED
    send → FAILED

owner destroyed + retained ref
    send → STALE
~~~

### 8.4 Ref lifetime / stale stress

Ref 生存期 / stale stress 应按顺序覆盖：

1. acquire many refs；
2. concurrent send；
3. owner destroy；
4. refs observe STALE；
5. release refs in arbitrary order；
6. last ref frees control block。

并放入 sanitizer/stress gate。这是 Actor C implementation 最容易出 use-after-free 的地方。

### 8.5 Actor-to-Machine refinement evidence

选定前一章的 Connection Machine，发送同一串 `Connect`、`ConnectedEvent`、`Disconnect`、`ClosedEvent`，分别走直接 Machine Instance 路径与 Actor mailbox/ref 路径；比较最终 Machine state、observation trace、消费事件数和首个错误，结果应保持一致。这就是 `accepted_handoff_refines_machine` 在 C 侧的差分对应检查。

### 8.6 Failure evidence

人为触发 Machine Action 失败、Subscription 失败和 Scheduler 准入失败，检查 Actor 是否只进入一次 `FAILED`、拒绝后续 send、保留首个失败、不隐式 restart，并正确 settle 所有权。

## 9. CNet 2.3 SG + ACE Strategy：何时不需要 Actor 外壳

这一节是**后续已发布 SDK 的独立对照**，不是本章固定版 Actor 实现的改写。证据锚点为 Salts `v2.3.0-rc.4` 的 `cnet/owner_placement.h`、`destination_policy.h`、`handoff.h`、`manager.h` 和 `client_pool.h`；可执行验证见 [`qualification/ch12_cnet_strategy.c`](../qualification/ch12_cnet_strategy.c)。CI 总是使用最新已发布 SDK，不按这个源码标签固定消费版本。

本章前面的 Actor 模型解决的是**应用级消息准入、邮箱和状态变更的串行化**。如果连接的真实 I/O 和所有权已经由 CNet Sharded Graph（SG）管理，额外创建 Actor 不会自动改善连接处理，反而可能重复队列、生命周期和执行路径。首先选择普通 C + 现有 CNet Owner：

~~~text
listener accepts detached TCP stream
  -> server cnet_owner_placement_choose()       # only an advisory choice
  -> cnet_handoff_reserve/publish()              # real bounded credit; moves stream
  -> final Owner: take -> cnet_manager_adopt()   # CNet owns transport progress
  -> Owner drives CNet and manager.advance()
  -> terminal + context/lease settlement        # then return handoff credit
~~~

上述流程是多 Owner 场景的**示意伪代码**，不是所有调用都在同一线程执行。特别是 `choose()` 成功不等于已保留容量；`publish()` 成功转移 detached stream，不能在生产者侧重复关闭或发布；`handoff_destroy()` 之前还须保证生产者与唤醒尾部真正静止。已经建立的连接不会因为 placement 策略再次执行而迁移 Owner。

两种 Strategy 作用于不同维度，不能混用：

| 边界 | 选择依据 | 关键不变量 |
|---|---|---|
| Server Owner Placement | SG 中的最终本地 Owner | `STRICT_KEY` 依据 `key_hash % owner_count`；选中的 Owner 满额时拒绝，不偷偷迁移 |
| Client Destination Policy | 远端 Endpoint 集合 | `STRICT_KEY` 对稳定 `endpoint_id` 做 rendezvous hashing；不是数组下标；对不可用 winner 拒绝而非改选 |
| Client Pool | Owner 内已真正 protocol READY 的物理连接 | 真实协议 slot/lease 必须准入；不创建连接、线程、等待或自动重试 |
| Recovery / Retry | 传输恢复与**逻辑请求重试**各自的许可 | `CONNECTED != protocol READY`；不能从恢复 TCP 推导允许重放业务 DATA |

客户端的普通 C 控制流同样是**先选择、再实际准入**：

~~~text
remote_candidate = destination.choose(eligible_snapshot)
if candidate rejected: report the error; do not silently choose another
connection = owner_local_pool.try_acquire(compatible_key, protocol_slot)
if no READY lease: caller explicitly decides whether/when to dial
logical_request_retry = retry.evaluate(application + protocol evidence)
~~~

`CMeta` 的 `CMETA_INTERFACE` 可以提供 ACE 风格的**有类型 Strategy/Observer 回调**，把选择结果交给普通 C 函数；它不会因此创建第二个 Reactor、Proactor 或连接对象。只有应用真的要求独立的 mailbox、producer identity、typed event 和额外状态机时，才考虑本章 Actor 的那层语义。

这里的核心可检查条件是：`policy selection != capacity reservation`，`transport connected != protocol ready`，`reconnect != application retry`。这些都是实际 API 的准入约束，而不是“用了 SG 所以自动正确”的推断。

### 9.1 两个真实 SG Owner：TCP handoff 与回收

前面的 `ch12_cnet_strategy.c` 只证明策略选择的准入与拒绝条件，不会创建 socket。另一个严格 C11 安装版测试 [`qualification/ch12_cnet_sg_handoff.c`](../qualification/ch12_cnet_sg_handoff.c) 则真正运行两个 NativeIO SG shard，分别持有独立的 host lease 和 external CNet client。它使用本机回环 TCP，不是模拟 accepted stream。

~~~text
Owner 0                               Owner 1
listener.accept_detached()
  |                                      |
placement.choose(1)                     |
handoff.reserve()  -- bounded credit -->|
handoff.publish(socket) ---------------> handoff.take()
                                         manager.reserve()
                                         manager.adopt(socket)
CNet sends "ping" ---------------------> CNet receives "ping"
CNet receives "pong" <------------------ CNet sends "pong"
CNet terminal                           CNet terminal
listener/client cleanup                 manager.advance() -> recycle
                                         handoff.release(ticket)
         final SG barrier  ->  inbox seal/destroy  ->  SG shutdown
~~~

每个 Owner 的进展回合仅执行一次 `native_io_sharded_context_observe_host()`，再调用 `cnet_sg_host_route_batch()` 分发 NativeIO completion。回调通过线程 Owner token 检查亲和性。Producer 在 `publish` 成功后失去 detached socket 所有权；最终 Owner 经过 `take`、`adopt`、实际数据接收、terminal 和 Manager recycle 才归还 credit，重复 `release` 必须失败。主线程在两个方向的发送与接收均完成之后才授权关闭，避免将 send completion 错当作对端已消费。

这个测试是**一次完整的真实 TCP 路径**，实际执行在最新版已发布的安装版 SDK 上；它不是高并发压力测试、多设备测试或性能比较。CNet SG 的 backend、connection 和 callback 仍归各自 Owner 所有，应用不需要再创建 Actor mailbox。

## 10. CMeta + CFlow 的 ACE Active Object：真正需要应用邮箱时再引入

这一节引用的是**后续 Salts 2.3 公开 CFlow/ACE 实现**。新增安装版 C11 程序 [ch12_cmeta_ace_active_object.c](../qualification/ch12_cmeta_ace_active_object.c) 与上面的 CNet SG TCP handoff 是**两条不同的工程路径**。Active Object 适合独立的有类型应用事件和状态机，而不用于重新封装已有 SG transport。

### 10.1 一份有类型声明，两个明确的 Owner

应用首先用 `CMETA_INTERFACE` 声明 `book_ace_actor_port.send(int)` 和 `book_ace_actor_work.transform(int)`。`CMETA_IMPLEMENTS` 将两者绑定到普通 C：

~~~text
应用 Producer
  -> typed CMeta Port.send(value)
  -> cflow_actor_ref_try_send(typed event)      # admission, not execution
  -> CFlow Actor mailbox (capacity = 2)
  -> CFlow Machine action
  -> typed CMeta Strategy.transform(value)
  -> Subscriber receives one result
~~~

CMeta Port/Strategy 只是借用的 `{self,vtable}` 与 FunctionDesc/FunctionAbi；`CFlow Actor` 才拥有 mailbox、Machine Instance 和停止/取消状态，`CFlow Scheduler/Executor` 才拥有 worker 的执行能力。成功接受一次 `7` 后，测试的 Strategy 输出 `107`，只调用一次且只发布一次观察结果；这些值不是对所有 Actor 的性能结论。

### 10.2 STOPPED、STALE 与借用的生存期

~~~text
RUNNING: try_send(7) -> ACCEPTED -> one delivery(107)
request_stop -> wait -> STOPPED
STOPPED: try_send(8) -> STOPPED
actor_destroy, retained producer ref
STALE:   try_send(9) -> STALE
producer_ref_release -> release remaining ref authority
~~~

Port 中保存的是 **Producer Ref 的借用**，并不拥有 Actor；调用方保留 ref 直到验证 STALE，之后释放。所有 Strategy context 必须持续有效直到 Actor 停止，不能在 worker 仍可能访问时销毁。状态机的 mutation seriality 来自 CFlow 协议，不能从 CMeta 的 Interface 元数据推导。

### 10.3 与 Half-Sync/Half-Async、Pipes and Filters 和 CNet 的关系

客户端/服务器的网络收发仍由 `CNet/NativeIO` 完成。如果 CPU 业务必须与 I/O Owner 分离，使用显式有界 `CFlow Channel` 承接已复制的数据，再按需求选择 Graph 的 `Filter -> Map`、Scheduler 或应用 Actor。`FULL` 时由协议决定拒绝、背压或丢弃，绝不能假定 Channel 会无限扩容。只有应用拥有自己的 typed event、生命周期和状态修改语义时，才选择 Actor；仅仅为了跨 Owner 迁移 TCP socket，则应使用前一节的 SG handoff 而不是 Actor。

ACE 模式不是一个必须完整安装的“框架”：它们是对行为更改点、执行策略和生命周期责任的可验证分解。对并发连接，`Acceptor-Connector/Proactor + CNet SG` 与 `CMeta typed Strategy` 已足够；应用状态复杂化之后，再有选择地加入 `CFlow Active Object`。

## 11. 小结

Actor 将并发投递与串行执行分开：生产者提交有类型事件，邮箱限制待处理数量，单一执行者修改状态机实例。身份与代次用于拒绝已经失效的引用，地址复用不能让旧引用重新获得访问权。关闭时先停止接受新事件，再处理已接受事件的执行或取消与清理。并发队列的正确性、状态机转移语义和 Actor 生存期分别承担不同证明义务，组合时必须检查这些契约是否相容。
