# 第八章：从重复 API 契约到 Contract Compiler——DataBind IDL、FunctionDesc 与多后端生成

> **本章路线**
>
> 这一章不再列举 Serialization、RPC、Plugin、Workflow 等“高级应用”。我们只跟踪一个真实问题：**同一个业务操作为什么要在 C prototype、HTTP、RPC、Plugin、OpenAPI、Mock、WASM 里重复描述？**
>
> 然后一步一步把这些重复收成：
>
> ~~~text
> DataBind Contract IR
>         +
> generated native binding
>         +
> CMeta Native Semantic IR
>         ↓ compile/admit
> immutable DataBindBindingPlan
>         +
> exact DataBindNativeExecution
>         ↓
> HTTP / RPC / Plugin / WASM / OpenAPI / Mock
> ~~~
>
> 本章的目标不是发明更多 runtime。
>
> 目标恰好相反：
>
> **把更多决定提前到 compiler/control plane，让 runtime 只执行已经编译好的 plan。**

---

## 1. 从一个 C 函数到 Logical Contract

假设系统只有一个查询用户的函数：

~~~c
typedef struct UserRepository UserRepository;

typedef struct User {
    uint64_t id;
    const char *name;
} User;

int get_user(
    UserRepository *repo,
    uint64_t id,
    User *out_user);
~~~

这已经是很好的 C。

调用也很简单：

~~~c
User user = {0};

int rc = get_user(repo, 42u, &user);

if (rc != 0) {
    ...
}
~~~

如果程序只有一个调用点，不需要任何 IDL。

问题出现在这个 operation 开始被多个系统暴露。

---

### 1.1 HTTP 第一次重复描述它

一个普通 HTTP handler 可能是：

~~~c
static int get_user_http(
    void *ctx,
    const chttp_server_request_view *request,
    chttp_server_response *response)
{
    UserRepository *repo = ctx;

    const char *id_text =
        chttp_server_request_param(request, "id");

    uint64_t id = 0;

    if (parse_u64(id_text, &id) != 0)
        return chttp_server_reply(response, 400, "text/plain",
                                  "invalid id", 10);

    User user = {0};

    if (get_user(repo, id, &user) != 0)
        return chttp_server_reply(response, 404, "text/plain",
                                  "not found", 9);

    char json[1024];
    size_t json_size = encode_user_json(json, sizeof(json), &user);

    return chttp_server_reply(
        response,
        200,
        "application/json",
        json,
        json_size);
}
~~~

然后注册：

~~~c
chttp_server_get(
    server,
    "/users/:id",
    get_user_http,
    repo);
~~~

这里第一次重复出现 operation identity、输入字段 `id`、输入类型 `uint64`、结果 `User` 和 error mapping。HTTP 本身没有错。

重复知识开始出现。

---

### 1.2 RPC、OpenAPI、Plugin、Mock、WASM 再次重复

RPC 可能再写：

~~~c
crpc_server_register(
    rpc,
    "UserService.GetUser",
    get_user_rpc,
    repo);
~~~

OpenAPI 再描述：

~~~text
GET /users/{id}

parameter:
    id : uint64

response 200:
    User

response 404:
    NotFound
~~~

Plugin 再维护 export_id、contract_id、contract_version、function metadata 和 adapter。

Mock 再写一份函数签名。

WASM 再定义 host/guest ABI。

最后我们得到 C prototype、HTTP route/decoder、RPC method/decoder、OpenAPI、Plugin export、Mock declaration 和 WASM ABI。这些代码不一定逐行相同。

但它们共同维护一份事实：

> **UserService.GetUser 是一个 typed logical operation。**

这就是新的重复知识。

---

### 1.3 FunctionDesc 是 native truth，不是 logical contract

第三章已经把普通 C 函数描述成 `cmeta_function_desc`。

概念上：

~~~c
static const cmeta_param_desc get_user_params[] = {
    { "repo",     CMETA_TYPE(UserRepository_ptr), CMETA_IN },
    { "id",       CMETA_TYPE(uint64_t),           CMETA_IN },
    { "out_user", CMETA_TYPE(User_ptr),           CMETA_OUT }
};

static const cmeta_function_desc get_user_desc = {
    .name = "get_user",
    .return_type = CMETA_TYPE(int),
    .params = get_user_params,
    .param_count = 3
};
~~~

这告诉工具 **native C function 是什么**。

但它仍然没有回答：

- 业务操作叫什么？
- logical request 是什么？
- logical response 是什么？
- `repo` 是业务输入，还是 host dependency？
- HTTP/RPC/Plugin 是否应该看到 `repo`？

所以 **FunctionDesc != Service Contract**。

这就是为什么 Function Reflection 并不能替代 IDL。

---

### 1.4 DataBind IDL 描述 logical contract

现在把逻辑契约单独写出来：

~~~text
message GetUserRequest {
    uint64 id;
}

message GetUserResponse {
    User user;
}

service UserService {
    GetUser: GetUserRequest -> GetUserResponse;
}
~~~

这里没有：

~~~text
GET
POST
/path
RPC method alias
DLL name
WASM export
C function name
~~~

这很重要。

IDL 回答 **what is promised?**；CMeta 回答 **what is implemented in C?**。

---

### 1.5 Service、Channel、Component 的语义边界

DataBind 的核心 vocabulary 应该很小。

### Service

Service 表达 **Request → Response**。

例如：

~~~text
service UserService {
    GetUser: GetUserRequest -> GetUserResponse;
}
~~~

### Channel

Channel 表达 **Message / Event**。

例如：

~~~text
channel UserEvents {
    UserChanged;
}
~~~

### Component

Component 只组合 capability：

~~~text
component UserModule {
    service UserService;
    channel UserEvents;
}
~~~

它表示“哪些 capability 属于一个逻辑模块”，但不表示 DLL、process、HTTP server 或 WASM module；这些是后面的 projection。

---

## 2. Native Binding：Contract IR Join CMeta

compiler 可以为标准 Service ABI 生成 header：

~~~c
int user_service_get_user(
    const GetUserRequest *request,
    GetUserResponse *response);
~~~

用户只写：

~~~c
#include "user.generated.h"

int user_service_get_user(
    const GetUserRequest *request,
    GetUserResponse *response)
{
    User user = {0};

    if (repository_get(
            global_repository(),
            request->id,
            &user) != 0) {
        return USER_SERVICE_NOT_FOUND;
    }

    response->user = user;
    return 0;
}
~~~

这是最简单的 convention-first path。

但已有代码不一定长这样。

我们仍然希望能绑定：

~~~c
int get_user(
    UserRepository *repo,
    uint64_t id,
    User *out_user);
~~~

于是需要 compiler join。

---

### 2.1 Binding Judgment

逻辑 operation：

~~~text
UserService.GetUser :
    GetUserRequest -> GetUserResponse
~~~

native function：

~~~text
get_user :
    (UserRepository*, uint64_t, User*) -> int
~~~

可以先写一个轻量 judgment：

~~~text
Γ ⊢ UserService.GetUser :
      GetUserRequest -> GetUserResponse

Γ ⊢ get_user :
      (UserRepository*, uint64_t, User*) -> int

Γ ⊢ repo : injected-context
Γ ⊢ GetUserRequest.id ↦ id : exact
Γ ⊢ out_user ↦ GetUserResponse.user : exact
────────────────────────────────────────────
Γ ⊢ bind(UserService.GetUser, get_user) : valid
~~~

这个 judgment 已经明确了四件事：

1. repo 不是 wire request；
2. request.id 绑定 native id；
3. native OUT User 构造 response.user；
4. binding 不是按参数位置盲猜。

---


### 2.2 现在是两阶段 Binding Compiler，而不是把 Plan 伪装成静态产物

当前 SaltsUtils 已经把这个边界写得更准确。

build-time compiler 负责生成**不可变 native-binding inputs**，例如：

~~~text
IDL Service operation
      ↓ salts-idlc
generated Request / Response native data
      +
DataBindServiceNativeBinding
      +
FunctionDesc / FunctionAbi references
~~~

它**不**把最终 `DataBindBindingPlan` 序列化成一个静态“compiler artifact”。

最终 plan 由 DataBind runtime 在 control plane 编译：

~~~c
DataBindStatus data_bind_binding_plan_compile_service(
    DataBind *codec,
    const char *service_name,
    const char *operation_name,
    const DataBindBindingProjection *projection,
    const DataBindServiceNativeBinding *native,
    DataBindBindingPlan **out_plan,
    DataBindBindingPlanDiagnostic *diagnostic);
~~~

这一步 join 的是真实运行环境中已经可验证的四类事实：

~~~text
logical DataBind contract
        +
compile-time projection
        +
generated native binding
        +
current CMeta Function/Data descriptors
        ↓
immutable DataBindBindingPlan
~~~

这样既没有把 transport/session state 塞进 compiler artifact，也没有在 request hot path 重新 walk IDL AST。

这里的时间边界必须说清楚：

~~~text
build time:
    salts-idlc
        -> generated native binding inputs

startup / admission / plan construction:
    data_bind_binding_plan_compile_service(...)
        -> immutable plan

request hot path:
    execute immutable entries
        -> exact native execution
~~~

所以“更多工作提前”不等于“所有对象都必须在 build time 固化”。


### 2.3 BindingPlan：真实对象是 opaque、immutable、transport-neutral

当前 public API 直接把 `DataBindBindingPlan` 保持为 opaque object：

~~~c
typedef struct DataBindBindingPlan DataBindBindingPlan;
~~~

compile 成功后，可以只读取已经解析好的 operation/projection/function 与 ingress/egress entries：

~~~c
const char *data_bind_binding_plan_operation_id(
    const DataBindBindingPlan *plan);

const cmeta_function_desc *data_bind_binding_plan_function(
    const DataBindBindingPlan *plan);

size_t data_bind_binding_plan_ingress_count(
    const DataBindBindingPlan *plan);

size_t data_bind_binding_plan_egress_count(
    const DataBindBindingPlan *plan);
~~~

这比前面“概念性 `service_binding_plan` struct”更重要，因为它暴露了真实 ownership boundary：

- plan 不保留 frontend AST node；
- plan 不保留 codec-owned 临时字符串；
- plan 不包含 HTTP request / RPC envelope / Plugin session；
- ingress/egress 已经变成 generic immutable addresses；
- plan 的 descriptor/callback lifetime 仍受其 authoritative owner 约束。

因此 control plane object 的正确图是：

~~~text
IDL/frontend objects
      ↓ compile
generated native binding
      +
CMeta descriptors
      ↓ plan compile
DataBindBindingPlan
      ↓
immutable runtime execution input
~~~

不是让 runtime 每次从 schema 重新推导同样的关系。


### 2.4 Exact execution 仍然不是 Universal Dynamic Invocation

当前 native execution 使用显式 exact descriptor。

概念上它保存：

~~~text
FunctionDesc
FunctionAbi
context
exact invoke function
~~~

也就是 `DataBindNativeExecution`。

因此执行链是：

~~~text
FunctionDesc / FunctionAbi
        ↓ validate/admit
DataBindNativeExecution
        ↓ exact invoke
ordinary C implementation
~~~

这里仍然没有一个“根据任意 descriptor 在运行时解释 C ABI”的 universal reflection VM。

这样可以把职责继续拆开：

| 对象 | 角色 |
|---|---|
| FunctionDesc | native semantic truth |
| FunctionAbi | exact carrier facts |
| DataBindServiceNativeBinding | generated Service/native join input |
| DataBindBindingPlan | compiled logical/native binding |
| DataBindNativeExecution | admitted exact execution |

如果 backend 无法生成或 admit exact execution shape，就应该 fail closed，而不是退回 `values[]` + runtime ABI guessing。

## 3. HTTP / RPC / OpenAPI Projections

现在再生成 HTTP。

Service 本身的 `GetUser: GetUserRequest -> GetUserResponse` 并不知道它是不是 `GET /users/{id}`。

HTTP backend 根据 convention 或单独 projection config 编译：

~~~text
HTTP MethodPlan

method = GET
route  = /users/:id

ingress:
    path "id"
        -> GetUserRequest.id

egress:
    GetUserResponse
        -> JSON body

errors:
    NOT_FOUND -> 404
~~~

注意：GET、path、query、header、cookie、body placement 都属于 HTTP projection。

不进入 canonical Service IDL。

---

### 3.1 CHttp::Service 执行 Generated MethodPlan

CHttp::Server 仍然是纯 transport/runtime：

~~~text
H1/H2
router
middleware
JWT
session
body sink
deferred response
streaming
WebSocket
file serving
~~~

它不需要理解 DataBind。

生成的 route 可以挂在已有接口上：

~~~c
chttp_server_route(
    server,
    plan->method,
    plan->route,
    chttp_service_dispatch,
    plan);
~~~

generic handler：

~~~c
static int chttp_service_dispatch(
    void *user,
    const chttp_server_request_view *request,
    chttp_server_response *response)
{
    const http_method_plan *plan = user;

    return http_method_plan_execute(
        plan,
        request,
        response);
}
~~~

这是 **HTTP runtime hot path**；箭头表示 request/control flow，不表示 compiler lowering：

~~~text
request
    ↓ route lookup
router
    ↓ select immutable plan
HTTP MethodPlan
    ↓ decode/bind
precompiled ingress
    ↓ invoke
exact adapter
    ↓ encode/map result
precompiled egress
    ↓ emit
response
~~~

hot path 不再 parse IDL、walk schema AST、lookup FunctionDesc 或 guess native ABI。

---

### 3.2 RPC 使用同一个 Service、不同 MethodPlan

RPC backend 可以生成：

~~~text
RPC MethodPlan

wire_name:
    UserService.GetUser

params:
    id -> GetUserRequest.id

result:
    GetUserResponse -> result

errors:
    NOT_FOUND -> application error
~~~

CRPC runtime 仍然拥有 JSON-RPC envelope、batch、notification、deadline、cancel 和 transport；DataBind compiler 只生成 typed params/result binding。

所以 **HTTP runtime != RPC runtime**，但 logical Service Contract 是同一个。

---

### 3.3 OpenAPI 来自 Service + HTTP Projection

Service alone：

~~~text
GetUser:
    Request -> Response
~~~

不能告诉 OpenAPI：

~~~text
GET /users/{id}
~~~

所以 OpenAPI 是 **compile-time derived artifact**，不是 runtime hop：

~~~text
Service Contract
        +
HTTP MethodPlan / projection IR
        ↓ derive documentation
OpenAPI
~~~

例如：

~~~text
HTTP projection says:
    id comes from path

DataBind says:
    id is uint64 and required

        ↓

OpenAPI:
    path parameter id
    integer
    required = true
~~~

runtime 与 docs 从同一个 projection IR 生成。

这样不需要维护第二份 HTTP contract。

---

## 4. Plugin / Interface / WASM / Build Projections

同一个 component：

~~~text
component UserModule {
    service UserService;
}
~~~

选择：

~~~cmake
PROJECTIONS
    PLUGIN
~~~

compiler 可以生成：

~~~text
Plugin
└── UserService
    └── GetUser
        ├── FunctionDesc
        └── exact adapter
~~~

用户不手写 export table、manifest 或 `salts_plugin_query()`；这些都是 generated runtime machinery。

---

### 4.1 Provider/vtable 不应该被强行变成 Service

Executor 是典型反例：它天然有 long-lived self 和一组 related operations。

例如：

~~~c
typedef struct cflow_executor {
    void *self;
    const cflow_executor_vtable *vtable;
} cflow_executor;
~~~

Plugin 可以发布 `InterfaceDesc + { self, vtable }`。

而不是拆成 executor_submit / executor_cancel / executor_destroy 三个 FunctionDesc 再拼回对象。

所以 Plugin runtime 支持两种 representation：

| Capability shape | Representation |
|---|---|
| Service / Function | FunctionDesc + exact adapter |
| Provider / Interface | InterfaceDesc + `{self,vtable}` |

它们共享 loader、registry、lease 和 quiescent unload，但不共享 semantic shape。

---

### 4.2 WASM：Contract 高于 Native ABI

同一个：

~~~text
component UserModule {
    service UserService;
}
~~~

选择：

~~~cmake
PROJECTIONS
    WASM
~~~

WASM backend 不能把 `UserRepository*`、`User*` 或 native vtable pointer 直接暴露到 guest boundary。

它必须经过 **WASM ABI-lowering pipeline**：

~~~text
DataBind logical data
    ↓ lower portable representation
portable ABI representation
    ↓ generate bridge
host/guest adapter
    ↓ materialize boundary
WASM import/export
~~~

如果 ownership 无法安全表示，就直接 generation fail，而不是让 runtime 猜。

这说明：

> **IDL contract 的抽象层次必须高于任何一个 native ABI。**

---


### 4.3 真实 Compiler / CMake 入口：`salts-idlc` 与 `salts_idl_target`

当前 compiler identity 是：

~~~text
salts-idlc
~~~

旧的 `databindc` identity 已删除，不保留 alias。

CMake public frontend 也已经是一个统一入口：

~~~cmake
salts_idl_target(
  TARGET installed_image
  IDL image.schema
  COMPONENT "Image.ImageProcessor"
  VERSION "1.0.0"
  ARTIFACT_NAME "image"
  ARTIFACTS PLUGIN
  SOURCES business.c)
~~~

Transport 与 artifact 是两个正交轴。

当前 public CMake surface 明确接受：

~~~text
ARTIFACTS:
    NATIVE
    MESSAGE
    PLUGIN
    WASM
    OPENAPI

TRANSPORTS:
    HTTP
    RPC
    SOCKET
    FLOWMQ
~~~

例如 transport-only target：

~~~cmake
salts_idl_target(
  TARGET installed_socket
  IDL socket.schema
  ARTIFACT_NAME "installed_device"
  TRANSPORTS SOCKET
  PROJECTION_CONFIG socket_config.json)
~~~

注意这里不再写一个“未来可能有的统一 API”来代替真实实现。

真正 pipeline 是：

~~~text
.schema
   ↓ salts-idlc
typed IdlContract
   ├── binding compiler inputs
   ├── format plans
   ├── transport plans
   └── artifact projections
            ↓
generated ordinary C / build targets
~~~

然后 DataBind runtime 再把 generated binding inputs 与当前 CMeta descriptors 编译成 immutable `DataBindBindingPlan`。

### 4.4 IDL completeness 必须同时通过 Reflection 与 Plugin boundary

一个 logical Service operation 只有“能生成 C header”还不够。

对这本书，完整性判断是：

~~~text
Reflection can represent/admit it
        AND
Plugin can publish/use it safely across DSO
        AND
no second handwritten semantic contract is needed
~~~

Plugin path 现在有一个非常具体的 admission helper：

~~~c
data_bind_plugin_operation_execution_admit(
    operation,
    function_export,
    &execution);
~~~

它验证 generated DataBind catalog row 与 Plugin FUNCTION export 是否描述同一个 FunctionDesc / FunctionAbi / request / response shape，然后得到 canonical `DataBindNativeExecution`。

更重要的是 lease interval：

~~~text
acquire Plugin lease
    ↓
admit operation/export
    ↓
compile/use BindingPlan
    ↓
bind native staging
    ↓
invoke exact execution
    ↓
publish response / typed error
    ↓
restore native values to semantic zero
    ↓
release Plugin lease
~~~

lease 不能只包住 machine-code function call。

因为 FunctionDesc、FunctionAbi、exact invoke、generated lifecycle callback、provider-owned cleanup code 都可能属于 DSO。

这就是：

~~~text
IDL completeness
    <=>
Reflection completeness
AND
Plugin-boundary completeness
~~~

在现有 memory/lifecycle model 下的实际含义。

## 5. Failure Semantics 与 Proof Obligations

IDL：

~~~text
message GetUserRequest {
    uint64 id;
}
~~~

native function：

~~~c
int get_user(
    UserRepository *repo,
    const char *id,
    User *out);
~~~

如果没有显式 conversion：

~~~text
uint64 -> const char *
~~~

compiler 必须失败：

~~~text
error:
UserService.GetUser
  request field: id : uint64
  native param:   id : const char *
  no admitted conversion
~~~

不能在运行时偷偷 `atoi`、隐式 reinterpret 或 fallback to string。这就是 compiler-driven design 的价值。

---


### 5.1 Failure Atomicity 现在有真实 lifetime transaction

当前 API 不再只靠一句“temporary storage then commit”表达 failure atomicity。

一个完整 Service call 可以显式建立 single-owner lifetime：

~~~c
DataBindStatus data_bind_binding_plan_bind_call(
    const DataBindBindingPlan *plan,
    const DataBindBindingProvider *provider,
    const DataBindNativeOptions *native_options,
    DataBindBindingCallFrame *frame,
    DataBindBindingCallLifetime *lifetime,
    DataBindBindingPlanDiagnostic *diagnostic);
~~~

成功后：

~~~text
fresh native staging
    ↓ bind_call
live DataBindBindingCallLifetime
    ↓ exact invocation
DataBindBindingOutcome
    ↓ transactional egress
write_outcome
    ↓ cleanup
data_bind_binding_call_restore_zero
~~~

失败语义也因此更具体：

- `bind_call` 失败时，已初始化 native values 回滚到 canonical semantic zero；
- lifetime 只在完整 bind 成功后才变成 live；
- typed error / native status / bridge failure 是不同结果层；
- output publication 使用 begin/write/commit/abort transaction；
- teardown 消费 lifetime 一次，不能重试 destruction；
- Plugin-backed cleanup 必须发生在最终 lease release 之前。

可以把核心不变量写成：

~~~text
bind_call = error
    -> lifetime is empty
    -> no partially-owned native staging escapes

live lifetime
    -> exactly one restore_zero discharge
~~~

这比“出错就 free 一下”强得多，因为 cleanup authority 来自 canonical CMeta/DataBind lifecycle，而不是从 C pointer spelling 猜出来。

### 5.2 哪些地方值得形式证明

IDL parser 正常解析一个字段，不值得因此引入 Lean。

更值得 formalize 的是：

### Projection preservation

如果 backend 声称保持 logical operation：

~~~text
exec_HTTP(P_HTTP(op), req)
=
exec_Logical(op, decode_HTTP(req))
~~~

至少要说明 observable relation。

### Binding refinement

generated exact adapter 应该 refinement native binding plan：

~~~text
adapter_result
~
logical_service_result
~~~

### Transactional law

~~~text
failure before commit
    -> no observable partial output
~~~

是否进入 Lean，取决于风险和复用程度。

先写清 rule，再决定 machine-check。

## 6. 三种 IR 与 Runtime Hot Path

现在可以看到：

~~~text
DataBind Contract IR
    UserService.GetUser
    Request -> Response

CMeta Native Semantic IR
    get_user
    params / direction / ownership

CFlow Execution IR
    optional admitted execution graph
~~~

这里是 **compiler join / optional execution projection**，不是 runtime pipeline：

~~~text
Contract IR
    +
Native Semantic IR
    ↓ compile binding
BindingPlan / exact adapter
    ↓ optional execution admission
Execution IR
~~~

三个 IR 不能合并成一个“大一统 descriptor”。

因为它们回答三个不同问题。

---

### 6.1 Runtime 最后到底剩下什么

下面第一条是明确的 **runtime anti-pattern**：

~~~text
request
    ↓ runtime reflection
reflection
    ↓ schema lookup
schema lookup
    ↓ dynamic ABI work
dynamic invocation
~~~

期望的 hot path 是：

~~~text
request
    ↓ pre-resolved plan
precompiled MethodPlan
    ↓ exact call
exact C adapter
    ↓ encode/emit
response
~~~

Plugin 使用 **capability-resolution/call path**：

~~~text
lookup once / acquire lease
    ↓ resolve and retain
pre-resolved capability
    ↓ invoke
exact call
~~~

WASM 使用 **host/guest ABI boundary**：generated host adapter 调用已经定义好的 guest ABI；这里不是重新解析 IDL。

这再次回到全书的核心：

> **Know more before execution; do less during execution.**

## 7. Evidence：怎样证明这不是架构图

至少需要下面这些真实 gate。

### IDL/codegen

~~~text
valid IDL -> generated C compiles
invalid IDL -> deterministic diagnostic
~~~

### Native binding

~~~text
Service + FunctionDesc compatible -> plan
incompatible -> generation fails
~~~

### HTTP

~~~text
generated MethodPlan
-> real CHttp::Server
-> request/response integration test
~~~

## 8. 这不是一个更大的框架

我们没有得到“HTTP owns Service / RPC owns Service / Plugin owns Function metadata / WASM owns another IDL”，而是：

| 层 | 职责 |
|---|---|
| DataBind | logical contract |
| CMeta | native semantics |
| `salts-idlc` / `salts_idl_target` | IDL frontend + build-time projections |
| DataBind runtime plan compiler | generated binding + CMeta -> immutable BindingPlan |
| CHttp / CRPC / Plugin / WASM | runtime consumers |
| CFlow | optional execution IR |

减少的是 **duplicated stable knowledge**，不是 ordinary C implementation。

## 9. What We Learned

从一个普通函数：

~~~c
int get_user(UserRepository *, uint64_t, User *);
~~~

我们没有直接跳到“大型 Service Framework”。

我们先发现 HTTP、RPC、Plugin、OpenAPI、Mock、WASM 都在重复描述同一个 logical operation，于是增加最小 Contract IR：message、service、channel、component。

CMeta 继续保留 FunctionDesc/FunctionAbi 这份 native truth。 `salts-idlc` 负责 typed contract 与 build-time projection；generated `DataBindServiceNativeBinding` 与当前 CMeta descriptors 再由 DataBind runtime 编译成 immutable `DataBindBindingPlan`。 Plugin 路径通过 exact execution admission 证明 publication 与 native semantics 一致，并让 lease 覆盖 bind/invoke/egress/cleanup。最终 hot path 仍然执行 precompiled plan + exact ordinary C call。
