# 第八章：契约绑定与代码生成：CMeta 与 DataBind 的应用

一个 `get_user` 操作可能同时出现在 C 函数、HTTP 路由、RPC 方法和 Plugin 导出中。若各处分别维护输入类型、错误映射和清理规则，修改一个字段就容易造成不一致。DataBind 把服务契约与 CMeta 的本地函数事实对应起来，生成可检查的绑定计划；每次调用则独立保存临时值、输出和清理进度。

## 1. 本地函数与外部契约

下面是应用函数的声明片段，需要 `<stdint.h>`。示例约定返回零表示成功；成功时 `name` 借用仓库中的字符数据，仓库必须保证其在使用期间有效。

~~~c
typedef struct UserRepository UserRepository;

typedef struct User {
    uint64_t id;
    const char *name;
} User;

int get_user(
    UserRepository *repo,
    uint64_t id,
    User *out_user);
~~~

单个 C 调用只需准备 `User` 并检查状态。外部调用者却不应收到 `UserRepository *`，也不能把本地 `User` 的原始字节当作网络响应。指针宽度、填充和字符数据的生存期都属于本地表示。

IDL 是 interface definition language（接口定义语言），用于声明逻辑请求、响应、事件和错误。以下是说明契约关系的简化 IDL，不是包含所有导入和数据定义的完整输入文件：

~~~text
message GetUserRequest {
    uint64 id;
}
message GetUserResponse {
    User user;
}
service UserService {
    GetUser: GetUserRequest -> GetUserResponse;
}
~~~

`Service` 表达请求到响应的操作，`Channel` 表达消息或事件，`Component` 组合这些能力。它们不决定 DLL 名称、HTTP 路由或进程部署。CMeta FunctionDesc 描述本地签名，DataBind 契约描述对外承诺；两者需要对应，但并非同一个对象。

## 2. 绑定必须明确每个参数来自哪里

**绑定（binding）**把逻辑契约对应到具体 C 存储和调用；**投影（projection）**把契约映射为某种传输或产物所需的表示。对于本例，可先写出如下映射：

| 本地对象 | 来源或去向 | 必要条件 |
|---|---|---|
| `repo` | 主机注入的上下文 | 借用仓库覆盖调用及结果使用 |
| `id` | `GetUserRequest.id` | 无损转换为 `uint64_t` |
| `out_user` | `GetUserResponse.user` | 有效输出存储，明确字段生命周期 |
| `int` 返回值 | 原生状态与业务错误映射 | 零与非零的含义由契约规定 |

这张表是绑定设计，不表示编译器能自动把任意旧 C 函数变成任意服务。使用已有 `get_user` 时，可以先写符合生成服务 ABI 的薄适配函数，再由 CMeta 描述它。仓库依赖和借用字符串需要在这层落实，不能让生成器从参数名猜测。

例如，若逻辑输入为 `uint64`，本地参数却是 `const char *`，没有已准入转换就必须拒绝。两个类型的大小偶然相同也无关；强转指针、隐式文本转换和截断都不是类型匹配。

## 3. 输入转换的数值边界

HTTP 路径中的 `"42"` 是字符序列，不是一个已经存在的 `uint64_t` 对象。下面的完整普通 C 函数说明十进制无符号转换的关键检查，需要 `<stdbool.h>`、`<stddef.h>` 和 `<stdint.h>`。它只接受非空十进制数字串，不接受空格、正负号或前缀；`out` 必须指向可写对象。

~~~c
bool book_parse_u64(const char *text, uint64_t *out)
{
    if (text == NULL || out == NULL || *text == '\0')
        return false;
    uint64_t value = 0;
    for (const char *p = text; *p != '\0'; ++p) {
        if (*p < '0' || *p > '9')
            return false;
        unsigned digit = (unsigned)(*p - '0');
        if (value > (UINT64_MAX - digit) / 10u)
            return false;
        value = value * 10u + digit;
    }
    *out = value;
    return true;
}
~~~

循环不变量为：`value` 等于已读前缀的数值，且不超过 `UINT64_MAX`。乘加前的条件把 `10 × value + digit <= UINT64_MAX` 改写为不会先溢出的比较，因此每一步保持不变量。只在全部输入通过后写 `out`，所以任何失败都保留原输出。

这不是 DataBind 解码器的替代实现，而是转换准入为什么必须包含范围检查的具体证明。生成的绑定还需处理缺失、显式 null、默认值及字段格式；缺失与数值零是不同状态。

## 4. 两阶段生成与计划编译

`salts-idlc` 在构建期生成请求、响应和类型错误的本地表示，以及 `DataBindServiceNativeBinding` 等不可变输入。最终 `DataBindBindingPlan` 在启动或挂载时，由 DataBind 把这些输入、投影和当前 CMeta 描述符结合起来编译。

~~~c
DataBindStatus data_bind_binding_plan_compile_service(
    DataBind *codec,
    const char *service_name,
    const char *operation_name,
    const DataBindBindingProjection *projection,
    const DataBindServiceNativeBinding *native,
    DataBindBindingPlan **out_plan,
    DataBindBindingPlanDiagnostic *diagnostic);
~~~

这里展示公开函数签名，调用前需准备有效 codec、服务与操作名、投影和 native binding。计划编译并非每请求解释 IDL；也不能把最终计划直接当作可序列化的静态编译产物。

~~~text
compile_binding(contract, projection, native):
    resolve the logical operation
    validate native descriptors and declared request/response/error shapes
    for each required field:
        resolve its native location and direction
        require an admitted type conversion and ownership rule
        compile a transport-neutral address
    copy the plan-owned names and entries
    publish the immutable plan only after every check succeeds
~~~

**输入侧（ingress）**把外部值送入本地对象；**输出侧（egress）**把本地结果投影给外部提供方。DataBind 核心解释通用绑定类别，投影产生的名称、空间与序号由相应适配器使用，核心不根据 HTTP、RPC 或消息协议分支。

计划是 **不透明类型（opaque type）**，使用方通过公开访问器读取操作身份、函数和输入输出条目，通过 `data_bind_binding_plan_free` 释放。它不保留前端 AST 节点或 codec 临时字符串，但借用的描述符和代码仍须由外层所有者保持有效。

## 5. 精确执行仍是具体 C 调用

固定快照的执行描述包含 CMeta 语义、ABI 和显式适配入口：

~~~c
typedef struct DataBindNativeExecution {
    size_t size;
    uint32_t abi_version;
    const cmeta_function_desc *function;
    const cmeta_function_abi_desc *abi;
    void *context;
    DataBindNativeInvokeFn invoke;
} DataBindNativeExecution;
~~~

`invoke` 是第三章那种按已知签名生成的调用适配函数。`params[i]` 指向该参数真实 C 对象，返回存储对应真实返回类型。桥接函数的布尔返回表示适配与准入是否成功；业务函数的 `int` 状态仍保存在其返回契约中。

| 结果层 | 含义 | 是否已有业务结果 |
|---|---|---|
| 桥接或准入失败 | 无法合法完成精确调用 | 不能当作业务错误响应 |
| 原生非零状态 | 业务函数按契约报告状态 | 不发布成功或类型错误载荷 |
| 类型错误结果 | 声明过的错误变体及其载荷 | 按对应错误投影发布 |
| 成功结果 | 正常响应 | 按成功投影发布 |

原生状态与类型错误同时出现的歧义组合应拒绝。描述符相等只说明契约相容，不会从未知地址推导可调用 ABI；执行能力必须由提供方明确交付。

## 6. 一次调用的生命周期事务

固定快照用 `DataBindBindingCallLifetime` 表达一次成功绑定后的单所有者清理责任。完整绑定入口为：

~~~c
DataBindStatus data_bind_binding_plan_bind_call(
    const DataBindBindingPlan *plan,
    const DataBindBindingProvider *provider,
    const DataBindNativeOptions *native_options,
    DataBindBindingCallFrame *frame,
    DataBindBindingCallLifetime *lifetime,
    DataBindBindingPlanDiagnostic *diagnostic);
~~~

存储必须是新鲜、尚未拥有资源的暂存对象；生命周期位置应彼此独立，只有明确允许的请求根别名例外。绑定成功后不要复制或重新初始化 lifetime，也不要修改帧元数据和参数数组。延迟执行可以通过同步交接转移独占使用权。

~~~text
call_service(plan, frame, provider):
    initialize an empty call lifetime
    bind the complete frame
    if binding fails:
        return with initialized staging rolled back and lifetime empty
    invoke the admitted exact capability
    if bridge succeeds:
        classify and transactionally publish one outcome
    restore native values through their canonical lifecycle
    consume the call lifetime
~~~

证明可用已初始化集合 `L`：开始 `L` 为空；每次初始化成功，才把该对象加入 `L`；失败时只清理 `L` 中的对象。这样不会销毁未初始化对象，也不会漏掉前面成功取得的资源。完整成功后，`L` 对应 live lifetime，其后调用、输出失败或主动放弃都需要终结这项责任。

`data_bind_binding_call_restore_zero` 通过缓存的规范描述恢复语义零值，并清除 presence/null 状态。语义零值是生命周期协议规定的空状态，不能任意用 `memset` 代替资源销毁。预检若发现无效帧或错误标签，lifetime 保持 live 且值不变；一旦清理开始，lifetime 被消费，即使某项规范清理失败也继续处理其余值，不允许重试而重复销毁。

## 7. 输出发布为何需要事务

提供方提供 begin、write、commit、abort 操作。正确提供方在 commit 前暂存输出；若某个字段转换失败，abort 丢弃暂存内容。只有这样，“未成功提交就没有部分响应”才成立。把 write 直接实现为不可撤销的网络发送，会破坏这项提供方前提。

~~~text
publish(outcome):
    validate the selected success or typed-error shape
    begin output transaction
    for each compiled output entry:
        convert and write into transaction-local storage
        on failure: abort and return failure
    commit the complete output
    on commit failure: abort and report failure
~~~

证明分两种路径：任意写入失败都在 commit 前退出，因此外部没有成功发布；所有写入成功才尝试唯一一次 commit。应用还需按协议处理 commit 失败，不能把不确定的网络交付重新解释为业务函数没有执行。发布失败通常不授权再次调用一个有副作用的业务函数。

## 8. HTTP 挂载与延迟执行

HTTP 投影决定方法、路由、路径或查询字段、响应编码和错误状态。例如 `GET /users/:id` 把路径字段转换为请求 `id`；这项路由规则不属于纯 Service 契约。CHttp 固定快照提供 `CHttp::Service`，在 mount 时检查 MethodPlan、本地布局与精确执行能力，然后注册路由。

| 模式 | 已准入后的工作 |
|---|---|
| INLINE_DIRECT | 在 HTTP 所有者回调上执行精确入口 |
| DEFERRED_DIRECT | 先物化本地帧，再交给有界执行器 |
| DEFERRED_CFLOW | 挂载时编译计划，工作线程执行该计划 |
| DEFERRED_PLUGIN | 挂载时解析导出并取得独立租约，随后调用缓存入口 |

**物化（materialization）**把短暂视图的数据转成具有明确存储与生命周期的对象。延迟模式不能把 HTTP request view 或 CNet 回调视图交给工作线程；跨回调边界的是已经物化的本地帧。已接受任务持有方法运行域直到 finalizer 完成请求、响应与错误清理。

固定快照的 Service 仅实现其声明的输入输出范围；结构化 body/egress 和请求上下文仍有拒绝边界。因此本章含字符串字段的完整 `User` 是绑定设计案例，不能据此宣称该快照已支持整条 HTTP 路径。`CMETA_EFFECT_ASYNC` 的原生函数也不能仅靠选择 deferred 模式就通过挂载：deferred 在这里把已准入的同步操作移交给执行器。

输出在每次调用的事务存储中编码一次，形成受界的 `mem_buffer_t`，完成 writer 后再由 `chttp_server_reply_buffer` 持有发布。并发调用不共享可变请求或响应暂存区。停止服务器后，应等待接受的执行任务终结，再按契约销毁服务器和 Service；仍有延迟调用存活时 Service 销毁返回 BUSY 并保留所需资源。

## 9. RPC 与文档复用同一契约

`CHttp::RpcService` 使用 RPC MethodPlan、本地 binding 和精确执行能力挂载操作。RPC 投影负责方法名、参数名称或序号、结果和类型错误映射；CRPC 负责 envelope（协议封套，即承载请求标识、方法、参数或结果的外层消息）、批次、通知、截止时间和传输。

类型化客户端使用预编译输入条目编码请求，并把分类后的成功或类型错误解码进调用方存储。SUCCESS、TYPED_ERROR、REMOTE_ERROR 与传输、HTTP、超时或协议解析失败属于不同层，不能只保留一个无法解释的整数。

固定快照的 RPC 路径有标量参数和有限结果形状等支持限制，不支持的结构化或混合投影应拒绝。OpenAPI 则由 Service 加 HTTP 投影生成：契约提供 `id` 的类型与必需性，HTTP 投影提供它位于路径。文档生成不是每次请求必须经过的运行步骤。

## 10. Plugin、WASM 与构建产物

`salts_idl_target` 是构建前端，`ARTIFACTS` 与 `TRANSPORTS` 分别选择生成产物和传输投影。下面是固定快照的调用形状；`image.schema` 和 `business.c` 由应用提供。

~~~cmake
salts_idl_target(
  TARGET installed_image
  IDL image.schema
  COMPONENT "Image.ImageProcessor"
  VERSION "1.0.0"
  ARTIFACT_NAME "image"
  ARTIFACTS PLUGIN
  SOURCES business.c)
~~~

Plugin 产物需要明确 Component、版本与实现来源。生成器发布契约、FunctionDesc、FunctionAbi 和精确入口；`data_bind_plugin_operation_execution_admit` 检查操作目录与函数导出是否匹配。长期对象提供方则发布 InterfaceDesc 与 `{self, vtable}`，不必强拆成若干无关联函数。

**租约（lease）**是保证模块代码与数据生存期的持有凭据。其区间必须覆盖解析、绑定、调用、输出和规范清理，因为清理函数也可能位于动态库内。先销毁依赖的计划和本地值，再释放最后租约；仅包住业务函数调用不足以安全卸载。

WASM 产物还需 Component 和 `WASM_CORE_MODULE`。本地仓库指针、对象指针和 vtable 不能直接成为 guest 可用的地址；桥接器必须按约定的可移植表示转换数据和所有权。不能表示的契约应在生成或准入时拒绝。

## 11. 固定快照与证据边界

DataBind 的实际接口见 [data_bind_binding_plan.h](https://github.com/qigao/salts-utils/blob/23c01b1379d3e578a4633acdf7c44166a1eb0714/databind/runtime/data_bind_binding_plan.h) 与 [data_bind_native_binding.h](https://github.com/qigao/salts-utils/blob/23c01b1379d3e578a4633acdf7c44166a1eb0714/databind/runtime/data_bind_native_binding.h)。HTTP 契约见 [CHttp Service 头文件](https://github.com/qigao/chttp/blob/2e950615a7f47190258c4cb1d2cdab32e80a05b8/service/include/chttp_service/service.h)。

CHttp 这个快照仍使用迁移前的 Plugin 类型名，不能视为已经与本版 CMeta/SaltsUtils 完成组合构建。各仓库的独立证据、书中统一的组件称呼与实际二进制兼容是三件事；`SOURCE_SNAPSHOTS.md` 保留了这项限制。

验证应从合法 IDL 生成 C、非法映射诊断、失败回滚和输出 abort 开始，再分别进行真实 HTTP/RPC 往返、安装后的 Plugin 加载和租约清理测试。生成的运行目标应依赖 DataBind 与所需运行库，不把 IDL/Schema 前端拖进每次请求。本文的转换和生命周期推导是手工论证，没有声称所有这些桥接器已经获得 Lean 实现证明。

## 12. 小结

DataBind 契约、CMeta 本地描述和传输投影在控制阶段编译为绑定计划；精确调用仍执行具体 C 函数。每次调用独立拥有暂存值和清理责任，输出以事务提交，Plugin 租约持续覆盖最后的清理。复用同一契约能减少重复维护，但每个传输的支持范围、ABI 与资源边界仍须单独验证。
