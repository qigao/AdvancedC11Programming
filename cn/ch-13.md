# 第八章：契约绑定与代码生成：CMeta 与 DataBind 的应用

同一个 `get_user` 操作可能同时出现在 C 函数、HTTP 路由、RPC 方法和 Plugin 导出中。分别描述它们容易让参数类型、错误和清理义务发生偏差。本章把 DataBind 的服务契约与 CMeta 函数描述对应起来，展示绑定计划的生成、输入转换与精确调用，并用失败回滚和租约生存期说明如何安全地复用这些事实。

**术语说明：** IDL 是 interface definition language（接口定义语言），用于声明操作、请求、响应和错误等契约。binding（绑定）把契约对应到具体 C 类型和函数；projection（投影）则从同一契约生成 HTTP、RPC 等目标所需的表示。

## 1. 从一个 C 函数到 Logical Contract

假设系统只有一个查询用户的函数：

~~~c
typedef struct UserRepository UserRepository;

typedef struct User {
    uint64_t id;
    const char *name;
} User;

int get_user(
    UserRepository *repo,
    uint64_t id,
    User *out_user);
~~~

这已经是很好的 C。调用也很简单：

~~~c
User user = {0};

int rc = get_user(repo, 42u, &user);

if (rc != 0) {
    ...
}
~~~

如果程序只有一个调用点，不需要任何 IDL。问题出现在这个 operation 开始被多个系统暴露。

### 1.1 HTTP 第一次重复描述它

一个普通 HTTP handler 可能是：

~~~c
static int get_user_http(
    void *ctx,
    const chttp_server_request_view *request,
    chttp_server_response *response)
{
    UserRepository *repo = ctx;

    const char *id_text =
        chttp_server_request_param(request, "id");

    uint64_t id = 0;

    if (parse_u64(id_text, &id) != 0)
        return chttp_server_reply(response, 400, "text/plain",
                                  "invalid id", 10);

    User user = {0};

    if (get_user(repo, id, &user) != 0)
        return chttp_server_reply(response, 404, "text/plain",
                                  "not found", 9);

    char json[1024];
    size_t json_size = encode_user_json(json, sizeof(json), &user);

    return chttp_server_reply(
        response,
        200,
        "application/json",
        json,
        json_size);
}
~~~

然后注册：

~~~c
chttp_server_get(
    server,
    "/users/:id",
    get_user_http,
    repo);
~~~

这里第一次重复出现 operation identity、输入字段 `id`、输入类型 `uint64`、结果 `User` 和 error mapping。HTTP 本身没有错。重复知识开始出现。

### 1.2 RPC、OpenAPI、Plugin、Mock、WASM 再次重复

RPC 可能再写：

~~~c
crpc_server_register(
    rpc,
    "UserService.GetUser",
    get_user_rpc,
    repo);
~~~

OpenAPI 再描述：

~~~text
GET /users/{id}

parameter:
    id : uint64

response 200:
    User

response 404:
    NotFound
~~~

Plugin 还会维护 `export_id`、`contract_id`、`contract_version`、函数元数据和 adapter；Mock 再写一份函数签名，WASM 再定义 host/guest ABI。最终出现了 C prototype、HTTP route/decoder、RPC method/decoder、OpenAPI、Plugin export、Mock 声明和 WASM ABI。它们不一定逐行相同，却共同维护着同一份操作契约：

UserService.GetUser 是一个 typed logical operation。这就是新的重复知识。

### 1.3 FunctionDesc 是 native truth，不是 logical contract

第三章已经把普通 C 函数描述成 `cmeta_function_desc`。概念上：

~~~c
static const cmeta_param_desc get_user_params[] = {
    { "repo",     CMETA_TYPE(UserRepository_ptr), CMETA_IN },
    { "id",       CMETA_TYPE(uint64_t),           CMETA_IN },
    { "out_user", CMETA_TYPE(User_ptr),           CMETA_OUT }
};

static const cmeta_function_desc get_user_desc = {
    .name = "get_user",
    .return_type = CMETA_TYPE(int),
    .params = get_user_params,
    .param_count = 3
};
~~~

这告诉工具 **native C function 是什么**。但它仍然没有回答：

- 业务操作叫什么？
- logical request 是什么？
- logical response 是什么？
- `repo` 是业务输入，还是 host dependency？
- HTTP/RPC/Plugin 是否应该看到 `repo`？

所以 **FunctionDesc != Service Contract**。这就是为什么函数反射并不能替代 IDL。

### 1.4 DataBind IDL 描述 logical contract

现在把逻辑契约单独写出来：

~~~text
message GetUserRequest {
    uint64 id;
}

message GetUserResponse {
    User user;
}

service UserService {
    GetUser: GetUserRequest -> GetUserResponse;
}
~~~

这里没有：

~~~text
GET
POST
/path
RPC method alias
DLL name
WASM export
C function name
~~~

IDL 回答 **what is promised?**；CMeta 回答 **what is implemented in C?**。

### 1.5 Service、Channel、Component 的语义边界

DataBind 的核心 vocabulary 应该很小。

### Service

Service 表达 **Request → Response**。例如：

~~~text
service UserService {
    GetUser: GetUserRequest -> GetUserResponse;
}
~~~

### Channel

Channel 表达 **Message / Event**。例如：

~~~text
channel UserEvents {
    UserChanged;
}
~~~

### Component

Component 只组合 capability：

~~~text
component UserModule {
    service UserService;
    channel UserEvents;
}
~~~

它表示“哪些 capability 属于一个逻辑模块”，但不表示 DLL、process、HTTP server 或 WASM module；这些是后面的 projection。

## 2. Native Binding：Contract IR Join CMeta

编译器可以为标准 Service ABI 生成 header：

~~~c
int user_service_get_user(
    const GetUserRequest *request,
    GetUserResponse *response);
~~~

用户只写：

~~~c
#include "user.generated.h"

int user_service_get_user(
    const GetUserRequest *request,
    GetUserResponse *response)
{
    User user = {0};

    if (repository_get(
            global_repository(),
            request->id,
            &user) != 0) {
        return USER_SERVICE_NOT_FOUND;
    }

    response->user = user;
    return 0;
}
~~~

这是最简单的 convention-first path。但已有代码不一定长这样。我们仍然希望能绑定：

~~~c
int get_user(
    UserRepository *repo,
    uint64_t id,
    User *out_user);
~~~

于是需要编译器 join。

### 2.1 Binding Judgment

逻辑 operation：

~~~text
UserService.GetUser :
    GetUserRequest -> GetUserResponse
~~~

native function：

~~~text
get_user :
    (UserRepository*, uint64_t, User*) -> int
~~~

可以先写一个轻量 judgment：

~~~text
Γ ⊢ UserService.GetUser :
      GetUserRequest -> GetUserResponse

Γ ⊢ get_user :
      (UserRepository*, uint64_t, User*) -> int

Γ ⊢ repo : injected-context
Γ ⊢ GetUserRequest.id ↦ id : exact
Γ ⊢ out_user ↦ GetUserResponse.user : exact
────────────────────────────────────────────
Γ ⊢ bind(UserService.GetUser, get_user) : valid
~~~

这个 judgment 已经明确了四件事：

1. repo 不是 wire request；
2. request.id 绑定 native id；
3. native OUT User 构造 response.user；
4. binding 不是按参数位置盲猜。

### 2.2 现在是两阶段 Binding Compiler，而不是把 Plan 伪装成静态产物

当前 SaltsUtils 已经把这个边界写得更准确。构建期编译器负责生成**不可变 native-binding inputs**，例如：

~~~text
IDL Service operation
      ↓ salts-idlc
generated Request / Response native data
      +
DataBindServiceNativeBinding
      +
FunctionDesc / FunctionAbi references
~~~

它**不**把最终 `DataBindBindingPlan` 序列化成一个静态“编译器 artifact”。最终 plan 由 DataBind 运行时在控制面编译：

~~~c
DataBindStatus data_bind_binding_plan_compile_service(
    DataBind *codec,
    const char *service_name,
    const char *operation_name,
    const DataBindBindingProjection *projection,
    const DataBindServiceNativeBinding *native,
    DataBindBindingPlan **out_plan,
    DataBindBindingPlanDiagnostic *diagnostic);
~~~

这一步 join 的是真实运行环境中已经可验证的四类事实：

~~~text
logical DataBind contract
        +
compile-time projection
        +
generated native binding
        +
current CMeta Function/Data descriptors
        ↓
immutable DataBindBindingPlan
~~~

这样既没有把 transport/session state 塞进编译器 artifact，也没有在 request 热路径重新 walk IDL AST。这里的时间边界必须说清楚：

~~~text
build time:
    salts-idlc
        -> generated native binding inputs

startup / admission / plan construction:
    data_bind_binding_plan_compile_service(...)
        -> immutable plan

request hot path:
    execute immutable entries
        -> exact native execution
~~~

所以“更多工作提前”不等于“所有对象都必须在构建时固化”。

### 2.3 BindingPlan：真实对象是 opaque、不可变、transport-neutral

不透明类型（opaque type）只在公共头文件中声明名字，调用方通过指针和公开函数使用它，不能直接访问其字段。这里隐藏的是绑定计划的内部布局；计划的所有权、可调用操作与销毁责任仍属于公开契约。当前 public API 直接把 `DataBindBindingPlan` 保持为 opaque object：

~~~c
typedef struct DataBindBindingPlan DataBindBindingPlan;
~~~

compile 成功后，可以只读取已经解析好的 operation/projection/function 与 ingress/egress entries：

~~~c
const char *data_bind_binding_plan_operation_id(
    const DataBindBindingPlan *plan);

const cmeta_function_desc *data_bind_binding_plan_function(
    const DataBindBindingPlan *plan);

size_t data_bind_binding_plan_ingress_count(
    const DataBindBindingPlan *plan);

size_t data_bind_binding_plan_egress_count(
    const DataBindBindingPlan *plan);
~~~

这比前面“概念性 `service_binding_plan` struct”更重要，因为它暴露了真实所有权 boundary：

- plan 不保留 frontend AST node；
- plan 不保留 codec-owned 临时字符串；
- plan 不包含 HTTP request / RPC envelope / Plugin session；
- ingress/egress 已经变成 generic 不可变 addresses；
- plan 的描述符/回调生存期仍受其 authoritative owner 约束。

因此控制面 object 的正确图是：

~~~text
IDL/frontend objects
      ↓ compile
generated native binding
      +
CMeta descriptors
      ↓ plan compile
DataBindBindingPlan
      ↓
immutable runtime execution input
~~~

不是让运行时每次从 schema 重新推导同样的关系。

### 2.4 Exact execution 仍然不是 Universal Dynamic Invocation

当前 native execution 使用显式 exact 描述符。概念上它保存：

- FunctionDesc
- FunctionAbi
- context
- exact invoke function

也就是 `DataBindNativeExecution`。因此执行链是：

~~~text
FunctionDesc / FunctionAbi
        ↓ validate/admit
DataBindNativeExecution
        ↓ exact invoke
ordinary C implementation
~~~

这里仍然没有一个“根据任意描述符在运行时解释 C ABI”的 universal reflection VM。这样可以把职责继续拆开：

| 对象 | 角色 |
|---|---|
| FunctionDesc | native semantic truth |
| FunctionAbi | exact carrier facts |
| DataBindServiceNativeBinding | generated Service/native join input |
| DataBindBindingPlan | compiled logical/native binding |
| DataBindNativeExecution | admitted exact execution |

如果 backend 无法生成或 admit exact execution shape，就应该 fail closed，而不是退回 `values[]` + 运行时 ABI guessing。

## 3. HTTP / RPC / OpenAPI Projections

现在再生成 HTTP。Service 本身的 `GetUser: GetUserRequest -> GetUserResponse` 并不知道它是不是 `GET /users/{id}`。HTTP backend 根据 convention 或单独 projection config 编译：

~~~text
HTTP MethodPlan

method = GET
route  = /users/:id

ingress:
    path "id"
        -> GetUserRequest.id

egress:
    GetUserResponse
        -> JSON body

errors:
    NOT_FOUND -> 404
~~~

注意：GET、path、query、header、cookie、body placement 都属于 HTTP projection。不进入 canonical Service IDL。

### 3.1 CHttp::Service：真实运行时使用方，不再是概念 generic handler

当前 CHttp 已经提供独立安装目标 `CHttp::Service`。它不会让 `CHttp::Server` 直接理解 IDL，而是在两者之间放置明确的 adapter 运行时。下面给出的 **mount 结构只是按本版 CMeta Plugin 命名整理的示意，并非固定快照的逐字摘录**。CHttp 固定快照的公共头文件仍使用迁移前的 Plugin 类型名；这里写出的 `cmeta_plugin_registry` / `cmeta_plugin_ref` 代表对齐当前 CMeta Plugin API 后的目标形态，并不表示该 CHttp 快照已经通过与本版 Salts/SaltsUtils SDK 的组合构建。具体版本见 `SOURCE_SNAPSHOTS.md`。

~~~c
typedef struct chttp_service_http_mount {
    size_t size;
    const DataBindHttpMethodPlan *method_plan;
    const DataBindServiceNativeBinding *native_binding;
    const DataBindNativeExecution *execution;
    chttp_service_execution_mode execution_mode;
    cflow_executor *executor;
    const cflow_function_typed_adapter_projection *cflow_projection;

    cmeta_plugin_registry *plugin_registry;
    cmeta_plugin_ref plugin_ref;
    const char *plugin_export_id;
} chttp_service_http_mount;
~~~

然后：

~~~c
int chttp_service_mount_http(
    chttp_service *service,
    chttp_server *server,
    const chttp_service_http_mount *mount);
~~~

这里已经把书前面分开的四种 authority 接在一起：

~~~text
DataBindHttpMethodPlan
    = HTTP projection truth

DataBindServiceNativeBinding
    = request/response/error native layout

DataBindNativeExecution
    = admitted exact FunctionDesc/FunctionAbi execution

CHttp::Server
    = HTTP transport/runtime
~~~

mount-time 准入检查只做一次。当前明确支持四种执行模式：

| mode | 控制面 meaning |
|---|---|
| INLINE_DIRECT | HTTP owner 回调上直接执行 exact native capability |
| DEFERRED_DIRECT | 先 materialize native frame，再交有界 executor |
| DEFERRED_CFLOW | mount 时编译不可变 CFlow Plan，worker 只执行 Plan |
| DEFERRED_PLUGIN | mount 时解析 Plugin export、取得独立 lease、缓存 exact execution |

计划在挂载时完成这些检查。资格测试确认逐次请求执行不会重复以下工作：

- FunctionDesc equality / ABI validation
- Plugin registry lookup
- FunctionMeta / FunctionAbi lookup
- CFlow graph construction / Plan compilation

热路径只消费已经 admitted 的状态：

~~~text
HTTP request
    ↓ route
mounted MethodPlan / BindingPlan
    ↓ bind native frame
precompiled ingress
    ↓ exact capability
DataBindNativeExecution or immutable CFlow Plan
    ↓ transactional egress
DataBindBindingOutcome
    ↓ materialize once
pooled mem_buffer_t
    ↓ retained publish
chttp_server_reply_buffer()
~~~

因此书里原先那个手写概念函数：

~~~text
chttp_service_dispatch(plan, request, response)
~~~

现在可以删掉。真正的工程结论更强：

CHttp::Service 在 mount/控制面完成 semantic/ABI 准入检查；request 热路径不 lookup 反射，也不重建 native ABI。

#### Deferred 生存期也已经有明确边界

deferred mode 不能把：

- chttp_server_request_view *
- CNet callback-scoped view

带到 worker。只有已经 materialize 的 native request frame 可以跨回调 boundary。accepted deferred work 还持有 mounted method/domain 生存期，直到 task finalizer 完成 request/response/error native teardown。因此：

~~~text
deferred_in_flight > 0
        ↓
chttp_service_destroy()
        -> SALTS_EBUSY
~~~

对 Plugin mode，mount-owned Plugin lease 保持到 Service destroy；依赖它的 CFlow Plan / 描述符 / exact execution 必须先结束，再 release lease。这正好与上一节 DataBind 的 call-生存期不变量对齐：

~~~text
HTTP domain lifetime
    owns when work may still run

DataBind/CMeta lifecycle
    owns how native values are destroyed

Plugin lease
    owns DSO code/data reachability
~~~

三者不能合并成一个 cleanup flag。

#### Egress 也已经收敛成 single materialization

当前 generated Service success path 是：

~~~text
native result
    ↓
DataBind / CSerde encode once
    ↓
pooled mem_buffer_t
    ↓
cserde_writer_finish()
    ↓
chttp_server_reply_buffer()
~~~

不再把结果先写到共享 response scratch，再复制进 HTTP response builder。这里的价值不是“一次 copy 少一点”这句口号，而是：

per-call 可变 state 属于 invocation；mounted operation 只保留不可变/control 元数据。

### 3.2 CHttp::RpcService：同一个 Service Contract，另一种 plan-driven 运行时

当前 CHttp 也已经有独立安装目标：

~~~text
CHttp::RpcService
~~~

server mount 的真实输入是：

~~~c
typedef struct chttp_rpc_service_mount_options {
    size_t size;
    const char *target;
    const DataBindRpcMethodPlan *method_plan;
    const DataBindServiceNativeBinding *native_binding;
    const DataBindNativeExecution *execution;
} chttp_rpc_service_mount_options;
~~~

然后注册：

~~~c
int chttp_rpc_service_mount(
    chttp_rpc_service *service,
    crpc_server *server,
    const chttp_rpc_service_mount_options *mount);
~~~

与 HTTP 一样：

~~~text
mount
    -> validate FunctionDesc / FunctionAbi / native layout once

call hot path
    -> no Reflection lookup
    -> no dynamic ABI reconstruction
~~~

CRPC 运行时仍然拥有：

- JSON-RPC envelope
- request id
- batch / notification
- deadline / cancel
- H1/H2 / TLS transport
- remote-error protocol semantics

DataBind RpcMethodPlan 则拥有：

- wire method
- params name/ordinal projection
- result projection
- typed-error mapping

所以：

~~~text
logical Service Contract
        |
        +--> HTTP MethodPlan -> CHttp::Service
        |
        '--> RPC MethodPlan  -> CHttp::RpcService
~~~

不是两个独立的 Service 模型。

#### Typed client 也已经不需要手写 encoder/decoder

当前 blocking typed entry 是：

~~~c
int chttp_rpc_service_client_call(
    crpc_client *client,
    const chttp_rpc_service_client_call_options *options,
    chttp_rpc_service_client_outcome *outcome,
    crpc_error *out_error);
~~~

它消费：

~~~text
DataBindRpcMethodPlan
+
DataBindServiceNativeBinding
+
caller-owned native request/response/error storage
~~~

因此调用端不再手写 `encode_params`，也不需要自己遍历 `cserde_token`。路径是：

~~~text
native request
    ↓ plan-driven params
CRPC JSON-RPC envelope
    ↓ HTTP/CNet
remote response
    ↓ plan-driven result/error binding
native response / generated typed-error envelope
~~~

合法 response outcome 还保持三种语义：

~~~text
SUCCESS
TYPED_ERROR
REMOTE_ERROR
~~~

而 transport / HTTP / deadline / envelope / native encode-decode failure 仍然是另一层 error。这再次说明：

transport 运行时与 logical outcome 不应该被压成一个整数状态码。当前 snapshot 的 RpcService slice 仍然有明确有限边界：scalar params、有限 result/error shape；unsupported structured/mixed projection fail closed，而不是动态猜。

### 3.3 OpenAPI 来自 Service + HTTP Projection

Service alone：

~~~text
GetUser:
    Request -> Response
~~~

不能告诉 OpenAPI：

~~~text
GET /users/{id}
~~~

当前 CHttp tree 已经有 DataBind HTTP OpenAPI 提供方；所以 OpenAPI 是 **编译期 derived artifact**，不是运行时 hop：

~~~text
Service Contract
        +
HTTP MethodPlan / projection IR
        ↓ derive documentation
OpenAPI
~~~

例如：

~~~text
HTTP projection says:
    id comes from path

DataBind says:
    id is uint64 and required

        ↓

OpenAPI:
    path parameter id
    integer
    required = true
~~~

运行时与 docs 从同一个 projection IR 生成。这样不需要维护第二份 HTTP contract。

## 4. Plugin / Interface / WASM / Build Projections

同一个 component：

~~~text
component UserModule {
    service UserService;
}
~~~

在当前 public frontend 中，这属于：

~~~cmake
ARTIFACTS
    PLUGIN
~~~

完整 `salts_idl_target()` 还必须显式提供 Plugin 所需的 COMPONENT、VERSION 以及 SOURCES/LIBRARIES。编译器可以生成：

~~~text
Plugin
└── UserService
    └── GetUser
        ├── FunctionDesc
        └── exact adapter
~~~

用户不手写 export table、manifest 或 `cmeta_plugin_query()`；这些都是 generated 运行时 machinery。

### 4.1 Provider/vtable 不应该被强行变成 Service

Executor 是典型反例：它天然有 long-lived self 和一组 related operations。例如：

~~~c
typedef struct cflow_executor {
    void *self;
    const cflow_executor_vtable *vtable;
} cflow_executor;
~~~

Plugin 可以发布 `InterfaceDesc + { self, vtable }`。而不是拆成 executor_submit / executor_cancel / executor_destroy 三个 FunctionDesc 再拼回对象。所以 Plugin 运行时支持两种 representation：

| Capability shape | Representation |
|---|---|
| Service / Function | FunctionDesc + exact adapter |
| Provider / Interface | InterfaceDesc + `{self,vtable}` |

它们共享 loader、registry、lease 和 quiescent unload，但不共享 semantic shape。

**Quiescent（静止状态）**表示相关执行与回调已经结束，且不会再访问待卸载资源。quiescent unload 因而要求先关闭新的访问、等待使用者与相关租约结束，再卸载动态库。

### 4.2 WASM：Contract 高于 Native ABI

同一个：

~~~text
component UserModule {
    service UserService;
}
~~~

在当前 public frontend 中，这属于：

~~~cmake
ARTIFACTS
    WASM
~~~

完整 target 还必须显式提供 COMPONENT 与 WASM_CORE_MODULE。WASM backend 不能把 `UserRepository*`、`User*` 或 native vtable pointer 直接暴露到 guest boundary。它必须经过 **WASM ABI-lowering pipeline**：

~~~text
DataBind logical data
    ↓ lower portable representation
portable ABI representation
    ↓ generate bridge
host/guest adapter
    ↓ materialize boundary
WASM import/export
~~~

如果所有权无法安全表示，就直接 generation fail，而不是让运行时猜。这说明：

IDL contract 的抽象层次必须高于任何一个 native ABI。

### 4.3 真实 Compiler / CMake 入口：`salts-idlc` 与 `salts_idl_target`

当前编译器 identity 是：

~~~text
salts-idlc
~~~

旧的 `databindc` identity 已删除，不保留 alias。CMake public frontend 也已经是一个统一入口：

~~~cmake
salts_idl_target(
  TARGET installed_image
  IDL image.schema
  COMPONENT "Image.ImageProcessor"
  VERSION "1.0.0"
  ARTIFACT_NAME "image"
  ARTIFACTS PLUGIN
  SOURCES business.c)
~~~

Transport 与 artifact 是两个正交轴。当前 public CMake surface 明确接受：

~~~text
ARTIFACTS:
    NATIVE
    MESSAGE
    PLUGIN
    WASM
    OPENAPI

TRANSPORTS:
    HTTP
    RPC
    SOCKET
    FLOWMQ
~~~

例如 transport-only target：

~~~cmake
salts_idl_target(
  TARGET installed_socket
  IDL socket.schema
  ARTIFACT_NAME "installed_device"
  TRANSPORTS SOCKET
  PROJECTION_CONFIG socket_config.json)
~~~

注意这里不再写一个“未来可能有的统一 API”来代替真实实现。真正 pipeline 是：

~~~text
.schema
   ↓ salts-idlc
typed IdlContract
   ├── binding compiler inputs
   ├── format plans
   ├── transport plans
   └── artifact projections
            ↓
generated ordinary C / build targets
~~~

然后 DataBind 运行时再把 generated binding inputs 与当前 CMeta 描述符编译成不可变 `DataBindBindingPlan`。

### 4.4 IDL completeness 必须同时通过反射与 Plugin boundary

一个 logical Service operation 只有“能生成 C header”还不够。对这本书，完整性判断是：

~~~text
Reflection can represent/admit it
        AND
Plugin can publish/use it safely across DSO
        AND
no second handwritten semantic contract is needed
~~~

Plugin path 现在有一个非常具体的准入检查 helper：

~~~c
data_bind_plugin_operation_execution_admit(
    operation,
    function_export,
    &execution);
~~~

它验证 generated DataBind 目录条目与 Plugin FUNCTION export 是否描述同一个 FunctionDesc / FunctionAbi / request / response shape，然后得到 canonical `DataBindNativeExecution`。更重要的是 lease interval：

~~~text
acquire Plugin lease
    ↓
admit operation/export
    ↓
compile/use BindingPlan
    ↓
bind native staging
    ↓
invoke exact execution
    ↓
publish response / typed error
    ↓
restore native values to semantic zero
    ↓
release Plugin lease
~~~

lease 不能只包住 machine-code function call。因为 FunctionDesc、FunctionAbi、exact invoke、generated lifecycle 回调、提供方-owned cleanup code 都可能属于 DSO。

~~~text
IDL completeness
    <=>
Reflection completeness
AND
Plugin-boundary completeness
~~~

在现有 memory/lifecycle model 下的实际含义。

## 5. Failure Semantics 与 Proof Obligations

IDL：

~~~text
message GetUserRequest {
    uint64 id;
}
~~~

native function：

~~~c
int get_user(
    UserRepository *repo,
    const char *id,
    User *out);
~~~

如果没有显式 conversion：

~~~text
uint64 -> const char *
~~~

编译器必须失败：

~~~text
error:
UserService.GetUser
  request field: id : uint64
  native param:   id : const char *
  no admitted conversion
~~~

不能在运行时偷偷 `atoi`、隐式 reinterpret 或 fallback to string。这就是编译器-driven design 的价值。

### 5.1 数值转换必须有可证明的边界

即使 conversion 被明确准入，也不能把“文本可以转成整数”写成模糊的运行时承诺。HTTP path 中的 `"42"` 是字符序列，不是已经存在的 `uint64_t` 对象。下面这个完整 C11 函数只接受非空十进制数字，不接受空格、正负号或前缀，并且只在整段输入成功后写入输出：

~~~c
bool book_parse_u64(const char *text, uint64_t *out)
{
    if (text == NULL || out == NULL || *text == '\0')
        return false;

    uint64_t value = 0;

    for (const char *p = text; *p != '\0'; ++p) {
        if (*p < '0' || *p > '9')
            return false;

        unsigned digit = (unsigned)(*p - '0');

        if (value > (UINT64_MAX - digit) / 10u)
            return false;

        value = value * 10u + digit;
    }

    *out = value;
    return true;
}
~~~

循环不变量是：`value` 等于已经读取的十进制前缀，并且 `value <= UINT64_MAX`。真正危险的表达式是：

~~~text
10 * value + digit
~~~

不能先计算它再检查是否溢出。条件：

~~~text
value <= (UINT64_MAX - digit) / 10
~~~

把同一个上界改写成不会先发生无符号 wraparound 的比较。于是每次乘加执行前都已经证明结果可表示。

输出还有一个独立的不变量：

~~~text
parse fails
    -> *out unchanged

parse succeeds
    -> *out written exactly once with the complete value
~~~

边界例应至少覆盖：

| 输入 | 结果 |
|---|---|
| `"0"` | 成功，得到 `0` |
| `"18446744073709551615"` | 成功，得到 `UINT64_MAX` |
| `"18446744073709551616"` | 失败，输出保持原值 |
| `""`、`"+1"`、`" 1"`、`"1x"` | 失败，输出保持原值 |

这不是要求 DataBind 复制这一段 parser；它是一个 **Plain C proof baseline**。真正的生成 conversion 可以使用别的实现，但必须保持同样的可观察 contract：接受哪些词法形式、怎样处理范围、失败是否保留目标对象，以及 null/missing/default 是否是不同状态。

### 5.2 Failure Atomicity 现在有真实生存期 transaction

当前 API 不再只靠一句“temporary storage then commit”表达 failure atomicity。一个完整 Service call 可以显式建立 single-owner 生存期：

~~~c
DataBindStatus data_bind_binding_plan_bind_call(
    const DataBindBindingPlan *plan,
    const DataBindBindingProvider *provider,
    const DataBindNativeOptions *native_options,
    DataBindBindingCallFrame *frame,
    DataBindBindingCallLifetime *lifetime,
    DataBindBindingPlanDiagnostic *diagnostic);
~~~

成功后：

~~~text
fresh native staging
    ↓ bind_call
live DataBindBindingCallLifetime
    ↓ exact invocation
DataBindBindingOutcome
    ↓ transactional egress
write_outcome
    ↓ cleanup
data_bind_binding_call_restore_zero
~~~

失败语义也因此更具体：

- `bind_call` 失败时，已初始化 native values 回滚到 canonical semantic zero；
- 生存期只在完整 bind 成功后才变成 live；
- typed error / native status / bridge failure 是不同结果层；
- output publication 使用 begin/write/commit/abort transaction；
- teardown 消费生存期一次，不能重试 destruction；
- Plugin-backed cleanup 必须发生在最终 lease release 之前。

可以把核心不变量写成：

~~~text
bind_call = error
    -> lifetime is empty
    -> no partially-owned native staging escapes

live lifetime
    -> exactly one restore_zero discharge
~~~

这比“出错就 free 一下”强得多，因为 cleanup authority 来自 canonical CMeta/DataBind lifecycle，而不是从 C pointer spelling 猜出来。

这两个结论还可以用“已初始化对象集合”来推导。令 `L` 表示当前已经成功取得生命周期责任的 staging 对象：

~~~text
L = {}

for each required native staging object x:
    initialize x
    if initialization fails:
        restore every object in L
        return with lifetime empty
    add x to L

publish live lifetime owning exactly L
~~~

对象只有在初始化成功后才进入 `L`，所以失败回滚不会销毁未初始化对象；失败时又遍历整个 `L`，所以不会漏掉之前已经取得的资源。完整 bind 成功后，`L` 不再属于一个局部回滚过程，而是整体转移给 live `DataBindBindingCallLifetime`；之后无论 exact invocation、egress 还是上层主动放弃，最终都只能消费这项责任一次。

输出事务则有另一条边界。固定快照中的 `DataBindBindingProvider` 明确提供 `begin_output`、`write_output`、`commit_output` 和 `abort_output`；`data_bind_binding_plan_write_outcome` 用这组入口发布成功或 typed error。其控制流可以概括为：

~~~text
publish(outcome):
    validate the selected outcome before publication
    begin_output
    for each compiled egress entry:
        convert native value
        write_output into provider-local staging
        if conversion/write fails:
            abort_output
            return failure
    commit_output
    if commit fails:
        abort_output
        return failure
    return success
~~~

这里 `write_output` 必须写入可撤销的 provider-local staging，而不是直接产生不可逆网络副作用；否则 `abort_output` 无法满足“commit 前失败不发布完整结果”的事务前提。header 的契约也明确规定：write/commit 失败必须 abort，并且不能报告成功。

因此需要分开两个事实：

~~~text
business invocation completed
        !=
output transaction committed
~~~

如果 exact business function 已经执行，而后续 `write_outcome` 或 transport commit 失败，失败只说明**发布没有被确认成功**，不能倒推出业务函数没有运行。默认 fail-fast policy 因此不能自动再次调用一个可能有副作用的业务函数；只有上层契约明确证明操作可重试、并定义去重/幂等语义时，才可以另行决定 retry。这与全书的 no-silent-fallback 原则一致。

### 5.3 哪些地方值得形式证明

IDL parser 正常解析一个字段，不值得因此引入 Lean。更值得 formalize 的是：

### Projection preservation

如果 backend 声称保持 logical operation：

~~~text
exec_HTTP(P_HTTP(op), req)
=
exec_Logical(op, decode_HTTP(req))
~~~

至少要说明 observable relation。

### Binding refinement

generated exact adapter 应该 refinement native binding plan：

~~~text
adapter_result
~
logical_service_result
~~~

### Transactional law

~~~text
failure before commit
    -> no observable partial output
~~~

是否进入 Lean，取决于风险和复用程度。先写清 rule，再决定 machine-check。

## 6. 三种 IR 与 Runtime Hot Path

现在可以看到：

~~~text
DataBind Contract IR
    UserService.GetUser
    Request -> Response

CMeta Native Semantic IR
    get_user
    params / direction / ownership

CFlow Execution IR
    optional admitted execution graph
~~~

这里是 **编译器 join / optional execution projection**，不是运行时 pipeline：

~~~text
Contract IR
    +
Native Semantic IR
    ↓ compile binding
BindingPlan / exact adapter
    ↓ optional execution admission
Execution IR
~~~

三个 IR 不能合并成一个“大一统描述符”。因为它们回答三个不同问题。

### 6.1 Runtime 最后到底剩下什么

下面第一条是明确的 **运行时 anti-pattern**：

~~~text
request
    ↓ runtime reflection
reflection
    ↓ schema lookup
schema lookup
    ↓ dynamic ABI work
dynamic invocation
~~~

期望的热路径是：

~~~text
request
    ↓ pre-resolved plan
precompiled MethodPlan
    ↓ exact call
exact C adapter
    ↓ encode/emit
response
~~~

Plugin 使用 **capability-resolution/call path**：

~~~text
lookup once / acquire lease
    ↓ resolve and retain
pre-resolved capability
    ↓ invoke
exact call
~~~

WASM 使用 **host/guest ABI boundary**：generated host adapter 调用已经定义好的 guest ABI；这里不是重新解析 IDL。这再次回到全书的核心：

Know more before execution; do less during execution.

## 7. Evidence：怎样证明这不是架构图

至少需要下面这些真实 gate。

### IDL/codegen

~~~text
valid IDL -> generated C compiles
invalid IDL -> deterministic diagnostic
~~~

### Native binding

~~~text
Service + FunctionDesc compatible -> plan
incompatible -> generation fails
~~~

### HTTP

~~~text
generated MethodPlan
-> real CHttp::Server
-> request/response integration test
~~~

### RPC

~~~text
typed client
-> CRPC
-> typed server
-> round trip
~~~

### Plugin / installed SDK

当前 installed-使用方 qualification 直接用 `salts_idl_target(... ARTIFACTS PLUGIN ...)` 生成 Plugin 与 client target。测试还要求 generated Plugin/client：

~~~text
must not link Salts::IDL / Salts::Schema frontend
~~~

这证明 frontend/编译器 knowledge 已经在 build plane 消失；installed 运行时使用方只带运行所需 closure。运行生命周期仍然要验证：

~~~text
installed shared library
-> acquire lease
-> admit generated operation/export
-> bind/call/publish/cleanup
-> quiescent unload
~~~

### WASM

~~~text
host
-> generated adapter
-> .wasm
-> response
~~~

### Cross-TU / DSO identity

这里验证的是：描述符 address 可以不同，但语义契约仍然匹配。这些证据分别验证不同主张。

## 8. 这不是一个更大的框架

我们没有得到“HTTP owns Service / RPC owns Service / Plugin owns Function 元数据 / WASM owns another IDL”，而是：

| 层 | 职责 |
|---|---|
| DataBind | logical contract |
| CMeta | native semantics |
| `salts-idlc` / `salts_idl_target` | IDL frontend + 构建期 projections |
| DataBind 运行时 plan 编译器 | generated binding + CMeta -> 不可变 BindingPlan |
| CHttp / CRPC / Plugin / WASM | 运行时使用方 |
| CFlow | optional execution IR |

减少的是 **duplicated 稳定知识**，不是普通 C implementation。

## 9. 小结

DataBind 的逻辑契约与 CMeta 的本地函数事实通过绑定编译连接。计划保存已检查的字段映射、转换与执行入口；每次调用单独拥有临时值、错误状态和清理进度。不同传输使用自己的投影，但应复用同一操作契约。绑定失败时，只回滚已经成功初始化的对象；Plugin 路径的外层租约必须持续到输入、调用、输出和清理全部结束。固定快照之间尚未完成的 API 迁移需要独立组合构建确认，示意命名不能代替该证据。
