# 第十一章：事件与状态机：类型检查、转移和提交

连接对象收到连接请求、成功通知和关闭事件时，会改变当前状态。把这些分支集中为状态机，可以在运行前检查事件类型和转移关系，并让所有运行实例遵守相同的选择与提交规则。CFlow Machine 保存不可变定义，Machine Instance 保存当前状态、邮箱和执行进度；CMeta 提供它们所依赖的类型与调用契约。

## 1. 用一个连接过程确定状态与事件

考虑三个状态：Disconnected、Connecting、Connected。事件 ConnectRequested 触发连接尝试，ConnectedEvent 携带连接标识，CloseRequested 结束使用。每种事件都有自己的身份，即使两个事件都携带 `int`，也不能互换。

以下普通 C 数据类型用于教学示例，不是 SDK 结构：

~~~c
typedef struct book_connecting {
    unsigned attempt;
} book_connecting;

typedef struct book_connected_event {
    int socket_id;
} book_connected_event;

typedef struct book_connected {
    int socket_id;
} book_connected;
~~~

连接成功的动作把事件中已验证的标识写入目标状态。`socket_id` 在本例中只是非负整数标识，不代表这个函数已经验证或取得了操作系统套接字的所有权。真实应用还要给套接字资源单独规定关闭责任。

| 源状态 | 事件 | 动作结果 | 目标状态 |
|---|---|---|---|
| Disconnected | ConnectRequested | 创建一次尝试的状态 | Connecting |
| Connecting | ConnectedEvent | 保存已接受的连接标识 | Connected |
| Connecting 或 Connected | CloseRequested | 生成终止状态值 | Closed |

这张表定义应用含义。执行器选用哪条线程、事件何时到达，是另外的运行问题。

## 2. 声明与实例分开

固定快照的转移行明确记录源状态、事件、守卫、动作、目标和优先级：

~~~c
typedef struct cflow_machine_transition {
    cflow_machine_state_id source;
    cflow_event_id event;
    cflow_machine_guard_id guard;
    cflow_machine_action_id action;
    cflow_machine_state_id target;
    uint32_t priority;
} cflow_machine_transition;
~~~

**守卫（guard）**是在候选转移中判断是否启用的条件函数。**动作（action）**根据源状态与事件构造目标状态，并可能准备输出。定义描述它们的类型、效果与标识；实例绑定真正的回调及上下文。

`cflow_machine_build` 复制声明数组、规范化、验证，成功后一次性发布不可变 Machine；失败保持空输出。CMeta 描述符仍被借用直到销毁。构建要拒绝重复或未知标识、类型不匹配、不合法终端转移和无法按规则消解的歧义，不能留到“恰好选中数组第一行”。

## 3. 事件接受不执行转移

`cflow_machine_instance_try_send` 把类型化事件复制进实例的有界邮箱。返回接受仅说明事件进入执行责任范围，不能据此认为目标状态已经可见。事件身份与载荷类型必须同时匹配；只比较载荷字节数不足以区别两个不同事件。

~~~text
admit_event(instance, event):
    reject closed or cancelled admission
    require declared event identity
    require matching payload type and valid storage
    require supported bounded payload and free mailbox capacity
    copy payload into one mailbox slot
    publish the accepted event
~~~

实际实例要求非手动的 SerialExecutor，并借用 Machine、执行器、回调与上下文直到销毁。多个生产者可以尝试发送事件，状态修改仍由串行执行域完成。序列化是实例的运行契约，不能靠用户回调偶然很短来代替。

## 4. 动作先构造暂存结果

下面的函数是与本章数据类型匹配的普通 C 教学动作，需要 `<stdbool.h>` 和 `<stddef.h>`。调用者必须传入活动且类型正确的对象；`target` 是与当前状态分离的暂存对象。

~~~c
static bool book_prepare_connected(
    const book_connecting *source,
    const book_connected_event *event,
    book_connected *target)
{
    if (source == NULL || event == NULL || target == NULL)
        return false;
    if (event->socket_id < 0)
        return false;

    book_connected next = { .socket_id = event->socket_id };
    *target = next;
    return true;
}
~~~

失败分支在写入 `target` 前返回，源状态始终只读。成功分支完整构造 `next` 后写入暂存区。这里的 **staging（暂存）**是先建立候选结果、稍后再决定是否发布，避免把半成品写入可见状态。

SDK 的统一动作回调使用 `void *` 存储入口，生成或绑定的代码必须像第三章 thunk 一样保持真实类型、对齐与生存期。`const void *` 也不能阻止回调通过另一个别名修改状态；遵守借用和无别名契约仍是实现责任。

## 5. 选择、执行与提交算法

下面的算法概括实例协议。内部互斥与回调调用位置经过简化；它不是可直接替换 SDK 的并发实现。

~~~text
step(instance, event):
    require a running, well-typed instance and a typed accepted event
    select one transition by the validated priority/guard rules
    if selection fails: record terminal error and consume this event once
    prepare target state and optional observation in separate storage
    if action fails:
        discard prepared output
        retain the old state value and record terminal error
    else:
        enter commit synchronization
        if cancellation has already won:
            discard prepared state and observation
        else:
            publish target state and its observation once
        leave commit synchronization
    settle the event and its temporary storage
~~~

**线性化点（linearization point）**是把一个并发操作视为已经生效的明确时刻。提交同步下发布目标状态，使观察者看到完整的旧状态或完整的新状态。它不意味着整个动作回调在一条机器指令中完成。

类型保持可分步推导：有效定义把选定动作的源类型和事件类型与当前输入对应；成功动作产生声明的目标类型；提交只发布这个已检查的值，因此新状态仍符合目标状态声明。动作失败保留原状态值，同时记录终止错误。若回调谎报类型或写出界，这些前提已被破坏，元数据无法修复内存错误。

## 6. Close 与 Cancel 的区别

固定快照对两种操作给出不同的在途处理规则：

| 操作 | 新事件与排队事件 | 已经执行的转移 |
|---|---|---|
| close | 停止接受并取消排队事件 | 保留在途转移的提交，然后终结 |
| cancel | 停止接受并取消排队事件 | 与提交竞争；取消先赢则丢弃暂存结果 |

假设动作已经算出新状态，但尚未提交。close 不撤销这次在途工作；正常成功的转移仍发布一次。cancel 若先取得提交同步，则暂存状态和观察均被丢弃；若提交先赢，结果保持可观察一次，cancel 阻止后续事件。动作自身失败仍按错误路径处理。

这些规则只覆盖 Machine 拥有的状态与准备的观察。动作若已经发出网络请求、写日志或修改外部对象，取消不会自动撤销这些效果。需要补偿、幂等请求或事务资源时，应用必须提供相应协议，不能把“状态未提交”解释为“世界没有变化”。

## 7. 小步语义与证明范围

**小步语义（small-step semantics）**用一次事件推进定义状态变化。固定快照的 `smallStep_deterministic` 表示：给定相同 Machine、守卫判定、动作解释、前置配置和事件，两次合法小步得到相同后置配置。它没有证明一个读取时钟的实际回调会在两次运行中返回相同值。

`step_consumes_once` 表示一个成立的小步使消耗计数增加一；失败小步也可能消耗事件，因此不能把它写成“每个事件必然成功转移一次”。`step_preserves_state_typing` 在模型条件下保持状态类型，`terminal_no_step` 和 `terminal_state_no_step` 排除终止后的继续推进。

动作失败定理还明确保留旧状态和值并进入错误终态。这与第五节的暂存算法一致，但对外部 I/O 不作回滚保证。源文件见 [Proofs/Machine.lean](https://github.com/qigao/salts/blob/a650262031e9b3e5f11a227a7911a75db9ae1fb8/formal/cmeta_cflow_calculus/CMetaCFlowCalculus/Proofs/Machine.lean)。

## 8. 应用与验证

定义层的失败例应覆盖未知事件、错误目标类型、重复优先级造成的歧义和终端出边。实例层应检查错误载荷不进入邮箱，接受后只由串行执行域修改状态，动作失败不发布半成品，以及 close/cancel 在提交前后的不同结果。

用第一个连接示例，可以在动作中设置可控屏障，分别让测试线程在准备前、准备后提交前、提交后发出关闭或取消。这种受控时序能直接对应契约，比依靠随机睡眠更容易诊断。销毁前应使生产者及附加的 Publisher/Resumable 适配器静止；`cflow_machine_instance_destroy` 要求静止实例，不能用它替代任意并发取消。

真实契约见 [machine.h](https://github.com/qigao/salts/blob/a650262031e9b3e5f11a227a7911a75db9ae1fb8/cflow/include/cflow/machine.h) 与 [machine_instance.h](https://github.com/qigao/salts/blob/a650262031e9b3e5f11a227a7911a75db9ae1fb8/cflow/include/cflow/machine_instance.h)。需要多生产者长期持有可撤销发送能力时，下一章在实例外增加 Actor 的身份与生命周期控制。

## 9. 小结

Machine 定义保存类型与转移规则，Instance 保存可变执行状态。事件接受、动作准备与状态提交是不同步骤，分别有自己的检查和失败行为。暂存使动作失败能够保留原状态，提交同步使取消竞争有明确结果；这些保证以真实类型、串行修改和有效借用为前提，并不自动回滚外部效果。
