# 第十一章：事件与状态机：类型检查、转移和提交

连接处理需要根据当前状态和输入事件选择动作。把转移关系存为数据后，CMeta 的类型描述和可调用对象可以检查事件载荷、守卫函数与动作函数。本章从这些 C 表示推导状态机的构建、选择、暂存和提交过程，明确并发输入、动作失败和取消分别在哪一步影响可见状态。

## 1. Typed Event 与 Immutable Transition

先把 event 表示清楚：

~~~c
typedef struct cflow_event {
    uint32_t type_id;
    const cmeta_type_desc *payload_type;
    const void *payload;
} cflow_event;
~~~

Event identity 与 payload type 分开。例如：

| Event | Payload |
|---|---|
| `CONNECT_OK` | `ConnectionInfo` |
| `TIMEOUT` | `TimeoutInfo` |

build/准入检查阶段检查 `event.type_id` 是否匹配 `transition.event`，以及 `payload_type` 是否匹配声明的 payload type；不是在 action 里 reinterpret_cast 风格猜测。

### 1.1 Transition 是 Immutable Definition

~~~c
typedef struct machine_transition {
    uint32_t from_state;
    uint32_t event_type;
    cmeta_callable guard;
    cmeta_callable action;
    uint32_t to_state;
} machine_transition;
~~~

Machine definition 经过 build 后不可变。Instance 才拥有：

~~~c
typedef struct machine_instance {
    const machine_def *def;
    uint32_t state;
} machine_instance;
~~~

所以：

| 对象 | 含义 |
|---|---|
| MachineDef | program |
| MachineInstance | 可变 execution state |

## 2. Build / Step / Admission

~~~text
build_machine(definition):

    require unique state ids
    require unique event ids

    for transition in definition.transitions:

        require known_state(transition.from)
        require known_state(transition.to)
        require known_event(transition.event)

        require guard signature admitted
        require action signature admitted

        bucket =
            index[transition.from,
                  transition.event]

        if transition is unguarded
           and bucket already has unguarded transition:
            reject AMBIGUOUS

        bucket.append(transition)

    for terminal state:
        require no outgoing admitted transition

    freeze definition
~~~

典型构建期 failure 包括 unknown state、unknown event、payload mismatch、duplicate unguarded transition、invalid guard/action 签名，以及 terminal state with outgoing transition。

### 2.1 Step Algorithm：Selection、Action、Commit 分开

~~~text
step(instance, event):

    require instance.state not terminal

    require event payload type valid

    candidates =
        index[instance.state, event.type]

    enabled = []

    for t in candidates:
        if no guard(t) or guard(t, event):
            enabled.append(t)

    require exactly_one(enabled)

    t = enabled[0]

    staged =
        run_action(t.action,
                   instance.state,
                   event)

    require staged.success

    old = instance.state
    instance.state = t.to_state

    observe_commit(old, event, t.to_state)

    return staged.effects
~~~

关键线性化点是 `instance.state = t.to_state`。在此之前都是 selection / staging。之后 transition 才对 observer 可见。

## 3. Small-Step Judgment、Admission 与 Failure

核心语义可以压缩成：

~~~text
M ⊢ (s, e) ⇓ (s', effects)
~~~

要求：

~~~text
event_typed(e)
∧ transition_selected_uniquely(M, s, e)
∧ guard_enabled
∧ action_success
────────────────────────────────────────
M ⊢ (s, e) ⇓ (s', effects)
~~~

determinism：

~~~text
M.Valid
∧ M ⊢ (s,e) ⇓ r1
∧ M ⊢ (s,e) ⇓ r2
────────────────
r1 = r2
~~~

terminal law：

~~~text
terminal(M, s)
──────────────
no step from s
~~~

这些才是 Lean 值得证明的对象。

### 3.1 Admission 不等于 Execution

如果 Machine 通过 mailbox/Actor 被调用，下面是 **message-准入检查 + serialized-execution path**：

~~~text
send(event)
    ↓ admission check
mailbox
    ↓ dequeue accepted event
serial executor
    ↓ owns mutation context
step(instance,event)
~~~

`send()` 返回 `OK` 只表示 **event accepted**，不表示 **transition committed**。这条边界后面直接被 Actor 复用。

### 3.2 Failure Paths

#### Ambiguous transition

~~~text
same state + same event
two enabled transitions
        ↓
AMBIGUOUS
~~~

不随机选一个。

#### Action failure

~~~text
action fails before commit
        ↓
state unchanged
~~~

可以写成：

~~~text
action(t,e) = error
───────────────────
state_after = state_before
~~~

#### Terminal state

~~~text
state is terminal
    ↓
CLOSED / NO_STEP
~~~

不允许 action 再偷偷把 terminal state 复活。后半章的 formal SmallStep、当前 C 实现和证据都围绕这些已明确算法展开。

## 4. 从 Machine 结构到 Canonical Machine

前面的设计已经把关键边界分开：Event 是有类型的值，Machine 是经过校验的不可变定义，只有 Instance 拥有可变状态；Guard 只决定转移是否可用，Action 复用已有 Callable，Serial Executor 提供串行修改边界，而 Machine 与更高层 Statechart 也不是同一个抽象。

后半章不再泛化“Machine 还能扩展什么”，而是固定一台 canonical connection machine，逐步展示一次 Event 如何经过准入、选择、Guard、暂存和提交。Lean 的小步语义与 C 实现围绕同一份转移契约展开，再分别用构建检查、有类型事件、串行修改、close/cancel 竞争和 sanitizer 证据约束实现。

### 4.1 Canonical Machine：把连接状态机变成 Typed Control Program

本章前面已经出现五个 state：Disconnected、Connecting、Connected、Closing、Closed，以及五个 event：Connect、ConnectedEvent、Disconnect、Timeout、ClosedEvent。这非常适合作为 Part IV 的贯穿 control example。普通 C 基线可以直接写成：

~~~c
switch (state) {
case DISCONNECTED:
    if (event.id == CONNECT) {
        state = CONNECTING;
    }
    break;

case CONNECTING:
    if (event.id == CONNECTED_EVENT) {
        state = CONNECTED;
    } else if (event.id == TIMEOUT) {
        state = DISCONNECTED;
    }
    break;

case CONNECTED:
    if (event.id == DISCONNECT) {
        state = CLOSING;
    }
    break;

case CLOSING:
    if (event.id == CLOSED_EVENT) {
        state = CLOSED;
    }
    break;

case CLOSED:
    break;
}
~~~

对于小程序，这仍然是很好的实现。只有当系统真正需要事件载荷类型检查、转移歧义检测、Guard/Action 契约、状态值类型变化、终止状态检查、可达性分析、有界 mailbox 准入、串行修改、形式化小步语义，或可复用的 observation/runtime adapter 时，Machine IR 才值得出现。因此本章仍然遵守全书第一原则：

普通 C first. Machine IR 不是为了替代简单 switch，而是为了保存 switch 里已经开始分散的程序知识。

## 5. Semantic Contract：一次 Event 到底如何改变 State

把 Machine 变成 IR 后，最重要的不是 struct 长什么样，而是明确一次 transition 的顺序。本书统一采用 **Machine small-step phase pipeline**：

~~~text
Event Admission
      ↓ validate identity/type
Transition Selection
      ↓ evaluate enablement
Guard Evaluation
      ↓ choose admitted transition
Action Evaluation
      ↓ stage result
State Commit
      ↓ publish committed effect
Observation Publication
~~~

这里箭头表示一次 SmallStep 内的阶段推进；每一步都有不同的所有权和 failure boundary。

### 5.1 Event Admission 不等于 Event Execution

Producer 调用 send 时，先校验 event id 与 payload type，再把事件复制进有界 mailbox，并返回准入结果；producer 线程不会直接运行 Guard/Action，也不会就地修改状态。这里描述的不是时间先后，而是一条**并发漏斗（concurrency funnel）**：

| 外部并发 | Admission boundary | Mutable owner |
|---|---|---|
| many producers | one 有界 mailbox | one serialized Machine owner |

因此可以接受并发 send，同时避免调用方 stack 成为 Machine transition stack。

### 5.2 Event identity 与 payload type 必须同时匹配

一个 Event 要合法，至少要求 event id 已声明，而且声明的 payload type 与提交时的 payload type 一致。即使二者都使用 `Buffer`，`DataReceived(Buffer)` 与 `ConfigLoaded(Buffer)` 仍是不同事件；载荷类型不能代替事件身份。

### 5.3 Transition Selection 必须 deterministic

对于 `state = Connecting, event = Timeout`，不能存在两个同优先级且同时可用的 transition，再让运行时按数组顺序“刚好选一个”。Machine build 应把这种歧义提前到控制面拒绝。若设计确实允许多个候选项，选择策略必须成为明确的语义规则，例如规定**显式优先级最小者获胜**，并保证优先级键足以消除未决平局。

### 5.4 Guard 只决定 enable，不拥有 commit

Guard 可以读取当前状态值和 event payload，并返回 enabled/disabled，但不应修改 Machine 拥有的状态。否则“选择哪条 transition”本身就产生副作用，确定性、重试和验证都会变得困难。因此 Guard 契约倾向要求 `PURE`、`DETERMINISTIC`、`TOTAL`、`NO_ALIAS`。注意：

> 这些元数据是准入检查 contract；如果要依赖更强的数学性质，仍需要 trusted implementation/证明。

### 5.5 Action 应先构造 staged target，再 commit

Action 不应该一边运行一边直接覆写 current state。更安全的事务边界是：

~~~text
current state
+
event
    ↓
action
    ↓
staged target state
+
optional observation
    ↓
validate result
    ↓
atomic commit
~~~

这样 Action failure 可以保持 **current Machine state unchanged**，至少对 Machine-owned state 是如此。外部 I/O side effect 是否可回滚，则属于另一个 contract，不能被 Machine 假装解决。

### 5.6 Commit 是 transition 的线性化点

对于并发 close/cancel 与正在执行的 transition，需要有一个明确问题：

> 到底谁先赢？

如果 commit 先赢：

~~~text
new state/observation
    → visible exactly once
~~~

如果 cancel 在 commit 以前赢：

~~~text
staged state/observation
    → discarded
~~~

线性化点（linearization point）是在一次并发操作的执行区间内，规定该操作对外视为已经发生的时刻。这里用提交步骤决定转移结果与取消谁先取得可见效果，从而给并发调用确定的顺序；互斥锁的范围只是实现手段，还需与这项顺序契约一致。实现必须让可观察结果符合这个提交顺序。

### 5.7 Terminal State 必须阻止后续 SmallStep

`Closed`、`Done`、`Error` 等终止状态不是普通标签。一旦 Machine 进入终止状态，**后续任何 Event 都不能再启动会修改状态的小步转移**。Producer 可以收到 `CLOSED`、`CANCELLED` 或其他终止状态码，但不能把原 Instance 重新拉回活动状态；需要重新开始时，应构造新的 Instance。

## 6. Lean：Machine 已经有真正的 SmallStep semantics

本版 Salts 快照中的 `CMetaCFlowCalculus/CFlow/Machine.lean` 与 `CMetaCFlowCalculus/Proofs/Machine.lean` 已经把 Machine 从设计图推进为形式化转移系统。核心对象包括 `StateDecl`、`GuardDecl`、`ActionDecl`、`Transition`、`Machine`、`TypedEvent`、`Config`、`ActionResult`、`MachineObservation` 和 `SmallStep`，它们与本章的 C 设计逐项对应。

### 6.1 Machine.Valid：把构建期 validation 变成证明 premise

formal Machine.Valid 要求：

- states nonempty；
- state / guard / action IDs unique and nonzero；
- event schema valid；
- initial state known；
- transition source/target/event known；
- guard types align；
- action source/event/target types align；
- active-source requirement；
- priority keys unique；
- all states reachable；
- all declared guards/actions used。

这正好对应一个专业 Machine builder 应该在 publish 不可变 IR 以前做的事情。于是运行时定理不需要每一步重新问“这个 transition target 到底存在吗？”，因为 Machine.Valid 已经把这项检查提前付掉了。这是典型的：

这些检查在构建时完成，运行时只使用已验证的转移定义。

### 6.2 smallStep_deterministic

当前定理 `smallStep_deterministic` 表达：

如果同一个 Machine、Guard valuation、Action evaluation、Before Config 和 Typed Event 分别得到 first 与 second，那么：

~~~text
first = second
~~~

这就是 state-machine determinism 的核心。注意它并不说“所有 C 回调都天然 deterministic”，而是说：

> 在给定 formal guard/action evaluation 的前提下，Machine transition relation 本身是 deterministic。

这会迫使 C design 把 selection rule、priority、ambiguity 和 guard/action contract 说清楚。

### 6.3 smallStep_requires_event_typing

已有定理 `smallStep_requires_event_typing` 说明任何成功 SmallStep 都蕴含 event id 已知，并且 payload type 与 declared event schema 匹配。这让 typed mailbox 不再只是 API ergonomics。它直接成为 transition semantics 的前置条件。

### 6.4 step_consumes_once

现有 `step_consumes_once` 证明每个成功 SmallStep：

~~~text
after.consumedEvents
=
before.consumedEvents + 1
~~~

这个不变量给出已消费事件数与成功提交次数的关系：

~~~text
one admitted/selected event
    → at most one committed Machine step
~~~

后面把 Machine 放进 Actor mailbox 后，这条性质会成为 message accounting 的基础。

### 6.5 step_preserves_state_typing

现有定理 `step_preserves_state_typing` 在以下前提下：

~~~text
Machine.Valid
before.WellTyped
EventTyped
SmallStep
~~~

前提下，证明：

~~~text
after.WellTyped
~~~

也就是说：

> 一次合法 transition 不会把 state value 变成与 target state 声明不匹配的类型。

这正是 Typed State Machine 相对普通 “enum state + void*” 真正增加的价值。

### 6.6 terminal_no_step / terminal_state_no_step

`terminal_no_step` 与 `terminal_state_no_step` 说明：

~~~text
terminal Config
or
terminal state kind
    ↓
no next Machine step
~~~

所以 terminal 不是文档约定，而是 transition relation 的结构约束。

### 6.7 Action failure 保持 Machine-owned state

已有定理 `applyTransition_action_failure`。对于声明 MAY_FAIL 且实际返回 error 的 Action，after 保持：

~~~text
state = before.state
stateValue = before.stateValue
terminal = error(message)
~~~

这精确表达了：

> action 可以失败，但不能留下半提交的 Machine-owned state。

这就是 staged action + atomic commit 为什么值得设计。

## 7. Current C Implementation：Machine 定义与 Instance 严格分层

对照本版 Salts 实现快照 qigao/salts@a650262031e9b3e5f11a227a7911a75db9ae1fb8：

当前实现明确分成两个层次：

| 对象 | 职责 |
|---|---|
| cflow_machine | 不可变 definition |
| cflow_machine_instance | live 可变 execution owner |

这比把所有字段塞进一个 Machine struct 清楚很多。

### 7.1 Immutable Machine 是 transactional build artifact

当前 Machine definition 接收 states、events、guards、actions、transitions 和 initial state；build API 依次执行复制、规范化、校验和原子发布。任何一步失败，destination 都保持为空。这与 Graph normalize/optimize 的“构造并发布新产物”原则一致。

#### Build 可以明确拒绝

当前状态码已经覆盖重复 id、未知 state/event/guard/action、类型不匹配、无效契约、无效 observation、从终止状态发出的 transition、歧义 transition、不可达状态、未使用声明和超出限制等情况。这说明大量错误已经真正从运行时转移前移到 build/准入阶段。

### 7.2 Transition 声明行是普通、可检查的数据

当前 transition 直接保存 source、event、guard、action、target 和 priority。这使 transition relation 不再藏在回调 control flow 里。Build、diagnostics、formal model、test tooling 都可以讨论同一个结构。

### 7.3 State / Guard / Action 全部带类型信息

State / Guard / Action 的类型事实可以直接列成表：

| Row | Typed facts |
|---|---|
| State | state id、state value type、state kind |
| Guard | state type、event id/type、effects、properties |
| Action | source type、event id/type、target type、effects、properties、observation kind/type |

这使 State Machine 真正继承前几章的 CMeta/Callable vocabulary，而不是重新造一套弱类型回调 system。

### 7.4 Instance 才拥有可变 state

Machine Instance 的配置包含不可变 Machine、初始状态字节、Guard/Action 绑定、有界 mailbox 容量、Serial Executor 和可选输出类型；Instance 本身负责当前状态、mailbox、正在进行的 transition、首个错误、cancel/close 状态、observations 和统计信息。这正对应形式化 `Config` 的运行时层。

### 7.5 Instance 明确要求 non-manual SerialExecutor

当前初始化契约要求 **executor 必须是非 manual 的 SerialExecutor**。这是前一章 Executor 设计第一次直接服务于更高层模型。Machine 不需要知道具体 worker thread、线程池布局或 OS 调度策略；它只依赖**串行执行能力**，从而保证 transition mutation 始终只有一个 owner。

### 7.6 Mailbox 是有界 typed 准入检查 boundary

当前 Event/Mailbox API 使用 event id + payload 描述符的有限 schema；初始化时固定 schema、容量和 payload stride/storage。send 时：

~~~text
unknown id
    → INVALID_ARGUMENT

known id + wrong payload type
    → TYPE_MISMATCH

full
    → FULL

closed/cancelled
    → explicit terminal status
~~~

而不是 silent drop。这会直接成为下一章 Actor message 准入检查的基础。

## 8. Close / Cancel 与正在执行的 Transition

真实 stateful 运行时最难的部分，往往不是正常 transition，而是 shutdown race。当前 Machine Instance 已经明确区分：

~~~text
close
cancel
~~~

### 8.1 Close

Close 会 stop new 准入检查、cancel queued Events，并 preserve an already executing transition commit。如果 close 与 transition 重叠：

> 正在执行的 transition 如果已经赢得 commit，会 exactly once 可见，然后再 terminal settlement。

这更接近 graceful shutdown。

### 8.2 Cancel

Cancel 同样停止准入检查并取消 queued Events，但与正在执行 transition 的 commit 竞争：

~~~text
cancel wins before commit
    → staged state/observation discarded

commit wins first
    → result remains observable exactly once
~~~

这里的 commit/cancel linearization 是语义契约。Lock 只是实现机制。

### 8.3 External Action Effects 不自动 rollback

当前 contract 也明确：

> Action 回调对 Machine-owned state 之外产生的 effect 不会被自动回滚。

状态机事务可以保护自身暂存的状态和观察结果发布，但不能撤销已经发生的网络发送、数据库写入、文件修改或硬件动作。需要补偿这些副作用时，应用必须另行定义工作流或事务策略。

## 9. Evidence：Machine 需要同时验证 build、step、race 和 refinement

### 9.1 Build-time evidence

每类非法 Machine 都应有明确测试，例如重复 ID、未知引用、类型不匹配、歧义 transition、从终止状态出发的 transition、不可达状态、未使用 Guard/Action 和无效 observation 契约，并验证失败后目标对象保持规定状态。

~~~text
failed build
    → destination remains empty
~~~

### 9.2 Small-step conformance

C 测试应构造与 Lean fixture 对应的同一套 state schema、event schema、transition 声明和 Guard/Action 结果，然后比较 **Lean `SmallStep` 的期望 trace/state** 与 **C Instance 实际观察到的 trace/state**。这比只验证几个业务结果更接近真正的 refinement 检查。

### 9.3 Typed Event evidence

Mailbox tests需要确认：

~~~text
correct event id/type
    → accepted

known id + wrong descriptor
    → TYPE_MISMATCH

unknown id
    → INVALID_ARGUMENT

capacity exhausted
    → FULL
~~~

并且失败不能部分写入 mailbox。

### 9.4 Serial mutation evidence

多个 producer 并发发送 Event 时，对 Machine 当前状态的修改仍必须满足**一次只提交一个 transition**。可以用 in-flight instrumentation、transition trace、Serial Executor 统计和压力测试验证这一点，而不能仅凭“用了 mutex”就假定语义等价。

### 9.5 Close / cancel race evidence

至少覆盖执行前 close、Action 执行后但 commit 前 close、commit 后 close、commit 前 cancel、commit 后 cancel，以及重复 close/cancel，并检查状态可见性、observation 数量、队列事件取消、首个错误和终止标志。

### 9.6 Sanitizer evidence

Guard/Action 绑定和有类型状态复制涉及借用回调、user context、状态 buffer、event payload 副本和 mailbox 存储，因此必须进入 ASan/UBSan/压力测试。Lean 可以证明 `WellTyped` 等语义性质，但不会替 C 实现发现 buffer 生存期错误。

## 10. 小结

状态机定义保存状态、事件和转移规则，实例保存可变状态。构建阶段利用 CMeta 类型与调用契约检查事件载荷、守卫和动作；执行阶段则按选择、暂存和提交推进一次转移。事件进入队列并不意味着转移已经执行。动作失败、关闭和取消需要以明确的提交顺序决定哪些结果可见，且同一实例只能有一个状态修改者。Actor 将在这个模型外增加并发投递、身份和生存期管理。
