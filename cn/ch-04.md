# 第四章：从可调用对象到计算图：表示与类型检查

CMeta 可以描述单个函数的类型与调用方式；组合多个函数时，还需要记录哪个输出进入哪个输入。CFlow 的计算图保存这些连接关系，并在执行前检查类型、容量和拓扑。本章从偶数平方和循环构造节点与边，用判断规则说明合法连接，再给出构图、规范化与执行状态分离的实现。

**术语说明：** IR 是 intermediate representation（中间表示），把后续阶段需要检查或转换的知识显式保存为数据；本章的 Graph 就是计算关系的 IR。control plane（控制面）负责构造、校验和选择执行方案，hot path（热路径）则处理实际流经的值。

## 1. Plain C Baseline：先固定同一条类型链

在引入 Graph 之前，先把贯穿第 4–7 章的三个普通 C 函数写清楚：

~~~c
#include <stdbool.h>
#include <stddef.h>

static bool is_even(int x)
{
    return x % 2 == 0;
}

static long square(int x)
{
    return (long)x * (long)x;
}

static long sum(long a, long b)
{
    return a + b;
}

long sum_even_squares(const int *xs, size_t n)
{
    long total = 0;

    for (size_t i = 0; i < n; ++i) {
        int x = xs[i];

        if (!is_even(x))
            continue;

        total = sum(total, square(x));
    }

    return total;
}
~~~

后续都使用同一组类型：

~~~text
is_even : int -> bool
square  : int -> long
sum     : (long, long) -> long
~~~

示例假设每次平方与累加结果都能由 `long` 表示；整数溢出不是 Graph 可以替调用方消除的前置条件。

这段循环已经是很好的 C。如果系统只需要这一条固定计算，不需要检查、改写或选择其他执行后端，就应继续保留它。Graph 的价值不在于“替代 for loop”，而在于让原本只隐含在控制流里的 `Filter → Map → Reduce` 关系在执行前成为可检查的数据。

## 2. Node 与 Edge 的 C Representation

概念性 Node：

~~~c
typedef struct cflow_node {
    cflow_op op;

    cmeta_type_id input_type;
    cmeta_type_id output_type;

    const cmeta_callable *callable;
} cflow_node;
~~~

Edge：

~~~c
typedef struct cflow_edge {
    uint32_t from;
    uint32_t to;
} cflow_edge;
~~~

Graph：

~~~c
typedef struct cflow_graph {
    cflow_node *nodes;
    size_t node_count;

    cflow_edge *edges;
    size_t edge_count;
} cflow_graph;
~~~

Graph 保存的是 **program structure**，不是 live execution state。

## 3. Build Algorithm：类型错误在构造阶段失败

~~~text
add_edge(graph, from, to):

    a = graph.nodes[from]
    b = graph.nodes[to]

    require a.output_type == b.input_type

    require no forbidden cycle
    require capacity available

    graph.edges.append(from, to)

    return OK
~~~

例如，把 `Map<int,long>` 接到 `Filter<User>` 时，因为 `long != User`，构造阶段直接返回 `TYPE_MISMATCH`，不用等第一条 value 到来才发现。

## 4. Graph Validity Judgment

**记号说明：** `Γ ⊢ e : T` 读作“在环境 Γ 给出的类型与假设下，e 具有 T”；横线以上是前提，以下是由这些前提推出的结论。这里的判断式描述 Graph 必须满足的条件。

最小判断式：

~~~text
Γ ⊢ node_i : A -> B
Γ ⊢ node_j : B -> C
──────────────────────
Γ ⊢ edge(i,j) : valid
~~~

整图：

~~~text
all nodes typed
∧ all edges type-compatible
∧ all required inputs connected
∧ terminal/output constraints satisfied
───────────────────────────────────────
Γ ⊢ Graph : Valid
~~~

Graph.Valid 是后续 normalize/optimize/证明的前提。

## 5. Graph 不直接拥有 Runtime

不要让 Node 同时保存当前值、线程、socket、pending wake 或可变 Subscription 状态。Graph 应保持不可变；活动状态属于 frame、Subscription、Executor、Source 或 Machine Instance。

| 对象 | 含义 |
|---|---|
| Graph | program |
| Execution state | 运行时 instance |

这条边界让同一 Graph 可以有不同执行 backend。

## 6. Build -> Normalize -> Compile

Graph 进入执行前至少经过下面这条 **编译器/artifact transformation pipeline**；箭头表示“产生下一阶段 artifact”，不是运行时数据流：

~~~text
Surface Graph
    ↓ validate
Primitive Graph
    ↓ normalize
Normalized Snapshot
    ↓ optimize
Optimized Graph
    ↓ compile
Plan / Direct
~~~

伪码：

~~~text
compile(graph):

    require validate(graph)

    g1 = normalize(graph)
    g2 = optimize(g1)

    if direct_eligible(g2):
        return compile_direct(g2)

    return compile_plan(g2)
~~~

所以 Graph 是控制面 IR，不必成为每个 value 的热路径 lookup table。

## 7. Failure Cases

### Type mismatch

如果 edge 的 source output type 与 destination input type 不兼容，返回 `TYPE_MISMATCH`。

### Capacity

如果 `node_count == max_nodes`，返回 `FULL`。如果有界 graph 是 contract，就不偷偷 realloc。

### Unsupported operator shape

如果 operator 不能 lower 到 selected backend，返回 `UNSUPPORTED`. 不要 silent fallback 到另一套运行时。后半章继续用同一个 canonical pipeline 检查 Graph semantics、证明 obligation、C implementation 与 performance 证据。

## 8. Canonical Example：把第三章的三个 Callable 连成一张 Graph

第三章最后已经准备了三个 callable：`is_even : int -> bool`、`square : int -> int` 和 `sum : int × int -> int`。普通 C 最直接的版本其实仍然很好：

~~~c
long total = 0;
bool has_value = false;

for (size_t i = 0; i < n; ++i) {
    int x = input[i];

    if (!is_even(x))
        continue;

    int y = square(x);

    if (!has_value) {
        total = y;
        has_value = true;
    } else {
        total = sum(total, y);
    }
}
~~~

如果程序只需要这一条固定 pipeline，普通 C 甚至可能就是最好的实现。Graph 出现的条件不是“for loop 不够现代”，而是系统开始需要在执行之前知道：

- 有哪些 stage？
- stage 的 input/output type 是什么？
- 哪些 stage 会丢弃 value？
- 哪些 stage 改变 cardinality？
- 哪些 Callable 有 effect/property？
- 哪些连接不合法？
- 是否允许 normalize / optimize / compile？

于是同一个计算可以先被保存成：

~~~text
Input<int>
    ↓
Filter<int>(is_even)
    ↓
Map<int,int>(square)
    ↓
Reduce<int>(sum)
~~~

这一步的本质是：

把只存在于控制流里的关系，提升成可以检查和变换的数据。

### 8.1 Graph 不是执行结果，而是执行前的知识

一旦关系被保存下来，我们第一次同时拥有：

~~~text
topology
types
operators
callables
effects
properties
parameters
nested subgraphs
~~~

这使后续阶段能够在任何 input value 到来之前完成大量工作。这里不是“construction 转换成 execution”，而是两个阶段承担不同成本：

| 阶段 | 职责 |
|---|---|
| Graph construction | pay semantic/structural cost early |
| Graph execution | use already-admitted structure |

这正是全书后面不断重复的 **Pay Before Execution**。

## 9. Semantic Contract：什么才算一张合法 Typed Graph

Graph 不是“装着一些 node 的数组”。它至少需要满足四类 contract。

### 9.1 Topology well-formedness

每条 Edge 必须引用存在的 node/port。不能出现 dangling endpoint、invalid port、invalid nested subgraph reference 或 impossible entry/tail。这属于结构合法性。

### 9.2 Type preservation across edges

如果 node A 的输出类型是 `T`、node B 的输入类型是 `U`，那么连接 `A -> B` 必须满足对应的语义类型兼容关系。不能因为两个值都能通过 `void *` 传递，就允许它们连接。对于贯穿全书的例子：

~~~text
Input<int>
  -> Filter<int>
  -> Map<int,int>
  -> Reduce<int>
~~~

每一步的类型都是准入检查的一部分，而不是运行时 cast 的猜测。

### 9.3 Operator contract

Node 不只保存 Callable。Operator 自己还带有语义，例如：

~~~text
FILTER
    cardinality: 0..1
    output type: same as input

MAP
    cardinality: 1
    output type: callable return

FLAT_MAP
    cardinality: 0..N

REDUCE
    cardinality: N..1
~~~

所以 Graph 的类型推导需要同时考虑 **operator schema、callable 签名、input type**，而不是只看 function pointer。

### 9.4 Mutation / snapshot boundary

Graph 构造阶段可以修改 owning IR。但一旦某个 Graph 被交给 normalize、optimize、compile、verify 或 execute，这些阶段都必须绑定到一个明确版本的结构。如果结构在背后变化，而 Plan/Certificate 仍然继续使用旧假设，就会破坏可信边界。因此 Graph version 不是普通 debug counter。它表达的是：

这份 downstream knowledge 到底绑定到哪一个具体 IR snapshot。

## 10. Lean / Proof Obligation：Graph 阶段先证明什么

第四章还不需要把整个 optimizer correctness 一次证明完。这里最重要的是先建立 Graph semantics 的基础。

### 10.1 Well-formed Graph

可以定义一个 predicate：

~~~text
WellFormed(g)
~~~

它至少要求：node 引用有效、edge port 有效、边两端类型兼容、operator 签名已准入、嵌套 Graph 结构良好，以及 root/entry/exit 合法。只有这样，后续定理才能共享统一前提：

~~~text
WellFormed(g) → ...
~~~

而不是每个改写都重新证明一遍结构合法性。

### 10.2 Graph observable semantics

必须先回答：

> “两张 Graph 语义相同”到底是什么意思？

最小模型可以先把一张纯同步 Graph 看成：

~~~text
input sequence
    ↓
zero or more output values / terminal result
~~~

于是可以定义某种：

~~~text
observe(g, input)
~~~

后面的 normalize / optimize 定理才能写成：

~~~text
observe(surface, input)
=
observe(normalized, input)
~~~

或更一般的 ObsEq。如果没有 observable semantics，“结构更简单”本身并不能推出“程序等价”。

### 10.3 Normalize preservation

Normalize 最先应该拥有的定理不是“更快”，而是：

~~~text
WellFormed(surface)
→
ObsEq(surface, normalize(surface))
~~~

这条 law 很关键。因为从这里开始，Surface Graph 与 Primitive/Normalized Graph 可以是两种不同 physical representation，但仍然属于同一个 semantic program。

### 10.4 Lean 暂时不证明 Graph storage layout

本章仍然要明确证明边界。Lean 不会证明 `malloc` 一定成功、C struct ABI 在所有编译器上完全一致、某种 cache layout 一定更快，或任意指针生存期都正确；这些属于 C 实现、工具链和运行时证据。这里的形式化只覆盖 IR 含义、类型关系、结构不变量和语义保持。

## 11. Current C Implementation：Graph 已经是一个真正的 owning IR

对照本版 Salts 实现快照 `qigao/salts@ad389928b437c0612c1c60844fe53677f3ed27a6`：

本版 CFlow 实现 Graph 已经不是抽象伪代码。它有明确的：

~~~text
cflow_graph
  owns subgraphs

cflow_subgraph
  owns nodes + edges

cflow_node
  stores op/callable/types/params/nested refs

cflow_edge
  stores typed topology coordinates
~~~

### 11.1 Edge 是显式 IR 条目

本版 snapshot 中 `cflow_edge` 的 public definition 已经明确到端口：

~~~c
typedef struct cflow_edge {
    cflow_node_id from;
    uint16_t from_port;
    cflow_node_id to;
    uint16_t to_port;
} cflow_edge;
~~~

这意味着 Graph 不再被限制为“线性数组里的下一个 operator”。Branch、Relation、Subgraph 可以在同一 IR 中拥有显式拓扑。

### 11.2 Node 保存的是 operator semantics + callable + type knowledge

同一 snapshot 中，node 的职责可以概括成：

~~~text
operator
optional callable
optional fused callable chain
input type
output type
nested subgraph references
typed semantic parameters
relation policy
~~~

这和前面三章形成真正连接。这里是 **node-construction equation**，不是执行顺序：

**Typed Graph Node = CMeta Type + CMeta Callable + CFlow Operator Schema**

因此 Graph 是前面 Meta 能力的 integration point，而不是另起一套 type system。

### 11.3 Graph 是 owning handle，但声明行是 read-only introspection

当前 API 的边界非常专业：

~~~text
Graph builder functions
    → supported mutation API

node/edge/subgraph rows
    → read-only introspection
~~~

直接修改 storage/容量并不是 public contract。这解决一个常见 C library 问题：

> “struct 是 public 的”不等于“每个字段都允许调用方任意写”。

### 11.4 Version 把 downstream artifacts 绑定到具体 Graph state

当前 owning Graph 持有 process-local nonzero mutation token。成功 mutation / clone / initialization 会更新版本；destroy 恢复 zero。这让 optimizer trace、certificate、compiled plan 和运行时准入检查都可以明确回答：

> “我是不是还绑定在原来那张未变化的 Graph 上？”

### 11.5 Normalize / Optimize 都输出新的 Graph

当前 optimizer 契约已经明确：`src` 是不可变的 normalized Graph，`dst` 是新建且独立拥有的 optimized Graph，不在源对象上边执行边改写。这样源图含义始终可检查，变换结果拥有自己的 IR，验证也可以直接比较两边；这与形式化的 preservation 证明自然一致。

## 12. Evidence：Graph 这一层已经可以建立完整 C-side verification chain

第四章不能只用“Graph validate 返回 true”作为证据。当前代码已经提供更完整的 verification pipeline：

~~~text
validate surface
    ↓
normalize + validate
    ↓
normalize(normalized)
    ↓
check structural idempotence
    ↓
optimize + validate
    ↓
optimize(optimized)
    ↓
check structural idempotence
    ↓
execute surface / normalized / optimized
    ↓
compare observable output
    ↓
when eligible:
compile direct plan
    ↓
compare output again
~~~

这些证据分别覆盖模型、代码生成和实际执行。

### 12.1 Structural evidence

检查 topology、node 描述符、relation schema 和 fused chains 是否满足预期结构。

### 12.2 Differential semantic evidence

同一 input 分别经过 surface、normalized、optimized 和 compiled plan；如果 observable result 不同，就说明 transformation chain 有真实 regression。

### 12.3 Formal evidence

Lean 负责证明：**某类 transformation 在明确前提下 preserves observable semantics**。

### 12.4 Runtime evidence

C differential tests 检查真实 implementation 是否符合 formalized transformation contract。两者结合比任何一方单独存在都强。

## 13. Performance Evidence：Graph 本身也需要知道自己的成本

Graph 作为控制面 IR，并不意味着 Graph traversal cost 可以忽略。本版 CFlow 已经有专门的 graph-path benchmark，覆盖 1、16、256、4096 个 operator。并比较不同 successor representation / traversal strategy。只要某个 abstraction 可能进入热路径，就必须测量它；如果它不应该进入热路径，就要展示怎样把它 compile/lower 掉。

因此第四章不需要声称“Graph 是零成本的”。更准确的结论是：**Graph 是可分析的控制面 IR；后续执行路径应尽量避免反复解释 Graph。** 这自然引出第七章的 Plan、Direct 与 AOT。

## 14. 小结

计算图保存操作、类型和连接关系，使类型不相容、缺失输入和非法拓扑可以在构造时被拒绝。CMeta 的可调用对象进入节点后，其参数与结果契约成为连接检查的依据；执行中的当前值、等待状态和资源仍由独立实例拥有。不可变快照为规范化、优化和计划编译提供稳定输入。后续变换须证明保持指定的观察结果，执行成本则通过与普通循环的比较确定。Stream 接口将在这些规则之上简化构图。
