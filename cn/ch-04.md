# 第四章：从可调用对象到计算图：表示与类型检查

把三个函数顺序调用，并不需要计算图。只有在执行前需要检查连接、选择受支持的执行方式或改写组合时，才值得把调用关系保存为数据。CFlow 使用 CMeta 的类型描述和可调用对象建立这种表示。本章用偶数平方和说明图中保存什么、如何检查，以及检查通过后能够保证什么。

## 1. 从循环提取计算关系

下面是普通 C 函数片段，需要 `<stddef.h>`。前提是 `n <= 1000`，各输入在 `[-100, 100]` 内，非空输入由有效数组提供。每个平方不超过 `10000`，总和不超过一千万，落在 C11 保证的 `long` 范围内。

~~~c
long sum_even_squares(const int *xs, size_t n)
{
    long total = 0;
    for (size_t i = 0; i < n; ++i) {
        int x = xs[i];
        if (x % 2 != 0)
            continue;
        total += (long)x * x;
    }
    return total;
}
~~~

输入 `{1, 2, 3, 4, 5, 6}` 得到 `56`；空输入得到零。循环包含三个不同的操作：筛选保留偶数，映射把 `int` 变成 `long`，归约把若干 `long` 合并为一个 `long`。它们的类型关系如下。

| 操作 | 调用签名 | 值流的类型和数量 |
|---|---|---|
| Filter | `int -> bool` | 保留输入的 `int` 类型，可能减少数量 |
| Map | `int -> long` | 每个保留值产生一个 `long` |
| Seeded Reduce | `(long, long) -> long` | 以零为初值，最后产生一个 `long` |

这里使用有初值归约来解释循环。第五章的无初值 Reduce 在空输入时没有结果，使用方须明确处理这种差别。一个 `int` 归约器不能仅因示例数值较小就接到 `long` 输出之后。

## 2. 节点、端口与边

IR 是 intermediate representation（中间表示），即把后续阶段需要检查或转换的程序事实保存为数据。Graph 是计算关系的 IR；节点保存算子、类型与调用信息，边连接节点的端口。端口是节点对外编号的输入或输出位置，不能在多输入节点上省略。

固定快照的边表示为：

~~~c
typedef struct cflow_edge {
    cflow_node_id from;
    uint16_t from_port;
    cflow_node_id to;
    uint16_t to_port;
} cflow_edge;
~~~

下面是用于解释校验的简化结构，不是 SDK 布局。`book_port` 只保留类型，实际节点还包含算子模式、可调用对象和子图信息。

~~~c
typedef struct book_port {
    const cmeta_type_desc *type;
} book_port;

typedef struct book_node_view {
    const book_port *inputs;
    size_t input_count;
    const book_port *outputs;
    size_t output_count;
} book_node_view;
~~~

索引和指针承担不同职责：节点编号用于在图中定位，CMeta 类型身份用于判断语义类型相容。不能把两个描述符的地址相等作为跨翻译单元的类型相等条件；第二章介绍的结构化身份才是这项检查的依据。

## 3. 先检查地址范围，再读取类型

以下是连接检查的伪代码，`type_equal` 代表 CMeta 的语义类型比较。返回名称用于说明失败类别，不是承诺某个 API 具有同名状态码。

~~~text
connect(graph, from, out_port, to, in_port):
    reject if either node id is outside graph
    a = graph.nodes[from]
    b = graph.nodes[to]
    reject if out_port or in_port is outside its node
    reject if the destination port is already occupied
    reject if not type_equal(a.outputs[out_port], b.inputs[in_port])
    reject if this edge violates the operator's topology rules
    reserve storage; on failure leave the logical graph unchanged
    append the edge and update the graph version
~~~

顺序本身是安全条件。先访问 `graph.nodes[from]`，再检查 `from`，已经来不及防止越界。类似地，类型比较只有在两个端口存在、描述符有效时才有意义。

局部连接正确还不足以建立整图有效性。构图过程中可以暂时存在未连接端口；提交给规范化或计划编译前，必须检查必需输入是否齐全、根与终端是否合法、嵌套子图引用是否存在，以及所用算子允许的拓扑。第九章的等待与恢复状态属于执行实例，不能通过加入普通数据边替代其协议。

## 4. 类型保持的推导

`Γ ⊢ e : T` 读作“在环境 Γ 的声明和假设下，e 具有类型 T”。下面的规则把一个已知输出与一个相容输入连接起来：

~~~text
Γ ⊢ f : A -> B       Γ ⊢ g : B -> C
-----------------------------------
Γ ⊢ g ∘ f : A -> C
~~~

`g ∘ f` 表示先执行 `f` 再执行 `g`。若 `f` 接受一个有效的 `A` 并成功产生有效的 `B`，则 `g` 的类型前提得到满足；在 `g` 也成功的条件下，结果具有 `C` 类型。沿有限线性管道归纳，就得到每一条成功传递的值符合下一节点输入类型的结论。

这项推导依赖三个条件：描述符真实描述了 C 调用，调用者提供有效存储，操作实现遵守声明。类型相容不能证明 `square` 不溢出，也不能证明一个借用指针仍然有效。循环的数值范围前提和函数的生存期契约必须一起保留。

Filter 的证明还要说明数量变化。对每个输入，谓词为真时传递原值，为假时不传递，因此输出保持输入类型及相对次序。Reduce 则需要累加器类型封闭：本例 `long × long -> long` 的每一步都能作为下一步的左实参。归约是否允许重排是另一个问题，留到第七章讨论。

## 5. 构图对象与运行实例

Graph 在构造期间可变；交给一次校验、变换或执行编译时，应遵守相应 API 的不变借用要求。固定快照用非零版本令牌标识初始化、克隆和成功修改后的图状态，销毁后版本归零。它帮助识别旧证据，不能代替并发访问同步。

| 对象 | 保存的状态 | 生存期责任 |
|---|---|---|
| Graph | 节点、边、子图和构图参数 | 按图 API 构造和销毁；借用的描述仍需有效 |
| Plan | 已解析的执行步骤与调用信息 | 按计划 API 编译和销毁 |
| 执行帧或 Subscription | 当前值、需求额度、等待和清理状态 | 每次执行独立维护 |
| Executor | 任务排队、运行与关闭 | 依照接受任务后的清理协议 |

同一份计算关系可以用于多次执行，但不能让节点中的一个可变计数器被多个执行实例无约束地共享。例如 Take 的静态上限属于图，每次执行已经取出的数量属于该次执行。

## 6. 从有效图构造执行产物

**规范化（normalization）**把不同合法写法整理为后续阶段约定的基本形式。它处理程序表示，不消费输入值。下面的伪代码把后端选择列为显式输入：

~~~text
compile_surface(surface, requested_backend):
    require valid(surface)
    normalized = normalize_into_separate_destination(surface)
    require valid(normalized)
    optimized = apply_authorized_rewrites(normalized)
    require supported(optimized, requested_backend)
    return compile_for(optimized, requested_backend)
~~~

一个合法图仍可能超出某个后端的支持范围。请求 Direct 却包含 Reduce 时，应报告不支持；由调用者另行选择 Plan。存储分配失败与执行后端不支持也不是同一种错误。实际 Graph 使用其自身的存储管理规则，不能把某个教学用固定数组的 `FULL` 规则说成所有 Graph API 的契约。

固定快照的 `cflow_graph_create_seeded_reduce_node` 创建有初值的齐次归约节点，并拥有初值的类型化副本。这个 API 可以表达第一节循环的初值语义；具体构图还需有效子图、匹配的 reducer 和正确的连接。低层节点创建不等于整图已经完成校验。

## 7. 如何验证图检查器

检查应针对错误所在的层次。先测试无效节点和端口能否在解引用前拒绝，再测试 `Map<int,long>` 到 `Filter<User>` 的类型错误；最后测试缺少必需输入和无效子图等整图条件。对于有效图，用第五章的输入比较手写循环和图执行结果，并单独检查空输入。

变换验证还需要保留源图并比较变换前后的观察结果。修改源图后，依赖原版本的匹配证据应失效；销毁与重新初始化不能使旧证据重新获得效力。有关执行产物的证书在第七章展开。

本章实际结构与 API 依据固定快照的 [graph.h](https://github.com/qigao/salts/blob/a650262031e9b3e5f11a227a7911a75db9ae1fb8/cflow/include/cflow/graph.h)。类型推导是针对所述线性组合的手工论证，不是对任意图或任意 C 函数的自动证明。

## 8. 小结

计算图保存循环中原本隐含的算子、类型和连接关系。有效连接要求端点存在、端口合法、语义类型相容且拓扑符合算子规则；完整执行还需要输入范围、有效存储和生存期前提。图描述与执行状态分开后，规范化和计划编译可以提前处理结构，而每次运行独立维护值、计数器及资源。
