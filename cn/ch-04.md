# 第四章：从 Callable 到 Graph——把计算本身变成数据

> **Graph 的新增价值只有一个：保存计算关系。**
>
> Plain C 已经能算。
>
> Graph 让系统在执行前看到 operator、input/output type、callable、edge relation 和 ownership，因此可以在 build time 完成 validate、normalize、rewrite 和 compile。

**术语说明：** IR 是 intermediate representation（中间表示），把后续阶段需要检查或转换的知识显式保存为数据；本章的 Graph 就是计算关系的 IR。control plane（控制面）负责构造、校验和选择执行方案，hot path（热路径）则处理实际流经的值。

---

## 1. Plain C Baseline

~~~c
long sum_even_squares(const int *xs, size_t n)
{
    long total = 0;

    for (size_t i = 0; i < n; ++i) {
        int x = xs[i];

        if ((x & 1) != 0)
            continue;

        total += (long)x * x;
    }

    return total;
}
~~~

这段代码没有问题。

它的问题只在于执行以后，`Filter → Map → Reduce` 这个结构不再作为 program object 存在。

如果不需要 inspect / rewrite / alternate backend，继续使用这个 loop。

---

## 2. Node 与 Edge 的 C Representation

概念性 Node：

~~~c
typedef struct cflow_node {
    cflow_op op;

    cmeta_type_id input_type;
    cmeta_type_id output_type;

    const cmeta_callable *callable;
} cflow_node;
~~~

Edge：

~~~c
typedef struct cflow_edge {
    uint32_t from;
    uint32_t to;
} cflow_edge;
~~~

Graph：

~~~c
typedef struct cflow_graph {
    cflow_node *nodes;
    size_t node_count;

    cflow_edge *edges;
    size_t edge_count;
} cflow_graph;
~~~

Graph 保存的是 **program structure**，不是 live execution state。

---

## 3. Build Algorithm：类型错误在构造阶段失败

~~~text
add_edge(graph, from, to):

    a = graph.nodes[from]
    b = graph.nodes[to]

    require a.output_type == b.input_type

    require no forbidden cycle
    require capacity available

    graph.edges.append(from, to)

    return OK
~~~

例如，把 `Map<int,long>` 接到 `Filter<User>` 时，因为 `long != User`，构造阶段直接返回 `TYPE_MISMATCH`，不用等第一条 value 到来才发现。

---

## 4. Graph Validity Judgment

**记号说明：** `Γ ⊢ e : T` 读作“在环境 Γ 给出的类型与假设下，e 具有 T”；横线以上是前提，以下是由这些前提推出的结论。这里的判断式描述 Graph 必须满足的条件。

最小判断式：

~~~text
Γ ⊢ node_i : A -> B
Γ ⊢ node_j : B -> C
──────────────────────
Γ ⊢ edge(i,j) : valid
~~~

整图：

~~~text
all nodes typed
∧ all edges type-compatible
∧ all required inputs connected
∧ terminal/output constraints satisfied
───────────────────────────────────────
Γ ⊢ Graph : Valid
~~~

Graph.Valid 是后续 normalize/optimize/proof 的前提。

---

## 5. Graph 不直接拥有 Runtime

不要让 Node 同时包含 current value、thread、socket、pending wake 或 mutable subscription state。Graph 应该 immutable。

Live state 属于 frame、subscription、executor、source 或 machine instance。

| 对象 | 含义 |
|---|---|
| Graph | program |
| Execution state | runtime instance |

这条边界让同一 Graph 可以有不同执行 backend。

---

## 6. Build -> Normalize -> Compile

Graph 进入执行前至少经过下面这条 **compiler/artifact transformation pipeline**；箭头表示“产生下一阶段 artifact”，不是 runtime dataflow：

~~~text
Surface Graph
    ↓ validate
Primitive Graph
    ↓ normalize
Normalized Snapshot
    ↓ optimize
Optimized Graph
    ↓ compile
Plan / Direct
~~~

伪码：

~~~text
compile(graph):

    require validate(graph)

    g1 = normalize(graph)
    g2 = optimize(g1)

    if direct_eligible(g2):
        return compile_direct(g2)

    return compile_plan(g2)
~~~

所以 Graph 是 control-plane IR，不必成为每个 value 的 hot-path lookup table。

---

## 7. Failure Cases

### Type mismatch

如果 edge 的 source output type 与 destination input type 不兼容，返回 `TYPE_MISMATCH`。

### Capacity

如果 `node_count == max_nodes`，返回 `FULL`。如果 bounded graph 是 contract，就不偷偷 realloc。

### Unsupported operator shape

如果 operator 不能 lower 到 selected backend，返回 `UNSUPPORTED`.

不要 silent fallback 到另一套 runtime。

后半章继续用同一个 canonical pipeline 检查 Graph semantics、proof obligation、C implementation 与 performance evidence。

## 8. Canonical Example：把第三章的三个 Callable 连成一张 Graph

第三章最后已经准备了三个 callable：`is_even : int -> bool`、`square : int -> int` 和 `sum : int × int -> int`。

Plain C 最直接的版本其实仍然很好：

~~~c
long total = 0;
bool has_value = false;

for (size_t i = 0; i < n; ++i) {
    int x = input[i];

    if (!is_even(x))
        continue;

    int y = square(x);

    if (!has_value) {
        total = y;
        has_value = true;
    } else {
        total = sum(total, y);
    }
}
~~~

这段代码没有问题。

如果程序只需要这一条固定 pipeline，普通 C 甚至可能就是最好的实现。

Graph 出现的条件不是“for loop 不够现代”，而是系统开始需要在执行之前知道：

- 有哪些 stage？
- stage 的 input/output type 是什么？
- 哪些 stage 会丢弃 value？
- 哪些 stage 改变 cardinality？
- 哪些 Callable 有 effect/property？
- 哪些连接不合法？
- 是否允许 normalize / optimize / compile？

于是同一个计算可以先被保存成：

~~~text
Input<int>
    ↓
Filter<int>(is_even)
    ↓
Map<int,int>(square)
    ↓
Reduce<int>(sum)
~~~

这一步的本质是：

> **把只存在于控制流里的关系，提升成可以检查和变换的数据。**

### 8.1 Graph 不是执行结果，而是执行前的知识

一旦关系被保存下来，我们第一次同时拥有：

~~~text
topology
types
operators
callables
effects
properties
parameters
nested subgraphs
~~~

这使后续阶段能够在任何 input value 到来之前完成大量工作。

这里不是“construction 转换成 execution”，而是两个阶段承担不同成本：

| 阶段 | 职责 |
|---|---|
| Graph construction | pay semantic/structural cost early |
| Graph execution | use already-admitted structure |

这正是全书后面不断重复的 **Pay Before Execution**。

---

## 9. Semantic Contract：什么才算一张合法 Typed Graph

Graph 不是“装着一些 node 的数组”。

它至少需要满足四类 contract。

### 9.1 Topology well-formedness

每条 Edge 必须引用存在的 node/port。

不能出现 dangling endpoint、invalid port、invalid nested subgraph reference 或 impossible entry/tail。这属于结构合法性。

### 9.2 Type preservation across edges

如果 node A 的 output type 是 `T`、node B 的 input type 是 `U`，那么连接 `A -> B` 必须满足对应的 semantic type compatibility。

不能因为两个 value 都能塞进 void * 就允许连接。

对于 canonical example：

~~~text
Input<int>
  -> Filter<int>
  -> Map<int,int>
  -> Reduce<int>
~~~

每一步的类型都是 admission 的一部分，而不是 runtime cast 的猜测。

### 9.3 Operator contract

Node 不只保存 Callable。

Operator 自己还带有语义，例如：

~~~text
FILTER
    cardinality: 0..1
    output type: same as input

MAP
    cardinality: 1
    output type: callable return

FLAT_MAP
    cardinality: 0..N

REDUCE
    cardinality: N..1
~~~

所以 Graph 的类型推导需要同时考虑 **operator schema、callable signature、input type**，而不是只看 function pointer。

### 9.4 Mutation / snapshot boundary

Graph 构造阶段可以修改 owning IR。

但一旦某个 Graph 被交给 normalize、optimize、compile、verify 或 execute，这些阶段都必须绑定到一个明确版本的结构。

如果结构在背后变化，而 Plan/Certificate 仍然继续使用旧假设，就会破坏可信边界。

因此 Graph version 不是普通 debug counter。

它表达的是：

> **这份 downstream knowledge 到底绑定到哪一个具体 IR snapshot。**

---

## 10. Lean / Proof Obligation：Graph 阶段先证明什么

第四章还不需要把整个 optimizer correctness 一次证明完。

这里最重要的是先建立 Graph semantics 的基础。

### 10.1 Well-formed Graph

可以定义一个 predicate：

~~~text
WellFormed(g)
~~~

它至少包含 node references valid、edge ports valid、edge types compatible、operator signatures admitted、nested graphs well formed，以及 root/entry/exit valid。

然后后面的 theorem 才能拥有统一前提：

~~~text
WellFormed(g) → ...
~~~

而不是每个 rewrite 都重新证明一遍结构合法性。

### 10.2 Graph observable semantics

必须先回答：

> “两张 Graph 语义相同”到底是什么意思？

最小模型可以先把一张纯同步 Graph 看成：

~~~text
input sequence
    ↓
zero or more output values / terminal result
~~~

于是可以定义某种：

~~~text
observe(g, input)
~~~

后面的 normalize / optimize theorem 才能写成：

~~~text
observe(surface, input)
=
observe(normalized, input)
~~~

或更一般的 ObsEq。

如果没有 observable semantics，“结构更简单”本身并不能推出“程序等价”。

### 10.3 Normalize preservation

Normalize 最先应该拥有的 theorem 不是“更快”，而是：

~~~text
WellFormed(surface)
→
ObsEq(surface, normalize(surface))
~~~

这条 law 很关键。

因为从这里开始，Surface Graph 与 Primitive/Normalized Graph 可以是两种不同 physical representation，但仍然属于同一个 semantic program。

### 10.4 Lean 暂时不证明 Graph storage layout

这一章仍然要保持 proof boundary。

Lean 不应该假装证明 malloc 一定成功、C struct ABI 在所有 compiler 上相同、cache layout 一定更快或 pointer lifetime 永远正确；这些属于 C implementation / toolchain / runtime evidence。

形式化在这里证明的是 IR meaning、type relation、structural invariant 和 semantic preservation。

## 11. Current C Implementation：Graph 已经是一个真正的 owning IR

对照本版 Salts 实现快照 `qigao/salts@ad389928b437c0612c1c60844fe53677f3ed27a6`：

本版 CFlow 实现 Graph 已经不是抽象伪代码。

它有明确的：

~~~text
cflow_graph
  owns subgraphs

cflow_subgraph
  owns nodes + edges

cflow_node
  stores op/callable/types/params/nested refs

cflow_edge
  stores typed topology coordinates
~~~

### 11.1 Edge 是显式 IR row

本版 snapshot 中 `cflow_edge` 的 public definition 已经明确到端口：

~~~c
typedef struct cflow_edge {
    cflow_node_id from;
    uint16_t from_port;
    cflow_node_id to;
    uint16_t to_port;
} cflow_edge;
~~~

这意味着 Graph 不再被限制为“线性数组里的下一个 operator”。

Branch、Relation、Subgraph 可以在同一 IR 中拥有显式拓扑。

### 11.2 Node 保存的是 operator semantics + callable + type knowledge

同一 snapshot 中，node 的职责可以概括成：

~~~text
operator
optional callable
optional fused callable chain
input type
output type
nested subgraph references
typed semantic parameters
relation policy
~~~

这和前面三章形成真正连接。这里是 **node-construction equation**，不是执行顺序：

**Typed Graph Node = CMeta Type + CMeta Callable + CFlow Operator Schema**

因此 Graph 是前面 Meta 能力的 integration point，而不是另起一套 type system。

### 11.3 Graph 是 owning handle，但 rows 是 read-only introspection

当前 API 的边界非常专业：

~~~text
Graph builder functions
    → supported mutation API

node/edge/subgraph rows
    → read-only introspection
~~~

直接修改 storage/capacity 并不是 public contract。

这解决一个常见 C library 问题：

> “struct 是 public 的”不等于“每个 field 都允许 caller 任意写”。

### 11.4 Version 把 downstream artifacts 绑定到具体 Graph state

当前 owning Graph 持有 process-local nonzero mutation token。

成功 mutation / clone / initialization 会更新版本；

destroy 恢复 zero。

这让 optimizer trace、certificate、compiled plan 和 runtime admission 都可以明确回答：

> “我是不是还绑定在原来那张未变化的 Graph 上？”

### 11.5 Normalize / Optimize 都输出新的 Graph

当前 optimizer contract 已经明确：`src` 是 immutable normalized Graph，`dst` 是 new owned optimized Graph，而不是在原对象上边执行边改写。

这是非常重要的工程边界：source meaning remains inspectable、transformation result owns new IR、verification can compare both sides。它也天然适合 formal preservation story。

---

## 12. Evidence：Graph 这一层已经可以建立完整 C-side verification chain

第四章不能只用“Graph validate 返回 true”作为证据。

当前代码已经提供更完整的 verification pipeline：

~~~text
validate surface
    ↓
normalize + validate
    ↓
normalize(normalized)
    ↓
check structural idempotence
    ↓
optimize + validate
    ↓
optimize(optimized)
    ↓
check structural idempotence
    ↓
execute surface / normalized / optimized
    ↓
compare observable output
    ↓
when eligible:
compile direct plan
    ↓
compare output again
~~~

这非常重要，因为它把几类 evidence 分开了。

### 12.1 Structural evidence

检查 topology、node descriptors、relation schema 和 fused chains 是否满足预期结构。

### 12.2 Differential semantic evidence

同一 input 分别经过 surface、normalized、optimized 和 compiled plan；如果 observable result 不同，就说明 transformation chain 有真实 regression。

### 12.3 Formal evidence

Lean 负责证明：**某类 transformation 在明确前提下 preserves observable semantics**。

### 12.4 Runtime evidence

C differential tests 检查真实 implementation 是否符合 formalized transformation contract。两者结合比任何一方单独存在都强。

---

## 13. Performance Evidence：Graph 本身也需要知道自己的成本

Graph 作为 control-plane IR，并不意味着 Graph traversal cost 可以忽略。

本版 CFlow 已经有专门的 graph-path benchmark，覆盖 1、16、256、4096 个 operator。

并比较不同 successor representation / traversal strategy。

这给书一个非常好的写作原则：

> **只要某个 abstraction 可能进入 hot path，就必须测量它；如果它不应该进入 hot path，就要展示怎样把它 compile/lower 掉。**

所以第四章不需要声称“Graph is zero-cost”。更准确的说法是：**Graph is analyzable control-plane IR，later execution paths should avoid repeated Graph interpretation when possible。**

这会自然引到第七章的 Plan / Direct / AOT。

---

## 14. What We Learned

第四章完成的是一条 **design progression**，不是 runtime pipeline：

**Typed Data → Typed Behavior → Typed Program Structure**。

Graph 的价值不在于替换 for loop。

它真正带来的是：

1. **Topology becomes data.**
2. **Types survive across computation boundaries.**
3. **Operator semantics become explicit.**
4. **Construction/admission can fail before execution.**
5. **Normalize / Optimize / Compile can work on immutable snapshots.**
6. **Lean finally has a program structure on which to state preservation theorems.**
7. **C verification can compare surface/normalized/optimized/compiled observations.**
8. **Execution can later remove Graph knowledge instead of repeatedly interpreting it.**

canonical example 也从 three independent Callables 正式变成：

~~~text
Source<int>
    ↓
Filter(is_even)
    ↓
Map(square)
    ↓
Reduce(sum)
~~~

第五章不会重新设计一套数据处理 runtime。

它只回答：

> **既然 Graph 已经能够表达这条 pipeline，能不能给普通 C 用户一个更轻、更自然的 façade 来构造它？**

答案就是 Stream。

---

**小结：Graph 让“行为”进一步变成“程序结构”**

前一章把 Function **描述/投影为可组合的 Callable**；这一章再把多个 Callable 之间的 relation **物化为 Graph**。

这是一条 semantic-design progression，不是 runtime 调用链。Graph 保存的是行为之间的关系，而不是“先调用 Callable、再调用 Graph”。

于是第一次可以**在执行之前看到整个计算**，并对它进行 Validation、Type Propagation、Inference、Lowering、Optimization 和 Compilation。

这就是 CFlow 真正出现的地方。

而 Graph 做出来以后，我们很快发现它特别适合表达 Filter、Map、FlatMap、Reduce、Collect 这一类数据转换。

也正是在这里，下一步才自然出现：

> **既然 Graph 已经能够很好地表达数据转换，能不能在它上面提供类似 Java Stream 的高级接口，让复杂的数据处理在 C 中也可以用更声明式、更类型化的方式表达？**

下一章将从这个发现继续：**从 Graph 到 Stream——为什么高级数据转换 API 可以只是 Graph 的一个轻量 façade，而不需要成为另一个重量级运行时。**
