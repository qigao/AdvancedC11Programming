# 第五章：Stream 接口：构造有类型的计算图

直接建立节点和边能够完整表达计算，但常见的过滤、映射和归约还可以提供更紧凑的接口。本章用 Stream 构造前一章的同一张计算图，逐步追踪操作对应的节点、输入范围的借用和执行状态的创建，并说明为什么接口改写必须保持图的输出、顺序和错误行为。

**术语回顾：** façade 是薄的外观接口；本章的 Stream 负责把用户操作转换成 Graph。observable semantics（可观察语义）指调用者按契约能够观察到的行为，例如输出值、顺序和错误；接口变得更方便后，这些行为仍须保持一致。

## 1. Surface API

下面用接近 C 的伪代码表示接口意图，并非当前 SDK 中可直接编译的调用。实际的显式接收者接口见本章第 11.3 节：

~~~text
stream_int s =
    stream_from_int(xs, n);

stream_long out =
    stream_int_filter(
        &s,
        &is_even)
    .map(&square);

long total =
    stream_long_reduce(
        &out,
        0,
        &sum);
~~~

过滤和映射调用只向同一张图追加节点，归约描述最终结果的计算方式。构图与实际遍历输入是两个阶段。

## 2. Builder Pseudocode

~~~text
stream.filter(predicate):

    require predicate : T -> bool

    node =
        graph.add(
            FILTER,
            input=T,
            output=T,
            callable=predicate)

    graph.connect(stream.tail, node)

    return Stream<T>(
        graph = stream.graph,
        tail  = node)
~~~

Map：

~~~text
stream.map(f):

    require f : T -> U

    node = graph.add(
        MAP,
        input=T,
        output=U,
        callable=f)

    graph.connect(stream.tail, node)

    return Stream<U>(
        graph,
        node)
~~~

Reduce：

~~~text
stream.reduce(init, reducer):

    require reducer : (A,T) -> A

    node = graph.add(
        REDUCE,
        input=T,
        output=A,
        callable=reducer,
        init=init)

    graph.connect(stream.tail, node)

    return Terminal<A>(graph,node)
~~~

## 3. Type Rules

Filter：

~~~text
p : T -> bool
────────────────
Filter<T>(p) : T -> T
~~~

Map：

~~~text
f : T -> U
──────────────
Map<T,U>(f) : T -> U
~~~

Reduce：

~~~text
r : (A,T) -> A
────────────────
Reduce<A,T>(r) : Stream<T> -> A
~~~

所以很多错误在 builder call 时已经可拒绝。

## 4. Range / Stream / Collector Ownership

不要让 Stream secretly own user data。推荐所有权：

| 对象 | Ownership |
|---|---|
| Range | borrows source data |
| Stream | owns/borrows Graph builder state |
| Collector | owns destination policy |
| Execution | owns transient frame |

下面的接口伪代码只展示输入、输出与执行对象之间的关系：

~~~text
IntRange range =
    int_range(xs, n);

UserVec out = {0};

UserVec_init(&out, 64);

stream_execute(
    stream_from_range(&range)
        .filter(...)
        .map(...),
    vec_collector(&out));
~~~

源与目标所有权仍然由普通 C object 表达。

## 5. Façade Preservation Rule

接口构造与直接构图必须表达相同的计算。这里的相等指图语义相同，不要求两个描述对象占用同一地址：

~~~text
build_stream(program)
=
build_graph(program)
~~~

更具体：

~~~text
eval(lower(StreamSurface))
=
eval(CanonicalGraph)
~~~

所以 Stream 不应该偷偷改变 encounter order、插入 hidden buffering、drop error、改变所有权，或选择不同的 fallback backend。

## 6. Lowering 回普通 Loop

对于：

~~~text
Source
 -> Filter(is_even)
 -> Map(square)
 -> Reduce(sum)
~~~

下面的普通循环是这条计算的语义基线。固定快照的 Direct 路径主要支持 Filter/Map；包含 Reduce 的完整流程应按第七章说明使用编译计划，不能把这个循环当作当前 Direct 已生成的结果：

~~~c
long total = 0;

for (size_t i = 0; i < n; ++i) {
    int x = xs[i];

    if (!is_even(x))
        continue;

    total += square(x);
}
~~~

这个基线用于核对输出与执行成本；后端能否生成等价的直接代码，还取决于其支持范围和资格检查。

## 7. Failure Cases

### Wrong predicate

如果 `Stream<int>` 收到 `User -> bool` predicate，返回 `TYPE_MISMATCH`。

### Invalid reducer

如果 reducer 是 `(double,int) -> long`，而要求的是 `(long,int) -> long`，返回 `TYPE_MISMATCH`。

### Unsupported lowering

如果 surface 已接受、canonical Graph 也合法，但所选 backend 无法 lower，就返回 `UNSUPPORTED`。Façade API 的存在并不意味着所有 backend 都支持所有 Graph 形状。后半章继续检查 canonical pipeline、语义保持、真实 C 实现和 benchmark 约束。

## 8. Canonical Example：同一张 Graph，换一个更适合用户的入口

第四章已经有了：

~~~text
Input<int>
    ↓
Filter(is_even)
    ↓
Map(square)
    ↓
Reduce(sum)
~~~

下面是构图顺序的简化示意，省略了当前 API 的配置和错误处理，不能作为完整 SDK 示例直接编译：

~~~c
cflow_stream s = {0};

cflow_stream_init(&s, &cmeta_type_int);

s.filter(&s, is_even)
 ->map(&s, square)
 ->reduce(&s, sum);
~~~

三次调用分别追加 Filter、Map 和 Reduce 节点，节点类型与连接合法性仍由已有 Graph 规则检查。接口改变的是构图方式，后续优化与执行继续使用同一份图描述。

## 9. Semantic Contract：Stream façade 不能偷偷改变什么

### 9.1 Operator semantics 必须与 Graph 一致

如果 Graph 中：

~~~text
FILTER
    output type = input type
    cardinality = 0..1

MAP
    output type = callable return
    cardinality = 1

REDUCE
    homogeneous fold
    cardinality = N..1
~~~

那么 Stream 不能因为 surface API 不同而重新定义这些规则。因此 Stream method 本质上应该是 **typed Graph builder wrapper**，而不是 second semantic authority。

### 9.2 Stream owns the description, not the source data

Stream 可以拥有 Graph 描述、复制后的 Range view、evaluation options 和 builder/准入状态，但输入 object/container 的真实数据仍由原 owner 管理。因此 **Stream 生存期不等于 container 生存期**。如果绑定的是 borrowed Range，那么整个 evaluation 期间原 owner 都必须继续存活，并满足 Range 契约。

### 9.3 Evaluation state 必须与 reusable Graph 分离

可重复执行的描述需要满足：

> 同一条 Stream/Graph description 可以在条件允许时多次执行，但每次执行拥有新的 cursor/operator state。

不能把 reduce accumulator、skip counter、take counter、publisher cursor 这些 live execution facts 写回 Graph 本身，否则 **Build Once, Execute Many** 会立刻失效。

### 9.4 “可链式”不等于“延迟执行对象无限增长”

Stream 只负责 construction。当用户真正执行时，可以选择 direct synchronous evaluation、normalized Graph、compiled Plan 或 Reactive Subscription。因此链式 API 不是成本模型。真正成本取决于：

实际选中的执行后端及其状态和分派方式。

## 10. Lean / Proof Obligation：Stream 这一层应该证明什么

Stream façade 本身不需要拥有一套新的复杂 formal semantics。更自然的证明目标是：

### 10.1 Surface-to-Graph construction correctness

如果一串 Stream 方法依次是 filter `f`、map `g`、reduce `h`，并构造出对应的 `FILTER(f)`、`MAP(g)`、`REDUCE(h)` Graph，那么 Stream 的可观察语义应直接继承 Graph。证明问题因此可以写成：

~~~text
BuildStream(ops) = g
→
StreamSemantics(ops, input)
=
GraphSemantics(g, input)
~~~

如果 Stream 只是 deterministic builder，这个定理应该非常薄。这正是好事。Façade 越薄，需要独立证明的语义就越少。

### 10.2 Type-chain preservation

对于：

~~~text
T
  --filter--> T
  --map f--> U
  --reduce--> U
~~~

需要确保 surface method 不可能偷偷绕过 Graph 准入检查。例如：

~~~text
map : T -> U
next filter expects V
U != V
~~~

应该在 Graph construction/准入检查阶段失败。

### 10.3 Reusable description / fresh execution separation

形式模型中最好明确区分 **Program Description** 与 **Execution State**。这会在后面的 Reactive 章节变得更加重要。如果 formal model 一开始就把 cursor/demand/cancel state 塞进 Graph，就会把控制面与 execution plane 混在一起。

## 11. Current C Implementation：Stream 真的就是 Graph façade

对照本版 Salts 实现快照 `qigao/salts@ad389928b437c0612c1c60844fe53677f3ed27a6`：

当前 cflow_stream 的核心形态非常直接：

~~~c
struct cflow_stream {
    cflow_graph graph;

    cmeta_range input_range;
    bool has_input_range;

    cflow_eval_options eval_options;
    bool failed;

    /* generated explicit-self operator methods */
    ...
};
~~~

这段 representation 本身就回答了很多问题。

### 11.1 Graph 是 Stream 的核心 owned description

Stream 不是指向一个隐藏 Stream 运行时。它直接拥有 `cflow_graph graph`，operator method 的主要工作就是继续构造它。这里不是运行时 flow，而是实际 **representation/所有权 relation**：Stream 直接 owns Graph description。它不是架构图上的理想关系，而是 data layout 本身。

### 11.2 Range 是输入协议，不是 Graph 的一部分

`input_range` 与 `has_input_range` 表示这个 Stream 当前绑定了哪一种 input view，但不改变 Graph 的 operator semantics。这让 array、container Range、channel-like publisher 和 other source 可以逐步共享后面的计算描述。

### 11.3 Method 字段是显式 self 的 ISO C11 façade

当前 Stream methods 不是 C++ member function。它们仍然只是 C function pointer 字段：

~~~text
stream.filter(&stream, ...)
stream.map(&stream, ...)
~~~

这样的设计有两个价值：

1. 保持 ISO C11；
2. surface syntax 更接近 fluent API，但没有引入 object 运行时。

### 11.4 Public Graph view 是 read-only introspection

当前 API 的 `cflow_stream_graph()` 返回 borrowed read-only Graph view。普通用户不应该直接写 `stream.graph.nodes[...] = ...` 来绕过 builder contract。这延续了第四章的原则：

public visibility 不等于 arbitrary mutability。

## 12. Evidence：canonical pipeline 已经存在于真实测试里

本版 CFlow 实现的 certificate tests 已经使用几乎和本书完全一致的 pipeline：

~~~text
filter even
    ↓
map square
    ↓
reduce add
~~~

测试会继续执行：

~~~text
Stream
    ↓
Surface Graph
    ↓
Normalize
    ↓
Optimize
    ↓
Compile Plan
    ↓
Build Certificate
    ↓
Check Certificate
~~~

这说明 canonical example 不是为了书临时发明的 toy example。它已经是实际 trusted execution path 的测试对象。

### 12.1 Surface/API evidence

需要验证：

~~~text
filter/map/reduce method
    ↓
Graph rows appear with expected operators/types
~~~

### 12.2 Reuse evidence

同一 Stream description 在合法 Range contract 下多次 evaluation，应拥有独立 execution state。特别要检查 reduce accumulator、take/skip counters 和 temporary value storage 不能泄漏回 Graph description。

### 12.3 Ownership evidence

测试要明确：Stream destroys its Graph，但不会 destroy borrowed container/Range owner。

### 12.4 Certificate / verification evidence

当 Stream 构造完成以后，所有 trusted transformation 都应该针对 Graph / Plan / Certificate，而不是 surface syntax。这再次证明：

Stream 不是 semantic center；Graph 才是。

## 13. Performance：不要 benchmark “链式语法”，要 benchmark execution path

Stream API 本身主要发生在构建/控制面。因此性能问题不能简单问“`stream.map()` 比普通 C 慢多少？”，更有意义的问题是：**同一条 pipeline 最终以什么形式执行？** 应比较手写 C 循环、Surface Graph interpreter、normalized/optimized Graph、编译后的 Plan 和 Direct/AOT 路径。如果最终能够 lower 成与手写循环等价的执行形式，那么 Stream 的表达能力与热路径成本就可以分离。这正是本书反复强调的原则。

高级 API 的成本不应该自动等于每个 value 的执行成本。

## 14. 小结

Stream 将过滤、映射和归约请求翻译为计算图。类型检查和操作语义继续由图规则决定，输入范围仍按原有生存期借用；可重复执行的描述不应混入某一次执行的游标、累加器或等待状态。正确性要求接口构造的图与直接构造的图产生相同的约定观察。性能比较应固定输入、操作和执行后端，分别测量构造与执行成本。下一章给出图改写所需的观察语义和证明条件。
