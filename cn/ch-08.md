# 第九章：从 Stream 到 Reactive——WAIT、Wake、Demand 与 Backpressure

> **本章只增加 execution state，不增加第二套 Graph。**
>
> 同一个 `Source → Filter → Map → Reduce` pipeline 保持不变。
>
> 在同步执行里，Source 每次被询问都必须立即返回值或结束。Reactive 只放松这一条假设：**source may temporarily have no value**。
>
> 因此真正新增的对象只有 poll result、subscription state、wake generation、demand ledger 和 scheduler capability。

**术语说明：** demand（需求额度）是下游尚允许接收多少个值；backpressure（背压）是让生产或交付受下游处理能力约束的机制。本章用显式 demand 限制交付数量，wake（唤醒）只通知条件可能已变化，不增加需求额度。

---

## 1. Source Poll Protocol：VALUE / WAIT / DONE / ERROR

**Continuation（续体）**是继续一次未完成计算所需的信息，例如执行位置、保留的值与节点状态。在本章的 C 实现中，它可以由显式状态结构保存，不要求语言提供协程，也不意味着保留整个线程调用栈。

先把协议写成 C，而不是先解释“异步”。

~~~c
typedef enum cflow_poll_kind {
    CFLOW_POLL_VALUE,
    CFLOW_POLL_WAIT,
    CFLOW_POLL_DONE,
    CFLOW_POLL_ERROR
} cflow_poll_kind;

typedef struct cflow_poll_result {
    cflow_poll_kind kind;
    int error;
} cflow_poll_result;

cflow_poll_result
source_poll(source *src, value *out);
~~~

同步 source 通常只返回 `VALUE`、`DONE` 或 `ERROR`；异步 source 多一个 `WAIT`。

`WAIT` 的唯一语义是：**现在没有值，但 continuation 仍然有效；外部条件变化后可以重新 poll。**

它不表示 block current thread、sleep、spin、consume demand 或 finish stream。

## 2. Subscription State Machine

**术语说明：** waitable 是可登记等待的条件或对象，waker 是条件可能变化时使用的通知入口；arm 表示登记这次通知。wake generation（唤醒代次）用于区分先后两次登记，避免旧回调错误地恢复新一轮等待。

Graph 是 immutable program structure。

真正活着的状态属于 Subscription：

~~~c
typedef enum subscription_state {
    SUB_READY,
    SUB_ARMING,
    SUB_SUSPENDED,
    SUB_TERMINAL
} subscription_state;

typedef struct subscription {
    subscription_state state;
    uint64_t demand;
    uint64_t wake_generation;
    bool wake_pending;
} subscription;
~~~

执行状态机：

~~~text
READY
  poll -> VALUE  : emit; demand--; stay READY
  poll -> WAIT   : enter ARMING
  poll -> DONE   : TERMINAL
  poll -> ERROR  : TERMINAL

ARMING
  install waker
  recheck source
  ready          : cancel arm -> READY
  still waiting  : SUSPENDED

SUSPENDED
  matching wake  : READY
  cancel         : TERMINAL

TERMINAL
  no further step
~~~

这比“Publisher 变成 resumable”更具体。

---

## 3. Poll Loop Pseudocode

~~~text
drive(subscription):

    while subscription.state == READY:

        if subscription.demand == 0:
            return

        r = source.poll()

        match r:
            VALUE:
                downstream.emit(value)
                subscription.demand -= 1

            WAIT:
                subscription.state = ARMING
                arm_wait(subscription)
                return

            DONE:
                subscription.state = TERMINAL
                downstream.complete()
                return

            ERROR:
                subscription.state = TERMINAL
                downstream.error(r.error)
                return
~~~

Demand 的作用也因此非常明确：

- Demand 限制 emitted VALUE 的数量；
- Demand 不统计 poll attempts；
- `WAIT` 不消耗 demand；
- Wake 也不消耗 demand。

对应 ledger：

~~~text
emitted <= requested

requested - emitted = remaining demand
~~~

## 4. Lost Wakeup：为什么 ARMING 必须有 Recheck

错误时序：

~~~text
T0  poll() -> WAIT
T1  source becomes ready
T2  source emits wake
T3  consumer installs waker
T4  consumer sleeps forever
~~~

所以不能：

~~~text
WAIT
 -> install waker
 -> sleep
~~~

而要：

~~~text
WAIT
 -> enter ARMING
 -> install waker
 -> recheck readiness
 -> only then SUSPENDED
~~~

伪码：

~~~text
arm_wait(sub):

    g = sub.wake_generation + 1
    sub.wake_generation = g

    source.install_waker(g, wake_callback)

    if source.is_ready():
        source.cancel_waker(g)
        sub.state = READY
        schedule(sub)
        return

    if sub.wake_pending_for(g):
        sub.state = READY
        schedule(sub)
        return

    sub.state = SUSPENDED
~~~

这里真正需要证明的是：**ready-after-first-WAIT cannot be lost between arm and suspend**，而不是“异步系统通常很复杂”。

## 5. Wake Rule 与 Generation

wake callback 不直接执行 Graph。

它只做状态转换与 schedule：

~~~text
wake(sub, generation):

    if sub.state == TERMINAL:
        return STALE

    if generation != sub.wake_generation:
        return STALE

    if sub.state == ARMING:
        sub.wake_pending = true
        return OK

    if sub.state == SUSPENDED:
        sub.state = READY
        scheduler.schedule(sub)
        return OK

    return ALREADY_READY
~~~

Generation 防止旧 I/O completion 唤醒新的等待周期。

语义身份不是 callback address。

---

## 6. Scheduler 只决定“什么时候继续”

Scheduler 不拥有 Graph，也不拥有 demand semantics。

最小接口可以近似：

~~~c
typedef struct scheduler_vtable {
    int (*schedule)(void *self, subscription *sub);
    int (*schedule_at)(void *self, uint64_t deadline, subscription *sub);
} scheduler_vtable;
~~~

职责表：

| 对象 | 拥有什么 |
|---|---|
| Graph | operator topology |
| Subscription | live demand / wait / terminal state |
| Source | readiness + value production |
| Waker | one resume signal |
| Scheduler | when a READY subscription runs |
| Executor | where/how scheduled work executes |

不要把这些合成一个“Reactive Runtime”巨型对象。

---

## 7. Failure Paths

至少四种失败必须显式：

- `request(0)`：按 contract 定义为 no-op 或 invalid；
- TERMINAL 状态下继续 request：返回 `CLOSED`；
- stale generation 的 wake：返回 `STALE`；
- arm resource capacity exhausted：返回 bounded error，而不是 hidden allocation。

一个重要 invariant 是 **TERMINAL is absorbing**。

即：

~~~text
state = TERMINAL
─────────────────
no VALUE / WAIT transition
~~~

后面的 formal model 只需要证明这些已经写清楚的规则。

## 8. Canonical Example：Graph 不变，Source 开始拥有时间

Part II 的同步 Stream 可以理解成下面的 **value dataflow**：

~~~text
input array / Range
      ↓ value
Source<int>
      ↓ value
Filter(is_even)
      ↓ value
Map(square)
      ↓ value
Reduce(sum)
~~~

同步 source 的一个隐含假设是：

> 每次被询问时，要么马上给值，要么马上结束。

Reactive 打破的只有这个假设。

Graph 本身仍然保持 Filter(is_even)、Map(square)、Reduce(sum) 这些 operator。

变化的是 source protocol。这里不是顺序流程，而是 **一次 resume() 的五种互斥返回结果**：

~~~text
resume()
  ├─ VALUE
  ├─ VALUE_AND_DONE
  ├─ WAIT
  ├─ DONE
  └─ ERROR
~~~

其中 WAIT 的语义必须非常精确：

> **现在没有值，但这个 continuation 仍然有效；当外部条件变化时，系统可以被唤醒并重新尝试。**

它不是 sleep current thread，不是 treat as DONE，更不是 spin until something appears。

这一个区别，让同一张 Graph 可以从 already-materialized input 延伸到 timer、channel、readiness、socket/pipe/file completion 或 custom asynchronous publisher，而不需要重新设计 operator semantics。

## 9. Semantic Contract：Reactive 新增的是 execution state，而不是 Graph state

这一章最重要的分层是：

| 对象 | 含义 |
|---|---|
| Graph | immutable/reusable program description |
| Subscription | one live execution |

### 9.1 WAIT 只是 source outcome，不是“已经注册成功”

source 返回 `WAIT` 时，只说明 continuation 已保存、waitable 可用；接下来仍然存在一个独立的 `arm(waitable, waker)` 步骤。因此 **WAIT ≠ SUSPENDED**。

更准确的状态变化是：

~~~text
READY
  ↓ resume returns WAIT
PENDING_ARM
  ↓ arm succeeds quietly
SUSPENDED
  ↓ matching wake
READY
~~~

把 WAIT 与 armed suspension 分开，是处理 lost wakeup 的关键。

### 9.2 Wake 不产生 demand

Wake 的意义只是：

> “外部条件可能变化了，可以重新调度一次 continuation。”

它不代表“允许多产生一个 downstream value”，所以 Wake 应保持 demand 不变。

| 概念 | 含义 |
|---|---|
| readiness | can retry |
| demand | downstream permits output |

两者来自不同事实源。

### 9.3 Demand 是 downstream-value demand，不是 Publisher pull count

这是 Reactive 中最容易被写错的地方之一。

例如：

~~~text
Source<int>
    ↓
Filter(is_even)
    ↓
Map(square)
~~~

下游请求 `demand = 1`，并不意味着 `source.resume() exactly once`。

因为第一个 input 可能被 Filter 丢掉。

为了产生一个 downstream value，source 可能需要被 resume 多次。

因此 contract 是：

> **Demand 只在真正向 downstream emit 一个 value 时消耗。**

source VALUE 本身不自动消耗 downstream demand。

这让 Filter、FlatMap、Relation 和其他 cardinality-changing operators 都可以共享一致的 demand 语义。

### 9.4 Terminal 必须有唯一事实源

Reactive run 的终止不能由 `done`、`cancelled`、`failed`、`maybe_source_done` 等多个 bool 拼出来。

更清楚的模型是：

~~~text
RUNNING
DONE
ERROR(message)
CANCELLED
~~~

并且 terminal state 一旦建立，就不能再开始新的 kernel small-step。

这里还必须区分 **source done** 与 **whole run done**。即使 source 已经没有新 input，Graph 下游仍可能需要 reduce finalization、buffer drain 或 pending terminal emission。

所以 run lifecycle 必须保留一个 draining 阶段：

~~~text
source completion
    ↓ enter draining
draining
    ↓ downstream finalized
whole-run DONE
~~~

这里箭头表示 lifecycle transition，不能把 source done 与 whole-run done 压成一个状态。

### 9.5 Cancel 是显式语义，不是 Error 的别名

Cancel 应该：

- 停止新的执行推进；
- unarm/cancel 当前 wait registration；
- 建立 CANCELLED terminal；
- 按 ownership contract 释放或结算 live state。

它不是：

~~~text
ERROR("cancelled")
~~~

因为 cancellation 是 control-plane decision，而 error 是 computation/source failure。

### 9.6 Subscription 是 live state 的唯一 owner

Graph 不应该保存 demand、wait registration、cancelled flag、reduce accumulator、slice counter、live temporary value 或 opened backend state；这些都属于一次 execution。

因此一个 Subscription 的 ownership contract 应接近：

~~~text
owns:
    moved Publisher
    demand
    wait state
    continuation/live slots
    per-node mutable state
    cancellation/terminal/error state

borrows:
    immutable Graph
    Scheduler
    Subscriber
    backend/interface tables
~~~

这条边界是后面 Executor、Machine、Actor 能继续组合的基础。

## 10. Lean：这一章已经有真实的 Reactive small-step calculus

这里不需要再发明一套“可能的 Lean 模型”。

本版 Salts 快照已经包含 `formal/cmeta_cflow_calculus/CMetaCFlowCalculus/CFlow/Execution.lean` 与 `formal/cmeta_cflow_calculus/CMetaCFlowCalculus/Proofs/Execution.lean`。

它把本章最关键的 execution facts 显式建模为：

~~~text
SourceState
Demand
WaitState
Terminal
SourceTerminal
DrainState
RuntimeState
Config
SourceResult
SourceStep
ArmStep
WakeStep
EmitStep
DrainStep
FinishStep
CancelStep
~~~

这正好展示 Lean 怎样反过来帮助 C 设计变清楚。

### 10.1 Demand.consume：零 demand 不能 emit

formal model 将 demand 定义为有限剩余数量，并让：

~~~text
consume(0)
    = none

consume(n + 1)
    = some(n)
~~~

因此 downstream emission 必须拿到一个成功 consume witness。

已经存在 theorem `step_value_decrements_demand`。

表达：

> 每次真正向 downstream emit 一个 value，恰好消耗一个 demand。

而 `zero_demand_no_value` 表达：

> demand 为零时，不可能发生 value-emitting kernel step。

这正好对应 C runtime 最重要的 backpressure safety property。

### 10.2 Source VALUE 不直接消耗 downstream demand

现有 theorem `source_value_preserves_demand` 明确证明：

~~~text
SourceStep VALUE
    ↓
demand unchanged
~~~

为什么要这样？

因为 source value 还可能经过 Filter、FlatMap 或其他 cardinality-changing computation。

真正消耗 demand 的位置是 downstream EmitStep。

这正是前面“Demand 不是 Publisher pull count”的形式化版本。

### 10.3 WAIT → arm → wake 保留 continuation 与 demand

现有 theorem `wait_arm_wake_preserves_source` 表达 quiet arm + matching wake 后：

~~~text
saved continuation preserved
wait returns READY
ownership preserved
demand preserved
source terminal preserved
drain state preserved
run terminal preserved
wake generation advances exactly once
~~~

这非常有价值，因为它证明：

> Wake 本身不是一次数据消费，也不是一次状态重建；它只是安全恢复同一个 continuation。

### 10.4 Lost Wakeup 不是一句“加个锁”就能解决

formal model 直接区分 `noSignal`、`signalBeforeArm`、`signalConcurrentWithArm`，并已有 theorem `signal_before_arm_is_ready` 与 `signal_concurrent_with_arm_is_ready`。

它们保证：

> 如果 readiness 在注册前或注册竞争中已经被观察到，run 不会错误地进入 suspended。

另外，`arm_issues_fresh_token` 保证每次 arm 都使用当前 generation 并只推进一次 generation。

因此 stale wake 与 current registration 可以在模型里被区分。

这比一句模糊的“avoid lost wakeup”强得多。

它把 race condition 变成了明确 state machine contract。

### 10.5 Terminal 是 absorbing

现有 theorem `terminal_no_step` 说明：

~~~text
terminal != RUNNING
    ↓
no kernel Step can start
~~~

而 `cancel_unarms_and_terminates` 说明 Cancel：

~~~text
wait -> READY
terminal -> CANCELLED
~~~

这给 C implementation 一个非常直接的 refinement target。

### 10.6 Safety 与 Liveness 必须分开

上面的 theorem 大部分是 safety：不会在 zero demand 下 emit、不会从 terminal 继续 step、不会因为 arm race 永久丢掉已经看到的 signal，而且 wake 不修改 demand。

但它们并不能自动证明外部设备最终一定 ready、Scheduler 最终一定运行某个 task、OS 一定返回 I/O completion，或线程永远不会饿死。

这些属于环境公平性或 platform liveness assumption。

所以书里必须保持：

> **Lean 可以证明“如果事件发生，状态机怎样安全变化”；不能凭空证明现实世界一定给你事件。**

## 11. Current C Implementation：formal state 已经有清晰的 C counterpart

对照本版 Salts 实现快照 `qigao/salts@ad389928b437c0612c1c60844fe53677f3ed27a6`：

### 11.1 Source outcome 是五态 protocol

当前 C API 直接定义 `CFLOW_STEP_VALUE`、`CFLOW_STEP_VALUE_AND_DONE`、`CFLOW_STEP_WAIT`、`CFLOW_STEP_DONE` 和 `CFLOW_STEP_ERROR`，与 formal SourceResult 对应。

WAIT 还携带一个 waitable：

~~~text
arm(waker)
cancel()
~~~

所以等待不是一个 bool，而是一个明确协议对象。

### 11.2 Publish context 直接传递 downstream demand snapshot

当前 publish context 中保存 scheduler 与 downstream_demand。

注释明确说明 downstream_demand 是：

> Subscription 在调用 resume 前的精确 outstanding downstream-value demand。

这让 source 可以利用 demand 做 bounded read/window admission，但不能重新定义 demand 的含义。

例如 I/O publisher 可以：

~~~text
target window
=
min(downstream demand, configured capacity)
~~~

这就是 backpressure 与 bounded resources 的连接点。

### 11.3 Subscription 是 opaque execution owner

Graph 在前两章刻意保持 concrete IR，方便 introspection 和验证。

Subscription 则相反：

~~~c
typedef struct cflow_subscription {
    void *impl;
} cflow_subscription;
~~~

这是一个非常好的对比。

为什么？

Subscription 拥有 live mutable execution state、locks/scheduling state、demand、wait registration、continuations、mutable node state 和 terminal state。这些细节需要演进，也不应该被 caller 直接改写。

| 对象 | API shape |
|---|---|
| Graph | concrete read-only IR rows |
| Subscription | opaque mutable execution owner |

这不是风格不一致，而是 ownership 不同导致的正确 API 形状。

### 11.4 Subscribe 使用 move-style Publisher ownership

当前 contract 非常明确：

~~~text
before success:
    caller owns Publisher

subscribe succeeds:
    Subscription takes Publisher
    caller Publisher is cleared

admission fails:
    ownership remains with caller
~~~

同时 Graph、Scheduler 和 Subscriber 都是 borrowed。

这把错误恢复和 destroy 顺序变得可推理。

### 11.5 Request 保留 outstanding demand，即使调度 admission 暂时失败

request API 的 **demand-accounting sequence** 是：

~~~text
demand accepted
    ↓ scheduling attempt
pump scheduling may fail immediately
    ↓ accounting unchanged
outstanding demand remains retained
    ↓ later trigger
later wake/request may retry
~~~

这里箭头表示 demand/accounting state 的推进，不是 value dataflow。

这避免把 scheduler queue full 错误解释成 downstream no longer wants the value。

Demand 是 semantic fact；scheduler admission 是 execution resource fact。

两者不能混在一起。

### 11.6 Wake 可以从任意 driver/event-loop callback 调用

当前 `cflow_subscription_wake()` 被定义为 advanced integration hook，可由外部 event loop / driver callback 调用。

Wake 的实现最终重新进入 Subscription pump admission，而不是让 driver 自己执行 Graph state mutation。

这是 **control-notification path**：

~~~text
external readiness
    ↓ notify
wake notification
    ↓ enqueue/resume ownership
Subscription / Scheduler
    ↓ drive admitted work
Graph execution
~~~

它不是 data value 本身的流向。

## 12. Scheduler：时间与执行位置是 capability，不是继承层次

当前 Scheduler 同样是小 Interface，而不是 class hierarchy。

它显式声明 DELAYED、MANUAL_CLOCK、CONCURRENT、CALLER_DRIVEN_ZERO_DELAY 等 capabilities，并提供多个实现策略。

### 12.1 Inline Scheduler

Inline Scheduler 的 timing guarantee 是：**accepted zero-delay task 在 admission 返回前完成执行**。它没有 queue、clock 或 timer storage，适合明确需要 zero-hop 的边界。

### 12.2 Manual Scheduler

Manual Scheduler 使用 bounded ready queue，由 caller 驱动 `run_one` / `run_ready` / `run_until_idle`，没有 timer clock。

它特别适合 external event loop、deterministic batch processing 和 tests。

### 12.3 Test Scheduler / Manual Clock

支持 `post_after`、`advance(ticks)`、`run_until_idle`，因此时间不再依赖 `sleep(...)` 或 wall-clock race。

从而可以写 deterministic temporal tests。

### 12.4 Worker Scheduler

把 dispatch 移到 worker threads，并显式提供 bounded ready/timer capacity 与统计。

因此：

> Scheduler 回答何时/在哪个 execution context 执行，不拥有 Graph semantics。

## 13. Evidence：Reactive 需要同时验证 demand、wait、race 与 bounded resources

本章不能只写一个 async demo。

至少需要几类 evidence。

### 13.1 Demand conformance

当前 reactive tests 已经检查 request result、outstanding demand retained/decremented，以及 scheduler admission failure 不会 silently discard demand。

calculus conformance tests也直接观察：

~~~text
demand = 1
...
emit
...
demand = 0
~~~

这对应 Lean 的 step_value_decrements_demand。

### 13.2 WAIT / Waitable evidence

Reactive、Temporal、I/O、Machine adapter tests 都有：

~~~text
resume
    ↓
CFLOW_STEP_WAIT
    ↓
waitable valid
    ↓
arm(waker)
~~~

这证明 WAIT 已经是多个 subsystem 共享的 protocol，而不是某个 socket backend 的特殊状态。

### 13.3 Wake race / quiescence evidence

Readiness tests 中已经存在非常具体的并发场景，例如 **cancel waits until old callback waker is quiescent**。这类测试属于 C implementation race evidence。

Lean 的 ArmTiming theorem 给 state-machine safety model；

真实 readiness test 则检查：

> 实际 callback/lock/lifetime implementation 是否遵守那个模型。

两者不能互相替代。

### 13.4 Bounded scheduler evidence

Scheduler tests 已经检查 bounded admission，例如：

~~~text
capacity = 1
second admission rejected_full
drain/advance
capacity reused
~~~

因此 Backpressure 不只是 demand counter。

它还必须覆盖 bounded scheduling、bounded buffers、bounded publisher windows 和 bounded operator state。

### 13.5 Temporal determinism

Timer/temporal tests 使用可控 Scheduler/Clock 路径检查 **WAIT → advance time → wake → resume → terminal → cancel**，比 wall-clock sleep-based test 更适合作为 semantic regression gate。

## 14. What We Learned

本章没有重新设计一套“Async Graph”，而是在同一张 Typed Graph 外增加 live execution state。

| 层 | 负责什么 |
|---|---|
| Graph | immutable computation description |
| Subscription | demand、wait registration、mutable operator state、terminal/cancel/error |
| Publisher | source-side value/readiness production |
| Scheduler | when / where execution resumes |
| Waitable / Waker | external readiness notification |

真正需要保持的 execution invariants 是：

- zero demand → no emitted value；
- one downstream emit → demand decreases exactly once；
- source VALUE 本身不消耗 downstream demand；
- WAIT + safe arm + matching wake → resume the same continuation；
- readiness 与 arm race 不能变成 lost suspension；
- terminal 是 absorbing；
- cancel 必须 unarm 并进入 CANCELLED。

这些规则一部分适合 Lean theorem，一部分必须由 readiness/race/sanitizer tests 验证。两种证据不能互相替代。

Reactive 因此只给 Graph 增加了**时间、流量控制和 live ownership**，没有重新定义 Filter、Map、Reduce 等 computation semantics。

下一章只再抽出一个 execution primitive：**Executor**。

> **能不能让一个底层对象只理解 Task admission、capacity、settlement 和 execution，而完全不知道 Graph、Stream、Reactive、Machine 或 Actor？**

这就是 Executor。
