# 第九章：响应式执行：等待、唤醒、需求额度与背压

同一条过滤与映射计算，可以处理数组，也可以处理尚未到达的网络数据。区别在于数组通常能立即给出下一个元素，外部输入则可能暂时没有值。响应式执行保存未完成计算，在条件改变后继续推进，并限制向下游交付的数量。本章沿用 CMeta 的类型与生存期契约，将活动状态放进订阅，逐步检查交付、等待、唤醒、取消和结束。

**续体（continuation）**是恢复一次未完成计算所需的信息，例如执行位置、保留的值和节点状态。C 实现可以把这些信息保存在结构体中，不必保存整个线程调用栈。**需求额度（demand）**是下游尚允许接收多少个值；**背压（backpressure）**通过限制交付及相关资源使用，使生产速度受到下游能力约束。

## 1. 一次恢复调用可以产生什么

固定接口用 `cflow_step` 表示一次 `resume` 的结果。下面的表说明每种结果是否在调用方提供的空存储中构造一个活动值，以及执行方接下来应做什么。**活动值**是已经完成初始化、其生存期尚未结束的对象；空存储尚不包含这样的对象。

| 结果 | 输出存储 | 后续动作 |
|---|---|---|
| `CFLOW_STEP_VALUE` | 一个活动值 | 把值交给图处理，之后仍可恢复源 |
| `CFLOW_STEP_VALUE_AND_DONE` | 一个活动值 | 先处理最后的值，再记录源结束 |
| `CFLOW_STEP_WAIT` | 保持为空 | 保存续体，并取得可登记等待的对象 |
| `CFLOW_STEP_DONE` | 保持为空 | 记录源结束，处理图中尚未完成的输出 |
| `CFLOW_STEP_ERROR` | 保持为空 | 进入失败路径并清理活动状态 |

`WAIT` 只说明当前取不到值。它不消耗额度，不表示整个执行结束，也不说明已经登记了通知。**等待对象（waitable）**提供登记与取消操作；**唤醒入口（waker）**是在条件可能变化时调用的通知函数。登记（arm）把当前通知入口交给等待对象，其结果与源返回 `WAIT` 是两个步骤。

恢复时仍要服从 CMeta 的对象契约。保存一个借用指针，并不会让原对象跨越等待而继续存活；已活动的输出也不能被下一次恢复直接覆盖。固定 `cflow_resumable_ops` 要求只有两个产生值的结果才构造输出，其余结果保持存储为空。

## 2. 额度记在交付处

对于 `Filter(is_even)` 后接 `Map(square)` 的图，下游请求一个值时，源可能先返回 1，再返回 2。1 被过滤掉，2 产生输出 4，因此一次下游交付对应两次取得源值。**输出数量会改变**的操作都要求在图的出口记账，不能在源返回 `VALUE` 时就扣除额度。

下面是串行使用的 C11 教学片段；参数 `d` 必须指向有效、可写的计数器。它展示饱和加法和单次扣减，不是运行时并发实现，也没有包含订阅终止检查。实际请求入口另行拒绝零请求。

~~~c
#include <stdbool.h>
#include <stddef.h>
#include <stdint.h>

typedef struct demand_counter {
    size_t remaining;
} demand_counter;

/* Serialized teaching model; not safe for concurrent callers. */
static size_t demand_add(demand_counter *d, size_t n)
{
    size_t room = SIZE_MAX - d->remaining;
    size_t added = n < room ? n : room;
    d->remaining += added;
    return added;
}

static bool demand_take(demand_counter *d)
{
    if (d->remaining == 0)
        return false;
    --d->remaining;
    return true;
}
~~~

**饱和加法（saturating addition）**在达到最大值时保留最大值，不绕回零。先算 `SIZE_MAX - remaining` 可得到剩余空间，再只加入可容纳的数量，所以加法本身不会溢出。运行时有并发请求，必须用同步操作完成“读取、检查、修改”；把这段普通 C 直接交给多个线程会产生数据竞争。

设 `A` 是累计实际增加的额度，`E` 是已经预留并开始交付的次数，`D` 是当前剩余额度。在没有重置的一个执行中，教学模型满足 `D = A - E`。这里的累计量按数学整数理解；发生饱和时，`A` 只增加被计数器容纳的部分，不能把所有请求参数直接相加。一次交付在调用下游前取得额度；下游随后拒绝这个值会导致失败，不把已经发生的回调解释为“从未交付”。

| 事件 | 源取得值的次数 | 下游交付次数 | 剩余额度 |
|---|---:|---:|---:|
| 请求 1 个值 | 0 | 0 | 1 |
| 源返回 1，Filter 丢弃 | 1 | 0 | 1 |
| 源返回 `WAIT`，随后被唤醒 | 1 | 0 | 1 |
| 源返回 2，交付平方值 4 | 2 | 1 | 0 |

对事件数作归纳即可得到记账不变量：请求只增加 `A` 和 `D`；成功取得额度只增加 `E`、减少 `D`；源取值、等待与唤醒均不改变这三个量。`demand_take` 拒绝从零继续扣减，因此 `E <= A`。这证明交付数量受限，但没有证明源查询次数、缓冲区或调度队列也自动有界。

## 3. 推进循环必须经过图的出口

下面是带步数预算的教学伪代码，不是 `subscription.c` 的逐字翻译。`step_budget` 限制一次调度连续执行多少步；它用来说明公平调度所需的额外条件，不表示固定实现已经提供这个参数。每个活动值都须记录所有者，过滤后释放、累计后保留、交付后结束借用。

~~~text
drive(run, step_budget):
    while run is RUNNING and run.wait is READY and step_budget > 0:
        step_budget -= 1
        if a downstream value is pending:
            if demand is zero: return
            reserve one credit
            invoke the subscriber with the borrowed value
            release the value; terminate on subscriber rejection
        else if source is done:
            advance draining or finish, if permitted by its contract
            return if draining needs credit that is unavailable
        else:
            if demand is zero: return
            result = resume source into empty storage
            VALUE / VALUE_AND_DONE:
                pass the value through the graph
                save any pending output or per-node state
                for VALUE_AND_DONE, mark source done
            WAIT:
                register waiting; return
            DONE:
                mark source done
            ERROR:
                terminate with error; return
    if runnable work remains: request a later turn
~~~

关键区别在于：源值先经过图处理，只有形成下游输出时才预留交付额度。Reduce 可以处理多个源值后才产生一个结果；Filter 可以在取得一个输出前丢弃多个源值。若无限源永远不满足谓词，即使下游只请求一个值，无预算的循环仍可能长时间占用线程。因此，额度限制、单次执行预算和存储容量是三个不同约束。

完成通知也不同于值交付。没有待交付值时，结束可以不消耗额度；仍有待输出的归约结果时，则要先取得对应额度。固定源接口另有终止查询能力，允许执行方在必要时观察源是否已经结束；不能用“额度为零就完全不看任何终止事件”替代完整协议。

## 4. 从丢失唤醒推导登记协议

丢失唤醒发生在以下竞争中：执行方查询后得到 `WAIT`，源随即就绪并发出通知，但执行方尚未登记；之后它进入等待，再也收不到这次已经过去的通知。登记后复查就绪状态能覆盖这个窗口，但如果“最后一次检查”和“写入等待状态”之间仍可插入一个回调，竞争并没有解决。

下面采用一个明确的教学模型。等待提供方的 `arm_and_observe` 必须把登记与就绪观察衔接起来：此前已经就绪的条件可被观察到，登记后的变化会通知当前 waker；瞬时事件若不能保留，则应由提供方保存事件或序号。该名字是伪代码操作，真实 `cflow_waitable.arm` 返回布尔值，提供方可以通过同步调用 waker 表示已经发生的信号。

订阅的等待状态与回调共用一把锁。执行所有者串行进行恢复与重新登记；回调只修改等待标志并请求调度。调用提供方、等待旧回调退出和调用调度器都放在锁外，因为这些操作可能同步回调或等待别的线程。`run` 及登记上下文的生存期必须覆盖这些操作。

~~~text
arm_wait(run):
    lock(run)
    if run is terminal: unlock(run); return
    g = allocate a fresh, non-reused registration token
    run.token = g
    run.pending = false
    run.wait = ARMING
    unlock(run)

    outcome = provider.arm_and_observe(g, wake)   # may call wake now
    lock(run)
    if run is terminal:
        action = release_registration
    else if outcome is FAILED:
        mark terminal error
        action = release_registration
    else if outcome is SIGNAL or run.pending:
        run.wait = READY
        action = release_registration_then_schedule
    else:
        run.wait = SUSPENDED
        action = none
    unlock(run)
    perform action outside the lock
~~~

下面的唤醒伪代码与上一段使用同一把锁。`ARMING` 是正在登记，`SUSPENDED` 是已经登记且尚未观察到信号，`READY` 是允许再次尝试；终止状态单独保存。

~~~text
wake(run, g):
    lock(run)
    if run is terminal or g != run.token:
        unlock(run); return STALE
    if run.wait == ARMING:
        run.pending = true
        unlock(run); return
    if run.wait == SUSPENDED:
        run.wait = READY
        need_schedule = true
    else:
        need_schedule = false
    unlock(run)
    if need_schedule: request a coalesced execution turn
~~~

**竞争推导。** 如果信号先于登记，提供方的就绪观察必须返回 `SIGNAL`；如果信号发生在登记中，回调在锁内设置 `pending`，最后一次检查便选择 `READY`；如果信号发生在最后一次检查之后，回调只能在写入 `SUSPENDED` 并解锁之后取得锁，随后将它改为 `READY`。所以不存在“回调认为尚未等待、执行方却随后睡下”的检查空隙。重复信号在 `READY` 状态合并，不增加额度。

这个推导依赖提供方的登记协议和共享锁，单独加一次 `is_ready()` 调用并不足够。它也只证明信号不会在这些转移中丢失；调度器暂时拒绝任务时，执行方必须保留可运行事实并向调用者报告结果，不能据此宣称任务最终必然运行。

## 5. 登记身份、取消与回调生存期

**登记令牌（token）**标识一次具体等待；**代次（generation）**区分同一个对象先后进行的登记。旧回调携带旧令牌时不能恢复新等待。模型中的令牌在旧回调仍可能存在期间不可重用；有限计数器即将绕回时，需要明确的拒绝或静止后重建规则，不能悄悄回绕。

令牌检查只解决身份，不解决内存生存期。回调必须先能安全访问 `run`，才能比较令牌；如果订阅已经释放，所谓“发现过期后忽略”本身就是释放后访问。**静止（quiescence）**在这里指旧回调已全部退出，且不会再以旧登记访问相关对象。取消必须使旧登记失效，并在释放其上下文前取得这项保证。

一种可审查的关闭顺序是：在同步保护下建立终止事实并禁止新推进；在锁外取消登记、等待正在执行的回调退出；最后清理续体、活动值和源对象。已经进入的推进也必须结束或在明确边界停止，不能与清理同时访问同一状态。前节唤醒后尚未撤销的登记，由执行所有者在再次使用等待对象前处理，不应在回调里等待该回调自身退出。

**终止态是吸收态（absorbing state）**表示执行一旦终止，就没有新的正常计算步骤从它出发。它不是“把某个等待字段永远冻结”；清理可以继续进行，但旧通知不能重新启动计算。固定 `close` 契约还区分外部调用与订阅自身回调中的调用：外部关闭同步完成，自身回调中请求关闭则把销毁延迟到当前推进返回。

## 6. 源结束之后可能还有结果

对 `1, 2, 3, 4` 执行偶数平方和，源可以在返回 4 时同时返回 `VALUE_AND_DONE`。此时先将 4 映射为 16，与已有累计值 4 合并得到 20，再输出最终累计值。若把“源结束”立即当成“整个执行结束”，20 就会丢失。

**收尾阶段（draining）**负责源不再产生新输入之后，仍须完成的累计值输出、缓冲区排空或其他节点收尾。图的结构没有改变，但订阅需要分别记录源终止、收尾进度和整个执行的终止结果。对于未设置种子的空归约，没有累计值，不能凭空输出零。

| 状态事实 | 本例中的含义 |
|---|---|
| 源已结束 | 不再向源请求第 5 个元素 |
| 收尾尚未完成 | 累计值 20 仍待交付 |
| 运行完成 | 待交付值已按额度处理，节点已完成收尾 |
| 运行取消 | 调用方终止执行，按取消规则清理未交付状态 |

取消是调用方的控制决定，错误是源或计算失败，两者应有不同终止结果。无论以何种方式结束，图描述都不应保存本次执行的累计值、需求额度或取消标志。

## 7. 固定 C 接口中的所有权

以下声明节选自 [reactive.h](https://github.com/qigao/salts/blob/a650262031e9b3e5f11a227a7911a75db9ae1fb8/cflow/include/cflow/reactive.h)，省略了其他入口。`opaque`（不透明）表示调用者只持有句柄，内部布局由实现管理；`void *impl` 不授权使用方把它转换为猜测的内部结构。

~~~c
typedef struct cflow_subscription {
    void *impl;
} cflow_subscription;

bool cflow_subscribe(cflow_subscription *subscription,
                     const cflow_graph *graph,
                     cflow_publisher *publisher,
                     cflow_scheduler *scheduler,
                     const cflow_subscriber *subscriber);

cflow_status_result cflow_subscription_request_result(
    cflow_subscription *subscription, size_t n);
void cflow_subscription_close(cflow_subscription *subscription);
~~~

订阅须先置零。成功的 `cflow_subscribe` 接管 Publisher 并清空调用方的 Publisher 句柄；准入失败则保留调用方的所有权。图、调度器和 Subscriber 被借用。CMeta 接口表提供具体调用能力和类型契约，订阅另外保存需求额度、等待与活动对象状态。描述符本身不会为这些借用延长生存期。

`cflow_subscription_request_result` 的固定实现拒绝 `n == 0`，以饱和方式增加额度，再尝试安排推进。若调度准入立即失败，已经记下的额度仍保留；随后有明确触发时可以重试安排执行。因此调用方不能仅凭一个非成功返回值就重复增加同一份请求，否则可能重复记账。状态 `CLOSED` 既可能来自已经完成的订阅，也可能来自记账后拒绝任务的调度器，应结合订阅状态与剩余额度判断。

下游 value 回调只在回调期间借用该值。若要保留它，必须使用类型允许的复制、移动或引用持有协议；直接保存回调参数地址并稍后使用没有生存期保证。类型检查、执行准入和对象生存期检查解决的是相互关联但不同的问题。

## 8. 把手工推导对应到 Lean 定理

**小步语义（small-step semantics）**把执行表示为一系列局部状态转移，每一步只处理取值、登记、唤醒或交付等一种事件。固定快照的 [执行模型](https://github.com/qigao/salts/blob/a650262031e9b3e5f11a227a7911a75db9ae1fb8/formal/cmeta_cflow_calculus/CMetaCFlowCalculus/CFlow/Execution.lean) 和 [证明文件](https://github.com/qigao/salts/blob/a650262031e9b3e5f11a227a7911a75db9ae1fb8/formal/cmeta_cflow_calculus/CMetaCFlowCalculus/Proofs/Execution.lean) 给出了这种模型。本章新增的教学伪代码不是这些文件的机器生成实现，也没有新增机器检查证明。

先看“零额度不能交付”。下面节选现有证明，需放在其原有模块和定义上下文中阅读。`before`、`after` 是转移前后的配置，`Step` 表示合法转移，`event.EmitsValue` 表示该事件交付一个值；`¬` 表示否定。

~~~lean
theorem zero_demand_no_value {sourceTy outputTy : CMeta.Ty}
    {before after : Config sourceTy outputTy}
    {event : Event sourceTy outputTy}
    (zero : before.runtime.demand = .finite 0)
    (step : Step before event after) :
    ¬event.EmitsValue := by
  intro emits
  obtain ⟨n, positive, _⟩ := step_value_decrements_demand step emits
  rw [zero] at positive
  simp at positive
~~~

证明先假设发生交付，再由 `step_value_decrements_demand` 得到转移前的额度必须为 `n + 1`。将已知的零额度代入，就得到零等于一个正自然数的矛盾。这里的 **见证（witness）**是能证明前提成立的证据，例如扣减成功所提供的正额度；它不是另外一次交付，也不是运行时随意设置的布尔标志。

| 现有定理 | 模型中得到的性质 | 对实现的要求或限制 |
|---|---|---|
| `source_value_preserves_demand` | 取到源值不改变额度 | 在图出口扣减，不在源入口扣减 |
| `wait_arm_wake_preserves_source` | 安静登记后匹配唤醒保留续体和额度等状态 | 实现不能用通知重建或丢弃活动值 |
| `signal_before_arm_is_ready`、`signal_concurrent_with_arm_is_ready` | 模型已观察到的信号使等待状态回到可运行 | 平台登记协议须实现这些观察条件 |
| `arm_issues_fresh_token` | 每次登记取得当前令牌并推进代次 | C 中仍需处理有限计数器与回调生存期 |
| `terminal_no_step`、`cancel_unarms_and_terminates` | 终止阻止新计算步骤，取消建立终止状态 | 实际锁、回调退出和销毁仍要验证 |

**安全性（safety）**说明不会发生禁止的事件，例如无额度交付；**活性（liveness）**说明所期望的进展最终发生。上述状态机证明不能保证设备最终就绪、调度器公平或线程不被永久饿死。把 C 实现对应到模型称为**精化（refinement）**：还要说明实际同步、错误与资源管理怎样实现模型的转移，不能仅因两个结构的字段相似就认为对应已经证明。

## 9. 调度策略与可重复的验证

调度器安排何时以及在哪个执行上下文推进订阅，不改变 Filter、Map 或 Reduce 的计算含义。**准入（admission）**是把任务接纳到执行系统之前的能力与容量检查；检查失败不应变成隐式扩容或静默更换执行方式。

| 策略 | 推进方式 | 适合验证的性质 |
|---|---|---|
| Inline | 接受的零延迟任务在准入返回前执行 | 调用过程中可能立即回调，初始化必须先完成 |
| Manual | 调用者驱动有界就绪队列，无计时器时钟 | 不依赖线程竞争地控制执行次序 |
| Test / Manual Clock | 显式推进逻辑时间 | 等待、计时唤醒和取消的确定性时序 |
| Worker | 工作线程执行，有界就绪及计时容量 | 并发回调、队列满和关闭期间的所有权 |

源码依据见 [scheduler.h](https://github.com/qigao/salts/blob/a650262031e9b3e5f11a227a7911a75db9ae1fb8/cflow/include/cflow/scheduler.h)、[subscription.c](https://github.com/qigao/salts/blob/a650262031e9b3e5f11a227a7911a75db9ae1fb8/cflow/src/subscription.c) 和 [readiness.c](https://github.com/qigao/salts/blob/a650262031e9b3e5f11a227a7911a75db9ae1fb8/cflow/src/readiness.c)。登记令牌的教学模型不是声称运行时把同名字段逐一放进订阅结构；真实实现会在订阅、等待适配器和底层登记之间分配同步与身份责任。

[响应式测试](https://github.com/qigao/salts/blob/a650262031e9b3e5f11a227a7911a75db9ae1fb8/cflow/tests/cflow_reactive_test.c) 检查额度保留、消耗和调度失败；[就绪测试](https://github.com/qigao/salts/blob/a650262031e9b3e5f11a227a7911a75db9ae1fb8/cflow/tests/cflow_readiness_test.c) 包含登记失败不转移所有权、取消等待旧回调静止，以及正在执行的回调退出后才关闭和释放用户对象等场景。它们是固定源码中的验证案例，不是本章刚刚重新运行的测量结果。

验证本章的教学模型时，应分别覆盖：零额度拒绝交付、过滤不扣额度、饱和请求不回绕；信号先于登记、发生在登记中、发生在挂起之后；重复与过期通知；源结束但仍有待交付结果；调度队列满后仍保留额度；取消后旧回调不能访问已释放存储。有限事件枚举可以检查状态模型的竞争分支，真实并发测试才能继续检查平台锁和对象生存期。

## 10. 小结

响应式执行把 CMeta 类型与生存期契约用于跨时间的计算。源取得值，图处理值，出口按额度交付值；等待与唤醒只改变何时可以重试。登记正确性依赖可观察的提供方协议和原子化的等待状态转换，取消还须等待旧回调退出。将这些事实分开保存和证明，才能同时解释空输出、收尾、背压与资源清理，而不把通知误当作数据或执行许可。
