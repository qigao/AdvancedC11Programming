# 第三章：函数语义与执行投影——FunctionDesc、Receiver、Bind 与 Invokable

> **本章只做一个区分：**
>
> 描述一个 C 函数是什么，与决定怎样执行、绑定或投影它，是两件不同的事。

---

## 1. 普通函数与函数指针仍然是 baseline

最简单的情况仍然是普通 C：

~~~c
long square(int x)
{
    return (long)x * x;
}

long (*fn)(int) = square;
long y = fn(7);
~~~

如果调用端只需要一个函数地址，停在这里。

Function Reflection 只有在多个 consumer 需要共享稳定语义时才值得加入，例如：

~~~text
parameter direction
ownership / nullability
result ownership
effects / properties
ABI carrier
receiver identity
~~~

---

## 2. FunctionDecl 先生成普通 C，不生成万能 invoke runtime

canonical declaration 可以写成：

~~~c
FunctionDecl(value, int, add,
    (int, left, CMETA_PARAM_IN),
    (int, right, CMETA_PARAM_IN));

int add(int left, int right)
{
    return left + right;
}
~~~

这条 declaration 生成的是：

~~~text
normal C prototype
        +
immutable TU-local FunctionDesc
        +
immutable FunctionAbi sidecar
        +
static-inline metadata getters
~~~

消费入口：

~~~c
const cmeta_function_desc *f = FunctionMeta(add);
const cmeta_function_abi_desc *abi = FunctionAbi(add);
~~~

最重要的规则是：

> **Function reflection is descriptive only.**

FunctionDecl 不会自动生成 universal erased ABI invocation path。

真正调用仍然可以直接是：

~~~c
int result = add(2, 3);
~~~

---

## 3. FunctionDesc 与 FunctionAbi 是两个层次

**术语说明：** sidecar（附属描述）是与主描述符关联、但职责独立的一份元数据。ABI carrier（ABI 承载类别）说明值以标量、对象指针、聚合值等哪一类本地形式跨越调用边界；它不同于参数的业务含义。

FunctionDesc 保存 semantic contract：

~~~text
name
return type
parameter names / types / flags
effects
properties
result ownership / nullability
~~~

FunctionAbi sidecar 保存 executable boundary 所需的 carrier facts：

~~~text
return carrier
parameter carriers
~~~

因此：

~~~text
FunctionDesc
    = what the function means

FunctionAbi
    = how the declared native boundary is carried
~~~

两者仍然只是 metadata。

它们不会因为存在就自动获得 execution authority。

---

## 4. Parameter row 是 canonical fact

Function parameter 有三种显式程度：

~~~text
(type, name, flags)

(type, name, flags, descriptor)

(type, name, flags, descriptor, abi_carrier)
~~~

完整 ABI row 例如：

~~~c
(int, value,
 CMETA_PARAM_IN,
 &cmeta_type_int,
 CMETA_ABI_SCALAR)
~~~

同一 row 可以生成：

~~~text
native prototype
      +
ParamDesc
      +
FunctionAbi carrier
      +
TinyMock projection
      +
Plugin declaration
      +
bind / exact adapter
~~~

这正是第二章 finite tuple kernel 的实际 consumer。

---

## 5. Result ownership 是描述事实，不是 cleanup runtime

可以显式声明返回语义：

~~~c
FunctionDeclAsAbiResult(
    value,
    char *,
    &cmeta_type_char_ptr,
    CMETA_ABI_OBJECT_POINTER,
    CMETA_RESULT_BORROWED,
    find_name,
    (int, id, CMETA_PARAM_IN,
     &cmeta_type_int, CMETA_ABI_SCALAR));
~~~

VALUE、BORROWED、SHARED、OWNED 描述 result contract。

它们告诉 compiler / generator：

~~~text
VALUE
    -> native value result

BORROWED
    -> no ownership transfer

SHARED
    -> release obligation when admitted

OWNED
    -> ownership transfer / destroy obligation
~~~

descriptor 本身不执行 cleanup，也不保存 lexical LIVE/MOVED state。

cleanup placement 属于 compiler/generator 或真正的 runtime domain。

---

## 6. 需要 exact invocation 时必须显式选择

**Thunk（调用适配函数）**在本节指为某个已知函数生成的一小段包装代码：它接收统一形式的参数存储地址，按声明的 C 类型取值，调用原函数，再写回结果。这里的 exact 表示调用仍遵守该函数的具体本地签名。

**Type erasure（类型擦除）**是把接口中的具体类型隐藏在统一表示之后；此处统一入口使用 `void *`，生成的 thunk 仍知道真实类型。它不是把任意对象强转后都能安全调用的通用解释器。thunk 在其他语境也可指延迟计算的包装，本节使用的是调用适配含义。

如果 consumer 真正需要 erased exact thunk，可以明确声明：

~~~c
#include <cmeta/invoke_decl.h>

FunctionInvokeDecl(value, int, increment,
    (int, input, CMETA_PARAM_IN));

int increment(int input)
{
    return input + 1;
}
~~~

然后使用：

~~~c
int input = 4;
int output = 0;
void *params[] = { &input };

bool ok =
    FunctionInvoke(increment)(
        &output,
        params,
        1);
~~~

在上例中，适配函数检查参数个数和必需存储地址非空，随后从 `params[0]` 指向的 `int` 对象取值，调用 `increment(4)`，把 `5` 写入 `output`。调用者仍须提供类型、对齐与生存期均正确的存储；这些责任不能由 `void *` 上的空指针检查代替。实现见固定快照的 [invoke_decl.h](https://github.com/qigao/salts/blob/a650262031e9b3e5f11a227a7911a75db9ae1fb8/cmeta/include/cmeta/invoke_decl.h)。

因果关系是：

~~~text
FunctionDecl
    -> description only

FunctionInvokeDecl
    -> FunctionDecl
       + explicitly requested exact thunk
~~~

而不是：

~~~text
Reflection
    -> automatically dynamic invocation
~~~

description 与 execution capability 保持分离。

---

## 7. Receiver 是参数零的 semantic role，不是隐藏 object runtime

receiver function 仍然是普通 C：

~~~c
int list_add(IntList *self, int value);
~~~

Reflection 只把参数零标记为 receiver，例如：

~~~text
IN / INOUT
+
BORROWED
+
CMETA_PARAM_RECEIVER
~~~

规则是：

~~~text
receiver metadata
    -> descriptive role

C ABI
    -> unchanged ordinary first parameter
~~~

CMETA_PARAM_RECEIVER 不会：

- 改变 native calling convention；
- 创建 vtable；
- 创建 hidden self object；
- 自动引入 runtime dispatch。

它只是允许 compiler/generator 理解：

~~~text
obj.add(x)
    may lower to
List_add(&obj, x)
~~~

这种 dot-call lowering 是可选 frontend，不是使用 CMeta 的前置条件。

---

## 8. Receiver projection 的语义归 Function 所有

绑定 receiver 后：

~~~text
original:
(self, value) -> result

projected:
(value) -> result
~~~

不能简单理解成“删掉第一个参数”。

必须保持：

~~~text
same return type
same result ownership / nullability
same effects
same properties
same remaining parameter names / types / flags
~~~

所以 canonical validator 是 Function-owned：

~~~c
cmeta_function_receiver_projection_valid(
    source,
    projected);
~~~

一般 parameter projection 则由：

~~~c
cmeta_function_projection_valid(
    source_abi,
    projected_abi,
    bound,
    count);
~~~

负责。

receiver subsystem 不再拥有一份平行函数语义。

---

## 9. Receiver operation set 只做薄索引

当前 operation row 很小：

~~~c
typedef struct cmeta_receiver_operation {
    const char *name;
    const cmeta_function_abi_desc *abi;
} cmeta_receiver_operation;
~~~

关系是：

~~~text
FunctionDesc
    ^
    |
FunctionAbi
    ^
    |
receiver operation
  { name, abi }
    ^
    |
operation set
  receiver type
  operations
  optional generic owner
~~~

operation set 负责：

~~~text
name -> canonical FunctionAbi
~~~

它不再保存第二份 FunctionDesc。

> **receiver lookup 可以拥有索引，但 Function 仍然拥有 callable semantics。**

---

## 10. Bind 是 parameter projection，不需要单独的 Lambda object model

普通函数：

~~~c
int add(int a, int b);
~~~

先声明 canonical semantics：

~~~c
FunctionDeclAsAbiResult(
    value,
    int,
    &cmeta_type_int,
    CMETA_ABI_SCALAR,
    CMETA_RESULT_VALUE,
    add,
    (int, a, CMETA_PARAM_IN,
     &cmeta_type_int, CMETA_ABI_SCALAR),
    (int, b, CMETA_PARAM_IN,
     &cmeta_type_int, CMETA_ABI_SCALAR));
~~~

然后显式绑定 a = 10：

~~~c
FunctionBindDeclAsAbiResult(
    value,
    int,
    &cmeta_type_int,
    CMETA_ABI_SCALAR,
    CMETA_RESULT_VALUE,
    plus10,
    add,
    CMETA_SIG_U_I_I,
    (value,
        (int, a, CMETA_PARAM_IN,
         &cmeta_type_int, CMETA_ABI_SCALAR)),
    (arg,
        (int, b, CMETA_PARAM_IN,
         &cmeta_type_int, CMETA_ABI_SCALAR)));
~~~

row mode 是显式的：

~~~text
arg
    -> remain a call argument

value
    -> capture a trivial scalar snapshot

borrow
    -> capture an explicit borrowed object pointer
~~~

receiver bind 使用同一个模型，只是 borrow row 同时带 RECEIVER flag。

因此不需要另建 ReceiverClosure / MethodLambda / BoundMethodObject 一套 object hierarchy。

---

## 11. Capture 是 bounded byte snapshot，不是隐藏 ownership system

cmeta_callable 有固定 inline capture：

~~~text
CMETA_CAPTURE_INLINE
~~~

绑定规则包括：

~~~text
value
    -> registered trivial scalar only

borrow
    -> explicit BORROWED object pointer only

managed / consuming capture
    -> rejected

capture bytes > inline capacity
    -> compile failure
~~~

没有：

~~~text
hidden malloc
automatic retain
automatic release
silent SBO fallback
~~~

复制 callable 只复制 inline bytes。

如果 bytes 中保存 borrowed pointer：

~~~text
copy callable
    !=
retain pointee / provider / Plugin
~~~

调用方必须保证 authoritative owner 与外层 Plugin lease 活得足够久。

---

## 12. cmeta_invokable 是语义与执行的 admitted join

Function metadata 与 cmeta_callable 真正结合时：

~~~c
cmeta_status status =
    cmeta_invokable_bind(
        FunctionMeta(plus10),
        callable,
        &invokable);
~~~

成功 bind 表示：

~~~text
FunctionDesc
      +
cmeta_callable
      |
      v
validate semantic / executable agreement once
      |
      v
cmeta_invokable
~~~

它仍然是 borrowed binding：

- 不 retain descriptor；
- 不 retain provider；
- 不 retain Plugin module；
- 不延长 captured borrow 的 lifetime。

authoritative owner 必须覆盖整个 use lifetime。

---

## 13. Validate once，然后走 admitted path

普通 checked invoke：

~~~c
cmeta_invokable_invoke(
    &invokable,
    &output,
    args);
~~~

对成功 bind 后保持不变的 admitted binding：

~~~c
cmeta_invokable_invoke_admitted(
    &invokable,
    &output,
    args);
~~~

admitted path 仍检查 call storage，但不重新遍历 descriptor graph。

~~~text
foreign / raw metadata
        |
        v
full validation / bind
        |
        v
admitted capability
        |
        v
repeated execution
without re-proving descriptor graph
~~~

这就是：

> **validate once; inspect/use many.**

---

## 14. Object provider 仍然必须提供 exact receiver-bound callable

operation lookup 只描述：

~~~text
name
+
FunctionAbi
~~~

执行 object receiver operation 时，provider 必须给出：

~~~text
receiver-bound exact callable
        +
receiver-elided FunctionData
~~~

再通过：

~~~c
cmeta_receiver_operation_invokable_bind(...)
~~~

或者：

~~~c
cmeta_object_operation_invokable_bind(...)
~~~

验证它确实是 canonical Function 的合法 receiver projection。

CMeta 不会：

~~~text
take arbitrary receiver pointer
    -> cast it
    -> guess original ABI
    -> invoke by method name
~~~

ABI boundary 保持 explicit、fail-fast。

---

## 15. Function 与 Interface 仍然不是同一个 abstraction

独立 operation 适合：

~~~text
FunctionDesc
+
FunctionAbi
+
optional exact adapter
~~~

长期 provider 适合：

~~~text
InterfaceDesc
+
{ self, vtable }
~~~

它们可以共享 Plugin loader / lease / admission infrastructure，但不应伪装成同一种 semantic representation。

---

## 16. Effects / properties 是 claim，不是 rewrite theorem

FunctionDesc 可以记录：

~~~text
effects:
    IO
    STATEFUL
    MAY_FAIL

properties:
    DETERMINISTIC
    IDEMPOTENT
    ASSOCIATIVE
~~~

这些 metadata 可以参与 admission 和 optimization candidate selection。

但是：

~~~text
property bit
    !=
semantic proof
~~~

真正授权 CFlow rewrite 的 law 留到 Execution IR 章节。

---

## 17. Engineering Evidence

### Description-only contract

普通 FunctionDecl 应证明：

~~~text
prototype exists
metadata exists
FunctionAbi exists
no implicit erased thunk
~~~

### Exact invocation

只有显式 FunctionInvokeDecl 才生成 exact invocation surface。

### Projection compile-fail

必须拒绝：

~~~text
wrong native signature
wrong result carrier
wrong parameter flags
wrong projected parameter
receiver mismatch
capture too large
managed value capture
unregistered projected signature
~~~

### Admission

成功 bind 后，checked invoke 与 admitted invoke 必须得到相同 semantic result。

### Lifetime

borrowed receiver / descriptor / provider / module 必须由外层 owner 保证寿命；复制 callable 不得隐式 retain。

### Performance

至少分别测量：

~~~text
direct C call
exact generated thunk
checked invokable
admitted invokable
capturing bind
~~~

不能只写 zero-cost。

---

## 18. What We Learned

本章得到：

~~~text
ordinary C function
       |
       +--> FunctionDesc
       |       semantic truth
       |
       +--> FunctionAbi
       |       carrier facts
       |
       +--> optional exact thunk
       |
       +--> receiver projection
       |
       '--> parameter bind
                |
                v
          cmeta_callable
                |
          validate / admit
                |
                v
          cmeta_invokable
~~~

核心边界有五条：

1. Function Reflection 是 descriptive，不自动拥有 invocation。
2. Receiver 是 canonical Function parameter semantic，不是 object runtime。
3. Operation set 是薄索引，不复制 FunctionDesc。
4. Bind 是显式 parameter projection；capture bounded 且不隐藏 ownership。
5. 成功 admission 后复用 capability，不在每次调用时重新解释 Reflection。
