# 第三章：函数反射：描述符、调用适配与参数绑定

一个 C 函数的类型决定怎样调用它，但参数方向、借用关系和返回值清理义务通常还保存在文档中。CMeta 将这些事实写入函数描述符，供绑定器、生成器和动态模块检查。本章以普通调用为起点，展开调用适配函数的实现，推导参数绑定与类型擦除的前置条件，再说明描述符和函数代码的生存期如何影响调用。

## 1. 普通函数与函数指针

下面的片段定义 `square`，再通过同一签名的函数指针调用它。实参 `7` 的平方可由 `long` 表示，因此结果为 `49`；若推广到任意 `int` 输入，还需检查乘法结果是否超出 `long` 的范围。

~~~c
long square(int x)
{
    return (long)x * x;
}

long (*fn)(int) = square;
long y = fn(7);
~~~

如果使用方只需要保存和调用这个地址，函数指针已经足够。多个模块需要共同检查参数方向、可空性、返回值所有权或副作用时，才需要把这些事实另行记录。CMeta 的函数描述符承担这项记录工作，实际调用方式仍由使用方选择。

## 2. 从声明生成普通 C 与描述符

`FunctionDecl` 从同一组参数声明生成普通函数原型、翻译单元内的只读 FunctionDesc、附属 FunctionAbi，以及取得这些元数据的内联入口。下面的声明仍由一个普通 C 函数实现；对 `add` 的一般调用要求加法结果能由 `int` 表示。

~~~c
FunctionDecl(value, int, add,
    (int, left, CMETA_PARAM_IN),
    (int, right, CMETA_PARAM_IN));

int add(int left, int right)
{
    return left + right;
}
~~~

使用方通过以下入口取得两份描述：

~~~c
const cmeta_function_desc *f = FunctionMeta(add);
const cmeta_function_abi_desc *abi = FunctionAbi(add);
~~~

描述符只提供可检查的事实。声明本身不会生成统一的动态调用器，直接调用仍然写成：

~~~c
int result = add(2, 3);
~~~

## 3. FunctionDesc 与 FunctionAbi 的职责

FunctionDesc 保存函数的语义契约：函数名、返回类型、参数名与类型、参数标志、副作用、性质以及返回值的所有权和可空性。FunctionAbi 则补充本地调用边界采用的承载类别。

附属描述（sidecar）是与主描述符关联、但职责独立的一份元数据。ABI 承载类别（carrier）区分标量、对象指针、聚合值等本地表示。它回答值怎样跨越调用边界，不能代替参数在业务上的含义。

| 对象 | 保存的信息 | 使用方需要检查什么 |
|---|---|---|
| FunctionDesc | 参数、结果及行为契约 | 方向、类型、所有权和语义条件 |
| FunctionAbi | 返回值与参数的本地承载类别 | 所选执行方式是否符合声明的 ABI |

两者可以支持生成和验证调用代码，但仅有描述符还不能执行函数。执行需要一个具体目标和与之匹配的调用入口。

## 4. 参数声明作为共享事实

每个参数可写成三项、四项或五项声明，依次补充显式类型描述符与 ABI 承载类别。省略项只能按声明规则补全，使用方不应自行猜测其位置或含义。

| 声明形式 | 显式给出的事实 |
|---|---|
| `(type, name, flags)` | C 类型、参数名与语义标志 |
| `(type, name, flags, descriptor)` | 另加类型描述符 |
| `(type, name, flags, descriptor, abi_carrier)` | 再加本地承载类别 |

完整参数声明的例子如下：

~~~c
(int, value,
 CMETA_PARAM_IN,
 &cmeta_type_int,
 CMETA_ABI_SCALAR)
~~~

同一行可投影为函数原型、ParamDesc、FunctionAbi 条目、TinyMock 声明、Plugin 导出或绑定适配代码。第二章的元组投影负责一致地取出各项，具体生成器再检查自身需要的条件。

## 5. 返回值所有权与清理责任

下面的声明显式说明 `find_name` 返回一个借用的字符指针。它把返回契约写入元数据，供生成器或运行时使用方判断清理责任。

~~~c
FunctionDeclAsAbiResult(
    value,
    char *,
    &cmeta_type_char_ptr,
    CMETA_ABI_OBJECT_POINTER,
    CMETA_RESULT_BORROWED,
    find_name,
    (int, id, CMETA_PARAM_IN,
     &cmeta_type_int, CMETA_ABI_SCALAR));
~~~

| 标志 | 返回契约 |
|---|---|
| VALUE | 返回本地值 |
| BORROWED | 不转移所指资源的所有权 |
| SHARED | 按准入后的共享协议承担释放义务 |
| OWNED | 转移所有权，并承担对应销毁义务 |

描述符本身不执行清理，也不记录某个局部对象是否已经移动或销毁。清理放在哪里、正常返回与失败返回分别走哪条路径，仍由生成器或拥有该资源的运行时决定。

## 6. 精确调用适配函数及其正确性

**Thunk（调用适配函数）**在本节指为某个已知函数生成的一小段包装代码：它接收统一形式的参数存储地址，按声明的 C 类型取值，调用原函数，再写回结果。这里的 exact 表示调用仍遵守该函数的具体本地签名。

**Type erasure（类型擦除）**是把接口中的具体类型隐藏在统一表示之后；此处统一入口使用 `void *`，生成的 thunk 仍知道真实类型。它不是把任意对象强转后都能安全调用的通用解释器。thunk 在其他语境也可指延迟计算的包装，本节使用的是调用适配含义。

如果使用方真正需要 erased exact thunk，可以明确声明：

~~~c
#include <cmeta/invoke_decl.h>

FunctionInvokeDecl(value, int, increment,
    (int, input, CMETA_PARAM_IN));

int increment(int input)
{
    return input + 1;
}
~~~

然后使用：

~~~c
int input = 4;
int output = 0;
void *params[] = { &input };

bool ok =
    FunctionInvoke(increment)(
        &output,
        params,
        1);
~~~

在上例中，适配函数检查参数个数和必需存储地址非空，随后从 `params[0]` 指向的 `int` 对象取值，调用 `increment(4)`，把 `5` 写入 `output`。调用者仍须提供类型、对齐与生存期均正确的存储；这些责任不能由 `void *` 上的空指针检查代替。实现见固定快照的 [invoke_decl.h](https://github.com/qigao/salts/blob/a650262031e9b3e5f11a227a7911a75db9ae1fb8/cmeta/include/cmeta/invoke_decl.h)。`FunctionDecl` 只生成描述；`FunctionInvokeDecl` 在描述之外显式生成适配函数。下面展开这段新增代码。

**把 thunk 展开为 C。** 下面是前例调用适配逻辑的教学展开，使用前面定义的 `increment`，并需要 `<stdbool.h>` 与 `<stddef.h>`。实际宏生成的名字和静态检查不同；这段代码保留运行时检查与具体函数调用，便于逐条推导。

~~~c
static bool increment_adapter(
    void *result, void *const *args, size_t count)
{
    if (count != 1 || args == NULL)
        return false;
    if (args[0] == NULL || result == NULL)
        return false;

    *(int *)result = increment(*(int *)args[0]);
    return true;
}
~~~

伪代码把调用方的存储责任与适配函数执行的步骤分开。它没有在运行时检查对象真实类型、对齐或生存期；这些是能够安全读取和写入对象的前提。

~~~text
adapt_increment(result, args, count):
    reject wrong count or missing argument array
    reject missing argument or result storage
    read x from the int object at args[0]
    compute y = increment(x)
    write y to the int object at result
    return true
~~~

**正确性推导。** 假设 `args` 指向至少一个有效指针元素，`args[0]` 指向值为 `x` 的活动 `int` 对象，`result` 指向可写的活动 `int` 对象，存储满足对齐要求、访问没有数据竞争，并且 `x < INT_MAX`。当 `count == 1` 且必需地址非空时，前两个分支均不返回；赋值右侧读取 `x`，调用 `increment` 一次得到可表示的 `x + 1`，再写入结果对象，最终返回 `true`。允许输入与结果是同一个 `int` 对象：读取和函数调用完成后才发生赋值。

若参数个数或必需地址检查失败，控制流在调用前返回 `false`，目标函数未执行，结果未被写入。非空但悬空、未对齐或类型错误的地址不属于这个失败保证；执行解引用前就必须由调用方排除。这个手工推导说明 exact thunk 保留了具体签名，而没有把 `void *` 变成运行时类型证明。

### 6.1 用一个可执行 Gate 检查成功与拒绝路径

前面的片段可以合并成一个完整的 installed-consumer C11 程序。它要求固定快照中的 `<cmeta/invoke_decl.h>` 与 `Salts::CMeta`，并用调用计数器区分“返回 false”与“目标函数真的没有执行”：

~~~c
#include <cmeta/invoke_decl.h>

static int calls;

int increment(int input);

FunctionInvokeDecl(
    value,
    int,
    increment,
    (int, input, CMETA_PARAM_IN));

int increment(int input)
{
    ++calls;
    return input + 1;
}

int main(void)
{
    int input = 4;
    int output = -1;
    void *params[] = { &input };

    if (!FunctionInvoke(increment)(&output, params, 1))
        return 1;
    if (output != 5 || calls != 1)
        return 2;

    int alias = 4;
    void *alias_params[] = { &alias };

    if (!FunctionInvoke(increment)(
            &alias, alias_params, 1))
        return 3;
    if (alias != 5 || calls != 2)
        return 4;

    output = 77;

    if (FunctionInvoke(increment)(
            &output, params, 0))
        return 5;
    if (output != 77 || calls != 2)
        return 6;

    if (FunctionInvoke(increment)(
            &output, NULL, 1))
        return 7;
    if (output != 77 || calls != 2)
        return 8;

    void *null_arg[] = { NULL };

    if (FunctionInvoke(increment)(
            &output, null_arg, 1))
        return 9;
    if (output != 77 || calls != 2)
        return 10;

    if (FunctionInvoke(increment)(
            NULL, params, 1))
        return 11;
    if (calls != 2)
        return 12;

    return 0;
}
~~~

这个 gate 同时验证六种行为：

| 情形 | 返回 | native call count | 结果存储 |
|---|---:|---:|---|
| 正常输入 `4` | `true` | +1 | 写入 `5` |
| input/result 是同一 `int` | `true` | +1 | 原地变为 `5` |
| wrong count | `false` | 不变 | 不变 |
| `params == NULL` | `false` | 不变 | 不变 |
| `params[0] == NULL` | `false` | 不变 | 不变 |
| non-void `result == NULL` | `false` | 不变 | 无写入 |

这里的失败保证仍然只覆盖 thunk 能检查的 **count/null contract**。故意传入非空但类型错误、未对齐、悬空或发生数据竞争的地址，不是“应该返回 false”的负例，而是违反调用前置条件；测试不能通过制造未定义行为来证明运行时类型检查存在。

installed consumer 可以只使用公开包边界：

~~~cmake
find_package(Salts CONFIG REQUIRED)

add_executable(
    exact_invoke_gate
    exact_invoke_gate.c)

target_link_libraries(
    exact_invoke_gate
    PRIVATE
        Salts::CMeta)
~~~

因此这个 gate 同时检查生成声明、exact thunk 的拒绝顺序、本地调用次数以及公开安装目标，而不依赖 Salts source-tree include path。对应的 canonical CI source 是 `qualification/ch03_exact_invoke.c`。

## 7. 接收者：从普通第一个参数到可验证投影

接收者（receiver）是操作所针对的对象。在这里，它仍然通过第零个 C 参数传入，例如 `list_add` 的 `self`：

~~~c
int list_add(IntList *self, int value);
~~~

反射以 `CMETA_PARAM_RECEIVER` 标记这个角色，并与 `IN`/`INOUT`、`BORROWED` 等标志共同描述使用方式。该标志不改变调用约定，不分配隐藏对象，也不创建虚函数表。

可选语法前端可以据此把 `obj.add(x)` 转换为 `List_add(&obj, x)`。转换的依据是已经声明的接收者类型和函数，而普通 C 使用方可以直接调用后者。

### 7.1 接收者绑定后的参数投影

绑定 `self` 后，调用形式从 `(self, value) -> result` 变为 `(value) -> result`。这不仅是省去一个参数：结果类型、结果所有权和可空性、副作用、性质，以及剩余参数的名字、类型和标志都必须按原契约保留。

函数模块通过接收者投影检查入口验证这些条件：

~~~c
cmeta_function_receiver_projection_valid(
    source,
    projected);
~~~

一般参数投影使用下列入口，检查源 ABI、投影 ABI 与绑定位置的对应关系：

~~~c
cmeta_function_projection_valid(
    source_abi,
    projected_abi,
    bound,
    count);
~~~

这些规则由函数描述统一定义。接收者查找只负责找到原函数的描述，避免维护另一份可能与它不一致的函数语义。

### 7.2 操作集合只负责索引，不复制函数语义

一个接收者操作条目只保存操作名与 FunctionAbi 指针：

~~~c
typedef struct cmeta_receiver_operation {
    const char *name;
    const cmeta_function_abi_desc *abi;
} cmeta_receiver_operation;
~~~

操作集合在接收者类型及可选泛型所有者的上下文中执行名字查找，再通过 FunctionAbi 找到已有的函数描述。它不复制 FunctionDesc，也不因查找到名字就获得任意调用权；执行能力还需与原函数及绑定结果一致。

## 8. 绑定与捕获：把部分参数变成可复用调用能力

参数绑定（binding）把原函数的一部分参数保存在可调用对象中，其余参数留到以后调用时提供。以 `add` 为例，若把 `a` 绑定为 `10`，新调用只需提供 `b`，效果为 `add(10, b)`。本节代码展示各层声明的形状，应按各自示例理解，不与第 2 节重复声明一起作为一个独立源文件编译。

~~~c
int add(int a, int b);
~~~

先显式给出参数和结果的类型描述、ABI 承载类别与所有权：

~~~c
FunctionDeclAsAbiResult(
    value,
    int,
    &cmeta_type_int,
    CMETA_ABI_SCALAR,
    CMETA_RESULT_VALUE,
    add,
    (int, a, CMETA_PARAM_IN,
     &cmeta_type_int, CMETA_ABI_SCALAR),
    (int, b, CMETA_PARAM_IN,
     &cmeta_type_int, CMETA_ABI_SCALAR));
~~~

再声明名为 `plus10` 的投影形状：`a` 作为捕获值，`b` 保留为调用参数。这项声明选择哪些参数被绑定；具体捕获值由随后构造的可调用对象提供。

~~~c
FunctionBindDeclAsAbiResult(
    value,
    int,
    &cmeta_type_int,
    CMETA_ABI_SCALAR,
    CMETA_RESULT_VALUE,
    plus10,
    add,
    CMETA_SIG_U_I_I,
    (value,
        (int, a, CMETA_PARAM_IN,
         &cmeta_type_int, CMETA_ABI_SCALAR)),
    (arg,
        (int, b, CMETA_PARAM_IN,
         &cmeta_type_int, CMETA_ABI_SCALAR)));
~~~

| 模式 | 含义 |
|---|---|
| `arg` | 保留为后续调用的实参 |
| `value` | 保存已注册的普通标量值快照 |
| `borrow` | 保存显式借用的对象指针 |

接收者绑定使用同一模型，并在借用参数上保留 RECEIVER 标志。参数类型、绑定位置和剩余签名的合法性仍由函数投影规则检查。

### 8.1 捕获的容量与生存期

捕获（capture）是把后续调用需要的值或地址保存在可调用对象中。`cmeta_callable` 用 `CMETA_CAPTURE_INLINE` 规定内部存储容量，复制对象只复制这些字节。若其中保存指针，复制字节不会自动延长指向对象、提供方或 Plugin 的生存期。

SBO 是 small-buffer optimization（小缓冲区优化），通常将小对象放在对象内部，较大对象另行分配。这里采用的是固定容量规则：超限被拒绝，不改走堆分配。

| 输入 | 绑定要求 |
|---|---|
| `value` | 仅接受已注册的普通标量 |
| `borrow` | 显式标记为 BORROWED 的对象指针 |
| 需要托管或消费所有权的捕获 | 拒绝 |
| 捕获字节数超过内部容量 | 编译失败 |

调用方必须使借用对象和外层 Plugin 租约覆盖整个使用区间，包括仍需访问这些对象的清理动作。这些责任不能由复制 Callable 的动作代替。

### 8.2 Invokable 连接语义与执行能力

`cmeta_invokable_bind` 检查函数描述与可调用对象是否一致，成功后得到可复用的执行能力。下面的片段假定 `callable` 与输出对象已按前文契约构造：

~~~c
cmeta_status status =
    cmeta_invokable_bind(
        FunctionMeta(plus10),
        callable,
        &invokable);
~~~

绑定得到的 Invokable 仍然借用描述符、提供方和模块，也不会延长已捕获借用的生存期。因此，成功校验只说明当时的语义与执行表示相容；调用方仍需保证这些对象在以后每次使用时有效。

### 8.3 复用已经通过校验的绑定

普通调用入口仍执行所需检查：

~~~c
cmeta_invokable_invoke(
    &invokable,
    &output,
    args);
~~~

对成功绑定后保持不变、且所有借用仍有效的对象，可以使用已准入入口：

~~~c
cmeta_invokable_invoke_admitted(
    &invokable,
    &output,
    args);
~~~

该路径继续检查调用存储，但不重新遍历整张描述符图。复用节省的是重复的语义检查；如果描述或绑定被修改，或借用已经结束，就不能继续依赖原准入结果。

## 9. 对象提供方：描述与执行入口必须一起交付

按操作名查找只得到 FunctionAbi 等描述信息。要执行对象上的操作，提供方还必须给出精确匹配、已经绑定接收者的 Callable，以及去掉接收者参数后的函数数据。下面列出两个检查入口的名称，省略号表示未展开的参数：

~~~c
cmeta_receiver_operation_invokable_bind(...)
~~~

~~~c
cmeta_object_operation_invokable_bind(...)
~~~

检查器验证这对描述与执行对象是否构成原函数的合法投影。它不会根据任意对象指针猜测函数 ABI，也不会仅凭方法名把未知地址转换成可调用目标。

### 9.1 函数操作与接口提供方

独立操作可以由 FunctionDesc、FunctionAbi 和可选适配函数描述；长期提供多项能力的对象则使用 InterfaceDesc 与 `{self, vtable}`。前者围绕一个函数签名，后者还涉及提供方实例及多个操作的共同生存期。

两类对象可以共用 Plugin 加载器、租约和准入设施，但其描述和执行表示仍需分别校验。共用基础设施并不允许用一种对象的生命周期规则解释另一种对象。

## 10. 副作用与性质声明只是可检查主张

副作用（effects）描述函数与外部状态的交互或执行限制；性质（properties）声明函数行为满足的规律。FunctionDesc 可以记录下列标志，供调用方筛选允许的操作或供优化器寻找候选规则。

| 类别 | 例子 | 对使用方的意义 |
|---|---|---|
| 副作用与执行限制 | `IO`、`STATEFUL`、`MAY_FAIL` | 调用可能进行 I/O、依赖状态或失败 |
| 行为性质 | `DETERMINISTIC`、`IDEMPOTENT`、`ASSOCIATIVE` | 声明确定性、幂等性或结合律 |

设置性质标志只是提出相应主张。比如根据幂等性删除第二次调用，需要在约定输入与观察模型下证明 `f(f(x)) = f(x)`；若日志、错误顺序等也可观察，还须证明这些行为被保持。第六章把这种规律连接到具体图改写。

## 11. 验证生成代码、调用结果与借用生存期

验证应分别覆盖声明生成、投影检查、调用结果和借用生存期。下面各项针对不同失败方式，不能仅凭一次成功调用认定整个绑定模型正确。

| 检查对象 | 应观察的结果 |
|---|---|
| `FunctionDecl` | 生成原型与描述符，不隐式生成擦除类型的调用入口 |
| `FunctionInvokeDecl` | §6.1 的 gate 验证成功调用一次；wrong count/null storage 在 native call 前拒绝 |
| 非法投影 | 拒绝签名、承载类别、标志、接收者或绑定位置不匹配 |
| 非法捕获 | 拒绝超限、托管值及未注册的投影签名 |
| 成功准入 | 普通检查入口与已准入入口得到一致的语义结果 |
| 生存期 | 外层所有者覆盖借用区间，复制 Callable 不隐式增加持有关系 |

性能测量分别比较直接 C 调用、生成的 thunk、普通 Invokable、已准入 Invokable 和带捕获的绑定。报告应说明输入、编译选项和测量范围，不能以“零成本”代替结果。

## 12. CMeta 实现 ACE：有类型 Strategy 与可检查的 Interceptor

这一节的公开 API 来自**后续发布的 Salts 2.3 CMeta ACE 实现**，并非把本章的固定源码快照追认为已有这些模式。完整、可直接编译的安装版 C11 程序是 [ch03_cmeta_ace_patterns.c](../qualification/ch03_cmeta_ace_patterns.c)。

### 12.1 Strategy：一份声明同时生成函数签名与反射事实

ACE Strategy 的本质是把可替换操作封装为契约。普通 C 函数指针已经能解决一个固定回调；当独立模块还需要检查同一调用约定时，CMeta 才有价值：

~~~c
#define BOOK_STRATEGY_METHODS(X, I) \
    X(I, FR1, int, apply, stateful, \
      &cmeta_type_int, CMETA_ABI_SCALAR, CMETA_RESULT_VALUE, \
      (int, value, CMETA_PARAM_IN, &cmeta_type_int, CMETA_ABI_SCALAR))
CMETA_INTERFACE(book_ace_strategy, BOOK_STRATEGY_METHODS);
~~~

`CMETA_IMPLEMENTS` 把 `book_apply(void *self, int value)` 绑定到有类型的 `{self, vtable}`，`book_ace_strategy_apply(&strategy, 5)` 最终仍执行普通 C。`FR1` 同时声明返回值语义、参数方向与 ABI carrier，而不是从 `void *` 猜测。Interface 值是**借用能力**：复制它不会保留 provider、Module 或 Plugin 租约。

### 12.2 Interceptor：提前拒绝和逆序收口都有确定语义

`CMETA_INTERCEPTOR_TYPE(book_ace_interceptor, int, int)` 生成 exact native target/hook 类型。最多 16 个 hook，在调用前检查整条链。成功和拒绝路径分别是：

~~~text
成功:
  before(A) -> before(B) -> target -> after(B) -> after(A)

B 拒绝:
  before(A) -> before(B) -> on_error(B) -> on_error(A)
  target_calls 不增加；response 不改写
~~~

应用可以把鉴权、审计和计量放在普通 C 服务方法之外。`before` 拒绝时不调用目标；已进入 hook 按逆序 `on_error`。如果目标自身返回错误，其部分输出仍由目标原有 native 契约负责，Interceptor 不会假造 rollback 或隐式资源拥有权。

### 12.3 校验合同

安装版程序检查 `ABTba` 与 `AB21` 两条真实 trace；编译器检查目标及 hook 的精确函数签名。Provider、hook context 和 Plugin Scope 必须在整次调用中保持有效。CMeta 元数据不代表线程安全、对象持有或 DSO 安全卸载；需要互斥时由第十章的 Platform + Scoped Locking 提供。第十五章的 [ACE Service Configurator](./ch-15.md) 进一步演示如何从真实配置文件校验 Strategy、在没有活跃借用时更新 vtable，并明确拒绝跨线程和未结算的重配置。

## 13. 小结

FunctionDesc 保存函数的语义契约，FunctionAbi 描述本地调用承载类别；调用适配函数、绑定后的 Callable 与 Invokable 则提供不同形式的执行能力。展开后的 thunk 表明，统一入口仍然调用一个具体类型的 C 函数，调用方仍负责存储的类型、对齐和生存期。参数绑定把一部分参数保留为后续输入，把另一部分保存为受限的值快照或显式借用。复制可调用对象不会自动延长指向对象或动态库的生存期；通过准入检查后的能力只能在原契约成立期间复用。计算图将在这些已知调用之间进一步记录类型连接。
