# 第十三章：CMeta 工程边界：类型身份、ABI 与动态库

头文件中的静态描述符进入多个翻译单元或动态库后，地址可能不同，代码与数据的生存期也不再由一个调用栈决定。本章用独立编译的例子检验 CMeta 的类型身份，再讨论 Plugin 租约、精确 ABI 代际检查和安装包依赖。每项模型假设都对应真实的编译、加载或销毁行为。

## 1. Semantic Identity Across Translation Units

当前 CMeta 把语义身份从描述符 object 地址中显式分离。一个 header-local type 可以写成：

~~~c
/* user_meta.h */

typedef struct User {
    int id;
} User;

static const cmeta_type_identity User_identity =
    CMETA_TYPE_ID_ATOM_INIT("book.User");

static const cmeta_type_desc User_desc = {
    .name = "User",
    .size = sizeof(User),
    .align = _Alignof(User),
    .kind = CMETA_T_OBJECT,
    .pointee = NULL,
    .traits = NULL,
    .identity = &User_identity
};

static inline const cmeta_type_desc *
User_type(void)
{
    return &User_desc;
}
~~~

TU A：

~~~c
/* tu_a.c */

#include "user_meta.h"

const cmeta_type_desc *type_from_a(void)
{
    return User_type();
}
~~~

TU B：

~~~c
/* tu_b.c */

#include "user_meta.h"

const cmeta_type_desc *type_from_b(void)
{
    return User_type();
}
~~~

两个 Translation Unit 会各自拥有 header-local representation。测试必须允许描述符地址不同，同时要求 semantic equality：

~~~c
const cmeta_type_desc *a = type_from_a();
const cmeta_type_desc *b = type_from_b();

assert(a != b); /* representation may differ */

assert(cmeta_type_equal(a, b));

assert(cmeta_type_identity_equal(
    cmeta_type_identity_of(a),
    cmeta_type_identity_of(b)));
~~~

这里不要比较：

~~~c
a->identity == b->identity
~~~

因为 identity object 自身也可能是 TU-local representation。核心规则：

| 对象 | 表示什么 |
|---|---|
| 描述符 pointer | 描述符 representation identity |
| `cmeta_type_identity` | structural 语义身份 |
| `cmeta_type_equal()` | TypeDesc semantic equality authority |

### 1.1 同一个测试形状扩展到 FunctionDesc

函数元数据也不能依赖地址：

~~~c
const cmeta_function_desc *fa =
    function_from_a();

const cmeta_function_desc *fb =
    function_from_b();

assert(fa != fb);

assert(cmeta_function_desc_equal(
    fa, fb));
~~~

当前 `cmeta_function_desc_equal()` 比较名称、返回类型的语义相等性、参数数量/名称/类型/标志、结果标志、effects 与 properties。若精确执行载体也属于边界契约，就必须另外比较 `cmeta_function_abi_desc_equal()`；FunctionDesc 的语义相等不能替代 FunctionAbi 的相等。不能写：

~~~c
if (fa == fb) {
    /* same function contract */
}
~~~

### 1.2 DataBind Contract Identity 也不能等于内存地址

假设两个独立 codegen 使用方都包含：

~~~text
service UserService {
    GetUser: GetUserRequest -> GetUserResponse;
}
~~~

Host 与 Plugin 中的 ServiceDesc 地址可能不同。测试应比较限定后的 contract id、contract version、operation identity 以及逻辑 request/response 类型，而不是比较 `service_desc_host == service_desc_plugin`。因此 **Contract IR 的身份不等于描述符地址**；这与 CMeta 的语义身份原则一致。

## 2. DSO Lifetime 与 Plugin ABI

**术语回顾：** lease（租约）在这里是显式取得并释放的生存期凭据，不是超时到期的网络租约。持有 Plugin lease 可让借用的代码、描述符和回调在使用期间保持有效。quiescent（静止状态）表示相关执行与回调已结束，且不会再访问待卸载资源；quiescent unload 要在满足这些条件后才卸载动态库。

Plugin qualification 不能只在单 executable 内 mock。测试形状：

~~~text
host executable
    |
    | dlopen / LoadLibrary
    v
plugin DSO
    |
    +-- manifest
    +-- FunctionDesc exports
    +-- Interface {self,vtable}
~~~

Host 使用本版 CMeta Plugin 运行时：

~~~c
cmeta_plugin_ref ref = {0};
cmeta_plugin_lease lease = {0};
const cmeta_plugin_manifest *manifest = NULL;

assert(
    cmeta_plugin_registry_load(
        &registry,
        plugin_path,
        &ref) == CMETA_PLUGIN_OK);

assert(
    cmeta_plugin_registry_start(
        &registry,
        ref) == CMETA_PLUGIN_OK);

assert(
    cmeta_plugin_registry_acquire(
        &registry,
        ref,
        &lease,
        &manifest) == CMETA_PLUGIN_OK);
~~~

`acquire` 借用的是 **STARTED plugin** 中由 DSO 拥有的 manifest、export、FunctionDesc、FunctionAbi、interface 和代码。lease 不必与单次调用一一对应；它应覆盖所有仍可能解引用这些 DSO 所有对象的操作。真正需要验证的是 contract identity、精确 ABI epoch 准入、借用与 DSO 代码的生存期、stale generation 以及 quiescent unload，而不是描述符指针是否相等。

### 2.1 Interface/vtable Borrow 必须挡住 Unload

如果 Host 持有：

~~~c
cflow_executor exec;
~~~

其中 `exec.vtable` 指向 Plugin DSO code。那么：

~~~text
lease > 0
or callback in flight
──────────────────────
unload = BUSY
~~~

明确的 **unsafe-unload anti-pattern** 是：

~~~text
unload DSO
    ↓ while borrow still live
host still owns {self,vtable}
    ↓ next indirect call
jump into unmapped code
~~~

正确测试是一条 **生存期 qualification sequence**：

~~~text
acquire interface lease
attempt unload -> CMETA_PLUGIN_BUSY
release lease
request stop / reach quiescent
unload -> CMETA_PLUGIN_OK
old ref -> CMETA_PLUGIN_STALE
~~~

这比解释“vtable 生存期很重要”更直接。

## 3. Installed/Public Contract Gate

源码树内：

~~~cmake
target_link_libraries(test PRIVATE internal_target)
~~~

能通过，不代表安装包能被用户使用。资格测试必须走完整的 **installed-使用方 qualification pipeline**：

~~~text
build library
    ↓ install artifact
install to fresh prefix
    ↓ configure consumer
new independent project
    ↓ package discovery
find_package(...)
    ↓ public compile contract
include public headers
    ↓ public link contract
link public targets
    ↓ runtime smoke test
run
~~~

例如：

~~~cmake
find_package(Salts CONFIG REQUIRED)
find_package(SaltsUtils CONFIG REQUIRED)

add_executable(consumer main.c)

target_link_libraries(
    consumer
    PRIVATE
        Salts::CMeta
        Salts::Plugin)
~~~

任何 private include、source-tree path 或未导出的 transitive dependency 都应该在这里失败。

### 3.1 当前 Plugin ABI：exact epoch，而不是 readable-prefix negotiation

**ABI epoch（ABI 代际标识）**标记一组约定的二进制契约。本节的 exact epoch 要求生产者与消费者使用相同代际，并通过其他规定的布局和契约检查；epoch 相同并不能代替所有 ABI 校验。

`cmeta_plugin_manifest` 的确带有：

~~~c
uint32_t struct_size;
uint32_t abi_version;
~~~

但当前 CMeta Plugin contract **不是**“只要 prefix 可读就兼容”。它明确要求：

~~~text
manifest.struct_size == current layout
manifest.abi_version == CMETA_PLUGIN_ABI_VERSION
        |
        v
admit

otherwise
        |
        v
reject / rebuild plugin
~~~

原因是 Plugin export 会直接暴露当前 CMeta 反射 layout：

- FunctionDesc
- FunctionAbi
- InterfaceDesc
- Type/Data/trait pointers
- exact invoke code

所以 Plugin ABI epoch 同时覆盖 publication layout 与其传递暴露的反射 ABI。当前设计刻意没有：

- old-layout retry
- ABI negotiation
- readable-prefix compatibility
- tail compatibility
- fallback adapter

Plugin 的策略是 exact epoch + fail-fast rebuild，不是跨 epoch 的结构体兼容协议。后面讨论其它提供方 ABI 时仍然可以采用 size-versioned readable prefix；但不能把那套扩展策略投射到当前 Plugin manifest 上。

### 3.2 Evidence Matrix

| Claim | Real gate |
|---|---|
| semantic identity survives TU boundary | two-TU test |
| FunctionDesc contract survives duplicate representation | independent descriptor test |
| DataBind contract survives codegen boundary | cross-generated contract test |
| Plugin ABI survives DSO | installed host + real shared library |
| vtable borrow blocks unsafe unload | live lease + unload BUSY test |
| old ref cannot call recycled plugin | generation STALE test |
| public package is complete | fresh-prefix installed consumer |
| memory/lifetime is safe | ASan/UBSan + stress |
| Plugin ABI epoch mismatch fails closed | wrong epoch/layout -> load rejection |

这章后面的 case study 和具体 ABI 讨论，都应该继续落回这些 executable gates。

## 4. Semantic Identity Case Studies

单 Translation Unit 中，最诱人的实现是：

~~~c
if (a_type == b_type) {
    /* same type */
}
~~~

如果所有描述符都来自同一个全局对象，比较地址甚至可能长期“看起来正确”。但进入 header-local 生成描述符、同一静态库被多个 DSO 嵌入、Plugin/共享库边界或独立翻译单元之后，同一个语义类型完全可能对应多个描述符对象：地址不同，含义相同。因此 **pointer equality ≠ semantic type equality**。这不是抽象洁癖，而是 Multi-TU/DSO 正确性的必要条件。

### 4.1 本版 CMeta 实现已经把 Identity 从 Descriptor 中显式分离

当前 type 描述符包含 name、size、align、kind、pointee、traits 和 identity，而 `cmeta_type_identity` 可以表达：

~~~text
ATOM(stable id)
POINTER(base identity)
CONST(base identity)
APPLY(generic constructor, arguments...)
~~~

Generic constructor 自身还有 stable_id、display_name、min/max 参数个数和 category。因此 `Pair<int, long>` 的语义身份是下面的结构：

~~~text
APPLY(
    constructor = "cmeta.Pair",
    args = ["cmeta.int", "cmeta.long"]
)
~~~

而不是依赖 one Pair 描述符的地址。

### 4.2 Structural identity 已经有真实 Multi-TU test

当前测试不是在同一个源文件里复制两个指针做比较，而是让 peer Translation Unit 返回 independently constructed identity：local `Pair<A,B>` 和 peer `Pair<A,B>`。并验证：

~~~text
local identity address != peer identity address
local constructor address != peer constructor address

but

cmeta_type_identity_equal(local, peer) == true
~~~

这就是第十三章需要的证据类型：

不是证明“理论上支持 Multi-TU”，而是让两个真正独立编译单元产生不同 representation，再验证 semantic equality。

### 4.3 Custom Trait Descriptor 也要跨 TU 保持语义一致

本版 CMeta 测试还覆盖自定义 `owned_int` 描述符：TU A 与对等 TU B 分别构造自己的描述符。测试目标不是指针相等，而是两边拥有相同类型语义、相同 Trait 契约，并且跨 TU 行为仍然有效。这样 Traits 才不是只在 header demo 中成立的机制。

### 4.4 Callable Identity：函数地址也不是统一答案

Callable 比 Type 更复杂，因为它可能同时有 canonical raw target、adapter、生成器、捕获、effects、properties 和签名。所以 Callable identity 必须先问：

> “哪一种 dispatch 表示是 authoritative？”

当前实现已经区分 `CANONICAL_RAW` 与 `ADAPTER`：

| Dispatch representation | Identity authority |
|---|---|
| canonical raw | authoritative raw target across translation units |
| adapter | adapter/generator pointers + capture bytes |

### 4.5 为什么 canonical raw 可以跨 TU

如果两个翻译单元各自产生不同的 wrapper/adapter 地址，但最终都解析到同一个权威 raw C function，那么 callable 的语义身份不应因为 wrapper 地址不同而失败。当前测试已经通过 raw target 覆盖跨翻译单元的 canonical callable identity，并直接服务于 Graph 结构相等、Optimizer 重复检测、AOT Graph/Stage 匹配和 Certificate 检查。

所以 callable identity 不是一个局部 helper。它已经成为编译器/控制面 correctness 的基础。

### 4.6 Capturing Callable 则必须把 Capture 纳入 identity

对于：

~~~text
bind(multiply, 10)
bind(multiply, 20)
~~~

raw/adapter code 可能相同，但捕获不同。因此它们不能被当成 same callable。这说明 identity 的正确原则既不是 “always compare pointer”，也不是 “never compare pointer”，而是：

根据 representation 的 semantic authority 定义 equality。

### 4.7 Static / Shared Library：Duplicate Globals 不能成为语义事故

本版 CMeta 的 CMake 有一个很值得写进书里的工程决定：静态 CMeta archive 使用 `C_VISIBILITY_PRESET hidden`。目的不只是减少导出符号。源码注释明确指出，同一个静态 CMeta archive 可能同时嵌入 Core 和多个 bridge DSO；每个 image 可以保留自己的不可变描述符与 helper，而类型兼容性依赖语义身份，不依赖地址。如果语义正确性要求进程内只有一个唯一描述符地址，那么同一静态库一旦被链接进两个 DSO，设计就天然脆弱。

而当前方向是一条 **语义身份 rule**：duplicate representation objects may exist，但语义身份仍必须一致。Symbol visibility 因此只是优化/封装问题，不是 type semantics 的事实源。

## 5. Public / Versioned ABI Contracts

C library 很容易出现一个错误推论：

`struct` 出现在 public header 中，并不意味着所有字段都属于调用方可自由解释的契约。C 层面的可见性与语义所有权必须分开。第七章已经看到，Graph 为了 introspection 保持 concrete IR；Subscription/Actor 这类活动执行对象则使用 opaque handle。工程边界还应进一步把公开字段分成三类。

### 5.1 Stable contract fields

例如 configuration 声明行、status/result structs、documented method pointers、semantic enum values，调用方可以按照文档初始化/读取。

### 5.2 Read-only introspection

例如 Graph、Node、Edge、Subgraph、Plan input/output type 和 stats，可见是为了 diagnostics、verification、advanced tooling。不代表调用方可以绕过 builder mutation。

### 5.3 Internal carrier

例如 `void *impl` 即使出现在 public struct 中，也不因此获得额外语义。调用方不能解引用、序列化、把它当身份比较、复制其活动 owner，也不能把 `sizeof/offsetof` 当作持久化协议。ABI 规则应明确写出：

C visibility is not semantic ownership.

### 5.4 Versioned Provider ABI：扩展 Struct 时保留 Admission Boundary

对于可扩展 provider/vtable，最危险的做法是直接假定调用方与 library 的 `struct` 布局永远完全同步。本版 CMeta data 描述符/提供方采用 `struct_size` 和 `abi_version`，使 checked façade 可以先验证 ABI 版本、最小可读 `struct` 前缀、storage type identity、所有权/layout 契约和必需操作，再访问可选追加字段。这种模式适合描述符、provider ops 和扩展接口，但必须遵守：

1. 旧 prefix meaning 不能静默改变；
2. 新字段 append 后要有 version/size 准入检查；
3. optional capability 与 required capability 分开；
4. 调用方不能因为字段当前存在就推断 future ABI；
5. enum/status numeric values若公开，也属于 ABI。

### 5.5 CFlow SOVERSION：ABI Version 是真实 Library Artifact

本版 CFlow library snapshot 是 `version = 4.1.0`、`SOVERSION = 4`，Windows shared build 还会把 ABI major 写进输出名。如果一个 library 对外暴露 public `struct`、枚举值、函数签名、调用约定、符号名或所有权契约，那么 ABI 破坏不能只藏在 Git 历史里；至少应有 library ABI major、package version 和明确的 release compatibility policy。当然：

SOVERSION 本身不会自动让 ABI 稳定。它只是把 incompatible boundary 变得可表达。真正 stability 仍然依赖 public API discipline 和 qualification。

### 5.6 Compile-time Configuration 也是 ABI 的一部分

CMeta 的有限签名全集和 CFlow 的配置上限都可能进入公共编译契约。例如 CFlow 当前把 `CFLOW_MACHINE_MAX_STATES`、`CFLOW_MACHINE_MAX_EVENTS`、`CFLOW_MACHINE_MAX_GUARDS`、`CFLOW_MACHINE_MAX_ACTIONS`、`CFLOW_MACHINE_MAX_TRANSITIONS` 等作为 PUBLIC compile definitions 导出。这意味着使用方看到的 public header 配置必须与 library contract 一致。

同样，CMeta user relation/type lists属于 shared 编译期 configuration。文档明确要求：

> affected translation units 必须看到一致的 callable ABI/configuration。

因此 Multi-TU 正确性不只要求 struct 声明一致，还要求有限签名全集、编译期配置以及公共 feature/limit 契约一致。如果不同 TU 使用不同 relation universe，却彼此交换 callable 或描述符对象，问题可能从语义错误直接升级为 ABI 错误。

### 5.7 Header / Source Boundary：哪些 Meta 必须留在调用点

Modern C meta library 不应该走向 everything header-only，也不应该走向 everything hidden in `.c`。正确边界取决于信息在哪里存在。

### 5.8 必须在 Header / Call Site 的内容

典型包括 `_Generic` selection、编译期 type assertion、finite macro specialization、有类型的包装函数 generation 和 call-site C type inspection，因为 C 编译器只在调用点知道 actual static C type。

### 5.9 应该放进 compiled C library 的内容

包括 container algorithms、Graph mutation/validation、Subscription 运行时、Executor、Machine/Actor 运行时、type identity comparison、optimizer、plan 编译器和 certificate checker。这些没有理由因为“Meta”而被复制到每个 Translation Unit。因此：

header-only typed façade 不等于 header-only implementation。这也是控制代码膨胀、ABI、编译时和 debug experience 的关键。

### 5.10 Compiler capability 也是 public engineering boundary

第一到三章已经使用 finite PP、native typeof、same-type、zero-argument variadics、cleanup attribute 等能力。这些能力不能在工程章节里被当成“编译器细节”。Public header 如果根据编译器 / language mode 生成不同 guarantee，那么使用方的编译环境就是 contract 的一部分。正确模型是：

~~~text
semantic requirement
        |
        v
compiler capability query
        |
   +----+----+
   |         |
supported   unsupported
   |         |
   v         v
strong      explicit weaker contract
surface     or compile failure
~~~

不能：

~~~text
feature unavailable
        |
        v
unsafe cast / guessed fallback
        |
        v
pretend guarantee is unchanged
~~~

例如需要分别 qualification：

| Capability | Engineering question |
|---|---|
| native typeof / same-type | 当前 C/C++ 编译器 mode 是否真正提供对应 type guarantee？ |
| zero-argument variadics | 是否处于公开支持 VA_OPT 的标准模式？ |
| cleanup attribute | backend 是否真的提供 lexical cleanup attribute？ |
| section / used attributes | ELF / COFF / Mach-O 是否有明确 backend contract？ |
| unique counter | 只用于 TU-local naming，不能成为语义身份 |

因此 cross-编译器 gate 不应该只问“GCC / Clang / MSVC 都能编译吗”。它应该问：

~~~text
same semantic contract?
+
capability differences explicit?
+
unsupported paths fail honestly?
+
installed public headers preserve the same documented guarantee?
~~~

这也是 fail-fast 原则在编译器 abstraction 上的版本。Portability 不是让所有编译器假装一样，而是让差异发生在一个显式、可测试的 capability boundary。

## 6. Generated Artifact Ownership 与 Packaging

本书已经看到 `builtin_signature_manifest.h`、`builtin_operator_policy.h` 等 generated C headers；同类 artifact 应由 formal source/生成器单向生成并由 CI 检查。工程规则必须非常严格：

| Artifact | 角色 |
|---|---|
| formal model | authoritative source |
| generated header | checked-in build artifact |
| manual edit generated header | forbidden |

普通使用方构建**不需要 Lean**；只有 CI 或语义开发流程运行相应生成器的 `--check` 模式，验证生成产物没有漂移。这样既能保持可复现的 package 与普通 C 使用方体验，又保留单一事实源和可审阅的生成差异。

### 6.1 Install / Export：源码树里能 link 远远不够

本版源码快照通过 Salts 发行包提供标准 CMake package/export 边界：`SaltsConfig.cmake`、`SaltsConfigVersion.cmake`、`SaltsTargets.cmake`，并使用 `Salts::` namespace。CMeta/CFlow 分别导出为 **Salts::CMeta** 与 **Salts::CFlow**，同时安装公共头文件、library/archive、运行时产物、package config 与 target export；安装后使用方只依赖这些公开入口。

这里的 `Salts` 是包名与目标 namespace；正文中的库名仍为 CMeta / CFlow，CMeta Plugin 对应 `Salts::Plugin`。包名不会改变 `cmeta_*` / `CMETA_*` 这些公共符号。使用方的目标形态是：

~~~cmake
find_package(Salts CONFIG REQUIRED)

target_link_libraries(app PRIVATE
    Salts::CMeta
    Salts::CFlow)
~~~

这比依赖 source-tree add_subdirectory、source-tree include path 或随意链接某个 .a 文件重要得多。因为 install boundary 会立刻暴露：

~~~text
missing public dependency
wrong include interface
private header leak
missing transitive target
wrong compile definition export
bad symbol visibility
source-tree-only path
~~~

### 6.2 CFlow 的 public dependency 必须通过 target contract 导出

本版 CFlow 实现 link contract包含：

~~~text
PUBLIC
    Salts::CMeta
    Salts::NativeIO
    Salts::Platform

PRIVATE
    Salts::Concurrency
~~~

这不是 CMake aesthetics。它表达：

> external 使用方使用 CFlow public headers / symbols 时，哪些 dependency 是 exported contract，哪些只是 implementation detail。

如果 PRIVATE dependency 的 symbol 出现在 public ABI，却没有被 export，source-tree build 可能绿，而 installed 使用方 link 会失败。

### 6.3 Public header install 也必须排除 private headers

本版 CFlow install public cflow headers，同时显式排除 plan_internal.h 和 relation_exec.h。这条边界很重要：

一个 header 放在仓库里，不代表它属于 SDK。如果 public header 偷偷 include private header，installed build 会最快把问题暴露出来。

### 6.4 Installed Consumer Qualification：最接近真实用户的 Gate

本书建议把 installed-使用方 test 当成正式 gate，而不是 release 前手工冒烟。推荐流程：

~~~text
clean source checkout
    ↓
configure/build/test Salts
    ↓
install into empty prefix
    ↓
new independent consumer source tree
    ↓
find_package(Salts CONFIG REQUIRED)
    ↓
link only exported Salts::* targets
    ↓
include only installed headers
    ↓
build
    ↓
run
~~~

使用方至少覆盖：

- CMeta type/traits/callable；
- CFlow Graph/Stream；
- Multi-TU use；
- static build；
- shared build where supported；
- C/C++ header compatibility。

关键规则是 no source-tree include path、no build-tree target、no undeclared private library、no generated source file copied manually。只有这样，才能证明：

“可安装 library”不是文档里的愿望，而是用户真正能拿到的 SDK contract。

## 7. Qualification Across Boundaries

一个弱 Multi-TU test 只是 `foo.c calls bar.c`，这不足以验证 Meta identity。真正有效的 test 要故意让两个 TU 各自拥有独立 representation。

### 7.1 Type Identity Test

~~~text
TU A:
    independently constructs Pair<A,B> identity

TU B:
    independently constructs Pair<A,B> identity

assert:
    addresses differ
    constructors may differ
    semantic equality true
~~~

本版 CMeta 实现已经有这种 peer test。

### 7.2 Callable Identity Test

~~~text
TU A:
    canonical callable wrapper A

TU B:
    canonical callable wrapper B

assert:
    wrapper representation can differ
    authoritative raw target identity agrees
~~~

当前 tests 同样覆盖这一点。

### 7.3 Generated Configuration Test

还应覆盖 shared configuration header 在 TU A/TU B 中一致，以及 callable 签名 ABI 在两边一致，并增加 negative compile/link test：

~~~text
intentionally inconsistent configuration
    → fail fast
~~~

如果工具链无法可靠诊断，则至少让这种状态成为明确 unsupported contract，而不是运行时猜测。

### 7.4 Cross-Compiler：Core Semantics 不能建立在偶然扩展上

CMeta 可以使用 C11 `_Generic`、preprocessor、`_Static_assert` 和 standard alignment/type rules，并针对 MSVC 的 conforming preprocessor mode 配置必要编译器 option。但书里需要保持一条原则：

编译器扩展可以优化实现，但不能成为语义模型的唯一基础。例如 GNU statement expression、`typeof` 扩展或编译器特定的 section 技巧可以形成可选 fast path；核心类型关系、callable 语义和 ABI 契约仍应由目标编译器正式支持的机制表达。跨编译器 CI 的意义也不只是“语法都能编译”，而是验证相同的声明语义、所有权/错误契约和安装后 API 形状在不同编译器族上仍然成立。

### 7.5 ABI Qualification：不要只比较 sizeof(struct)

ABI test 的层次至少有四类。

### 7.6 Compile ABI

检查 public headers 能作为 C11 编译、能从 supported C++ mode 引用、macro 不依赖 include accident、generated headers 自洽。本版 CFlow 实现已有 public/header C++ compile tests，这类 gate应持续扩展。

### 7.7 Link ABI

检查 public symbol 存在、calling convention 匹配、transitive dependency 已导出、static/shared 使用方都能链接。这是 installed 使用方才能真正验证的部分。

### 7.8 Semantic ABI

即使函数签名没有变化，如果 `FULL` 突然开始丢弃数据、`CLOSED` 变成可重试、Actor stale ref 改为返回 `INVALID_ARGUMENT`，或 Graph mutation 不再改变 version，这些仍然属于 breaking behavior。因此：

Status meaning、所有权、lifecycle、ordering、fallback 都属于 semantic ABI。

### 7.9 Data ABI

对于真正承诺跨 binary boundary 的 struct，prefix 字段、version、`struct_size`、enum values、alignment 和 pointed-data 所有权才需要正式版本化。而 opaque owner `void *impl` 就是为了避免把内部 layout 变成 ABI。

### 7.10 Fail-fast Across Boundaries：错误越晚越昂贵

全书反复出现的 fail-fast，在这里表示 **diagnostic-stage ordering**，不是运行时 pipeline：

~~~text
compile-time
    ↓ earlier is cheaper
build-time
    ↓
install/package-time
    ↓
link-time
    ↓
admission-time
    ↓
execution-time
~~~

原则是：

能在更早层发现，就不要把同一个错误留到更晚层。

| Error | Earliest proper boundary |
|---|---|
| unsupported TypeFunction row | compile-time |
| invalid Machine schema | build-time |
| generated manifest drift | CI/generator check |
| missing public link dependency | installed consumer link |
| wrong Event payload | admission |
| I/O failure | execution |

把所有错误都变成运行时 error string，不叫“API 简单”。那只是把诊断成本推给用户。

## 8. 小结

跨翻译单元的类型相等由语义身份决定，公共 ABI 则约束真实布局、调用方式和配置。Plugin 借用还要求描述符、函数代码和清理回调在租约释放前持续有效；精确 ABI 代际检查不提供跨代际布局兼容。这些条件必须由独立编译、动态库加载与卸载、安装后构建和失败路径检验。形式模型帮助陈述身份和生命周期规则，真实工具链验证其二进制实现。源码树内成功链接不能单独证明安装包可用。
