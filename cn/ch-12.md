# 第十三章：工程化边界——ABI、Multi-TU、Semantic Identity 与可安装的 C Library

> **这一章不先讨论“ABI 很重要”。**
>
> 直接写两个 Translation Unit，然后让 pointer equality 失败。工程边界要靠 Multi-TU test、installed consumer、real DSO、versioned ABI 和 sanitizer/stress，而不是靠同一个源码树里“看起来能 link”。

---

## 1. Semantic Identity Across Translation Units

当前 CMeta 把 semantic identity 从 descriptor object 地址中显式分离。

一个 header-local type 可以写成：

~~~c
/* user_meta.h */

typedef struct User {
    int id;
} User;

static const cmeta_type_identity User_identity =
    CMETA_TYPE_ID_ATOM_INIT("book.User");

static const cmeta_type_desc User_desc = {
    .name = "User",
    .size = sizeof(User),
    .align = _Alignof(User),
    .kind = CMETA_T_OBJECT,
    .pointee = NULL,
    .traits = NULL,
    .identity = &User_identity
};

static inline const cmeta_type_desc *
User_type(void)
{
    return &User_desc;
}
~~~

TU A：

~~~c
/* tu_a.c */

#include "user_meta.h"

const cmeta_type_desc *type_from_a(void)
{
    return User_type();
}
~~~

TU B：

~~~c
/* tu_b.c */

#include "user_meta.h"

const cmeta_type_desc *type_from_b(void)
{
    return User_type();
}
~~~

两个 Translation Unit 会各自拥有 header-local representation。

测试必须允许 descriptor 地址不同，同时要求 semantic equality：

~~~c
const cmeta_type_desc *a = type_from_a();
const cmeta_type_desc *b = type_from_b();

assert(a != b); /* representation may differ */

assert(cmeta_type_equal(a, b));

assert(cmeta_type_identity_equal(
    cmeta_type_identity_of(a),
    cmeta_type_identity_of(b)));
~~~

这里不要比较：

~~~c
a->identity == b->identity
~~~

因为 identity object 自身也可能是 TU-local representation。

核心规则：

| 对象 | 表示什么 |
|---|---|
| descriptor pointer | descriptor representation identity |
| `cmeta_type_identity` | structural semantic identity |
| `cmeta_type_equal()` | TypeDesc semantic equality authority |

---

### 1.1 同一个测试形状扩展到 FunctionDesc

函数 metadata 也不能依赖地址：

~~~c
const cmeta_function_desc *fa =
    function_from_a();

const cmeta_function_desc *fb =
    function_from_b();

assert(fa != fb);

assert(cmeta_function_desc_equal(
    fa, fb));
~~~

当前 `cmeta_function_desc_equal()` 比较 name、return type semantic equality、parameter count/name/type/flags、result flags、effects 与 properties。若 exact execution carrier 也属于边界契约，则必须另外比较 `cmeta_function_abi_desc_equal()`；FunctionDesc semantic equality 不应该偷偷代替 FunctionAbi equality。

不能写：

~~~c
if (fa == fb) {
    /* same function contract */
}
~~~

---

### 1.2 DataBind Contract Identity 也不能等于内存地址

假设两个独立 codegen consumer 都包含：

~~~text
service UserService {
    GetUser: GetUserRequest -> GetUserResponse;
}
~~~

Host 与 Plugin 里的 ServiceDesc 地址可能不同。

测试应该比较 qualified contract id、contract version、operation identities 和 logical request/response types，而不是比较 `service_desc_host == service_desc_plugin`。

所以 **Contract IR identity != descriptor address**，和 CMeta 使用同一个工程原则。

## 2. DSO Lifetime 与 Plugin ABI

Plugin qualification 不能只在单 executable 内 mock。

测试形状：

~~~text
host executable
    |
    | dlopen / LoadLibrary
    v
plugin DSO
    |
    +-- manifest
    +-- FunctionDesc exports
    +-- Interface {self,vtable}
~~~

Host 使用本版 CMeta Plugin runtime：

~~~c
cmeta_plugin_ref ref = {0};
cmeta_plugin_lease lease = {0};
const cmeta_plugin_manifest *manifest = NULL;

assert(
    cmeta_plugin_registry_load(
        &registry,
        plugin_path,
        &ref) == CMETA_PLUGIN_OK);

assert(
    cmeta_plugin_registry_start(
        &registry,
        ref) == CMETA_PLUGIN_OK);

assert(
    cmeta_plugin_registry_acquire(
        &registry,
        ref,
        &lease,
        &manifest) == CMETA_PLUGIN_OK);
~~~

`acquire` 借用的是 **STARTED plugin** 中的 DSO-owned manifest/export/FunctionDesc/FunctionAbi/interface/code。lease 不一定“一次调用一个”；它应该覆盖所有仍可能解引用这些 DSO-owned 对象的操作。

这里真正验证的是 contract identity、exact ABI epoch admission、borrow lifetime、DSO code lifetime、stale generation 和 quiescent unload，而不是 descriptor pointer。

---

### 2.1 Interface/vtable Borrow 必须挡住 Unload

如果 Host 持有：

~~~c
cflow_executor exec;
~~~

其中 `exec.vtable` 指向 Plugin DSO code。

那么：

~~~text
lease > 0
or callback in flight
──────────────────────
unload = BUSY
~~~

明确的 **unsafe-unload anti-pattern** 是：

~~~text
unload DSO
    ↓ while borrow still live
host still owns {self,vtable}
    ↓ next indirect call
jump into unmapped code
~~~

正确测试是一条 **lifetime qualification sequence**：

~~~text
acquire interface lease
attempt unload -> CMETA_PLUGIN_BUSY
release lease
request stop / reach quiescent
unload -> CMETA_PLUGIN_OK
old ref -> CMETA_PLUGIN_STALE
~~~

这比解释“vtable lifetime 很重要”更直接。

## 3. Installed/Public Contract Gate

源码树内：

~~~cmake
target_link_libraries(test PRIVATE internal_target)
~~~

能通过，不代表安装包能被用户使用。

资格测试必须走完整的 **installed-consumer qualification pipeline**：

~~~text
build library
    ↓ install artifact
install to fresh prefix
    ↓ configure consumer
new independent project
    ↓ package discovery
find_package(...)
    ↓ public compile contract
include public headers
    ↓ public link contract
link public targets
    ↓ runtime smoke test
run
~~~

例如：

~~~cmake
find_package(Salts CONFIG REQUIRED)
find_package(SaltsUtils CONFIG REQUIRED)

add_executable(consumer main.c)

target_link_libraries(
    consumer
    PRIVATE
        Salts::CMeta
        Salts::Plugin)
~~~

任何 private include、source-tree path 或未导出的 transitive dependency 都应该在这里失败。

---

### 3.1 当前 Plugin ABI：exact epoch，而不是 readable-prefix negotiation

`cmeta_plugin_manifest` 的确带有：

~~~c
uint32_t struct_size;
uint32_t abi_version;
~~~

但当前 CMeta Plugin contract **不是**“只要 prefix 可读就兼容”。

它明确要求：

~~~text
manifest.struct_size == current layout
manifest.abi_version == CMETA_PLUGIN_ABI_VERSION
        |
        v
admit

otherwise
        |
        v
reject / rebuild plugin
~~~

原因是 Plugin export 会直接暴露当前 CMeta Reflection layout：

~~~text
FunctionDesc
FunctionAbi
InterfaceDesc
Type/Data/trait pointers
exact invoke code
~~~

所以 Plugin ABI epoch 同时覆盖 publication layout 与其传递暴露的 Reflection ABI。

当前设计刻意没有：

~~~text
old-layout retry
ABI negotiation
readable-prefix compatibility
tail compatibility
fallback adapter
~~~

> **Plugin 的策略是 exact epoch + fail-fast rebuild，不是跨 epoch 的结构体兼容协议。**

后面讨论其它 provider ABI 时仍然可以采用 size-versioned readable prefix；但不能把那套扩展策略投射到当前 Plugin manifest 上。

---

### 3.2 Evidence Matrix

| Claim | Real gate |
|---|---|
| semantic identity survives TU boundary | two-TU test |
| FunctionDesc contract survives duplicate representation | independent descriptor test |
| DataBind contract survives codegen boundary | cross-generated contract test |
| Plugin ABI survives DSO | installed host + real shared library |
| vtable borrow blocks unsafe unload | live lease + unload BUSY test |
| old ref cannot call recycled plugin | generation STALE test |
| public package is complete | fresh-prefix installed consumer |
| memory/lifetime is safe | ASan/UBSan + stress |
| Plugin ABI epoch mismatch fails closed | wrong epoch/layout -> load rejection |

这章后面的 case study 和具体 ABI 讨论，都应该继续落回这些 executable gates。

## 4. Semantic Identity Case Studies

单 Translation Unit 中，最诱人的实现是：

~~~c
if (a_type == b_type) {
    /* same type */
}
~~~

如果所有 descriptor 都来自同一个全局 object，这甚至会长期“看起来正确”。

但一旦进入 header-local generated descriptors、static archive embedded into multiple DSOs、plugin/shared-library boundary 或 independent translation units，同一个 semantic type 完全可能存在多个 descriptor object，地址不同但 meaning 相同。所以 **pointer equality ≠ semantic type equality**。

这不是抽象洁癖，而是 Multi-TU/DSO correctness。

### 4.1 本版 CMeta 实现已经把 Identity 从 Descriptor 中显式分离

当前 type descriptor 包含 name、size、align、kind、pointee、traits 和 identity，而 `cmeta_type_identity` 可以表达：

~~~text
ATOM(stable id)
POINTER(base identity)
CONST(base identity)
APPLY(generic constructor, arguments...)
~~~

Generic constructor 自身还有 stable_id、display_name、min/max arity 和 category。

因此 `Pair<int, long>` 的 semantic identity 是下面的结构：

~~~text
APPLY(
    constructor = "cmeta.Pair",
    args = ["cmeta.int", "cmeta.long"]
)
~~~

而不是依赖 one Pair descriptor 的地址。

### 4.2 Structural identity 已经有真实 Multi-TU test

当前测试不是在同一个源文件里复制两个指针做比较，而是让 peer Translation Unit 返回 independently constructed identity：local `Pair<A,B>` 和 peer `Pair<A,B>`。

并验证：

~~~text
local identity address != peer identity address
local constructor address != peer constructor address

but

cmeta_type_identity_equal(local, peer) == true
~~~

这就是第十三章需要的证据类型：

> **不是证明“理论上支持 Multi-TU”，而是让两个真正独立编译单元产生不同 representation，再验证 semantic equality。**

### 4.3 Custom Trait Descriptor 也要跨 TU 保持语义一致

本版 CMeta tests 还覆盖 custom `owned_int` descriptor in TU A 与 peer descriptor in TU B。目标不是 descriptor pointer equality，而是 same type semantics、same trait contract，以及 cross-TU behavior remains valid。

这样 Traits 才不是“只有 header demo 能用”的机制。

---

### 4.4 Callable Identity：函数地址也不是统一答案

Callable 比 Type 更复杂，因为它可能同时有 canonical raw target、adapter、generator、capture、effects、properties 和 signature。

所以 Callable identity 必须先问：

> “哪一种 dispatch 表示是 authoritative？”

当前实现已经区分 `CANONICAL_RAW` 与 `ADAPTER`：

| Dispatch representation | Identity authority |
|---|---|
| canonical raw | authoritative raw target across translation units |
| adapter | adapter/generator pointers + capture bytes |

### 4.5 为什么 canonical raw 可以跨 TU

如果两个 Translation Unit 各自产生不同 wrapper/adapter 地址，但最终解析到同一个 authoritative raw C function，那么 semantic callable identity 不应该因为 wrapper 地址不同而失败。

当前测试已经覆盖 canonical callable identity across translation units by raw target，并直接服务 Graph structural equality、Optimizer duplicate detection、AOT Graph/Stage matching 和 Certificate checking。

所以 callable identity 不是一个局部 helper。

它已经成为 compiler/control-plane correctness 的基础。

### 4.6 Capturing Callable 则必须把 Capture 纳入 identity

对于：

~~~text
bind(multiply, 10)
bind(multiply, 20)
~~~

raw/adapter code 可能相同，但 capture 不同。

因此它们不能被当成 same callable。

这说明 identity 的正确原则既不是 “always compare pointer”，也不是 “never compare pointer”，而是：

> **根据 representation 的 semantic authority 定义 equality。**

---

### 4.7 Static / Shared Library：Duplicate Globals 不能成为语义事故

本版 CMeta 实现 CMake 有一个非常值得写进书里的工程决定。

对于 static CMeta archive 使用 `C_VISIBILITY_PRESET hidden`，原因不是单纯“减少导出符号”。

注释明确指出：static CMeta archive 可能同时被 Core 和多个 bridge DSO 嵌入；每个 image 的 immutable descriptors/helpers 可以保持 local；type compatibility 依赖 semantic identity，而不是 address。

这是一条非常成熟的 ABI 思路。

如果 semantic correctness 依赖 process-wide unique descriptor address，那么同一个 static archive 被链接进两个 DSO 时，设计天然脆弱。

而当前方向是一条 **semantic identity rule**：duplicate representation objects may exist，但 semantic identity 仍必须一致。Symbol visibility 因此只是优化/封装问题，不是 type semantics 的事实源。

## 5. Public / Versioned ABI Contracts

C library 很容易出现一个错误推论：

> **struct 在 public header ⇒ 所有 field 都属于 caller contract**

这并不成立。C visibility 与 semantic ownership 必须分开。

第七章已经看到 Graph 为了 introspection 保持 concrete IR；

Subscription / Actor 等 live execution owner 则使用 opaque handle。

第十三章应该进一步把 public field分成三类。

### 5.1 Stable contract fields

例如 configuration rows、status/result structs、documented method pointers、semantic enum values，caller 可以按照文档初始化/读取。

### 5.2 Read-only introspection

例如 Graph、Node、Edge、Subgraph、Plan input/output type 和 stats，可见是为了 diagnostics、verification、advanced tooling。

不代表 caller 可以绕过 builder mutation。

### 5.3 Internal carrier

例如 `void *impl`，即使它在 public struct 中可见，也没有额外 semantic meaning。

caller 不能 dereference、serialize、compare as identity、copy a live owner，也不能把 `sizeof/offsetof` 当 persistence protocol。

这一点应该明确写进 ABI philosophy：

> **C visibility is not semantic ownership.**

---

### 5.4 Versioned Provider ABI：扩展 Struct 时保留 Admission Boundary

对于可扩展 provider/vtable，最危险的做法是直接假设 caller 和 library 的 struct layout 完全同步。

本版 CMeta data descriptor/provider 已经采用 `struct_size` 和 `abi_version` 字段。

这使 checked facade 可以先验证 provider ABI version、minimum struct prefix size、storage type identity、ownership/layout contract 和 required operations，再使用 optional appended fields。

这种模式适合 descriptor、provider ops、plugin ABI 和 extension interface。

但必须遵守：

1. 旧 prefix meaning 不能静默改变；
2. 新 field append 后要有 version/size admission；
3. optional capability 与 required capability 分开；
4. caller不能因为 field 当前存在就推断 future ABI；
5. enum/status numeric values若公开，也属于 ABI。

---

### 5.5 CFlow SOVERSION：ABI Version 是真实 Library Artifact

本版 CFlow library snapshot 是 `version = 4.1.0`、`SOVERSION = 4`。

Windows shared build还会把 ABI major写进输出名。

这一点很重要。

如果一个 library 对外暴露 public structs、enum values、function signatures、calling conventions、symbol names 或 ownership contracts，那么 ABI break 不能只藏在 Git history 里。至少要有 library ABI major、package version 和 release compatibility policy。

当然：

> **SOVERSION 本身不会自动让 ABI 稳定。**

它只是把 incompatible boundary 变得可表达。

真正 stability 仍然依赖 public API discipline 和 qualification。

---

### 5.6 Compile-time Configuration 也是 ABI 的一部分

CMeta 的 finite signature universe 和 CFlow 的 configured limits 都可能进入 public compilation surface。

例如 CFlow 当前把 `CFLOW_MACHINE_MAX_STATES`、`CFLOW_MACHINE_MAX_EVENTS`、`CFLOW_MACHINE_MAX_GUARDS`、`CFLOW_MACHINE_MAX_ACTIONS`、`CFLOW_MACHINE_MAX_TRANSITIONS` 等作为 PUBLIC compile definitions 导出。

这意味着 consumer 编译看到的 public header configuration 必须与 library contract 一致。

同样，CMeta user relation/type lists属于 shared compile-time configuration。

文档明确要求：

> affected translation units 必须看到一致的 callable ABI/configuration。

所以 Multi-TU correctness 不只包括 same struct declaration，还包括 same finite signature universe、same compile-time configuration 和 same public feature/limit contract。

如果不同 TU 使用不同 relation universe，却共同交换 callable/descriptor object，行为可能从 semantic bug 变成 ABI bug。

---

### 5.7 Header / Source Boundary：哪些 Meta 必须留在调用点

Modern C meta library 不应该走向 everything header-only，也不应该走向 everything hidden in `.c`。

正确边界取决于信息在哪里存在。

### 5.8 必须在 Header / Call Site 的内容

典型包括 `_Generic` selection、compile-time type assertion、finite macro specialization、typed wrapper generation 和 call-site C type inspection，因为 C compiler 只在调用点知道 actual static C type。

### 5.9 应该放进 compiled C library 的内容

包括 container algorithms、Graph mutation/validation、Subscription runtime、Executor、Machine/Actor runtime、type identity comparison、optimizer、plan compiler 和 certificate checker。

这些没有理由因为“Meta”而被复制到每个 Translation Unit。

因此：

> **header-only typed façade 不等于 header-only implementation。**

这也是控制代码膨胀、ABI、compile time 和 debug experience 的关键。


### 5.10 Compiler capability 也是 public engineering boundary

第一到三章已经使用 finite PP、native typeof、same-type、zero-argument variadics、cleanup attribute 等能力。

这些能力不能在工程章节里被当成“编译器细节”。

Public header 如果根据 compiler / language mode 生成不同 guarantee，那么 consumer 的编译环境就是 contract 的一部分。

正确模型是：

~~~text
semantic requirement
        |
        v
compiler capability query
        |
   +----+----+
   |         |
supported   unsupported
   |         |
   v         v
strong      explicit weaker contract
surface     or compile failure
~~~

不能：

~~~text
feature unavailable
        |
        v
unsafe cast / guessed fallback
        |
        v
pretend guarantee is unchanged
~~~

例如需要分别 qualification：

| Capability | Engineering question |
|---|---|
| native typeof / same-type | 当前 C/C++ compiler mode 是否真正提供对应 type guarantee？ |
| zero-argument variadics | 是否处于公开支持 VA_OPT 的标准模式？ |
| cleanup attribute | backend 是否真的提供 lexical cleanup attribute？ |
| section / used attributes | ELF / COFF / Mach-O 是否有明确 backend contract？ |
| unique counter | 只用于 TU-local naming，不能成为 semantic identity |

因此 cross-compiler gate 不应该只问“GCC / Clang / MSVC 都能编译吗”。

它应该问：

~~~text
same semantic contract?
+
capability differences explicit?
+
unsupported paths fail honestly?
+
installed public headers preserve the same documented guarantee?
~~~

这也是 fail-fast 原则在 compiler abstraction 上的版本。

> **Portability 不是让所有 compiler 假装一样，而是让差异发生在一个显式、可测试的 capability boundary。**

## 6. Generated Artifact Ownership 与 Packaging

本书已经看到 `builtin_signature_manifest.h`、`builtin_operator_policy.h` 等 generated C headers；同类 artifact 应由 formal source/generator 单向生成并由 CI 检查。

工程规则必须非常严格：

| Artifact | 角色 |
|---|---|
| formal model | authoritative source |
| generated header | checked-in build artifact |
| manual edit generated header | forbidden |

普通 consumer build **does not require Lean**；CI / semantic development 运行 **generator --check** 验证 artifact 没有 drift。

这样同时得到 reproducible package、ordinary C consumer、single source of truth 和 reviewable generated diff。

---

### 6.1 Install / Export：源码树里能 link 远远不够

本版源码快照以 Salts 发行包提供标准 CMake package/export boundary：SaltsConfig.cmake、SaltsConfigVersion.cmake、SaltsTargets.cmake，并使用 Salts:: namespace。

CMeta / CFlow 分别 export 为 **Salts::CMeta** 与 **Salts::CFlow**，同时安装 public headers、library/archive/runtime artifact、package config 和 target export。

这里的 `Salts` 是包名与目标 namespace；正文中的库名仍为 CMeta / CFlow，CMeta Plugin 对应 `Salts::Plugin`。包名不会改变 `cmeta_*` / `CMETA_*` 这些公共符号。

consumer 的目标形态是：

~~~cmake
find_package(Salts CONFIG REQUIRED)

target_link_libraries(app PRIVATE
    Salts::CMeta
    Salts::CFlow)
~~~

这比依赖 source-tree add_subdirectory、source-tree include path 或随意链接某个 .a 文件重要得多。

因为 install boundary 会立刻暴露：

~~~text
missing public dependency
wrong include interface
private header leak
missing transitive target
wrong compile definition export
bad symbol visibility
source-tree-only path
~~~

### 6.2 CFlow 的 public dependency 必须通过 target contract 导出

本版 CFlow 实现 link contract包含：

~~~text
PUBLIC
    Salts::CMeta
    Salts::NativeIO
    Salts::Platform

PRIVATE
    Salts::Concurrency
~~~

这不是 CMake aesthetics。

它表达：

> external consumer 使用 CFlow public headers / symbols 时，哪些 dependency 是 exported contract，哪些只是 implementation detail。

如果 PRIVATE dependency 的 symbol 出现在 public ABI，却没有被 export，source-tree build 可能绿，而 installed consumer link 会失败。

### 6.3 Public header install 也必须排除 private headers

本版 CFlow install public cflow headers，同时显式排除 plan_internal.h 和 relation_exec.h。

这条边界很重要：

> **一个 header 放在仓库里，不代表它属于 SDK。**

如果 public header 偷偷 include private header，installed build 会最快把问题暴露出来。

---

### 6.4 Installed Consumer Qualification：最接近真实用户的 Gate

本书建议把 installed-consumer test 当成正式 gate，而不是 release 前手工冒烟。

推荐流程：

~~~text
clean source checkout
    ↓
configure/build/test Salts
    ↓
install into empty prefix
    ↓
new independent consumer source tree
    ↓
find_package(Salts CONFIG REQUIRED)
    ↓
link only exported Salts::* targets
    ↓
include only installed headers
    ↓
build
    ↓
run
~~~

consumer 至少覆盖：

- CMeta type/traits/callable；
- CFlow Graph/Stream；
- Multi-TU use；
- static build；
- shared build where supported；
- C/C++ header compatibility。

关键规则是 no source-tree include path、no build-tree target、no undeclared private library、no generated source file copied manually。

只有这样，才能证明：

> **“可安装 library”不是文档里的愿望，而是用户真正能拿到的 SDK contract。**

## 7. Qualification Across Boundaries

一个弱 Multi-TU test 只是 `foo.c calls bar.c`，这不足以验证 Meta identity。

真正有效的 test 要故意让两个 TU 各自拥有独立 representation。

### 7.1 Type Identity Test

~~~text
TU A:
    independently constructs Pair<A,B> identity

TU B:
    independently constructs Pair<A,B> identity

assert:
    addresses differ
    constructors may differ
    semantic equality true
~~~

本版 CMeta 实现 已经有这种 peer test。

### 7.2 Callable Identity Test

~~~text
TU A:
    canonical callable wrapper A

TU B:
    canonical callable wrapper B

assert:
    wrapper representation can differ
    authoritative raw target identity agrees
~~~

当前 tests 同样覆盖这一点。

### 7.3 Generated Configuration Test

还应覆盖 shared configuration header 在 TU A/TU B 中一致，以及 callable signature ABI 在两边一致，并增加 negative compile/link test：

~~~text
intentionally inconsistent configuration
    → fail fast
~~~

如果工具链无法可靠诊断，则至少让这种状态成为明确 unsupported contract，而不是 runtime 猜测。

---

### 7.4 Cross-Compiler：Core Semantics 不能建立在偶然扩展上

CMeta 可以使用 C11 `_Generic`、preprocessor、`_Static_assert` 和 standard alignment/type rules，并针对 MSVC 的 conforming preprocessor mode 配置必要 compiler option。

但书里需要保持一条原则：

> **Compiler extension 可以优化 implementation，但不能成为 semantic model 唯一基础。**

例如 GNU statement expression、`typeof` extension、compiler-specific section trick 可以做 optional fast path；

核心 type relation / callable semantics / ABI contract 应该仍能用支持目标 compiler 的正式机制表达。

Cross-compiler CI 的意义不是“语法都能编译”，而是验证 same declared semantics、same ownership/error contract 和 same installed API shape 在目标 compiler family 中保持成立。

---

### 7.5 ABI Qualification：不要只比较 sizeof(struct)

ABI test 的层次至少有四类。

### 7.6 Compile ABI

检查 public headers 能作为 C11 编译、能从 supported C++ mode 引用、macro 不依赖 include accident、generated headers 自洽。

本版 CFlow 实现 已有 public/header C++ compile tests，这类 gate应持续扩展。

### 7.7 Link ABI

检查 public symbol 存在、calling convention 匹配、transitive dependency 已导出、static/shared consumer 都能链接。

这是 installed consumer才能真正验证的部分。

### 7.8 Semantic ABI

即使 function signature 没变，如果 FULL suddenly starts dropping、CLOSED becomes retryable、Actor stale ref becomes INVALID_ARGUMENT 或 Graph mutation stops changing version，也属于 breaking behavior。

所以：

> **Status meaning、ownership、lifecycle、ordering、fallback 都属于 semantic ABI。**

### 7.9 Data ABI

对于真正承诺跨 binary boundary 的 struct，prefix fields、version、`struct_size`、enum values、alignment 和 pointed-data ownership 才需要正式版本化。而 opaque owner `void *impl` 就是为了避免把内部 layout 变成 ABI。

---

### 7.10 Fail-fast Across Boundaries：错误越晚越昂贵

全书反复出现的 fail-fast，在这里表示 **diagnostic-stage ordering**，不是 runtime pipeline：

~~~text
compile-time
    ↓ earlier is cheaper
build-time
    ↓
install/package-time
    ↓
link-time
    ↓
admission-time
    ↓
execution-time
~~~

原则是：

> **能在更早层发现，就不要把同一个错误留到更晚层。**

| Error | Earliest proper boundary |
|---|---|
| unsupported TypeFunction row | compile-time |
| invalid Machine schema | build-time |
| generated manifest drift | CI/generator check |
| missing public link dependency | installed consumer link |
| wrong Event payload | admission |
| I/O failure | execution |

把所有错误都变成 runtime error string，不叫“API 简单”。

那只是把诊断成本推给用户。

---

## 8. What We Learned

第十三章把前面所有“高级”能力重新压回普通 C 工程现实。

一个 Modern C abstraction 真正成熟，需要同时满足：

- semantic identity 不依赖 representation address；
- Multi-TU 能看到 compatible finite configuration；
- public ABI 区分 stable / read-only / internal fields；
- generated artifacts 只有一个 authority；
- ordinary build 不依赖 Lean；
- static/shared libraries 不依赖 duplicate-global coincidence；
- install/export 发布真实 dependency contract；
- external consumer 只依赖 installed SDK；
- cross-compiler 保持 core semantics；
- status / ownership / lifecycle 被当成 semantic ABI。

本版 Salts 快照已经有 structural type identity、cross-TU identity tests、cross-TU callable tests、CMake install/export、`Salts::*` imported targets、CFlow SOVERSION、public/private install headers、generated-header CI checks 和 public-header compile checks。

成熟 qualification 还应该持续把 independent installed consumer、static/shared matrix、negative ABI/config tests、platform/toolchain matrix 和 release compatibility 当成正式 gate。

Lean 在这一章的位置也变得非常清楚。

它可以帮助定义 semantic identity、finite schema、generated manifest 和 protocol invariants；但 linker、loader、symbol visibility、CMake package export、compiler ABI 与 shared-library resolution 必须用真实工具链验证。

这不是形式化能力不足。

而是：

> **正确的问题应该由正确的证据回答。**

到这里，Part IV 的可信边界可以概括为：

| 层 | Trusted boundary |
|---|---|
| Machine / Actor / protocol semantics | semantic/proof boundary |
| ABI / Multi-TU / package | binary/toolchain/package boundary |

下一章不再增加新的基础机制，而是反过来检查：

> **这些 abstraction 什么时候根本不值得使用？什么时候一个 loop、一个 function pointer、一个 switch 或一次 direct link 已经更好？**

这就是 Restraint：只有删除的稳定重复足以覆盖长期成本时，才继续抽象。
