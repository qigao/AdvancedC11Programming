# 第六章：计算图的语义与改写证明

优化器可以减少调用次数，但删掉一次调用是否正确，取决于这次调用可能产生什么可观察行为。CMeta 的性质标志为规则匹配提供事实声明，CFlow 的语义模型与证明说明这些声明在什么条件下足以授权改写。本章从一个可手算的函数出发，连接 C 实现、列表语义、Lean 定理和具体改写记录。

## 1. 一个可验证的幂等函数

下面的完整函数把整数限制在 `[0, 100]` 内；它不执行算术运算，不会因极端 `int` 输入而溢出。

~~~c
int clamp100(int x)
{
    if (x < 0)
        return 0;
    if (x > 100)
        return 100;
    return x;
}
~~~

**幂等（idempotent）**表示再次应用函数不会改变第一次的结果，即 `f(f(x)) = f(x)`。对 `clamp100` 可分三种情况证明：负输入第一次得到零，第二次仍为零；大于一百的输入第一次得到一百，第二次仍为一百；区间内输入两次均原样返回。三个分支覆盖所有 `int`，所以该定律在整个 `int` 域成立。

这不是递归：函数体没有调用自身。计算图中连续两个 Map 节点，对一个输入执行的表达式恰好是 `clamp100(clamp100(x))`。幂等律允许考虑删除其中一个节点。

## 2. 先确定比较哪些观察结果

仅比较最终数值会漏掉日志、错误和清理行为。**观察语义（observational semantics）**规定外部观察者可以区分哪些结果。本章使用模型中的值序列、效果记录、终止结果和所有权安全信息。实现测试还需检查其对应的回调顺序与资源行为。

| 行为 | 两次 Map 与一次 Map 是否自然相同 |
|---|---|
| `clamp100` 的输出值 | 根据上节证明相同 |
| 每次调用打印一行日志 | 不同：日志条数变化 |
| 每隔一次调用返回错误 | 不同：调用次数影响错误 |
| 每次调用取得并释放资源 | 需要额外的效果与所有权论证 |

**纯函数（pure function）**在这里不产生模型所关注的外部效果；**全函数（total function）**在允许的输入域内都有正常定义的结果。C 函数还可能有未定义行为，不能仅凭源代码里存在 `return` 就声称 total。第一节的分支函数容易建立这些条件，任意回调则需要单独验证。

## 3. 从单值定律推到整个流

对有限列表 `xs`，`map(f, xs)` 按原顺序对每个元素应用 `f`。目标是证明：

~~~text
map(f, map(f, xs)) = map(f, xs)
assuming: for every admitted x, f(f(x)) = f(x)
~~~

空列表两侧都为空。若 `xs = h :: t`，左侧的首元素为 `f(f(h))`，由幂等律等于 `f(h)`；余下列表由归纳假设相等。因此首元素和尾部都相等，整个列表相等。`h :: t` 表示把头元素 `h` 放在尾列表 `t` 前面。

上述推导只处理值序列。要把结论提升为完整 StreamResult 相等，还需模型中的纯性、全性及其他前提，使效果、终止与所有权观察保持一致。固定快照的定理把这些条件组织为 `IdempotentEndomapPremises`。**Endomap（同类型映射）**是输入和输出具有同一类型的映射，否则 `f(f(x))` 未必有类型意义。

## 4. Lean 定理实际证明什么

下面摘录固定快照中已有的定理。`premises` 是满足条件的语义解释，`stream` 是模型结果；这里没有给任意 C 函数指针自动附加一个已证明的数学含义。

~~~lean
theorem map_idempotent_elimination {Γ : Env} {ty : Ty}
    (premises : IdempotentEndomapPremises Γ ty)
    (stream : StreamResult (Value ty)) :
    (stream.map premises.meaning.apply).map premises.meaning.apply =
      stream.map premises.meaning.apply := by
  cases stream
  simp [StreamResult.map,
    list_map_idempotent premises.meaning.apply premises.idempotentLaw]
~~~

`cases stream` 展开结果结构，`simp` 使用流映射定义和已经证明的列表引理化简等式。上节的归纳解释了关键引理的数学内容。定理来自 [Proofs/Rewrite.lean](https://github.com/qigao/salts/blob/a650262031e9b3e5f11a227a7911a75db9ae1fb8/formal/cmeta_cflow_calculus/CMetaCFlowCalculus/Proofs/Rewrite.lean)；本章的 C 分支论证是手工证明，并未新增机器检查过的 C 实现验证。

`IDEMPOTENT` 标志只能声明某个函数应满足该性质。若函数实际上每次增加一个全局计数器，错误的元数据不会被上述定理纠正。把实现与语义解释对应起来，仍是调用提供方、代码生成器和验证工作的责任。

## 5. 从通用定理到一次具体改写

**改写记录（rewrite trace）**保存具体改写发生的位置与依据。它与定理的职责不同：定理说明规则在前提下成立，记录说明本次输入图上应用了哪条规则。以下伪代码展示这种配合，不是 SDK 函数的逐字实现。

~~~text
remove_duplicate_map(graph, candidate):
    require candidate contains two consecutive Map nodes
    require the same admitted callable meaning at both nodes
    require the callable is a pure, total endomap
    require an authorized idempotence law for that meaning
    build a new graph with one Map removed
    validate the new graph
    record rule, source identity, target identity, and affected nodes
    publish graph and record together
~~~

两个函数指针相等不足以单独证明完整调用相同：捕获值、签名和语义条件也必须一致。反过来，两个函数名字相同也不构成实现身份。记录需要绑定实际输入与输出快照，避免把旧图上的证明依据用在已经修改的图上。

快照中的 `IDEMPOTENT_MAP_ELIMINATION` 标识这项规则，相关记录包含保留与移除节点、可调用对象索引和子图信息。运行时检查器只能检查它理解的规则；遇到未知记录应拒绝，而不是忽略。

## 6. 多步改写为何仍保持语义

若第一次改写证明 `observe(G0) = observe(G1)`，第二次证明 `observe(G1) = observe(G2)`，则由等式传递性得到 `observe(G0) = observe(G2)`。对有限改写序列归纳，结论扩展到最终图。固定快照的 `certified_rewrite_preserves_observations` 对模型中的认证改写组合给出这类结论。

实现必须确保两份记录中间的 `G1` 确实是同一个受检产物。若第一份记录指向旧版本，第二份指向后来修改的图，即使各自规则名称正确，也不能拼成这条证明链。版本、结构匹配和明确的借用生存期共同约束这种连接。

融合两次 Map 是另一条规则：`map(g, map(f, xs))` 与 `map(g ∘ f, xs)` 保持值的相对次序。函数合成 `g ∘ f` 是先执行 `f`，再执行 `g`；带错误或外部效果的实现必须服从更完整的观察条件。不能从数值等式直接推出所有执行形式可交换。

## 7. 生成表、检查器与可信范围

**精化（refinement）**是用更具体的表示或执行步骤实现抽象语义，并证明约定的观察没有改变。将图编译为计划属于这种对应关系；它不等于重新证明每个 C 回调的机器码。

固定快照把部分内建签名与算子策略导出为生成头文件，例如 `builtin_signature_manifest.h` 和 `builtin_operator_policy.h`。普通 C 构建使用这些产物，不意味着每次编译 C 都运行 Lean。验证发布时，需要检查形式工程、生成工具和提交的产物是否相互对应。

| 层次 | 可提供的证据 | 仍需承担的假设 |
|---|---|---|
| 数学模型与 Lean 定理 | 指定前提下的语义等式 | 模型定义确实表达目标性质 |
| 规则与产物检查器 | 本次改写符合支持的形式和快照 | 检查器实现正确，输入存储有效 |
| C 执行与回调 | 编译、差分运行、失败路径测试 | 回调实现、ABI、工具链及生存期契约 |

证明的可信范围应随主张写清。安全性说明坏事不会发生，例如已拒绝的调用不执行；进展性说明工作最终完成。外部源永远不提供数据时，类型保持和改写证明都不能保证等待最终结束。

## 8. 验证与练习

对 `clamp100`，至少覆盖 `INT_MIN`、`-1`、`0`、`50`、`100`、`101`、`INT_MAX`，检查一次与两次调用相同。这些测试帮助发现实现偏离分支证明，但不能用有限样本替代全域论证。图级检查应比较原图与改写图的值、次序、终止和资源行为，并包含检查器能够识别的不一致元数据及过期记录的拒绝测试。

作为练习，把函数改为“限制范围后增加日志计数”。先证明输出值仍幂等，再指出完整观察为什么不同。这个反例迫使读者明确：授权删除节点的是一组语义条件，而不是一个性质名称。

## 9. 小结

一次正确优化需要对应的 C 行为、明确的观察模型、满足前提的规则以及绑定具体产物的改写记录。单值规律可通过归纳推广为流规律，多步改写可通过传递性组合；两项推导都依赖中间对象和前提保持有效。性质标志帮助筛选候选规则，不能独自证明任意实现符合该规则。
