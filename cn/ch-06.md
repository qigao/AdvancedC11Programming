# 第六章：Graph 的可信语义——从 Observable Semantics 到 Verified Rewrite

> **形式证明不是“Graph 很高级”的装饰。**
>
> 它只在一个具体问题出现时进入：optimizer 想把程序 P 改成 Q。此时必须回答：**对所有 admitted input，P 与 Q 的 observable result 是否相同？**

---

## 1. Property Claim 不是 Rewrite Authority

**Idempotent（幂等）**在这里表示对允许的输入满足 `f(f(x)) = f(x)`。这是关于函数行为的性质；声明一个 `IDEMPOTENT` 标志只是提出该性质成立的主张，尚未提供证明。

假设 metadata 写：

~~~c
clamp.properties |= IDEMPOTENT;
~~~

optimizer 想消除两个**串行**的 Map 节点。

先把数据流写完整：

~~~text
输入 x
  |
  v
Map(clamp)
  |
  | y = clamp(x)
  v
Map(clamp)
  |
  | z = clamp(y)
  v
输出 z
~~~

这里的关系是：

~~~text
Graph 层：
    两个 Map 节点按顺序执行
    = sequential composition

单个元素展开：
    y = clamp(x)
    z = clamp(y)
      = clamp(clamp(x))
    = nested function application

递归：
    不是。
    clamp() 的函数体并没有调用 clamp() 自己。
~~~

如果用函数复合表示，一般来说：

~~~text
Map(f) -> Map(g)

对单个元素 x 等价于：

g(f(x))

也就是：

Map(g) after Map(f)
    = Map(g ∘ f)
~~~

这里 f = g = clamp，所以：

~~~text
Map(clamp) -> Map(clamp)
    = Map(clamp ∘ clamp)
~~~

optimizer 希望利用幂等律把它改写成：

~~~text
输入 x
  |
  v
Map(clamp)
  |
  | z = clamp(x)
  v
输出 z
~~~

仅有 `IDEMPOTENT` bit 不够。

真正需要的 law：

~~~text
∀x, clamp(clamp(x)) = clamp(x)

也就是：

clamp ∘ clamp = clamp
~~~

所以两者职责不同：

| 对象 | 作用 |
|---|---|
| property bit | admission claim |
| semantic theorem | rewrite authority |

---

## 2. 先定义 Observable Semantics

对纯 data-flow pipeline，可以定义一个简化 evaluator：

~~~text
eval(Source(xs)) = xs

eval(Filter(p, s)) =
    [x in eval(s) | p(x)]

eval(Map(f, s)) =
    [f(x) | x in eval(s)]

eval(Reduce(r, z, s)) =
    foldl(r, z, eval(s))
~~~

这不是 runtime implementation，而是 **specification semantics**。只有先知道什么可观察，才能说 rewrite preservation。

---

## 3. Rewrite Judgment

把 optimizer rule 写成：

~~~text
Γ ⊢ P ~> Q
~~~

并要求：

~~~text
Γ ⊢ admitted(P)
Γ ⊢ rewrite_preconditions(P,Q)
Γ ⊢ ∀input, observe(eval(P,input))
             = observe(eval(Q,input))
────────────────────────────────────────
Γ ⊢ P ~> Q : sound
~~~

对于 idempotent map，先固定记号：

~~~text
Map(f); Map(f)
~~~

其中分号表示**pipeline 中先执行左边 Map，再执行右边 Map**，不是递归。

对任意单个输入 x：

~~~text
x
 -> first Map(f)
 -> f(x)
 -> second Map(f)
 -> f(f(x))
~~~

因此 rewrite rule 是：

~~~text
IDEMPOTENT(f)
∧ theorem ∀x, f(f(x)) = f(x)
────────────────────────────────
Map(f); Map(f)  ~>  Map(f)
~~~

metadata 只帮助选择候选。

theorem 决定是否允许重写。

---

## 4. Lean Theorem 必须绑定具体 Transformation

概念 theorem：

~~~text
theorem map_idempotent_preserves_eval
    (hf : ∀ x, f (f x) = f x) :
    eval (Map f (Map f s))
    =
    eval (Map f s)
~~~

C optimizer 使用它的方式不是“运行 Lean”，而是走一条 **proof-to-optimizer registration pipeline**；箭头表示 artifact/authority 传递，不是 runtime dataflow：

~~~text
Lean source
    ↓ prove theorem
approved rule manifest
    ↓ register authorized rule
C optimizer matcher
    ↓ apply matching rule
rewrite
~~~

普通 build 不依赖 theorem prover。

---

## 5. Proof Trace 与 Certificate

**术语说明：** refinement（精化）说明具体实现怎样满足抽象模型规定的行为；本章重点是保持已定义的可观察结果。certificate（证书）是供检查器核对具体产物与获准规则之间关系的证据记录，不是安全认证证书。fingerprint（指纹）是用于关联或区分产物的内容摘要，本身不是语义等价证明。

rewrite 时记录 rule id、input Graph fingerprint、output Graph fingerprint、required property ids 和 proof/certificate version。

例如：

~~~c
typedef struct rewrite_trace {
    uint32_t rule_id;
    uint64_t before_hash;
    uint64_t after_hash;
    uint32_t certificate_version;
} rewrite_trace;
~~~

Trace 回答“发生了哪次 rewrite？”，Certificate 回答“这个具体 artifact 是否满足已批准的 refinement relation？”。两者不是同一个东西。

---

## 6. Trusted Boundary

证据分层：

| Claim | Evidence |
|---|---|
| property declared | C metadata / generator |
| rewrite law valid | Lean theorem |
| optimizer used approved rule | trace / matcher test |
| generated C matches plan | differential/refinement test |
| ABI works | compile/link/install |
| faster | benchmark |

不要用 Lean theorem 证明 ABI，不要用有限 unit test 代替所有输入上的语义等价证明，也不要用 benchmark 证明 correctness。

---

## 7. Failure Cases

### Claim but no theorem

如果存在 `IDEMPOTENT` bit，但没有可用 proof rule，就返回 `NO_REWRITE`。

### Stale certificate

如果 Graph fingerprint 已改变而 certificate 仍绑定旧 fingerprint，就返回 `REJECT_CERTIFICATE`.

### Unsupported observation model

如果 rewrite 可能改变 encounter order、error timing、side effects 或 allocation observation，而 semantics 没有定义这些是否可观察，就 **rewrite not admitted**。

不要通过一句“PURE”把缺失的 semantics 猜出来。

后半章从具体 Idempotent Map case 开始，把这一条 trusted chain 走到底。

## 8. Case Study A：Idempotent Map——从 Property Claim 到 Verified Rewrite

第七章将继续使用这个**串行组合**：

~~~text
x
 |
 v
Map(clamp)
 |
 | y = clamp(x)
 v
Map(clamp)
 |
 | z = clamp(y) = clamp(clamp(x))
 v
z
~~~

它不是递归。两个 Graph node 分别调用一次同一个普通 C 函数。

如果幂等律成立：

~~~text
∀x, clamp(clamp(x)) = clamp(x)
~~~

则可以重写为：

~~~text
x
 |
 v
Map(clamp)
 |
 | z = clamp(x)
 v
z
~~~

这个例子可以把整条 trusted chain 走完整。

### 8.1 Claim

C metadata 可以声明 `IDEMPOTENT`。

它只表示：

> 这个 callable 被 admission 层声明为可参与 idempotent rule。

如果 claim 是手写的，它本身不是 proof。

### 8.2 Semantic Law

真正需要的是：

~~~text
forall x,
clamp (clamp x) = clamp x
~~~

这才是 rewrite premise。

### 8.3 Rule theorem

当前 formal Rewrite proof 已经有 `map_idempotent_elimination`。它的直接 premise 不是一个裸的 property bit，而是 `IdempotentEndomapPremises Γ ty`，其中包含被信任/建模的 callable meaning 以及真正的 idempotent law。

更一般的 `certified_rewrite_preserves_observations` 对有限组合的 certified rewrites 建立 observation preservation。

这类 theorem 回答：

> 如果 callable meaning 与对应 semantic law 已经进入 theorem premise，那么删除重复 Map preserve observable stream semantics。

注意 theorem 证明的是 rule。

它不是在每一次运行时重新证明 concrete C function。

### 8.4 Concrete rewrite instance

当前 C optimizer 的 property rewrite 可以产生稳定 rule id `IDEMPOTENT_MAP_ELIMINATION`，并在 proof trace 中记录 source subgraph、retained node/callable 和 removed node/callable。

Trace 回答：

> 这一次 optimized Graph 具体在哪个 source coordinate 应用了哪个 rule？

两者职责不同：

| 对象 | 作用 |
|---|---|
| Lean theorem | proof of rule |
| C trace | record of rule instance |

### 8.5 Trace checker / AOT matcher

后续 checker 可以验证：

- trace 绑定 exact source Graph/version；
- trace 绑定 exact optimized Graph/version；
- rule id supported；
- source/target coordinates match；
- final optimized structure matches expected Stage IR。

于是 trusted path 是一条 **evidence/authority chain**：

~~~text
Semantic Law
    ↓ proves rule sound
Lean rule theorem
    ↓ authorizes rule id
C optimizer applies rule
    ↓ records instance
Proof Trace
    ↓ checked against artifacts
Trace/IR checker
~~~

相反，下面是明确的 anti-pattern：

~~~text
property bit set
    ↓ no semantic proof
optimizer deletes node
~~~

后者把 metadata claim 错当成 rewrite authority。

---

Part IV 的 Reactive、Machine 与 Actor 会复用同样的 proof discipline：先定义 observable/state semantics，再证明有限 law，最后用 C implementation + race/sanitizer tests 验证 refinement。

但这些 stateful protocol 不属于本章的 LINQ/Graph 主线，因此不在这里提前展开。

## 9. Manifest：Lean 怎样进入普通 C，而不进入普通 C Build

形式化如果要求每个应用 consumer 都安装 Lean，工程边界就失败了。

本版 Salts 快照 已经采用 checked-in generated artifact 模式。

### 9.1 Builtin Signature Manifest

Lean 验证有限 builtin type/signature relation，然后生成 `cmeta/include/cmeta/generated/builtin_signature_manifest.h`。

普通 C/C++ build 只 includes checked-in header，**does not run Lean**。CI / semantic developer workflow 才运行 **cmeta-signature-gen --check**。

确保：

~~~text
formal source
    ↔
checked-in C artifact
~~~

没有漂移。

### 9.2 Builtin Operator Policy

同样，CFlow operator policy 的有限 relation 由 formal package 检查，并生成 `cflow/include/cflow/generated/builtin_operator_policy.h`。

这样 C optimizer/runtime 消费普通 C table/header，而不是在 hot path 调 theorem prover。

### 9.3 Generator 也是 trusted bridge

这里必须诚实：

如果 theorem 正确，但 generator 把结果错误地翻译成 C header，普通 C build仍然可能错误。

因此 trusted bridge 至少包括 formal definitions/theorems、generator mapping、generated-artifact check 和 C consumer interpretation。

所以 generated header 应该：

- 尽量简单；
- 可读；
- diff-friendly；
- CI 可重生成/check；
- 不允许手工修改成为第二事实源。

## 10. Certificate 与 Proof Trace：两个不同的 Runtime Bridge

这两个概念经常被混在一起。

### 10.1 Proof Trace

回答：

> optimized Graph 为什么从 source Graph 变成现在这样？

它记录 rewrite rule id、source coordinate、retained/removed node、callable coordinate 和 source/output Graph binding。Trace 是一个 **Transformation Witness**。

### 10.2 Certificate

回答：

> 这个 Plan / execution path 是否仍然对应被批准的 normalized/optimized semantic program？

它记录 Graph version/fingerprint、certified opcode rows、types、callables、effects/properties、execution path、ordering 和 required capabilities。Certificate 是一个 **Execution Artifact Witness**。

因此可信链不是二选一，而是：

~~~text
Source Graph
    ↓
Optimizer
    ↓
Proof Trace
    ↓
Optimized Graph
    ↓
Plan Compile
    ↓
Certificate
    ↓
Execution
~~~

如果将来需要更强 assurance，可以分别加强 trace checker、certificate checker、artifact identity 和 generator provenance，而不需要把整个 runtime 改造成 theorem prover。

## 11. Formal Trusted Base 与 Execution Trusted Base 必须分开

讨论“trusted computing base”时必须指定层次。

### 11.1 Formal proof trusted base

至少包括 formal definitions、theorem statements/premises、Lean checker/kernel/toolchain assumptions，以及 semantic model itself。

一个 theorem 只能相对于它的 model/premises 正确。

如果 observable semantics 定义错了，proof 可以 perfectly valid，却仍然 prove the wrong thing。所以 specification review 与 theorem proof 同样重要。

### 11.2 Bridge trusted base

Bridge trusted base 包括 generators、rule-id mapping、trace construction/checking、certificate construction/checking 和 type/callable identity mapping。这些把 formal world 连到 C artifact。

### 11.3 Execution trusted base

Execution trusted base 包括 C compiler/linker、C implementation、allocator/thread primitives、OS/runtime、hardware 和 borrowed callback/user code。

只有其中被 formalized/refined 的部分，才能获得对应 theorem 的 guarantee；其他部分需要 tests、sanitizers、ABI qualification、stress、platform CI 和 benchmark。

### 11.4 External liveness assumptions

“OS eventually schedules worker”、“socket eventually becomes ready”、“device eventually completes”、“user callback eventually returns”通常是环境 assumption，而不是 CMeta/CFlow theorem。

书里必须显式标注这种假设。

这样才不会把 safety proof 写成“系统永远不会卡住”的过度承诺。

---

## 12. Proof / Test / Runtime Check 的协作方式

一个成熟 feature 不应该问“proof 还是 test？”，而应该问：

> **这条 claim 分别在哪几个层次需要证据？**

以 idempotent rewrite 为例：

~~~text
Semantic law
    → Lean theorem

Concrete optimizer event
    → proof trace

Graph/optimized binding
    → trace checker

Plan binding
    → certificate

C implementation regression
    → differential tests

memory/lifetime
    → sanitizer

performance benefit
    → benchmark
~~~

以 Reactive demand 为例：

~~~text
demand mathematical invariant
    → Lean

runtime state mapping
    → conformance tests

wake/cancel race
    → stress/readiness tests

scheduler capacity behavior
    → bounded protocol tests

latency/throughput
    → benchmark
~~~

因此真正专业的 verification stack 是：

~~~text
Formal proof
+
Generated facts
+
Runtime admission
+
Differential testing
+
Memory/concurrency testing
+
ABI/platform qualification
+
Measurement
~~~

不是其中任意一个单独称霸。

## 13. What We Learned

本章真正建立的是全书的可信方法，而不是“Lean 章节”。

现在可以把证据链压缩成：

~~~text
Claim
    ↓
Semantic Definition
    ↓
Proof Obligation
    ↓
Lean Theorem
    ↓
Generated/Registered Rule
    ↓
Concrete Trace
    ↓
Artifact Certificate
    ↓
C Runtime
    ↓
Differential / Sanitizer / ABI Evidence
    ↓
Benchmark
~~~

但不是每个 feature 都必须经过所有层。

原则是：

> **用最适合的证据证明对应层次的 claim。**

三个真实 case 已经展示不同用法：

~~~text
Optimizer:
    theorem licenses transformation

Reactive:
    theorem shapes execution state machine

Machine:
    theorem constrains build/commit semantics
~~~

而 Manifest 展示的是 **generation relation**：formal knowledge 生成 checked-in ordinary C artifact，而不是 runtime 从 Lean “流向” C。

这使 Lean 真正成为：

> **Modern C control/trust plane 的设计与验证工具，而不是一个新的 runtime dependency。**

下一章继续留在 Execution IR，但把问题从“rewrite 是否正确”推进到“如何让执行更便宜”：

> **已经通过语义验证的 Graph，怎样 normalize、optimize、compile 成 Plan / Direct，让 hot path 尽量回到普通 C？**

这就是从 trusted semantics 进入 lowering。
