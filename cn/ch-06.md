# 第六章：计算图的语义与改写证明

优化器删除或合并节点会改变实际执行的函数调用。要判断变换是否正确，必须先说明程序允许观察什么，再证明这些观察在变换前后相同。本章以连续两次 Map 的幂等改写为例，从函数等式推导图的等价关系，解释 CMeta 性质声明、Lean 定理和 C 优化器检查各自承担的工作。

## 1. Property Claim 不是 Rewrite Authority

**Idempotent（幂等）**在这里表示对允许的输入满足 `f(f(x)) = f(x)`。这是关于函数行为的性质；声明一个 `IDEMPOTENT` 标志只是提出该性质成立的主张，尚未提供证明。

假设元数据写：

~~~c
clamp.properties |= IDEMPOTENT;
~~~

optimizer 想消除两个**串行**的 Map 节点。先把数据流写完整：

~~~text
输入 x
  |
  v
Map(clamp)
  |
  | y = clamp(x)
  v
Map(clamp)
  |
  | z = clamp(y)
  v
输出 z
~~~

这里的关系是：

~~~text
Graph 层：
    两个 Map 节点按顺序执行
    = sequential composition

单个元素展开：
    y = clamp(x)
    z = clamp(y)
      = clamp(clamp(x))
    = nested function application

递归：
    不是。
    clamp() 的函数体并没有调用 clamp() 自己。
~~~

如果用函数复合表示，一般来说：

~~~text
Map(f) -> Map(g)

对单个元素 x 等价于：

g(f(x))

也就是：

Map(g) after Map(f)
    = Map(g ∘ f)
~~~

这里 f = g = clamp，所以：

~~~text
Map(clamp) -> Map(clamp)
    = Map(clamp ∘ clamp)
~~~

optimizer 希望利用幂等律把它改写成：

~~~text
输入 x
  |
  v
Map(clamp)
  |
  | z = clamp(x)
  v
输出 z
~~~

仅有 `IDEMPOTENT` bit 不够。真正需要的 law：

~~~text
∀x, clamp(clamp(x)) = clamp(x)

也就是：

clamp ∘ clamp = clamp
~~~

所以两者职责不同：

| 对象 | 作用 |
|---|---|
| property bit | 准入检查主张 |
| semantic 定理 | 改写 authority |

## 2. 先定义 Observable Semantics

对纯 data-flow pipeline，可以定义一个简化 evaluator：

~~~text
eval(Source(xs)) = xs

eval(Filter(p, s)) =
    [x in eval(s) | p(x)]

eval(Map(f, s)) =
    [f(x) | x in eval(s)]

eval(Reduce(r, z, s)) =
    foldl(r, z, eval(s))
~~~

这不是运行时 implementation，而是 **specification semantics**。只有先知道什么可观察，才能说改写 preservation。

## 3. Rewrite Judgment

把 optimizer rule 写成：

~~~text
Γ ⊢ P ~> Q
~~~

并要求：

~~~text
Γ ⊢ admitted(P)
Γ ⊢ rewrite_preconditions(P,Q)
Γ ⊢ ∀input, observe(eval(P,input))
             = observe(eval(Q,input))
────────────────────────────────────────
Γ ⊢ P ~> Q : sound
~~~

对于 idempotent map，先固定记号：

~~~text
Map(f); Map(f)
~~~

其中分号表示**pipeline 中先执行左边 Map，再执行右边 Map**，不是递归。对任意单个输入 x：

~~~text
x
 -> first Map(f)
 -> f(x)
 -> second Map(f)
 -> f(f(x))
~~~

因此改写 rule 是：

~~~text
IDEMPOTENT(f)
∧ theorem ∀x, f(f(x)) = f(x)
────────────────────────────────
Map(f); Map(f)  ~>  Map(f)
~~~

元数据只帮助选择候选。定理决定是否允许重写。

## 4. Lean Theorem 必须绑定具体 Transformation

概念定理：

~~~text
theorem map_idempotent_preserves_eval
    (hf : ∀ x, f (f x) = f x) :
    eval (Map f (Map f s))
    =
    eval (Map f s)
~~~

C optimizer 使用它的方式不是“运行 Lean”，而是走一条 **证明-to-optimizer registration pipeline**；箭头表示 artifact/authority 传递，不是运行时数据流：

~~~text
Lean source
    ↓ prove theorem
approved rule manifest
    ↓ register authorized rule
C optimizer matcher
    ↓ apply matching rule
rewrite
~~~

普通 build 不依赖定理 prover。

## 5. Proof Trace 与 Certificate

**术语说明：** refinement（精化）说明具体实现怎样满足抽象模型规定的行为；本章重点是保持已定义的可观察结果。certificate（证书）是供检查器核对具体产物与获准规则之间关系的证据记录，不是安全认证证书。fingerprint（指纹）是用于关联或区分产物的内容摘要，本身不是语义等价证明。

改写时记录 rule id、input Graph fingerprint、output Graph fingerprint、required property ids 和证明/certificate version。例如：

~~~c
typedef struct rewrite_trace {
    uint32_t rule_id;
    uint64_t before_hash;
    uint64_t after_hash;
    uint32_t certificate_version;
} rewrite_trace;
~~~

Trace 回答“发生了哪次改写？”，Certificate 回答“这个具体 artifact 是否满足已批准的 refinement relation？”。两者不是同一个东西。

## 6. Trusted Boundary

证据分层：

| Claim | Evidence |
|---|---|
| property declared | C metadata / generator |
| rewrite law valid | Lean theorem |
| optimizer used approved rule | trace / matcher test |
| generated C matches plan | differential/refinement test |
| ABI works | compile/link/install |
| faster | benchmark |

不要用 Lean 定理证明 ABI，不要用有限 unit test 代替所有输入上的语义等价证明，也不要用 benchmark 证明 correctness。

## 7. Failure Cases

### Claim but no theorem

如果存在 `IDEMPOTENT` bit，但没有可用证明 rule，就返回 `NO_REWRITE`。

### Stale certificate

如果 Graph fingerprint 已改变而 certificate 仍绑定旧 fingerprint，就返回 `REJECT_CERTIFICATE`.

### Unsupported observation model

如果改写可能改变 encounter order、错误发生时机、副作用或分配行为，而语义模型没有说明这些是否可观察，那么该改写就**不能准入**。不能用一个 `PURE` 标志去猜测缺失的语义。后半章从具体的 Idempotent Map 例子出发，把这条可信链完整走一遍。

## 8. 当前实现怎样对应这条推导

前七节已经完成了这条改写的语义推导，因此这里不再重新展开 `clamp(clamp(x)) = clamp(x)`。需要确认的是：固定源码快照里的形式化对象、优化器规则和 trace 是否与前面的推导一一对应。

当前 formal Rewrite 证明包含 `map_idempotent_elimination`。它的前提不是一个裸的 `IDEMPOTENT` bit，而是 `IdempotentEndomapPremises Γ ty`：其中包含被建模的 callable meaning 与真正的幂等定律。更一般的 `certified_rewrite_preserves_observations` 则说明，有限组合的 certified rewrite 在满足前提时保持约定的观察结果。

C 侧使用稳定 rule id `IDEMPOTENT_MAP_ELIMINATION` 标记这类改写，并在 Proof Trace 中记录具体 source subgraph、保留的 node/callable 以及被删除的 node/callable。于是同一条改写在不同层次上有四个不同对象：

| 层次 | 具体对象 | 责任 |
|---|---|---|
| CMeta metadata | `IDEMPOTENT` | 把 callable 列为候选，不提供证明 |
| Lean | `map_idempotent_elimination` | 证明 rule 在前提下保持语义 |
| C optimizer | `IDEMPOTENT_MAP_ELIMINATION` | 在具体 Graph 上应用已授权规则 |
| Proof Trace / checker | source/target coordinates + rule id | 证明“这一次”改写确实匹配批准的 rule |

因此 checker 要验证的不是“bit 是否存在”，而是 trace 是否绑定精确的 source Graph/version 与 optimized Graph/version、rule id 是否受支持、source/target coordinate 是否匹配，以及最终结构是否符合预期 Stage IR。

这也给出明确的反例：如果 metadata 声明 `IDEMPOTENT`，却没有对应 theorem/authorized rule，optimizer 必须保持原 Graph；如果 trace 已经陈旧或无法绑定当前 Graph，也必须拒绝，而不是把 property bit 当成改写授权。

## 9. Manifest：Lean 怎样进入普通 C，而不进入普通 C Build

形式化如果要求每个应用使用方都安装 Lean，工程边界就失败了。本版 Salts 快照已经采用 checked-in generated artifact 模式。

### 9.1 Builtin Signature Manifest

Lean 验证有限的 builtin type/签名关系，并生成 `cmeta/include/cmeta/generated/builtin_signature_manifest.h`。普通 C/C++ 构建只包含仓库中已保存的 header，**不会运行 Lean**。只有 CI 或语义开发流程运行 **`cmeta-signature-gen --check <path>`**，检查生成结果与仓库中的 header 是否一致：

~~~text
formal source
    ↔
checked-in C artifact
~~~

没有漂移。

### 9.2 Builtin Operator Policy

同样，CFlow operator policy 的有限 relation 由 formal package 检查，并生成 `cflow/include/cflow/generated/builtin_operator_policy.h`。这样 C optimizer/运行时消费普通 C table/header，而不是在热路径调定理 prover。

### 9.3 Generator 也是 trusted bridge

这里必须诚实：

如果定理正确，但生成器把结果错误地翻译成 C header，普通 C build仍然可能错误。因此 trusted bridge 至少包括 formal definitions/theorems、生成器 mapping、generated-artifact check 和 C 使用方 interpretation。所以 generated header 应该：

- 尽量简单；
- 可读；
- diff-friendly；
- CI 可重生成/check；
- 不允许手工修改成为第二事实源。

## 10. Certificate 与 Proof Trace：两个不同的 Runtime Bridge

这两个概念经常被混在一起。

### 10.1 Proof Trace

回答：

> optimized Graph 为什么从 source Graph 变成现在这样？

它记录改写 rule id、source coordinate、retained/removed node、callable coordinate 和 source/output Graph binding。Trace 是一个 **Transformation Witness**。

### 10.2 Certificate

回答：

> 这个 Plan / execution path 是否仍然对应被批准的 normalized/optimized semantic program？

它记录 Graph version/fingerprint、已认证的操作码条目、types、callables、effects/properties、execution path、ordering 和 required capabilities。这里的 witness（见证）是供检查器使用、表明具体执行产物满足所需关系的证据记录。Certificate 把产物与图、规则及执行条件关联起来；它不只是声称“编译成功”的标志。因此可信链不是二选一，而是：

~~~text
Source Graph
    ↓
Optimizer
    ↓
Proof Trace
    ↓
Optimized Graph
    ↓
Plan Compile
    ↓
Certificate
    ↓
Execution
~~~

如果将来需要更强 assurance，可以分别加强 trace checker、certificate checker、artifact identity 和生成器 provenance，而不需要把整个运行时改造成定理 prover。

## 11. Formal Trusted Base 与 Execution Trusted Base 必须分开

讨论“trusted computing base”时必须指定层次。

### 11.1 Formal proof trusted base

形式化可信基至少包括：形式定义、定理陈述与前提、Lean checker/kernel/toolchain 的假设，以及语义模型本身。定理只能相对于自己的模型和前提成立；如果可观察语义定义错了，证明即使完全正确，也可能证明了错误的问题。因此 specification review 与定理证明同样重要。

### 11.2 Bridge trusted base

Bridge trusted base 包括生成器、rule-id mapping、trace construction/checking、certificate construction/checking 和 type/callable identity mapping。这些把 formal world 连到 C artifact。

### 11.3 Execution trusted base

执行可信基包括 C 编译器与 linker、C 实现、allocator/thread primitive、OS/运行时、硬件以及借用的回调和 user code。只有被形式化并建立 refinement 的部分，才能获得对应定理的保证；其余部分仍需要测试、sanitizer、ABI qualification、压力测试、平台 CI 和 benchmark。

### 11.4 External liveness assumptions

“OS eventually schedules worker”、“socket eventually becomes ready”、“device eventually completes”、“user 回调 eventually returns”通常是环境 assumption，而不是 CMeta/CFlow 定理。书里必须显式标注这种假设。这样才不会把 safety 证明写成“系统永远不会卡住”的过度承诺。

## 12. Proof / Test / Runtime Check 的协作方式

一个成熟 feature 不应该问“证明还是 test？”，而应该问：

这条主张分别在哪几个层次需要证据？以 idempotent 改写为例：

~~~text
Semantic law
    → Lean theorem

Concrete optimizer event
    → proof trace

Graph/optimized binding
    → trace checker

Plan binding
    → certificate

C implementation regression
    → differential tests

memory/lifetime
    → sanitizer

performance benefit
    → benchmark
~~~

以 Reactive demand 为例：

~~~text
demand mathematical invariant
    → Lean

runtime state mapping
    → conformance tests

wake/cancel race
    → stress/readiness tests

scheduler capacity behavior
    → bounded protocol tests

latency/throughput
    → benchmark
~~~

因此真正专业的 verification stack 是：

~~~text
Formal proof
+
Generated facts
+
Runtime admission
+
Differential testing
+
Memory/concurrency testing
+
ABI/platform qualification
+
Measurement
~~~

不是其中任意一个单独称霸。

## 13. 小结

图改写需要三个相互对应的对象：定义观察结果的语义模型、在明确假设下成立的变换规律，以及只在这些条件满足时执行改写的实现。CMeta 中的性质标志可以帮助选择候选规则，但不能证明任意 C 函数满足该规律。幂等 Map 的例子从 `f(f(x)) = f(x)` 推到逐元素结果一致；涉及顺序、错误、副作用或资源行为时，还必须把这些观察纳入模型。证明记录和证书将具体产物关联到获准规则，差分测试再检查 C 实现是否遵循这些规则。
