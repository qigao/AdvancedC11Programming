# 第十章：执行器与调度器：任务、容量和完成责任

异步调用把“谁请求工作”与“谁执行工作”分开，也把资源责任分成接受前和接受后两个阶段。执行器（Executor）必须明确回答：队列满时谁清理，关闭时尚未运行的任务怎么办，回调结束后何时可以释放上下文。本章用有界队列和任务计数关系推导这些契约。

## 1. 任务描述与上下文生存期

固定快照的任务描述如下，需要 `<cflow/executor.h>`：

~~~c
typedef struct cflow_executor_task {
    cflow_task_fn run;
    cflow_task_fn cancel;
    cflow_task_fn finalize;
    void *user;
} cflow_executor_task;
~~~

成功接受时，执行器复制描述，随后恰好选择 run 或 cancel 路径，再调用非空的 finalize。拒绝时不执行任何任务回调。`user` 是借用指针：复制描述不会复制其所指对象，也不自动增加引用计数。有 finalize 时，run 和 cancel 都必须让上下文继续有效，最终释放放在 finalize。

下面是普通 C 回调片段，使用 `<stdlib.h>`，演示把一个应用持有的引用交给最终清理。它假设这些回调之间遵循执行器的串行终结关系，且没有其他线程无同步读取该对象。

~~~c
struct book_job {
    int input;
    int output;
    int cancelled;
};

static void book_run(void *user)
{
    struct book_job *job = user;
    job->output = job->input; /* A stand-in for the admitted computation. */
}

static void book_cancel(void *user)
{
    struct book_job *job = user;
    job->cancelled = 1;
}

static void book_finalize(void *user)
{
    free(user);
}
~~~

`job` 必须来自匹配的分配方式。接受后最终回调可释放它，因此提交者不能在返回成功后继续通过原指针读取结果；结果交付需要另一个有明确生存期的通道。任务也可能在投递返回前已开始运行，不能把“post 已返回”作为回调获得上下文的前提。

## 2. 接受是一次提交

以下伪代码展示非阻塞接受路径。锁保护生命周期、容量检查和入队提交；用户回调在锁外执行。

~~~text
try_post(task):
    validate the descriptor
    lock executor
    if lifecycle is not OPEN: unlock; return CLOSED
    if queued == capacity: unlock; return FULL
    copy task into one queue slot
    increment queued and accepted
    unlock executor
    notify a worker if required
    return ACCEPTED
~~~

**准入（admission）**是决定是否接受一次工作及其后续责任。接受后，执行器负责把任务带到运行或取消的终点；这不等于它取得了 `user` 可达的所有资源。拒绝后，提交者仍负责上下文清理。

~~~text
job = allocate and fully initialize context
status = try_post({run, cancel, finalize, job})
if status is not ACCEPTED:
    release the caller-owned context
else:
    do not access context through the submitted ownership reference
~~~

这两条释放路径互斥。若被拒绝，执行器没有回调义务，由调用方释放一次；若已接受，则由 finalize 释放一次。该推导依赖没有把同一个唯一拥有的指针重复提交，也依赖释放之后没有继续访问。

## 3. 已接受任务的计数守恒

令 `A` 为累计接受数，`Q` 为排队数，`R` 为运行数，`C` 为已完成数，`X` 为已取消数。任务状态互斥，得到：

~~~text
A = Q + R + C + X
0 <= Q <= capacity
for a Serial executor: R <= 1
~~~

每个转换都保持等式。接受同时增加 `A` 与 `Q`；开始运行把一个 `Q` 转为 `R`；完成把 `R` 转为 `C`；取消排队任务把 `Q` 转为 `X`。FULL 与 CLOSED 拒绝不改变这些任务计数，只能增加相应拒绝统计。

例如容量二的手动执行器接受两项后为 `(A,Q,R,C,X)=(2,2,0,0,0)`。再投递被拒绝；运行一项后为 `(2,1,0,1,0)`；取消剩余项后为 `(2,0,0,1,1)`。空闲时 `A=C+X`，因此每个被接受的任务都有唯一终结去向。

例如 Manual 实现把已从物理队列取出、但仍在执行 cancel/finalize 的任务继续计入协议的 queued，清理完成后才计入 cancelled。因此物理队列长度与协议阶段计数不能混用，否则关闭途中会看起来“丢失”任务。

这是数学整数上的不变量。C 统计字段具有有限位宽，长期累计计数的溢出策略应遵循实现契约，不能仅凭自然数模型声称无限期计数精确。观察快照也不能替代等待终结的同步操作。

## 4. 关闭先停止接受，再完成已有责任

执行器生命周期为 OPEN、CLOSING、CLOSED。关闭策略在首次关闭时确定：DRAIN 执行已接受的排队任务；CANCEL_PENDING 取消尚未开始的任务。已经运行的回调仍须完成其规定的终结过程。

~~~text
begin_shutdown(policy):
    lock executor
    close admission and select the policy once
    if cancel-pending:
        detach queued tasks into a settlement set
    unlock executor
    for each detached task:
        call cancel if present
        call finalize if present
        account for terminal settlement
    wait or explicitly drive remaining work as the backend requires
    publish CLOSED only after accepted work is settled
~~~

**终结（settlement）**指任务运行或取消，并完成最终回调和记账。队列暂时为空不表示已经终结：一个工作线程可能仍在回调中访问 `user`。因此必须在规定的等待点之后销毁执行器及其借用资源。

## 5. 手动、串行与工作线程执行器

| 形式 | 谁推进任务 | 可以依赖的性质 |
|---|---|---|
| Manual | 调用方显式驱动 | 便于控制执行顺序；等待不会替调用方暗中泵送 |
| Serial | 串行执行上下文 | 同时至多一个任务修改该执行域 |
| Worker | 工作线程池 | 可并发运行，但不自动证明任务之间可交换 |

Manual 的控制等待可能返回 PENDING，调用方需要显式推进。线程池调用方可以按照控制协议等待容量；同执行器回调若需要等待自身释放容量，则返回 WOULD_BLOCK。`cflow_executor_try_post_task` 是非阻塞准入入口，`cflow_executor_control_post_task` 属于可选控制接口，不能把两者的等待行为混为一谈。

第三章的 InterfaceDesc 和 `{self, vtable}` 支持执行器提供方分派。`cflow_executor_as_control` 通过创建该句柄的提供方取得控制视图；视图借用后端，销毁所有者后失效。不能在另一个动态模块里根据内部结构猜测它属于哪种执行器。

## 6. 回调为什么不能同步等待自身

设串行任务 T 正在运行，它投递 U 后同步等待执行器空闲。空闲要求 T 完成，T 完成又要求等待返回，构成循环依赖。即使队列有空间，这个等待也无法通过运行 U 解除。因此回调不能销毁或同步等待同一执行器；需要把后续步骤安排为另一个任务，或让外部控制线程等待。

调度器（Scheduler）在执行任务之外增加时钟、延迟、取消标识和恢复策略。第九章的订阅用它决定何时再次推进，执行器只承担已接受任务的执行协议。不能因为存在 Worker 就推断一个任意归约具备第七章要求的结合律。

## 7. 形式证明与实现验证

固定快照 [Proofs/ExecutorProtocol.lean](https://github.com/qigao/salts/blob/a650262031e9b3e5f11a227a7911a75db9ae1fb8/formal/cmeta_cflow_calculus/CMetaCFlowCalculus/Proofs/ExecutorProtocol.lean) 的 `task_partition` 按任务列表归纳：空列表各计数为零；加入一个任务只增加它所属的一个阶段计数。`tryPost_preserves_safe`、`start_preserves_safe` 和 `finish_preserves_safe` 则检查接受、开始和结束保持边界条件。

这些定理约束抽象协议，不证明操作系统公平性，也不代替 C 中的锁、对象生存期与内存模型验证。真实接口见 [executor.h](https://github.com/qigao/salts/blob/a650262031e9b3e5f11a227a7911a75db9ae1fb8/cflow/include/cflow/executor.h)。

实现测试应覆盖容量一或二的队列、run/cancel/finalize 的互斥与次序、重复关闭、回调内投递、同执行器等待，以及最后一个 finalize 释放上下文的路径。终结后核对 `accepted == completed + cancelled`，并用并发记录确认 Serial 从未有两个运行任务。成功运行一个回调不足以验证整个协议。

## 8. 小结

执行器把任务接受与最终清理连接起来。计数守恒解释任务不会因关闭或容量拒绝而消失，互斥回调路径解释上下文应由谁释放。复制任务描述只建立借用；提供方、上下文和回调代码都必须活到最后一次使用结束。具体后端决定如何推进任务，计算是否允许并发仍需由计算契约证明。
