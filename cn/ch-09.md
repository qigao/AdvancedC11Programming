# 第十章：执行器与调度器：任务、容量和完成责任

计算描述确定要做什么，执行器负责已经接受的任务何时获得执行机会，以及取消后怎样清理。本章给出有界队列的投递和关闭算法，用任务计数守恒检查任务是否遗失，并比较手动、串行和工作线程执行方式。调度器进一步处理时间与恢复上下文，其能力不能替代计算本身的并行安全条件。

## 1. 最小 Task Contract

最简单的 task：

~~~c
typedef void (*task_run_fn)(void *user);

typedef struct task {
    task_run_fn run;
    void *user;
} task;
~~~

真实 executor 通常还需要取消和最终清理：

~~~c
typedef struct executor_task {
    void (*run)(void *user);
    void (*cancel)(void *user);
    void (*finalize)(void *user);
    void *user;
} executor_task;
~~~

accepted task 的所有权从调用方转移到 Executor，直到 **run + finalize** 或 **cancel + finalize** 完成。

## 2. Admission Algorithm：FULL / CLOSED 都是正常结果

~~~text
try_post(exec, task):

    lock(exec)

    if exec.state != OPEN:
        unlock(exec)
        return CLOSED

    if exec.queue.size == exec.capacity:
        exec.stats.full += 1
        unlock(exec)
        return FULL

    exec.queue.push(task)
    exec.accepted += 1

    unlock(exec)

    wake_one_worker(exec)

    return OK
~~~

这里没有 hidden queue growth、silent drop、automatic retry，也没有 fallback to synchronous execution。调用方看到 `FULL`，才能决定真正的业务策略。

## 3. Settlement Ledger

每个已接受任务必须处于排队、运行或已结算状态之一。定义计数 `accepted`、`queued`、`running`、`settled`，得到不变量 **`accepted = queued + running + settled`**。以下状态迁移分别检查等式两侧的变化：

~~~text
POST:
    accepted++, queued++

START:
    queued--, running++

COMPLETE:
    running--, settled++

CANCEL_PENDING:
    queued--, settled++
~~~

FULL / CLOSED 不改变 ledger：

~~~text
post(task) = FULL or CLOSED
───────────────────────────
accepted' = accepted
~~~

## 4. Lifecycle State Machine

~~~text
OPEN
  post accepted
  shutdown -> CLOSING

CLOSING
  no new post
  queued/running tasks settle
  when queued=0 && running=0 -> CLOSED

CLOSED
  terminal
~~~

伪码：

~~~text
shutdown(exec, policy):

    atomic OPEN -> CLOSING

    if policy == CANCEL_PENDING:
        while queue not empty:
            task = pop()
            task.cancel()
            task.finalize()
            settled++

    wake_all_workers()

    when queue empty and running == 0:
        state = CLOSED
~~~

Shutdown policy 只能选一次。

## 5. Manual / Serial / Worker：共享协议，不共享实现

| Capability | Manual | Serial | Worker |
|---|---:|---:|---:|
| caller-driven drain | yes | no | no |
| concurrent producers | possible | possible | yes |
| max running | 1 | 1 | N |
| single mutable owner guarantee | by caller discipline | yes | no |
| hidden thread required | no | maybe | yes |
| same Task contract | yes | yes | yes |

Serial 的关键 invariant 是 **`running <= 1`**。这不等于 “must own one dedicated thread”。Manual executor 也可以维持同样的 single-owner 语义。

## 6. Executor Interface 与 Scheduler Boundary

Executor 很适合 Interface/vtable，因为它天然是 long-lived 提供方：

~~~c
typedef struct cflow_executor {
    void *self;
    const cflow_executor_vtable *vtable;
} cflow_executor;
~~~

调用者只依赖 `try_post`、`shutdown`、`stats` 等 capability。

| 对象 | 决定什么 |
|---|---|
| Scheduler | when |
| Executor | how / where |

因此 **Scheduler != Executor**。组合可以是：

~~~text
timer scheduler
    ↓ due task
serial executor
    ↓
task.run()
~~~

而不是继承层次。

## 7. Fail-Fast Cases

### Same-executor synchronous wait

~~~text
Serial executor callback
    ↓
posts task to same executor
    ↓
waits synchronously for that task
~~~

这会自锁。应该：

~~~text
detect same execution context
    ↓
return WOULD_BLOCK / INVALID
~~~

而不是“希望另一个线程出现”。

### Capacity exhausted

当 `queue.size == capacity` 时返回 `FULL`，不偷偷 malloc。

### Shutdown

当 `state != OPEN` 时返回 `CLOSED`，不接受后再偷偷 cancel。后面的 formal protocol只需要证明这些已经明确的 ledger、boundedness 和 lifecycle 规则。

## 8. Semantic Contract：Executor 最小但并不模糊

Executor 的 API 可以很小，但它的 contract 必须非常精确。

### 8.1 Task 准入检查是一次明确的所有权 boundary

最简单的 task 仍然可以是：

~~~c
void task(void *user);
~~~

但在真实工程中，一个已经准入的 task 往往还需要 `run`、`cancel`、`finalize` 和 `user`。如果 Executor 在 shutdown 时取消尚未执行的 task，“没有运行”并不等于“无需处理”；系统仍可能需要释放 retained user state、把 buffer 归还对象池、settle promise/future，或减少 outstanding 所有权计数。因此 task 描述符更接近：

~~~text
accepted
    ↓
exactly one of:
    run
    cancel
    ↓
optional finalize
~~~

Rejected 准入检查则必须：

> 不调用任何 task 回调，也不偷走调用方所有权。

这条规则让 FULL/CLOSED 不再是模糊错误码，而是所有权 protocol。

### 8.2 Capacity 是语义边界，不是性能 hint

如果 Executor 声明 `capacity = N`，那么必须保持 `queued <= N`。满了以后不能偷偷 malloc 一个 overflow queue。否则上层看到的 backpressure contract 就是假的。因此 FULL 的意义是：

当前 resource boundary 已经到达；下一步 policy 由上层决定。Executor 本身不自动 drop、retry forever、block any 调用方、spill to heap 或 create new worker。

### 8.3 Serial 的核心不是“一条线程”，而是 single 可变 owner

Serial Executor 真正保证的是：

~~~text
running <= 1
~~~

Serial 并不意味着“必须拥有专用线程”。它可以由调用方驱动的 manual queue、单 worker，或外部 event-loop adapter 实现。因此 State Machine/Actor 可以依赖串行语义，而不依赖某种具体线程拓扑。

### 8.4 Worker 只提供 concurrent capability，不授权语义并行

Worker Executor 能并行运行 task，并不意味着任意 Graph node、State transition 或 Actor message 都允许并行。真正的决定关系仍然是：

~~~text
semantic layer says parallelism is legal
        +
Executor provides CONCURRENT capability
        ↓
parallel execution admitted
~~~

Mechanism 不替 policy 决策。

### 8.5 Lifecycle 必须从 OPEN 明确走向 CLOSED

Executor lifecycle 至少需要：

~~~text
OPEN
    ↓ shutdown
CLOSING
    ↓ all accepted work settles
CLOSED
~~~

一旦不再 OPEN：

~~~text
new post
    → CLOSED / rejected
~~~

而已经 accepted 的 task 如何处理，取决于 explicit shutdown policy：`DRAIN` 或 `CANCEL_PENDING`。这比“destroy() then hope 回调 stop”安全得多。

### 8.6 Same-executor 回调不能同步等待自己

这是一个很容易被 API 忽略的 deadlock boundary。如果当前正在某 Executor 回调内且 queue is full，再调用可能等待容量的 blocking post，或者调用 `wait_idle()` 等自己执行完，就会形成 self-deadlock。所以 contract 必须允许显式返回 `WOULD_BLOCK`。这不是实现细节。这是执行模型的一部分。

## 9. Lean：Executor 已经有完整协议模型

本版 Salts 快照 formal calculus 已经包含：

~~~text
CMetaCFlowCalculus/CFlow/ExecutorProtocol.lean
CMetaCFlowCalculus/Proofs/ExecutorProtocol.lean
~~~

模型不是从 thread API 出发，而是从协议事实出发。它定义：

~~~text
ExecutorKind
    manual
    serial
    worker

ShutdownPolicy
    drain
    cancelPending

Lifecycle
    open
    closing
    closed

TaskPhase
    queued
    running
    completed
    cancelled

AdmissionResult
    accepted
    full
    closed
    wouldBlock
~~~

这与 C API 的边界非常接近。

### 9.1 Bounded：队列永远不越过容量

formal state 定义：

~~~text
Bounded(state)
:=
queued <= capacity
~~~

而定理：

~~~text
accepted_post_is_bounded_and_conserved
~~~

证明只要当前还有 room，一次 accepted post 后：

~~~text
queued' = queued + 1
accepted' = accepted + 1
Safe(state')
~~~

更一般的 `tryPost_preserves_safe` 证明 ACCEPTED/FULL/CLOSED 都不会破坏 Safe invariant。这直接约束 C：

> 如果 C backend 在 FULL 时仍然偷偷存入 task，那么它不是“实现不同”，而是违反模型。

### 9.2 Task ledger conservation：accepted task 不会凭空消失

formal model 定义：

~~~text
accepted
=
queued
+
running
+
completed
+
cancelled
~~~

并由 `state_conserved` 保证 conservation；最终 settlement 后：

~~~text
accepted
=
completed + cancelled
~~~

对应定理 `settled_tasks_have_exactly_one_terminal_outcome`。这给 shutdown 一个非常强的工程目标：

> 每个 accepted task 最终必须拥有且只拥有一个 terminal outcome。

不是“maybe ran / maybe got lost during destroy”。

### 9.3 SerialSafe：Manual / Serial 同时最多一个 running task

formal definition 可以直接写成：

| Mode | Running constraint |
|---|---|
| manual / serial | `running <= 1` |
| worker | no such restriction |

`start_preserves_safe` 保证 start transition 不破坏这个约束。这就是 single 可变 owner 的数学形式。

### 9.4 FULL 与 CLOSED 不改变 task ledger

已有定理 `full_post_preserves_task_ledger` 与 `post_shutdown_rejected`，说明 rejected post **does not append a task**，只更新相应 rejection observation。这和所有权 contract 完全一致：

~~~text
rejected admission
    ↓
caller still owns task/user
~~~

### 9.5 Same-回调 blocking operation 必须 fail fast

现有定理 `self_blocking_operations_fail_fast` 直接表达：当调用方是 same Executor 回调且 queue full 时：

~~~text
blockingPost
    → WOULD_BLOCK

waitIdle
    → WOULD_BLOCK
~~~

这是 Lean 很实际地帮助 API 设计的例子。如果没有模型，很容易写出一个“看起来方便”的 blocking API，直到 production 遇到回调 self-deadlock。

### 9.6 Shutdown settlement

formal model 区分 drain 与 cancelPending，并证明 `beginShutdown_preserves_safe`、`settleShutdown_settled`、`settleShutdown_quiescent` 和 `close_produces_closed_quiescent`。于是 CLOSED 的含义不是“一个 bool 被设成 true”，而是同时满足 `lifecycle = CLOSED`、`queued = 0`、`running = 0`。这就是 ClosedQuiescent。

### 9.7 这里仍然不证明 OS fairness

formal settleShutdown 是一个 summary transition，并明确写着：

> running task 最终结束、drain-mode queued task 最终被驱动，是外部 premise，不是 OS-liveness 定理。

所以 Lean 证明：

~~~text
if accepted work is driven/settled
then protocol accounting is correct
~~~

它不证明 worker thread 一定永不挂死、OS 一定调度，或 user task 一定 return。这一点和第九章 safety/liveness 边界完全一致。

## 10. Current C Implementation：Task protocol 已经比简单 fn/user 更完整

对照本版 Salts 实现快照 qigao/salts@ad389928b437c0612c1c60844fe53677f3ed27a6：

本版 snapshot 中 built-in Executor 的 task 描述符定义为：

~~~c
typedef struct cflow_executor_task {
    cflow_task_fn run;
    cflow_task_fn cancel;
    cflow_task_fn finalize;
    void *user;
} cflow_executor_task;
~~~

它的 contract 是 **settlement rule**，不是数据流：

| Admission result | Required callback outcome |
|---|---|
| successful admission | exactly one of run/cancel, then finalize if present |
| rejected admission | no task callback |

这与 Lean task ledger 的“exactly one terminal outcome”非常吻合。

### 10.1 Manual Executor 是显式调用方-driven queue

当前 Manual implementation 持有有界 task array、count、settling、容量、accepted/completed/cancelled counters、rejection counters、lifecycle、shutdown policy 和 running flag。它不是一个“测试专用假对象”。它表达了一种真实 execution policy：

> task 准入检查与 task driving 分离，何时 run_one/run_ready 由 owner 决定。

这非常适合 deterministic test、external batch/event loop 和 single-thread 所有权 boundary。

### 10.2 FULL 被直接统计，而不是自动扩容

Manual try_post：

~~~text
if count >= capacity
    rejected_full++
    return FULL
~~~

没有 hidden fallback allocation。这正好实现了 formal Bounded。

### 10.3 Shutdown policy 只选择一次

当前实现记录 shutdown_policy_selected。第一次 shutdown 选择 DRAIN 或 CANCEL_PENDING；后续如果尝试用另一个 policy 重写 shutdown meaning，会失败，避免 closing halfway 后 application 又改变 semantics。

### 10.4 CANCEL_PENDING 会执行 cancel/finalize

pending task 被 cancel 时：

~~~text
cancel(user)
finalize(user)
cancelled++
~~~

不是单纯丢弃 队列项。这就是所有权 protocol 真正落地的地方。

### 10.5 回调 context 通过 thread-local 边界识别

Manual implementation 记录当前正在执行哪个 Executor state。因此 post that would need waiting 与 wait_idle 在 same-executor 回调中可以返回 WOULD_BLOCK，而不是自锁。这是 formal self_blocking_operations_fail_fast 的现实 counterpart。

## 11. Manual / Serial / Worker：三种实现共享的是协议，不是结构

本章应该避免把三种 Executor 讲成三套 framework。真正共享的是 Task 准入检查、容量、lifecycle、settlement、statistics 和 capabilities。

### 11.1 Manual

CAP_MANUAL：调用方 drives work，且 running <= 1。最适合 deterministic control。

### 11.2 Serial

CAP_SERIAL：execution may be automatically driven，但 semantic guarantee 仍是 single running task。适合 Machine mutation、Actor state 和 single-owner 回调。

### 11.3 Worker

CAP_CONCURRENT：multiple accepted tasks may run concurrently。适合 parallel Plan、independent work 和 I/O/computation dispatch，但只有上层 semantic 准入检查已经允许时才应该使用并行。

## 12. Executor 与 Scheduler 为什么仍然不是同一个对象

第九章已经看到 Scheduler 与 Executor 的职责不同：

| 对象 | 主要职责 |
|---|---|
| Scheduler | delay、clock、cancel by task id、advance virtual time、timer queue |
| Executor | accept Task、run Task、bound work、settle lifecycle |

因此 Executor 是 execution resource / ordering primitive，Scheduler 是 temporal dispatch policy。Scheduler 可以内部使用 Executor，但上层不应该因此把二者混为一个 interface。典型关系是 **temporal-dispatch composition**，不是数据流：

~~~text
timer/readiness
    ↓ decides when
Scheduler
    ↓ posts admitted work
Executor / posting context
    ↓ runs
Task
~~~

Manual Scheduler 也可以组合 Manual Executor。这里是 capability composition，不是继承层次。

## 13. Evidence：Executor 必须验证协议，而不仅是“task 跑了”

这一章至少需要以下证据。

### 13.1 Capacity evidence

对于容量=N：

~~~text
accept up to N queued work
N+1
    → FULL
drain one
    → capacity reusable
~~~

并检查：

~~~text
peak_pending
rejected_full
~~~

### 13.2 Ledger evidence

在 normal completion、cancel-pending shutdown 和 drain shutdown 之后检查：

~~~text
accepted
=
completed + cancelled
~~~

这与 Lean 定理一一对应。

### 13.3 Serial evidence

同时提交多个 task，必须证明 **running never exceeds 1**。这里可以用 instrumentation / atomic counter 测试，而不是只检查最终输出顺序。

### 13.4 Self-callback evidence

在 task 回调内测试：

~~~text
wait_idle(same executor)
    → WOULD_BLOCK

blocking post when full
    → WOULD_BLOCK
~~~

正常完成路径无法暴露同一执行器内同步等待自己的死锁风险，因此这里需要专门的失败场景。

### 13.5 Shutdown evidence

分别测试：

~~~text
DRAIN
    queued work runs/finalizes

CANCEL_PENDING
    queued work cancels/finalizes

after closing
    new post rejected
~~~

以及 repeated/invalid shutdown policy behavior。

### 13.6 Sanitizer / ownership evidence

Task user 所有权最容易出错的路径包括：准入后又取消、`run` 回调递归 post 新任务、`finalize` 释放最后一个引用，以及 destroy 与 pending work 竞争。这些路径需要 ASan/UBSan 和面向 race 的压力测试作为 C 实现证据；Lean 不会替实现发现 use-after-free。

## 14. 小结

执行器接受任务后承担执行或取消及最终清理的责任。`accepted = queued + running + settled` 将这项责任落实为可检查的计数关系；`FULL` 和 `CLOSED` 拒绝投递时不增加已接受任务数，也不转移任务所有权。手动、串行和工作线程执行器可以共享投递与关闭契约，但执行上下文不同。调度器增加时间和恢复策略，计算是否允许并行仍由操作的类型、所有权和语义条件决定。
