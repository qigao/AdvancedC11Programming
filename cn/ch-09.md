# 第十章：Executor——把执行策略从计算语义中拆出来

> **Executor 只回答一件事：accepted task 怎样被执行和 settle。**
>
> 它不拥有 Graph，不判断某个 Graph 是否允许并行，也不拥有 Scheduler 的时间语义。本章只需要四个对象：Task、Queue、Executor lifecycle 和 settlement ledger。

**Settlement（结算）**在本章指已接受的任务最终完成执行或取消，并完成相应清理。settlement ledger（结算账本）是追踪这些任务去向的计数记录，用于检查任务是否遗失或重复结算。

---

## 1. 最小 Task Contract

最简单的 task：

~~~c
typedef void (*task_run_fn)(void *user);

typedef struct task {
    task_run_fn run;
    void *user;
} task;
~~~

真实 executor 通常还需要取消和最终清理：

~~~c
typedef struct executor_task {
    void (*run)(void *user);
    void (*cancel)(void *user);
    void (*finalize)(void *user);
    void *user;
} executor_task;
~~~

accepted task 的 ownership 从调用方转移到 Executor，直到 **run + finalize** 或 **cancel + finalize** 完成。

---

## 2. Admission Algorithm：FULL / CLOSED 都是正常结果

~~~text
try_post(exec, task):

    lock(exec)

    if exec.state != OPEN:
        unlock(exec)
        return CLOSED

    if exec.queue.size == exec.capacity:
        exec.stats.full += 1
        unlock(exec)
        return FULL

    exec.queue.push(task)
    exec.accepted += 1

    unlock(exec)

    wake_one_worker(exec)

    return OK
~~~

这里没有 hidden queue growth、silent drop、automatic retry，也没有 fallback to synchronous execution。调用方看到 `FULL`，才能决定真正的业务策略。

---

## 3. Settlement Ledger

Executor 最重要的 invariant 不是“task 最后大概会跑”。

而是 accepted task 不会凭空消失。

定义四个计数：`accepted`、`queued`、`running`、`settled`。核心 invariant 是 **`accepted = queued + running + settled`**。

状态迁移：

~~~text
POST:
    accepted++, queued++

START:
    queued--, running++

COMPLETE:
    running--, settled++

CANCEL_PENDING:
    queued--, settled++
~~~

FULL / CLOSED 不改变 ledger：

~~~text
post(task) = FULL or CLOSED
───────────────────────────
accepted' = accepted
~~~

---

## 4. Lifecycle State Machine

~~~text
OPEN
  post accepted
  shutdown -> CLOSING

CLOSING
  no new post
  queued/running tasks settle
  when queued=0 && running=0 -> CLOSED

CLOSED
  terminal
~~~

伪码：

~~~text
shutdown(exec, policy):

    atomic OPEN -> CLOSING

    if policy == CANCEL_PENDING:
        while queue not empty:
            task = pop()
            task.cancel()
            task.finalize()
            settled++

    wake_all_workers()

    when queue empty and running == 0:
        state = CLOSED
~~~

Shutdown policy 只能选一次。

---

## 5. Manual / Serial / Worker：共享协议，不共享实现

| Capability | Manual | Serial | Worker |
|---|---:|---:|---:|
| caller-driven drain | yes | no | no |
| concurrent producers | possible | possible | yes |
| max running | 1 | 1 | N |
| single mutable owner guarantee | by caller discipline | yes | no |
| hidden thread required | no | maybe | yes |
| same Task contract | yes | yes | yes |

Serial 的关键 invariant 是 **`running <= 1`**。这不等于 “must own one dedicated thread”。

Manual executor 也可以维持同样的 single-owner 语义。

---

## 6. Executor Interface 与 Scheduler Boundary

Executor 很适合 Interface/vtable，因为它天然是 long-lived provider：

~~~c
typedef struct cflow_executor {
    void *self;
    const cflow_executor_vtable *vtable;
} cflow_executor;
~~~

调用者只依赖 `try_post`、`shutdown`、`stats` 等 capability。

| 对象 | 决定什么 |
|---|---|
| Scheduler | when |
| Executor | how / where |

因此 **Scheduler != Executor**。

组合可以是：

~~~text
timer scheduler
    ↓ due task
serial executor
    ↓
task.run()
~~~

而不是继承层次。

## 7. Fail-Fast Cases

### Same-executor synchronous wait

~~~text
Serial executor callback
    ↓
posts task to same executor
    ↓
waits synchronously for that task
~~~

这会自锁。

应该：

~~~text
detect same execution context
    ↓
return WOULD_BLOCK / INVALID
~~~

而不是“希望另一个线程出现”。

### Capacity exhausted

当 `queue.size == capacity` 时返回 `FULL`，不偷偷 malloc。

### Shutdown

当 `state != OPEN` 时返回 `CLOSED`，不接受后再偷偷 cancel。

后面的 formal protocol只需要证明这些已经明确的 ledger、boundedness 和 lifecycle 规则。

## 8. Semantic Contract：Executor 最小但并不模糊

Executor 的 API 可以很小，但它的 contract 必须非常精确。

### 8.1 Task admission 是一次明确的 ownership boundary

最简单的 task 仍然可以是：

~~~c
void task(void *user);
~~~

但真实工程中，一个 accepted task 往往还需要 `run`、`cancel`、`finalize` 和 `user`。原因很直接。

如果 Executor 在 shutdown 时选择 cancel pending，那么“这个 task 没执行”并不意味着“什么都不用做”。它可能仍然需要 release retained user state、return buffer to pool、settle promise/future、decrement outstanding ownership。

因此一个 task descriptor 更接近：

~~~text
accepted
    ↓
exactly one of:
    run
    cancel
    ↓
optional finalize
~~~

Rejected admission 则必须：

> 不调用任何 task callback，也不偷走 caller ownership。

这条规则让 FULL/CLOSED 不再是模糊错误码，而是 ownership protocol。

### 8.2 Capacity 是语义边界，不是性能 hint

如果 Executor 声明 `capacity = N`，那么必须保持 `queued <= N`。满了以后不能偷偷 malloc 一个 overflow queue。

否则上层看到的 backpressure contract 就是假的。

因此 FULL 的意义是：

> **当前 resource boundary 已经到达；下一步 policy 由上层决定。**

Executor 本身不自动 drop、retry forever、block any caller、spill to heap 或 create new worker。

### 8.3 Serial 的核心不是“一条线程”，而是 single mutable owner

Serial Executor 真正保证的是：

~~~text
running <= 1
~~~

它不等于 “must have a dedicated thread”。Serial 可以由 manual caller-driven queue、single worker 或 external event loop adapter 实现。

这也是为什么 State Machine / Actor 可以依赖 serial semantics，而不依赖某个具体 thread topology。

### 8.4 Worker 只提供 concurrent capability，不授权语义并行

Worker Executor 能并行运行 task，并不意味着任意 Graph node、State transition 或 Actor message 都允许并行。

真正的决定关系仍然是：

~~~text
semantic layer says parallelism is legal
        +
Executor provides CONCURRENT capability
        ↓
parallel execution admitted
~~~

Mechanism 不替 policy 决策。

### 8.5 Lifecycle 必须从 OPEN 明确走向 CLOSED

Executor lifecycle 至少需要：

~~~text
OPEN
    ↓ shutdown
CLOSING
    ↓ all accepted work settles
CLOSED
~~~

一旦不再 OPEN：

~~~text
new post
    → CLOSED / rejected
~~~

而已经 accepted 的 task 如何处理，取决于 explicit shutdown policy：`DRAIN` 或 `CANCEL_PENDING`。这比“destroy() then hope callbacks stop”安全得多。

### 8.6 Same-executor callback 不能同步等待自己

这是一个很容易被 API 忽略的 deadlock boundary。

如果当前正在某 Executor callback 内且 queue is full，再调用可能等待 capacity 的 blocking post，或者调用 `wait_idle()` 等自己执行完，就会形成 self-deadlock。所以 contract 必须允许显式返回 `WOULD_BLOCK`。

这不是实现细节。

这是执行模型的一部分。

## 9. Lean：Executor 已经有完整协议模型

本版 Salts 快照 formal calculus 已经包含：

~~~text
CMetaCFlowCalculus/CFlow/ExecutorProtocol.lean
CMetaCFlowCalculus/Proofs/ExecutorProtocol.lean
~~~

模型不是从 thread API 出发，而是从协议事实出发。

它定义：

~~~text
ExecutorKind
    manual
    serial
    worker

ShutdownPolicy
    drain
    cancelPending

Lifecycle
    open
    closing
    closed

TaskPhase
    queued
    running
    completed
    cancelled

AdmissionResult
    accepted
    full
    closed
    wouldBlock
~~~

这与 C API 的边界非常接近。

### 9.1 Bounded：队列永远不越过 capacity

formal state 定义：

~~~text
Bounded(state)
:=
queued <= capacity
~~~

而 theorem：

~~~text
accepted_post_is_bounded_and_conserved
~~~

证明只要当前还有 room，一次 accepted post 后：

~~~text
queued' = queued + 1
accepted' = accepted + 1
Safe(state')
~~~

更一般的 `tryPost_preserves_safe` 证明 ACCEPTED/FULL/CLOSED 都不会破坏 Safe invariant。

这直接约束 C：

> 如果 C backend 在 FULL 时仍然偷偷存入 task，那么它不是“实现不同”，而是违反模型。

### 9.2 Task ledger conservation：accepted task 不会凭空消失

formal model 定义：

~~~text
accepted
=
queued
+
running
+
completed
+
cancelled
~~~

并由 `state_conserved` 保证 conservation；最终 settlement 后：

~~~text
accepted
=
completed + cancelled
~~~

对应 theorem `settled_tasks_have_exactly_one_terminal_outcome`。

这给 shutdown 一个非常强的工程目标：

> 每个 accepted task 最终必须拥有且只拥有一个 terminal outcome。

不是“maybe ran / maybe got lost during destroy”。

### 9.3 SerialSafe：Manual / Serial 同时最多一个 running task

formal definition 可以直接写成：

| Mode | Running constraint |
|---|---|
| manual / serial | `running <= 1` |
| worker | no such restriction |

`start_preserves_safe` 保证 start transition 不破坏这个约束。

这就是 single mutable owner 的数学形式。

### 9.4 FULL 与 CLOSED 不改变 task ledger

已有 theorem `full_post_preserves_task_ledger` 与 `post_shutdown_rejected`，说明 rejected post **does not append a task**，只更新相应 rejection observation。

这和 ownership contract 完全一致：

~~~text
rejected admission
    ↓
caller still owns task/user
~~~

### 9.5 Same-callback blocking operation 必须 fail fast

现有 theorem `self_blocking_operations_fail_fast` 直接表达：当 caller 是 same Executor callback 且 queue full 时：

~~~text
blockingPost
    → WOULD_BLOCK

waitIdle
    → WOULD_BLOCK
~~~

这是 Lean 很实际地帮助 API 设计的例子。

如果没有模型，很容易写出一个“看起来方便”的 blocking API，直到 production 遇到 callback self-deadlock。

### 9.6 Shutdown settlement

formal model 区分 drain 与 cancelPending，并证明 `beginShutdown_preserves_safe`、`settleShutdown_settled`、`settleShutdown_quiescent` 和 `close_produces_closed_quiescent`。

于是 CLOSED 的含义不是“一个 bool 被设成 true”，而是同时满足 `lifecycle = CLOSED`、`queued = 0`、`running = 0`。这就是 ClosedQuiescent。

### 9.7 这里仍然不证明 OS fairness

formal settleShutdown 是一个 summary transition，并明确写着：

> running task 最终结束、drain-mode queued task 最终被驱动，是外部 premise，不是 OS-liveness theorem。

所以 Lean 证明：

~~~text
if accepted work is driven/settled
then protocol accounting is correct
~~~

它不证明 worker thread 一定永不挂死、OS 一定调度，或 user task 一定 return。

这一点和第九章 safety/liveness 边界完全一致。

## 10. Current C Implementation：Task protocol 已经比简单 fn/user 更完整

对照本版 Salts 实现快照 qigao/salts@ad389928b437c0612c1c60844fe53677f3ed27a6：

本版 snapshot 中 built-in Executor 的 task descriptor 定义为：

~~~c
typedef struct cflow_executor_task {
    cflow_task_fn run;
    cflow_task_fn cancel;
    cflow_task_fn finalize;
    void *user;
} cflow_executor_task;
~~~

它的 contract 是 **settlement rule**，不是 dataflow：

| Admission result | Required callback outcome |
|---|---|
| successful admission | exactly one of run/cancel, then finalize if present |
| rejected admission | no task callback |

这与 Lean task ledger 的“exactly one terminal outcome”非常吻合。

### 10.1 Manual Executor 是显式 caller-driven queue

当前 Manual implementation 持有 bounded task array、count、settling、capacity、accepted/completed/cancelled counters、rejection counters、lifecycle、shutdown policy 和 running flag。

它不是一个“测试专用假对象”。

它表达了一种真实 execution policy：

> task admission 与 task driving 分离，何时 run_one/run_ready 由 owner 决定。

这非常适合 deterministic test、external batch/event loop 和 single-thread ownership boundary。

### 10.2 FULL 被直接统计，而不是自动扩容

Manual try_post：

~~~text
if count >= capacity
    rejected_full++
    return FULL
~~~

没有 hidden fallback allocation。

这正好实现了 formal Bounded。

### 10.3 Shutdown policy 只选择一次

当前实现记录 shutdown_policy_selected。第一次 shutdown 选择 DRAIN 或 CANCEL_PENDING；后续如果尝试用另一个 policy 重写 shutdown meaning，会失败，避免 closing halfway 后 application 又改变 semantics。

### 10.4 CANCEL_PENDING 会执行 cancel/finalize

pending task 被 cancel 时：

~~~text
cancel(user)
finalize(user)
cancelled++
~~~

不是单纯丢弃 queue row。

这就是 ownership protocol 真正落地的地方。

### 10.5 callback context 通过 thread-local 边界识别

Manual implementation 记录当前正在执行哪个 Executor state。

因此 post that would need waiting 与 wait_idle 在 same-executor callback 中可以返回 WOULD_BLOCK，而不是自锁。

这是 formal self_blocking_operations_fail_fast 的现实 counterpart。

---

## 11. Manual / Serial / Worker：三种实现共享的是协议，不是结构

本章应该避免把三种 Executor 讲成三套 framework。

真正共享的是 Task admission、capacity、lifecycle、settlement、statistics 和 capabilities。

### 11.1 Manual

CAP_MANUAL：caller drives work，且 running <= 1。最适合 deterministic control。

### 11.2 Serial

CAP_SERIAL：execution may be automatically driven，但 semantic guarantee 仍是 single running task。适合 Machine mutation、Actor state 和 single-owner callbacks。

### 11.3 Worker

CAP_CONCURRENT：multiple accepted tasks may run concurrently。适合 parallel Plan、independent work 和 I/O/computation dispatch，但只有上层 semantic admission 已经允许时才应该使用并行。

## 12. Executor 与 Scheduler 为什么仍然不是同一个对象

第九章已经看到 Scheduler 与 Executor 的职责不同：

| 对象 | 主要职责 |
|---|---|
| Scheduler | delay、clock、cancel by task id、advance virtual time、timer queue |
| Executor | accept Task、run Task、bound work、settle lifecycle |

因此 Executor 是 execution resource / ordering primitive，Scheduler 是 temporal dispatch policy。

Scheduler 可以内部使用 Executor，但上层不应该因此把二者混为一个 interface。

典型关系是 **temporal-dispatch composition**，不是数据流：

~~~text
timer/readiness
    ↓ decides when
Scheduler
    ↓ posts admitted work
Executor / posting context
    ↓ runs
Task
~~~

Manual Scheduler 也可以组合 Manual Executor。这里是 capability composition，不是继承层次。

## 13. Evidence：Executor 必须验证协议，而不仅是“task 跑了”

这一章至少需要以下证据。

### 13.1 Capacity evidence

对于 capacity=N：

~~~text
accept up to N queued work
N+1
    → FULL
drain one
    → capacity reusable
~~~

并检查：

~~~text
peak_pending
rejected_full
~~~

### 13.2 Ledger evidence

在 normal completion、cancel-pending shutdown 和 drain shutdown 之后检查：

~~~text
accepted
=
completed + cancelled
~~~

这与 Lean theorem 一一对应。

### 13.3 Serial evidence

同时提交多个 task，必须证明 **running never exceeds 1**。这里可以用 instrumentation / atomic counter 测试，而不是只检查最终输出顺序。

### 13.4 Self-callback evidence

在 task callback 内测试：

~~~text
wait_idle(same executor)
    → WOULD_BLOCK

blocking post when full
    → WOULD_BLOCK
~~~

这类测试非常重要，因为普通 happy-path test 根本看不出 deadlock risk。

### 13.5 Shutdown evidence

分别测试：

~~~text
DRAIN
    queued work runs/finalizes

CANCEL_PENDING
    queued work cancels/finalizes

after closing
    new post rejected
~~~

以及 repeated/invalid shutdown policy behavior。

### 13.6 Sanitizer / ownership evidence

Task user ownership 最容易出错的路径包括 accepted then cancelled、run callback recursively posts、finalize releases last ref、destroy races with pending work。这些需要 ASan/UBSan 与 stress/race-focused tests 作为 C implementation evidence。

Lean 不会替你发现 use-after-free。

## 14. What We Learned

Executor 的价值不在于“知道很多”，而在于它只拥有一个很小的 execution contract。

| 层 | 职责 |
|---|---|
| Graph | computation description |
| Stream | construction façade |
| Reactive Subscription | live execution state |
| Scheduler | when / where work becomes runnable |
| Executor | bounded Task admission, execution, settlement |

核心 invariants 只有几条：

- queued <= capacity；
- accepted = queued + running + completed + cancelled；
- Manual / Serial 保持 running <= 1；
- FULL / CLOSED 不接收 task；
- same-executor blocking operation 必须 fail fast；
- shutdown 完成后 accepted = completed + cancelled；
- CLOSED 必须同时满足 queued = 0、running = 0。

这些 invariant 适合 formalize；task user lifetime、callback recursion、destroy race、use-after-free 仍需要 sanitizer / stress / runtime tests。

因此 Executor 是一个 **bounded Task execution primitive**，不是 Graph/Reactive/Machine 的第二套语义系统。
