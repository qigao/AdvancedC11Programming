# 第十五章：从重复知识到三种 IR——Modern C 的 Contract、Native 与 Execution 语义

> **本章路线**
>
> 最后一章不再按模块回顾功能，而是收束成一套可复用方法：
>
> ~~~text
> Understand
>     ↓
> Model
>     ↓
> Formalize
>     ↓
> Verify
>     ↓
> Implement
>     ↓
> Lower
>     ↓
> Measure
> ~~~
>
> 这套方法并不保证最后一定得到 CMeta/CFlow。很多时候，正确结果仍然只是 one function、one loop、one switch 或 one struct。
>
> Modern C 的专业性不在于抽象数量，而在于：**知道什么时候应该把重复知识提升成显式语义，也知道什么时候应该停在普通 C。**

## 1. 从 ordinary C 的工具分工到 Native Semantic IR

这本书现在不从“宏很痛苦，所以离开宏”开始。

起点是 ordinary C 中不同机制的职责：

| 机制 | 负责什么 |
|---|---|
| normal function / static inline | typed behavior |
| finite macro / PP | token、declaration、schema replay |
| compiler capability | native compile-time facts |
| CMeta | stable native semantic facts |
| DataBind | logical contract facts |
| CFlow | execution relations |
| Lean | selected semantic laws |

第一步不是用宏替代 C。

而是：

~~~text
ordinary C
    |
    v
identify repeated stable knowledge
    |
    v
use the smallest compile-time / semantic object
    |
    v
return to ordinary C execution
~~~

真正目标仍然是：

> **一个稳定事实只定义一次，让多个消费者使用它，并尽量在执行前消费掉。**

---

### 1.1 Native Semantic IR：描述 meaning，不自动增加 runtime

CMeta 增加的是有限、显式的 native semantic model：

| C reality | Semantic object |
|---|---|
| C type | TypeDesc / semantic identity |
| field facts | Struct / reflected-data metadata |
| capability | Traits / InterfaceDesc |
| native function | FunctionDesc + FunctionAbi |
| executable value | cmeta_callable |
| admitted semantic/execution join | cmeta_invokable |

最重要的分离已经变成：

| 描述对象 | 执行/绑定对象 |
|---|---|
| FunctionDesc + FunctionAbi | direct C call / optional exact thunk / cmeta_callable / cmeta_invokable |
| InterfaceDesc | live {self,vtable} |

Function Reflection 是 descriptive。

它不会因为 metadata 存在就自动把：

~~~c
add(2, 3);
~~~

改造成 runtime Reflection dispatch。

dynamic / foreign boundary 才需要：

~~~text
raw descriptor
    -> validate / admit once
    -> admitted capability
    -> repeated use
~~~

---

### 1.2 Generic 与 Type Relation：共享 kernel，不共享万能 router

当前 Generic 入口是有限、明确的：

~~~c
cmeta_type(Vec, IntVec, int);
cmeta_type(Option, MaybeUser, User);
~~~

它只接受注册过的 generic kind。

这与 historical universal routing surface 不同：

~~~text
historical:
typed(...)
    -> many unrelated DSL families

current:
cmeta_type(...)
    -> finite Generic declaration only
~~~

有限类型关系仍然来自显式 rows：

~~~c
TypeFunction(CommonArithmetic,
    (int, int, int),
    (int, double, double),
    (double, int, double),
    (double, double, double)
);
~~~

如果没有对应 row，就明确失败。

因此长期纪律仍然是：

> **finite、explicit、bounded、unsupported is explicit。**

---

### 1.3 Function semantic 与 executable projection：需要哪一层，就显式选择哪一层

普通 direct call：

~~~c
long square(int x);
~~~

不需要 Callable object。

需要共享 native function meaning 时：

~~~text
FunctionDecl
    -> FunctionDesc
    -> FunctionAbi
~~~

需要 exact erased invocation 时：

~~~text
FunctionInvokeDecl
    -> explicitly generated exact thunk
~~~

需要 receiver / parameter binding 时：

~~~text
canonical Function
    -> explicit projection
    -> bounded cmeta_callable capture
    -> cmeta_invokable admission
~~~

receiver operation set 只是：

~~~text
name -> canonical FunctionAbi
~~~

的薄索引，不复制 FunctionDesc。

因此最小表示现在是：

| 需求 | 最小表示 |
|---|---|
| direct call | ordinary function / function pointer |
| describe native function | FunctionDesc + FunctionAbi |
| exact erased boundary | explicit exact thunk |
| bind / capture / receiver projection | cmeta_callable + cmeta_invokable |
| long-lived provider | Interface + {self,vtable} |

Bind 的意义是显式 parameter projection。

它不要求再发明一套独立 Lambda object model，也不隐藏 malloc、retain 或 managed ownership。


## 2. Execution IR 与 Verified Transformation

一旦多个 admitted callable 需要组合，真正新的知识不再是单个函数，而是它们之间的 relation。

例如：

~~~text
Source<int>
    ↓
Filter(is_even)
    ↓
Map(square)
    ↓
Reduce(sum)
~~~

Graph 把 topology、type chain、operator semantics 与 callable relation 保存成 program object。

这使系统第一次能够在执行前完成：

- type admission；
- normalize；
- semantic rewrite；
- plan compilation；
- Direct/AOT eligibility。

如果只有一个固定 loop，Graph 没有必要存在。

---

### 2.1 Formal Semantics：证明只服务真实 transformation

一旦 optimizer 想把 P 改成 Q，才真正出现 proof obligation。

例如：

~~~text
Map(f); Map(f)  ~>  Map(f)
~~~

需要的不只是 `IDEMPOTENT` metadata，而是：

~~~text
∀x, f(f(x)) = f(x)
~~~

因此：

| 层 | 证据 |
|---|---|
| metadata claim | admission |
| semantic law | Lean theorem |
| one concrete rewrite | trace / certificate |
| real C implementation | differential test |
| performance | benchmark |

Lean 不是装饰，也不是 ABI/link/sanitizer 的替代品。

---

## 3. Contract IR 与 Live Runtime

Native function semantic truth 并不能回答 logical API contract。

例如：

~~~c
int get_user(
    UserRepository *repo,
    uint64_t id,
    User *out_user);
~~~

CMeta 可以描述参数，但不能自行决定 `repo` 是 host dependency、`id` 是 logical request field、`out_user` 是 logical response。

DataBind 因此增加 Contract IR：

~~~text
service UserService {
    GetUser: GetUserRequest -> GetUserResponse;
}
~~~

Compiler 再把 Contract IR 与 Native Semantic IR join：

~~~text
Service Operation
      +
FunctionDesc
      ↓
BindingPlan
      +
exact adapter
~~~

这些 downstream artifact 都不再拥有独立 service truth：

- HTTP / RPC：transport projection；
- Plugin / WASM：artifact / ABI projection；
- Mock：test projection；
- OpenAPI：由 **Service Contract + HTTP Projection** 派生。

它们共享同一个 logical contract，但并不意味着所有 backend 都从 Service alone 得到完整语义。

---

### 3.1 Live Runtime：新增 state，不复制 semantic truth

Reactive、Executor、Machine、Actor 的作用不是再造一套 application semantics。

它们分别增加有限的 live state：

| Runtime object | 新增的 live concern |
|---|---|
| Subscription | WAIT / Wake / Demand / terminal |
| Executor | bounded admission / settlement |
| Machine Instance | current state / transition commit |
| Actor | mailbox / ref / lifecycle / single owner |
| Plugin lease | DSO lifetime / quiescent unload |

共同原则是：**immutable description 与 live execution state 分开**。

因此同一 Graph、Service 或 Machine definition 可以被不同 runtime instance 重用，而 hot path 不需要重新解释全部 metadata。

---

## 4. 三种 IR 最终形成一条编译链

到这里，全书不再是一组彼此独立的 feature。

| IR | 回答的问题 |
|---|---|
| DataBind Contract IR | What does the program promise? |
| CMeta Native Semantic IR | What is the C implementation? |
| CFlow Execution IR | How is admitted work composed/executed? |

它们通过 compiler/control plane 连接，而不是在 runtime 里动态拼装：

~~~text
DataBind Contract IR
        +
CMeta Native IR
        ↓
binding / validation / generation
        ↓
immutable plans / exact adapters
        ↓
optional CFlow Execution IR
        ↓
lowered ordinary C execution
~~~

第 10 节开始，不再继续回顾功能，而把这条链收敛成一套可重复使用的方法。

## 5. 最终方法：Understand → Model → Formalize → Verify → Implement → Lower → Measure

前面的所有章节最终都可以还原成这七步。

它不是一个必须机械执行的流程，而是一套判断顺序。

---

### 5.1 Understand：先把普通 C 问题看清楚

第一步不是问“Which framework should I use?”、“Which macro should I invent?” 或 “Can Lean prove this?”，而是：

> **如果完全不用新 abstraction，普通 C 会怎么写？**

需要先得到 **Plain C baseline**，然后识别重复的到底是代码、事实、类型关系、runtime decision，还是 semantic reasoning。

如果只是“两段代码长得像”，不要急着抽象。只有当同一份稳定知识已经被多个模块独立维护时，才进入下一步。

---

### 5.2 Model：把真正稳定的知识显式化

Model 不等于“做 DSL”。

它可以很小，例如 Type Descriptor、Trait、Callable Signature、Event Schema、Graph Node、Transition Row 或 Executor State。

一个好的 model 应该明确 data、identity、ownership、lifetime、failure、capacity、state transition 和 module owner。

并且回答：

> **哪些信息是 semantic truth，哪些只是 representation？**

例如：

| Representation / mechanism | Semantic meaning |
|---|---|
| descriptor address | semantic type identity |
| Actor worker thread | Actor lifecycle + mailbox + single mutable owner |

左边是 representation/mechanism，右边才是 semantic meaning。

Model 的目标是把“隐含约定”变成显式程序事实。

---

### 5.3 Formalize：只形式化真正稳定且值得共享的关系

不是所有 model 都应该进入 Lean。

最值得形式化的是 finite type relation、rewrite law、demand invariant、wait/wake state transition、executor ledger、state-machine small step、refinement relation 和 certificate condition。

形式化前先问：

> **Observable semantics 是什么？**

如果这个问题都回答不了，就还不应该证明 rewrite correctness。

形式化的真正价值之一，是暴露设计中没有说清楚的前提。

例如：

- ASSOCIATIVE 到底对什么数值语义成立？
- WAIT 与 SUSPENDED 是不是同一个状态？
- cancel 与 commit 谁是 linearization point？
- parallel reduce 是否保留 encounter order？

Proof obligation 经常会反过来改变 API。

这比“最后补一个 theorem”更有价值。

---

### 5.4 Verify：选择正确层次的证据

Verification 不是 Lean 的同义词。

不同 claim 需要不同证据：

| Claim | Evidence |
|---|---|
| semantic law | Lean theorem |
| generated fact | generator check |
| C representation | compile/runtime tests |
| Multi-TU identity | peer translation-unit test |
| ABI/install | independent installed consumer |
| memory/lifetime | sanitizer |
| race | stress / deterministic concurrency test |
| performance | benchmark |

专业工程的关键是：

> **不拿一种证据去证明它证明不了的东西。**

Lean theorem 不能替代 shared-library link test，benchmark 也不能替代 semantic preservation proof。

---

### 5.5 Implement：让 Formal/Design 落到普通 C Ownership

实现阶段必须重新回到 C 最现实的问题：

- 谁 owns memory？
- 谁 borrow？
- 谁 destroy？
- 谁可以 mutate？
- 什么时候 fail？
- capacity 是多少？
- callback 在哪个 context？
- public ABI 是什么？

最终应该看到真实的 struct、enum、function、status、descriptor、opaque handle、builder 和 destroy，而不是只有 architecture diagram。

这一阶段的标准是：

> **一个不了解 formal proof 的普通 C 工程师，也能通过 public header 理解 ownership 与 failure contract。**

---

### 5.6 Lower：让丰富知识尽量在执行前被消费

Typed model 的目标不是让 runtime 不断查询 metadata。

而是：

~~~text
know more before execution
    ↓
validate earlier
    ↓
bind earlier
    ↓
normalize earlier
    ↓
optimize earlier
    ↓
compile earlier
    ↓
do less per value/event/task
~~~

典型路径：

~~~text
Stream
    ↓
Surface Graph
    ↓
Normalize
    ↓
Optimize
    ↓
Plan / Direct
    ↓
simple execution
~~~

Machine 也是一样：

~~~text
Definition
    ↓
Build validation
    ↓
Immutable Machine
    ↓
Instance
    ↓
selection / guard / action / commit
~~~

Meta 如果无法被消掉，就要问：

> **它是不是其实属于 Runtime Feature？**

---

### 5.7 Measure：最后用现实机器检查成本

只有做到 Measure，才能完整回答“这个 abstraction 值得吗？”。需要区分 control-plane cost、execution cost、memory cost、compile-time cost、binary/ABI cost 和 operational cost。

一个 abstraction 可能 build 慢一点，但执行很多次后更便宜；也可能 API 很漂亮，但 hot path 永远多一层动态 dispatch。

只有 benchmark、profiling、installed build 和真实 workload 能回答这些问题。

所以整个循环不是 “Design → Done”，而是：

~~~text
Understand
→ Model
→ Formalize
→ Verify
→ Implement
→ Lower
→ Measure
        ↓
        └──── feedback to Model/Design
~~~

---

## 6. 三个 Worked Synthesis：同一方法怎样得到不同结果

这套方法最重要的特点是：

> **它不会永远得出“需要更高级 abstraction”。**

---

### 6.1 一个固定 Filter + Map

需求只是遍历数组、保留偶数、平方、写输出。

Understand：one fixed pipeline、one call site、no dynamic composition。

Model：**没有新的稳定知识需要共享**。

结论：

~~~c
for (...) {
    if (!is_even(x))
        continue;
    out[n++] = square(x);
}
~~~

最佳答案就是普通 C。

如果后来出现几十条 pipeline、统一 operator、type propagation、verification 或 multiple execution backends，再升级为 Graph。

---

### 6.2 一个异步数据源

最开始只是 read source / process value。后来 source 需要表达 now has value、temporarily unavailable、done、error，于是 Model 才出现 `VALUE`、`WAIT`、`DONE`、`ERROR`。

再加 downstream demand。

Formalize 暴露出四条关键语义：**WAIT != armed wait**、Wake does not consume demand、Emit consumes demand、Terminal is absorbing。于是 Lean proof 反过来要求 pendingArm、suspended generation 和 explicit cancellation。

最终 C runtime拥有更清晰的 Subscription state machine。

这里 abstraction 是值得的，因为它删除的是每个 async source 重复实现的 race/demand/lifecycle knowledge。

---

### 6.3 一个长期并发 Connection Object

最初可能是：

~~~c
mutex_lock();
switch (state) {
...
}
mutex_unlock();
~~~

如果状态少、event 少、没有多 producer、没有复杂 lifecycle，就继续这样写。

当需求发展到 typed event payload、multiple producers、bounded admission、serialized transition、close/cancel race、stale producer ref 或 formal transition correctness 时，才逐步得到：

~~~text
Typed Event
    ↓
Machine
    ↓
Mailbox
    ↓
Serial Executor
    ↓
Actor lifecycle shell
~~~

Actor 不是起点。

它是需求逐步稳定后的组合结果。

---

## 7. 最终 Equation：这本书所说的 Modern C

前面的设计最终可以压缩成：

~~~text
Ordinary C
+
Explicit Contract IR
+
Explicit Native Semantics
+
Explicit Execution IR
+
Verified High-Risk Transformations
+
Aggressive Lowering
=
Modern C
~~~

这里每一项都有明确对应物。

### 7.1 Ordinary C

保留 native data layout、ordinary ABI、explicit lifetime、direct function calls，以及正常的 compiler / linker / debugger。

### 7.2 Explicit Contract IR

DataBind 用 message、service、channel、component 描述 Contract IR。它回答：**What does the program promise?**

### 7.3 Explicit Native Semantics

CMeta 描述 type identity、traits、FunctionDesc、InterfaceDesc、effects/properties 和 ownership facts。它回答：**What is the C implementation?**

### 7.4 Explicit Execution IR

CFlow 描述 Graph、Plan、Publisher/Subscription、Machine 和 execution relations。它回答：**How is admitted work composed and executed?**

### 7.5 Verified High-Risk Transformations

只有真正有 semantic risk 的 rewrite、normalization、state invariant、refinement 和 certificate 才需要 machine-check。

### 7.6 Aggressive Lowering

尽量在 build、generation、admission 和 control plane 消费高级知识，让最终 hot path 重新接近 ordinary C。

---

## 8. DataBind / CMeta / CFlow / Lean：Promise / Know / Structure / Trust

新的全书关系不是一个“大一统 framework”。

它是四个不同问题。

### 8.1 DataBind — Promise

DataBind 建立 Contract IR，回答四个问题：

- What data is exchanged?
- What operation is promised?
- What messages/events exist?
- Which capabilities form one component?

它不拥有 HTTP socket、Plugin loader、WASM engine 或 CFlow scheduler。

### 8.2 CMeta — Know

CMeta 建立 Native Semantic IR，回答：

- What is this C type?
- What is this native function?
- Which parameter is IN / OUT?
- What ownership/capability is known?
- What semantic identity survives representation boundaries?

### 8.3 CFlow — Structure / Execute

CFlow 建立 Execution IR，回答：

- How are computations related?
- Which execution shapes are admitted?
- How can work be normalized, scheduled, optimized, or lowered?

### 8.4 Lean — Trust selected semantic claims

Lean 不拥有任何 runtime。它只回答 selected semantic claims，例如：

- Does this rewrite preserve observation?
- Does this transition preserve the invariant?
- Does this refinement preserve the promised result?

因此完整关系是：

~~~text
DataBind Contract IR
        +
CMeta Native IR
        ↓
compiler / binding
        ↓
generated plans/adapters
        ↓
optional CFlow Execution IR
        ↓
verified transformation where needed
        ↓
ordinary C execution
~~~

四者共同服务 ordinary C program，而不是建立一个替代 C 的世界。

## 9. 真正的 Modern C 与 Design Checklist

很多语言比较喜欢问：C 能不能有 lambda、generic、stream、actor？

这本书最终更关心另一个问题：

> **C 系统能不能少维护重复知识，同时仍然保持显式 ownership、稳定 ABI、可预测 cost 和普通 toolchain？**

所以“现代”不是更多 syntax sugar，而是更强 semantic sharing、更早 error detection、更明确 ownership、更小 trusted duplication、更可验证 transformation 和更简单 execution。

这是一种 systems-engineering 意义上的 Modern C。

---

### 9.1 给读者的最终 Design Checklist

面对一个新的 C 系统问题，可以按下面顺序问：

1. 普通 C baseline 是什么？
2. 当前真正痛点是什么？
3. 重复的是代码，还是知识？
4. 哪些事实已经稳定？
5. 这些事实属于哪个 module？
6. 是否需要 semantic identity？
7. ownership/lifetime/capacity/failure 是否明确？
8. 哪些错误可以提前？
9. 哪些 dynamic behavior 真的是必要的？
10. observable semantics 是什么？
11. 哪些 law/invariant 值得形式化？
12. theorem 会授权哪个真实实现行为？
13. C representation 是什么？
14. Multi-TU/ABI/install boundary 是否成立？
15. abstraction 能否在 hot path 消失？
16. 性能/内存/并发成本如何测量？
17. 普通 C 是否仍然更简单？

如果第 17 个问题答案是 **Yes**，就用普通 C。

这是一个完全正确的结论。

## 10. 一本 Modern C 书最终应该教会什么

这本书最终希望读者获得的不是“如何记住一套宏 API”，而是以下能力。

### 10.1 从代码中识别稳定知识

知道什么应该继续写代码，什么已经值得成为 schema/type/relation。

### 10.2 从高级 API 中看到底层 ownership

看到 lambda、stream、actor、rpc 时，仍然问：谁 owns？谁 borrow？capacity 是多少？failure 怎样发生？lifetime 是什么？什么会进入 hot path？

### 10.3 从形式证明中得到设计反馈

不是“写完代码后给 theorem 打勾”，而是：

~~~text
proof obligation
    ↓
发现 design ambiguity
    ↓
修改 API/runtime contract
~~~

### 10.4 从 abstraction 中寻找 lowering

每增加一层 abstraction，都问：

> **它最终怎样重新变成简单 C？**

### 10.5 从 benchmark 中保持诚实

不把 zero-cost、faster、scalable 当成设计形容词。

让 measurements 决定。

---

## 11. 最终闭环与 Final Statement

全书从 ordinary C 的 function / static inline / finite macro 分工开始，最后走到：

~~~text
Native Semantic IR
Typed Computation / Execution IR
Formal Semantics / Verified Rewrite
Reactive Execution
Machine / Actor
Contract IR / IDL Compiler
HTTP / RPC / Plugin / WASM projections
ABI / Multi-TU
~~~

看起来跨度很大。

但真正主线一直只有一条：

> **把反复出现而且已经稳定的知识提取出来，建立唯一、显式、可检查的事实源。**

然后再做两件事：**尽量提前消费这些知识；不要让 abstraction 比问题本身更复杂。**

所以最终循环可以写成：

~~~text
Understand
    ↓
Model
    ↓
Formalize
    ↓
Verify
    ↓
Implement
    ↓
Lower
    ↓
Measure
    ↓
Simplify / Refine / Remove
    ↺
~~~

注意最后还有 **Remove**，因为 measurement 和使用经验可能告诉我们：

> 这个 abstraction 不值得存在。

能够删除 abstraction，也是成熟设计的一部分。

---

### 11.1 Final Statement

如果需要用一句完整的话总结这本书：

> **Modern C 不是给 C 套上更多运行时，而是让 C 在执行之前拥有更多有限、明确、可验证的知识，从而在真正执行时做更少、更直接、更可预测的事情。**

或者压缩成两句：

**Know More → Do Less**

以及：

**Ordinary C Remains the Execution Language**

这也是从第一章到最后一章始终没有改变的目标。
