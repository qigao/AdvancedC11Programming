# 第十五章：CMeta 综合应用：从声明事实到可靠执行

本章将前面的技巧放回完整应用：字段声明生成类型事实，函数描述支持绑定与调用，计算图记录组合关系，运行实例负责状态与清理。通过比较这些步骤的输入、输出和证明义务，可以判断一个新需求应由宏、描述符、生成器还是运行时承担。

## 1. 从普通 C 的工具分工到 Native Semantic IR

前面各章建立了下列职责分工，用于判断新需求应放在哪一种机制中：

| 机制 | 负责什么 |
|---|---|
| normal function / static inline | 有类型的行为 |
| finite macro / PP | token、声明、schema replay |
| 编译器 capability | native 编译期 facts |
| CMeta | stable native 语义事实 |
| DataBind | logical contract facts |
| CFlow | execution relations |
| Lean | selected semantic laws |

第一步不是用宏替代 C。而是：

~~~text
ordinary C
    |
    v
identify repeated stable knowledge
    |
    v
use the smallest compile-time / semantic object
    |
    v
return to ordinary C execution
~~~

真正目标仍然是：

一个稳定事实只定义一次，让多个消费者使用它，并尽量在执行前消费掉。

### 1.1 Native Semantic IR：描述 meaning，不自动增加运行时

CMeta 增加的是有限、显式的 native semantic model：

| C reality | Semantic object |
|---|---|
| C type | TypeDesc / semantic identity |
| field facts | Struct / reflected-data metadata |
| capability | Traits / InterfaceDesc |
| native function | FunctionDesc + FunctionAbi |
| executable value | cmeta_callable |
| admitted semantic/execution join | cmeta_invokable |

描述与执行使用不同对象：

| 描述对象 | 执行/绑定对象 |
|---|---|
| FunctionDesc + FunctionAbi | direct C call / optional exact thunk / cmeta_callable / cmeta_invokable |
| InterfaceDesc | live {self,vtable} |

函数反射是 descriptive。它不会因为元数据存在就自动把：

~~~c
add(2, 3);
~~~

改造成运行时反射 dispatch。dynamic / foreign boundary 才需要：

~~~text
raw descriptor
    -> validate / admit once
    -> admitted capability
    -> repeated use
~~~

### 1.2 Generic 与 Type Relation：共享 kernel，不共享万能 router

当前 Generic 入口是有限、明确的：

~~~c
cmeta_type(Vec, IntVec, int);
cmeta_type(Option, MaybeUser, User);
~~~

它只接受注册过的 generic kind。这与 historical universal routing surface 不同：

~~~text
historical:
typed(...)
    -> many unrelated DSL families

current:
cmeta_type(...)
    -> finite Generic declaration only
~~~

有限类型关系仍然来自显式声明行：

~~~c
TypeFunction(CommonArithmetic,
    (int, int, int),
    (int, double, double),
    (double, int, double),
    (double, double, double)
);
~~~

如果没有对应声明行，就明确失败。因此长期纪律仍然是：

finite、explicit、bounded、unsupported is explicit。

### 1.3 Function semantic 与 executable projection：需要哪一层，就显式选择哪一层

普通 direct call：

~~~c
long square(int x);
~~~

不需要 Callable object。需要共享 native function meaning 时：

~~~text
FunctionDecl
    -> FunctionDesc
    -> FunctionAbi
~~~

需要 exact erased invocation 时：

~~~text
FunctionInvokeDecl
    -> explicitly generated exact thunk
~~~

需要 receiver / 参数 binding 时：

~~~text
canonical Function
    -> explicit projection
    -> bounded cmeta_callable capture
    -> cmeta_invokable admission
~~~

receiver operation set 只是：

~~~text
name -> canonical FunctionAbi
~~~

的薄索引，不复制 FunctionDesc。因此最小表示现在是：

| 需求 | 最小表示 |
|---|---|
| direct call | ordinary function / function pointer |
| describe native function | FunctionDesc + FunctionAbi |
| exact erased boundary | explicit exact thunk |
| bind / 捕获 / receiver projection | cmeta_callable + cmeta_invokable |
| long-lived 提供方 | Interface + {self,vtable} |

Bind 的意义是显式参数投影。它不要求再发明一套独立 Lambda object model，也不隐藏 malloc、retain 或 managed 所有权。

## 2. Execution IR 与 Verified Transformation

一旦多个 admitted callable 需要组合，真正新的知识不再是单个函数，而是它们之间的 relation。例如：

~~~text
Source<int>
    ↓
Filter(is_even)
    ↓
Map(square)
    ↓
Reduce(sum)
~~~

Graph 把 topology、type chain、operator semantics 与 callable relation 保存成 program object。这使系统第一次能够在执行前完成：

- type admission；
- normalize；
- semantic rewrite；
- plan compilation；
- Direct/AOT eligibility。

如果只有一个固定 loop，Graph 没有必要存在。

### 2.1 Formal Semantics：证明只服务真实 transformation

一旦 optimizer 想把 P 改成 Q，才真正出现证明 obligation。例如：

~~~text
Map(f); Map(f)  ~>  Map(f)
~~~

需要的不只是 `IDEMPOTENT` 元数据，而是：

~~~text
∀x, f(f(x)) = f(x)
~~~

因此：

| 层 | 证据 |
|---|---|
| 元数据主张 | 准入检查 |
| semantic law | Lean 定理 |
| one concrete 改写 | trace / certificate |
| real C implementation | differential test |
| performance | benchmark |

Lean 不是装饰，也不是 ABI/link/sanitizer 的替代品。

## 3. Contract IR 与 Live Runtime

Native function semantic truth 并不能回答 logical API contract。例如：

~~~c
int get_user(
    UserRepository *repo,
    uint64_t id,
    User *out_user);
~~~

CMeta 可以描述参数，但不能自行决定 `repo` 是 host dependency、`id` 是 logical request 字段、`out_user` 是 logical response。DataBind 因此增加 Contract IR：

~~~text
service UserService {
    GetUser: GetUserRequest -> GetUserResponse;
}
~~~

Compiler 再把 Contract IR 与 Native Semantic IR join：

~~~text
Service Operation
      +
FunctionDesc
      ↓
BindingPlan
      +
exact adapter
~~~

这些 downstream artifact 都不再拥有独立 service truth：

- HTTP / RPC：transport projection；
- Plugin / WASM：artifact / ABI projection；
- Mock：test projection；
- OpenAPI：由 **Service Contract + HTTP Projection** 派生。

它们共享同一个 logical contract，但并不意味着所有 backend 都从 Service alone 得到完整语义。

### 3.1 Live Runtime：新增 state，不复制 semantic truth

Reactive、Executor、Machine、Actor 的作用不是再造一套 application semantics。它们分别增加有限的 live state：

| Runtime object | 新增的 live concern |
|---|---|
| Subscription | WAIT / Wake / Demand / terminal |
| Executor | 有界准入检查 / settlement |
| Machine Instance | current state / transition commit |
| Actor | mailbox / ref / lifecycle / single owner |
| Plugin lease | DSO 生存期 / quiescent unload |

共同原则是：**不可变描述与活动执行状态分开**。因此，同一份 Graph、Service 或 Machine 定义可以被多个运行实例复用，而热路径不必反复解释完整元数据。

## 4. 三种 IR 最终形成一条编译链

到这里，全书不再是一组彼此孤立的功能。

| IR | 回答的问题 |
|---|---|
| DataBind Contract IR | 程序对外承诺什么？ |
| CMeta Native Semantic IR | C 实现实际上是什么？ |
| CFlow Execution IR | 已准入的计算如何组合并执行？ |

它们通过编译器/控制面连接，而不是在运行时里动态拼装：

~~~text
DataBind Contract IR
        +
CMeta Native IR
        ↓
binding / validation / generation
        ↓
immutable plans / exact adapters
        ↓
optional CFlow Execution IR
        ↓
lowered ordinary C execution
~~~

下一节不再逐项回顾功能，而把这条链收敛成一套可以重复使用的判断方法。

## 5. 最终方法：理解 → 建模 → 形式化 → 验证 → 实现 → 降低 → 测量

前面的所有章节最终都可以还原成这七步。它们不是必须机械执行的流水线，而是一组按风险逐层收紧的判断问题。

### 5.1 Understand：先把普通 C 问题看清楚

第一步不是选框架、发明宏，也不是先问 Lean 能不能证明设计，而是先问：**如果不引入任何新抽象，普通 C 会怎么写？** 先得到可运行的普通 C 基线，并写清失败行为；再判断真正重复的是代码、稳定事实、类型关系、运行时决策，还是必须证明的语义关系。两段代码只是“长得像”并不足以抽象。只有同一份稳定知识已经被多个使用方独立维护时，建模才开始有价值。

### 5.2 Model：把真正稳定的知识显式化

模型并不等于“做一门 DSL”。它可以很小，例如类型描述符（Type Descriptor）、Trait、可调用签名（Callable Signature）、事件模式（Event Schema）、Graph Node、Transition Row 或 Executor State。一个好的模型应明确数据、身份、所有权、生存期、失败方式、容量、状态转移和模块归属，并回答一个更关键的问题：**哪些是其他组件可以依赖的语义事实，哪些只是表示或实现机制？** 例如：

| Representation / mechanism | Semantic meaning |
|---|---|
| 描述符地址 | 语义类型身份 |
| Actor 工作线程 | Actor 生命周期 + 邮箱 + 单一可变所有者 |

左边只是表示或机制，右边才是其他组件能够依赖的语义。建模的目标，是把隐含约定变成显式、可检查的程序事实。

### 5.3 Formalize：只形式化真正稳定且值得共享的关系

不是所有模型都应该进入 Lean。最值得形式化的是有限类型关系、改写定律、需求额度不变量、wait/wake 状态转移、执行器账本、状态机小步语义、精化关系和证书条件。形式化之前先定义**可观察语义**：调用者究竟能观察到哪些结果、顺序、错误和资源行为？如果这个问题还不清楚，就不应急着证明改写正确性。形式化的重要价值之一，正是暴露原先没有写明的前提。例如：

- `ASSOCIATIVE` 在什么数值语义下成立？
- `WAIT` 与 `SUSPENDED` 是否表示同一状态？
- cancel 与 commit 的竞争在哪一步线性化？
- 并行归约是否保持输入遇见顺序（encounter order）？

证明义务经常会反过来暴露 API 的歧义，并迫使接口变得更精确。这比“实现完成后再补一个定理”更有价值。

### 5.4 Verify：选择正确层次的证据

验证不等于 Lean。不同主张需要不同层次的证据：

| 主张 | 合适的证据 |
|---|---|
| 语义定律 | Lean 定理 |
| 生成结果 | 生成器一致性检查 |
| C 表示与行为 | 编译与运行测试 |
| 跨翻译单元身份 | 对等翻译单元测试 |
| ABI / 安装边界 | 独立安装后使用方 |
| 内存与生存期 | sanitizer |
| 并发竞争 | 压力测试 / 确定性并发测试 |
| 性能 | benchmark |

专业工程的关键，是让证据与主张处在同一层次。Lean 定理不能替代动态库链接测试，benchmark 也不能替代语义保持证明。

### 5.5 实现：让设计重新落到普通 C 的所有权上

实现阶段必须重新回到 C 最现实的问题：

- 谁拥有内存？
- 谁只是借用？
- 谁负责销毁？
- 谁可以修改状态？
- 失败发生在什么时候？
- 容量是多少？
- 回调在哪个执行上下文运行？
- 对外 ABI 是什么？

最终应该看到真实的 `struct`、`enum`、函数、状态码、描述符、不透明句柄、builder 和销毁路径，而不是只有架构图。一个不了解形式证明的 C 工程师，也应当能仅凭公共头文件理解所有权与失败契约。

### 5.6 降低（Lower）：让丰富知识尽量在执行前被消费

Typed model 的目标不是让运行时不断查询元数据。而是：

~~~text
know more before execution
    ↓
validate earlier
    ↓
bind earlier
    ↓
normalize earlier
    ↓
optimize earlier
    ↓
compile earlier
    ↓
do less per value/event/task
~~~

典型路径：

~~~text
Stream
    ↓
Surface Graph
    ↓
Normalize
    ↓
Optimize
    ↓
Plan / Direct
    ↓
simple execution
~~~

Machine 也是一样：

~~~text
Definition
    ↓
Build validation
    ↓
Immutable Machine
    ↓
Instance
    ↓
selection / guard / action / commit
~~~

如果一份元数据在热路径之前始终无法被消费掉，就要重新判断：它是否其实属于运行时状态或运行时策略，而不是元数据。

### 5.7 测量（Measure）：最后用真实机器检查成本

只有测量才能完整回答“这个抽象值得保留吗？”。需要区分控制面成本、执行成本、内存成本、编译期成本、二进制/ABI 成本和运维成本。一个抽象可能构建更慢，却在大量重复执行后更便宜；也可能 API 很漂亮，却让热路径永久保留一次不必要的动态分派。最终要靠 benchmark、profiling、安装后构建和真实负载来判断。因此整个循环不是“Design → Done”，而是：

~~~text
Understand
→ Model
→ Formalize
→ Verify
→ Implement
→ Lower
→ Measure
        ↓
        └──── feedback to Model/Design
~~~

## 6. 三个综合例子：同一方法为什么会得到不同答案

这套方法的价值，恰恰在于它并不会总是得出“需要更高级抽象”的结论。

### 6.1 一个固定 Filter + Map

如果需求只是遍历数组、保留偶数、平方并写入输出，那么这里只有一条固定 pipeline、一个调用点，也没有动态组合。普通 C 已经完整表达需求，**没有新的稳定知识需要共享**：

~~~c
for (...) {
    if (!is_even(x))
        continue;
    out[n++] = square(x);
}
~~~

此时最佳答案就是普通 C。只有当项目后来出现几十条 pipeline、统一 operator、类型传播、验证需求或多个执行后端时，Graph 才开始解决真实的重复知识。

### 6.2 一个异步数据源

再看异步数据源。起初接口可能只有“读取下一个值”；当数据源必须区分“已有值”“暂时无值”“输入结束”和“错误”时，模型才需要 `VALUE`、`WAIT`、`DONE`、`ERROR`，以及下游需求额度。形式化随后暴露出四条关键规则：`WAIT` 不等于已经登记等待；Wake 不消耗需求额度；Emit 消耗一个需求额度；终止状态一旦建立就不能退出。

这些规则进一步要求 C 运行时显式保存待登记状态、唤醒代次和取消行为，于是 Subscription 状态机变得可以检查。这里抽象是值得的，因为它集中保存了原本会被每个异步数据源重复实现的竞争、需求额度和生命周期知识。

### 6.3 一个长期并发 Connection Object

最初可能是：

~~~c
mutex_lock();
switch (state) {
...
}
mutex_unlock();
~~~

如果状态和事件都很少，没有多个生产者，也不存在复杂生命周期，继续使用这段普通 C 就足够了。只有当需求增长到有类型的事件载荷、多个并发生产者、有界准入、串行状态转移、close/cancel 竞争、过期 producer ref 或可证明的转移正确性时，下面这些结构才逐步变得必要：

~~~text
Typed Event
    ↓
Machine
    ↓
Mailbox
    ↓
Serial Executor
    ↓
Actor lifecycle shell
~~~

Actor 不是起点，而是这些约束逐渐稳定后形成的组合结果。这只是**应用状态对象**的一条路线，而不是每个长连接必须具有的运行时外壳。

若运行时已经采用 Salts 2.3 的 CNet Sharded Graph，则存在更直接的路线：`CNet Owner + admission/placement policy + Manager/ClientPool`。本地 Owner 的选择与远端 Endpoint 的选择是两种不同决策，选择结果不能代替真实容量准入；协议尚未 READY 时不能将连接放入可复用池，传输 Reconnect 也不能授权业务 Retry。CMeta ACE 风格的类型化 Strategy 回调可以在不创建 Actor、第二个 Reactor 或隐藏线程的前提下表示行为。第十二章的 [SG 对照](./ch-11.md)及安装版 [C11 测试](../qualification/ch12_cnet_strategy.c)验证这些边界，但**不会**把它们声称为 Actor Lean 模型的实现证明。

## 7. 最终结论：这本书所说的 Modern C

前面的设计最终可以压缩成：

~~~text
Ordinary C
+
Explicit Contract IR
+
Explicit Native Semantics
+
Explicit Execution IR
+
Verified High-Risk Transformations
+
Aggressive Lowering
=
Modern C
~~~

这里每一项都有明确对应物。

### 7.1 Ordinary C

保留原生数据布局、普通 ABI、显式生存期、直接函数调用，以及常规的编译器、链接器和调试器工具链。

### 7.2 Explicit Contract IR

DataBind 用 `message`、`service`、`channel` 和 `component` 描述 Contract IR。它回答：**程序对外承诺什么？**

### 7.3 Explicit Native Semantics

CMeta 描述类型身份、Trait、FunctionDesc、InterfaceDesc、effects/properties 和所有权事实。它回答：**这个 C 实现实际上是什么？**

### 7.4 Explicit Execution IR

CFlow 描述 Graph、Plan、Publisher/Subscription、Machine 及其执行关系。它回答：**已经准入的计算怎样组合并执行？**

### 7.5 Verified High-Risk Transformations

只有真正涉及语义风险的改写、规范化、状态不变量、精化关系和证书条件，才值得引入机器检查。

### 7.6 Aggressive Lowering

尽量在构建、代码生成、准入检查和控制面阶段消费这些高级知识，让最终热路径重新接近普通 C。

## 8. DataBind / CMeta / CFlow / Lean：承诺、已知事实、执行结构与可信性

这四者不是一个“大一统框架”，而是分别回答四类问题。

### 8.1 DataBind — Promise

DataBind 建立 Contract IR，回答：交换什么数据、承诺什么操作、有哪些 message/event，以及哪些能力共同构成一个 component。它不拥有 HTTP socket、Plugin loader、WASM engine 或 CFlow scheduler；这些属于具体运行时。

### 8.2 CMeta — Know

CMeta 建立 Native Semantic IR，回答：这个 C 类型是什么、这个本地函数是什么、哪些参数是 IN/OUT、已知哪些所有权或能力事实，以及什么语义身份能够跨越表示边界保持稳定。

### 8.3 CFlow — Structure / Execute

CFlow 建立 Execution IR，回答：计算之间怎样关联、哪些执行形状可以准入，以及工作怎样被规范化、调度、优化或降低。

### 8.4 Lean — Trust selected semantic claims

Lean 不拥有任何运行时。它只检查经过选择的语义主张，例如：某次改写是否保持可观察结果、某次状态转移是否保持不变量、某个执行精化是否仍满足原先承诺的结果。

因此完整关系是：

~~~text
DataBind Contract IR
        +
CMeta Native IR
        ↓
compiler / binding
        ↓
generated plans/adapters
        ↓
optional CFlow Execution IR
        ↓
verified transformation where needed
        ↓
ordinary C execution
~~~

四者共同服务于普通 C 程序，而不是建立一个替代 C 的运行世界。

## 9. 真正的 Modern C 与最终检查表

很多语言比较喜欢问：C 能不能拥有 lambda、generic、stream 或 actor？这本书更关心另一个问题：**C 系统能不能少维护重复知识，同时仍然保持显式所有权、稳定 ABI、可预测成本和普通工具链？** 因此，这里所说的“现代”不是更多语法糖，而是更少的重复事实、更早的错误发现、更明确的所有权、更小的可信基、更可验证的变换，以及更简单的执行路径。这是系统工程意义上的 Modern C。

### 9.1 给读者的最终检查表

面对一个新的 C 系统问题，可以按下面顺序问：

1. 普通 C 基线是什么？
2. 当前真正痛点是什么？
3. 重复的是代码，还是知识？
4. 哪些事实已经稳定？
5. 这些事实属于哪个模块？
6. 是否需要稳定的语义身份？
7. 所有权、生存期、容量和失败契约是否明确？
8. 哪些错误可以提前到构建或准入阶段？
9. 哪些动态行为确实不可避免？
10. 可观察语义是什么？
11. 哪些定律或不变量值得形式化？
12. 定理具体授权哪一种实现变换？
13. 对应的 C 表示是什么？
14. Multi-TU、ABI 和安装边界是否成立？
15. 新增抽象能否在热路径中消失？
16. 性能/内存/并发成本如何测量？
17. 普通 C 是否仍然更简单？

如果第 17 个问题答案是“是”，就继续使用普通 C。

## 10. 一本 Modern C 书最终应该教会什么

这本书最终希望读者获得的，不是“如何记住一套宏 API”，而是一组可以迁移到其他 C 系统的判断能力。

### 10.1 从代码中识别稳定知识

能够区分一次性的实现代码与值得共享的稳定事实，并判断后者何时应成为 schema、类型描述或关系。

### 10.2 从高级 API 中看到底层所有权

看到 lambda、stream、actor 或 RPC 时，仍然追问：谁拥有资源、谁只是借用、容量是多少、失败怎样发生、生存期到哪里结束，以及哪些工作最终进入热路径。

### 10.3 从形式证明中得到设计反馈

形式证明不是“写完代码后给定理打勾”，而应参与发现设计歧义：

~~~text
proof obligation
    ↓
发现 design ambiguity
    ↓
修改 API/runtime contract
~~~

### 10.4 从 abstraction 中寻找 lowering

每增加一层抽象，都要问：**它最终怎样重新变成简单 C？**

### 10.5 从 benchmark 中保持诚实

不把 zero-cost、faster、scalable 当成设计形容词；让测量结果决定这些结论是否成立。

## 11. CMeta + ACE 模式地图：先选择责任，再选择模式

`ACE` 提供的是可组合的设计词汇，而不是一套必须全部复制的 class/runtime。CMeta 将接口和调用契约落实为 C11 的静态类型、X-list、FunctionDesc、FunctionAbi 与有限 hook；不同组件仍然保留真正的执行职责。下表按 **Salts 2.3 后续 SDK** 的公开证据区分设计和实现，不改写本书固定版源码快照。

| ACE 模式 | CMeta 负责什么 | 执行和生存期的责任 | 安装版验证 |
|---|---|---|---|
| Strategy / Adapter | 类型化 `{self,vtable}`、Fn ABI、借用的回调 | 普通 C 的服务函数或 CNet client/server | `ch03_cmeta_ace_patterns.c`；`ch12_cnet_strategy.c` |
| Interceptor | exact target/hook、最多 16 个 hook、前向进入/逆向退出 | Caller 保留 hook/context/Plugin Scope | `ch03_cmeta_ace_patterns.c` |
| Scoped/Strategized Locking、Thread-Safe Interface | `cmeta_ace_lockable`、类型安全的同步 body | Platform mutex/RWLock；调用中不得挂起 | `ch03_cmeta_ace_patterns.c` |
| Monitor Object、Thread-Specific Storage、Leader/Followers | 精确接口、CPU-event FunctionDesc、owner 合同 | Platform mutex、condition、TLS、独立 CPU-event Leader 交接 | 本书 `ch10_cmeta_ace_monitor.c` 验证 Monitor/TLS，`ch10_cmeta_ace_leader_followers.c` 独立验证有界 CPU 事件、显式 baton、关闭与计数守恒；非 CNet I/O Reactor |
| Active Object | 有类型应用 Port/Strategy | CFlow Actor、Machine、bounded mailbox、Executor | `ch12_cmeta_ace_active_object.c` |
| Half-Sync/Half-Async、Pipes and Filters | typed channel item、filter/map 函数语义 | CFlow Channel/Graph/Scheduler，容量/需求控制 | 上游 installed CFlow ACE consumer；本书已有 Graph/Channel gate |
| Reactor 风格应用派发 / Acceptor-Connector | CMeta fully reflected typed Handler；不拥有 backend | 调用方执行 listener readiness + CNet client poll；底层 NativeIO 仍由 CNet 消费 | `ch12_ace_reactor_dispatch.c` |
| Proactor / NativeIO SG | 完成回调 ABI 与 one-shot token 身份 | 单一 SG host lease 负责 observe，最终 Owner 负责 terminal/recycle/credit | `ch12_cnet_sg_handoff.c`；`ch03_cmeta_ace_patterns.c` |
| Service Configurator（应用例子） | 配置分别选择有类型 Server Owner 和 Client Destination Strategy | 应用拥有严格解析、调用 lease 和静止点发布；调用真正的 CNet 策略选择 API，**不是通用热部署** | `ch15_cmeta_ace_configurator.c`；`ch15_cmeta_ace_cnet_policy_config.c` |

模式的选择顺序可以写成一段**决策伪代码**，而不是继承关系：

~~~text
fixed direct call?                     -> ordinary C function
multiple implementations, exact ABI?  -> CMeta Strategy
cross-cutting call checks?             -> CMeta Interceptor (borrowed hooks)
shared mutable state?                  -> Platform lock + typed scoped gate
network I/O and many connections?      -> CNet/NativeIO SG Owner + policies
application typed event/state machine? -> CFlow Active Object (optional)
I/O-to-CPU handoff?                    -> bounded CFlow Channel + explicit FULL policy
runtime reconfiguration?               -> validate config, quiesce old owner, replace explicitly
~~~

这里的 `Config/Configurator` 属于**应用控制面设计**：配置文件可以由 DataBind 解析和验证，再选择 `CMeta Strategy` 或 CNet 客户端/服务端策略；它不会自动赋予热替换、Plugin 租约、静默重连或连接迁移的能力。正确的更换顺序需要先停止新准入、结算旧任务和借用，然后发布新的只读配置。没有验收的生命周期，不应以“可动态配置”作为功能承诺。

这两组安装版示例与 CNet SG gate 分别验证：`ABTba/AB21` 的有序拦截、四 worker 下的同步计数、一次性 NativeIO completion、Actor 接受/停止/STALE，以及实际 TCP handoff。它们**不证明**全部 ACE 模式均已实现，也不是性能、sanitizer 或跨平台 ABI 的替代证据；跨平台发布验证由独立的 SDK 矩阵承担。

### 11.1 Service Configurator：配置文件决定 Strategy，但不拥有运行时

ACE 的 Service Configurator 模式首先解决的是**配置何时转换成可调用的行为**。应用可以从文件读取选择，再在明确的控制面边界发布一个借用的 CMeta Interface；这与“任意时刻热替换连接、插件或线程”是不同能力。

[安装版 C11 示例](../qualification/ch15_cmeta_ace_configurator.c) 使用真实配置文件，不使用另一套类系统。文件语法故意保持很小：

~~~text
version=1
strategy=add
operand=3
~~~

三个字段必须各出现一次；`strategy` 仅接受 `add`、`scale`，`operand` 在 `1..16`。未知键、重复键、缺失字段、越界或非法整数均被拒绝。解析到临时 `book_config`，**全部通过后**才向 Owner 持有的、地址稳定的 `active` 写入。工业化的 JSON/YAML 校验可以由 DataBind 承担；本例是为了让读者直接审查解析、发布和拒绝路径，不冒充已实现完整 DataBind Configurator。

~~~text
config file -> strict parser -> candidate typed spec
                                    |
                           validation fails?
                             yes: no publication
                                    |
                            owner + no live lease?
                             no: BUSY / reject
                                    |
                       commit config generation
                                    |
                 acquire a new ONE-SHOT call lease
                                    |
                 bind CMeta self to that lease slot
                                    |
                              ordinary C call
~~~

`CMETA_INTERFACE(book_ace_config_strategy, ...)` 生成一个精确的 **`apply(int value, int *out)` status/out 契约**（`FR2`；返回值是 Salts 状态码，业务结果只写入调用者持有的 `out`）。两份 `CMETA_IMPLEMENTS` 分别选择普通 C 加法或乘法；空输出、整数溢出或失效 lease 在写入之前拒绝，因而可以合法返回负数业务结果而不与错误码混淆。`book_host_acquire()` 需要调用者提供**全新的、零初始化、地址稳定的一次性 lease 槽位**，并让 CMeta Interface 的 `self` 借用这个槽位，而非直接借用共享 `host`。每次 `apply` 都检查 lease 身份、`live`、owner token 和配置代次；释放后的旧 Interface 返回 `SALTS_ESHUTDOWN`，**即使另一份新 lease 已被准入也不会重新生效**。已使用过的槽位永久标记 `spent`，不能用同一地址重新获取，避免指针复用造成旧 Interface 的 ABA 复活。槽位存储必须保持存活，直到所有旧 Interface 不再被检查。调用未结束时 `reload`/`close` 仍必须拒绝；复制 lease 也不会复制释放权限。

~~~text
add.cfg      acquire -> apply(7) = 10
scale.cfg    reload while lease live -> BUSY, generation unchanged
             release once -> OK; repeated release -> STALE
             old Interface.apply() -> ESHUTDOWN, even with new lease
             reuse old lease slot -> STALE (one-shot only)
invalid.cfg  reload -> INVALID, active config unchanged
scale.cfg    reload after quiescence -> generation++ -> apply(7) = 14
close        no live leases -> OK; subsequent acquire -> STALE
~~~

这也是 ACE 在 C 中值得保留的设计技巧：**行为通过有类型 Interface 表达；重配置由拥有它的应用控制面在静止点提交；执行时仍是普通 C 函数**。若需要完整热部署，仍须独立证明 Plugin 租约、CNet Owner、回调结算与连接迁移等边界。本例没有实现那些能力，不能将它写成已发布的 CMeta 通用配置运行时。

### 11.2 Reactor 与 Proactor：分开验证事件派发和异步完成

这两种 ACE 事件模式需要放到同一张架构图中，但不能误认为“都用了异步 I/O，所以等价”：

~~~text
Reactor 风格：listener.wait(READY) -> accept -> owner.poll()
                  -> CMeta typed Observer -> application decision
Proactor：      async NativeIO/CNet submit -> SG host.observe(COMPLETION)
                  -> CNet route_batch -> final Owner terminal/recycle
~~~

第十二章的 [`ch12_ace_reactor_dispatch.c`](../qualification/ch12_ace_reactor_dispatch.c) 为真实 TCP 事件注册并派发有类型观察者，测试 invalid-admission、CONNECTED/terminal 的数量和 callback 生命周期。第十二章另一个 [`ch12_cnet_sg_handoff.c`](../qualification/ch12_cnet_sg_handoff.c) 在两个 SG Owner 上执行真实 completion 分发、socket 转移、双向收发和一次性资源归还。第十章的 `NATIVE_IO_ACE_TOKEN_TYPE` 只负责核验一次 completion 身份，不是另一个 I/O 执行器。

重要边界是：`cnet_client_poll` 的实现本身也由 CNet 消费 NativeIO completion。书中所谓 *Reactor 风格* 只描述调用方的就绪检查与 Handler 分派结构，**不**宣称新的纯 Reactor 后端。应用若已有 CNet SG，就不应为了展示 ACE 模式而再建立第二个 Reactor、Actor 或线程池。

### 11.3 一个真正用于网络的 Service Configurator：Server Owner 与 Client Destination

上一小节的 `add/scale` 演示了如何从真实文件选择一个 Strategy，但网络应用需要同时配置**服务端连接归属**和**客户端远端选择**。它们不是同一件事，更不能借“统一负载均衡”之名让连接在 SG Owner 之间偷偷迁移。

新 C11 安装版例子 [`ch15_cmeta_ace_cnet_policy_config.c`](../qualification/ch15_cmeta_ace_cnet_policy_config.c) 采用封闭的字段合同：

~~~text
version=1
server=strict_key
client=round_robin
~~~

`server` 和 `client` 各自只能选择 `strict_key` 或 `round_robin`。完整解析要求三个字段全部出现且不重复，未知值与缺失字段立即失败。两个 CMeta 接口分别生成 `book_ace_server_policy.select(ticket, out)` 和 `book_ace_client_policy.select(ticket, out)` 的精确 C11 调用（`FR2`，真实 `int *` 输出参数和 ABI 描述）。四份 `CMETA_IMPLEMENTS` 最终调用的**不是仿制算法**，而是已发布的 CNet：

~~~c
/* 本地最终 Owner，key % owner_count */
cnet_owner_placement_choose(&placement, &owner);

/* 远端稳定 endpoint_id，strict-key 用 rendezvous hashing */
cnet_destination_choose(&selection, &destination);
~~~

应用持有一个 `Owner`，每次获取两个借用接口时都提交一个**新的、不可复用的一次性 lease 槽位**。两个 Interface 的 `self` 都指向同一个 lease 槽位，每次调用验证精确的身份与 generation；一个旧 Interface 即使在另一个新租约有效时也不能继续选择 Owner 或 Destination。每个在途调用通过 generation-safe lease 保护；配置的 server/client 更换只能在 `leases == 0` 时进行，并在同一提交中增加一次 generation。外部线程不能取得 lease 或改配置；**把已借出的 Interface 复制到外线程直接调用也会返回 `SALTS_EPERM`**；释放最后一个 lease 后，再使用旧 Interface 返回 `SALTS_ESHUTDOWN`。复制 lease 并不会复制释放权限。`choose` 失败时 `out` 保留旧值：这使“拒绝而不更换 endpoint”成为容易检查的合约。


~~~text
初始文件: strict / strict
    local ticket 5 -> SG Owner 2 (5 % 3)
    remote ticket 5 -> stable endpoint_id (11 / 22 / 33)
    pinned local FULL    -> ENOBUFS, not rerouted
    pinned remote FULL   -> ENOBUFS, not rerouted

活跃调用: reload(strict / rr) -> BUSY
调用全部释放: reload(strict / rr) -> generation + 1
    local ticket 5 -> Owner 2
    remote ticket 5 -> endpoint_id 33

后续 reload(rr / rr):
    owner 2 marked unavailable -> select Owner 0
    endpoint 33 unavailable    -> select endpoint 11
~~~

请注意，Server `choose` 成功仍需 `cnet_handoff_reserve`、`cnet_manager_reserve` 或最终 Owner 的真实 CNet 准入；Client `choose` 成功仍需安全上下文检查、真实 dial 或协议 READY 的连接池 lease。示例**不会**创建 socket、后台重试、Actor 或第二个 Reactor；它资格验证的是应用 ACE Configurator 与 CNet 两类公开 Strategy 的组合控制面，而非端到端负载均衡性能。

### 11.4 两份 CMeta Strategy 如何进入同一条真实 TCP 路径

同一个应用可以同时保留两份 **FR2 status/out** CMeta Strategy，但输出并不代表同一种资源。第十五章 [Configurator 测试](../qualification/ch15_cmeta_ace_cnet_policy_config.c) 以一次性 lease 绑定 `server.select(ticket, int *out)` 和 `client.select(ticket, int *out)`：调用首先检查 lease、调用线程和代次，再执行真正的 CNet 策略 API；拒绝时不得改写 `out`。**策略输出是候选，不是连接、槽位或连接池 Lease。**

~~~text
validate file(server=STRICT_KEY, client=STRICT_KEY/ROUND_ROBIN)
    -> publish config generation only at quiescence
    -> acquire fresh one-shot CMeta call lease
    -> client.select(ticket, &remote_id)   # 远端稳定身份
    -> server.select(ticket, &owner_index) # 本地 SG Owner 下标
    -> release call lease
    -> application performs each independent admission separately
~~~

这里的控制面示意并不是一个已实现的自动组合器：实际测试里，Configurator 检查的是**配置/借用的正确性**；第十二章 [SG live gate](../qualification/ch12_cnet_sg_handoff.c) 检查的是**真实客户端拨号、Owner 移交与资源回收**。后者会先拒绝不可用远端 ID 101（另一个候选仍可用，却不改选），恢复候选后只拨号一次；再拒绝不可用的 strict-key Owner 1，恢复后才执行真实 handoff。两个验证共享公开策略合同，但**没有**声称可在已建立的连接上动态重配置、迁移 Owner 或自动重放逻辑请求。

| 阶段拒绝点 | 必须保持的结果 | 证据 |
|---|---|---|
| CMeta lease 过期 / 配置无效 | `out` 不变；旧 Interface 不复活 | Chapter 15 Configurator |
| 远端 `choose` → `ENOBUFS` | 不改选另一个远端；`connect_attempts=0` | Chapter 12 real TCP |
| 本地 `choose` → `ENOBUFS` | 不改选 Owner；不 detach/publish socket | Chapter 12 real TCP |
| 已选 Owner 的真实 handoff 容量已满 | `reserve` 拒绝，无隐式扩容或 retry | Chapter 12 real TCP |
| 连接终态但 Manager 未 recycle | credit 不得归还；完成 recycle 后只释放一次 | Chapter 12 real TCP |

配置代次描述**未来决策**，不是已建立物理连接的 Owner 身份；远端 ID 描述 **网络目的地**，不是本地 SG shard。要把这些边界做成生产级可重配置服务，应用还需要独立设计真实连接引用、lease 静止点和协议 READY/Retry；不能只复制一份 CMeta Interface 就宣布完成。

### 11.5 Client Pool 的协议 READY 与恢复：Configurator 无法替代资源生命周期

Service Configurator 选择的两个 CMeta Strategy 仍然只决定“用哪个远端候选”和“让哪个本地 SG Owner 负责”。在下一阶段的 [真实 Client Pool/Recovery C11 验收](../qualification/ch12_cnet_pool_recovery.c) 中，客户端 CNet Owner 另有三份**不可互相替代**的状态：Manager 的物理连接身份、Pool 的连接/Lease 台账，以及应用协议的 READY 与槽位 token。

| 阶段 | 判断权由谁持有 | 正确拒绝条件 |
|---|---|---|
| 远端目的地 | Destination Strategy | 不允许的 endpoint 不能静默改选 |
| TCP 连接与终态 | CNet Client + Manager | `BOUND` 不等于业务 READY；Manager 未退休不得 Pool terminal |
| 协议就绪 | 应用实际收到 `RDY!` 并明确发布 | 没有完成握手不得调用 Pool `bind_ready` |
| 借用资源 | Pool + 协议 `reserve/release` | 没有物理/协议双重容量返回 `ENOBUFS` |
| 停止与销毁 | Pool drain + Manager recycle + Lease 归还 | 只要业务还借用 Lease，`destroy` 必须返回 `EBUSY` |
| 逻辑请求重试 | Recovery 时间预算 + Retry 授权 | 默认禁用、一请求一次、安全失败或缺乏重放证据都拒绝 |

按逻辑可写出 `CanLease = READY ∧ compatible_key ∧ ManagerBOUND ∧ physical_capacity ∧ protocol_reserve_succeeded`，但这是**必要条件的组合**，不是额外的 Pool 隐式线程或隐藏重试。我们的实际 Gate 使用真实 TCP 和实际本地协议槽位；`RDY!` 仅为教学用应用标记，不是加密认证，也没有证明远端 exactly-once 或真实多路复用服务。第十二章解释各阶段的程序、失败结算与测试证据。想将其接入实际 HTTP/FlowMQ/P2P，还要保留各协议自身的身份、握手、请求响应和回调租约。

### 11.6 从配置策略到 Signed MMP：按不同状态所有者决定何时归还 Lease

配置选择、协议握手、资源准入和一次真实命令的发送生命周期分别由不同的 Owner 约束。CMeta Strategy 只描述被选中调用的类型，不能直接生成“发送成功”或“允许业务重试”的证明。新的[本书原始 CNet 本地发送 Gate](../qualification/ch12_cnet_pool_recovery.c)展示：只有收到 `RDY!` 并绑定真实 Manager 后才能借出 Pool Lease；一次 `CMD!` 的 `cnet_send_buffer` 入队并不能归还 Lease，必须等待同一 Owner 的原始 `on_send`；远端应用的接收是随后单独检查的事件。独立的另一个 Lease 跨 Manager 物理退休仍保留至业务显式释放。

~~~text
typed Destination/Owner Strategy -> advisory choose
  -> real CNet transport + exact Manager generation
  -> application-authenticated protocol READY
  -> Pool key + actual protocol slot reservation -> Lease
  -> one command send admission (not completion)
  -> original owner send terminal -> once-only Lease release
  -> optional remote application response / explicit replay authorization
  -> Manager RETIRED + all leases settled -> Pool destroy
~~~

这个过程是**必要的生命周期切分**，并非已编写的自动通用 Configurator。对于 TurboP2P [Draft PR #68](https://github.com/qigao/turboP2P/pull/68)，READY 还需真实 Cookie/Noise、签名 MMP HELLO、Router 代次和同一 Manager 物理连接，发送终态需要验证完整加密逻辑写入及物理失败分支。其 [`088d064` 代码](https://github.com/qigao/turboP2P/commit/088d06429ef5348b43e4ee74ce7f5f5d0568ee5e) 和通过的 Linux CI 是**未合并工程分支的研究证据**，不属于当前发布版 Salts SDK，亦非本书 C11 的真实 Signed MMP 集成测试。应用重试必须重新取得当前认证身份、授权与请求证明；Transport 自动恢复、CNet 写终态和远端业务 ACK 是三个不同的事实。

## 12. 小结

CMeta 的高级技巧贯穿同一个过程：用声明保存可共享事实，通过类型和契约检查生成或选择调用方式，再由应用管理实际执行状态。宏展开、函数适配、计算图改写和异步推进各有自己的输入、输出与正确性条件，不能仅凭共用描述符就合并这些责任。面对新应用，先写普通 C 基线和失败行为，再确定哪些事实需要共享；随后给出生成算法或状态转移，推导其前置条件与不变量，并用编译、运行或证明检查具体实现。只有这些步骤带来可确认的维护收益或执行收益，才有理由保留新增机制。
