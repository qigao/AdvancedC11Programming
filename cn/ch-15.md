# 第十五章：CMeta 综合应用：从声明事实到可靠执行

本章将前面的技巧放回完整应用：字段声明生成类型事实，函数描述支持绑定与调用，计算图记录组合关系，运行实例负责状态与清理。通过比较这些步骤的输入、输出和证明义务，可以判断一个新需求应由宏、描述符、生成器还是运行时承担。

## 1. 从普通 C 的工具分工到 Native Semantic IR

前面各章建立了下列职责分工，用于判断新需求应放在哪一种机制中：

| 机制 | 负责什么 |
|---|---|
| normal function / static inline | 有类型的行为 |
| finite macro / PP | token、声明、schema replay |
| 编译器 capability | native 编译期 facts |
| CMeta | stable native 语义事实 |
| DataBind | logical contract facts |
| CFlow | execution relations |
| Lean | selected semantic laws |

第一步不是用宏替代 C。而是：

~~~text
ordinary C
    |
    v
identify repeated stable knowledge
    |
    v
use the smallest compile-time / semantic object
    |
    v
return to ordinary C execution
~~~

真正目标仍然是：

一个稳定事实只定义一次，让多个消费者使用它，并尽量在执行前消费掉。

### 1.1 Native Semantic IR：描述 meaning，不自动增加运行时

CMeta 增加的是有限、显式的 native semantic model：

| C reality | Semantic object |
|---|---|
| C type | TypeDesc / semantic identity |
| field facts | Struct / reflected-data metadata |
| capability | Traits / InterfaceDesc |
| native function | FunctionDesc + FunctionAbi |
| executable value | cmeta_callable |
| admitted semantic/execution join | cmeta_invokable |

描述与执行使用不同对象：

| 描述对象 | 执行/绑定对象 |
|---|---|
| FunctionDesc + FunctionAbi | direct C call / optional exact thunk / cmeta_callable / cmeta_invokable |
| InterfaceDesc | live {self,vtable} |

函数反射是 descriptive。它不会因为元数据存在就自动把：

~~~c
add(2, 3);
~~~

改造成运行时反射 dispatch。dynamic / foreign boundary 才需要：

~~~text
raw descriptor
    -> validate / admit once
    -> admitted capability
    -> repeated use
~~~

### 1.2 Generic 与 Type Relation：共享 kernel，不共享万能 router

当前 Generic 入口是有限、明确的：

~~~c
cmeta_type(Vec, IntVec, int);
cmeta_type(Option, MaybeUser, User);
~~~

它只接受注册过的 generic kind。这与 historical universal routing surface 不同：

~~~text
historical:
typed(...)
    -> many unrelated DSL families

current:
cmeta_type(...)
    -> finite Generic declaration only
~~~

有限类型关系仍然来自显式声明行：

~~~c
TypeFunction(CommonArithmetic,
    (int, int, int),
    (int, double, double),
    (double, int, double),
    (double, double, double)
);
~~~

如果没有对应声明行，就明确失败。因此长期纪律仍然是：

finite、explicit、bounded、unsupported is explicit。

### 1.3 Function semantic 与 executable projection：需要哪一层，就显式选择哪一层

普通 direct call：

~~~c
long square(int x);
~~~

不需要 Callable object。需要共享 native function meaning 时：

~~~text
FunctionDecl
    -> FunctionDesc
    -> FunctionAbi
~~~

需要 exact erased invocation 时：

~~~text
FunctionInvokeDecl
    -> explicitly generated exact thunk
~~~

需要 receiver / 参数 binding 时：

~~~text
canonical Function
    -> explicit projection
    -> bounded cmeta_callable capture
    -> cmeta_invokable admission
~~~

receiver operation set 只是：

~~~text
name -> canonical FunctionAbi
~~~

的薄索引，不复制 FunctionDesc。因此最小表示现在是：

| 需求 | 最小表示 |
|---|---|
| direct call | ordinary function / function pointer |
| describe native function | FunctionDesc + FunctionAbi |
| exact erased boundary | explicit exact thunk |
| bind / 捕获 / receiver projection | cmeta_callable + cmeta_invokable |
| long-lived 提供方 | Interface + {self,vtable} |

Bind 的意义是显式参数投影。它不要求再发明一套独立 Lambda object model，也不隐藏 malloc、retain 或 managed 所有权。

## 2. Execution IR 与 Verified Transformation

一旦多个 admitted callable 需要组合，真正新的知识不再是单个函数，而是它们之间的 relation。例如：

~~~text
Source<int>
    ↓
Filter(is_even)
    ↓
Map(square)
    ↓
Reduce(sum)
~~~

Graph 把 topology、type chain、operator semantics 与 callable relation 保存成 program object。这使系统第一次能够在执行前完成：

- type admission；
- normalize；
- semantic rewrite；
- plan compilation；
- Direct/AOT eligibility。

如果只有一个固定 loop，Graph 没有必要存在。

### 2.1 Formal Semantics：证明只服务真实 transformation

一旦 optimizer 想把 P 改成 Q，才真正出现证明 obligation。例如：

~~~text
Map(f); Map(f)  ~>  Map(f)
~~~

需要的不只是 `IDEMPOTENT` 元数据，而是：

~~~text
∀x, f(f(x)) = f(x)
~~~

因此：

| 层 | 证据 |
|---|---|
| 元数据主张 | 准入检查 |
| semantic law | Lean 定理 |
| one concrete 改写 | trace / certificate |
| real C implementation | differential test |
| performance | benchmark |

Lean 不是装饰，也不是 ABI/link/sanitizer 的替代品。

## 3. Contract IR 与 Live Runtime

Native function semantic truth 并不能回答 logical API contract。例如：

~~~c
int get_user(
    UserRepository *repo,
    uint64_t id,
    User *out_user);
~~~

CMeta 可以描述参数，但不能自行决定 `repo` 是 host dependency、`id` 是 logical request 字段、`out_user` 是 logical response。DataBind 因此增加 Contract IR：

~~~text
service UserService {
    GetUser: GetUserRequest -> GetUserResponse;
}
~~~

Compiler 再把 Contract IR 与 Native Semantic IR join：

~~~text
Service Operation
      +
FunctionDesc
      ↓
BindingPlan
      +
exact adapter
~~~

这些 downstream artifact 都不再拥有独立 service truth：

- HTTP / RPC：transport projection；
- Plugin / WASM：artifact / ABI projection；
- Mock：test projection；
- OpenAPI：由 **Service Contract + HTTP Projection** 派生。

它们共享同一个 logical contract，但并不意味着所有 backend 都从 Service alone 得到完整语义。

### 3.1 Live Runtime：新增 state，不复制 semantic truth

Reactive、Executor、Machine、Actor 的作用不是再造一套 application semantics。它们分别增加有限的 live state：

| Runtime object | 新增的 live concern |
|---|---|
| Subscription | WAIT / Wake / Demand / terminal |
| Executor | 有界准入检查 / settlement |
| Machine Instance | current state / transition commit |
| Actor | mailbox / ref / lifecycle / single owner |
| Plugin lease | DSO 生存期 / quiescent unload |

共同原则是：**不可变描述与活动执行状态分开**。因此，同一份 Graph、Service 或 Machine 定义可以被多个运行实例复用，而热路径不必反复解释完整元数据。

## 4. 三种 IR 最终形成一条编译链

到这里，全书不再是一组彼此孤立的功能。

| IR | 回答的问题 |
|---|---|
| DataBind Contract IR | 程序对外承诺什么？ |
| CMeta Native Semantic IR | C 实现实际上是什么？ |
| CFlow Execution IR | 已准入的计算如何组合并执行？ |

它们通过编译器/控制面连接，而不是在运行时里动态拼装：

~~~text
DataBind Contract IR
        +
CMeta Native IR
        ↓
binding / validation / generation
        ↓
immutable plans / exact adapters
        ↓
optional CFlow Execution IR
        ↓
lowered ordinary C execution
~~~

下一节不再逐项回顾功能，而把这条链收敛成一套可以重复使用的判断方法。

## 5. 最终方法：理解 → 建模 → 形式化 → 验证 → 实现 → 降低 → 测量

前面的所有章节最终都可以还原成这七步。它们不是必须机械执行的流水线，而是一组按风险逐层收紧的判断问题。

### 5.1 Understand：先把普通 C 问题看清楚

第一步不是选框架、发明宏，也不是先问 Lean 能不能证明设计，而是先问：**如果不引入任何新抽象，普通 C 会怎么写？** 先得到可运行的普通 C 基线，并写清失败行为；再判断真正重复的是代码、稳定事实、类型关系、运行时决策，还是必须证明的语义关系。两段代码只是“长得像”并不足以抽象。只有同一份稳定知识已经被多个使用方独立维护时，建模才开始有价值。

### 5.2 Model：把真正稳定的知识显式化

模型并不等于“做一门 DSL”。它可以很小，例如类型描述符（Type Descriptor）、Trait、可调用签名（Callable Signature）、事件模式（Event Schema）、Graph Node、Transition Row 或 Executor State。一个好的模型应明确数据、身份、所有权、生存期、失败方式、容量、状态转移和模块归属，并回答一个更关键的问题：**哪些是其他组件可以依赖的语义事实，哪些只是表示或实现机制？** 例如：

| Representation / mechanism | Semantic meaning |
|---|---|
| 描述符地址 | 语义类型身份 |
| Actor 工作线程 | Actor 生命周期 + 邮箱 + 单一可变所有者 |

左边只是表示或机制，右边才是其他组件能够依赖的语义。建模的目标，是把隐含约定变成显式、可检查的程序事实。

### 5.3 Formalize：只形式化真正稳定且值得共享的关系

不是所有模型都应该进入 Lean。最值得形式化的是有限类型关系、改写定律、需求额度不变量、wait/wake 状态转移、执行器账本、状态机小步语义、精化关系和证书条件。形式化之前先定义**可观察语义**：调用者究竟能观察到哪些结果、顺序、错误和资源行为？如果这个问题还不清楚，就不应急着证明改写正确性。形式化的重要价值之一，正是暴露原先没有写明的前提。例如：

- `ASSOCIATIVE` 在什么数值语义下成立？
- `WAIT` 与 `SUSPENDED` 是否表示同一状态？
- cancel 与 commit 的竞争在哪一步线性化？
- 并行归约是否保持输入遇见顺序（encounter order）？

证明义务经常会反过来暴露 API 的歧义，并迫使接口变得更精确。这比“实现完成后再补一个定理”更有价值。

### 5.4 Verify：选择正确层次的证据

验证不等于 Lean。不同主张需要不同层次的证据：

| 主张 | 合适的证据 |
|---|---|
| 语义定律 | Lean 定理 |
| 生成结果 | 生成器一致性检查 |
| C 表示与行为 | 编译与运行测试 |
| 跨翻译单元身份 | 对等翻译单元测试 |
| ABI / 安装边界 | 独立安装后使用方 |
| 内存与生存期 | sanitizer |
| 并发竞争 | 压力测试 / 确定性并发测试 |
| 性能 | benchmark |

专业工程的关键，是让证据与主张处在同一层次。Lean 定理不能替代动态库链接测试，benchmark 也不能替代语义保持证明。

### 5.5 实现：让设计重新落到普通 C 的所有权上

实现阶段必须重新回到 C 最现实的问题：

- 谁拥有内存？
- 谁只是借用？
- 谁负责销毁？
- 谁可以修改状态？
- 失败发生在什么时候？
- 容量是多少？
- 回调在哪个执行上下文运行？
- 对外 ABI 是什么？

最终应该看到真实的 `struct`、`enum`、函数、状态码、描述符、不透明句柄、builder 和销毁路径，而不是只有架构图。一个不了解形式证明的 C 工程师，也应当能仅凭公共头文件理解所有权与失败契约。

### 5.6 降低（Lower）：让丰富知识尽量在执行前被消费

Typed model 的目标不是让运行时不断查询元数据。而是：

~~~text
know more before execution
    ↓
validate earlier
    ↓
bind earlier
    ↓
normalize earlier
    ↓
optimize earlier
    ↓
compile earlier
    ↓
do less per value/event/task
~~~

典型路径：

~~~text
Stream
    ↓
Surface Graph
    ↓
Normalize
    ↓
Optimize
    ↓
Plan / Direct
    ↓
simple execution
~~~

Machine 也是一样：

~~~text
Definition
    ↓
Build validation
    ↓
Immutable Machine
    ↓
Instance
    ↓
selection / guard / action / commit
~~~

如果一份元数据在热路径之前始终无法被消费掉，就要重新判断：它是否其实属于运行时状态或运行时策略，而不是元数据。

### 5.7 测量（Measure）：最后用真实机器检查成本

只有测量才能完整回答“这个抽象值得保留吗？”。需要区分控制面成本、执行成本、内存成本、编译期成本、二进制/ABI 成本和运维成本。一个抽象可能构建更慢，却在大量重复执行后更便宜；也可能 API 很漂亮，却让热路径永久保留一次不必要的动态分派。最终要靠 benchmark、profiling、安装后构建和真实负载来判断。因此整个循环不是“Design → Done”，而是：

~~~text
Understand
→ Model
→ Formalize
→ Verify
→ Implement
→ Lower
→ Measure
        ↓
        └──── feedback to Model/Design
~~~

## 6. 三个综合例子：同一方法为什么会得到不同答案

这套方法的价值，恰恰在于它并不会总是得出“需要更高级抽象”的结论。

### 6.1 一个固定 Filter + Map

如果需求只是遍历数组、保留偶数、平方并写入输出，那么这里只有一条固定 pipeline、一个调用点，也没有动态组合。普通 C 已经完整表达需求，**没有新的稳定知识需要共享**：

~~~c
for (...) {
    if (!is_even(x))
        continue;
    out[n++] = square(x);
}
~~~

此时最佳答案就是普通 C。只有当项目后来出现几十条 pipeline、统一 operator、类型传播、验证需求或多个执行后端时，Graph 才开始解决真实的重复知识。

### 6.2 一个异步数据源

再看异步数据源。起初接口可能只有“读取下一个值”；当数据源必须区分“已有值”“暂时无值”“输入结束”和“错误”时，模型才需要 `VALUE`、`WAIT`、`DONE`、`ERROR`，以及下游需求额度。形式化随后暴露出四条关键规则：`WAIT` 不等于已经登记等待；Wake 不消耗需求额度；Emit 消耗一个需求额度；终止状态一旦建立就不能退出。

这些规则进一步要求 C 运行时显式保存待登记状态、唤醒代次和取消行为，于是 Subscription 状态机变得可以检查。这里抽象是值得的，因为它集中保存了原本会被每个异步数据源重复实现的竞争、需求额度和生命周期知识。

### 6.3 一个长期并发 Connection Object

最初可能是：

~~~c
mutex_lock();
switch (state) {
...
}
mutex_unlock();
~~~

如果状态和事件都很少，没有多个生产者，也不存在复杂生命周期，继续使用这段普通 C 就足够了。只有当需求增长到有类型的事件载荷、多个并发生产者、有界准入、串行状态转移、close/cancel 竞争、过期 producer ref 或可证明的转移正确性时，下面这些结构才逐步变得必要：

~~~text
Typed Event
    ↓
Machine
    ↓
Mailbox
    ↓
Serial Executor
    ↓
Actor lifecycle shell
~~~

Actor 不是起点，而是这些约束逐渐稳定后形成的组合结果。

## 7. 最终结论：这本书所说的 Modern C

前面的设计最终可以压缩成：

~~~text
Ordinary C
+
Explicit Contract IR
+
Explicit Native Semantics
+
Explicit Execution IR
+
Verified High-Risk Transformations
+
Aggressive Lowering
=
Modern C
~~~

这里每一项都有明确对应物。

### 7.1 Ordinary C

保留原生数据布局、普通 ABI、显式生存期、直接函数调用，以及常规的编译器、链接器和调试器工具链。

### 7.2 Explicit Contract IR

DataBind 用 `message`、`service`、`channel` 和 `component` 描述 Contract IR。它回答：**程序对外承诺什么？**

### 7.3 Explicit Native Semantics

CMeta 描述类型身份、Trait、FunctionDesc、InterfaceDesc、effects/properties 和所有权事实。它回答：**这个 C 实现实际上是什么？**

### 7.4 Explicit Execution IR

CFlow 描述 Graph、Plan、Publisher/Subscription、Machine 及其执行关系。它回答：**已经准入的计算怎样组合并执行？**

### 7.5 Verified High-Risk Transformations

只有真正涉及语义风险的改写、规范化、状态不变量、精化关系和证书条件，才值得引入机器检查。

### 7.6 Aggressive Lowering

尽量在构建、代码生成、准入检查和控制面阶段消费这些高级知识，让最终热路径重新接近普通 C。

## 8. DataBind / CMeta / CFlow / Lean：承诺、已知事实、执行结构与可信性

这四者不是一个“大一统框架”，而是分别回答四类问题。

### 8.1 DataBind — Promise

DataBind 建立 Contract IR，回答：交换什么数据、承诺什么操作、有哪些 message/event，以及哪些能力共同构成一个 component。它不拥有 HTTP socket、Plugin loader、WASM engine 或 CFlow scheduler；这些属于具体运行时。

### 8.2 CMeta — Know

CMeta 建立 Native Semantic IR，回答：这个 C 类型是什么、这个本地函数是什么、哪些参数是 IN/OUT、已知哪些所有权或能力事实，以及什么语义身份能够跨越表示边界保持稳定。

### 8.3 CFlow — Structure / Execute

CFlow 建立 Execution IR，回答：计算之间怎样关联、哪些执行形状可以准入，以及工作怎样被规范化、调度、优化或降低。

### 8.4 Lean — Trust selected semantic claims

Lean 不拥有任何运行时。它只检查经过选择的语义主张，例如：某次改写是否保持可观察结果、某次状态转移是否保持不变量、某个执行精化是否仍满足原先承诺的结果。

因此完整关系是：

~~~text
DataBind Contract IR
        +
CMeta Native IR
        ↓
compiler / binding
        ↓
generated plans/adapters
        ↓
optional CFlow Execution IR
        ↓
verified transformation where needed
        ↓
ordinary C execution
~~~

四者共同服务于普通 C 程序，而不是建立一个替代 C 的运行世界。

## 9. 真正的 Modern C 与最终检查表

很多语言比较喜欢问：C 能不能拥有 lambda、generic、stream 或 actor？这本书更关心另一个问题：**C 系统能不能少维护重复知识，同时仍然保持显式所有权、稳定 ABI、可预测成本和普通工具链？** 因此，这里所说的“现代”不是更多语法糖，而是更少的重复事实、更早的错误发现、更明确的所有权、更小的可信基、更可验证的变换，以及更简单的执行路径。这是系统工程意义上的 Modern C。

### 9.1 给读者的最终检查表

面对一个新的 C 系统问题，可以按下面顺序问：

1. 普通 C 基线是什么？
2. 当前真正痛点是什么？
3. 重复的是代码，还是知识？
4. 哪些事实已经稳定？
5. 这些事实属于哪个模块？
6. 是否需要稳定的语义身份？
7. 所有权、生存期、容量和失败契约是否明确？
8. 哪些错误可以提前到构建或准入阶段？
9. 哪些动态行为确实不可避免？
10. 可观察语义是什么？
11. 哪些定律或不变量值得形式化？
12. 定理具体授权哪一种实现变换？
13. 对应的 C 表示是什么？
14. Multi-TU、ABI 和安装边界是否成立？
15. 新增抽象能否在热路径中消失？
16. 性能/内存/并发成本如何测量？
17. 普通 C 是否仍然更简单？

如果第 17 个问题答案是“是”，就继续使用普通 C。

## 10. 一本 Modern C 书最终应该教会什么

这本书最终希望读者获得的，不是“如何记住一套宏 API”，而是一组可以迁移到其他 C 系统的判断能力。

### 10.1 从代码中识别稳定知识

能够区分一次性的实现代码与值得共享的稳定事实，并判断后者何时应成为 schema、类型描述或关系。

### 10.2 从高级 API 中看到底层所有权

看到 lambda、stream、actor 或 RPC 时，仍然追问：谁拥有资源、谁只是借用、容量是多少、失败怎样发生、生存期到哪里结束，以及哪些工作最终进入热路径。

### 10.3 从形式证明中得到设计反馈

形式证明不是“写完代码后给定理打勾”，而应参与发现设计歧义：

~~~text
proof obligation
    ↓
发现 design ambiguity
    ↓
修改 API/runtime contract
~~~

### 10.4 从 abstraction 中寻找 lowering

每增加一层抽象，都要问：**它最终怎样重新变成简单 C？**

### 10.5 从 benchmark 中保持诚实

不把 zero-cost、faster、scalable 当成设计形容词；让测量结果决定这些结论是否成立。

## 11. 小结

CMeta 的高级技巧贯穿同一个过程：用声明保存可共享事实，通过类型和契约检查生成或选择调用方式，再由应用管理实际执行状态。宏展开、函数适配、计算图改写和异步推进各有自己的输入、输出与正确性条件，不能仅凭共用描述符就合并这些责任。面对新应用，先写普通 C 基线和失败行为，再确定哪些事实需要共享；随后给出生成算法或状态转移，推导其前置条件与不变量，并用编译、运行或证明检查具体实现。只有这些步骤带来可确认的维护收益或执行收益，才有理由保留新增机制。
