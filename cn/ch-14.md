# 第十四章：有限、显式、按需——什么时候应该停止 Meta 化

> **本章只问一个问题：**
>
> 一个 abstraction 删除的稳定重复，是否真的大于它引入的长期成本？
>
> 如果答案是否定的，就继续写普通 C。

---

## 1. Decision Tree：先问是否真的需要抽象

~~~text
problem appears
    |
    v
Can ordinary C express it clearly?
    |
   yes
    |
    v
Is stable knowledge duplicated across modules/backends?
    |
   no -----------------> keep ordinary C
    |
   yes
    |
    v
Can that knowledge be finite / explicit / bounded?
    |
   no -----------------> keep it local or runtime-specific
    |
   yes
    |
    v
Does one shared semantic object remove real maintenance/correctness risk?
    |
   no -----------------> keep ordinary C
    |
   yes
    |
    v
introduce the smallest semantic object
~~~

抽象不是默认答案。


### 1.1 先选最小的 C 机制，再决定是否需要 semantic object

第一章的工具分工在这里变成 restraint rule：

~~~text
Can a normal C function express the behavior?
        |
       yes
        v
normal function / static inline

Need tokens, declarations, identifiers, or finite schema replay?
        |
       yes
        v
finite macro / PP kernel

Need compiler-native knowledge?
        |
       yes
        v
capability-gated compiler abstraction

Need stable meaning shared by independent consumers?
        |
       yes
        v
canonical Reflection / semantic descriptor
~~~

特别要拒绝这条路线：

~~~text
macro
  -> more macro
  -> hidden behavior
  -> hidden allocation / dispatch / ownership
~~~

更好的默认形状是：

~~~text
schema / facts
    |
    v
small finite macro
    |
    v
static-inline typed facade
    |
    v
shared ordinary-C implementation
~~~

Macro 负责 C function 无法表达的 token/declaration generation。

static inline 负责 typed behavior、正常求值规则与 direct-call surface。

Reflection 只在 stable meaning 需要被多个 consumer 共享时出现。

> **不要因为可以用 macro 写 behavior，就让 macro 取代类型明确的 C function；也不要因为已有 Reflection，就让 direct C call 变成 runtime reflection dispatch。**

## 2. 四个“普通 C 更好”的正例

### 2.1 一个固定 Pipeline：保留 loop

~~~c
size_t copy_even_squares(
    const int *xs,
    size_t n,
    long *out)
{
    size_t m = 0;

    for (size_t i = 0; i < n; ++i) {
        int x = xs[i];

        if ((x & 1) != 0)
            continue;

        out[m++] = (long)x * x;
    }

    return m;
}
~~~

如果只有 one pipeline、one call site，没有 dynamic composition、rewrite、verification 或 alternate backend，Graph 没有删除新的稳定重复。

结论：**keep the loop**。

### 2.2 一个 Callback：保留 function pointer

~~~c
typedef void (*done_fn)(void *user);

void request_start(done_fn done, void *user);
~~~

如果 callback 不跨复杂 lifetime 保存、不组合、不反射、不优化，就不需要 Callable object。

### 2.3 一个内部函数：不要引入 IDL

~~~c
static int
lookup_user(
    UserRepository *repo,
    uint64_t id,
    User *out);
~~~

如果它只在一个 binary 内直接调用，没有 HTTP / RPC / Plugin / WASM / generated Mock / external contract，就不需要 message、service、component 或 databindc。

IDL 的价值来自 **same logical contract repeated across boundaries**，不是来自“函数存在”。

### 2.4 一个 link-time 已知实现：不要引入 Plugin

~~~cmake
target_link_libraries(app PRIVATE image_codec)
~~~

如果 implementation 唯一、link time 已知、不需要 discovery / replacement / unload，direct link 比 loader + registry + manifest + lease + quiescent unload 更简单。

## 3. Counterexample Lab：六种最危险的“方便”

### 3.1 只有一次重复，就立刻造 Meta DSL

~~~c
int user_age(const User *u)
{
    return u->age;
}

int order_count(const Order *o)
{
    return o->count;
}
~~~

因为两个函数形状相似，就设计 FieldGetter、GenerateAccessor、Reflect、GenericInvoke。

问题在于：你抽象的是**当前代码形状**，不是稳定知识。

只有当 field schema 被 serializer、binder、UI、query 等多个独立消费者重复维护时，Field Metadata 才成为共享事实。

---

### 3.2 Descriptor pointer 被当成 semantic identity

错误：

~~~c
if (a == b) {
    /* same type */
}
~~~

单 TU 可能一直绿；Multi-TU / DSO 后，同一个 Pair<int,long> 可以拥有多个 descriptor object。

地址回答“representation object 在哪里”，不是“semantic type 是什么”。

正确做法是 stable id + constructor identity + structural arguments。

---

### 3.3 Inline capture 超限后偷偷 malloc

错误策略：

~~~text
capture > inline_capacity
    ↓
secret malloc
    ↓
API still looks like bounded value semantics
~~~

这会悄悄改变 copy、destroy、failure、thread/lifetime 与 ABI contract。

正确选择必须显式：

- TOO_LARGE；
- explicit heap-backed callable；
- caller-owned external context。

> **Hidden convenience that changes ownership is semantic drift.**

---

### 3.4 Queue 满了就自动增长

错误策略：

~~~text
queue full
    ↓
realloc / linked-list growth
    ↓
keep accepting
~~~

当 producer rate > consumer rate 时，这不会产生 backpressure，只会产生更晚的 memory / latency / OOM failure。

正确 primitive：

~~~text
capacity exhausted
    ↓
FULL
~~~

上层再显式决定 retry、drop、shed load 或 backpressure。

---

### 3.5 Requested execution 不可用时 silent fallback

用户显式请求 parallel reduce，但 reducer contract 不满足、Executor FULL 或 backend 不支持。

错误行为：

~~~text
parallel requested
    ↓ failure
quietly run sequentially
~~~

即使 result 相同，latency、CPU topology、resource usage、deadline behavior 与 benchmark 都变了。

正确行为是返回 UNSUPPORTED / FULL / INELIGIBLE，由 application 明确选择 fallback。

> **Semantic equivalence does not imply operational equivalence.**

---

### 3.6 “上层需要”就把 domain semantics 塞进 Core

典型漂移：

- RPC 需要 retry → 把 retry policy 放进 Executor；
- Workflow 需要 compensation → 把 compensation 放进 Machine；
- JSON 需要 field name → 把 JSON syntax 放进 CMeta。

判断规则只有三个：

1. 这个 meaning 是否 domain-specific？
2. 是否在多个独立 domain 中稳定重复？
3. Core 在没有它时是否仍然完整？

如果答案是 domain-specific，就留在上层。

> **Reuse does not require ownership transfer.**

## 5. Cost 与 Evidence 必须同时预算

一个 abstraction 进入 Core，不只增加 API，也增加永久维护义务。

| Abstraction | 删除什么重复 | 新增长期成本 |
|---|---|---|
| Generic | repeated type-instantiation facts | generated API / diagnostics |
| FunctionDesc | repeated native function metadata | descriptor ABI / ownership rules |
| Graph | repeated composition / analysis logic | IR + optimizer + qualification |
| DataBind IDL | repeated logical contracts | compiler + versioning + codegen |
| Plugin | dynamic capability publication | loader + lease + unload ABI |
| WASM | portable component ABI | host/guest lowering |
| Actor | concurrency admission/lifecycle duplication | mailbox/ref/generation protocol |

每一种新能力还必须带上对应 evidence：

| New claim | Required gate |
|---|---|
| generated syntax | compile-pass / compile-fail |
| semantic identity | Multi-TU / DSO tests |
| lifecycle | sanitizer / stress |
| rewrite | semantic theorem + differential test |
| public ABI | installed consumer |
| performance | benchmark |
| projection backend | end-to-end integration |

如果长期成本和 evidence budget 都无法解释，abstraction 还不应该进入 Core。

## 6. Static Interior，Dynamic Boundary

不要为了“统一”把所有东西都做成 {self, vtable}。

| 区域 | 例子 |
|---|---|
| Dynamic Boundary | Publisher / Scheduler / plugin provider |
| Static Interior | known Graph stage / Plan instruction / direct target |

Dynamic interface 是 boundary tool，不是 universal object model。

已知信息应尽量在 build/control plane 消费掉，让 hot path 回到更直接的 C。

---

## 7. Review Checklist

设计新的 Meta / Runtime abstraction 时，直接问：

- [ ] 有没有 Plain C baseline？
- [ ] 重复的是稳定知识，还是只是代码形状？
- [ ] 是否至少有两个独立消费者需要同一事实？
- [ ] 为什么不能只是 module-local helper？
- [ ] identity 是否跨 TU / DSO？
- [ ] ownership / failure / capacity 是否显式？
- [ ] 是否存在 hidden allocation / silent fallback？
- [ ] dynamic dispatch 是否进入不必要的 hot path？
- [ ] failure 是否尽可能提前？
- [ ] theorem / toolchain / benchmark 是否各自证明正确层次的 claim？
- [ ] abstraction 能否在 hot path 中被 lower 掉？

如果很多项答不上来，正确动作通常不是“继续完善 abstraction”，而是**缩小 abstraction**。

---

## 8. What We Learned

Restraint 不是“少做功能”。

它是一种系统能力：

> **只把值得长期维护的稳定知识提升成共享语义。**

Modern C 同时需要两种能力：

- 知道什么时候应该建立 Typed / Verified abstraction；
- 知道什么时候一个 loop、function pointer、switch、struct 或 direct link 已经更好。

下一章不再增加 feature。

它只保留一套方法：

~~~text
Understand
→ Model
→ Formalize
→ Verify
→ Implement
→ Lower
→ Measure
~~~

并用它回答：

> **什么才是这本书所说的 Modern C？**
