# 第十四章：高级技巧的取舍：何时保留普通 C

描述符、生成器和运行时对象都增加维护责任。选择 CMeta 技巧时，应比较它消除的重复事实与新增的类型、容量、生存期和构建约束。本章从一个有完整边界的普通 C 函数出发，分析什么时候继续使用它，什么时候增加宏、反射或执行对象。

## 1. 一个受界的 Filter/Map 函数

下面的普通 C 函数需要 `<stdbool.h>` 和 `<stddef.h>`。它接受最多一千个 `[-100, 100]` 内的整数，把偶数平方写入 `long` 数组。非空数组必须有效，输入、完整输出存储和 `written` 所指对象必须互不重叠；这是调用方前提，空指针检查不能证明对象有效。

~~~c
bool book_copy_even_squares(
    const int *xs, size_t n,
    long *out, size_t capacity, size_t *written)
{
    if (written == NULL || n > 1000 || capacity < n)
        return false;
    if (n != 0 && (xs == NULL || out == NULL))
        return false;
    for (size_t i = 0; i < n; ++i)
        if (xs[i] < -100 || xs[i] > 100)
            return false;

    size_t m = 0;
    for (size_t i = 0; i < n; ++i) {
        int x = xs[i];
        if (x % 2 == 0)
            out[m++] = (long)x * x;
    }
    *written = m;
    return true;
}
~~~

先检查全部值域，随后才写输出，因此无效输入不会留下部分平方结果。容量要求 `capacity >= n` 比实际保留数量更强，但使函数在执行谓词前就能确定空间足够。若需要精确小容量，可另行设计两遍计数协议；它增加遍历成本，并要求两遍之间输入不变。

## 2. 从循环不变量推导正确性

在第二个循环开始处理下标 `i` 时，不变量为：`0 <= m <= i`，输出前 `m` 项恰好是输入前 `i` 项中偶数的平方，顺序相同。初始 `i=m=0` 成立。奇数不写输出，不变量随 `i` 增加保持；偶数在 `m` 位置写入平方并增加 `m`，由于 `m <= i < n <= capacity`，写入在界内。

输入检查保证平方不超过 `10000`，所以乘法由 `long` 安全表示。循环结束得到全部保留值，`written` 记录数量。对于 `{1,2,3,4,5,6}`，结果为 `{4,16,36}` 和数量三；空输入成功且数量零。除调用方存储前提外，失败均发生在首次输出写入前。

这些性质已经足以服务一个固定调用点。增加 Graph 只有在需要检查或变换组合、统一维护多条管道、或选择多个执行形式时，才消除新的重复工作。否则图的构造、错误处理与销毁只会扩大实现。

## 3. 按信息需求选择机制

| 需求 | 适合的起点 | 新增条件 |
|---|---|---|
| 已知类型的计算 | 普通函数或 `static inline` | 参数和值域前提 |
| 生成字段、标识符或声明 | 有限宏与共享 schema | 展开上限、分隔符和诊断 |
| 调用点原生类型检查 | 编译器能力入口 | 支持的编译模式 |
| 多个使用方共享类型或函数事实 | CMeta 描述符 | 语义身份、配置及生存期 |
| 多种计算组合与执行形式 | CFlow Graph/Plan | 支持范围、变换证明和资源 |
| 对外复用逻辑服务 | DataBind 契约与投影 | 版本、绑定、错误与传输限制 |

`static inline` 能遵守函数参数的正常求值规则；宏则能生成函数做不到的声明和记号。两者配合比把行为都塞进宏更容易检查。描述符提供共享知识，但一个已知直接调用不必因此改走动态反射。

两个结构相似的 getter 并不自动构成需要反射的事实。若字段表确实被序列化器、绑定器和校验器独立维护，第二章的共享 schema 才有明确收益：修改字段时多个使用方从同一输入生成。

## 4. 回调、契约与动态模块的最小选择

一个简单异步入口可以保留以下普通 C 声明：

~~~c
typedef void (*book_done_fn)(void *user);
void book_request_start(book_done_fn done, void *user);
~~~

这仍需说明回调是否必定执行、是否可能同步执行、取消后何时结束借用，以及 `user` 由谁释放。只是不需要参数绑定、反射或组合时，可以不增加 Callable 对象。简单接口不会自动免除生存期设计。

同理，只在一个二进制内直接调用的 `get_user` 通常不需要 IDL。多个外部使用方重复维护同一请求、响应和错误规则时，再引入契约编译。若实现始终在链接时确定，`target_link_libraries(app PRIVATE image_codec)` 已经表达依赖；Plugin 增加的发现、替换与卸载能力应有实际需求。

## 5. 隐藏分配怎样改变契约

第三章的固定捕获容量使复制 Callable 只需复制规定的字节。若超限后自动改为堆对象，复制就需要回答共享还是深拷贝，销毁要释放资源，构造会新增分配失败，跨线程使用也可能需要引用计数。原有值语义已经改变。

~~~text
choose_capture(values, required_bytes):
    if required_bytes fits the declared inline bound:
        construct the admitted inline capture
    else:
        reject this representation
        let the caller explicitly choose an external context or other API
~~~

对捕获中的借用指针也不能隐藏 retain。若应用需要拥有外部上下文，应选择有独立构造、复制和销毁契约的表示。把两种对象塞进同一外观却不公开区别，会使清理证明失去前提。

## 6. 容量与执行选择是可观察条件

设生产速率为 `λ`，消费速率为 `μ`，在一段时间内 `λ > μ`。若队列无界增长，积压近似按 `(λ-μ)t` 增加；自动扩容只是推迟内存与延迟问题。有界队列通过 FULL 让应用显式决定拒绝、等待或有截止时间的重试。

这项近似模型不保证每次短时波动都溢出，也不是实际吞吐测量；它说明持续过载不能由分配更多内存根治。第十章的计数守恒还要求被拒绝任务不转移清理责任。

请求并行归约后静默改为顺序执行，即使数值相同，也会改变时延、线程占用和截止时间。正确控制流保留选择结果：

~~~text
result = try_requested_backend(plan, policy)
if result is unsupported or rejected:
    report it to the policy owner
    only an explicit policy decision may start another execution
~~~

不能在不清楚第一轮是否产生外部效果时直接重跑。回退策略必须同时规定重试资格、所有权和可观察结果，而不只是换一个函数名。

## 7. 保持组件职责可解释

CMeta 保存本地类型和调用事实，DataBind 保存逻辑契约，传输适配器解释 HTTP 或 RPC 地址。向 CMeta 加入 JSON 字段语法，或让 Executor 自动重试业务请求，会把具体领域策略藏进多个使用方共享的底层。

判断一个新字段是否进入公共层，可以检查它是否被独立使用方以相同含义使用，以及移除它后底层契约是否仍完整。只有一个应用需要的补偿流程可以先留在应用中。复用底层机制不要求底层接管上层语义。

动态边界适合 `{self, vtable}`，例如可替换 Publisher 或 Plugin 提供方；内部已知调用可以保持直接 C。计划也可能保留必要的间接分派，是否值得消除要根据第七章的测量，不能仅因“统一接口”强制所有路径间接化。

## 8. 验证成本与设计练习

| 新增主张 | 要承担的验证 |
|---|---|
| 生成声明正确 | 编译成功和预期编译失败例 |
| 跨 TU/DSO 身份一致 | 独立表示和动态库测试 |
| 固定资源与单次清理 | 容量边界、失败路径与生存期检查 |
| 优化保持语义 | 明确前提的证明及差分执行 |
| 安装后可用 | 独立使用方构建 |
| 执行更快 | 相同输入和配置的基线测量 |

给第一节增加“每个输出通知一次回调”的需求。若通知有外部效果，第一次通知后第二次失败就不再满足原来的输出原子性。请分别设计“全部计算后统一通知”和“允许部分进度并返回已提交数”的契约，并指出各自新增的暂存空间和重试条件。

这个练习表明，抽象的成本不仅是多几个结构体，还包括调用者今后能够依赖什么。保留哪个方案，应由真实使用方式和可验证条件决定。

## 9. 小结

普通 C 基线使新增机制的收益可以比较。宏解决声明生成，描述符解决共享事实，运行对象解决明确的状态与生存期问题；它们各有适用条件。固定容量、显式失败和公开的后端选择让这些条件持续可检查，隐藏分配与静默重试则会改变已有证明和清理责任。
