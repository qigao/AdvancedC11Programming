# 第二章：有限元编程：泛型、结构体、特征与类型关系

字段列表和参数列表常被重复用于声明、类型检查和反射。如果每个使用方都自行拆解列表，它们可能对元素个数、字段位置和分隔符产生不同理解。本章建立 CMeta 的有限预处理内核，展示同一组声明怎样生成不同代码，并用唯一匹配与结构化身份规则约束泛型和类型关系。

**术语说明：** tuple（元组）是按位置组织的一组元素，例如 `(int, value, flags)`；这里是预处理器记号组成的行，不是运行时容器。projection（投影）指选取或按规则映射其中的信息，例如从这一行取出类型和名字生成声明。

## 1. 先看一份字段事实怎样被重复消费

假设一个程序既需要 `User` 的 C 声明，又需要字段名表。最直接的写法会把 `id` 和 `score` 手写两次：一次写进 `struct`，一次写进元数据数组。字段一旦重命名或增删，两份代码就可能漂移。

先不用 CMeta，只用普通 C11 宏把“字段列表”提升成一份事实：

~~~c
#include <stddef.h>
#include <stdio.h>

#define USER_FIELDS(X) \
    X(int, id)         \
    X(double, score)

#define DECL_FIELD(type, name) type name;
#define FIELD_NAME(type, name) #name,

typedef struct User {
    USER_FIELDS(DECL_FIELD)
} User;

static const char *const User_field_names[] = {
    USER_FIELDS(FIELD_NAME)
};

int main(void)
{
    User u = { .id = 7, .score = 9.5 };

    printf("%s=%d %s=%.1f\n",
           User_field_names[0], u.id,
           User_field_names[1], u.score);
    return 0;
}
~~~

这段程序的关键不在宏语法，而在依赖关系：

~~~text
USER_FIELDS
    |
    +--> native field declarations
    '--> field-name metadata
~~~

`USER_FIELDS` 是唯一需要人工维护的字段集合；两个使用方只是机械投影。新增 `X(long, generation)` 后，声明与字段名表会同时得到第三项。

但这个小例子也暴露出下一层问题。项目一旦有很多类似声明，每个子系统都可能重新实现 `FOR_EACH`、参数计数、tuple 拆分、逗号处理和空参数规则。重复没有消失，只是从业务字段移动到了 macro infrastructure。CMeta 因此不为每个 DSL 复制一套宏技巧，而是把这些机械操作收敛为一个**有限、显式、有边界**的 PP/compiler kernel；Generic、Struct、Traits 和后续 Function 声明只负责描述各自的语义事实。

## 2. Production PP kernel 首先必须 finite

CMeta 当前的 canonical map 入口包括：

~~~c
CMETA_PP_MAP(M, C, a, b, c)
CMETA_PP_MAP_N(3, M, C, a, b, c)

CMETA_PP_MAP_COMMA_N(...)
CMETA_PP_MAP_SEMI_N(...)
CMETA_PP_MAP_PREFIX_COMMA_N(...)
~~~

平铺 type/name pair 也由同一个有限 kernel 消费：

~~~c
CMETA_PP_PAIR_MAP_N(
    2,
    EMIT_PARAM,
    context,
    int, fd,
    size_t *, written
)
~~~

mapper 只描述一个 item：

~~~c
#define EMIT_PARAM(type, name, context) type name
~~~

于是同一组参数 facts 可以投影为：

~~~text
int, fd, size_t *, written
            |
            v
      finite pair map
       |      |      |
       v      v      v
 prototype metadata arguments
~~~

当前这些 map 明确以 0–16 项为边界。有限带来的是可验证性：

~~~text
finite expansion
    -> bounded compile behavior

explicit arity
    -> testable failure boundary

shared map
    -> no per-DSL R0..R16 family
~~~

生产核心不需要把 DEFER / OBSTRUCT / EVAL 递归宏机器当成基础设施。

## 3. Separator 与元组 projection 属于 kernel

如果 mapper 自己负责逗号和分号，很快会出现：

~~~text
EMIT_PARAM
EMIT_PARAM_COMMA
EMIT_PARAM_FIRST
EMIT_PARAM_LAST
EMIT_PARAM_SEMI
~~~

因此 separator policy 由共享 map 提供：

~~~c
CMETA_PP_MAP_COMMA(...)
CMETA_PP_MAP_SEMI(...)
CMETA_PP_MAP_PREFIX_COMMA(...)
~~~

同样，canonical 声明行不应该由每个使用方手工拆位置。例如 function 参数的内部声明行可以是：

~~~text
(type, name, flags, descriptor, carrier)
~~~

共享元组 primitive：

~~~c
CMETA_PP_TUPLE_GET_0(row)
CMETA_PP_TUPLE_GET_1(row)
CMETA_PP_TUPLE_GET_2(row)
CMETA_PP_TUPLE_HEAD(row)
CMETA_PP_TUPLE_TAIL(row)
CMETA_PP_TUPLE_APPLY(M, row)
~~~

让同一声明行被多个使用方使用：

~~~text
parameter row
      |
      +--> native declaration
      +--> FunctionDesc
      +--> ABI validation
      '--> exact adapter
~~~

参数个数与声明行 position 是共享 data contract，不应该编码进每个 DSL 的宏名。

## 4. Token predicate 不是 C type system

PP 层可以提供：

~~~c
CMETA_PP_BOOL(x)
CMETA_PP_NOT(x)
CMETA_PP_AND(a, b)
CMETA_PP_OR(a, b)
CMETA_PP_IF(x)
CMETA_PP_WHEN(x)

CMETA_PP_IS_VOID(x)
~~~

但它只能回答有限 token 问题。

~~~text
CMETA_PP_IS_VOID(void)
    -> token predicate

typedef void nothing;
CMETA_PP_IS_VOID(nothing)
    -> 不是通用 C type introspection
~~~

所以必须区分：

~~~text
PP token relation
        !=
native compiler type relation
        !=
CMeta semantic identity
~~~

编译器-本地类型 reasoning 属于 CMETA_NATIVE_TYPEOF / CMETA_SAME_TYPE 一层。CMeta 描述符 selection 则使用 CMETA_TYPEOF(T)。两种 typeof 不是一个概念：

~~~text
CMETA_NATIVE_TYPEOF(expr)
    -> C compiler native type

CMETA_TYPEOF(T)
    -> CMeta semantic descriptor
~~~

## 5. Zero arguments 与 unique name 都必须有明确边界

空 variadic 参数是 portability 高风险区。只有 capability：

~~~c
CMETA_HAS_VA_OPT
~~~

成立时，才开放标准 zero-safe 入口，例如：

~~~c
CMETA_PP_NARG_ZERO(...)
CMETA_PP_MAP_ZERO(...)
CMETA_PP_MAP_COMMA_ZERO(...)
CMETA_PP_PREFIX_COMMA(...)
~~~

严格 C11 可以继续使用显式 count：

~~~c
CMETA_PP_MAP_N(0, M, C, )
~~~

规则是：

~~~text
compiler happens to accept an extension
        !=
library promises that capability
~~~

生成局部名字也一样：

~~~c
CMETA_PP_UNIQUE(cmeta_scope_)
~~~

它解决的是 same-TU lexical naming。它不定义：

- cross-TU type identity
- Plugin contract identity
- schema order
- resource order

所以：

~~~text
unique token != semantic stable ID
~~~

## 6. Generic 只是 kernel 的一个使用方

旧模型容易把一个入口越做越大：

~~~text
typed(...)
    -> container?
    -> callable?
    -> operator?
    -> another DSL?
~~~

CMeta 当前 canonical Generic 入口已经收窄为：

~~~c
cmeta_type(List, IntList, int);
cmeta_type(Vec, IntVec, int);
~~~

它只接受注册过的 finite generic kind。

~~~text
registered(kind)
        |
        v
cmeta_type(kind, Name, T)
        |
        v
concrete ordinary-C type

unregistered(kind)
        |
        v
compile failure
~~~

因此 Generic 不再是 universal token router。它只是：

有限 Generic kind 到 concrete C 声明的明确映射。调用端仍然使用普通 concrete API：

~~~c
IntList list = {0};
IntList_push_back(&list, 10);
~~~

Generic 不需要运行时 template engine。

## 7. Macro 应生成小的 typed facade，不应复制整个算法

**Façade（外观接口，也写作 facade）**是在已有实现前提供的薄接口。这里的 typed façade 用具体 C 类型做检查和转发，让共享实现继续负责算法。

Generic 声明的典型构建期结果是：

~~~text
cmeta_type(List, IntList, int)
        |
        +--> concrete C type
        +--> canonical metadata
        '--> small typed wrappers
~~~

有类型的包装函数可以概念化为：

~~~c
static inline cmeta_status
IntList_push(IntList *self, int value)
{
    return list_push_raw(
        &self->raw,
        &value,
        sizeof(value),
        CMETA_TYPEOF(int));
}
~~~

真正的 allocation / growth / move algorithm 应尽量 compiled once。所以：

~~~text
macro generation
    -> declaration / small wrapper

runtime algorithm
    -> shared ordinary C
~~~

这是避免 Generic 变成 code-bloat 生成器的关键。

## 8. Struct：只有需要 structural 元数据时才提升字段事实

普通 C 永远可以直接写：

~~~c
typedef struct User {
    int id;
    double score;
} User;
~~~

只有 C code 使用它时，停在这里。当多个使用方需要字段 facts，可以写：

~~~c
cmeta_struct(User,
    cmeta_field(int, id)
    cmeta_field(double, score)
);
~~~

同一组 facts 生成：

~~~text
native struct declaration
        +
field metadata
        +
layout proof
        +
inline metadata accessor
~~~

编译期证明会检查真实 native layout，例如：

为了看清“layout proof”到底证明什么，可以先把宏想象成下面这种 **teaching expansion**。这不是固定快照中描述符结构的逐字源码，而是只保留原生声明和编译期约束的等价教学形状：

~~~c
#include <stddef.h>

typedef struct User {
    int id;
    double score;
} User;

_Static_assert(
    _Generic(&((User *)0)->id,
             int *: 1,
             default: 0),
    "User.id type mismatch");

_Static_assert(
    _Generic(&((User *)0)->score,
             double *: 1,
             default: 0),
    "User.score type mismatch");

_Static_assert(
    offsetof(User, id) + sizeof(((User *)0)->id)
        <= sizeof(User),
    "User.id outside owner layout");

_Static_assert(
    offsetof(User, score) + sizeof(((User *)0)->score)
        <= sizeof(User),
    "User.score outside owner layout");
~~~

这里没有运行时反射查询。字段类型由编译器的原生类型系统检查，offset/size 约束由 `_Static_assert` 在翻译期拒绝。真正的 CMeta 生成器再把同一份字段事实投影到字段描述符和 accessor，因此“声明”和“元数据”不是两份独立手写 schema。


~~~text
declared field type
        ==
actual member type

offset + size
        within owner
~~~

所以元数据不是第二份手写 schema。

### 已有本地类型不必重写

现实项目中可能已经有：

~~~c
typedef struct Account {
    int id;
    double balance;
} Account;
~~~

可以外部投影：

~~~c
cmeta_reflect_data(Account, "app.Account",
    cmeta_field(int, id)
    cmeta_field(double, balance)
);
~~~

关系是：

~~~text
existing native type
        +
selected field facts
        |
        v
semantic projection
~~~

而不是反射接管本地类型的所有权。

## 9. Traits：flag 与回调必须来自同一事实

脆弱设计会写两次：

~~~c
traits.flags =
    CMETA_TRAIT_EQUAL |
    CMETA_TRAIT_HASH;

traits.equal = user_equal;
traits.hash = user_hash;
~~~

canonical row：

~~~c
cmeta_traits(User,
    (equal, user_equal),
    (hash, user_hash)
);
~~~

同一个声明行：

~~~text
(equal, user_equal)
        |
        +--> CMETA_TRAIT_EQUAL
        '--> .equal = user_equal
~~~

生成器可以在编译时拒绝：

- duplicate trait
- unknown trait
- callback signature mismatch

而不是把错误留成：

~~~text
flag says HASH
but hash callback == NULL
~~~

Traits 是 finite capability 元数据，不是 dynamic object hierarchy。

## 10. TypeFunction：有限类型关系首先是 token-keyed compile-time relation

有些共享事实写成有限关系：

~~~text
f(T1, T2) = T3
~~~

例如：

~~~c
TypeFunction(CommonArithmetic,
    (int, int, int),
    (int, double, double),
    (double, int, double),
    (double, double, double)
);

typedef TypeEval(CommonArithmetic, int, double) result_type;
~~~

这里的 `result_type` 是 `double`。固定 Salts 快照中的实现不是运行时查表，也不是按 C 的类型兼容关系搜索。每一行先生成一个由**输入 token**组成的 `typedef` 名，二元关系的教学展开近似为：

~~~c
typedef double cmeta_type_fn_CommonArithmetic_2_int_double;
~~~

而：

~~~c
TypeEval(CommonArithmetic, int, double)
~~~

只会重新拼出 `cmeta_type_fn_CommonArithmetic_2_int_double`。所以 compile-time key 是预处理器 token，不是“经过 typedef 展开后的语义类型”。

这可以直接形成一组 compile matrix：

| 情况 | 例子 | 预期 |
|---|---|---|
| 已声明 key | `TypeEval(F, int, double)` | compile-pass |
| 缺失 key | `TypeEval(F, float, double)` | compile-fail：引用未声明 typedef |
| typedef alias 作为不同 token | `typedef int my_int; TypeEval(F, my_int, double)` | 若只声明了 `int` key，则 compile-fail |
| 同一 key、同一 result 重复 | 两次 `(int, double, double)` | C11 下可以 compile-pass |
| 同一 key、不同 result 冲突 | `(int, double, double)` 与 `(int, double, long)` | compile-fail：同名 typedef 类型冲突 |

最后两项尤其重要。下面两行：

~~~c
TypeFunction(SameResult,
    (int, double, double),
    (int, double, double)
);
~~~

会产生等价于：

~~~c
typedef double cmeta_type_fn_SameResult_2_int_double;
typedef double cmeta_type_fn_SameResult_2_int_double;
~~~

C11 允许在同一作用域把 typedef 名重新定义为它当前表示的同一非 variably-modified 类型，因此**不能声称 `TypeFunction` 自己会拒绝所有 duplicate rows**。若项目要求“任何重复输入行都非法”，必须在更高一层 schema/生成器校验中显式检查。

相反：

~~~c
TypeFunction(Conflict,
    (int, double, double),
    (int, double, long)
);
~~~

会尝试让同一个 token-keyed typedef 名同时表示 `double` 与 `long`，编译器必须拒绝。

因此这一层的准确 contract 是：

~~~text
finite token rows
    |
    +--> one generated typedef name per token key
    |
    +--> TypeEval composes that same name
    |
    +--> missing key / conflicting result fail at translation
    |
    '--> identical duplicate needs separate schema rejection
         if the project forbids duplicates
~~~

如果同一批事实还需要运行时 inference，应显式投影：

~~~c
InferenceRules(common_type_relation, CommonRows);
~~~

正确因果链是：

~~~text
canonical finite rows
      |
      +--> compile-time TypeFunction / TypeEval
      '--> explicit runtime inference projection
~~~

不是 TypeFunction 偷偷拥有运行时 registry。
## 11. Semantic identity 不等于描述符 address

不同 TU 可以拥有不同描述符 object。因此：

~~~text
descriptor address equality
        !=
semantic type identity
~~~

对于 Generic application，概念 identity 来自：

~~~text
generic constructor stable identity
        +
argument semantic identities
~~~

例如：

~~~text
List<int>
    =
List stable generic owner
    +
int semantic identity
~~~

这条规则以后会进入 Multi-TU、DSO、Plugin 与 installed 使用方。CMETA_PP_UNIQUE 产生的唯一 token 同样不能替代 semantic stable ID。

**结构化身份的推导。** 令 `Atom(id)` 表示以稳定标识命名的基本类型，`Apply(k, args)` 表示构造器 `k` 应用于一组类型参数。这里给出用于理解身份比较的有限、无环模型；它是教学伪代码，不是当前 CMeta 比较函数的源码。

~~~text
same_type(a, b):
    if a.kind != b.kind: return false
    if a.kind == ATOM: return a.stable_id == b.stable_id
    if a.constructor_id != b.constructor_id: return false
    if a.argument_count != b.argument_count: return false
    for each corresponding argument pair (x, y):
        if not same_type(x, y): return false
    return true
~~~

假设稳定标识在约定命名域内没有冲突，并且类型应用形成有限无环树。以树高归纳：高度为零时，相同基本类型具有相同稳定标识；高度增加时，相同构造器、相同参数个数以及逐项相等的子身份使比较返回真。比较全过程没有使用描述符地址，因此移动描述符或在另一翻译单元复制它不会改变模型中的类型身份。这项推导只说明身份关系，不证明两个声明具有相同布局或清理协议。若调用方依赖这些性质，还必须检查对应描述事实；实际实现还需通过跨翻译单元及动态库测试。

## 12. 为什么不能合成一个万能 DSL

到这里已经有：

~~~text
PP map / tuple kernel
compiler capabilities
cmeta_type
cmeta_struct
cmeta_reflect_data
cmeta_traits
TypeFunction
~~~

可以共享 implementation mechanics，但不能共享一个万能 semantic authority。

| 入口 | 声明的事实 |
|---|---|
| cmeta_type | finite generic application |
| cmeta_struct | native 声明 + structure |
| cmeta_reflect_data | existing native data projection |
| cmeta_traits | finite capability set |
| TypeFunction | finite 类型关系 |
| PP/编译器 kernel | mechanical generation capability |

所以正确设计是：

~~~text
shared mechanics
      |
      v
separate semantic entry points
~~~

而不是：

~~~text
OneMetaThing(...)
    -> guess everything
~~~

## 13. Engineering Evidence

这一层主要由 toolchain 证据负责。

### Compile-pass

~~~text
registered generic kind
valid Struct rows
valid Traits rows
valid TypeFunction rows
    -> compile
~~~

### Compile-fail

~~~text
unregistered generic kind
wrong field type
duplicate trait
wrong callback type
unsupported relation
arity beyond finite bound
    -> fail early
~~~

### Preprocess

~~~bash
cc -E sample.c
~~~

应该能看到：

~~~text
finite rows
    -> ordinary C declarations
    -> static metadata
    -> small typed facade
~~~

### Multi-TU

语义身份不能依赖描述符 pointer equality。

### Code size

生成 wrapper 应该小；大型算法不应按每个 concrete type 完整复制。

## 14. 小结

有限映射统一处理参数个数、分隔符和元组位置，使 Generic、Struct、Traits 和类型关系可以共享展开机制。每个入口仍需验证自己的声明规则：未知泛型种类、重复关系行、错误回调签名和超出容量的输入都应在规定边界拒绝。类型身份由构造器和参数的语义身份决定，描述符地址只表示当前存储位置。这使同一类型能跨翻译单元被识别，也为下一章共享函数参数事实提供基础。
