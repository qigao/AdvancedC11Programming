# 第二章：有限元编程内核——Generic、Struct、Traits 与类型关系

> **本章只回答一个问题：**
>
> 当 Generic、Struct、Traits、Function declaration 和 compiler 都需要相同的 tuple、arity、type selection 与 schema replay 时，怎样让它们共享一套有限 kernel，而不是各自发明一套宏语言？

---

## 1. 重复不能只是从业务代码移动到 macro infrastructure

第一章建立了工具分工：

~~~text
function / static inline
    -> typed behavior

macro / PP
    -> tokens / declarations / schema replay

compiler capability
    -> native compile-time facts

Reflection
    -> stable semantic truth
~~~

但如果每个上层模块都自己实现：

~~~text
NARG
CAT
FOR_EACH
tuple extraction
arity dispatch
comma placement
zero-argument handling
~~~

重复仍然存在，只是换了位置。

所以这一章不发明更大的 DSL，而是建立：

~~~text
small finite PP/compiler kernel
            |
            v
reusable row projection
            |
       +----+-----+------+
       |          |      |
    Generic     Struct  Traits ...
~~~

上层 declaration 只描述自己的 semantic facts。

---

## 2. Production PP kernel 首先必须 finite

CMeta 当前的 canonical map 入口包括：

~~~c
CMETA_PP_MAP(M, C, a, b, c)
CMETA_PP_MAP_N(3, M, C, a, b, c)

CMETA_PP_MAP_COMMA_N(...)
CMETA_PP_MAP_SEMI_N(...)
CMETA_PP_MAP_PREFIX_COMMA_N(...)
~~~

平铺 type/name pair 也由同一个有限 kernel 消费：

~~~c
CMETA_PP_PAIR_MAP_N(
    2,
    EMIT_PARAM,
    context,
    int, fd,
    size_t *, written
)
~~~

mapper 只描述一个 item：

~~~c
#define EMIT_PARAM(type, name, context) type name
~~~

于是同一组参数 facts 可以投影为：

~~~text
int, fd, size_t *, written
            |
            v
      finite pair map
       |      |      |
       v      v      v
 prototype metadata arguments
~~~

当前这些 map 明确以 0–16 项为边界。

有限带来的是可验证性：

~~~text
finite expansion
    -> bounded compile behavior

explicit arity
    -> testable failure boundary

shared map
    -> no per-DSL R0..R16 family
~~~

生产核心不需要把 DEFER / OBSTRUCT / EVAL 递归宏机器当成基础设施。

---

## 3. Separator 与 tuple projection 属于 kernel

如果 mapper 自己负责逗号和分号，很快会出现：

~~~text
EMIT_PARAM
EMIT_PARAM_COMMA
EMIT_PARAM_FIRST
EMIT_PARAM_LAST
EMIT_PARAM_SEMI
~~~

因此 separator policy 由共享 map 提供：

~~~c
CMETA_PP_MAP_COMMA(...)
CMETA_PP_MAP_SEMI(...)
CMETA_PP_MAP_PREFIX_COMMA(...)
~~~

同样，canonical row 不应该由每个 consumer 手工拆位置。

例如 function parameter 的内部 row 可以是：

~~~text
(type, name, flags, descriptor, carrier)
~~~

共享 tuple primitive：

~~~c
CMETA_PP_TUPLE_GET_0(row)
CMETA_PP_TUPLE_GET_1(row)
CMETA_PP_TUPLE_GET_2(row)
CMETA_PP_TUPLE_HEAD(row)
CMETA_PP_TUPLE_TAIL(row)
CMETA_PP_TUPLE_APPLY(M, row)
~~~

让同一 row 被多个 consumer 使用：

~~~text
parameter row
      |
      +--> native declaration
      +--> FunctionDesc
      +--> ABI validation
      '--> exact adapter
~~~

> **arity 与 row position 是共享 data contract，不应该编码进每个 DSL 的宏名。**

---

## 4. Token predicate 不是 C type system

PP 层可以提供：

~~~c
CMETA_PP_BOOL(x)
CMETA_PP_NOT(x)
CMETA_PP_AND(a, b)
CMETA_PP_OR(a, b)
CMETA_PP_IF(x)
CMETA_PP_WHEN(x)

CMETA_PP_IS_VOID(x)
~~~

但它只能回答有限 token 问题。

~~~text
CMETA_PP_IS_VOID(void)
    -> token predicate

typedef void nothing;
CMETA_PP_IS_VOID(nothing)
    -> 不是通用 C type introspection
~~~

所以必须区分：

~~~text
PP token relation
        !=
native compiler type relation
        !=
CMeta semantic identity
~~~

compiler-native type reasoning 属于 CMETA_NATIVE_TYPEOF / CMETA_SAME_TYPE 一层。

CMeta descriptor selection 则使用 CMETA_TYPEOF(T)。

两种 typeof 不是一个概念：

~~~text
CMETA_NATIVE_TYPEOF(expr)
    -> C compiler native type

CMETA_TYPEOF(T)
    -> CMeta semantic descriptor
~~~

---

## 5. Zero arguments 与 unique name 都必须有明确边界

空 variadic 参数是 portability 高风险区。

只有 capability：

~~~c
CMETA_HAS_VA_OPT
~~~

成立时，才开放标准 zero-safe 入口，例如：

~~~c
CMETA_PP_NARG_ZERO(...)
CMETA_PP_MAP_ZERO(...)
CMETA_PP_MAP_COMMA_ZERO(...)
CMETA_PP_PREFIX_COMMA(...)
~~~

严格 C11 可以继续使用显式 count：

~~~c
CMETA_PP_MAP_N(0, M, C, )
~~~

规则是：

~~~text
compiler happens to accept an extension
        !=
library promises that capability
~~~

生成局部名字也一样：

~~~c
CMETA_PP_UNIQUE(cmeta_scope_)
~~~

它解决的是 same-TU lexical naming。

它不定义：

~~~text
cross-TU type identity
Plugin contract identity
schema order
resource order
~~~

所以：

~~~text
unique token != semantic stable ID
~~~

---

## 6. Generic 只是 kernel 的一个 consumer

旧模型容易把一个入口越做越大：

~~~text
typed(...)
    -> container?
    -> callable?
    -> operator?
    -> another DSL?
~~~

CMeta 当前 canonical Generic 入口已经收窄为：

~~~c
cmeta_type(List, IntList, int);
cmeta_type(Vec, IntVec, int);
~~~

它只接受注册过的 finite generic kind。

~~~text
registered(kind)
        |
        v
cmeta_type(kind, Name, T)
        |
        v
concrete ordinary-C type

unregistered(kind)
        |
        v
compile failure
~~~

因此 Generic 不再是 universal token router。

它只是：

> **有限 Generic kind 到 concrete C declaration 的明确映射。**

调用端仍然使用普通 concrete API：

~~~c
IntList list = {0};
IntList_push_back(&list, 10);
~~~

Generic 不需要 runtime template engine。

---

## 7. Macro 应生成小的 typed facade，不应复制整个算法

Generic declaration 的典型 build-time 结果是：

~~~text
cmeta_type(List, IntList, int)
        |
        +--> concrete C type
        +--> canonical metadata
        '--> small typed wrappers
~~~

typed wrapper 可以概念化为：

~~~c
static inline cmeta_status
IntList_push(IntList *self, int value)
{
    return list_push_raw(
        &self->raw,
        &value,
        sizeof(value),
        CMETA_TYPEOF(int));
}
~~~

真正的 allocation / growth / move algorithm 应尽量 compiled once。

所以：

~~~text
macro generation
    -> declaration / small wrapper

runtime algorithm
    -> shared ordinary C
~~~

这是避免 Generic 变成 code-bloat generator 的关键。

---

## 8. Struct：只有需要 structural metadata 时才提升字段事实

普通 C 永远可以直接写：

~~~c
typedef struct User {
    int id;
    double score;
} User;
~~~

只有 C code 使用它时，停在这里。

当多个 consumer 需要 field facts，可以写：

~~~c
cmeta_struct(User,
    cmeta_field(int, id)
    cmeta_field(double, score)
);
~~~

同一组 facts 生成：

~~~text
native struct declaration
        +
field metadata
        +
layout proof
        +
inline metadata accessor
~~~

compile-time proof 会检查真实 native layout，例如：

~~~text
declared field type
        ==
actual member type

offset + size
        within owner
~~~

所以 metadata 不是第二份手写 schema。

### 已有 native type 不必重写

现实项目中可能已经有：

~~~c
typedef struct Account {
    int id;
    double balance;
} Account;
~~~

可以外部投影：

~~~c
cmeta_reflect_data(Account, "app.Account",
    cmeta_field(int, id)
    cmeta_field(double, balance)
);
~~~

关系是：

~~~text
existing native type
        +
selected field facts
        |
        v
semantic projection
~~~

而不是 Reflection 接管 native type 的所有权。

---

## 9. Traits：flag 与 callback 必须来自同一事实

脆弱设计会写两次：

~~~c
traits.flags =
    CMETA_TRAIT_EQUAL |
    CMETA_TRAIT_HASH;

traits.equal = user_equal;
traits.hash = user_hash;
~~~

canonical row：

~~~c
cmeta_traits(User,
    (equal, user_equal),
    (hash, user_hash)
);
~~~

同一个 row：

~~~text
(equal, user_equal)
        |
        +--> CMETA_TRAIT_EQUAL
        '--> .equal = user_equal
~~~

generator 可以在 compile time 拒绝：

~~~text
duplicate trait
unknown trait
callback signature mismatch
~~~

而不是把错误留成：

~~~text
flag says HASH
but hash callback == NULL
~~~

Traits 是 finite capability metadata，不是 dynamic object hierarchy。

---

## 10. TypeFunction：有限类型关系也是 semantic fact

有些知识不是字段，而是：

~~~text
f(T1, T2) = T3
~~~

例如：

~~~c
TypeFunction(CommonArithmetic,
    (int, int, int),
    (int, double, double),
    (double, int, double),
    (double, double, double)
);
~~~

使用：

~~~c
typedef TypeEval(CommonArithmetic, int, double) result_type;
~~~

语义是：

~~~text
lookup(CommonArithmetic, int, double)
    = exactly one row
    -> double
~~~

失败也应该确定：

~~~text
no row
    -> unsupported

duplicate / ambiguous row
    -> invalid definition
~~~

它不是 best-effort implicit conversion，也不是隐藏的 template specialization system。

如果同一批 row 还需要 runtime inference，应显式投影：

~~~c
InferenceRules(common_type_relation, CommonRows);
~~~

正确因果链是：

~~~text
canonical finite rows
      |
      +--> compile-time TypeFunction / TypeEval
      '--> explicit runtime inference projection
~~~

不是 TypeFunction 偷偷拥有 runtime registry。

---

## 11. Semantic identity 不等于 descriptor address

不同 TU 可以拥有不同 descriptor object。

因此：

~~~text
descriptor address equality
        !=
semantic type identity
~~~

对于 Generic application，概念 identity 来自：

~~~text
generic constructor stable identity
        +
argument semantic identities
~~~

例如：

~~~text
List<int>
    =
List stable generic owner
    +
int semantic identity
~~~

这条规则以后会进入 Multi-TU、DSO、Plugin 与 installed consumer。

CMETA_PP_UNIQUE 产生的唯一 token 同样不能替代 semantic stable ID。

---

## 12. 为什么不能合成一个万能 DSL

到这里已经有：

~~~text
PP map / tuple kernel
compiler capabilities
cmeta_type
cmeta_struct
cmeta_reflect_data
cmeta_traits
TypeFunction
~~~

可以共享 implementation mechanics，但不能共享一个万能 semantic authority。

| 入口 | 声明的事实 |
|---|---|
| cmeta_type | finite generic application |
| cmeta_struct | native declaration + structure |
| cmeta_reflect_data | existing native data projection |
| cmeta_traits | finite capability set |
| TypeFunction | finite type relation |
| PP/compiler kernel | mechanical generation capability |

所以正确设计是：

~~~text
shared mechanics
      |
      v
separate semantic entry points
~~~

而不是：

~~~text
OneMetaThing(...)
    -> guess everything
~~~

---

## 13. Engineering Evidence

这一层主要由 toolchain 证据负责。

### Compile-pass

~~~text
registered generic kind
valid Struct rows
valid Traits rows
valid TypeFunction rows
    -> compile
~~~

### Compile-fail

~~~text
unregistered generic kind
wrong field type
duplicate trait
wrong callback type
unsupported relation
arity beyond finite bound
    -> fail early
~~~

### Preprocess

~~~bash
cc -E sample.c
~~~

应该能看到：

~~~text
finite rows
    -> ordinary C declarations
    -> static metadata
    -> small typed facade
~~~

### Multi-TU

semantic identity 不能依赖 descriptor pointer equality。

### Code size

生成 wrapper 应该小；大型算法不应按每个 concrete type 完整复制。

## 14. What We Learned

这一章没有建立 C template system。

建立的是：

~~~text
finite PP/compiler kernel
          |
          v
 reusable row projection
          |
   +------+------+------+
   |      |      |      |
Generic Struct Traits Relation
   |      |      |      |
   +------+------+------+
          |
          v
 ordinary C + metadata
~~~

最重要的迁移是：

~~~text
historical:
typed(...)
    = universal routing surface

current:
cmeta_type(...)
    = finite Generic only
~~~

以及：

> **共享 macro mechanics，不等于共享 semantic authority。**

下一章把这条原则应用到 function：让 declaration、FunctionDesc、receiver metadata 和 executable projection 共享事实，但仍然保持“描述函数”和“执行函数”是两件不同的事。
